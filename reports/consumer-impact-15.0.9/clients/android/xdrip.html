    xDrip+ (Android): Nightscout API usage (15.0.9 consumer impact)¶

    Living document, last changed 2026-09-23 at 64007ffc.

    All claims are read-derived: taken from the source with git grep / git show. Nothing was built or run, and nothing was sent to any server.
    repo externals/xDrip (NightscoutFoundation/xDrip)
    ref analysed origin/master 1ed760048, 2026-09-18 (release tags up to 2026.09.18 exist)
    development branch none: git branch -r has no dev. The other remote branches are topic branches and were not analysed
    local staleness local HEAD 1e86d9a2a is 277 behind origin/master and the working tree has 200 modified files. The working tree was not read; everything below is from origin/master
    server refs compared against cgm-remote-monitor origin/master 92d08342 (15.0.8), ef3404fd (#8754), 6d120fa2 (#8758)

    xDrip talks to Nightscout in three ways:

    1. REST uploader (NightscoutUploader, Retrofit 2.9.0 / OkHttp 5.3.2). The base URL takes the form https://<secret>@host/api/v1/, and the secret is sent SHA-1 hashed in the api-secret header.
    2. "Nightscout follow" collector (cgm/nsfollow/*, Retrofit).
    3. An optional direct MongoDB uploader (cloud_storage_mongodb_enable), which bypasses the Nightscout API entirely and is out of scope.

    It has no socket.io client. It also hosts its own local web service that emulates Nightscout endpoints (webservices/*); that is a server, not a consumer, and is out of scope.

    S5 auth The header api-secret: sha1(secret) is taken from the URL userinfo, on both the uploader and the follower. There is no token=, no JWT, no /api/v2/authorization, no subject or role editing, and no X-Forwarded-For. With no secret, the follower sends no header (a Retrofit null header is dropped), so an AUTH_DEFAULT_ROLES=denied site answers 401 on 15.0.8 as it will on 15.0.9. On 401/403: the uploader throws UploaderException, which handleRestFailure counts. A "Nightscout Failure" notification appears only after about 24 h of failures, and only if warn_nightscout_failures is on. The follower shows the callback status text. A devicestatus 4xx suppresses devicestatus polling for 6 h (S15). Slow auth replies are bounded by OkHttp timeouts, and the candidate no longer delays correct-secret requests.     S6 websocket None found. There is no socket.io library in app/build.gradle and no socket code. AUTH_DEFAULT_ROLES=denied affects xDrip only through REST (S5). (absence) socket\.io, io\.socket, engineio, "authorize", loadRetro, dataUpdate
    S7 own _id Treatments: xDrip sends its own _id on PUT /api/v1/treatments, one record per request, with _id = uuid_to_id(uuid). The rule is: a UUID has its dashes removed and the first 24 lowercase hex characters kept; an id containing : or shorter than 24 characters becomes the first 24 hex characters of its MD5 (lowercase); a 24-character id is used as is. The request body also carries uuid. The response _id is not read back. Deletes use DELETE /api/v1/treatments/<24-char id>. The id is either the queue's reference_uuid when that is 24 characters long, or it comes from GET treatments.json?find[uuid]=<uuid> followed by reading [0]._id. The Nightscout backfill screen re-queues every treatment as update, so it relies on the server upserting by _id. On the server: 15.0.8 already turns a 24-hex _id on PUT into an ObjectId (normalizeTreatmentId, lib/server/treatments.js@92d08342:394-410). But a treatment that ≤15.0.6 stored with a string _id gets an ObjectId copy beside it on the next PUT, and a DELETE by hex id misses the string copy. #8758 (6d120fa2) matches both forms and deletes the stale string copy (treatments.js@6d120fa2:160-171,276-280). xDrip is a direct beneficiary of #8758, and the reason it needs it. Entries, devicestatus, and activity are POSTed with no _id; entries rely on server dedup by date+type. On download, NightscoutTreatments keeps Nightscout's _id and uses uuid if present, otherwise a name-based UUID made from _id. NightscoutUploader.java:148-149,158-159,245-256,810-847,880-903; NightscoutBackfillActivity.java:115-122; NightscoutTreatments.java:40-41 "_id", uuid_to_id, uuid, deleteTreatment, @PUT, @DELETE
    S8 treatment edits Inserts and updates both go through PUT (upsert), one per request; the batched POST path exists but is unused (insert_array is never filled). A delete is a hard v1 DELETE by _id with no count, so the new "delete with bad count is refused" rule does not apply. created_at is the treatment's own string, and timestamp (ms) plus sysTime are also sent. Treatments that came from Nightscout (enteredBy ending "via Nightscout") are not sent back. If the uuid lookup finds nothing, the delete is marked done and not retried.     S15 errors Entries upload: one POST per cycle carries the whole BG, meter, and calibration array. A non-2xx response throws, and uploadRest returns false. UploaderTask then leaves every queue item pending, so the next cycle retries the whole batch indefinitely; data is not marked uploaded. A deterministic 400 on entries would therefore stall BG upload while local data keeps queueing, with only the optional notification after ~24 h. Devicestatus is posted only after entries succeed, and its errors are ignored. Treatments: exceptions are caught and do not fail the entries result. An item that fails stays pending and is retried every cycle, and the throw also stops the treatments after it in that cycle. Follower entries: a failure shows status text and it retries next wake-up; an empty [] is processed as "no new data". Follower devicestatus: any 4xx, including 401 and 403 and not only Juggluco's 400, disables devicestatus polling for 6 h (process lifetime; reset by changing the URL).     Things not analysed, and why¶

    • Topic branches: there is no dev branch. origin/lib_reorg, origin/gradle8 and the others were not diffed.
    • The Mongo direct uploader writes straight to MongoDB and bypasses every API change. Only its existence is noted. The form of its _id values is not established.
    • Server default count for GET /api/v1/treatments with no parameters: the release notes say "as before". This was not re-verified in server code.
