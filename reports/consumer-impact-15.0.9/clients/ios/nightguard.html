    S1–S15¶

    S-id what the client does anchor (nightguard@75404bd) patterns searched
    S1 count Every v1 count is a GET, and each is a literal or a clamped integer: 20 (chart preview), 500 (entries-stream fallback), max(2,min(limit,100)) (hybrid display read, limit defaults to 20), 1440 (day/range reads), 2 (current value), 1 (last sensor/cannula/battery change; last temp target), 5 (devicestatus), 500 (today's treatments). None can be 0, negative, fractional or huge. No count is sent on any write. No DELETE anywhere. NightscoutService.swift:736, :816, :882+:901, :1051, :1503, :1777, :1829, :1983, :2036 "count", count=, count: , DELETE
    S2 find operators v1 fallbacks use find[date][$gt], find[date][$lte], find[created_at][$gte], find[eventType] (plain equality). All are in the allowlist. There is no $exists, no $regex, no $expr, and no pipeline. v3 filters: date$gte, date$lt, type$in, eventType$eq, eventType$in, created_at$gte, all v3 syntax. :1049-1050, :1776, :1828, :2035; v3 :808-810, :1064-1067, :1783-1784, :1835-1836, :2041-2042 find\[, \$exists, \$regex, \$expr, pipeline, \$ne, \$in
    S3 numeric compares The v1 range read sends find[date][$gt] and [$lte] as "\(Double)": epoch-ms built from timeIntervalSince1970*1000, which can carry a fraction (e.g. …123.456 for the "last two hours" window). On 15.0.8 date goes through parseInt (truncates). On the candidate it goes through parseFloat (lib/server/query-coercion.js toNumber, table entries.date: number). Stored date values are whole milliseconds, so the matched set is the same either way. The client also filters the range locally ("older servers ignore date operators") and so does not depend on the old behaviour. Treatment filters use created_at ISO-8601 UTC strings. created_at is not in the coercion table, so nothing changes there. :1043-1051, :1100-1103 (local range filter), :1776, :2035; server cgm-remote-monitor@6d120fa2 lib/server/query-coercion.js:90-97 \$gt, \$gte, \$lt, \$lte, created_at, date
    S4 shared read endpoints GET /api/v1/status.json (units; token in the API-SECRET header). GET /api/v2/properties (IOB, COB, battery and delta enrichment; token in the token= query; any failure is logged and ignored). Not used: /api/v1/count, /times, /slice, /echo, /api/v2/ddata, /verifyauth. :974, :1590-1633 api/v1/status, api/v2/properties, api/v1/count, times, slice, echo, ddata, verifyauth
    S5 auth (a) The JWT comes from GET /api/v2/authorization/request/token=<accessToken>: the literal token= prefix sits in the path segment. The server's findSubject splits on - and matches the last segment against the digest, so the prefix is harmless on 15.0.8 and on the candidate. The JWT is cached per server+token and refreshed once on 401. (b) The v1 fallback sends the raw access token in the API-SECRET header (not hashed). The server accepts this through doesAccessTokenExist(api_secret), unchanged on #8754 head ef3404fd. (c) Other v1/v2 calls append token= to the query. There is no SHA-1 API_SECRET path. Care actions (writing treatments) require a token. 401 and 403 get user-facing messages. There is no special handling for slow auth replies: 20 s timeouts on every read. The client does not set X-Forwarded-For. It does not create subjects or roles. :440-477, :366-376, UserDefaultsRepository.swift:261-286, :219-222; NightscoutService.swift:66-78; server cgm-remote-monitor@ef3404fd lib/authorization/index.js:190-195, storage.js:336-366 api-secret, API-SECRET, sha1, Insecure, token=, Bearer, authorization/request, subjects, roles, X-Forwarded
    S6 websocket None found. No socket.io client. The Package.resolved files list only Firebase and Google packages, and there is no Swift reference to a socket or websocket. Alarms are computed on the device from polled data. nightguard.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved; nightguard.xcworkspace/xcshareddata/swiftpm/Package.resolved socket, SocketIO, SocketManager, Starscream, URLSessionWebSocketTask, websocket, /alarm, dbAdd
    S7 _id New treatments are POSTed through v3 (v1 POST only as a fallback) without _id or identifier, so the server assigns the id. Reads ask for the identifier,_id fields and prefer identifier over _id as the local key. The client does no PUT or DELETE by id and has no upper-case ids. :1927-1960; nightguard/domain/treatment/TreatmentsStream.swift:106-108; NightscoutService.swift:812, :889 "_id", identifier, PUT, PATCH, DELETE
    S8 treatment edits Create only: Temporary Target, Carb Correction, Site/Sensor/Pump-battery change. "Cancel temp target" is a new Temporary Target treatment with duration: 0, not a delete. Each write carries created_at (ISO-8601 UTC), date, mills, app and enteredBy. The v1 fallback POST carries a meaningless now= query value (the description of a function reference). The server ignores it. :1868-1885, :1927-1960, :1948 createTreatment, duration, PUT, DELETE
    S9 food None found. — food, quickpick, hideafteruse
    S10 profile None found: nightguard neither reads nor writes /api/v1/profile. The pump's active profile name comes from devicestatus.pump.extended.ActiveProfile. :1996-2010 profile, api/v1/profile, Profile Switch
    S11 COB/IOB Nightguard writes no devicestatus. It displays Nightscout-computed COB/IOB from /api/v2/properties (cob.display, iob.display) on the main screen, the watch and the widgets. The 15.0.9 notes say COB "now shows the value reported by your looping app"; if that change reaches /api/v2/properties cob, nightguard's COB number changes without any client change. :1622-1627, :1685-1689 cob, iob, api/v2/properties, pebble
    S12 query shape v1 uses bracket notation only (find[x][$op]=v); there are no v1 arrays. The v3 $in values are pipe-joined: type$in=sgv|mbg (2 values) and eventType$in=Carb Correction|Meal Bolus|Correction Bolus|Bolus Wizard (4 values, containing spaces). Maximum $in size: 4. Every parameter has a value. :810, :887, :1067, :2042 \$in, \[\], |
    S13 API v3 Capability probe GET /api/v3/version. limit values 1, 2, 20, 2..100, 500, never 0. The statistics read sends no limit (server API3_MAX_LIMIT) and pages with skip + sort$desc=date, up to 32 pages; it has a "did not progress" guard and de-duplicates locally by timestamp. It uses the fields projection and v3 POST /api/v3/treatments. No v3 PUT, PATCH, DELETE or history. The candidate's _id tie-break in v3 sort (lib/api3/generic/search/input.js) makes the skip paging stable; that helps this client. On 15.0.8 and the candidate alike, limit=500 gets a 400 if an operator set API3_MAX_LIMIT below 500. :207, :726-735, :806-812, :884-890, :1058-1067, :1136-1153, :1497-1501, :1779-1786, :1831-1837, :1950, :2038-2044 api/v3, limit, skip, sort\$desc, fields, lastModified, history
    S14 other None found: no Loop remote-command notifications, no /api/v1/notifications/ack, no Alexa. Snooze is local (SnoozeModalView, SlideToSnoozeView). The "Max" background push (MaxBackgroundPushRegistrationService.swift) goes to a third-party backend, not to Nightscout. nightguard/app/MaxBackgroundPushRegistrationService.swift notifications, ack, snooze (in network code), api/v2/notifications
    S15 errors No 2xx: v1 and v3 both produce NightscoutHTTPError. The entries and chart reads pass it to the UI and keep the cached values. There is no retry loop and no stall. A 400 shows as an error and the last data stays on screen. Soft-failure paths: readLastTreatementEventTimestamp returns Date() (now) on any error or empty array, so sensor, cannula or battery age shows as "just changed". Devicestatus returns an empty model. readLatestTreatements returns []. The properties enrichment is skipped.     Join questions (ranked by user visibility)¶

    1. S11 (wrong numbers). Does any 15.0.9 change alter the cob (or iob) object that /api/v2/properties returns (the "COB now shows the value reported by your looping app" item)? Nightguard shows cob.display directly, so it would show a different COB on the same data. Cross-check the release-note wording against the actual properties output.
    2. S5 (data stops). Confirm that #8754 (ef3404fd) keeps (a) GET /api/v2/authorization/request/<anything ending in -digest16> issuing a JWT and (b) a raw access token in the API-SECRET header resolving through doesAccessTokenExist. Nightguard's v3 path and its v1 fallback depend on both. Read-derived: both look unchanged.
    3. S13 (cosmetic, statistics). The candidate's v3 sort tie-break and fields-projector rewrite: check that fields=identifier,_id,date,dateString,mills,type,sgv,mbg,direction,units (top-level names only) still returns the same keys.
    4. S3 (none expected). The v1 find[date][$gt] value has a fractional-millisecond part; parseInt became parseFloat. Expected to give the same result on whole-ms stored dates; worth one test row.
