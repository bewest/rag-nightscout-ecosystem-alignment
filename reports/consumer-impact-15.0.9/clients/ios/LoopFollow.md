## Join questions (ranked by how likely a user would notice)

1. **S5 token provisioning (setup flow; failure = follower cannot be configured).** On the #8754 head, confirm: (a) `POST /api/v2/authorization/subjects` with `{name, roles}` still answers 2xx with an object carrying `_id`; (b) the token the server accepts for that subject is still derived from `_id` + site key + name exactly as on 15.0.8 (read-derived: identical expression), so LoopFollow's locally derived token keeps working; (c) `GET /subjects` still lists `accessToken`. Any change to token derivation or to the create response shape silently breaks LoopFollow's onboarding.
2. **S1 BG/stats counts** (data stops arriving if refused). Values 1152…5760 (main) and `days × 1152` (stats, unbounded above for very old custom ranges but finite integers). Confirm the candidate validator (`lib/api/index.js:73-90`, whole numbers, no cap) accepts these, and no per-collection maximum exists. A refusal here would turn into a 10-second retry loop with a banner.
3. **S6 poll stretching** (pre-existing; stale data risk rather than a 15.0.9 regression). The join should confirm that the #8754 socket changes do not alter when `connected` is emitted versus when `read` is granted. If a later release made `authorize` disconnect or not emit `connected` for `read=false`, LoopFollow would fall back to normal polling (an improvement); if it emitted `connected` for more cases, LoopFollow would poll less often.
4. **S10** — `/api/v1/profiles.json` with `find[startDate][$lte]` and `count=1000`: confirm the allowlist and count validator pass it and that `startDate` is not typed by `query-coercion.json` (read-derived: it is not).
5. **S4** — `/api/v2/properties/dbsize`: confirm no permission change on v2 properties in 15.0.9 (the two re-permissioned shared routes are v1 `count` and `slice`, per `d3ac8026`, which LoopFollow does not call).
