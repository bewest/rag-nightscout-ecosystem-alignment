## Join questions (ranked by user visibility)

1. **S8/S15, data disappears locally.** For `GET /api/v1/treatments?find[_id]=<X>&count=1`, confirm the candidate returns the record in every form in which 15.0.8 returned it: (a) X is 24-hex and the stored `_id` is an ObjectId, (b) X is a UUID with `UUID_HANDLING` on and off (where `identifier`=X or `_id`=X), (c) X is lower case against a stored value in a different case. Any case that becomes `[]` makes xDrip4iOS **silently mark the treatment deleted on the phone**. Read-derived, 6d120fa2 `query_for` → `idForms.matchEitherForm` *adds* string forms for hex (an improvement for 15.0.6-era records), and the UUID `$or` path is unchanged.
2. **S15, data stops arriving.** Is there any candidate path by which `POST /api/v1/entries` (an array of `sgv` docs with a random 24-char alphanumeric `_id`, `sysTime`, `date`, `dateString`) now answers 400? The client would stall and re-send the same batch forever. Read-derived: the non-hex `_id` is stripped on both, and the new `$setOnInsert: {_id}` path runs only for docs that still carry an `_id`, which these do not after stripping.
3. **S15, a duplicate-key workaround.** The client treats a **500 with `description.code == 66`** as success. Does any #8758 change turn a formerly 500/66 response into a different status or body shape (for example, now updating instead)? If it becomes a 4xx, the batch stalls.
4. **S7/S8.** For `PUT /api/v1/treatments` with a 24-hex `_id` and `eventTime` but no `created_at`: confirm the candidate still derives `created_at` from `eventTime`. Also confirm the new stale-string-form cleanup (`deleteMany({_id:{$in: stale}})`, treatments.js:320) only removes the string twin of the same id.
5. **S1, none expected.** Follower `count` is from 2 to 1921 and the import uses 2000/1000. Confirm there is no candidate upper bound below 2000 on v1 `count`.
