    S15 Any non-200 is a failure (callNS); response body wrapped into NightscoutError. In Loop's RemoteDataServicesManager, a failed batch does not advance the query anchor, so the same batch (up to 1000 records) is re-sent on the next trigger — a persistent 400 on any record in a batch stalls that data type indefinitely (head-of-line). Also a POST whose response array length differs from the request length is a failure → same stall. Two specific pre-existing defects make 4xx outcomes worse: (i) overrides — if the DELETE /api/v1/treatments/<UUID> step returns an error, NightscoutService logs it and never calls completion, so Loop's override upload queue blocks on semaphore.wait() until the app is relaunched; (ii) pump events — uploadPumpEventData calls completion(.success(false)) synchronously after starting the upload, so the anchor advances and a failed pump-event batch is silently dropped (completion also fires a second time). next-dev: (ii) is fixed (async/throws, would stall instead of drop); (i) is restructured into async/throws (the error path was not fully read). Empty array on GET: NightscoutRemoteCGM returns .noData; no fallback. Profile/current failure surfaces as incompatibleTherapySettings or the error.     Join questions (ranked: data stops > wrong numbers > cosmetic)¶

    1. Data stops (overrides queue hang). Does 15.0.9 (dev ddd9b600 + #8754 + #8758) answer DELETE /api/v1/treatments/<upper-case UUID> (no count, no find) with anything other than HTTP 200, with or without UUID_HANDLING? The server injects count=10 when absent (lib/api/treatments/index.js delete_records); confirm that injected value passes the new count validation on DELETE and that the _id normaliser still maps a non-hex, upper-case string without a 400. Any non-200 here hangs Loop's override upload queue until relaunch (NightscoutService fe075ef:167-185). #8758 says "the 400 for a non-hex _id on the other v1 routes ... unchanged" — confirm treatments DELETE is not one of those routes.
    2. Data stops (treatments/entries batch stall). Does any change make POST /api/v1/treatments or /entries (arrays of up to 1000, no _id except override UUIDs) return non-200, or a response array whose length differs from the request (e.g. dedup collapsing two identical items)? Either stalls the whole data type. In particular: an override POST carrying a UUID _id together with the #8758 staleFormsFor/withStaleStringsRemoved path — confirm non-hex ids are skipped and the bulk response still has one element per input.
    3. Data stops (carb edit/delete). Loop caches the _id string from the treatments POST response and later PUTs/DELETEs with it. Confirm the candidate still returns a lower-case 24-hex string _id for every element of a treatments POST response (including upserted-by-identifier and deduped ones), and that PUT /api/v1/treatments with that _id in the body updates rather than inserting a second copy.
    4. Data stops (profile / APNS routing). Confirm POST /api/v1/profile with a 400-element array, no _id, and mills as a string is accepted unchanged, and that the remote-command push path still reads loopSettings.deviceToken/bundleIdentifier/isAPNSProduction from the latest profile.
    5. Wrong numbers (COB display). The release notes say Nightscout now shows the looping app's COB. Confirm the server reads Loop's shape devicestatus.loop.cob.cob (with loop.cob.timestamp), and note that Loop only uploads devicestatus for certain decision reasons, so the COB age may lag.
    6. Cosmetic/setup. GET /api/v1/experiments/test with the SHA-1 api-secret header must still return 200 for a valid secret and 401 (not 403 or a delayed reply beyond URLSession's default timeout) for a wrong one; the throttle change should only affect failed attempts.
    7. Remote-command senders (via LoopCaregiver). POST /api/v2/notifications/loop with string duration/remoteBolus/remoteCarbs/remoteAbsorption values: confirm the candidate's clearer error bodies are still non-200 for failures and 200 for success (NightscoutKit treats only 200 as success).
