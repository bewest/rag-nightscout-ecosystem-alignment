    Item 1: last-owner revocation (reproduced, fixed)¶

    Mechanism (b70ad83f). lib/subject-admin/postgres.js remove() with an owner policy checks the acting owner's current authority (authorizePermissions(…, [])) and then deletes the target's role links, credential metadata and subject. It never reads tenant_owner_actors for the target. Deleting the subject of the only usable owner leaves the tenant with an owner actor row that no longer counts (no subject), that is, no usable owner, until an operator recovery. Two owners revoking each other at the same time each lock only their own target subject, so both commit (write skew) with the same result.

    Fix (lane commit). In owner mode, after current authority and before the target lock, remove() selects the subjects of every usable owner with FOR UPDATE OF s in subject_id order, and refuses SUBJECT_ADMIN_LAST_OWNER when the target is the only one. The sorted lock serializes concurrent revocations without a deadlock; the second one re-reads after the first commits and is refused. HTTP maps the code to 409. Revoking a co-owner, or one's own subject, while another usable owner remains is unchanged (decision owner-may-revoke-subjects). Legacy mode (no owner policy) is unchanged; see item 2. Files: lib/subject-admin/postgres.js, lib/server/subject-management-app.js, tests/owner-subject-policy.integration.test.js (three cases), tests/owner-subject-store-source.test.js (the synthetic connection models the new owner query).

    Before the fix (tests added, source at b70ad83f; NS_OWNER_SUBJECT_POLICY_DOCKER_TEST=1 node bin/with-env.js ./tests/ci.test.env node_modules/mocha/bin/mocha.js --fail-zero --timeout 60000 --require ./tests/hooks.js --exit tests/owner-subject-policy.integration.test.js): 23 passing, 2 failing.

    • "refuses revoking the last usable owner subject (409) …": {}; persistent effects changed: true / 200 !== 409: the HTTP revocation of the only usable owner's subject succeeded.
    • "race: two owners revoking each other …": outcomes ['applied', 'applied'], expected ['SUBJECT_ADMIN_LAST_OWNER', 'applied']: both concurrent revocations committed.

    The race is a real interleaving, not a sequence: a holder connection takes LOCK TABLE … tenant_subject_admin_audit IN SHARE MODE; the test waits until pg_stat_activity shows 2 nightscout-subject-admin sessions with wait_event_type='Lock' (both inside their transactions, deletes done, waiting at the audit insert) before releasing it.

    Item 2: legacy subject writers (reproduced at the store level; decision question)¶

    Mechanism. createPostgresSubjectAdmin composed without ownerPolicy ("legacy" writer) keeps its pre-owner privilege shape: no SELECT on tenant_owner_actors or tenant_owner_policy (measured: has_table_privilege('legacy_writer', …, 'SELECT') false for both). Its remove() locks only the target subject and credential metadata rows. The operator ownership store takes the policy row FOR UPDATE and reads subjects without a row lock. Nothing the two share is locked by both, and the legacy writer cannot see which subjects are owners.

    Reproduction (scratch file, not committed: externals/work/m6b-followups-20261110-evidence/legacy-writer-ownership.repro.js (local, git-ignored, with the run logs), run with CRM_TREE=<lane worktree> from the lane worktree from the lane worktree with the suite fixture; real PostgreSQL; synthetic tenant and identifiers), 1 passing, 2 failing:

    • Sequential: a legacy remove() of the only owner's subject returns true and leaves usable owners []. No concurrency is needed; the legacy writer is blind to ownership.
    • Concurrent: legacy remove(TARGET) held at its audit insert (delete done, uncommitted) while an operator transfer(manager → TARGET) runs, plans against the still-visible TARGET subject, writes the actor rows and waits at its own audit insert. Both sessions observed waiting at once (pg_stat_activity: one nightscout-ownership-ops, one nightscout-subject-admin, both on INSERT INTO "owner_policy_test".tenant_s…). Released: revoke=applied transfer=applied:null owners_reported=[TARGET] usable_after=[]. The transfer reported an owner whose subject no longer exists.
    • Control: the same interleaving through the owner-policy store: revoke=applied transfer=refused:OWNERSHIP_SUBJECT_UNKNOWN usable_after=["manager"] (passes).

    Reachability (measured). The only shipped composer of the store is lib/server/serve/owner-preview.js, which passes config.ownerPolicy; the owner-preview configuration parser requires it: the same configuration parsed with ownerPolicy and refused without it (invalid explicit headless owner preview configuration). No other lib/, bin/ or deploy/ file composes the store (grep, read-derived). So on b70ad83f the defect is reachable only by a composition that does not exist yet; it is a property of the module, which still accepts no ownerPolicy in multi mode.

    Why no fix was written. The legacy writer cannot evaluate the owner invariant without reading owner rows, and the existing suite asserts that legacy remove keeps working ("allows explicit owner revocation and preserves legacy/default update/remove behavior"). Every fix changes either that tested behaviour or a database identity's privilege shape. The decision question is below.

    Item 3: export-file expiry (unsettled, decision question)¶

    What is stated. Decision tenant-deletion-key-retention keeps the Transit keys and the export artifact for 30 days, then an operator destroys the keys, which cryptographically erases the artifact's secrets. lib/tenant-lifecycle/README.md says "Expiry of the export artifact file itself is not automated by this module", and the key-retention lane's operator note tells operators to delete the file themselves because glucose and treatment records in it are not encrypted by those keys.

    What the code does (read-derived). saveTenantArtifact writes <directory>/tenant-artifact-<digest>/artifact.json (0600). The only removal in lib/tenant-lifecycle is the staging directory on a failed save (filesystem-artifact.js:48). In the shipped tree only tools/lab/tenant-whole-c/core.js calls saveTenantArtifact; the ceremony verifies an artifact through a directory the operator configures. No code removes the artifact at or after the window, at destroy, or on a timer.

    Why unsettled. No document states whether the artifact file must be removed at the end of the window, by whom, or whether it is the operator's backup to keep. Measuring "the file is still there after destroy" would only confirm the stated behaviour; it is not a defect until the intended behaviour is decided.

    Decision questions¶

    D-A. Legacy subject writers in multitenant mode (item 2)¶

    • Mechanism: lib/subject-admin/postgres.js:20-28 accepts ownerPolicy undefined in multi mode; remove() (:181-194 at b70ad83f) then deletes any subject without reading tenant_owner_actors, whose rows that identity cannot read.
    • Options:
    • Refuse legacy remove() in multi mode (as legacy create() already refuses SUBJECT_ADMIN_FORBIDDEN). Smallest change; changes the asserted "preserve legacy remove" behaviour of a writer no shipped runtime composes.
    • Require ownerPolicy for every multi-mode store (delete the legacy branch). Removes the unguarded path entirely; the legacy-mode suites (subject-admin-postgres, subject-management-http, part of owner-subject-policy) move to the owner writer shape.
    • Keep the legacy writer and give its identity SELECT on owner actors plus UPDATE(owner_fence) on the policy row, then apply the item 1 guard and take the policy row FOR SHARE. Keeps the API, but the legacy identity grows to the owner writer's shape (a deployment-grant change; deploy/multitenant/config.js was out of this lane's scope).
    • Users/operators: nothing changes for operators today (no composition); the choice decides whether a future multitenant composition can orphan a tenant through a subject revocation.
    • Single/multi: multitenant only. Single-tenant MongoDB subject administration is a different store and is not affected.
    • Recommendation (if asked): option 2 for long-term direction and maintenance (one guarded writer, one privilege shape, nothing to keep in step), with option 1 as the interim if the legacy suites are to be migrated later. Unmeasured: whether any lab or native harness outside lib/ composes a legacy multi-mode writer (tests/native/oidc-matrix was not run).

    D-B. Export artifact file at the end of the retention window (item 3)¶

    • Mechanism: see item 3; destroyRetainedKeys (lib/tenant-lifecycle/key-retention.js) erases secrets cryptographically and leaves the artifact file, whose clinical records stay readable.
    • Options: (a) the operator's destroy step also removes the artifact it knows by digest from the configured artifact directory, audited in the same record, after the keys are confirmed absent; (b) a separate scheduled sweep of expired artifacts; (c) keep it an operator responsibility and document it in the deletion runbook (today's behaviour).
    • Trade-off: (a) ties removal to an explicit, already window-gated operator action and adds no timer; it cannot reach copies outside the directory. (b) removes files without an operator present, but adds a time-driven writer to the lifecycle domain. (c) adds nothing, but leaves plaintext clinical data on disk past the window unless the operator acts.
    • Single/multi: multitenant lifecycle only.
    • Recommendation (if asked): (a), for reliability (one audited step) and maintenance (no new scheduler); unmeasured: how operators store artifacts in practice (only the lab harness saves them today).
