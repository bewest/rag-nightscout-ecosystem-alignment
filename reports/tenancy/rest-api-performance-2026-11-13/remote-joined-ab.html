    Living document, last changed 2026-11-15 at 9d4e89982.

    Reproduced diagnostic: the joined candidate does less SQL work and improves latency and achieved throughput in this workload. At 30 offered requests/s, successful throughput rises 19.9%, API data-role SQL calls normalized to completed HTTP fall 21.2%, and read/write p95 latency falls 18.2%/15.7%.     Correctness and limits¶

    Every issued HTTP/content check passes; refused/uncertain writes and failed/ invalid reads are zero. Independent SQL checks match every accepted write's tenant, timestamp, device, type, glucose and dateString. Each fresh half also passes invalid/foreign credential refusal, the supported role-admin API control (A denied 401 while B reads 200, then A restored 200), and actual stored-value GREEN → RED → GREEN mutation/restoration. After each measured point, separate observations show stored/observed/completed/output clocks equal and pendingAt null. Selected BG-now mean/last/mills consistency passes. These are selected properties, not a connected-client or broad clinical-equivalence claim.

    No measured authority/isolation/persistence regression appeared. The coordinator still owns the joined readiness/full-acceptance boundary; this short diagnostic does not close it or declare a release ready.

    Both server wait/lock samplers are NO-INSTRUMENT: their Compose invocation refuses stat .: permission denied, leaving header-only activity/lock files. Raw empty wait arrays must not be read as zero contention. Driver pool-queue and API-stage durations are also NO-INSTRUMENT with diagnostics OFF. PostgreSQL per-process CPU is unavailable; cgroup CPU is measured. Docker stats and component/process bookends remain available. Low sampled k6 CPU does not establish a generator ceiling; both 30-offered points reach their VU bound.
