    A. Core: tokenFile alternative (MT-VAULT-TOKEN-FILE)¶

    Brief mismatch, measured: at ed2ced00 the only application getToken call site is lib/server/serve/preview-config.js:131. lib/human-session/access-config.js, lib/server/serve/owner-credential-config.js and lib/secrets/vault-access-signing.js named in the brief do not exist at ed2ced00 (git cat-file -e fails); they were added by eadf41f8 Bind human sessions to asymmetric access authority, which is on codex/next-batch-integration-20261107, codex/owner-oidc-combined-20261107 and codex/shared-oidc-sessions-20261107, not on the base. The change was made at the one real site; the three later sites need the same tokenEnv | tokenFile treatment when their branch joins (follow-up, below).

    Change (lib/server/serve/preview-config.js): tenant.vault accepts exactly one of tokenEnv (unchanged behaviour) or tokenFile; both or neither refuse at load; tokenFile must be a normalized absolute path (relative, empty, trailing slash, .., non-string refuse). The sink is read with fs.promises.readFile on every provider call, trimmed, must be non-empty, ≤ 4096 bytes, no whitespace; any failure throws SECRETS_PROVIDER_UNAVAILABLE (the Transit client already maps a throwing getToken to the same code). Several tenants may share one tokenFile; tokenEnv uniqueness is unchanged. Load-time check is shape only: the sink is not required to exist at load, so a sidecar that starts a moment later does not refuse the api (coordinator may tighten). lib/secrets/vault-transit.js untouched.     B. Deploy: Vault Agent overlay (DEPLOY-VAULT-AGENT)¶

    Files in nightscout-deploy: bindings/compose/vault-agent/{compose.vault-agent.yaml, agent.hcl, vault-agent-bootstrap.js, vault-agent.sh, README.md}, providers/secrets/vault-agent/README.md, a wave-3 "Vault service login" row and a status row in docs/roadmap.md. The imported tree bindings/compose/multitenant is unchanged: tools/compose-identity-check.sh <core> → ok twice, tree 8be3d761cbe592428357d6cee29612affafe4122; npm test → 0 targets checked, 0 failing.

    Mechanism: the override adds vault-agent (same digest, vault agent -config=…, runs as the runtime uid 1000 so it reads 0600 state files and writes a 0600 sink), a one-shot vault-agent-bootstrap step (application image, private network) and one read-only mount …/vault-agent/sink:/run/ns-vault:ro on api, realtime, evaluator, tenant-admin; api depends on the Agent being healthy (sink non-empty). The step reads the root token and layout the imported bootstrap left in /state/bootstrap/, enables AppRole, writes one policy that is the union of the imported per-tenant policies read back from Vault plus auth/token/renew-self (update) and auth/token/lookup-self (read), creates the role (token_no_default_policy, secret_id_num_uses=0, secret_id_ttl=24h, TTLs from env), writes role_id and secret_id (0600) to /state/vault-agent/creds/, and rewrites /state/api/config.json so each tenant's vault block carries tokenFile: /run/ns-vault/token instead of tokenEnv (dropping NS_VAULT_0/1 from env.json unless NS_VAULT_AGENT_KEEP_ENV_TOKENS=1). agent.hcl uses remove_secret_id_file_after_reading = true; the Agent keeps the value in memory for re-authentication after token_max_ttl, and a restarted Agent needs vault-agent.sh … secret-id.

    Design point for the maintainer (not decided here)¶

    The imported bootstrap mints one token per tenant with a per-tenant Vault policy. One Agent has one login, so the overlay creates one AppRole whose policy is the union of those per-tenant policies: every serving process holds a token that reaches every tenant's Transit keys on the mount, and tenant separation at Vault moves to the application's authority layer and RLS (the api selects the tenant's key from the tenant's config after the request is bound to a tenant). Gained: no login or renewal code in core, rotation without restarts, one credential custody per host, the same shape as a Kubernetes native sidecar. Alternative keeping Vault-side separation: one Agent and one sink per tenant (core's tokenFile already allows a distinct path per tenant; cost one container per tenant). Stated in bindings/compose/vault-agent/README.md; the decision belongs in releases/cgm-remote-monitor-16.0.0/decisions.md.

    Traps met¶

    1. Peer commit swept untracked files. nightscout-deploy moved from 75f0f61 to b3b29dfe (licence change) while this lane worked; that commit contains the first version of this lane's untracked overlay files and the roadmap edit. Symptom: git status suddenly showed only two of the lane's files modified. Avoidance: in a shared checkout, commit new files early or write them in a worktree; never git add -A.
    2. Host MongoDB 3.6 on 27017 fails 17 boot-path tests in test:affected with a wire-version refusal; use a dedicated mongo:7 container and repoint CUSTOMCONNSTR_mongo (memory local-mongod-is-3-6).
    3. Agent token without the default policy cannot renew itself; grant renew-self and lookup-self explicitly or the Agent silently re-authenticates each TTL.
    4. Brief's call-site list was read-derived from a later branch; two of three files do not exist at the pinned base.
    5. Shared demo.sh project name is fixed; the wrapper uses its own project name and env file so a plain demo on the same host is untouched.
