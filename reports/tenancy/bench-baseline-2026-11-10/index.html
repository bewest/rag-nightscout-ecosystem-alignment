    Host¶

    11th Gen Intel Core i7-11800H @ 2.30GHz, 16 logical cores, 64 GB RAM (65683804 kB), Docker root on /dev/nvme1n1p2 (453G, 193G free, 56% used), Docker 29.1.3, Compose 2.40.3, kernel 6.18.7. The brief's "92% / 42 GB free" is /dev/sda1 (/opt/external_home), not the Docker disk.

    Concurrent load: 44–46 containers of other projects ran throughout (52–53 running in all). Load average over the published runs ranged from 2.0 to 25.4 (1-minute, sampled every 2 s); most of it above 8 was this bench's own PostgreSQL. The samplers add load too: docker stats --no-stream every 2 s kept dockerd at about 1 core (114% in one top sample). The figures are therefore labelled under concurrent load.

    What was run¶

    Per tenant count: bench.sh deploy N (fresh project, volumes and private state), then two workloads on the same deployment, then teardown:

    • real: real cadence (BENCH_ACCEL=1), 300 s steady state;
    • x10: cycle compressed 10× (one 5-minute cycle per 30 s), 120 s.

    Each run: 30 s idle window (no clients) → k6 workload with the socket probe alongside → realtime restart (reconnect recovery) → oracle, disk, summaries. Client shapes, the hot tenant (×10) and the probe (20 sockets on the hot tenant, one on each of up to 40 others, polling transport like the stock browser, one sgv every 5 s) are in the harness README.

    Tenant counts: 1, 10, 50 measured. 100 and 200 do not start (below). N=50 x10 ran with realtime down: the realtime restart at the end of N=50 real did not come back (below), so its socket and realtime columns are empty by measurement, not omission.

    Reading the tables:

    • Latency columns are per client shape (k6/workload.js); "failed" is the request-weighted failure rate over all shapes; "dropped" counts k6 iterations not started because no VU was free.
    • Fanout is from sending the probe's POST to the first dataUpdate carrying that sgv on each socket of that tenant. "primed" counts sockets that received any dataUpdate within 30 s of opening.
    • Realtime restart: docker compose restart realtime with every probe socket connected. "Stock" waits 30 s with socket.io-client's own behaviour (no reconnect after a server-initiated disconnect, as the stock browser); "retrying" then makes every dark socket reconnect, re-trying each server disconnect after 1–5 s jitter, for up to 180 s.
    • Window leases per tenant per second: one INSERT INTO tenant_lifecycle_operations per tenant operation window (pg_stat_statements, reset per phase). For the evaluator this is its per-tenant cycle rate; at N=1 it is 4/s (two 1 s timers), at N=50 0.34–0.38/s, i.e. one cycle per tenant about every 3 s.
    • Bytes per tenant-day = table growth (heap, TOAST, indexes) per stored row × 288 per shape. The runs stored 10–111 rows per table, so 8 KB page allocation dominates: per-row growth ranged 1,100–2,294 B (entries), 2,253–10,426 B (devicestatus) and 1,386–8,192 B (treatments); stored doc size was 446, 1,602 and 446 B. The tenant-day figure is between 1.49 MB (n1 x10, the most rows per table) and 5.7 MB; the jsonb payload alone is 0.72 MB. A run with thousands of rows per table is needed for a single number (UNMEASURED below).
    • Oracle: GREEN on every run. At N=10 x10 43 writes and at N=50 x10 564 writes ended in a client timeout or 5xx; none of them was stored (stored = accepted in both).

    Bottlenecks observed¶

    Mechanisms are read from the source at 16a1fc2d; the costs are measured.

    1. Per-transaction catalogue admission. Every tenant transaction acquires an operation-window lease (lib/storage/postgres-connection.js:128) and re-runs the window admission (lib/tenant-lifecycle/operation-window.js:57 → operation-window-readiness.js:64-87): a role query plus one catalogue query per control table (5), every time. At idle these queries are most of the database work: N=1 idle, 174 DB-ms/s, of which /* operation-window-table */ and /* operation-window-role lifetime */ took 4,376 of 5,219 ms over 30 s; the lifetime role query costs 5–9 ms per call (EXISTS over pg_proc/pg_class with privilege functions). At N=1 under load the api role ran 93,795 operation-window-table statements (34.9 s DB) in 302 s.
    2. Per-tenant polling every second, independent of traffic. The evaluator runs an acquisition and a time-only cycle for every tenant every second (lib/server/serve/evaluator-runtime.js:240-241) and realtime refreshes every tenant every second (lib/server/realtime/runtime.js:46), each through (1). Idle PostgreSQL CPU: 125% at N=1, 899% at N=10, 715% at N=50 (16-core host); at N=50 the evaluator no longer keeps up (0.38 cycles/tenant/s against 4 at N=1).
    3. Fixed pool sizes. api data pool max: 4, 5 s connect timeout (lib/server/serve/preview-api.js:57-58); realtime max: 4 (lib/server/serve/preview-realtime.js:32); evaluator max: 4 (lib/server/serve/evaluator-preview.js:31); operation pool max: 8 per role (lib/server/serve/operation-cohort-config.js:49). The latency floor of 5,004 ms with 16.5% (N=10 x10) and 73.1% (N=50 x10) failures is the 5 s pool connect timeout.
    4. Socket fanout is sequential per socket and re-authorizes every second. fanout() walks every socket and awaits current(state) (an IPC authorizeSocket to the api, which opens its own tenant transaction) before sending, socket by socket (lib/server/realtime/protocol.js:180-199, :55), and sends a full dataUpdate to every primed socket on every 1 s refresh, changed or not. Hot-tenant fanout p50 with 20 sockets: 2,958 ms (N=1), 5,724 ms (N=10). The api's DB work at N=1 under load is 18,759 tenant transactions in 302 s for 117 k6 requests and about 60 probe writes; the attribution of the rest to these socket authorizations is read-derived.
    5. Socket admission under concurrency and restart. A socket's priming holds an operation-window lease while it authorizes and refreshes; when the pools are exhausted the window fails, initial() disconnects the socket (lib/server/realtime/protocol.js:81-84), and socket.io-client does not reconnect after a server-initiated disconnect. Shutdown also disconnects every socket server-side (protocol.js:240). Measured on an idle N=2 deployment, sockets opened at once: 9/9 primed with 9 sockets; with 13–21, 4 of 6 attempts refused most or all (0/13, 0/21, 3/17, 0/21 primed; 13/13 and 21/21 otherwise); opened 250 ms apart, 21/21 primed. After a realtime restart 0–1 of 20–29 stock sockets recovered; retrying clients recovered in 11.8–45.8 s (N=1, N=10).
    6. Configured ceiling. realtime maxSockets: 100 per process across all tenants (deploy/multitenant/config.js:133); not reached in these runs (at most 60 sockets).

    Compose fixes (nightscout-deploy bench/compose-baseline-20261110, not pushed)¶

    1. 54af5f2e api refuses startup on the unmodified plan (exit 78). The subject-admin store's root_writer connection runs under the operation window, whose admission needs the control-schema reads that grants() withheld from root_writer (config.js:98 at 16a1fc2d). Red on the unmodified plan, green with the fix. The decision whether root_writer should be fenced by the window (this fix) or its store should not use the window belongs to the root-admin parity owner.
    2. 4e5a1051 the plan is fixed at two tenants; NS_DEMO_TENANTS (1..1000, default 2) on the bootstrap service. At the default documents() is byte-identical to core's and bootstrap.test.js passes 5/5. restore.js and ownership-admin/ownership-grants.js still assume two tenants.

    N=100 and N=200 are not fixed: their causes are core pool sizes and startup concurrency, not deployment configuration.

    Controls¶

    • Oracle break-it: bench.sh control 2 on a 30 s run: baseline ORACLE GREEN … stored 36, accepted 36; one entry re-marked → ORACLE RED: tenants 2, mismatched 1, stored 35, accepted 36; restored → ORACLE GREEN … stored 36, accepted 36; CONTROL PASS (runs/n2-oracle-control.json). Two earlier attempts did not exercise the oracle (the ordinal trigger refused an unbound UPDATE; the control then picked the state directory); the N=10 campaign entry CONTROL FAIL is that harness defect, not a red.
    • Oracle found a harness defect: with a per-VU timestamp origin, colliding writes were merged by the server's dedup and the smoke oracle went red (stored 57, accepted 60); fixed with one run-wide origin.
    • Instrument perturbation found: pg_stat_statements created in the application database made the lifetime window admission refuse every evaluator/realtime cycle (foreign_functions); the harness creates it in postgres only.
    • Compose fix 1: red on the unmodified plan (api exit 78), green with the fix.
