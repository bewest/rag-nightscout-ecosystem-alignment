    Tenant registry and provisioning: design and lane record (MT-TENANT-REGISTRY)¶

    Living document, last changed 2026-11-11 at 10413d922.

    Contributor-facing lane record, 2026-11-11. Living until the lane hands off. Decisions implemented: tenant-registry, provisioning-split (as refined on alignment 3b841112c). Patterns reused: change-stamp-definer-function, admission-epoch-everywhere, readiness-serve-then-warm, pool-primitive-shared.

    Design¶

    What exists at 0392acf9 (read-derived)¶

    • lib/server/serve/preview-config.js:128-148 builds the resolver, one Vault Transit provider per tenant (encryptionKey, signingKey, signingVersion, tokenEnv | tokenFile), the client environment and the access-token trust keys from config.tenants and config.accessTokens.keys.
    • The api uses the static set in tenant-startup cells, human-session/runtime (tenants), root-admin authentication (tenants), secrets.providerFor, preview-domains (config.environments), and the operation window's static lock map (operation-cohort-config locks; operation-window.js:28).
    • Realtime, evaluator, tenant-admin, admin (ownership), the operation config (locks), the socket admission file and the UI config each carry their own tenant list.
    • Per-tenant provisioning today lives in the Compose bootstrap (nightscout-deploy bindings/compose/multitenant/bootstrap.js:91-149) and the core fixture (tests/fixtures/realtime-preview/bootstrap.js), mixed with lab priming.
    • Vault key names are index-based: tenant-<i>-data, tenant-<i>-signing, tenant-<i>-access, tenant-<i>-management, one ACL policy <prefix>_tenant_<i> per tenant; the Vault Agent policy is the union of those policies (vault-agent-bootstrap.js:63-72), so it grows with N and changes with every tenant.

    Catalogue, namespace and migration number¶

    A new operational catalogue lib/tenant-registry/postgres-candidate.json, migration 0001_tenant_registry, in its own namespace (deployment layout kind registry). It is added to the census OPERATIONAL list (lib/tenant-operations/catalogues.js:22) with its digest pinned: it is deployment configuration, never part of a tenant artifact, export, erase or restore.

    object columns access
    tenant_registry tenant_id uuid PK (not the metadata tenant), state text CHECK (state IN ('active','removed')), signing_version integer >= 1, revision bigint, created_at, updated_at FORCE RLS on app.current_tenant_id; SELECT granted to serving identities, so a role reads its own tenant's row only under that tenant's binding
    tenant_registry_hosts host text PK (lower-case, validated like tenant-resolution), tenant_id uuid FK, kind text CHECK (kind IN ('alias','internal')) no RLS, no grant to any login role; read only by the definer function
    tenant_registry_keys (tenant_id, purpose IN ('access','management'), kid) PK, public_key text (Ed25519, base64, public material) FORCE RLS; SELECT to api (access) and tenant-admin (management)
    tenant_registry_clock singleton revision bigint no RLS, no grant; read only by the revision function

    state holds existence only (active, removed). Pause and suspend stay in tenant_activity, their one home (decision activity-row-always-provisioned), read afresh per request as today.

    Definer functions, signatures and grants¶

    Shaped exactly as tenant_change_stamps (lib/change-stamps/postgres.js): SECURITY DEFINER, plpgsql, owned by the NOLOGIN catalogue owner, SET search_path = <registry ns>, pg_catalog, SET app.current_tenant_id = '' so a binding never leaks to the caller, REVOKE ALL ... FROM PUBLIC, EXECUTE granted only to the serving identities that resolve hosts (api, tenant-admin, realtime), named in the census operational inventory.

    tenant_registry_lookup(host text, kind text) RETURNS TABLE (tenant_id uuid, state text)
tenant_registry_revision() RETURNS bigint
    • lookup reads one tenant_registry_hosts row by exact (host, kind), binds that tenant with set_config('app.current_tenant_id', ..., true) and returns that tenant's (tenant_id, state). Zero or one row. No other column, no list, no prefix match.
    • revision returns the singleton counter. Every provisioning transaction (and any later alias, state or signing-version change) increments it in the same transaction.
    • Every call also returns the function's catalogue version (pg_proc.xmin plus owner attributes); an unadmitted version runs the full attribute check (definer, language, result type, body, owner without LOGIN/SUPERUSER/BYPASSRLS, no PUBLIC EXECUTE, pinned config) before any row is used, the change-stamp and admission-epoch rule. Refusal code TENANT_REGISTRY_FUNCTION_UNSAFE.

    Lookup, bounded cache and refresh rule¶

    lib/tenant-registry/reader.js is a resolver with the same resolve(req) contract and refusal codes as lib/tenant-resolution (every call site already awaits it), plus entry(tenant) for per-tenant attributes.

    • First request: the host is validated with the existing hostname() rules (TENANT_HOST_INVALID as today), then looked up through tenant_registry_lookup. Per-tenant attributes (signing_version, public keys) are read once under that tenant's RLS binding and cached with the entry.
    • Bound: an LRU of at most maxTenants positive entries (operator-set, default 10,000, maximum 100,000) and a separate negative cache of at most 1,024 unknown hosts. Concurrent misses for one host share one lookup.
    • Refresh (stage 1, aggregate poll): one tenant_registry_revision() statement per refreshMs (default 2,000 ms, bounds 250–60,000) per process, independent of tenant count. When the revision moves, the negative cache is cleared and every positive entry is marked stale; a stale entry is revalidated (one lookup) on its next use. No LISTEN/NOTIFY.
    • New tenant: served without a restart within refreshMs plus one lookup.
    • Unmeasured: revalidation after a change touches each cached host once on next use (about N lookups spread over traffic at N cached tenants). A changed-since function would remove that but returns tenant ids across tenants; left for stage 2 with NOTIFY.

    Unknown host¶

    Same refusal as today: TENANT_HOST_UNKNOWN (and TENANT_PROXY_UNTRUSTED, TENANT_SELECTOR_CONFLICT in canonical-internal mode with the same rules). The negative cache only bounds the database cost of repeated unknown hosts.

    Removed or suspended tenant and cached entries¶

    • removed: provisioning's removal path deletes the host rows and sets state='removed' in one transaction with a revision bump. Within one refresh interval every entry is stale; its next request re-looks up, finds no host, and refuses with TENANT_HOST_UNKNOWN. A cached entry(tenant) for a removed tenant answers TENANT_REMOVED.
    • Suspended or paused: unchanged. tenant_activity is read per request by the serving gate; the cache never holds it.
    • The registry never re-points a host to another tenant in place: an alias change is remove-then-add, both with revision bumps, so a stale cached host can only refuse, never serve the wrong tenant beyond one refresh interval. (Re-pointing is not offered by this lane.)

    Admission epochs and the restore fence with a cached tenant¶

    • The cache only supplies which tenant a host names and its Vault/key attributes. Every data transaction still acquires the operation window's shared advisory lock and reads the window row and catalogue epoch inside the transaction (operation-window.js assertClient), so a restore or maintenance window refuses requests whatever the cache holds.
    • The window's static locks map gives way to a lock-key rule (below) for registry tenants; the in-transaction check row.lock_key !== held.key (operation-window.js:128) remains the fence, so a lock key that differs from the window row refuses LIFECYCLE_WINDOW_BINDING_CHANGED.
    • A restore increments the window generation; existing invalidateTenant paths reset startup cells as today. Registry rows are operational and are not restored, so restore cannot change a tenant's hosts.
    • The registry functions carry their own version admission (above); registry tables are not added to the window's catalogue epoch.

    Fixed rules: Vault key names and lock keys¶

    • Vault Transit key names: tenant-<purpose>-<tenant uuid>, purpose in data, signing, access, management (for example tenant-data-0b5c...). Purpose first so that one role-level ACL can use prefix globs (path "<mount>/decrypt/tenant-data-*"); the index form tenant-<i>-<purpose> is not accepted in registry mode.
    • Vault credential: one role-level source (vault.tokenFile, the Vault Agent sink, or vault.tokenEnv); no per-tenant token reference exists to store. signing_version is per-tenant state in tenant_registry (it changes on rotation), not a Vault reference.
    • Operation-window lock key: derived, 1 + (first 62 bits of sha256('nightscout-tenant-lock-v1:' + uuid)), written once into tenant_lifecycle_windows.lock_key at provisioning (its existing home, UNIQUE); a collision refuses provisioning with TENANT_PROVISION_LOCK_COLLISION.

    Provisioning: library, admin operation, batch form¶

    lib/tenant-registry/provision.js is the implementation; the admin role exposes it on the operator plane as tenant-provisioning (new contract in lib/server/internal-api/contracts/). No caller writes provisioning rows with its own database credentials.

    Steps for one tenant, idempotency key the tenant id:

    1. Validate the spec (id, hosts, optional canonical internal host). If the id exists in the registry with the same hosts: outcome existing, nothing written. Same id with different hosts, or a host bound to another tenant: refused (TENANT_PROVISION_CONFLICT), nothing written.
    2. Vault: for each purpose, read the key; create it if absent (aes256-gcm96 for data and signing, ed25519 for access and management, non-exportable); an existing key of the wrong type refuses. Read the access and management public keys.
    3. Root secret record: if no root record exists for the tenant, generate and encrypt one through the secrets component; an existing record is reused.
    4. One PostgreSQL transaction on the provisioning identity, all or nothing: tenant_registry, tenant_registry_hosts, tenant_registry_keys, the clock bump; legacy_credential_config (root), tenant_authorization_config (anonymous_roles = {denied}), tenant_owner_policy (deployment catalogue), access_tenants, access_keys (key1/data, management1/management), tenant_write_clock, one tenant_consumer_checkpoint per configured consumer (consumer id and contract digest are deployment configuration of the operation), tenant_lifecycle_windows (derived lock key, active, generation 1), and the activity row and audit (tenant-activity/provisioning.js, in the same transaction as the window row).

    The commit point is the registry row, written in step 4. A tenant without a registry row is not served. Failure before or inside step 4 leaves no registry row and rolls back every row of step 4; Vault keys and the root secret record from steps 2–3 remain and are adopted by a re-run, which then produces the same state as a clean run. Nothing that serves a tenant exists before step 4 commits.

    Not provisioning (lab priming, stays in the bench and lab harness): subjects, roles, subject roles, owner actors, access credentials and sessions, management tokens, and synthetic entries. Restore authority (tenant_lifecycle_restore_authority) stays a separate operator step.

    Batch form (provisionTenants): at most 100 tenants per call (contract maxItems, and the admin listener's maxBytes); each tenant runs the single-tenant steps independently (one transaction per tenant, bounded concurrency 4); the response has one result per tenant in request order: { id, ref, outcome: 'created' | 'existing' | 'refused', code? }. A retried batch returns existing for tenants already committed, so retry after any failure is safe. Duplicate ids or hosts inside one batch refuse the whole batch before any work.

    Credential hook for priming: each seed row may carry ref, an opaque lab label echoed in every result. On created only, and only when the request sets issueRootSecret: true, the result carries the tenant's root secret once; the CLI writes it to a --secrets-out file (mode 0600) keyed by ref and id. The harness reads that file to prime each tenant through its normal data API. A re-run returns existing without a secret; the harness keeps its file. The provisioning CLI and the admin API load no data.

    The CLI: one thin client¶

    nightscout admin provision, a top-level client command beside healthcheck (which is also a client of a role's listener); nightscout multitenant <roles> stays the serving command.

    nightscout admin provision --id <uuid> --host <host> [--host <host>...] [--internal-host <host>] [--ref <label>]
nightscout admin provision --seed <file.json|file.csv> [--batch 100] [--secrets-out <file>]
  admin listener: --socket <path> | --url http://<private address>  (default from ADMIN_HOSTNAME/ADMIN_PORT)

    Seed schema, one for both formats:

    field JSON CSV column rule
    id string id canonical lower-case UUID, required
    hosts array of strings hosts, ;-separated at least one in direct-alias mode
    internalHost string internal_host canonical-internal mode only
    ref string ref optional, ^[A-Za-z0-9_.-]{1,64}$

    JSON is { "version": 1, "tenants": [ ... ] }; CSV has a header row naming exactly those columns. The CLI sends bounded batches, prints one line per tenant (ref id outcome [code]), exits 0 only when every tenant is created or existing, and is safe to re-run. It has no database or Vault credentials.

    Roles in registry mode, and refusing a tenant list¶

    A role selects the registry with a registry block (connection env of its serving identity, namespace, maxTenants, refreshMs). A config that carries registry and tenants (or per-tenant accessTokens.keys) is refused at load with registry configuration refuses a tenants list. Order of conversion:

    1. api (this lane, first): resolver, Vault providers by rule, access-token keys from tenant_registry_keys, client environment from tenantSettings (required in registry mode), startup cells created on first lookup, operation window lock by rule.
    2. tenant-admin and admin ownership (lookup and management keys).
    3. realtime and evaluator need the set of tenants without a request; they are open items (an enumeration path through the change-stamp or a registry function, sized for 10k), not in this lane's first delivery.

    Open¶

    Gaps to close before registry mode becomes the default:

    • Realtime and api socket forwarding. Not converted. Realtime's warm calls the api's private authorizeSocket (preview-realtime.js:77-80), and the api's private API resolves hosts from the static alias list and the socket admission file (realtime/private-api.js:36-39,92), which registry mode refuses. Realtime registry mode needs the admission object (realtime/admission.js: resolve, resolveHost, allows, enabled, ids, aliases) served from the registry (lookup for host, active for allows/enabled) on both the api and realtime, and the warm call without a tenant-to-host reverse lookup.
    • OIDC origins (OIDC_TENANT_ORIGINS, one per configured tenant, human-session/runtime.js:55-58): refused in registry mode.
    • Static mode still loads. A configuration without registry keeps its tenant list. Removing static mode (the decision's end state) also needs the fixtures (tests/fixtures/realtime-preview/bootstrap*.js, deploy/multitenant/) and nightscout-deploy moved to provisioning.
    • Tenant removal has no operator operation yet (tests remove by SQL); deletion ceremony integration is open.
    • Settings at provisioning. Provisioning writes no tenant_settings row; tenants start on operator-policy defaults.
    • Peer lane. A trial merge of workspace/capacity-fixes-20261111 (5517cb6c) conflicts in the five loaders this lane also changes (admin-config.js, evaluator-config.js, operation-cohort-config.js, owner-preview-config.js, preview-config.js); resolve at the join.
    • Unmeasured: first-request lookup latency and cache churn at 10k; revalidation cost after each registry change (each cached host re-looked up once on next use); the evaluator role end to end in registry mode.
