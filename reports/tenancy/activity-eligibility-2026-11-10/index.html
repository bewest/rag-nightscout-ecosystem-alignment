    What existed before this lane (read-derived, from b70ad83f)¶

    • No administrative pause or suspend existed. The only "suspended" in the multitenant tree is the restore maintenance hold: tenant_lifecycle_windows.phase = suspended while maintenance-window.js holds a tenant, set back to active on activation. Readers see it through the operation window (LIFECYCLE_WINDOW_SUSPENDED). It is not a desired-state flag and a restore clears it by design.
    • evaluator-runtime.js built its state map from every configured tenant and both timers called all() over that map (evaluator-runtime.js:15,112,169-170 at b70ad83f). A held or removed tenant was refused per cycle (EVALUATOR_WINDOW_REFUSED, EVALUATOR_TENANT_DISABLED) after the cycle had started, rather than skipped.
    • The consumer coordinator's timers iterated every configured tenant (evaluator-consumers.js:74-76 at b70ad83f).
    • Connectors have no multitenant runtime (roles.js:81 vcpool has no start).

    What was added¶

    Storage (lib/tenant-activity/postgres-candidate.json, migration 0001_tenant_activity, checksum ac9ed41b590d0bd4382d80e50da9763e509222925e0505ebe913d2341ca04159):

    • tenant_activity(tenant_id PK, version bigint, paused boolean, suspended boolean) under the tenant RLS policy used elsewhere. Two flags, three effective states: suspended wins over paused, else active.
    • tenant_activity_audit(tenant_id, version, verb, authority, principal, consumer, paused, suspended, event_time), append-only; a CHECK limits authority='owner' rows to pause/unpause.
    • A separate table from tenant_lifecycle_windows, so a restore's activation has no statement that touches it, and the restore operator grants (maintenance-window.js operatorGrants) include nothing on it.
    • grants({namespace, reader, owner, operator}): reader SELECT; owner SELECT + UPDATE(version, paused) + audit INSERT; operator adds INSERT and UPDATE(suspended). The store refuses at boot an identity whose privileges do not match its capability (ACTIVITY_STORE_UNSAFE).
    • A row is provisioned by the operator (provision, audited). An unprovisioned tenant is not eligible and reports …_ACTIVITY_NOT_PROVISIONED; an unreadable store reports …_ACTIVITY_UNAVAILABLE.

    Policy (lib/tenant-activity/policy.js): operation matrix evaluator: [active], notification: [active], ingest: [active, paused], connector: [active, paused]. Owner verbs pause, unpause; operator verbs add suspend, unsuspend. An owner cannot act on a suspended site, so an owner unpause cannot lift a suspension; operator unsuspend keeps an owner's pause.

    Evaluator (evaluator-runtime.js): with an activity selection every trigger, both timers and the boot acquisition read the tenant's current state first. Ineligible: no cycle, readCurrent, component, acquisition or output; the generation is bumped (an in-flight cycle cannot publish), queued tickets are released, the component is closed after any running cycle, last() is null, isCurrent() is false, health reports EVALUATOR_TENANT_PAUSED|SUSPENDED and activity. The cycle re-reads the state before publishing. On the first eligible read after inactivity the component is discarded and the next work is forced to a full acquisition, whatever triggered it. invalidateTenant (what restore activation's cohort invalidation calls) keeps the inactive code. Without an activity selection the runtime behaves as before.

    Consumers (evaluator-consumers.js): each drain iteration checks notification eligibility; a paused/suspended tenant gets no producer.select, no notifier.retry (so no retried or clearing delivery); health state: inactive, code: EVALUATOR_CONSUMER_TENANT_PAUSED|SUSPENDED.

    Connectors: eligibility.create({read}).connectorWorkList(tenants) returns the tenants to poll (paused keeps polling, suspended does not). No caller exists yet.

    Owner API (owner-settings.js, wired in owner-preview.js when ownerActivity is configured, which requires ownerSettings): GET /api/v1/tenant/activity, POST /api/v1/tenant/activity/pause and /unpause with {expectedVersion}. The tenant is the request-resolved tenant, which the router already requires to equal the credential's tenant. Authority is the owner-settings configuration authority (active and can_configure). No suspend route. Errors: ACTIVITY_FORBIDDEN 403, ACTIVITY_SUSPENDED 409, ACTIVITY_VERSION_CONFLICT 409, ACTIVITY_NOT_PROVISIONED 404.

    Configuration: evaluator activity: {connectionEnv, namespace}; owner preview ownerActivity: {connectionEnv, namespace}. Both optional, both run the catalogue check before use. deploy/multitenant/config.js is not changed (internal-listener lane's area).

    Design change: the activity tables moved into the lifecycle (control) namespace¶

    A backfill migration must read the tenant inventory, and catalogue SQL is static: a separate activity namespace cannot name the control namespace. The tables are therefore migration 0007_tenant_activity of lib/tenant-lifecycle/postgres-candidate.json (checksum 04e34feac301aa516bfe1bbac7355e413db26a2a5ccf4c03be652176d718b84e); lib/tenant-activity/postgres-candidate.json is deleted. Consequences:

    • tenant_activity.tenant_id references tenant_lifecycle_windows; a tenant is "provisioned" when it has a window row, the same definition the admin-lifecycle lane's tenantPhase uses.
    • Backfill: INSERT … SELECT FROM tenant_lifecycle_windows plus an audit row (provision/operator/migration/backfill-0007). tenant_lifecycle_windows has FORCE ROW LEVEL SECURITY, so a non-superuser schema owner would see no rows; the migration runs NO FORCE → backfill → FORCE inside its own transaction. A runner that is not the windows' owner fails the migration (loud), it does not backfill nothing.
    • LEDGER_TABLES (derived from the catalogue) now includes both tables, so the ceremony and key-retention relation inventories and the whole-deployment census include them automatically (census 47→49, 48→50 with the profile successor; seed rows added).
    • Numbering: the export-expiry lane adds 0006_tenant_lifecycle_artifact_removal to the same catalogue. This lane uses 0007 so either join order keeps names lexically ordered; neither is released.
    • New columns deletion_request_id, paused_before_deletion (both null or both set). New grant set grants({ceremony}): UPDATE(version, paused, suspended, deletion_request_id, paused_before_deletion), audit INSERT.
