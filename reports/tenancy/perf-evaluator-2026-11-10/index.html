    Perf lane EV: the evaluator works on change and due time, not a per-tenant one-second poll (2026-11-10)¶

    Living document, last changed 2026-11-11 at edbdb0213.

    Contributor-facing measurement record for decision cost-proportional-to-activity, stage 1. Captured 2026-11-10 20:48–23:20 local time; not edited after capture. Synthetic tenants and data only. Figures are labelled reproduced (run here, output in runs/) or derived (arithmetic on reproduced figures). Every run shared the host with other lanes; load averages are quoted per run.

    The change stamp: the clock floor is not enough (reproduced)¶

    The tenant write clock floor (tenant_write_clock.last_stamp) advances only when a transaction allocates a server date (lib/storage/postgres-write-clock.js:74). Two kinds of supported write do not:

    • hard deletes: v3 permanent delete, prune/autoPrune and v1 delete reach DELETE ... RETURNING in lib/storage/postgres-entries-write.js (remove, used by deleteMany :359 and deleteManyOr) with no srvDates.next();
    • unstamped domains: the activity collection carries no srvModified.

    The existing proof tests/tenant-current-state-recovery-proof.integration.test.js ("finds quiet canonical absence and unstamped activity through the explicit recovery backstop") deletes an entry and inserts an activity row: floor unchanged and row count unchanged. A floor-plus-count signature failed it (reproduced during this lane). Hence the per-row version digest. Decision m5-bounded-snapshot-reconciliation already requires recovery "independent of floor movement"; this is the same fact seen from the backstop.

    Cost of that coverage: the signature scans the tenant's admitted rows (bounded by maxRows): 0.25–0.79 DB-ms per check at 576 rows (reproduced, runs/bench.txt per-evaluation signature).

    Due-time rules (each from the plugin's own comparison)¶

    lib/data/evaluator-due.js: timeago warn/urgent onset (timeago.js isStale, strict >) and the "Last received" display boundaries while stale (calcDisplay resolvers); 10-minute reading recency for simplealarms/errorcodes (<) and ar2 (>); sbx.isCurrent 15 minutes (bwp); cage/sage/iage/bage threshold hours and the end of their 20-minute notification window, read from the same ddata lists the plugins use; treatmentnotify 10 minutes (wall clock); bwp recent carbs 60 minutes; openaps offline end; device-status look-back (24/48 h) and treatment window (60 h) exits; upbat 30 minutes; loop/openaps recent selection (warn/2) and 6 h window; pump clock warn/urgent and pump status window (2 × urgentClock); loop/openaps status warn/urgent from lastOkMoment/lastLoopMoment; any record dated in the future reaching now.

    Not expressible as an instant → bounded slow timer (say so per the brief): every alarm message carries IOB/COB lines that decay continuously and humanized times (buildDefaultMessage, ar2/loop/openaps from/formatAgo); bwp while the reading is current; xdripjs state notices on the wall clock; pump quiet-night hours in the profile's time zone. These keep a tenant on timeIntervalMs only while the condition holds; they do not undermine the model, because they hold only for tenants with an active alarm or fresh data.

    What runs out first, and at about what N (derived): 1. One evaluator process, around 1,500 tenants: CPU at ~40 ms per tenant-minute is one core at ~1,500, and resident memory at ~2.3 MB per tenant reaches the default V8 heap (~4 GB) near 1,700. Partitioned members (MT-EVALUATOR-PARTITION) divide both; eviction would cut memory only if the heap actually shrinks (unmeasured). 2. PostgreSQL across all members, around 9,000 tenants: the per-tenant signature check costs ~0.17% of a core per tenant at a 1 s backstop (171% at 1,000); 16 cores at ~9,000. It scales with tenants × backstop rate × rows per tenant, not with activity, and is the reason the decision's aggregate query matters. 3.     Conflicts with decisions recorded after this lane started (stop-and-report)¶

    The coordinator relayed change-stamp-definer-function and incremental-refresh while this lane ran. Neither is built here; both conflict with what was reproduced:

    1. A definer function returning (tenant_id, last_stamp) does not see hard deletes or unstamped (activity) writes. Reproduced: control C2 (signature = floor only) leaves a hard-deleted reading on display (222 !== 111) and misses an unstamped update; the shipped M5 proof (delete + activity insert) fails the same way. Options for the maintainer: (a) make every supported write that changes evaluated input advance the clock floor (hard delete paths in postgres-entries-write.js remove, and the activity domain), so last_stamp is a complete signature and the shared function suffices; (b) the function also returns a per-tenant row-version digest (the scan this lane does per tenant, now in one statement); (c) keep last_stamp for latency and a slower per-tenant digest pass for absence. (a) is the cheapest at runtime and touches the API write path and the event payload's stamp (null today for hard deletes). Swap point for the join: the runtime compares opaque signatures (evaluator-runtime.js:54 validSignature, same), obtained from component.signature() → postgres-durable-replay.js:169. A shared aggregate would replace the per-tenant read inside pass() (evaluator-runtime.js:316) with one call that returns signatures for the slice; check() already accepts any signature object.
    2. Incremental read saves little per evaluation, because the evaluation recomputes the whole window anyway. Reproduced at N=10: acquisition 33.7 CPU-ms / 8.9 DB-ms; time-only (no change rows read at all) 16.2 CPU-ms / 3.0 DB-ms and still 44 statements, because the views re-query the retained input through PostgreSQL every cycle and every plugin recomputes from the full window. An incremental read can remove at most the difference (~17 CPU-ms, ~6 DB-ms per acquisition, which at real cadence is one per tenant per 5 min). Hard deletes and unstamped writes also defeat stamp > checkpoint (point 1). The larger, per-evaluation cost is the projection-read path and the full plugin pass; that is where CPU-ms per evaluation can fall.

    What changed¶

    Lane (5ab35cad) - Evaluation-gap alert: EVALUATOR_NOT_EVALUATED_WITHIN_BOUND (evaluationAlertMs, default 60,000; evaluator config field of the same name). A tenant's evaluation is "confirmed current" by an acquisition, a time-only cycle, or a backstop check that found nothing changed; the alert fires once when the age since the runtime started or since the last confirmation exceeds the bound, and clears on confirmation. Paused, suspended and withdrawn tenants are exempt. It has its own watchdog schedule, so a stuck backstop still alerts. Exposed in health() (tenants[].evaluatedAgeMs, tenants[].alert, alerts) and in the evaluator inspection (tenants[].evaluation: { ageMs, alert }, an additive optional property of the evaluator-inspection contract). - Serve boot: boot: 'serve' returns at once and acquires in the background, bootConcurrency at a time, warm tenants first (isWarm); the backstop leaves queued tenants to that queue. 'all' is unchanged. - Bounded backstop: checks and the acquisitions they start share checkConcurrency slots (default 4); the in-flight guard is per tenant (one stuck check holds only itself); a refused check waits for the next pass instead of acquiring. - Config parse cache: readCurrent reuses the parsed evaluator config while the file's inode, size, mtime and ctime are unchanged.

    Join (41f9179a): the evaluator passes NS_TENANT_READINESS (default serve) and NS_TENANT_STARTUP_CONCURRENCY to tenant-startup.create and to the runtime boot, with isWarm from a new tenant-startup isReady(tenant); checkConcurrency is the evaluator pool size (NS_POOL_EVALUATOR_MAX); startup.health() is in health() and the inspection (startup, additive); the consumers' prepare tenant loop runs through perf-db's settleLimited at the startup concurrency instead of one tenant after another (the first failure still refuses the boot). The role-booting labs and the evaluator boot-protocol test run under NS_TENANT_READINESS=all, as perf-db did for the api's.

    Consumers on change (lib/server/serve/evaluator-consumers.js)¶

    • The pollIntervalMs/retryIntervalMs loops visit only active tenants: a pending or refused request, or an armed repeat clock (an alarm already delivered). Acks, snoozes and retries are seen as promptly as before where they can matter; an ack reaches the consumer through its next selection, and only a tenant with a delivered alarm can be acked.
    • A newly alarming tenant is found by the evaluator's revision wake (revised); a repeat by its arm timer.
    • Every tenant is visited by the slow backstop, backstopIntervalMs (default 60,000). Every pass, including the start pass, works at most maxConcurrentTenants (default 4) tenants at once. Both are optional consumer config fields; deploy/multitenant/config.js is unchanged (its 1,000 ms intervals now apply to active tenants only).
