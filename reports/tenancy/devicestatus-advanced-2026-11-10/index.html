    devicestatus.advanced in a multitenant tenant: client state measured against a single site¶

    Living document, last changed 2026-11-10 at 3a8024827.

    Evidence record, lane E1, 2026-11-10 (contributor-facing). Measurement; not edited after capture. Result: not reproduced. The setting differs between modes; the client state it controls does not, for the frames a tenant sends. No code change was made.

    1. Claim under test (read-derived, from tenant-extended-settings §6.3)¶

    A single site defaults devicestatus.advanced to true (lib/server/env.js:396). A tenant leaves it unset, so lib/client/receiveddata.js:159 takes the replace branch instead of mergeDataUpdate, and the browser's device status would differ from a single site's given the same frames.

    No queue item covers it: queue/work-queue.yaml mentions it only as an open note on the tenant extended-settings item (BF-232 lane).

    2. Mechanism read on 16a1fc2d¶

    • receiveddata.js:158-165: with advanced set, ddata.devicestatus = mergeDataUpdate(received.delta, …); without it, ddata.devicestatus = received.devicestatus.
    • receiveddata.js:46-49: mergeDataUpdate returns the received array unchanged when delta is false. So the flag changes client state only for delta:true frames.
    • The tenant's only dataUpdate source is lib/server/realtime/projection.js:29 ({ ...snapshot.ddata.dataWithRecentStatuses(), lastUpdated: at, delta: false }), wired as the sole create in lib/server/serve/preview-realtime.js:64, sent by protocol.js:110 and :196. The realtime README states main connections always receive full frames so absent rows replace browser state. retroUpdate (protocol.js:159) is stored in client.retro and does not read the flag.
    • The single site sends incremental frames marked delta: true (lib/data/calcdelta.js:8, emitted at lib/server/websocket.js:122), which is where the flag matters.
    • The only reader of devicestatus.advanced in lib/ is receiveddata.js:159. A search of the client repositories in externals/ (AndroidAPS, LoopCaregiver, LoopFollow, LoopWorkspace, nightguard, NightscoutKit, nightscout-reporter, nocturne, Trio, xDrip, xdripswift, DiaBLE, nightscout-connect, cgmsim-lib, mobile-ios, nightscout-roles-gateway) for devicestatus…advanced returned no file.

    3. Reproduction: not reproduced (client state); the setting difference is reproduced¶

    Harness: repro-base.js, synthetic data only (one synthetic Loop device, four statuses). It runs the actual realtime/protocol, realtime/runtime, realtime/projection, tenant snapshot, ddata.dataWithRecentStatuses and the projection-read SQL on the real PostgreSQL; only the replay bookkeeping queries (checkpoint, clock, counts, the replay page) are answered by a double, as in tests/realtime-preview.test.js. A recording socket authorizes on / with status:true; the store then loses status 1 and gains status 4, and the recovery backstop fans out. The captured frames are fed to the actual lib/client/receiveddata.js twice: with the tenant's served extended settings and with a single site's.

    5. Why the fix was not applied¶

    The brief makes the fix conditional on reproducing the client-state difference. It did not reproduce, so adding advanced: true to the tenant EXTENDED catalogue (lib/server/tenant-app/environment.js) would change only the value reported in /api/v1/status and the realtime status frame, with no measured consumer. The lane worktree and branch hold no commits.

    6. For the coordinator¶

    • No register-worthy defect found. Mechanism, for the record: the tenant omits a single-site default setting value from its status responses; the one reader of that value is a no-op for full frames, and the tenant sends only full frames.
    • Open, a decision rather than a defect: under the standing rule (multitenant behaves as a single tenant), whether /api/v1/status for a tenant should report devicestatus: {advanced: true, days: 1} for parity of the reported value alone. No client in the corpus reads it. If adopted, it must be documented as display-only for tenants while frames stay full, and the break-it row above is the test that should accompany it.
    • Suggested updates (not made here): the tenant extended-settings queue item's note "devicestatus.advanced … unset for a tenant (read-derived …)" can be closed as measured, not reproduced, citing this record; nothing for decisions.md, contents.md or the register unless the parity question above is taken.

    7. Fix (maintainer decision), 2026-11-10¶

    Decision relayed by the coordinator: a tenant reports devicestatus: {advanced: true, days: 1} in its status, for parity with a single site. The measurement above is unchanged; this section records the change made on that basis.

    Branch codex/devicestatus-advanced-20261110, head 0df0e66f25baacc329df4238dd8b98163fc785c3 (one commit on 16a1fc2d, not pushed; 6 files, +96/-24).

    file change
    lib/server/tenant-app/environment.js devicestatus: { advanced: boolean } joins EXTENDED; days stays limited to 1 or 2. The status projection (filteredSettings of a tenant's extended settings) adds DEVICESTATUS_REPORTED = {advanced: true, days: 1} under the operator's values. The environment object still carries only operator-supplied values, so the evaluator configuration's equality check (evaluator-config.js:53-54), its identity, and server-side day loading (cache.js:30, dataloader.js:494) are unchanged. Comment states display parity while frames stay full.
    lib/server/realtime/protocol.js the realtime status frame reports the same projection as the status route (it sent the raw environment object before).
    cgm-remote-monitor's architecture document multitenant-api-preview.md extendedSettings paragraph: the reported defaults, the operator override and types, display parity while tenant updates are full snapshots.
    tests/tenant-extended-settings.test.js EXT_DEVICESTATUS_DEFAULT, EXT_DEVICESTATUS_OVERRIDE (advanced false, days 2, both, mistyped values fall back to the defaults), evaluator config accepts advanced:false; EXT_ROUNDTRIP now carries devicestatus.advanced (from the catalogue) with days: 2; EXT_UNKNOWN_REFUSED adds advanced:'true' and days:3; devicestatus.advanced removed from EXT_EXCLUDED; per-request display view shows the defaults and the environment does not copy them.
    tests/realtime-preview.test.js RT_DEVICESTATUS_DEFAULT (tenant A frame reports the defaults, delta === false) and RT_DEVICESTATUS_OVERRIDE (tenant B's operator value, B only). The full-frame guard is the existing RT_ACTUAL_FULL_RESET in the same file, unchanged.
    tests/tenant-rest-context.integration.test.js over HTTP on both backends: tenant A (operator advanced:false, days:2) and tenant B (unset, {advanced:true, days:1}) in /api/v1/status.json.

    Choice made in the implementation: the default is applied where the tenant reports settings, not inside the environment. Putting it in the environment would make every existing operator evaluator configuration that supplies extendedSettings differ from its projection and be refused (read-derived from evaluator-config.js:53-54; not run). Both reporting surfaces (status route, realtime status frame) go through the one projection.

    Harness after the fix¶

    repro-base.js re-run on 0df0e66f (PostgreSQL 16.15 container, removed): tenant status route and realtime status frame {"advanced":true,"days":1}, single site {"advanced":true,"days":1}; client device status [1,2,3] → [2,3,4] with both, tenantFramesDiffer: false.
