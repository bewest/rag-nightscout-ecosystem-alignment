    3. Design points settled in-lane¶

    1. Config sources. NAME inline or NAME_FILE path, exclusive, for OIDC_ACCESS_CONFIG, OIDC_ACCESS_SIGNING_KEY, OIDC_IDENTITIES. An OIDC_ACCESS_CONFIG value not starting with { is the earlier path form and is still read. Local key and access JSON together refuse. Operator-written refusals carry code: OIDC_CONFIGURATION_INVALID; bootevent.js now shows those messages (they name settings and role names, never values, keys or file content) instead of the fixed string.
    2. Local signing. One Ed25519 PKCS#8 PEM; data and management keys derived with HKDF-SHA256 (salt nightscout-human-access-local-v1, info = purpose) because createHumanAccess requires distinct key material per purpose. kid = local-<purpose>-<22 chars of sha256(spki)>. Issuer nightscout-human-access:<OIDC_ORIGIN>, audiences nightscout-human-{data,management}:<OIDC_ORIGIN>. At start the kids are written as accepted keys (source: 'local'); a kid no longer configured is set inactive, so a key change ends existing access at the next request. Local key in multi mode refuses.
    3. Current roles. A principal's subject is an auth subject _id; roles.forSubject reads <prefix>subjects and <prefix>roles (stored over shipped defaults) at every operation, in every process. A missing subject grants nothing. The role read is outside the authority-document CAS: a role edit racing one in-flight operation applies from the next (the PostgreSQL adapter reads both in one statement; this is a read-derived difference, not measured as a race).
    4. Migration. lib/human-session is not in official/dev (preview only, #8898), so no operator database holds principals. A stored permissionGroups field is ignored; such a principal grants only through its subject (test "migration": a [['*']] copy grants nothing).
    5. List semantics: authoritative for what it manages (Grafana/Kubernetes-style declarative provisioning). Each entry gets a deterministic subject _id (sha256 of the binding id, 24 hex) so concurrent starts write the same rows; roles re-applied at each start; an entry removed from the list has its subject deleted first, then its binding removed (an interrupted start finishes the removal next time, no orphan subject). Bindings not created by the list are untouched; a list entry colliding with one refuses at start. Unknown role names refuse at start before any write. Between starts the database governs. Open for the maintainer, see section 6.
    6. Email. Email bindings are a separate id namespace hash([tenant, issuer, 'verified-email', email]). The provider returns email plus emailVerified only for a boolean email_verified === true; the session keeps the address only if verified; renewal replaces it with the issuer's current value. Case-insensitive compare. The email scope is requested only when an email entry exists.
    7. Fallback. OIDC_FALLBACK_ROLES (unset = refuse, the pre-lane behaviour; not a changed default). Data purpose only; per-person derived subject oidc-<40 hex>; no binding stored. Fallback sessions share at most 32 of the 128 slots and the oldest is evicted, so strangers cannot exhaust capacity for listed people.

    6. Open decision for the maintainer¶

    List authoritative vs. database wins at start. Mechanism: lib/human-session/provision.js re-applies listed roles to the list's subjects and removes bindings (and their subjects) whose entries left the list, at every start. Trade-off: chosen behaviour means editing the file always takes effect at restart, and removing someone always removes access; the cost is that an admin-UI role edit on a list-managed subject lasts only until the next restart (the subject's notes say so). The alternative, "seed only what is missing" (closest to how default roles fill gaps), keeps admin edits but means a role change or a removal in the file does nothing for an existing entry, which leaves access in place after an operator thinks it is gone. Recommendation: keep list-authoritative (safety on removal, predictability, matches declarative provisioning). Single-site only; multitenant is unaffected.

    Smaller points for review, not blocking: each list subject has the derived legacy access token every subject has (same roles, visible in the admin UI); a renewal whose fresh proof no longer matches returns a token that the next request refuses, rather than refusing the renewal itself.

    7. Operator summary (plain language)¶

    When sign-in is turned on (ENABLE=oidc), a single Nightscout site can now:

    • Say who may sign in and what each person may do, in one setting or one file. For example OIDC_IDENTITIES=sub:248289761001=careportal+readable,email:carer@example.test=readable lets the first person read and enter treatments, and the second only read. A person is matched by the account ID your sign-in provider gives them, or by their email address only when that same provider confirms the address is verified. The list can also be a CSV, TSV or JSON file (OIDC_IDENTITIES_FILE). Role names must already exist (for example readable, careportal).
    • Choose what anyone else who signs in can see with OIDC_FALLBACK_ROLES, for example readable. Leave it unset to turn away people who are not on the list. Anyone with an account at your sign-in provider can reach the fallback, so choose it as carefully as AUTH_DEFAULT_ROLES.
    • Change access without restarting: each listed person appears as a subject in the admin page, and changing that subject's roles there applies at their next request. At the next restart the list is applied again, and anyone removed from the list loses access.
    • Run without Vault: set OIDC_ACCESS_SIGNING_KEY (or OIDC_ACCESS_SIGNING_KEY_FILE) to a private key made with openssl genpkey -algorithm ed25519. Keep it secret like API_SECRET. Replacing it signs everyone out. Multitenant sites keep using Vault.
    • Settings are never both inline and as a file: setting X and X_FILE together stops sign-in from starting, with a message saying so.

    Nightscout shows CGM and pump data as a secondary display; these settings only decide who can view or enter data on your own site.

    8. UNMEASURED / not established¶

    • prcheck, test:browser, and the multitenant enabled corpus on this branch: not run (coordinator's frozen-candidate campaign).
    • The harness Mongo stages (mongo-sessions, mongo-http) use an in-memory roles double for the bound subject; actual subject/role collections are exercised by tests/human-session-provision.test.js (actual MongoDB), not inside the harness.
    • A role edit racing an in-flight operation (section 3.3): read-derived, not measured.
    • Real OpenID provider interoperability (email claim placement in ID token vs userinfo, email_verified types): synthetic provider only. Providers that put email only in userinfo will not match email entries.
    • Concurrent starts of several processes provisioning at once: deterministic ids and the revision CAS are read-derived as safe; not measured with parallel boots.
    • Pre-existing, not changed: data sessions are never pruned, so a listed person who signs in 33 times without signing out is refused for capacity (mongo.js per-principal 32). Read-derived.
