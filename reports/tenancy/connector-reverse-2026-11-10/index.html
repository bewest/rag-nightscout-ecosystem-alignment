    Design¶

    Write path: HTTP to the api role¶

    The connector writes through the tenant's own API over HTTP to the api role. It does not use an internal service contract. The decisions point to this path:

    • first-preview-no-push-provider says the connector is "writing through the tenant's own API as a tenant-bound subject".
    • D23 (lib/server/serve/roles.js header) says "On the data path api is the only writer".
    • internal-service-contracts covers realtime authority and writes, alarm delivery and lifecycle coordination. It has no data-ingest contract.
    • internal-listener-ory-pattern says serve.internal trusts its network and has no authentication of its own. A write sent there would not carry the subject's authority.

    The decisions do not conflict on this point, so this lane did not stop to ask.

    The connector authenticates with no change to nightscout-connect. Its Nightscout output sends API-SECRET: sha1(<credential>). The tenant verifier treats the sha1 of a subject's access token as that subject, as a single site does (lib/secrets/component.js:110,114). The credential is the connector subject's token, never the tenant root.

    Two deliberate departures¶

    1. The vcpool owns the schedule. The connector runs the driver's frame functions, not its xstate machine, so the per-cycle slice and activity checks can stop a tenant before any request. As a result the driver's own backoff (2.5 min × 2^n) is replaced by a fixed retryMs (default 150 000 ms), and session refresh is the frame's TTL rule.
    2. partition=on is admitted for vcpool. The evaluator refuses it in this build. The vcpool already has the per-cycle slice check that the evaluator lacks. The preview default stays off.

    Connector subject grants¶

    Create-only grants do not work on the v1 API. Two reasons:

    • The tenant API requires read on the collection for every v1 request, POST included (lib/server/tenant-app/data-access.js:52,57,147).
    • The driver's output reads the newest row of entries, treatments, devicestatus and profile to find its gap, and reads devicestatus for its checkpoint list.

    The lab subject role is api:entries:read,create, api:treatments:read,create, api:devicestatus:read and api:profile:read. This was measured: with create-only grants, A refuses with CONNECTOR_GAP_FAILED and write:401 × 6.

    Setup:

    • the api role with activity gating;
    • two single-site Nightscout sources, one per family, on their own MongoDB databases, each with a readable reader subject;
    • tenants A and B, each with a connector subject;
    • operator entry of three tenant secrets per tenant through the secrets component (an operator binding with encrypt only);
    • one vcpool process with the egress proxy pointing at a counting forward proxy.

    The oracles read tenant rows directly from PostgreSQL (preview_data.entries, preview_treatments.treatments) and source rows directly from MongoDB. They compare multisets of (type, sgv, date) for entries and (eventType, notes, created_at) for treatments.

    Findings and points for the maintainer¶

    1. Decision needed: pause versus a connector built during the pause. While a tenant is paused, the api refuses reads with HTTP 423 (lib/tenant-activity/serving.js:14-19 classifies every GET except the token exchange as a read). The driver's output reads the tenant to find its gap. A connector that existed before the pause keeps pulling, because its gap is cached in memory, and that is the case the gate measured. A connector built during the pause cannot pull: after a vcpool restart, a refusal, or a slice or activity change, it gets no gap. Measured: after a restart while A was paused, A stayed at 55 rows with source at 56, CONNECTOR_GAP_FAILED, write:423 ×30. After unpause, 56/56 with no duplicate. No data is lost, but the pull waits for unpause. Options:
    2. (a) Accept this for the first preview. The behaviour is now visible as write:423.
    3. (b) Let the api's paused gate admit the reads an uploader needs. This touches the activity decision, and Loop or AAPS reads during a pause raise the same question.
    4. (c) Give the vcpool a durable per-tenant bookmark. That is a new storage path.

    Recommendation: (a) for the preview, because nothing is lost and the state is visible. Take up (b) with the uploader read question, which is single- and multitenant alike. Unmeasured: whether uploaders other than the connector read during a pause. 2. Grants. As described under Connector subject grants, a create-only subject cannot write through v1. This lane provisioned read and create. Owners cannot configure this subject in the first preview: it is operator-provisioned. 3. roles.js change. vcpool.storage changed from 'write' to 'read', and describeComposition now lists it among the readers. 4. partition=on admitted for vcpool, unlike the evaluator. See departure 2. 5. Operator procedures that do not exist yet. - There is no operator command to enter a tenant secret. The lab used the secrets component's encrypt with an operator binding. - Rotation needs a new reference id (the store is insert-only), a configuration edit and a restart. The configuration is read once at boot. - The tenant host for the Host header is configuration (tenants[].host); only direct-alias resolution was exercised.
