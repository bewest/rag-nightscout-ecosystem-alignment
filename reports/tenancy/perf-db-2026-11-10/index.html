    1. The guarantee (read from source at cb1b751d)¶

    A tenant's restore must never overlap a tenant write, and the census must refuse unknown writers. Four mechanisms carry it; only the fourth was expensive.

    invariant where
    I1 lock a serving backend holds pg_try_advisory_lock_shared(key_t) for every tenant transaction, taken before BEGIN; restore takes pg_try_advisory_lock(key_t) exclusively, which cannot be granted while any shared holder remains operation-window.js:63 (now acquire), maintenance-window.js:158
    I2 phase inside the transaction, after binding app.current_tenant_id, the window row must read phase='active' with the configured lock_key; restore commits phase='suspended' (new generation, claim) before draining operation-window.js:87-91 (now in assertClient), maintenance-window.js:141-151
    I3 operations a serving operation commits an unfinished tenant_lifecycle_operations row (owner pid/birth by RLS) before its callback and finishes it after; restore waits for no unfinished rows before the exclusive lock, and re-checks under it operation-window.js:116,130, maintenance-window.js:155-159,106
    I4 admission the serving identity cannot alter or bypass I1–I3: not elevated or member of an elevated role; no CREATE on the database or any schema; does not own the namespace; the five control tables, their columns, defaults, constraints, forced RLS and exact policies, no triggers/rules/inheritance/foreign indexes, a NOLOGIN safe owner, exact column privileges; the birth helper exact; the migration ledger exact; for the lifetime identity, no write on any other relation and no EXECUTE on any other non-system function; object oids unchanged since ready(); datastore identity unchanged; not superuser/BYPASSRLS operation-window-readiness.js:232-293, called per transaction at operation-window.js:57-60
    census restore refuses a connected backend that is neither a registered participant nor an identity without clinical privileges and counter writes operation-cohort.js:79-133 (unchanged)

    I1–I3 were already the cheap, database-enforced per-tenant epoch and lock the brief lists as candidates (generation/phase row + shared/exclusive advisory lock). What cost 5–9 ms per call was I4: the full catalogue admission, re-run on every data transaction (lower) and every operation (lifetime).

    2. Design chosen: a catalogue epoch read inside the transaction¶

    Candidate taken: "a cache keyed on an epoch", with the epoch computed by the database inside the transaction from the live catalogue. lib/tenant-lifecycle/operation-window-epoch.js builds one expression: a SHA-256 over the oid/key and row version (xmin) of every catalogue row the admission reads (pg_class, pg_attribute, pg_attrdef, pg_constraint, pg_policy, pg_trigger, pg_rewrite, pg_index with its validity flags, pg_inherits for the five tables; the helper's pg_proc and pg_language rows; every pg_namespace row; the current pg_database row; every pg_auth_members row), the live attributes of every role, the current role's oid, the names re-resolved to oids, and the ledger rows. For the lifetime identity it also covers every user pg_class and pg_proc row (oid >= 16384, a superset of the swept namespaces) and every user pg_attribute row with a column ACL. PostgreSQL gives every committed catalogue change a new row version, so any grant, policy, owner, membership, object or ledger change changes the epoch.

    Per transaction (operation-window.js acquire / assertClient): shared lock (I1) → BEGIN → bind tenant → one prepared statement returning the epoch, rolsuper/rolbypassrls, the datastore identity and the window row (I2). An epoch the window has not admitted runs the full admission (I4) on that backend and is cached only if the epoch read after it is unchanged (two attempts, then LIFECYCLE_WINDOW_SCHEMA_UNSAFE). I3 and the census are unchanged.

    Rejected:

    • shared/exclusive lock taken by DDL: GRANT/ALTER ROLE do not take a lock a reader would see; it would rely on every DDL actor cooperating, so it is not database-enforced.
    • event-trigger epoch row (DDL bumps a counter): needs a superuser-created event trigger and a new control migration (deployment and managed-PostgreSQL impact), and still misses global objects (role attributes, memberships, database ACL), which would need the same direct reads anyway.
    • process cache with a time-to-live: not validated by the database; refused by the brief.

    Why this one, measured: the epoch statement costs 0.75 DB-ms (lower) and 1.5 DB-ms (lifetime) per transaction against at least 2.6 and 9.4 for the admission it replaces (table below), needs no migration, privilege or deployment change, and keeps every I4 check reachable on any change.

    Coverage limits (read-derived): changes only a superuser can make to built-in objects (renaming a type or language) are not in the epoch; in-place catalogue updates (relpages, relfrozenxid, …) do not change xmin but are not admission inputs. In a REPEATABLE READ snapshot transaction the epoch reads the transaction snapshot while privilege functions read the current catalogue; the re-check after admission is then trivially equal. A superuser can defeat any of this, as before.

    • DB-ms per tenant-minute is not a per-tenant cost at idle. It falls as N rises because the idle DB work is the evaluator's and realtime's per-tenant one-second polls, and those loops are throughput-bound: total operations per minute fall while N grows. The window's own share is now the epoch statement (§3.1).
    • Connections are fixed by the pool caps (evaluator 4, lifetime evaluator 8, lifetime realtime 8, realtime 4, outbox 2, suppression 2, maintenance 1; api's idle clients had been released): zero marginal connections per tenant. Pool waits were not instrumented (UNMEASURED); the collapse of operations per tenant is the observed effect.
    • api resident memory: about 0.65 MiB per tenant from 10 to 1,000 (derived from single samples); 3,000 tenants ≈ 2 GiB, 10,000 ≈ 6.5 GiB (derived, extrapolated).
    • Real cadence: not run in this lane (UNMEASURED); the k6 workload of MT-BENCH-BASELINE was not repeated at these tenant counts.

    What runs out first, and at about what N (derived from the table): the evaluator's per-tenant cycle. At 100 tenants each tenant is evaluated about every 6 s, at 1,000 about every 5 minutes, so time-driven alarms lag by minutes long before PostgreSQL CPU (82% at 1,000), connections (fixed) or memory (≈0.65 MiB per tenant) limit anything. Realtime refresh is second (2.5 minutes per tenant at 1,000). Both are the per-tenant poll model that the decision's items 1–2 replace (other lanes). Next after those: startup time at concurrency 4 grows about 0.34 s per tenant (≈17 minutes at 3,000, ≈57 minutes at 10,000, derived), and the stock Compose healthcheck budget (30 × 2 s, no start period) is shorter than the measured api start from 500 tenants (112 s).

    They now assert M5_HARD_DELETE_CLOCK / M5_ACTIVITY_CLOCK: the floor advances and the event carries the commit stamp. Unchanged: - activity rows still carry no srvModified; - replay of an unstamped row is still refused (REPLAY_UNSTAMPED_OR_UNFENCED_ROW); - snapshot recovery still reconciles.

    Readiness regression found and fixed (4851847b). The commit-clock HTTP suite failed 6 of 8 with listener must answer through current anonymous authority: 503 !== 403. - Cause: the serve-then-warm default (a52bc33b). The api CLI fixtures expected served requests as soon as the listener answered. - Fix: they now start the api with NS_TENANT_READINESS=all, as the decision provides for acceptance. - Earlier miss: these suites are opt-in, so the earlier integration-tier runs had them pending.
