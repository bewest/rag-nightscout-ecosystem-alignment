    2. What the change does¶

    • Completeness before removal (lib/tenant-lifecycle/key-retention.js assertKeyCompleteness, called from verifyDeletionRows in the destructive transaction and at claim). The artifact must name every key a trusted keyInventory({tenant}) capability returns (names only, [{mount,name}]) and hold every live ciphertext with its key reference. Refusals: LIFECYCLE_KEY_NAMES_MISSING, LIFECYCLE_KEY_REFERENCE_MISSING, LIFECYCLE_KEY_REFERENCE_UNKNOWN, LIFECYCLE_KEY_MATERIAL_UNVERIFIED. A missing per-ciphertext reference is refused earlier, at artifact validation (LIFECYCLE_CIPHERTEXT_WITHOUT_KEY_REFERENCE, existing).
    • Retention record: new lifecycle migration 0005_tenant_lifecycle_key_retention (checksum a12b4238…8fa7d), forced RLS, written in the same transaction as the deletes: retained, retain_until = executed_at + 30 days, key names, key-reference count. No ciphertext. CHECK constraints refuse restored_at outside the window and a destroy start before retain_until.
    • Restore gate: importArtifact and restoreLogical require ledgerNamespace; inside their transaction, before the first write, they refuse LIFECYCLE_KEYS_DESTROYED (any record destroying/destroyed) or LIFECYCLE_RETENTION_EXPIRED (a retained record past its window). Inside the window the restore proceeds and the record becomes restored. Never-deleted tenants have no record and are unaffected.
    • Destroy: destroyRetainedKeys is operator-plane only (via authorize, action destroy-keys), requires the intent string destroy-retained-keys:<tenant>:<requestId>, an ended window, and zero tenant rows in every admitted table. It commits destroying with actor/time, calls the custodian, then commits destroyed with actor/time. Provider failure leaves destroying (restore still refused); retry is explicit and idempotent.
    • Custodian: lib/secrets/vault-transit-custodian.js — separate operator credential; per key it checks keyAllowed, sets deletion_allowed, deletes, confirms 404 (absence, not 403). Fixed error codes only.
    • Time is the injected now of each call; the 30-day constant is not configurable.
    • Pre-existing defect fixed (reproduced): ceremony.js ready() admitted only [tenant_lifecycle_requests, tenant_lifecycle_ceremony] in the ledger namespace, while the candidate's 0003/0004 create four more tables there. On base dc795bd1, a namespace migrated with the full candidate (0001–0004) refused requestDeletion with LIFECYCLE_RELATION_UNADMITTED: lifecycle.tenant_lifecycle_operations (native probe, PostgreSQL 16). The lane head lists every candidate-created table (LEDGER_TABLES); the same probe returns accepted. The recording unit double modelled only two tables, so the unit tier could not see it.

    7. Operator note (plain language)¶

    After you delete a site, its encrypted settings and credentials can still be brought back for 30 days, because the keys that unlock them are kept. Once the 30 days have passed, Nightscout refuses to restore that site, and you can run the destroy step. Destroy cannot be undone: it permanently deletes the site's encryption keys, so the site's stored credentials — in the database and in any saved export file — can never be decrypted again by anyone. Destroy asks you to type the exact site and request identifiers, only runs after the 30 days, refuses if the site has data again, and records who ran it and when. It never shows a key or a secret. Glucose and treatment records in an export file are not encrypted by these keys; delete the export file itself when you no longer need it.
