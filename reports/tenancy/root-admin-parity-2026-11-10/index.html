    Decision questions¶

    Q1. Role edit and delete (PUT/DELETE /api/v2/authorization/roles). Answer 501 today. Mechanism: the audit constraint admits only update, remove, create, create-role, issue, owner-* (lib/tenant-authorization/postgres-candidate.json migration 0006), so an audited role update needs a new migration; the writer has no UPDATE(permissions) or DELETE on roles; roles are keyed by name and tenant_authorization_subject_roles has a foreign key to them, so deleting a held role fails where a single site leaves dangling names, and a rename would rewrite links. Options: (a) migration 0007 adding update-role/remove-role, grants on the root identity only, update inside catalogue ∩ ceiling, delete refused while held, rename refused; (b) keep 501. Recommendation (a): the admin tools' Save on an existing role is a PUT, so parity is incomplete without it; refusing a held delete keeps current authority valid (a missing role makes the authority throw TENANT_AUTHORITY_INVALID for every holder, read-derived from lib/tenant-authorization/postgres.js). Unmeasured: migration numbering against peer lanes. Multitenant only.

    Q2. Root's grant bound. Root is bounded by project catalogue ∩ operator ceiling (owner authority: owners "cannot exceed operator/project bounds"). In the compose demo the catalogue is ['api:entries:read'], so root there can grant only that; on a single site API_SECRET can grant *. Recommendation: keep the operator bound (root must not exceed operator authority) and have deployments that want single-site behaviour set catalogue and ceiling to ['*']. Multitenant only.

    Q3. Subjects with admin permissions. On a single site any subject whose roles grant admin:api:subjects:* (for example the default admin role, *) can use the admin tools (managementPermission in lib/authorization/endpoints.js). The restored routes accept only the root secret; owner authority states that data permissions including * confer no management membership. Recommendation: keep root-only; record the difference for operators.

    Q4. Tenants without an owner policy row. Root authority reads the policy row for catalogue digest and ceiling; without it every root admin call is 403 (read-derived from owner-policy.js authority). Operators must provision the policy row for root parity, as for owners.

    No defect is proposed for a BF id: the M6b item-2 property (a writer blind to ownership) is now closed by construction (case 8, C1) and measured on the root plane (race case).
