    Evaluator partitioning (MT-EVALUATOR-PARTITION, M7), lane EP: stopped at the overlap premise, 2026-11-10¶

    Living document, last changed 2026-11-10 at dcba324d8.

    Contributor-facing evidence record for lane EP. Captured 2026-11-10; not edited after capture. Decisions read: evaluator-static-partition, pool-primitive-shared, evaluator-partition-now, evaluator-revision-on-content-change and alarm-repeat-clock. Synthetic data only.

    Outcome¶

    The lane stopped before implementation, on the condition its brief named: the evaluator's notification output is not idempotent across two overlapping members. The evaluator-static-partition decision accepts duplicate evaluation "bounded to one heartbeat interval after a membership change" because "the evaluator's outputs are idempotent by contract (... notification intent with stable identity and suppression)". The shipping producer gives a new alarm effect, and so a new delivery request, on every pass in which the evaluator output it reads came from a different runtime than the previous pass. The decision says a measured duplicate external effect reopens the question; this is that measurement. No code was committed. The queue, decisions.md, contents.md and the register are unchanged.

    The finding¶

    Mechanism (file:line at 1792063a)¶

    1. The evaluator runtime stamps every output with a per-process runtimeId = randomUUID() and a per-process counter outputRevision (lib/server/serve/evaluator-runtime.js:42,115).
    2. The producer decides a pass is a fresh output by comparing the tuple [identity, runtimeId, outputRevision, inputCheckpoint] with the tuple stored in the durable producer state (lib/tenant-notifications/producer-state.js:43-44). A fresh pass runs the legacy notification processing, which emits the highest unsnoozed alarm (:70-79). The repeat clock applies only when the pass is not fresh (:49).
    3. Each emitted effect gets origin = digest(['producer-transition-v1', revision, i]), where revision is the producer-state revision (producer-state.js:88). The intent key is 'realtime-cycle:' + digest(identity) + ':' + origin (lib/tenant-notifications/producer.js:62).
    4. The store coalesces a re-presented intent only on the same key (lib/tenant-notifications/postgres.js:55,64); a new key inserts a new request (:72), which the notifier attempts.

    The producer state is shared in PostgreSQL per (tenant, consumer), and both members use the same consumer id. When two members both work one tenant, each pass sees the other member's runtimeId in the stored tuple, so every pass is fresh, re-emits the active alarm under a new key, and is delivered. The per-tenant advisory lock (producer-state.js:10-15) serialises the passes; it does not merge them.

    Measurement (reproduced, reducer level)¶

    Probe: reduce-probe.cjs drives the shipping reduce with one synthetic urgent alarm request, identical content, one pass per second for 10 s, repeat interval 60 s. It counts new non-clear alarm effects. Output at 1792063a:

    arm runtime ids per pass new alarm effects
    single owner A ×10 1
    two owners alternating A, B, A, B ... 10
    control: same alternation, one runtime id A ×10 1
    two owners, output revision numbers also differ A(1), B(7) ... 10
    handover, A for 3 s then B A A A B B B 2

    The control arm separates the cause: alternation alone gives 1; a second runtime id gives one effect per pass. The handover arm shows that a clean hand-over (no overlap) re-sends the active alarm once on the new member, as a single-site restart does.

    Read-derived, not run: that each new effect becomes a delivered request end to end through PostgreSQL and the alarm adapter (steps 3-4 above). No container was started.

    What this means for the gate¶

    The queue gate requires that "bounded overlapping evaluation produces no duplicate logical durable/external effect". With the decision's overlap bound (one heartbeat interval) and the consumer poll every pollIntervalMs, an overlap would deliver up to one extra alarm per poll per overlapping member, in place of one per repeat interval (60 s by default). Acknowledgement and snooze still hold: the alarm snapshot and the applied acknowledgements live in the shared producer state, and every pass re-reads acknowledgements (producer-state.js:59-68, read-derived). The duplicates are early repeats of an active, unacknowledged alarm. They are not a wrong alarm and not a silenced alarm sent again.

    Decision for the maintainer¶

    Question: the decision tolerated overlap on the strength of output idempotence, and the producer is not idempotent across runtimes. Which of these replaces that premise?

    option mechanism trade-off operators would notice
    (a) fence the overlap Each member treats its eligibility as valid only until its last successful heartbeat start plus leaseMs (a local lease bound, under the database-clock expiry of its row). The runtime re-checks before it publishes, the consumer coordinator gets a pool gate like its activity gate (evaluator-consumers.js:51-56), and the notifier's mayAttempt (:31) already refuses when the runtime output is withdrawn. Membership table only, no per-tenant lock. Overlap shrinks to work already in flight when validity ends (an adapter send). Depends on process clock rate against the database clock over one lease. Nothing in normal operation; after a stall, the stalled member stops at once rather than at its next check.
    (b) content-based freshness in the producer Replace [runtimeId, outputRevision] in the producer tuple (producer-state.js:43) with the evaluator's content digest (evaluator-runtime.js:18-20), so two runtimes with identical output are one output to the producer. Repeats stay on the durable repeat clock. Restores the decision's premise without coordination. Touches the alarm-repeat-clock work (BF-231). A restart or hand-over with unchanged content would no longer re-send at once; the next repeat comes from the stored repeatAt. Two members whose inputs differ by one new row still alternate until both have read it. Affects single owner and partitioned alike. One fewer immediate re-send after an evaluator restart, which differs from a single site (single-site re-sends after restart because its alarm state is in memory).
    (c) per-tenant commit fence A per-tenant lease or fencing token on publish. Rejected 2026-11-09 as unnecessary overhead; listed only because the decision says this measurement reopens it. Nothing visible; more writes.

    Recommendation (long-term direction, reliability, compatibility): (a) now, keep (b) open. (a) keeps the membership-table design and the single-tenant alarm behaviour unchanged, and makes the overlap a fault-path residue instead of a planned window. (b) changes alarm behaviour for every deployment, including single owner, and belongs with the BF-231 repeat-clock work if it is wanted. Unmeasured for both: the overlap window and duplicate count in the lab, and the clock-rate assumption in (a).

    Single- or multitenant: multitenant only for (a) and (c). (b) changes the multitenant producer that a single owner also uses.

    Other findings for whoever resumes (read-derived)¶

    1. Boot refusal blocks a rolling count change. evaluator-preview.js:37 throws when the slice is refused at boot (exit 78 through the CLI). During a 2→3 change, the first count-3 member boots while count-2 rows are live, is refused with POOL_COUNT_DISAGREEMENT and exits, so it crash-loops until every old member is gone. The vcpool has the same boot rule. A partitioned evaluator should boot refused, raise the alert and wait.
    2. The agreement rule stops the whole kind for the length of a rollout. From the first count-3 row until the last count-2 row is gone, every member is refused (lib/pool-membership/assess.js:13). The tick gap per tenant is therefore the rollout duration, not one lease TTL. Under the Kubernetes binding's OrderedReady policy (lane K record, reports/tenancy/k8s-binding-2026-11-10/README.md:54), a readiness probe tied to pool eligibility would deadlock the rollout: the new pod is never ready while old rows disagree, and the old pods are not replaced until it is. Readiness must not depend on eligibility, or the evaluator StatefulSet needs Parallel.
    3. Consumer timers are not gated by any per-cycle check. The realtime consumer has its own poll and retry timers (evaluator-consumers.js:98-99) and its repeat-clock wake. A gate only inside evaluator-runtime leaves those passes running on a refused member; they then reach the producer with whatever output the runtime still holds.
    4. The graceful path has no overlap. close stops consumers and the runtime before it deletes the member row (evaluator-preview.js:16,23), so a peer can become eligible only after this member has stopped. Overlap needs a member that stalls past its lease and resumes (a same-ordinal replacement registers after register deletes the expired row, lib/pool-membership/postgres.js:115), or the check-to-work interval the decision describes.
    5. Inspection listener in standalone mode. Serving an evaluator inspection contract whenever the evaluator runs would open a default socket ($XDG_RUNTIME_DIR/nightscout/evaluator.sock) in every evaluator process. Today a standalone evaluator opens none, and test fixtures start several evaluator processes on one host through serve.start without internal (tests/fixtures/evaluator-preview-worker.js:40, tests/fixtures/evaluator-consumer-worker.js:25). Proposed rule: always serve it when partitioned; serve it in standalone mode only when serve.internal is configured explicitly.
    6. Environment names. The canonical names are MULTITENANT_POOL_EVALUATOR_PARTITION, MULTITENANT_POOL_EVALUATOR_MEMBERS, MULTITENANT_POOL_EVALUATOR_ORDINAL, MULTITENANT_POOL_EVALUATOR_LEASE_MS, MULTITENANT_POOL_EVALUATOR_DATABASE_URL and MULTITENANT_POOL_EVALUATOR_NAMESPACE (lib/pool-membership/config.js, envName). The Kubernetes binding's provisional NS_EVALUATOR_POOL_MEMBERS and NS_EVALUATOR_POOL_ORDINAL map to the MEMBERS and ORDINAL names; the renderer's evaluatorPool should emit the core names. No alias was added.

    Design (file:line at cb1b751d)¶

    element where what
    content freshness lib/tenant-notifications/producer-state.js:50-53 The freshness tuple is [identity, contentDigest, inputCheckpoint]. An eligible output without a 64-hex digest is refused (NOTIFICATION_PRODUCER_CONTENT_REQUIRED). The runtime publishes the digest it already computes (lib/server/serve/evaluator-runtime.js:123).
    content-derived origins producer-state.js:72,82,91,109 Every emission is attributed to the step that caused it: ['output', prior output, next], ['repeat', next, stored repeatAt], ['ack', ack key, reset scope], ['reset', ...]. The origin is digest(['producer-transition-v2', cause, index within cause]). The cause uses only shared durable state and content, so two evaluators replaying one step derive one origin, hence one dedup_key. Distinct steps never share one: a return to an earlier output (A→B→A) has a different prior output, and each repeat has its own slot.
    clear provenance, acknowledgement, snooze, BF-231 repeat clock unchanged code paths postgres.js keeps a pending clear only while the current intents carry its exact origin. A clear's origin is stable across empty polls because effects persist in the producer state. Checked by the existing producer tests (stable clear origin, ack silence, stale clear retired, control clear with failed acquisition; all green) and by new tests: two acknowledgements of one output give two distinct clear origins. No mismatch found.
    desired count migration 0002_pool_desired_count (lib/pool-membership/postgres-candidate.json:17-19) Adds pool_desired(pool_kind, members, previous_members, slice_rule, revision, updated_at). On pool_membership it replaces expected_members with applied_members, the count this member currently works. The census pin moves to 08f21d64…d60f (lib/tenant-operations/catalogues.js:23).
    agreement and switch lib/pool-membership/assess.js:28-35 The count in effect is the desired count once every ordinal below it is live. Until then, and only while no live row has applied the desired count, it is the previous count if that count is fully live. Otherwise it is the desired count with the missing ordinals reported.     applied count lib/pool-membership/postgres.js:185 A member writes its applied count as soon as it changes, and again on every heartbeat.
    operator command lib/pool-membership/operator.js:34-48; lib/server/serve/admin-preview.js:53,97; contract pool-operations (/pool/get, /pool/members) The admin role composes pools beside, or instead of, ownership.     environment lib/pool-membership/config.js:47 MULTITENANT_POOL_<KIND>_MEMBERS is refused with a message that names setPoolMembers (POST /pool/members). A pod carries _PARTITION, _ORDINAL, _LEASE_MS, _DATABASE_URL and _NAMESPACE.

    Findings for the maintainer¶

    1. A killed member's serve.internal socket file blocks its restart in the same runtime directory. Observed: SOCKET_IPC_PATH_EXISTS at boot. In Kubernetes, a container restart within one Pod keeps a shared emptyDir /run/ns-ipc, so a crashed partitioned evaluator would not come back until the Pod is replaced. This is existing serve.internal behaviour (endpoint-composition lane). It matters now because every partitioned member opens a socket. The lab modelled Pod replacement by removing the file.
    2. The admin configuration now accepts pools without ownership (at least one service is required). This changes the admin role's configuration contract; the existing refusal of an empty composition still holds.
    3. The vcpool still exits 78 when it is refused at boot (the lane R rule). With the count in the table, a partitioned vcpool started before the operator sets its count exits with POOL_COUNT_UNSET. Aligning it with the evaluator (boot refused and wait) is a small change; it was not made here because the decision named the evaluator.
    4. Every member warms and observes every configured tenant (read-only). The configuration still lists all tenants on every member.
