    1. Bootstrap failure detail (reproduced)¶

    bootstrap.js printed {"error":"COMPOSE_BOOTSTRAP_FAILED"} for any error without a code. It now prints one JSON line: the same error code, detail (the underlying message, TypeError: prefix for non-plain errors) and at (top three stack frames, /opt/app/ stripped). Redacted from both: URL userinfo, password|secret|token=… clauses, SQL PASSWORD '…', Vault hvs./hvb./hvr. tokens, JWT-shaped strings and hex runs of 32+ characters (the generated passwords). A unit test feeds a synthetic connection string, password clause, Vault token and JWT and asserts none survives; duplicate key value … is left intact.

    Induced failure, real bootstrap container on a fresh stack (NS_DEMO_TENANTS=0, a deliberately invalid input; project nsdeployfixc, torn down after each run):

    The over-cap case itself, offline (compact role files for N synthetic tenants run through plan.validateFiles, the bootstrap's own validation, and printed with bootstrap.report): N=3000 gives "detail":"cannot read valid preview JSON configuration","at":["invalid (…/lib/server/serve/preview-config.js:15:9)","load (…/preview-config.js:56:13)",…]. Core wraps its own "too large" message in that generic one, so the detail names the loader and the frame, not the size; the size message is core's to improve.

    2. Compact JSON (reproduced)¶

    Role config.json, env.json, operation.json, admission.json, evaluator-metadata.json and ui/config.json are written compact; bootstrap/* custody files and ops/* operator files stay indented. The vault-agent overlay's rewrite of the api config.json/env.json is compact too.

    • Live stack, N=2: every role file is 1 line; role files total 17,106 bytes against 23,283 if indented (26.5% smaller). ops/config.json stays 988 lines.
    • Offline, synthetic documents with distinct keys (plan.documents → files → plan.validateFiles):

    Reduction 35.5% from N=1000 up. With core's 1 MiB cap the limit moves from under 2,000 tenants to between 2,500 and 2,600; 3,000 still needs a larger cap.

    Cap plumbing (off by default; read-derived, not run against a core that reads it): NS_BOOTSTRAP_CONFIG_MAX_BYTES on the bootstrap service (empty = off; integer up to 268435456, otherwise BOOTSTRAP_CONFIG_MAX_BYTES_INVALID). When set, the bootstrap writes MULTITENANT_CONFIG_MAX_BYTES=<value> into every role env.json and sets it for its own validateFiles. Variable name assumed from the peer core lane; core 0392acf9 does not read it. load-env.js (deploy tree) keeps its own fixed 1 MiB limit on env.json; at N=5000 the api env.json is not among the four largest files (each > 800 KB compact), so it is not the binding limit in this range (read from the size listing, not separately measured).

    3. Edge after a role restart (reproduced)¶

    nginx resolved api, realtime, ui once at startup. A role that comes back on a new backend address got 502 until the edge restarted. The Compose edge now mounts nginx.compose.conf: nginx.conf plus resolver 127.0.0.11 valid=10s ipv6=off; resolver_timeout 5s; and zone … 64k; server <name> resolve; per upstream. nginx.conf is unchanged, because the Kubernetes binding imports it byte for byte (lib/ns/nightscout.libsonnet:509) and 127.0.0.11 does not exist there; check-compose.js holds the two files equal apart from those lines (golden render still current). Locations, header stripping, websocket upgrade and security headers are unchanged: Socket.IO polling 200 and a Socket.IO client connected over transport=websocket through the edge; same polling/upgrade/header results with the old and new edge.

    Probe: one tenant, GET /api/v1/entries.json?count=1 with its synthetic token through the edge every 100 ms, 3 s client timeout. Times from the restart command's start.

    case address changed back to 200 after api healthy non-200 seen
    compose restart api alone no 1.3 s before healthy event one 503
    api stopped, old address held by a placeholder, api started (×5) yes 3.3, 6.4, 3.3, 6.4, 6.4 s 0.07–3.2 s 0–1 × 502, 1–2 transport errors
    compose restart api realtime evaluator tenant-admin (campaign shape, ×2) yes, shuffled 3.4, 1.7 s 0.8, −0.9 s 22 / 4 × 502

    The 3.2 s tail is one request in flight to the old address hitting the 3 s client timeout.

    Control (old nginx.conf mounted through a scratch override, api on a new address): no 200 for the whole 34 s window (3 × 502, 10 × client timeouts at 3 s, nginx dialing the vanished address); three curls after the window: 502 502 502. compose restart nginx (0.5 s), then the edge reached api again (401 without a token). Red as expected. Restored (nginx.compose.conf): back to 200 at 6.4 s.

    4. Start order (reproduced)¶

    depends_on: service_healthy: api waits for postgres and vault; realtime for api; evaluator for realtime; tenant-admin for postgres, vault and api; nginx for api, realtime, evaluator, tenant-admin and ui. Events from docker events during run --rm bootstrap then up --wait (seconds from the first start):

     0.00 postgres start      2.06 postgres healthy     0.01 vault start   2.10 vault healthy
 2.68 bootstrap start     5.86 bootstrap exit
 6.29 ui start            8.40 ui healthy

 9.43 realtime start     11.53 realtime healthy
 9.44 tenant-admin start 11.53 tenant-admin healthy
12.05 evaluator start    14.16 evaluator healthy
14.69 nginx start

    Mismatch with the brief, resolved toward the existing design: the bootstrap is not a depends_on of the roles. It stays in profile ops as the explicit one-shot step (check-compose.js asserts "Bootstrap must remain explicit"; the README calls it "not an application startup hook"). Making it a service_completed_successfully dependency would need it out of the profile, or would activate the demo restore service with it. demo.sh up runs it first, as above. Trade-off taken from the brief: the edge now also waits for the evaluator and tenant-admin, so an unhealthy evaluator keeps the edge from starting. The ownership-admin and vault-agent overlays already order their services (admin and ownership-grants on postgres; vault-agent on vault; api on vault-agent) and are unchanged. The Kubernetes README gains a paragraph: readiness probes, startup probes and Service names cover both concerns there; the binding is unchanged.

    Source checks (check-compose.js): start order with a control (drop nginx → evaluator: "nginx must wait for evaluator to be healthy"); a broken compose file (tenant-admin edge removed) went red with "nginx must wait for tenant-admin to be healthy"; the old nginx.conf went red with "nginx must use Docker DNS with a bounded validity"; edge drift control ("nginx.compose.conf must equal nginx.conf apart from upstream re-resolution"). All restored green.

    5. Overlay build path (reproduced)¶

    Cause: prepare.js/build.js ran git diff --quiet HEAD -- … deploy/multitenant in the core overlay, where tools/compose-overlay.sh replaces core's reduced fixture by design (config.js and README.md modified, 16 files untracked). Every overlay was BUILD_INPUTS_DIRTY (./demo.sh prepare on a fresh overlay of fe36212: Preparation refused: BUILD_INPUTS_DIRTY). Even past the check, build.js archived core's own deploy/multitenant, which has no Dockerfile. Not node_modules (ignored, not an input) and not a path comparison.

    Fix: the overlay script copies the tree by git archive of HEAD (refusing uncommitted changes there) and writes deploy/multitenant/.overlay.json (deploy checkout path and commit). With the marker, core HEAD is checked for every other input, deploy/multitenant must equal the deploy commit's tree byte for byte (diff -r, only .env, .state and the marker left out), the context is built from the two commits, and checkImage also checks org.nightscout.deploy.revision. Without the marker, behaviour is unchanged. The harness's prepare-overlay.js/build.sh workaround is no longer needed (not edited).

    Result: ./demo.sh prepare passed, ./demo.sh build built and labelled the image (29.7 s, cached layers), build.js --check-image passed. Refusal controls on the overlay, each restored to clean:

    break result
    line appended to nginx.compose.conf in the overlay BUILD_INPUTS_DIRTY
    stray file added to deploy/multitenant BUILD_INPUTS_DIRTY
    tracked core file lib/cli/commands/diagnose.js modified BUILD_INPUTS_DIRTY
    marker names an unknown deploy commit BUILD_OVERLAY_COMMIT_UNAVAILABLE
    marker removed (old behaviour) BUILD_INPUTS_DIRTY

    Untracked files elsewhere in core (an untracked lib/cli.js created by a mistyped first control) pass, as before: they are not in the archive the image is built from. diff -r does not compare file modes.

    • The capacity harness can switch to tools/compose-overlay.sh + demo.sh prepare/build (harness not edited here).
