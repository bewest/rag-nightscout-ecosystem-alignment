    REST replica history characterization — 2026-11-05¶

    Record

    Record as of 2026-11-05. A point-in-time document; it is not kept up to date.

    Contributor-facing measurement record. Reproduced parent focused evidence at CRM 2a6eaf738382ef62b8b3bfd0c76dbd005abb8480; subsequent instrument/cleanup candidate 714f6c8b229fbea171db4e75cbf8179edd7d2d57 is not accepted. Alignment baseline f7b555338e150c5eabce81511bfc10b932cb9f1b; local official/dev 4a482627bfdafb1fef8dcbe0ac6c484811cae563. Synthetic data only. This record establishes a failed general replica-history contract, not stateless deployment, Kubernetes, multi-node, high availability or durable event acceptance.

    Question and result¶

    Can two actual nightscout multitenant api CLI processes be interchanged on one operator-managed machine without losing history visibility? Selected entries CRUD, current grants and process replacement pass, but the broader claim fails: two already-running processes can assign equal history timestamps to sequential committed records, and an exclusive history cursor then omits the later record.

    Both processes boot before the characterized writes. A new-format tenant data token authenticates actual HTTP requests. First process POST succeeds; an independent PostgreSQL connection reads its raw stored srvModified. HTTP history returns that record and establishes the cursor before the second process POSTs a different identifier. Both replicas then omit the later record from /api/v3/entries/history/<cursor>, although addressed GET returns it successfully.

    Parent reproduced observation Result
    First raw PostgreSQL srvModified 1793948823488
    Second raw PostgreSQL srvModified 1793948823488
    Later record missing after exclusive cursor, queried through each replica true, true
    Later record addressed GET succeeds through both replicas
    Next write through the first process 1793948823489
    Write after restarting the second process 1793948823490
    Foreign tenant stored state unchanged

    The fixture uses an explicit child --require preload and NS_PREVIEW_REPLICA_CONTROL=history-clock with a shared millisecond value. Only Date.now() callers whose stack includes lib/server/srv-dates.js see that value. The actual allocator and storage code are unmodified. Authentication, expiry, provider and timeout clocks remain real. This makes the scheduling condition deterministic; no frequency under normal wall-clock load is measured.

    Read-derived mechanism: lib/server/srv-dates.js:35,62-68 keeps a per-process tenantClocks map and advances against wall time; restoreResolved:76-87 hydrates from persisted values at boot. lib/server/serve/preview-domains.js:68 restores before serving. lib/api3/generic/history/operation.js:74-84,103-104 uses an exclusive predicate for the URL cursor. Same-process advancement and restart hydration do not coordinate already-running allocators. No clock fix is selected.

    Bounded positive campaign¶

    Node v22.23.4, npm 10.9.9, private lockfile dependencies/build. Each fixture owns disposable PostgreSQL/Vault containers and launches real CLI children. Parent command at immutable 2a6eaf73:

    NS_MULTITENANT_PREVIEW_REPLICAS_DOCKER_TEST=1   node node_modules/mocha/bin/mocha.js --fail-zero --exit --timeout 120000   tests/multitenant-preview-replicas.integration.test.js

    Reproduced: 5 passing, 0 failing (11 seconds). These include the expected characterization of the failed history contract; the count is not replica acceptance. Other bounded assertions:

    • Actual entries POST/PATCH/read outcomes shared by both processes; equal identifiers in two tenants retain distinct values; data tokens cannot access another tenant or enable owner routes.
    • Already-used legacy and new-format credentials observe independently committed role revocation on their next requests in both workers. Replacing one worker reacquires persisted authority; restoring grants restores access.
    • A fixture holds the actual POST response after the handler calls res.end. An independent PostgreSQL read proves the row committed before SIGKILL. The client sees a transport error; retry through the survivor returns HTTP 200 and leaves one row for that identifier. No event/history exactly-once claim.
    • Altered migration ledger checksum refuses startup before either listener binds; restoring the ledger permits startup and authorized reads.
