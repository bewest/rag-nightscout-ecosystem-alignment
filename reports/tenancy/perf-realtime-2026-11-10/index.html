    Realtime publishes on change (perf lane RT), 2026-11-10¶

    Living document, last changed 2026-11-11 at ec6ad8464.

    Contributor-facing evidence record for perf lane RT (multitenant only). Captured 2026-11-10/11 (UTC); not edited after capture. Decisions read: cost-proportional-to-activity, activity-is-pause-suspend, suspended-refusal-423, tenant-devicestatus-status-parity, D6 and the durable event delivery contract; m7-capacity-gate for the marginal-cost section. Synthetic data only. Every figure is labelled reproduced (read from a run file here) or derived (arithmetic on reproduced figures, stated).

    Outcome¶

    Realtime sends a frame only when a tenant's view changes, authorizes a socket when it connects and then only on events, primes concurrent connects late instead of disconnecting them, and comes back after a restart at 50 and 100 tenants. No client change: lib/client is untouched, frames stay full (delta:false). Measured on the one-host Compose reference against the base head:

    base cb1b751d this lane 6f31c94b
    frames per idle connected socket per minute (1 tenant × 20) 20.0 0
    subject authorizations per connected socket per minute (1 × 20) 20.1 0.099
    realtime DB-ms per minute, 50 tenants × 20 sockets idle 44,989 83
    sockets primed when 1000 open (50 × 20) 14 / 1000 at 50 ms stagger (986 server-disconnected) 1000 / 1000 opened at once, none disconnected
    realtime after docker compose restart realtime, 50 tenants exit 78, never back running; reconnecting clients 1000/1000 in 32.8 s
    realtime start at 100 tenants exit 78 at deploy running; restart survived, 200/200 back in 35.1 s

    Restart root cause (reproduced): at boot realtime warms and refreshes every configured tenant at once, each inside an operation window that takes a client from the lifetime pool (max 8, 5 s connect timeout, operation-cohort-config.js:49). On a loaded PostgreSQL one window waits longer than 5 s, pg-pool rejects with timeout exceeded when trying to connect at operation-window.js:103, the startup Promise.allSettled treats any rejection as fatal (runtime.js:43-45 and tenant-startup.js warm, both at cb1b751d), and preview-realtime.js turns it into PreviewConfigError → exit 78. Shown with a diagnostic copy of preview-realtime.js that prints the swallowed error (runs/base-n50-restart-diagnostic.txt). It is not caused by the previous process: a fresh up of the stopped container failed the same way. The perf-db lane reproduced the same mechanism independently with unbounded warm at 200 (perf-db record).

    Not fixed here, measured in both heads: graceful shutdown with sockets attached overruns the 10 s bound (still open 10000 ms after SIGTERM: PipeWrap, PipeWrap, Timeout, …, then the watchdog exits 1; runs/base-n50-realtime-lifecycle.txt, runs/after-n50-realtime-lifecycle.txt). Without sockets the base restarted in 5 s with no overrun. The mechanism was not examined.

    Design (file:line at 6f31c94b)¶

    piece where what
    change hints in one round trip lib/storage/postgres-connection.js:232 scanTenants One READ ONLY transaction per 500 tenants: for each tenant set_config('app.current_tenant_id', …) then one fixed parameterless SELECT, so forced RLS scopes each statement to its tenant. No operation-window lease; nothing read is served. Refuses ;, $, \, non-SELECT, duplicate or non-UUID tenants.
    detector lib/server/realtime/change-detector.js:19 stampReader, :25 create, :47 invalidateIneligible Per interval: every tenant's tenant_write_clock.last_stamp (one scan), activity (tenant-activity/postgres.js:94 readMany, one scan), configuration identities (realtime/config.js:43 readAll, one file read). A tenant removed from admission or not eligible to be read (paused, suspended, unprovisioned, unreadable) has its sockets disconnected.
    runtime lib/server/realtime/runtime.js:54 due, :63 tick, :93 wake Refreshes a tenant only if its stamp differs from the checkpoint of its last published refresh (the clock floor read in the refresh's own snapshot), its configuration identity changed, its last refresh failed, or it was woken. At most two refreshes at a time (preview-realtime.js:11); startup bounded the same way (:88, preview-realtime.js:80). wake(tenant) is the seam for a later NOTIFY / slot reader.
    publish on change lib/server/realtime/protocol.js:52 sameView, :359 fanout A main socket gets a frame only when its view (frame minus lastUpdated, plus configuration identity) differs from what it last received. /storage gets only row changes. Frames stay delta:false. Fanout uses each socket's remembered rights: no per-frame api call.
    authorization by event protocol.js:130 remember, :60 expiryOf, :268 recheck, :295 sweep, :413 recheckTenant At connect/re-authorize: one api call. Afterwards: at the credential's JWT exp (a recheck the api answers; all stock carriers are JWTs with exp), every authorizationRecheckMs (optional config, default 30000, set explicitly in deploy/multitenant/config.js), on recheckTenant (revocation-event seam), and on pause/suspend/admission removal (detector) or lifecycle invalidation. One api call per distinct (namespace, host, credential) per tenant per recheck (:111 authorities). A refusal disconnects; an api that cannot answer holds that socket's frames until it can. Alarm delivery and loadRetro still authorize per request.
    late, not dropped protocol.js:160 queue, :171 later, :204 prime Connects are queued per tenant and primed in batches: authorization outside the window (one call per distinct credential), then one operation window for the refresh and every send. Pool pressure or an unanswering api retries the batch with jittered backoff (250 ms → 5 s); only refusals (:21 REFUSALS, window suspension) disconnect.
    shutdown protocol.js:429 close Unchanged: every socket is disconnected server-side.

    D6 mismatch, stated: the decision asks for "one aggregate query per member per interval". Every clinical and clock table is FORCE ROW LEVEL SECURITY and the realtime identity is NOBYPASSRLS (evaluator-readiness.js:15-19 refuses otherwise), so a single cross-tenant SELECT is not possible without a schema change (a security-definer function or a summary table outside RLS). scanTenants is one round trip and one transaction per member per interval, with one statement per tenant. A true aggregate statement is a schema decision for the batch join.

    Shared with the evaluator lane: stampReader is the evaluator's per-member change query too (stamps(tenants) → Map<tenant, last_stamp>; the evaluator compares with its own checkpoint), and readMany is its activity work list in one round trip. The peer branch codex/perf-evaluator-20261110 had no commits when this lane started, so nothing was reconciled yet.

    Overlap with perf-db (codex/perf-db-20261110, d53f12d6, a52bc33b): both lanes bound startup warm (tenant-startup.js warm). perf-db reads NS_TENANT_STARTUP_CONCURRENCY (default 4) for warm and realtime's first refresh and makes pool sizes configurable; this lane hard-codes 2 for warm, startup and change ticks. At the join take perf-db's setting for startup and derive the tick concurrency from NS_POOL_REALTIME_MAX. The new readiness-serve-then-warm decision (recorded after this lane started) is not implemented for realtime here: realtime still refuses the boot if any tenant's startup fails, and /health stays 503 until all are ready.

    What runs out first (derived, for one realtime process):

    1. Refresh throughput. Change ticks refresh at most two tenants at once and a refresh takes roughly 0.7–1.2 s of wall time (write-to-frame p50 1.2–1.7 s minus about half a detection interval), so about 100–170 refreshes per minute: about 500–850 tenants at one write per 5 minutes, fewer with several uploaders per tenant. Each refresh is a full current-state reconcile (postgres-durable-replay.js reconcile scans every row), so it grows with each tenant's stored data; the synthetic tenants here hold little. Raising the concurrency (pool 4, configurable in perf-db) or an incremental catch-up refresh moves this.
    2. The single Node thread. Idle sockets cost 3.6–18.5 CPU-ms per socket-minute, and one thread gives 60,000 ms per minute: roughly 3,000–4,500 idle sockets per process (1,000 to 1,500 tenants at 3 sockets each), less with writes (50 × 20 with writes: 17,957 ms/min).
    3. Memory. About 1.4 MB per tenant and 0.4–0.8 MB per socket: 3,000 tenants with 3 sockets each ≈ 4 GB + 4–7 GB per process.
    4. Realtime's own database time is not a limit at these sizes: about 1.8 ms per tenant-minute idle, about 40 ms with one write per 5 minutes (≈ 2 cores of PostgreSQL at 3,000 tenants).

    Sharding realtime across processes (MT-REALTIME-SHARDING) addresses 2 and 3; 1 is per process too.

    Design (file:line at the lane head)¶

    BF-233. lib/server/realtime/socket-server.js owns the Socket.IO server on the realtime listener. Shutdown is io.close() (namespaces, then engine.close(): every transport closes); protocol.close (protocol.js) no longer sends a server-side disconnect. socket.io-client then sees transport close and reconnects with its own backoff. No client change.

    Mechanism of the 10 s overrun (reproduced, control A below): a server-side disconnect(true) on a polling socket leaves its engine connection and two timers waiting for a client that, having been told "io server disconnect", no longer polls. After stop() resolved (119 ms) the process still held 829 TCP sockets and 1,656 timers for 828 disconnected sockets, so it outlived the 10 s bound and the watchdog exited 1. closeAllConnections was tried and is not needed (control B).

    Change stamps (decision change-stamp-definer-function). - lib/change-stamps/postgres-candidate.json: operational catalogue (census OPERATIONAL, digest-pinned, lib/tenant-operations/catalogues.js), one migration creating tenant_change_stamps(uuid[]) RETURNS TABLE (tenant_id uuid, last_stamp bigint), plpgsql, SECURITY DEFINER, SET search_path = pg_catalog, SET app.current_tenant_id = '', REVOKE ALL ... FROM PUBLIC. The body binds each requested tenant through the same RLS setting the serving paths use and selects that tenant's clock row: RLS on the clock is unchanged and the owner needs no bypass. The function's own SET app.current_tenant_id keeps its binding from reaching the caller. - Provisioning (lib/change-stamps/postgres.js grants, used by deploy/multitenant/config.js): ALTER FUNCTION ... SET search_path = <clock schema>, pg_catalog; USAGE and EXECUTE to the realtime and evaluator identities only; the catalogue ledger read to realtime only (its readiness checks the catalogue). bootstrap.js gives the function to the NOLOGIN catalogue owner, as every catalogue function (reviewed signature list). - Reader (lib/change-stamps/postgres.js create): one statement per poll returns the stamps and the function's catalogue version (pg_proc row version plus the owner's login/superuser/bypass flags) — the same idea as perf-db's catalogue epoch, applied to the one object perf-db's epoch does not cover. An unadmitted version calls the function with no tenants, runs the attribute check (owner NOLOGIN, NOSUPERUSER, NOBYPASSRLS and owning the clock table; SECURITY DEFINER; plpgsql; exact body; exact result type; exact proconfig; no PUBLIC EXECUTE), then calls it with the tenants. A refused check raises CHANGE_STAMPS_FUNCTION_UNSAFE; detection then answers nothing and the runtime refreshes only failed cells. - Realtime uses it when postgres.namespaces.changeStamps is set (the Compose plan sets it); a configuration without it keeps the per-tenant scan. The evaluator has EXECUTE and can adopt it; its configuration does not name the namespace yet.

    Incremental refresh (decision incremental-refresh). lib/storage/postgres-incremental-view.js, shared read path: - create({ connection, domains, indexed, clockTable, reconcile, pageSize, maxRows }); refresh() inside the tenant binding returns { mode: 'full' | 'incremental' | 'unchanged', changed, checkpoint, rows }; reset() forces a full read. - Cold start: the existing bounded replay.reconcile (checkpoint bookkeeping unchanged; it now also reports its physical row count and invalid keys from the same snapshot, postgres-durable-replay.js). - Afterwards one REPEATABLE READ snapshot: clock floor; rows stamped in (checkpoint, floor] through the generated, indexed "srvModified" column (entries, treatments, devicestatus; an expression for profile, food, activity); a physical row count per tenant. Soft deletes (isValid:false) remove, everything else replaces. - Full reconcile when the floor is below the checkpoint (rewind, restore), when more rows changed than the bound (gap), or when the count disagrees with the view (a hard delete — v1 entries remove, v3 prune or permanent delete — or a writer outside the clock leaves no stamp; durable event delivery contract §4). - Hard deletes advance no clock, so nothing announces them: the runtime refreshes every tenant at least every absenceCheckMs (default 60000, set in the Compose plan; the single-site data reload cadence). With the floor unmoved that refresh is one count and returns the published frame unchanged (projection.js). - The frame build's dbsize statistics (sum(pg_column_size(doc)) over every row, postgres-tenant-stats.js:19) are read at most every 5 minutes per tenant. - Frames stay full (delta:false).

    For the join with the evaluator lane (a335be89): the evaluator's backstop reads, per tenant per pass, a signature of floor + row count + a digest over every row's identity and xmin (one statement per tenant, cost with stored rows). The shared shape is: change-stamps for the floor of every member tenant in one statement, then postgres-incremental-view per changed tenant (its count check covers hard deletes and unstamped writes), with an absence interval for tenants with no stamp movement.

    Serve, then warm (decision readiness-serve-then-warm, on perf-db's mechanism). NS_TENANT_READINESS (default serve) reaches realtime's startup cells (preview-realtime.js) and runtime (runtime.js). In serve the role opens without awaiting tenants; each tick warms a bounded number of cold tenants after the changed ones; a failed tenant is retried after 30 s while the others serve; health().ready is the role's own, with healthy and failed counts. The stock client retries neither a handshake refusal nor a server disconnect (lib/client/index.js:1165 opens with default reconnection, which covers only transport loss), so a socket for a cold tenant is not refused: it waits in the priming queue built for pool pressure and gets its first frame when the tenant is warm. all restores the earlier await-every-tenant boot.

    Two defects found by measurement in already-committed code, fixed: - Absence checks stalled change detection at scale (addaa1ad). At 1,000 tenants every tenant's 60 s absence check was due at once; one tick refreshed about three per second and the stamp poll ran only between ticks: 0.3 stamp calls per minute in the window (reproduced, int-n1000-idle-s2). Each tick now takes the changed, failed or woken tenants plus at most ceil(N × interval / absenceCheckMs) absence checks, oldest first. - Configuration re-parsed on every check (20a49aab). One parse of the 1,000-tenant realtime configuration costs 85 ms (reproduced locally on the deployed file); it ran twice per refresh, once per fanout and once per tick, and the 143 KB admission file on every check. At 1,000 tenants realtime used 70–73 s of CPU per minute with no sockets (more than its one thread) and primed 4 of 2,000 sockets (reproduced). Both files are still read on every call; they are parsed only when their text changes. This cost was in the base too (every refresh, every socket check). - Also fixed on the way, each measured: the evaluator refused its boot because the grants gave it the change-stamp catalogue ledger outside its readiness screen (f62222cd); the 60 s absence check rebuilt every frame (261f568e); each frame build ran sum(pg_column_size(doc)) over the tenant's rows for the dbsize display (postgres-tenant-stats.js:19), now at most every 5 minutes per tenant (650cfce3).
