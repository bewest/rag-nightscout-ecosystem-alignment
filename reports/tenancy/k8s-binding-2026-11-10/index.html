    Install request for the cluster smoke (maintainer)¶

    kind runs Kubernetes nodes as Docker containers, which this host has. Kubernetes 1.29 or newer is needed (native sidecars; pod-index label 1.28+), and the host's kubectl 1.25 is outside the supported one-minor skew of such a server. Both binaries are single files; a user-local directory avoids a system-wide install. Verify each checksum before use:

    mkdir -p ~/.local/bin && cd "$(mktemp -d)"
curl -fsSLO https://github.com/kubernetes-sigs/kind/releases/download/v0.27.0/kind-linux-amd64
curl -fsSLO https://github.com/kubernetes-sigs/kind/releases/download/v0.27.0/kind-linux-amd64.sha256sum
sha256sum -c kind-linux-amd64.sha256sum && install -m 0755 kind-linux-amd64 ~/.local/bin/kind
curl -fsSLO https://dl.k8s.io/release/v1.32.2/bin/linux/amd64/kubectl
curl -fsSL https://dl.k8s.io/release/v1.32.2/bin/linux/amd64/kubectl.sha256 | awk '{print $1"  kubectl"}' | sha256sum -c && install -m 0755 kubectl ~/.local/bin/kubectl
kind version && ~/.local/bin/kubectl version --client

    kind v0.27.0's default node image is Kubernetes v1.32.2 (read-derived from the release notes; the node image version is printed by kind create cluster). kindnet enforces NetworkPolicy from kind v0.24 (read-derived); the smoke must confirm it with a denied connection before the NetworkPolicy rows count. The binding's spec.json names https://127.0.0.1:6443; a kind cluster created with networking.apiServerPort: 6443 matches it.

    Smoke plan once installed (each step a gate; UNMEASURED today): build and re-tag the Compose image at 16a1fc2d with the synced tree, kind load, tk apply, secrets.sh seed, Job provision complete, secrets.sh publish, cohort Ready; then the synthetic entry round-trip through api (legacy token exchange, then API3 write and read back), a Socket.IO connect through edge, the admin listOwners from an operator-labelled Pod, a denied connection to 1342 from an unlabelled Pod, and the control: scale the cohort to 2 out of band and require the second Pod to refuse to serve. Then kind delete cluster and docker image prune for the loaded images.

    Pool variables (canonical names)¶

    The binding now uses core's MULTITENANT_POOL_EVALUATOR_{PARTITION,MEMBERS,ORDINAL,LEASE_MS,DATABASE_URL,NAMESPACE}. The provisional names map as NS_EVALUATOR_POOL_ORDINAL → ORDINAL and NS_EVALUATOR_POOL_MEMBERS → MEMBERS.

    Mismatch with the coordinator's instruction ("render only the ordinal"). On core codex/pool-primitive-20261110 5a789903, lib/pool-membership/config.js fromEnvironment refuses an ordinal while the partition is off: - {ORDINAL: "0"} gives partition is off but MULTITENANT_POOL_EVALUATOR_ORDINAL set; - {PARTITION: "on", ORDINAL: "0"} gives MULTITENANT_POOL_EVALUATOR_MEMBERS must be a non-negative integer.

    The binding therefore renders no pool variable with the partition off, which is the preview. With partition: 'on' it renders PARTITION=on plus ORDINAL from the pod-index label and no MEMBERS, per the decision that the count lives in the pool table. Core at 5a789903 still requires MEMBERS when on, so that combination refuses until core follows the decision. Readiness stays the role health check.
