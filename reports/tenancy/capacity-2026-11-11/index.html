    Multitenant capacity campaign, one-host Compose reference (2026-11-11/12)¶

    Living document, last changed 2026-11-11 at 21fa4bce6.

    Dated measurement record (contributor-facing). Captured 2026-11-11 18:00Z to 2026-11-12 02:50Z; not edited after capture. Synthetic tenants only. Every figure is labelled measured (read from this campaign's tool output, files under runs/), derived (computed from measured figures, method stated) or read-derived (from reading code, not run).

    Verdicts¶

    question answer
    1,000-tenant milestone (m7-capacity-gate) Met on both heads. Every 1,000-tenant run (8) finished with every role healthy, the stored-count oracle GREEN with zero uncertain writes, all probe writes delivered, and all tenants evaluated after the full restart. Socket caps differ by run (table below).
    3,000-tenant gate Not met on core 5c60aec6 + deploy d1c7aca on this host. Deploy and the idle window succeed at 3,000; under the real cadence with 2 sockets per tenant, 99.8% of HTTP requests fail (p50 10.2 s) and 134 of 6,000 sockets prime in 300 s (r1, measured).
    What runs out first at 3,000 The api's single JavaScript main thread, driven by realtime's socket-authorize path, with heavy allocation. With sockets present (x2, x3) the api's event-loop utilisation is 0.993–0.995 and its process uses 4.4–4.5 cores, of which 0.94–0.96 is the main thread and 3.4–3.5 V8 worker (GC/compiler) threads; authorize throughput stays at about 140–215/s whatever the pool size (measured). With HTTP only (x1) the api's 8-client operation pool binds first: requests wait their 5 s pool timeout while the main thread runs at 0.74 (measured). PostgreSQL is not the limit (1.8–4.5 cores, 3–5 active backends on average; measured).
    Where the api main thread saturates About 1,350–1,400 tenants under this workload (real cadence + 2 sockets per tenant). Derived, an extrapolation: b4's api main-thread utilisation of 0.73 at 1,000 tenants, scaled linearly to 1.0. No run was made at that N.
    5,000 and 10,000 Not run (the 3,000 gate failed first).

    Reference to beat (from the decision): about 100 tenants per node for tenant-per-pod.

    Harness¶

    tools/mt-bench/capacity/: campaign.sh (quiet-host wait, then per run: deploy, idle, real cadence + sockets + probe writes, full four-role restart, oracle, summary, teardown), cap.sh (the steps), probe.js (sockets, probe writes, restart measurements), startup.js, summarize.js (one summary.json per run), aggregate.js (tables), k6/workload.js. Workload: k6 real cadence (sgv every 5 min per tenant, devicestatus, reads), 2 stock-browser Socket.IO clients per tenant (polling, no reconnect after a server-initiated disconnect), one probe sgv every 3 s; idle 600 s, load 900 s (x runs: 300 s / 600 s).

    Instruments (mounted over core files in the realtime and api containers; files listed in the run directories' compose extras, not committed): a 1 s realtime DIAG line (startup state, protocol counters, event-loop utilisation/delay), a counter around realtime's whole-file config read, and a 2 s api DIAGAPI line (startup state and alert causes, event-loop utilisation and delay, CPU by thread from /proc/self/task). The ctl run additionally mounts the unbounded per-socket warm (realtime design control).

    Socket cap per run: the 0392acf9 runs and b1 used a bench patch raising realtime maxSockets from 100 to 25,000. From d1c7aca the deploy tree sets maxSockets = max(100, N × NS_DEMO_SOCKETS_PER_TENANT); b2, b3 and r1 ran at the default 2 (cap 2N), b4 and x1–x3 at 4 (cap 4N). The 3,000-tenant runs used MULTITENANT_CONFIG_MAX_BYTES = 4,194,304.

    • The pool is refuted as the limit once sockets are present. In x3 the api's operation-pool identity reached 32 connections (per-role peaks summed to 84, 73 concurrent), and authorize throughput did not move from about 200/s (prediction was "well above 200/s, towards 800/s"). Throughput topped out far below that with the pool full: the per-call cost is api CPU, not database contention (measured).
    • The api is one process with one JavaScript thread (per-thread CPU from /proc/self/task): r1's 4.46 cores are one pinned main thread plus about 3.5 cores of V8 worker threads, generated by the socket/authorize path (x2), not by HTTP (x1: 0.87 cores). About 5 ms of main thread per authorize at about 200/s (derived: 0.96 core / 200 per s).
    • HTTP alone at 3,000 waits on the 8-client operation pool: p50 equals the 5,000 ms pool connect timeout, and the api's database statement rate is flat across N (about 9.5 k/s at 3,000 in x1, 10.1 k/s at 1,000 in r3, from pg_stat_statements; the most frequent statement's mean 0.77 vs 0.70 ms). Demand is three times larger; throughput is not (measured; the pool mechanism is read-derived from the api lane).
    • PostgreSQL max_connections 100 is a deployment ceiling: an api pool of 64 would have needed about 117 connections at peak (derived: r1 per-role peaks 61 − 8 + 64), above the 97 available; 32 was the largest one-variable step.

    Corrections to figures reported during the campaign¶

    1. Evaluator recovery after the restart was a probe artifact, not slower evaluation. probe.js restarted nginx with a synchronous spawnSync, freezing its own event loop for the command's duration (about 11 s when nginx waits out open connections). On the new head the edge samples before it included a 5 s hang, which moved the freeze into the evaluator's ready window: b1 freeze 13.9–25.1 s, ready read 25.2 s; b2 13.2–24.4 s, read 26.1 s. Evaluations during the freeze were absorbed into the warm baseline, so "evaluated within 60 s" fell to 471 and 444. Re-derived on one basis (evaluator log), the evaluator was ready at 10.8–11.8 s on every head (table above). Docker's own healthcheck in b2 first passed at 13.3 s (measured). Fixed in the harness (nginx restart asynchronous; role health polled in its own 250 ms loop, with Docker's healthcheck time kept as the reference); b3 then read 13.4 s and 926/1000. "Evaluated within 60 s" cannot be re-derived for the earlier runs: tenant_lifecycle_operations has no timestamp.
    2. "2000/2000 stock sockets back unaided" before b3 is affected by the same stall. While the probe was frozen its clients did not reconnect, so the reconnect surge never met realtime's cap. With clients reconnecting immediately (b3), 499 of 2000 received io server disconnect.
    3. The b3 drops were the socket cap, closed by b4. Cap 2N counts every live engine.io session, and sessions from the first reconnect stay live for up to about 45 s (read-derived, realtime disconnect record). b3 (measured, realtime's 1 s counter): sessions at exactly 2,000 from +27.5 to +50.6 s, then 2,000 → 1,501 by +55.6 s; invalidated and primeRefreshFailures 0. b4 at cap 4N (measured): zero server disconnects, 2000/2000 back unaided, sessions peaked at 2,455, above 2N. Decision: realtime-no-socket-cap (no per-process cap, plus cause codes).

    Limitations¶

    • Busy, shared host. Peer sessions' containers ran throughout. The quiet-host rule (1-minute load below 3 before each deploy) held at deploy for every run (quiet.txt); load1 during the load windows was 6.6–8.0 at 1,000 and 8.0–19.0 at 3,000 (mean of 2 s samples, table above), on 16 threads.
    • Load generators share the host. k6 used 0.21–0.32 cores on average (peaks 5.9–7.8 cores) and the probe process 0.80–0.90 cores with 6,000 sockets (x2, x3; load/loadgen.tsv); earlier runs did not record them.
    • One run per variant for b1–b4, r1 at 3,000 and x1–x3; three plus a control at 1,000 on 0392acf9.
    • Probe changes during the campaign (asynchronous nginx restart, own health loop, disconnect timeline) apply from b3 onward; the restart-phase figures of earlier runs are comparable only after Correction 1.
    • cap.sh was edited while r1 at 3,000 was running; the running shell logged one parse error (deploy.log line 4) after the probe ended; every artifact of that step is present.
    • The x runs used 300 s idle and 600 s load windows.
