OpenAPI specification for the Nightscout treatments collection documenting the de facto standard as implemented across AID systems circa 2025.

API versions

The operations declared here are Nightscout API v3 as shipped on cgm-remote-monitor dev 47723cda (lib/api3/swagger.yaml). The document schema describes the stored treatments document, which clients write through API v1 or API v3: Loop (NightscoutKit NightscoutClient.swift:13-17) and Trio (NightscoutAPI.swift:14-18, 0b29cd534) use API v1; AAPS uses API v3 (core/nssdk/.../networking/NightscoutApi.kt). The x-aid-controllers notes describe what each controller writes, through whichever API it uses; they are not API v3 behaviour.

In API v3:

  • a successful response is wrapped as {status, result} (lib/api3/shared/renderer.js:117-122);
  • identifier is the record's sync identity, assigned by the client; when none is sent the server computes one (lib/api3/shared/operationTools.js:209-216), and a document stored without one is read back with its _id string as identifier (lib/api3/storage/mongoCollection/utils.js:10-16);
  • _id is the storage key Nightscout assigns: API v3 does not return it (utils.js:10-16) and refuses a create or update body that carries it with 400 (operationTools.js:197-203, called from generic/create/operation.js:35 and generic/update/operation.js:32). API v1 keeps its own _id handling.

Data Flow

  • Producers: Loop, AAPS, Trio, xDrip+, Nightscout Careportal
  • Consumers: All AID systems, Nightscout web, follower apps, reporters

Key Insights

  • eventType is the primary classification field
  • syncIdentifier vs identifier usage varies by controller (GAP-003)
  • SMB identification requires checking type field, not just eventType

Changelog

2025.2.0 — corrected against measured data

Reconciled against 369,419 real treatment documents from 11 Nightscout sites (reports/schema-census/treatments.census.json). Evidence and method: docs/30-design/platform/nightscout-typed-schema-evidence-2026-09-10.md.

  • carbs, insulin: now nullable; null is the majority case (95.8% and 60.7% of documents)
  • timestamp: integer -> [string, number]; string in 100% of occurrences
  • eventType: enum extended with Bolus, Carbs
  • type: enum extended with lowercase normal, the only value in live data
  • added amount, userEnteredAt, userLastModifiedAt, insulinNeedsScaleFactor, correctionRange

Fields carry x-aid-evidence pointing at the census record that justifies them. Re-derive with make schema.
