AID Profile Collection - De Facto 2025 (2025.2.0)

Download OpenAPI specification:

License: AGPL-3.0

OpenAPI specification for the Nightscout profile collection documenting the de facto standard as implemented across AID systems circa 2025.

API versions

The operations declared here are Nightscout API v3 as shipped on cgm-remote-monitor dev 47723cda (lib/api3/swagger.yaml). The document schema describes the stored profile document, which clients write through API v1 or API v3: Loop (NightscoutKit NightscoutClient.swift:13-17) and Trio (NightscoutAPI.swift:14-18, 0b29cd534) use API v1; AAPS uses API v3 (core/nssdk/.../networking/NightscoutApi.kt). The x-aid-controllers notes describe what each controller writes, through whichever API it uses; they are not API v3 behaviour.

In API v3:

  • a successful response is wrapped as {status, result} (lib/api3/shared/renderer.js:117-122);
  • identifier is the record's sync identity, assigned by the client; when none is sent the server computes one (lib/api3/shared/operationTools.js:209-216), and a document stored without one is read back with its _id string as identifier (lib/api3/storage/mongoCollection/utils.js:10-16);
  • _id is the storage key Nightscout assigns: API v3 does not return it (utils.js:10-16) and refuses a create or update body that carries it with 400 (operationTools.js:197-203, called from generic/create/operation.js:35 and generic/update/operation.js:32). API v1 keeps its own _id handling.

Current Limitations

  • No distinction between prescribed, desired, and effective profiles
  • AAPS ProfileSwitch semantics differ from Loop overrides (GAP-002)
  • Profile percentage and timeshift not standardized

Changelog

2025.2.0 — corrected against measured data

Reconciled against 202 real profile documents from 11 Nightscout sites (reports/schema-census/profile.census.json). Evidence and method: docs/30-design/platform/nightscout-typed-schema-evidence-2026-09-10.md.

  • mills, carbs_hr, delay: now accept string; that is how 99% of live documents write them
  • units: enum widened; added a per-profile store.{}.units, which is present in 100% of documents on all 11 sites and was undeclared
  • added LoopSettings and LoopOverride: a 26-path subtree written by 10 of 11 sites into 99% of their profile documents, previously undescribed

Two fields inside LoopSettings are marked as sensitive rather than merely typed: deviceToken is an APNs credential, and bundleIdentifier embeds the builder's Apple Developer Team ID.

Fields carry x-aid-evidence pointing at the census record that justifies them. Re-derive with make schema.

Not in this file

ProfileExtended (intent, baseProfile, modifiers, source, authority) was a 2026 proposal; none of its fields appears in the 2026-04 corpus. It moved to aid-alignment-extensions.yaml on 2026-10-26.

ProfileDocument

_id
string

Storage key Nightscout assigns. API v3 does not return it and refuses a request body that carries it (400). See "API versions" above.

identifier
string

The record's sync identity, assigned by the client and the same on every retry; it need not be a UUID. When a client sends none, API v3 computes one; a document stored without one is read back through API v3 with its _id string as identifier. Immutable once stored. See "API versions" above.

created_at
string <date-time>
startDate
string <date-time>

When this profile becomes effective

defaultProfile
required
string

Name of the default profile in store

required
object

Map of profile name → profile settings

object (LoopSettings)

Loop's therapy-settings block, written into the profile document alongside store.

This is the attribute-flattening camp described in docs/sdqctl-proposals/x-aid-extensions-convention-proposal.md, measured: a 26-path subtree that 10 of 11 sites in the 2026-04 corpus write into 99% of their profile documents, and that no spec in this repo described before this revision.

Documented here because it exists and consumers must read it, not as an endorsement of flattening vendor settings into the shared document shape.

units
string
Enum: "mg/dl" "mg/dL" "mmol" "mmol/L"

Glucose display units.

Enum widened to cover live data. Three specs in this repo declared three different vocabularies ([mg, mmol] in entries, [mg/dl, mmol] here) and the corpus contains mg/dL, mg/dl and mmol/L — none matching any declaration. Settling on one vocabulary is an ecosystem question; until then a reader must accept all of these.

Profile

timezone
string

IANA timezone name

dia
number [ 2 .. 10 ]

Duration of Insulin Action in HOURS, as written to the profile document. The 2-10 bounds below describe stored values; each controller applies its own limits to its own DIA setting, and the value in a Nightscout profile is not necessarily the value a controller doses with.

  • oref0 (d219baf9) takes DIA from pump settings (insulin_action_curve, lib/profile/index.js:117-122), raises a value below 3 h to 3 h (lib/iob/total.js:23-27), and a value below 5 h to 5 h for the exponential curves rapid-acting and ultra-rapid (lib/iob/total.js:59-63).
  • Trio (0b29cd534) carries the same JavaScript (trio-oref/lib/iob/total.js:21-25, 57-61). Its Swift profile generator refuses a DIA below 5 h (APS/OpenAPSSwift/Profile/ProfileGenerator.swift:124-129) and its Swift IOB calculation raises one below 5 h to 5 h (APS/OpenAPSSwift/Iob/IobCalculation.swift:151-156). It uploads its own pump-settings DIA in the profile (Services/Network/Nightscout/NightscoutManager.swift:822).
  • AAPS (7e1d537d49) marks a profile invalid when DIA is outside 5-9 h, or 5-10 h for the pregnant age type (core/interfaces/.../utils/HardLimits.kt:36-42, core/objects/.../profile/ProfileSealed.kt:191-196).
  • Loop (LoopKit d9f14373) has no DIA setting: the duration is fixed by the selected exponential insulin model, 6 h, or 5 h for Afrezza (LoopKit/Insulin/ExponentialInsulinModelPreset.swift:21-34). It uploads a fixed dia of 6 h in the profile (NightscoutService 2cef489, NightscoutServiceKit/Extensions/StoredSettings.swift:83).
