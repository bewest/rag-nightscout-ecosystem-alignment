Zero bug bounce

Defects arrive in bursts, and each burst follows a new check

The daily count of new defect IDs does not fall smoothly. Each burst starts the day a new check is first run: the code audit, the security review, the survey of 40 client apps, the review of #8758, the triage of old GitHub issues, and then the release-candidate runs, soak and journey lab. The count then drops once that check stops finding new problems. A clearer readiness signal is the number of regressions that fix PRs put onto dev (orange below). There were seven, and all seven were fixed on 2026-09-26. Since the last four merges there have been no new IDs and no regressions, and the only change was a test-only fix. That is one quiet day, so it counts as one data point.

The seven regressions that reached dev, and how long each lasted

From left to right on each row: the day the causing PR merged, the day the regression was filed, and the day its fix merged. None of them shipped, because 15.0.8 contains none of them. Ten more were caught in review of #8758 before it merged (BF-109–113, 115–117, 130, 131).

What the seven regressions have in common

  • A rule applied on one path and not its siblings (BF-106, BF-140, BF-142). One example: v3 reads showed an empty identifier as the _id, but v3 DELETE fell back to the _id only when identifier was absent.
  • Empty values (BF-141, BF-143). "", null and a missing field were treated as the same on one side of a comparison and as different on the other.
  • State lost on restart (BF-144). The v3 history clock lived only in memory.
  • Coupling to shared state (BF-80). /alarm delivery waited on the failed-login delay list, which a whole household behind one address shares.

Each fix also adds tests for the same failure on the sibling paths: +30 in #8783 and +32 in #8781.

Quality control

Each claim has a record behind it, and each check has been shown to fail when it should

The workflow borrows the design-control vocabulary that medical-device quality systems use, as a working method.

design input

Register, journey map, client census

Every defect gets a row and a detail section with a status word: open, merged or released. The journey map spells out what "working" means for each person using the site. The census maps 40 client apps across 15 API surfaces.

design output

PR + tests + notes

Each PR explains what changes for the reader, lists the tests it adds and names its register IDs. The release notes say what changes for operators. Anything still live on 15.0.8 is described by mechanism only, never as a working attack.

verification

Six cells, break-its, probes, soak

Each cell runs against a fresh mongod whose version is read from the server. New tests are added by title only. Break-its revert one fix and confirm its tests fail. Red controls show that the harness can fail. An A/B soak runs against 15.0.8 with an entry for every expected difference.

validation

Real rigs, real households

The maintainer walked the site in a browser with 15.0.8 open alongside, while lab scripts played the phones. The step still open is real Loop, Trio, AAPS and xDrip+ rigs over real days.

release decision

Humans publish

Agents prepare branches and stop. Only people push, merge, tag or publish. A push to dev or master publishes a Docker image, so it counts as a publication event.

Paving the cowpaths

A spec should describe what clients really do

"There go my people; I must find out where they are going so I can lead them."

quoted in Ian Hickson, Power dynamics in web specifications, 2024-07-17. The WHATWG was founded on the rule that a specification has to describe reality.

Nightscout, a secondary display for CGM and pump data, sits in the same position as a web browser. Dozens of independent clients depend on how it actually behaves, not on what its documentation says. 15.0.9 shows the method in practice. First, take a census of how clients really use each API surface. Next, turn what they do into tests. Then fix defects without breaking those clients. Where a fix would break a real client, keep the client working behind a named setting and announce when that setting will go away.

The same need was written down in 2011 in the Diabetes Data Bus note: many devices, many apps, and one shared store that each app subscribes to and that the user controls. Fifteen years on, that bus exists, and it is several dozen apps talking to Nightscout. Keeping it healthy means managing it as a shared contract. The alignment workspace holds the pieces: 44 upstream repository checkouts side by side, mappings for 23 projects, 118 spec files and a 521-file conformance suite. This release is the first to run through that loop from start to finish: census, test, fix, declare, verify, record.
