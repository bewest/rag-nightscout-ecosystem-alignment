Logical API, workers and admission

One logical REST/API component

REST v1, v2 and v3 belong to one logical stateless request-serving API component, together with credential authorization and owner-management modules. Version-specific adapters retain their request, authorization and response semantics; protocol versions are not separate application services. Stateless means durable authority/data are external and request state is reconstructible, not that the process has no in-flight work or retained readiness state. This logical grouping does not prescribe a single listener, process or privilege set. Owner management retains its own audience and listener contract and may be colocated with API serving under the existing owner-authority boundary. The accepted separate-role reference remains one concrete composition, not a requirement that every REST responsibility become a separate service. Grouping the versions does not admit additional routes: the recorded compatibility scope and admitted handler/storage contracts still bound actual coverage.

Headless workload owners

Realtime owns live connections; the evaluator is a headless worker and remains one current workload owner. Connector actors (vcpool) belong to background polling/egress work and submit clinical writes through the canonical API boundary; the ed2 role declaration has no runnable start. Evaluator partitioning and realtime replication are separate future capabilities, not prerequisites for the queued request-serving API scale-out.

Private maintenance execution

The lifecycle/restore controller executes as a private operator CLI, job or worker; the ed2 operator tool composes it outside API serving. Each serving instance supplies generic operation-admission, lifetime and invalidation hooks; those hooks do not place a restore engine or maintenance credentials in every API replica. A future command/status REST surface could request or observe maintenance while the privileged worker executes it separately; no new endpoint or process layout is selected here. The logical placement map owns the broader component explanation.

Maintenance safety is distinct from desired activity

The existing claim/generation-bound maintenance window determines whether an operation can run safely during recovery. Operator-controlled resource/activity policy asks which serving, ingestion, evaluation or connector work should run at all; that policy remains proposed and undecided in the tenant-admission review. A maintenance phase named active is not evidence of operator enablement or background-work eligibility. Preserve the existing pause/suspend meanings and captured restore behavior; no activity field, transition or automatic inactive-tenant resource control is implemented by this database design. Observed health is a further separate fact. No new activity-policy gate is claimed by the diagrams below.

Component ownership

Read across each responsibility lane: admitted reads and owned persistence have different boundaries. The REST/API data and owner rows belong to one logical component; rows do not mandate separate processes. Cross-owner commands use application interfaces.

Database families

Logical groups in selected PostgreSQL namespaces. Tenant tables carry tenant_id; schemas organize domains and components. Expand a group for its source-defined restore treatment.

Clinical/document domains

entries, treatments, devicestatus, profile, food, activity, settings in their selected namespaces.

Relationship and restore treatment

Tenant-bound documents. The first five have insertion counters. settings is the existing document collection, distinct from owner presentation tenant_settings. Logical restore reconciles these selected domains.

Insertion state

tenant_insertion_ordinal(tenant_id,last_ordinal) in each ordered domain namespace.

Relationship and restore treatment

One row per tenant/collection; allocation trigger and unique tenant/ordinal index. The document relation and counter share a binding, not a declared foreign key.

History state

tenant_write_clock(tenant_id,last_stamp).

Relationship and restore treatment

Tenant-wide history floor across admitted stamped writes; current floor is retained and advanced during logical restore.

Projection state

tenant_consumer_checkpoint(tenant_id,consumer,checkpoint,projection,contract_digest).

Relationship and restore treatment

Per-consumer recovery position/materialization. Preview realtime and evaluator select separate checkpoint namespaces. Retained current during logical clinical restore; actual invalidation and fresh acquisition reconcile output.

Authentication / authorization

tenant_authorization_*, owner policy/actor tables and audit; access_tenants, access_credentials, access_sessions, access_keys; legacy_credential_*; secret_records, secret_audit.

Relationship and restore treatment

Current authority, credential generations, sessions and encryption/signing references remain current during clinical restore. Access credentials/keys reference tenant rows; sessions reference their credential/subject tuple. Provider key material is outside tenant artifact handling.

Owner / operator policy

subject_policy, subject_policy_audit, tenant_operator_policy, tenant_settings, tenant_settings_history, tenant_owner_configuration_authority, when selected.

Relationship and restore treatment

Policy and management state, not a clinical snapshot to rewind. The owner settings history is independent of the clinical settings collection.

Notification delivery

tenant_notification_state, tenant_notification_heads, tenant_notification_requests.

Relationship and restore treatment

Durable producer state, deduplication heads and attempts/receipts. Retained current; invalidation retires retained output/intents through the actual consumer protocol. No general exactly-once external effect follows from these tables.

Alarm acknowledgement

tenant_alarm_suppression(tenant_id,alarm_group,alarm_level,acked_at,expires_at).

Relationship and restore treatment

Current suppression state is retained; fresh eligibility reads remain tenant-bound.

Restore control

tenant_lifecycle_windows, tenant_lifecycle_operations, tenant_lifecycle_restore_authority, tenant_lifecycle_restore_audit.

Relationship and restore treatment

Durable phase/generation/claim, unfinished operations, authorized maintenance roles and audit. Operations, authority and audit reference window tenant rows. These are control authority, not clinical restore payload.

Deletion ceremony

tenant_lifecycle_requests, tenant_lifecycle_ceremony.

Relationship and restore treatment

Separate requested/confirmed/cancelled/executing/executed deletion workflow; ceremony references request plus tenant. A restore claim does not itself authorize deletion.
