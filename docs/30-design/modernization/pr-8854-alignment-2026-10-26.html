    #8854 and the write-path plans: background, differences and outcomes¶

    Record

    Record as of 2026-10-26. A point-in-time document; it is not kept up to date.

    Contributor-facing. Snapshot, 2026-10-26, read at cgm-remote-monitor dev 47723cda and draft #8854 at 880b7369; §5 re-measured at fa22d573. Status: decided 2026-10-26, outcome B with four conditions (§4); written for both maintainers to read together.

    1. What #8854 is¶

    8854 answers the architecture review of 2026-10-25. That review found the same class of defect recurring because v1, API v3, the socket and in-process callers each apply the common rules in their own place. #8854 makes one place that every one of them writes through. It changes no reply a client sees, except where §3 says so.¶

    part what it does files
    write boundary wraps the driver collection for the six v1 modules, the four socket write handlers and API v3; checks filters for query JavaScript; runs Temporary Target validation on socket writes; emits a storage-write-committed event for each driver operation that changed something lib/storage/write-step.js
    boundary gate fails CI if any of eight adapter files takes a collection outside the boundary scripts/check-write-boundary.js
    read contract inspects returned records without changing them; aggregate Nightscout-Data-Warnings header on API v3 reads; a bounded read-only diagnostic command lib/storage/read-contract.js, scripts/diagnose-data.js
    guards the cache tolerates object-valued dates and malformed ids; an authorization subject whose _id is unusable is skipped at load and stays stored; history cursors ignore malformed server times; a future server clock is warned about, not rewound lib/data/ddata.js, lib/authorization/storage.js, lib/server/srv-dates.js, lib/api3/generic/history/operation.js
    CI --fail-zero on every mocha command package.json
    pinning a 336-cell CRUD-by-id matrix whose cells equal a fresh dev baseline tests/api.crud-by-id.matrix.test.js

    Its own follow-up list names what it does not do yet: full write intent and event fan-out, atomic validation, read inventory, delivery and cursors, units and identity, validation policy, and stronger CI gates.

    2. How it relates to the plans in this repository¶

    plan item what it specifies relation to #8854
    WC-STEP-PATCH (write contract §2.3) write(intent) returning WriteResult.items[], one step for every path, today's matrix pinned #8854 is the layer underneath: it routes every path through one place but keeps the driver's results. write(intent) becomes its follow-up 1.
    SEAM-REFRESH (the September seam chain, 65ce54b9) a backend-neutral storage interface and filter AST, module conversions, PostgreSQL built on a base 678 commits behind dev; a single merge conflicts in 30 paths. Under #8854 the chain is reference for later slices, not a replay.
    D2–D4 (execution plan) shared storage with a tenant discriminator; PostgreSQL with row-level security for hosted; MongoDB permanent for single-tenant #8854 is MongoDB only and adds no tenancy. Two backends need the boundary to call a backend-neutral interface instead of a driver collection, which is an additive change inside write-step.js.
    D8 API v3's closed operator set is the query contract; v1 bounded #8854 passes Mongo filters through and refuses query JavaScript; the filter AST is a later slice.
    T4 (sync transport) one change event per write call, carrying the stored documents or removed ids, the largest srvModified and the origin #8854's event is per driver operation and carries counts only. See §3.2.
    BF-164 plan C (maintainer, 2026-10-25) /storage stays v3-only; records from other paths are announced there once write checks cover every path, and only those that pass the type checks #8854's event is the natural hook for plan C, if it carries the records.

    3. The differences, one at a time¶

    3.1 The name write-step and the contract behind it¶

    #8854 WC-STEP-PATCH
    shape a Proxy over the driver collection; callers keep Mongo method names and $set/$unset write(intent); callers state what they want written
    result the driver's own result and errors, unchanged WriteResult.items[], one per record, with its _id, identifier and outcome
    • Existing clients: no effect. Both are internal.
    • Next phases: write(intent) can sit on top of the Proxy, so the two are layers, not rivals. The shared name is the only friction: two different contracts would answer to "the write step".
    • Cost now vs later: renaming either one is cheap at any time while the module has no outside callers.
    • Suggested: keep #8854's module as the persistence boundary. Name the intent layer separately (for example write-intent.js). Amend the write-contract spec to say that layer 1 is #8854's boundary.

    3.2 The commit event¶

    #8854 T4
    granularity one per changed driver operation, including the committed part of a failed bulk write one per write call
    contents collection, source, operation, partial flag, counts; no documents, ids or selectors the stored documents or removed ids, the largest srvModified, the origin
    consumers none yet caches, /storage delivery under plan C, the hosted change feed (D6)
    • Existing clients: no effect. The event is internal and nothing subscribes to it.
    • Next phases: plan C and the change feed need the records. A count-only event cannot tell a subscriber which records to announce.
    • Cost now vs later: changing the shape is cheap until the first subscriber exists, and rises with each one.
    • Suggested: land the event as internal and unstable, and settle its shape in the slice that adds the first subscriber (plan C's hook). That slice adds _id, identifier and the origin, internal only.

    3.3 A refused socket write answers []¶

    8854 checks a whole socket dbAdd batch before the first write. Under WRITE_VALIDATION=reject, one invalid treatment refuses the batch, and the reply is [].¶

    today on dev #8854 decided for API v1 (#8841, D2)
    socket dbAdd with an invalid Temporary Target, reject stored; the socket is not validated the whole batch refused, reply [] the valid items are stored and the refused ones reported, one reply object per item
    • Existing clients: only sites that set WRITE_VALIDATION=reject are affected; the default is off. [] is also what the socket answers when an entry, food or activity whose _id is already stored is re-sent (write contract C6). A client cannot tell a refusal from that case, or from a failure. Under the upload-400 study, a refusal a client cannot recognise is lost silently.
    • Next phases: per-item results (ID-BATCH, write contract §2.3) are the planned shape on every path.
    • Cost now vs later: small either way, because reject is opt-in. Once a release documents [] as the socket's refusal, changing it is a behaviour change on that path.
    • Suggested: either apply D2 to the socket in #8854 (store the valid items; a refused item gets an object with a refused member), or leave socket validation out of #8854 until the socket's reply is decided.

    3.4 Nightscout-Data-Warnings on every API v3 read¶

    8854 sets Nightscout-Data-Warnings: <rule>=<count>, … on any API v3 response whose returned records break a read-contract rule. It is on by default and not tied to WRITE_VALIDATION.¶

    • Existing clients: a client that ignores unknown headers sees no change. The header carries rule names and counts only, no values or ids. It is a new public name, served by default.
    • Related decisions still open:
    • MOD-WRITE-VALIDATION-READ (needs decision) asks whether and how API v3 reads flag stored records that break a rule.

    • 8841 already uses a different convention for the same family of signal: Warning: 299 - "…" on v1 write replies (lib/api/index.js:94, lib/api/treatments/index.js:151).¶

    • Next phases: whatever name ships in 16.0.0 is the one clients and Nocturne will be asked to match.
    • Cost now vs later: renaming or gating it before a release costs a line; after a release it needs a deprecation.
    • Suggested: hold the header out of 16.0.0, or ship it behind an off-by-default setting, and settle its name and default in MOD-WRITE-VALIDATION-READ together with the Warning: 299 convention.

    3.5 Nocturne serves identifier equal to _id¶

    Not part of #8854. Raised by its follow-up 5 ("agree _id versus identifier precedence with client authors").

    • On dev, since #8845 (BF-169, BF-170): identifier is the client's sync identity, _id the server's key, and API v3 refuses a client _id.
    • On Nocturne 970031f6, re-checked at 36d5ef4a2 (2026-10-26), API v3 serves identifier and _id as the same 24-hex value (Controllers/V3/BaseV3Controller.cs:262-270 at 36d5ef4a2). Its open issue #1932 records that a client identifier is ignored on all three collections. This concerns the v3 surface Nocturne serves, not its write-back to Nightscout, which since 8a12bc163 (2026-09-27) sends a legacy id or a UUID's 24-hex prefix.
    • AndroidAPS, the only API v3 client, stores the server's identifier and works against both.
    • Next phases: controllers that send their own identifier (the Loop proposal; registered instances, where it is mandatory) would get different results from the two hubs.
    • Who: a shared-contract question for Nocturne's maintainers and ours. Nothing changes in #8854.

    3.6 #8501 and per-tenant alarm acknowledgements¶

    Not part of #8854. - #8501 (open since 2026-05-05) stores alarm snooze state in MongoDB (lib/storage/alarmStorage.js), so an acknowledgement holds across processes. - The September seam's T4.4/T4.4a (01c5b6d8, 81a1f6ce) does the same with lib/storage/ack-store.js, as one acknowledgement fact per tenant. - Who: review #8501 against T4.4 before either lands, so single-tenant and hosted keep one acknowledgement model.

    5. What a #8854-first path keeps compatible¶

    must hold pinned by
    backward _id forms: ObjectId, upper- and lower-case hex, UUID; UUID_HANDLING moving a non-hex _id to identifier #8854's matrix; tests/identity-matrix.test.js
    backward the API v3 create and deduplication reply, and the refusal texts AndroidAPS matches tests/write-validation.test.js; the v3 suites
    backward Loop's syncIdentifier and Trio's id stored and returned untouched the write-contract matrix
    forward a backend-neutral interface above the boundary, and write(intent) above that (D2–D4) the next-gen plan's ST-FILTER to WC-STEP-PATCH

    forward one event per call carrying the records (T4, plan C) ST-EVENT

    Measured 2026-10-26, in the replay trial (seam/replay-2610 f41cb244, seam/compose-8854-2610 873c0cbb, local):

    • #8854 changes nothing the write-contract matrix sees. 0 of its 336 cells differ from dev. Its cells cover four paths (v1, v3, socket, in-process), with stored state, server dates, history and emissions.
    • #8854's own matrix covers other ground. It covers CRUD by id, internal create and re-send, validation on four paths, and a boundary-source assertion per cell. It does not cover re-send identity, soft delete, server dates and history, or emissions. Each slice is gated on both.
    • The September seam's interface composes above #8854's boundary. They conflict in 2 paths, and #8854's 367 tests pass on the composition.
    • The boundary check needs one rule to accept a collection acquired through the interface (scripts/check-write-boundary.js flags websocket.js there). This is small, and it can be made in #8854 or in the first slice after it.

    Re-measured at fa22d573, the head after #8854 left draft (three commits past 880b7369: a7e65ecf atomic validated updates in lib/storage/validated-update.js, 3b095381, fa22d573):

    • Write-contract matrix. 0 of 336 cells differ from dev, and 0 with WRITE_VALIDATION=reject on both sides. The replay's known 3-cell difference shows the comparison can go red.
    • Validated updates are not covered by our matrix. Its fixtures carry no Temporary Target fields, so the new code path is reached only by #8854's own tests. Extending the matrix is the next-gen plan's QC-MATRIX-TT.
    • Composition. The September interface still composes above the boundary: the same 2 conflicting paths, and #8854's tests pass 429 of 430. The one failure is the boundary check's rule described above.
    • Socket updates on the composition. They now go through the interface into #8854's compare-and-set, and its socket, v3 and cross-path conditional-update tests pass.
    • What validated updates mean for the plan.
    • The compare-and-set sits at the driver edge and builds its filter with MongoDB $expr/$literal (validated-update.js:48-57).
    • For MongoDB it closes #8854's open item 2 (atomic validation).
    • It makes socket validation simpler.
    • Before a PostgreSQL backend, the same guarantee needs a backend-neutral adapter method (for example updateIfUnchanged(filter, snapshot, update)). The MongoDB adapter keeps $expr; PostgreSQL does it in SQL. That moves where the code lives, not what it does.
    • Conditions unchanged. The four conditions of §4 still apply at this head, as checked by session -66: the header at read-contract.js:93, the event at write-step.js:62, and the socket's [] at websocket.js:533/557/569.

    The next-gen platform plan lays these out as five slices after #8854.
