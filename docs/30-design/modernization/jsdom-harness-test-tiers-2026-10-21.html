    The jsdom test harness after cut 1: test tiers and per-file disposition, 2026-10-21¶

    Record

    Record as of 2026-10-21. A point-in-time document; it is not kept up to date.

    Contributor-facing. Snapshot, 2026-10-21, on official/dev 04d435eb (the 15.0.10 cycle start; its tests are identical to v15.0.9's 4bca2ac2), published cut 1 chore/retire-jsdom bce12ecc, the cut 5 tip chore/nightscout-modernization b1bdaca0, the local rehearsal branch rh/cut1 c77797e0 (see the cut rehearsal) and the cut 1 work branch wip/cut1-onto-15.0.10 8c117dd4; the last two are not pushed. Read-derived: every row comes from file contents and git log; no suite was run for this note.     1. What is decided and what is open¶

    Decided for cut 1 (maintainer, 2026-10-21, recorded in RT-REBASE's notes as option C): cut 1 ports the D3 (BF-103), clock-client and pill-title coverage to tests/browser/, keeps the jsdom harness for the rest of dev's tests, and a later cut retires the harness (RT-JSDOM-REST, which cut is not decided). wip/cut1-onto-15.0.10 carries those three ports (fcd90f26, 65248bed, 853b4145) and still has jsdom ^26.1.0 and every harness fixture.

    Decided for RT-JSDOM-REST (maintainer, 2026-10-21): scope B.

    scope what RT-JSDOM-REST removes jsdom afterwards
    A. Full removal benv/headless and secure-jsdom; every remaining DOM test becomes a browser test or a DOM-free test removed
    B. Three tiers (decided) benv/headless only; secure-jsdom stays for DOM tests with no layout dependency kept, upgraded to 29.x

    Why B. Section 4 shows that A and B differ on four test files today, because cut 1, the rehearsals and the cut 1 work branch have ported most of the suite. The difference is in what happens next. Between 2026-09-05 and 2026-10-07 dev added 11 jsdom test files (9 of them on secure-jsdom) and changed 4 more and the d3-chart fixture (section 4.1). None of the added files loads on published cut 1, which deletes the fixtures they require; the rehearsal found four of them as a semantic conflict with no textual conflict and ported them by hand (rh/cut1 5c121e4b). Under A, every jsdom test a backfix adds to dev needs the same port before the harness can go. Under B, a test written for secure-jsdom stays as it is. B also keeps npm test runnable without downloading a browser.

    dev's own docs/proposals/testing-modernization-proposal.md (Track 1, "Locked-Down jsdom Harness", and Track 2, "Logic/DOM Separation") describes tiers 1 and 2. Cut 1 adds tier 3.

    Upgrading jsdom in place, keeping benv/headless, is not one of the scopes: the whole-bundle harness loads node_modules/.cache/_ns_cache/public/js/bundle.app.js (the stale-bundle trap behind BF-173), and an upgrade changes nothing about stubbed geometry. The upgrade to 29.x is independent of the scope and can happen in cut 1 or before it (section 2).

    3. The tiers¶

    tier runs in belongs here never here
    T1 DOM-free plain mocha (npm run test:core, npm test) selection, filtering, unit conversion, duration cutting, URL building: logic moved into lib/client-core/ or another module with no DOM anything that reads the DOM
    T2 secure-jsdom (scope B only) plain mocha DOM structure, form handling, event wiring, text a renderer writes, SVG attributes computed by d3 scales layout, getBoundingClientRect, CSS computed values (touch-action), real d3 transitions or timers, a real socket transport, sanitizer and XSS behaviour
    T3 browser npm run test:browser (Playwright) everything in T2's "never here" column, and whole-page behaviour logic that T1 can test

    Sanitizer and XSS tests are T3 because a jsdom test checks DOMPurify against jsdom's HTML parser, not the browser's; mutation-XSS results depend on the parser. Cut 1 already moved sanitizer-differential and the DOMPurify reference tests to the browser.

    Rules for T2, so that it stays honest:

    1. Modules, not the bundle. A T2 test requires the lib/ modules it exercises. Nothing in T2 loads the built bundle; tests/fixtures/headless.js, benv-loader.js and benv-shim.js are deleted.
    2. No geometry stubs. A test that needs getBoundingClientRect, an explicit chart extent or a computed style to pass is T3. tests/fixtures/d3-chart.js sets the chart extent by hand ("jsdom has no SVG animated width/height"), which is why every test that uses it is T3 in section 4.
    3. Network blocked. createSecureDOM blocks resource loads, fetch and XMLHttpRequest.send; tests inject their own stubs. tests/fixtures/secure-jsdom.test.js and tests/dependency-jsdom.test.js stay as the harness's own checks.
    4. T1 first. Where a T2 test is really checking a calculation, the calculation moves to T1 and T2 keeps one rendering check. tests/profileeditor.records.test.js (pure modules in lib/client-core/profile-editor/) is the model.

    4. Per-file disposition¶

    Column key: it() is the number of it( call sites in the file (loops expand at run time). Harness is what the file uses on dev: secure = fixtures/secure-jsdom, globals = fixtures/dom-globals, benv = the benv shim, headless = the whole-bundle harness, raw = new JSDOM directly, d3-chart = the stubbed chart fixture. Port names an existing browser or DOM-free port. The last two columns give the disposition under scopes B and A.

    6. Run time¶

    Measured 2026-10-21 on wip/cut1-onto-15.0.10 8c117dd4 in a scratch worktree (Node 24.15.0, Chromium 153.0.8010.12, 16 cores, load average below 2), playwright-core 1.63.0:

    run cases wall time anchor
    the four files B keeps on secure-jsdom or moves onto it (boluscalc.quickpick-rebuild, client.renderer.tooltip-units, clock-token-link, report-daytoday-durations), one mocha process 36 1.93-2.09 s over 3 runs, of which about 1 s is mocha start-up npx mocha --exit <files>
    the same four, one file per process 8 / 14 / 11 / 3 0.63 / 0.82 / 1.62 / 0.72 s as above
    the browser suite, Chromium 444 85.4-87.7 s over 3 clean runs npm run test:browser

    In the browser suite, comparable DOM tests (stored-outputs, profile-settings, pill-tooltips, hashauth) take about 0.2 s per case. At that rate, the 36 cases scope A would have moved to the browser add an estimated 7 s per browser run, against about 1 s of in-process jsdom time; this is an estimate from per-case averages, not a measured port. CI runs the browser suite in 6 cells (Chromium, Firefox and WebKit on Node 22 and 24). The largest single cost is tests/browser/clock-client.test.js: 17 cases, 31 s, of which the four stale-data cases from 48ba1856 take 29 s (three at about 8 s, one at 4 s; each runs 15 to 30 simulated minutes under page.clock.runFor).

    One further run, the first of four, reported 408 passing and 6 failing; its failures were not captured (dot reporter), and the three runs after it passed all 444.
