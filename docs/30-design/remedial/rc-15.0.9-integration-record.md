**The `cob.lastCarbs` trace (BF-133's open question).** `lib/plugins/cob.js` names the last carb
entry in array order, and the dataloader sorts treatments with `(a, b) => a.mills - b.mills`.
Records written through API v3 reach the server's in-memory cache without `mills`:
`lib/api3/storage/mongoCachedCollection/index.js` passes the stored document to the cache as it is,
where the v1 paths add `mills` first. With such a record in the array, the comparator returns
`NaN`, and the order the sort produces no longer follows time. The code is the same on 15.0.8.

- **Measured:** a trace run (T1) repeated R29 with a scratch instrument loaded into each server
  (started by hand from the run's own environment file; no harness change). Over about 1750 reloads per
  arm, every time the last carb entry in array order was not the newest one, the array held
  AndroidAPS v3 records without `mills`, and never otherwise (A: 828 before the restart, 497 after;
  B: 827 and 500). `cob.lastCarbs` always equalled the last carb entry in array order.
- **Why the arms differ:** before the restart both arms name the same wrong entry, so nothing is
  reported. After it, 15.0.8 also holds the soft-deleted AndroidAPS records (BF-135), so the arms'
  arrays differ and the sort puts a different entry last. The traffic is identical, so the result
  repeats tick for tick.
- **Not a 15.0.9 regression:** it is BF-133's mechanism on both trees.

**A candidate new finding from the trace (not filed; for the coordinator).** `lib/plugins/iob.js`
and `cob.js` count a treatment only when its `mills` is not after the current time, so a record held
without `mills` counts in neither. In real time the next incremental load normally replaces a new v3
record with a copy that has `mills`. It does not when the record is dated earlier than that load's
window, as a late AndroidAPS upload is. A scratch reproduction on a fresh test database showed the
same on 15.0.8 and `699eb5fa`, with identical numbers. Once the server held enough treatments to
take its incremental load path, a v3 bolus and a v3 carb entry dated in the past did not change the
server's treatment-based IOB and COB until a restart. A v1 bolus of the same age, and a v3 bolus
dated now, were counted. With only a few treatments held, every load is a full load and the late
records counted at once. The server prefers a current IOB or COB from device status, so a site whose
AndroidAPS uploads device status would not show it in the pill. Live on 15.0.8, so not a 15.0.9
regression. The browser's own calculation was not checked. Details:
[proof-2026-09-27](../../../tools/lab/rc-soak/results/proof-2026-09-27.md#why-coblastcarbs-names-an-older-carb-entry-bf-133).

**Run 018's `bgnow` miss, explained.** In run 018's R24, 15.0.8's `bgnow` was empty once, at tick
282 and 3 s later. Tick 282 carries the first reading that falls inside the dataloader's two-day
entries window (in a compressed run the readings age into it during the run). The property is
rebuilt only when a reload finishes, and a write's reload is debounced with data promised within
5 s (`UPDATE_MAX_WAIT`). The harness asks 60 ms after the write and again at 3 s, both inside that
limit. The code on this path is the same on both trees, and R29 did not show it, so it is a timing
race on the first in-window reading, not a defect.

## Method

Every run follows these rules. A run that departs from one says so in its own section.

- **Candidate by SHA.** The candidate is built from `dev` by SHA, one `git merge --no-ff` per unit,
  and never pushed. Each unit's head is checked against its PR head before merging and again at the
  end of the run.
- **One mongod per cell.** Each cell gets a fresh `mongo:<ver>` container with
  `--ulimit nofile=64000:64000` (the #8758 suite peaks near 1130 open files). The server version is
  read from the container before the cell runs. The database is dropped before every run.
- **Rebuild the bundle after every merge.** The client tests run against the production webpack
  bundle, so a stale bundle reports an already-fixed defect.
- **A cell that prints no mocha totals counts as a failure.**
- **Additivity by title.** At each step, the sorted list of passing test titles is compared with the
  previous step's, leaving out lines that carry a generated ObjectId. A step may add only its own
  unit's titles.
- **Break-its count only when the failures show the defect.** A break reverts or edits one unit's
  fix, runs that unit's tests, and restores. `git status` must be clean afterwards, and the tests must
  pass again.
- **Harness red control.** The same runner is pointed at a tree or database set up to fail, to show
  that a green result depends on what it claims to test.
