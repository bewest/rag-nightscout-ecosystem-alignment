## `lib/api/index.js`: the overlap

This is the one file edited by both `bf/count-zero-empty` and `bf2/auth-hardening`.
The combined suite had not run before this record.

**Inspection.** In the merged file the two changes are textually and functionally
disjoint.

- auth-hardening adds one line after the app is created:
  `app.set('trust proxy', require('../server/client-ip').compileTrust(env.trustProxy))`.
  It is verbatim from `06c83f2f` on the modernization branch.
- count-zero replaces the body of the `validateCount` middleware and adds
  `refuseCount`, about 40 lines further down. `validateCount` reads only
  `req.method` and `req.query.count`. It does not read `req.ip`, `req.secure`,
  `req.protocol`, `req.hostname` or anything else that depends on `trust proxy`.
- The throttle's address key is `data.ip`, which `lib/authorization/index.js`
  resolves through `createClientIP(env.trustProxy)`, independently of Express's
  setting. With `TRUST_PROXY` unset that is `forwarded(req, req.headers || {}).ip`.
  Dev's `getRemoteIP` is `forwarded(req, req.headers).ip`, the same call, and dev
  makes it at the same sites (`lib/authorization/index.js`, `lib/server/websocket.js`,
  `lib/api/status.js`, `lib/api3/{alarmSocket,storageSocket,security}.js`). The only
  difference is the `|| {}` guard for a request with no headers.

**Count rules, live.** Measured on the final tree with `lib/server/server.js` on
127.0.0.1:11537, the agent's own database, API v1, 5 treatments seeded:

| request | answer |
|---|---|
| GET entries and treatments, `count=0` and `count=00` | 200 `[]` |
| GET, `count=5`, `count=9007199254740991` | 200 with records |
| GET, `count=0x10`, `2.5`, `-3`, `1e2`, `abc`, `9007199254740992`, `99999999999999999999` | 400 `Bad count` |
| POST treatments `count=abc`; PUT `count=abc`; PUT `count=0` | 200, record stored each time (5 → 6 → 7 → 8) |
| PATCH treatments, with and without `count=abc` | 404 both: v1 has no PATCH route, and `count` does not change the answer |
| DELETE matching all 8, `count=0`, `00`, `abc`, `-3`, `2.5`, `0x10`, `1e2`, `99999999999999999999` | 400 each; 8 records remain after every one |
| DELETE matching all 8, `count=2` | 200; 0 remain: a valid count is accepted and does not limit the delete |

The server answered `/api/v1/status.json` with 200 before the first probe and
after the last one. The test file names none of `9007199254740992`, PUT or PATCH,
so those rows rest on this probe alone.

**Overlap break-its.**

- *count-zero's hunk reverted, auth-hardening's line kept.* 17 of 36 count tests
  fail on the original symptom (table above). The full suite was not run under
  this break.
- *auth-hardening's line removed, count-zero's hunk kept.* `client-ip`,
  `authdelay`, `authsubjects`, `env`, `server.security-headers` and
  `api.count-parameter` all pass (154), and so does **the full suite, 2508/0/3**.
  The line has no test.

  A direct Express check (a sub-app with and without the line, `TRUST_PROXY` unset,
  `false` and `10.9.9.9`, request carrying `X-Forwarded-For` and
  `X-Forwarded-Proto: https`) shows why:

  - Mounted under a parent whose `trust proxy` is set as `lib/server/app.js` sets it,
    `req.ip` and `req.secure` are the same with and without the line, for all three
    values. Express 4 gives a mounted sub-app that has not set its own `trust proxy`
    the parent's setting.
  - Standalone with `TRUST_PROXY` unset, the line changes `req.ip` from the peer to
    the forwarded address and `req.secure` from false to true. No code under
    `lib/api/` reads either.

  So the green result is an inert line, not a blind test. Its effect is only in
  code that builds the v1 app without `lib/server/app.js` and then reads those
  getters, and no such code exists in the tree.

**Finding.** Both behaviours survive the merge. The count rules hold on the merged
file and on the running server. auth-hardening's unset default is dev's
`forwarded-for` call, and the throttle keys on `data.ip` (the unset-mode pin
"keys on the forwarded header as dev does today" fails when the key is broken).
The overlap is textual adjacency only.

**Recommendation: fold it into the auth-hardening PR as its own final commit.** It
cannot merge before auth-hardening. It edits the same function for the same
reviewer. The plan groups PRs by reviewer. And the decision it implements (BFQ-47:
the allow-list is intended, the fix is the admin-page loss) belongs to the
allow-list auth-hardening introduces. Keeping it as a distinct commit keeps it
droppable. If the maintainer wants a separate evaluate-then-merge step for it, open
it only after auth-hardening merges, so its diff is the one commit. The decision is
the maintainer's.
