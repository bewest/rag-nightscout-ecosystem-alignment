## Step 10: `lib/api/index.js` and `lib/api3/index.js` after the trims

**Files.** On `1b1977e0`, `lib/api/index.js` is byte-identical to its version on
`bf/count-zero-empty` `d19043b2`. Its diff against dev is count-zero's hunk alone:
`refuseCount` and the new `validateCount` body, +37/−6. `lib/api3/index.js` is identical
to dev. Record c found a textual adjacency between #8748 and auth-hardening in
`lib/api/index.js`. That adjacency no longer exists: auth-hardening no longer edits the
file.

**Live check, count rules and TRUST_PROXY.** The server was booted from
the real `lib/server/env`, `bootevent` and `lib/server/app.js` on `1b1977e0`
(`lib/server/server.js`, 127.0.0.1:11539, its own database, Node 20.20.0). A
`require.cache` wrap appended one read-only probe route to the v1 app. The probe
returned:

- `req.ip` and `req.secure`;
- the address `createClientIP(env.trustProxy)` resolves, which is what
  `lib/authorization` passes to the throttle;
- whether the v1 and v3 sub-apps hold their own `trust proxy fn` or the parent's.

No file in the tree was edited. Each setting got a request with no forwarding headers and
a request with a two-entry `X-Forwarded-For` chain plus `X-Forwarded-Proto: https`, from
the loopback peer.

| TRUST_PROXY | boots | chained request: `req.ip` = throttle address | `req.secure` | v1 / v3 fn | boot line |
|---|---|---|---|---|---|
| unset | yes | left-most forwarded entry (dev's `forwarded-for` answer) | true | parent's (inherited, own setting absent) / same | the unset SECURITY warning |
| `false` | yes | the socket peer | false | parent's / same | "keyed on the client address as resolved through TRUST_PROXY=false" |
| `127.0.0.1,::1` | yes | the entry the trusted peer added (right-most) | true | parent's / same | "… resolved through TRUST_PROXY=127.0.0.1,::1" |
| `1` | yes | the entry added by the proxy one hop away (right-most) | true | parent's / same | the hop-count line |
| `true` | yes | left-most forwarded entry | true | parent's / same | the every-hop SECURITY warning |
| `0` | no: startup error `TRUST_PROXY must be false, true, a whole number of proxy hops …` | | | | |

With no forwarding headers, every setting that booted gave the peer and
`secure: false`. In every row that booted, `req.ip` and the throttle address agreed.

The same five running servers each answered the count rules as record c recorded
(5 treatments seeded):

- GET `count=0` on treatments and `count=00` on entries: 200 `[]`.
- GET `count=2`: 200 with records.
- GET `abc`, `2.5`, `-3`, `0x10`, `1e2` and `9007199254740992`: 400 `Bad count`. These
  were measured with TRUST_PROXY unset only. The other four settings were checked with
  `abc`.
- DELETE matching all records with `count=0` or `count=abc`: 400, and 5 records remained.

`/api/v1/status.json` answered 200 on each.

**The API v3 trim is inert in production.** This was measured here with the installed
Express 4.22.2 and the branch's `compileTrust`. The parent sets `trust proxy` as
`lib/server/app.js:52` does, and the sub-app is mounted at `/api/v3` without its own
line. The sub-app's `app.get('trust proxy fn')` is then the parent's function itself
(`===`) for unset, `''`, `false`, a CIDR (`10.0.0.0/8`), `1`, `true` and `127.0.0.1,::1`.
It carries the legacy marker exactly when TRUST_PROXY is unset or empty.

`lib/api3/security.js:34` reads that function for the API v3 failed-login key:
`clientIP.getClientIP(req, app.get('trust proxy fn'))`. The live probe confirms it on the
booted server: `api3InheritsParentFn: true` and no own setting, for every value above.

With the removed line put back, the sub-app's function is a separately compiled
function. It is behaviourally the same one, and the `0a74ef4e` commit message reports 54
identical answers with and without it. That comparison was not repeated here.

**No test covers the API v3 key under the production unset default.**
`tests/fixtures/api3/instance.js` mounts the API v3 app on a bare `express()` parent,
with no `trust proxy` set (lines 120 and 132). There the sub-app inherits Express's
default. That default carries no legacy marker and does not trust the peer, so the API v3
tests see the socket peer, not the unset-default resolution production uses.

The `client-ip` tests that call `lib/api3/security.authenticate` pass an app built by
their own `appFor()`, which sets the trust itself. They do not use the mounted app. The
unchanged 2534 at step 10 is consistent with this: before the trim, the fixture's
sub-app had its own line. After it, the sub-app has the fixture parent's default, and no
test distinguishes the two.
