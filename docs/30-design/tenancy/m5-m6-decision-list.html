    M5/M6: current decisions and next review¶

    Living document, last changed 2026-11-10 at 4917b2d4a.

    Living contributor-facing decision index, 2026-11-10. Read this before older question packets. Release decisions own adopted policy; the roadmap owns acceptance; the queue/dashboard own claimed work/milestone state. This index records no new application measurement or promotion.

    Execute now¶

    2026-11-09 restructure. M6 is now M6a identity and owner API, M6b lifecycle and keys, M6c deployment trust (in nightscout-deploy), M6d connector sync, and M7 production readiness (decision). The owner/OIDC native matrix runs through a disposable harness (MT-OIDC-NATIVE); the grant/reservation ceremony is retired. Vault connectivity is a Vault Agent sidecar (DEPLOY-VAULT-AGENT) plus a tokenFile read in core (MT-VAULT-TOKEN-FILE). The umbrella queue items are closed as superseded; one capability item per remaining gap.

    The functional M5 reference on one host is accepted in R73. It includes bounded current-state/evaluator recovery, durable alarm/request state and actual reference-role/browser consumers, with accepted final comprehensive verification. Publication and remote CI retain their separate records; production/default admission and live provider/device delivery are not implied.

    Reuse the recorded proof gates for source-identical evidence instead of repeating native cases for documentation changes. New source behavior still needs affected checks and an appropriate joined verification. Do not silently add later provider, capacity or multi-node work to the satisfied M5 functional bar.

    M6 now includes accepted native tenant-local restore/restart and cold Compose reference evidence. The published ed2 candidate closes that bounded clinical restore capability; restoring or cloning credentials/identity is a separate contract. The owner/OIDC and internal service API work (M6a) and the lifecycle, key-retention, ownership and single-site provisioning work (M6b) have joined acceptance records (M6a, M6b); publication state and the remaining boundaries are in the release contents. The completion schedule owns assignments; the roadmap acceptance families own observable completion. Prefer a minimal working base with explicit later enhancements; that preference grants no production permission or criterion waiver.

    Human policy review¶

    These are bounded topics for a concrete proposal, not blanket implementation stops. A recommendation remains a proposal until recorded in release decisions. Shared OIDC/provider-backed renewal, bounded existing access during provider outage and tenant-wide alarm suppression are adopted. Review remaining session effects and operational parameters while implementation continues. Notification retry responsibility and deletion ceremony policy are settled. Their bounded proofs do not resolve live-provider admission or wider M6 identity/trust. The first-preview owner surface (settings, thresholds, credentials, integrations) is settled. The first-preview external delivery channel (no push provider; Nightscout-to-Nightscout sync) is settled. M6 human session effects (idle scope, logout, renewal, transport) are settled. M6 deployment and trust (ingress peer-list trust, one-provider secrets ladder, generic OIDC adapter with Authentik as intended reference, probe-plus-record admission) are settled. Vault Agent scope is settled: one AppRole per deployment; tenant separation at Vault is not a goal. Evaluator partitioning is settled in direction: member count and ordinal flag with a pool-membership table.

    The 2026-11-10 decisions (activity policy, root and admin tools, restore census, export removal, admin listener address, internal listener, evaluator revision and alarm repeat) are rows in the table above. No human-policy topic is open.

    The owner lifecycle packet retains source surveys and alternatives; its recommended grace periods, invitation lifetimes and self-service operations are not approved defaults. The earlier open-decision note preserves already answered A questions, not the current backlog.

    The counter and restore options analysis separates the tenant-local history clock from internal insertion order. The tenant-local insertion prototype removes cross-tenant allocation state while preserving supported per-tenant order; exact physical and logical backup fidelity retain their separate contracts.

    From preview to production¶

    The production critical path maps these adopted requirements to closing evidence and conditional topology choices. It separates M6 completion, a coherent released candidate and per-deployment production admission. Its proposed one-cohort scope and HA deferrals are not adopted policy.

    Measure before setting limits¶

    Decision 2026-11-09 (row): the envelope is measured first, not declared. MT-BENCH-BASELINE benchmarks the one-host reference at stepped synthetic tenant counts with a hot tenant and publishes p50/p95/p99 latency, socket fanout, evaluator cycle time, pool/lock waits, CPU and memory per role, disk per tenant-day and reconnect recovery. MT-BENCH-CONTRAST runs the same workload against the shapes operators run today (N single-tenant Mongo processes; the per-site process model) and reports the comparison side by side. MT-SCALE-UNBOUND proves each component scales horizontally or vertically as intended and itemises any binding with file:line. Limits, polling cadence and replay horizons are then set from those numbers. Use the experiment contract for oracle and control design. Nothing here is a prerequisite to current correctness work, and no number is invented from functional passes.

    Reviewing and closing a topic¶

    Bring one topic with current code anchors, user/operator effect, compatibility, recommendation, alternatives, reproduced evidence and named unknowns. Record the answer once in release decisions, link it here, and update the acceptance family. Do not add per-commit journals. The coordinator maps each required family to an actual source/command/artifact/verdict and records any explicit deferral before milestone promotion. M5/M6, real-data/identity admission and production/default role enablement remain separate claims.
