    Evaluator, realtime and API communication¶

    Living document, last changed 2026-11-10 at 4917b2d4a.

    Contributor-facing living explanation, 2026-11-07. Mechanisms below are read-derived from cgm-remote-monitor 151de0248a1e4301c85b5c638185eec3ca8c38e6, tree 3bb46431a19e604dc028768f0e72e6ad29616c26. Source file/line anchors were checked against that immutable tree. These are branch implementation mechanisms; pinned source links identify the inspected revision, not a released feature. Recorded reproductions retain their own source in the evidence section. The later c23 native matrix measures bounded tenant-local restart behavior; it does not relabel this inspected tree as the executed source.

    This guide explains which process owns each result and which messages cross a boundary. Decisions remain in tenancy decisions, the durable event contract, owner authority and the release decisions. The delivery dashboard owns milestone status; this guide does not promote M6.

    The two outputs have different owners¶

    Realtime and evaluator each acquire clinical data from PostgreSQL. The evaluator does not send its SQL projection to realtime. Realtime builds the browser's record frames from its own bounded projection and checkpoint. Separately, evaluator consumers can send a durable alarm/notification intent to realtime for browser fanout. That handoff is not a glucose-data replication stream or proof of device notification delivery.

    Component Owns Reads or sends
    API process Current client authority, REST and existing socket write handlers, canonical clinical mutation Tenant-bound PostgreSQL writes; scoped secrets; private socket authorization/mutation receiver
    Evaluator process Clinical acquisition, plugin cycle and eligibility of its current in-memory output Its own durable input checkpoint/projection; current configuration; independently scheduled durable notification producer/retries
    Realtime process Browser connections, socket namespace state, independent current-record projection Its own SQL reads/checkpoint; current API authorization; private API mutation forwarding; private alarm receiver
    Tenant-admin process Current tenant management and owner authority Separate listener and management credential audience; it does not execute clinical socket writes
    Private restore controller A's suspension, draining and exclusive maintenance claim, committed-data and activation outcome Fixed participants' control endpoints and actual backend identities; per-tenant invalidation

    These are application modules wired by explicit preview role configuration. Separate processes/containers can share a private directory containing Unix-domain sockets (UDS): an endpoint is a transport address, not shared JavaScript memory. The adopted separate-process decision retains this deployment boundary. A local EventEmitter does not become a durable cross-process event bus merely because the processes share a host.

    Clinical acquisition and browser records¶

    The evaluator's acquisition first commits a bounded current-state projection and input checkpoint, then computes the clinical/plugin cycle. Its checkpoint records input acquisition, not completed evaluation or notification delivery. A later failure can therefore leave committed input with no eligible evaluated output. The runtime reports an output revision only from a successful cycle and requires an admitted tenant operation for last(tenant) to expose it. Evaluator acquisition, runtime output and durable snapshot/checkpoint implement these separate stages.

    Adopted 2026-11-10, not in the inspected tree. The output revision changes only when the output content changes (time-driven changes included); an identical cycle keeps its revision, and the realtime consumer is woken on real changes only for tenants with a pending alarm. The inspected code bumps the revision on every cycle (read-derived, cited in the decision). Alarm repetition is separate: an active, unacknowledged, unsnoozed alarm repeats on its own clock equal to the single-site heartbeat (same setting, 60 s by default) and on new data, as on a single site. Both are BF-231 / MT-CONSUMER-STALE-RESELECT work. The evaluator only works tenants eligible under the activity policy: while a site is paused or suspended no alarms are computed or delivered.

    The namespaces for evaluator and realtime checkpoints must be distinct. Role composition enforces that ownership boundary. Realtime projection builds a full replacement frame, including absence, so a hard-deleted record is not retained by a delta-only merge. Its runtime rechecks the configuration identity before fanout and exposes no healthy last value after refusal. Realtime refresh supplies these checks.

    Public API3 identifier and the storage _id are different identities. A browser SGV frame carries the stored record key in _id and its value in mgdl; an API3 POST acknowledgement names the public identifier. Bind them through the actual stored record when comparing transports, rather than assuming the strings match. The shipping frame loader preserves this distinction.

    The current reference uses bounded snapshot reconciliation and polling schedules. It does not implement the full replication-slot/reader-NOTIFY design as a transport between these roles. The durable-event contract owns that longer-term direction; R73's polling/snapshot acceptance does not imply a LISTEN latency guarantee. Time-only evaluator ticks reuse retained successful input; they do not substitute for fresh acquisition or establish recovery after missed writes.

    Notification intents, retries and alarm handoff¶

    The evaluator's optional realtime consumer is separately scheduled from clinical computation. It reads eligible current output and current configuration, reconciles persisted producer state and suppression acknowledgements, and records durable intents with stable origin/request identity. The producer must still be current after pending reads. The coordinator then selects due requests for retry. Producer and consumer coordinator implement this path; when no consumer is selected, it opens no extra consumer pool, timer or socket.

    sequenceDiagram
    participant Eval as Evaluator runtime

    participant PG as PostgreSQL outbox / suppression

    participant Browser as Authorized browser
    Eval-->>Consumer: Current eligible output + configuration identity
    Consumer->>PG: Reconcile producer state and enqueue stable intents
    PG-->>Consumer: Durable request state committed
    Consumer->>PG: Claim due attempt, commit dispatch token/deadline
    Consumer->>Consumer: Recheck current eligibility and suppression
    Consumer->>RT: POST JSON /alarm over private UDS
    RT->>RT: Current tenant/socket authority checks
    RT-->>Browser: Alarm / clear event for admitted tenant sockets
    RT-->>Consumer: accepted:true (handoff receipt, not device ACK)
    Consumer->>PG: Persist accepted or uncertain attempt outcome
    opt Lost response or restart
        Consumer->>PG: Read durable due/uncertain request
        Consumer->>RT: Retry same stable request identity
    end

    The attempt and dispatch state commit before the adapter call; the network wait is not held inside SQL. Deadline, abort or an ambiguous response preserves a durable retryable outcome. Before dispatch, the notifier rechecks configuration eligibility and the current suppression reader, so an old selected cycle is not standing permission to deliver. Notification attempts owns the implementation. Clear requests have their own retirement/suppression handling; this is not a blanket rule to discard every request when an output is unavailable.

    The actual alarm adapter sends tenant, request ID, attempt, notification and receipts to /alarm. Acceptance means the realtime handoff completed. It does not mean a browser displayed it, a person acknowledged it, or a provider/device received it. A lost handoff response can repeat the unchanged request: there is no exactly-once delivery promise.

    A browser's ack follows the private API mutation route below. API checks current credential/tenant permission and, for linked consumer state, current evaluator configuration inside the acknowledgement admission. It persists original suppression state; the evaluator subsequently reads that state. Private acknowledgement admission is distinct from the transport receipt acknowledging an evaluator-to-realtime handoff.

    Browser authorization and mutations¶

    Socket.IO exposes /, /storage and /alarm. Tenant resolution uses the admitted host/configuration mapping. The root namespace accepts the existing authorize shape; /storage and /alarm use their own subscription/credential contracts. Their credential forms and permissions are not interchangeable. The realtime protocol rechecks current authority across asynchronous acquisition and before fanout; a long-lived connection is not a permanent grant.

    sequenceDiagram
    participant Browser as Browser / existing socket client
    participant RT as Realtime process
    participant API as API private UDS receiver
    participant PG as Tenant-bound PostgreSQL
    Browser->>RT: authorize / subscribe with client credential
    RT->>API: /authorize (host, tenant, namespace, credential)
    API->>PG: Current credential + tenant authority reads
    API-->>RT: Current permissions / selected collections
    RT-->>Browser: Namespace-specific acknowledgement and admitted data
    Browser->>RT: Existing mutation or ack event
    RT->>API: /mutate (host + original tenant/credential/event envelope)
    API->>API: Resolve tenant, authenticate transport AND client authority
    API->>PG: Existing socket write handler / suppression transaction
    PG-->>API: Canonical operation completes
    API-->>RT: Existing callback arguments
    RT-->>Browser: Unchanged callback acknowledgement

    Realtime does not replace the user's credential with its database identity. Forwarding preserves the event namespace, arguments and callback shape. Failure or ambiguity produces no synthetic success and no automatic socket mutation retry. The API executor invokes the same socket write handlers/purifier/write intents as the single-tenant socket listener. This is a private HTTP/JSON call over UDS, not a replay of a public REST request. Public REST requests use the real API handlers and shared storage/write-intent ports directly.

    The private API independently resolves the host and compares the envelope's tenant, authenticates the owned transport, verifies the current client credential and checks the operation's permission. Private API and namespace credential normalization define these boundaries. A socket-path possession check is not permission to mutate a tenant's records.

    Wire format and operation lifetimes¶

    The current private transport uses bounded JSON objects in HTTP POSTs over fixed UDS endpoints, with explicit byte/time limits and restrictive same-UID filesystem/socket ownership. It accepts a fixed operation list: /authorize, /mutate, /alarm, /cohort/status and /cohort/invalidate. Application payloads and cohort controls have different handlers; they are not a public administration API. A private directory and fixed manifest are deployment trust inputs, not an authentication substitute for each client's current authority.

    A registered tenant operation surrounds actual HTTP response completion, not just entry into a handler. API lifetime middleware waits for response finish/close; private IPC similarly retains its lifetime through response finish. Socket authorization, forwarding, clinical/evaluator acquisition and notification attempts also use the actual operation window. Tenant-scoped lower handles enforce that window when used. These lifetimes let maintenance drain real unfinished work rather than infer quiescence from a callback returning.

    Disconnect, restart and tenant-local restore¶

    Ordinary process restart reacquires current records and persisted checkpoints. An evaluator's in-memory output is recomputed; a committed input checkpoint is not relabelled as a successful output. Realtime rebuilds its own projection and full browser frame. Durable notification requests survive and retain their retry identity. Current credentials/configuration are checked again; retained process memory does not authorize a new connection.

    The logical restore policy requires forward changes and deletion records for known captured/current clinical identities, preserving public IDs and clinical fields. It retains current nonclinical authority, consumer state and the authoritative live clock; physical backup fidelity is a separate operation. Activity retains its existing full-read behavior rather than acquiring a new v3 history contract. IDs purged from both artifact and current retained history remain outside that bounded guarantee. Logical restore source enforces captured/live floor checks.

    The controller suspends A durably, drains A operations and holds an actual backend-bound exclusive claim. After definite outer DATA commit, it runs registered commit effects, invalidates the configured roles' tenant caches/sockets/output, then activates A. A's sockets disconnect; fresh readers and evaluator acquisition must obtain the restored current state. B has independent tenant operation keys and counters. Lost COMMIT or invalidation acknowledgement does not authorize blind replay, orphan clearance or expiry-based reopening. Controller contract and participant protocol supply this ordering; participant incarnation changes invalidate an old pin.

    Independent startup on the inspected candidate¶

    At 151de024, shared schema/ACL checks remain unconditional. Genuine suspension from the actual registered operation gate defers only that tenant's initialization; a lookalike error code, metadata drift, bad binding, transport failure or other application failure is not swallowed as suspension. The full configured tenant roster remains present. A deferred tenant retries through the same gate when work is admitted, with invalidation retiring its cached initialization. Tenant startup implements this provenance distinction; evaluator metadata admission runs READ ONLY, and consumer admission retains unconditional metadata and actual same-datastore checks before tenant-local initialization.

    Consequently the source intends a restarted shared API/realtime/evaluator process to serve active B while suspended A remains unavailable, with no stale A output. Realtime startup, API startup and evaluator startup use that mechanism. Aggregate health can remain degraded while B is available: do not omit A from the roster or require A to become active merely to make a process health summary green. The c23 native matrix reproduces this bounded restart criterion on its exact later source; the inspected 151de024 mechanisms above remain read-derived.
