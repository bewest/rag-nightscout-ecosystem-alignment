    1. What M4 asks for, and what today's evidence is¶

    The roadmap §4 criterion for M4: v1 and v3 uploader/follower shapes exercised on pinned versions; no coordinated app upgrade requirement; tenant-local identity and correct batch/retry/refusal semantics. The dashboard adds: actual client execution distinguished from source-pattern replay, with M4 blocked on M3.

    Today's client evidence is source-pinned synthetic replay, not client execution:

    • R40 pins NightscoutKit 4ec9fd12 and LoopFollow 4a74b781 and says "this is extracted client-pattern replay, not execution of Swift binaries". R41 repeats "server contracts and synthetic client patterns, not execution of client applications". The owned runner's README says the same (tools/lab/multitenant-rest-preview/README.md).
    • The CRM test that does it is tests/tenant-rest-client-replay.integration.test.js (opt-in NS_REST_CLIENT_REPLAY_TEST=1), whose fixture tests/fixtures/client-replay-patterns.js:5-8 states "Source-derived synthetic patterns, not execution of either Swift application." Its deployment fixture tests/fixtures/client-replay-http.js:3 boots the shipping multitenant CLI as a child (:98, bin/nightscout.js multitenant api) with two tenants in direct-alias resolution (:45-47) and selects the tenant with an explicit Host header (:136-142).
    • The November 2 draft PR body in this directory (multitenant-draft-pr-body-2026-11-02.md, a peer's file) carries only the M1–M3 "remains open" statements; the client-binary wording lives in R40/R41 and in the CRM READMEs, and in the live #8898 body the maintainer refreshed from R54, which is not in this repository.

    So M4's gap is exactly: run real client programs, at their pinned versions, against the preview executable, and classify every difference from single-site Mongo. This packet ranks which clients can be run at all on a Linux lab host, designs the lab for the top three, and names what stays unmeasured afterwards.

    Finding. An unmodified legacy client that sends the SHA-1 api-secret header (the Loop/Trio/xDrip/oref0/connector dialect) or a Bearer JWT obtained from the v2 exchange (the AAPS v3/nightguard/librelink-up dialect) presents a shape the preview accepts on both v1 and v3. A client that puts its token in the query (LoopFollow, oref0 token mode, Reporter) is accepted on v1/v2 through the legacy-exchange path and refused on v3. The pinned-pattern replay already relies on this split (tests/tenant-rest-client-replay.integration.test.js:24-27: "the pinned uploader hashes its API secret and sends api-secret; the pinned follower sends its subject token in the query"; tests/fixtures/client-replay-patterns.js:66-76 builds the follower path with token in the query for v1 and v2). The intentional multitenant difference is that a supplied invalid credential refuses instead of falling back to anonymous (tenant-app/README.md:252-260). No pinned client emits a new-format Ed25519 token; R48's readers are an addition, not a requirement, and this is consistent with the roadmap's "no coordinated app upgrade" criterion.

    What the lab must establish rather than assume: that the v1 legacy domains composed by legacy-domains.js carry the shipping count tolerance (RT-COUNT-COMPAT) and the shipping treatments write validation. Both are inherited by construction and both are UNMEASURED on the preview.

    4. Lab design for the top three (nightscout-connect, oref0, cgmsim-lib)¶

    The design borrows from four existing instruments by name: the journey lab (tools/review/journey-lab/: sites per app, scripted fire steps, a fake vendor upstream, secrets kept outside the tree and never printed), the compat pipeline (tools/qc/compat/: two trees, every differing cell explained, a verdict vocabulary), the id-batch-replies lab (tools/lab/id-batch-replies/: real connector module run cycle by cycle, stored rows counted from the database) and the connector-soak lab (tools/lab/connector-soak/: a source site and token/secret sinks through a counting proxy). The CRM-side scaffolding already exists in tests/fixtures/client-replay-http.js.

    4.1 Server under test¶

    • The explicit multitenant executable: bin/nightscout.js multitenant api (lib/cli/commands/multitenant.js:3-4, PLAT-SERVE D21; exit codes :6-13), with a preview configuration shaped as tests/multitenant-preview-process.integration.test.js:41-56 builds it: resolution.mode = direct-alias, two tenants A and B, each with one alias, per-tenant Vault encryption/signing keys, operator-applied candidate schemas in separate namespaces, the legacy credential catalogue, and domains covering entries, treatments, devicestatus and profile (the collections the three clients touch).
    • Disposable PostgreSQL and Vault owned by the run, as the owned runner does (tools/lab/multitenant-rest-preview/README.md); never a shared database.
    • Tenant A and B each get an imported root reference and one imported subject with the readable role, provisioned the way the replay fixture provisions them (the root credential a client presents is the SHA-1 of A's root, client-replay-http.js:277).
    • Name resolution is the first setup item. The preview selects the tenant from the wire Host. Real client binaries resolve a hostname themselves, so the lab must make A's and B's aliases reach the loopback listener without editing any client: run each client in its own container with host entries for the two aliases, or run the lab's own resolver. Do not switch to canonical-internal for this: it changes the trust surface (preview-config.js:90-101). The setup control: a plain status read with A's credential and A's alias answers from A, and the same read with an unconfigured alias refuses as an unknown tenant (the M2 criterion) before any client is started.

    4.2 Single-site baseline¶

    The same head 35903069 booted single-site on a disposable MongoDB (the compat pipeline's and the matrix harness's boot, tools/qc/write-contract-matrix.js:15-19), with AUTH_DEFAULT_ROLES=denied, one API secret and one readable subject. Every client run is executed once against the baseline and once against tenant A of the preview, from the same container image and the same client version, in the same order.

    4.3 Per-client runs, positive checks, controls and predictions¶

    Each run records, per request: method, path without query values, status, reply shape (array length, per-item keys), and afterwards the stored rows read through an independent oracle (the lab's own PostgreSQL reader for the preview, as client-replay-http.js reads rows; MongoDB for the baseline). Oracle rows are compared with only the normalisation the compat pipeline already uses (cache/wire and top-level server clock stamps, R41's rule); nothing else is normalised.

    Break-it controls for the lab itself (a check that has never failed is not evidence):

    • Remove the Host entries for the aliases: every positive check must go red with a resolution failure, not a 4xx.
    • Point the oracle at the wrong namespace or database: every stored-outcome assertion must go red with zero rows.
    • Plant one unapproved difference in a captured reply before classification: the classifier must report it as unexplained (the control the compat refresh lane used, roadmap §"RC backwards compatibility").
    • Restore each and re-run; the restored run is the one that counts.

    4.4 Differential against single-site Mongo through the compat pipeline¶

    The compat pipeline classifies cells that differ between two matrix runs into named groups with a verdict from Defect | Decided | Bug fix | No value change (releases/cgm-remote-monitor-16.0.0/compat/groups.yaml:10), and refuses to build the page while any cell is unexplained (tools/qc/compat/README.md, step 3). The lab reuses that classification and vocabulary, with one adapter the pipeline does not have today:

    • tools/qc/write-contract-matrix.js boots the server in-process from WC_WORKTREE via lib/server/server.js and reads stored state from MongoDB (:15-19, :23-26, :341-356, :427). It cannot boot multitenant api and cannot read PostgreSQL. So the lab does not run the matrix against the preview; it emits cells in the matrix's cell shape (collection, path, form, reply fields, stored fields) from its own client runs and oracles, and feeds the pair of cell sets to tools/qc/compat/wcdiff.py and classify_compat.py with the existing groups.yaml.
    • A cell that lands in no group stops the run with "unexplained", exactly as the pipeline does for a tree comparison. Differences already documented as intentional (strict invalid-credential refusal; dotted PATCH members refused with 400 on PostgreSQL; JSONB non-representable values refused) need their own group entries with verdict Decided and a decision basis before the run is called green.
    • Nothing in this comparison speaks for old releases: the pipeline's 15.0.9 → dev attribution stays separate, and no old-release-to-PostgreSQL transitivity is claimed.

    4.6 D23 entry condition 2: the NSClient v1 socket sequence against a forwarding realtime¶

    D23, adopted and amended on 2026-11-06 (execution plan §2.14), makes realtime a reader that forwards every socket write message and the alarm ack unchanged, with the socket's own authorization, to an internal write endpoint on api, which runs the write step with the socket source label and relays the result into the socket acknowledgement. Its entry condition 2 names this packet as the home for the proof, because AndroidAPS 3.4.2.3's NSClient (v1) plugin is the one corpus client whose whole upload path is the socket.

    Server under test: the explicit multitenant executable serving api and a forwarding realtime for two tenants, as in §4.1, plus the single-site Mongo baseline of §4.2 on the same head.

    Driver: a Node socket.io client replaying the plugin's message sequence as read from the pinned 3.4.2.3 source: authorize, a dbAdd for a treatment and a devicestatus, a dbUpdate by the id returned in the add's acknowledgement, the alarm ack, and a retried dbAdd after the driver withholds its own acknowledgement handling, which is what the plugin does when no ack arrives. The driver is pattern replay (R40's caveat applies: not execution of the plugin) and carries no payload from any real site.

    Check Predicted green Exact red symptom
    each forwarded write is stored once on tenant A with source label socket, and the acknowledgement carries the same id or result string the single-site baseline returns stored rows and ack bodies equal across baseline and preview, per the compat verdict vocabulary a differing ack shape, a missing source label, or a row on tenant B
    the retried dbAdd after a withheld ack stores no duplicate one row, one ack on the retry two rows for one logical add
    control: acknowledge before api confirms (patch the forwarder in a scratch copy to reply before the forward resolves, then make the forward fail) the lost-write assertion goes red: an acknowledged add with no stored row if it stays green the assertion is vacuous; restore and rerun
    control: api unavailable the socket write receives no acknowledgement and the driver's retry fires; nothing is stored until api returns a success reply during the outage

    single unchanged the baseline's socket writes go directly to storage as today; no forwarder in the path a forwarded write observed in single-site mode

    6. What the lab must not claim¶

    • M4 promotion, or any milestone. Promotion is a maintainer decision recorded in the roadmap and dashboard after the criterion list is fully met.
    • Compatibility for any client that was not executed. A green run of three Node/bash clients says nothing about Swift, Kotlin or Java binaries; their rows stay source-pattern replay with the R40/R41 wording.
    • "No coordinated app upgrade requirement" as a general statement. The lab can say it for the credential shapes it exercised (SHA-1 header, query token on v1/v2, Bearer from the exchange) and must say it is unproven for subject-creating onboarding and sockets.
    • Equality of HTTP replies as proof of equal stored outcomes, or the reverse. Both are recorded; the classification is per cell.
    • That single-site behaviour is unchanged. That is the full nonbrowser and browser campaign's job on the batch head, not this lab's.
    • Anything about the vendor drivers beyond "the fake upstream was reached". Real vendor accounts, exports, traces or identifiers never enter the lab; every record is synthetic.
    • Old-release transitivity: the compat pipeline's 15.0.9/dev classification is a separate measurement and is not re-run here.
