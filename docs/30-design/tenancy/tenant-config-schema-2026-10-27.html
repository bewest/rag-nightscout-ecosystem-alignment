    Tenant configuration schema for hosted Nightscout (T30-SCHEMA-CONFIG)¶

    Record

    Record as of 2026-10-27. A point-in-time document; it is not kept up to date.

    Contributor-facing. Draft of 2026-10-27, for the maintainer's review. Queue item T30-SCHEMA-CONFIG. It builds on D22 (execution plan §2.13), the census re-measured on dev (§3a), and the configuration-surface document (§A, §A.3, §B.3, §C, §E, §F.1). The schema runs in tools/lab/tenant-config-schema/, which holds 57 tests and 72 controls. Nothing here decides a question those documents leave open: such questions are listed in §11.

    Marks: [M] means measured by the lab, in the run recorded in its results.json (PostgreSQL 16.15). [R] means read or reasoned, not measured. Test ids (ISO-…, FLOOR-…) name the lab's tests.

    1. What this is¶

    Under TENANCY_MODE=multi, a tenant's configuration decides what a person's site shows, who may read it, what it connects to and, once multi-mode alarms pass the gate in §7a, when an alarm fires. D22 gives that configuration three layers:

    1. project floors, which are fixed in code;
    2. the operator's policy, written on the operator plane;
    3. the owner's values, written on the tenant-owner listener.

    D22 also says that integrations are typed records, that credentials live in a separate secrets component, and that every change is versioned and can be rolled back.

    This document gives those decisions a PostgreSQL schema. It has three design goals:

    • a wrong value fails loudly at the moment it is written, and is never stored and then silently rewritten;
    • a forgotten tenant filter returns nothing (D3);
    • no table holds secret material.

    2. The tables, and why each exists¶

    Two tables already exist on the seam branch (81a1f6ce:lib/admin/platform.sql), and this schema leaves both unchanged:

    • tenants has no RLS, because it is read before a tenant context exists.
    • tenant_members has RLS.

    The lab's migration 0001 is that file byte for byte. [M]

    table tenant-scoped written by why it exists
    config_setting no migrations only The catalogue of setting names hosted configuration may carry. It records each setting's type, whether the owner may set it, whether it is an alarm setting, whether it needs a deletion confirmation, and its project floor. A name missing from here cannot appear in any policy or owner row, because foreign keys forbid it. That absence is how the "not offered" floors reach the database.
    integration_kind no migrations only The driver catalogue. For each kind: the schema its settings must satisfy, the hosts a driver may call, and the names of the credential parts the owner and the operator each supply.
    deployment_policy no operator D22's one deployment policy: per setting, a default, a mode (open, bounded or pinned), a constraint and a pin.
    tenant_policy_override yes operator, with the tenant bound D22's operator overrides for individual tenants. A row replaces the deployment row for that tenant and setting.
    tenant_setting_value yes tenant-owner listener The owner's values, accepted only within the governing policy row and the floor.
    tenant_alarm_thresholds yes nobody yet (see §5) The owner's four glucose thresholds, as typed NOT NULL integer columns in mg/dL. It exists so the §A.3 hazard cannot be expressed. See §6.
    tenant_config_version yes tenant-owner listener (insert only) One numbered, append-only row per change. It records the plane, the identity provider's subject, the time, the kind (change, rollback, bootstrap, import) and the full owner-scope state after the change.
    deployment_integration no operator The operator's part of a kind's credential (for example a push service's application token), held as a reference.
    tenant_integration yes tenant-owner listener One record per connector, webhook or push target. Each has a kind, settings validated by the kind's schema, a reference to the owner's credential, and an enabled flag.
    tenant_integration_status yes consumer and connector roles The last success and last error. They are kept apart so that a connector's polling never creates a configuration version.

    Three functions carry the write path. All are SECURITY INVOKER, so RLS and table grants apply to everything they do:

    • cfg_apply(tenant, changes, plane, subject, …) is the single write path for owner-scope state.
    • cfg_rollback(tenant, version, …) restores an earlier version.
    • cfg_policy_for(tenant, key) returns the governing policy row: the override, else the deployment row, else the catalogue default.

    2.1 Roles¶

    The lab's roles are cfg_owner, ns_operator, ns_tenant_admin and ns_api.

    • cfg_owner runs the migrations and owns every table. It is NOSUPERUSER NOBYPASSRLS.
    • The other three own nothing. They map to D7's operator plane, D16's tenant-owner listener, and D5/D21's consumer, evaluator and connector roles.

    The grants are in 0007_grants.up.sql.

    Measured, and in tension with a claim in the seam's code (§10, M7): the tables are owned by a role that is not the application role. RLS is still active for every application role, with row_security_active() true on all seven tenant tables (ISO-roles, ISO-<table>). [M]

    3. The merge rule, and where it runs¶

    Rule (D22). For each setting, the effective value is:

    1. the code default;
    2. replaced by the operator default, if the governing row has one;
    3. replaced by the owner value, if:
    4. the catalogue marks the setting owner-settable,
    5. the value is well typed,
    6. it satisfies the floor,
    7. the mode is not pinned,
    8. and, where the mode is bounded, the constraint accepts it;
    9. replaced by the operator pin, if the mode is pinned.

    An owner value that fails step 3 is not used, and it is reported in ignoredOwnerValues with the reason (MERGE-override-narrows, MERGE-pin-beats-owner). [M]

    A floor is checked once more on the effective value. For example, with no operator row, WRITE_VALIDATION falls back to the code default off, which breaks the floor. The merge reports this so that the process refuses to serve (MERGE-floor-on-effective). [M]

    The thresholds are merged as a set:

    • the owner's row if one exists;
    • otherwise the effective BG_* values, key by key.

    A set that is out of order is reported. It is never nudged, unlike dev's verifyThresholds (lib/settings.js:311-334 on db3b9e4e, BF-67) (MERGE-thresholds-refused-not-rewritten). [M]

    Where it runs. The merge runs in application code (lib/merge.js in the lab). The write-time checks run in the database, as triggers. There are four reasons. [R]

    1. The code defaults live in the code (lib/settings.js, lib/server/env.js). A merge in SQL would need them passed in, or copied into the database, and a second copy can drift.
    2. The process environment is visible only to code. D22 says floors are "enforced in code under multi", and several of them are process-level (§4).
    3. D22's "saving invalidates the tenant's cached settings" implies that the merged result is cached in the process. The merge is computed on a cache miss, and the result is what the evaluator and the API use.
    4. An operator or owner can write rows through a path other than the intended code. A wrong row must not be storable at all, so acceptance (type, floor, mode, constraint) is checked by triggers on every write.

    Two spellings of one rule can drift. The lab therefore runs a differential test: 30 cases go through the JavaScript acceptance rule and the SQL one, and the test requires agreement. Its control plants an off-by-one in the JavaScript ordinal minimum, and the test goes red (MERGE-differential). [M] A release should generate both rules from one source, or keep this differential in CI. [R]

    The rule behind the split [R]:

    • A floor goes in the database when it is a property of a row, so that no tool, script or future endpoint can store a row that breaks it. Each such check is in a trigger or CHECK that the application roles cannot alter: FLOOR-catalogue-readonly shows the catalogue is read-only to all three. [M]
    • A floor goes in the application when its input is something the database cannot see:
    • the process environment;
    • a DNS answer at send time;
    • whether the person was actually shown an export offer;
    • the merged value when no row exists.

    6. Alarm thresholds and the §A.3 hazard¶

    §A.2 drafted the thresholds as keys inside a JSON settings object, guarded by one CHECK. §A.3 predicted, from PostgreSQL's documentation, that a partial mmol override would pass that CHECK on SQL NULL. The lab applied §A.2's tenant_settings verbatim (old-shape/) and measured it (MMOL-old-shape-profile). [M]

    input §A.2 draft this schema
    partial {"bgHigh": 14} accepted refused: all four are written together (and the columns are NOT NULL)
    complete mmol {3.1, 4.5, 10, 14} refused (23514) refused: not a whole mg/dL value; convert mmol/L at the write boundary
    integer mmol-looking {3, 5, 10, 14} refused refused: tenant_alarm_thresholds_plausible_mgdl
    misordered {80, 55, 180, 260} refused refused: tenant_alarm_thresholds_ordered. It is not rewritten (contrast BF-67).
    string {"x", 80, 180, 260} refused, 23514 (the read-derived cast error did not reproduce on this input) refused: must be a number
    valid {56, 81, 180, 252} accepted accepted, stored exactly

    The draft's CHECK works when all four keys are present. It fails only on the NULL path. In this schema the NULL path does not exist, because each threshold is its own NOT NULL column. MMOL-stored-safely is green on the new shape. It goes red on the old shape, and red again when the new shape's range CHECK is dropped and the columns are made nullable. [M]

    The write boundary is the application's. It converts mmol/L with dev's factor 18.01559 (lib/constants.json:10), stores mg/dL, keeps entered_units, and echoes the stored numbers back (§A.3 defence 2). The lab's thresholdsForStorage turns 3.1/4.5/10/14 mmol/L into 56/81/180/252. Its control skips the conversion, and the database then refuses the write (MMOL-converted-and-echoed). [M]

    Refusing partial input follows J11's recommendation, and J11 is still open. A nullable-per-column variant would also refuse a lone mmol bgHigh on range. Its ordering could then only be checked after the merge, in code. [R]

    7. Versions and rollback¶

    Recording. cfg_apply takes a per-tenant transaction advisory lock, applies the changes, and appends version N+1 with the state after the change.

    • Two owner sessions saving at once get consecutive versions. Without the lock, the second fails with a duplicate version (VERSION-concurrent-writers). [M]
    • A deferred constraint trigger requires, at commit, that the tenant's live owner-scope state equals its newest version's state. A direct UPDATE, INSERT or DELETE that skips cfg_apply cannot commit (VERSION-unversioned-write-refused). [M]
    • Limit: this guard compares the live state with the version through the same cfg_current_state function. If that function were wrong, the guard would not notice; the test did (VERSION-numbered, control). [M]
    • Versions are append-only:
    • the owner listener has no UPDATE or DELETE grant;
    • a trigger refuses both, even to the owning migration role (VERSION-append-only);
    • the one exception is the cascade from deleting the tenant. [M]

    Rollback. cfg_rollback(tenant, N) computes the changes that make the live state equal version N. It applies them through cfg_apply as a new version, with kind rollback and rollback_of N. Values, thresholds and integrations are all restored (VERSION-rollback-restores). [M]

    Rollback against a policy that has changed since version N. Every restored row passes the same checks as a fresh write, against the current policy and floors.

    • In the lab, if the operator has since pinned or narrowed a setting that the rollback would restore, the whole rollback is refused. The error names the setting, nothing changes, and no version is written (VERSION-rollback-vs-new-pin). [M]
    • A rollback to a version with permanent deletion turned on needs a fresh confirmation. The old confirmation is not part of the version state and is not carried forward (VERSION-rollback-needs-fresh-confirmation). [M]

    Refusing the whole rollback was chosen by the lab, not by any decision. The alternatives are in §11 (Q3).

    What is versioned. Owner-scope state is versioned: owner values, thresholds and integration records. Integration status is not. Operator policy changes are not versioned here, so whether they need history is open (Q5). Saving a new version should invalidate the tenant's cached merge; how the hosted processes learn of that (D6's feed, or a version-number check) is not built here. [R]

    8. Integrations and secret references¶

    tenant_integration has these guarantees:

    • Settings are validated against the kind's schema: required fields, no unknown fields, enums, types, lengths and host rules (INTEGRATION-settings-schema). [M]
    • The operator controls which kinds are enabled and how many each tenant may have (INTEGRATION-kind-limits). [M]
    • A kind's owner credential parts require a reference. A kind with an operator part is refused until the operator has configured that part (INTEGRATION-credential-parts). [M]

    No plaintext secret column anywhere (SECRETS-schema-scan). [M] The test scans information_schema and requires:

    • no column named like a credential, except *_ref and *_parts;
    • no bytea column;
    • that every *_ref column is guarded by the reference-format CHECK.

    Three controls each add an offending column, and the test goes red each time. Two more checks close the gaps around the scan:

    • Settings cannot smuggle a credential. An unknown field such as password is refused, and no kind's schema may declare a credential-like field (SECRETS-not-in-settings). [M]
    • A pasted plaintext value in a reference column is refused by the format check (SECRETS-reference-format). [M]

    The reference format sref:v1:<backend>:<opaque id> is a lab placeholder. The format CHECK catches accidents only: a plaintext value shaped like a reference would pass it. Whether a reference belongs to the tenant can only be checked by the secrets component, which holds the keys (D22: keys never leave it). [R]

    9. RLS on every tenant-scoped table¶

    Every tenant-scoped table has RLS enabled and forced, with the seam's predicate copied character for character: tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid, in both USING and WITH CHECK.

    ISO-complete discovers tables by their tenant_id column, as the seam's tenantScopedTables does, and requires all three properties. Its control adds an unprotected table, and the test goes red. [M]

    For each of the seven tables, the role bound to tenant A:

    • reads only A's rows;
    • reads nothing when unbound;
    • updates none of B's rows;
    • is refused (42501) when inserting a row for B.
    table reader in the test cross-tenant insert attempted by
    tenant_members ns_api ns_tenant_admin
    tenant_policy_override ns_api ns_operator
    tenant_setting_value ns_api ns_tenant_admin
    tenant_alarm_thresholds ns_api ns_tenant_admin (with the post-gate grant)
    tenant_config_version ns_api ns_tenant_admin
    tenant_integration ns_api ns_tenant_admin
    tenant_integration_status ns_api ns_api

    Each table has two controls, RLS disabled and the same reads done as the container superuser. All 14 go red. [M]

    The operator writes per-tenant overrides with the tenant bound, which is J12's option 1 shape applied to a new table. J12 is still open. [R]

    10. single mode¶

    Nothing changes. single reads the process environment, as today (D15, D1). It does not create or read these tables, does not run these migrations, and does not apply the floors above. The floors are multi-only (D22). The environment names keep their meaning, including CONNECT_*, BRIDGE_*, WEBHOOK_* and PUSHOVER_* as aliases (D22). The lab's settingsReadByIdPermission keeps dev's behaviour for single, and FLOOR-app-settings-private checks it. [M]

    10a. Comparison with Nocturne¶

    Nocturne at 42275c812 was read for comparison. [R]

    • Generic settings are rows keyed by tenant and key, with a value (SettingsEntity).
    • Thresholds are alert rules with JSON parameters (AlertRuleEntity.condition_params).
    • TenantAlertSettingsEntity holds a do-not-disturb schedule, not thresholds.
    • Connector configuration keeps its secret properties encrypted in a secrets JSON column on the same row (ConnectorConfigurationEntity.SecretsJson, AES-256-GCM per its comment).
    • Migrations are EF Core migrations, run at start under a dedicated migrator role, separate from the application role (DatabaseInitializationExtensions.cs:80-113).

    The two designs agree in several places:

    • a generic key/value layer;
    • typed side-tables where constraints matter;
    • a migrator role separate from the application role.

    They differ in one place. D22 moves secret material into a separate component, so this schema holds references only, where Nocturne keeps ciphertext beside the configuration it belongs to. That difference follows from D22's keys-stay decision. It is not a judgement on Nocturne's choice. [R]

    10b. Mismatches found (stop-and-report)¶

    These are inconsistencies between decisions, documents and code. None was resolved by this work.

    • M1. The execution plan's §2.13 lists five floor groups, the fifth added on 2026-10-27, but introduces them as "Decided as four groups". The decision row D22 does not count them. [R]
    • M2. D17 as amended makes the identity provider interchangeable and tenant_members.subject_id the provider's subject, with no foreign key. Two places do not fit that:
    • On the seam (81a1f6ce), the column is uuid NOT NULL. A provider whose subjects are not UUIDs cannot be stored.
    • On seam/t30-schema-cred (65ce54b9), the column became text with a composite foreign key to tenant_subject, against "no foreign key".

    This schema leaves tenant_members unchanged and records actors as text with no foreign key (tenant_config_version.actor_subject). [R] - M3. tenant_secret stores material bytea in the platform schema. It is drafted in config-surface §A.2 and §C.5 (J4) and built on 65ce54b9. D22's later decisions say keys never leave the secrets component. They do not say where the built-in signer keeps its encrypted keys. This schema holds references only, and SECRETS-schema-scan forbids bytea in it. If the built-in signer's store is to live in the same schema, that check needs a defined scope. [R] - M4. Census §3a row 5 says TRUST_PROXY is "never a tenant row", and row 12 gives DEBUG_LOGGING no policy. The call-path lab's lib/policy.js models both as per-tenant pinned policy rows. That lab is evidence for the call path, not for the setting model, but the two disagree. [R] - M5. Config-surface §B.3 says class D settings are read from process.env under multi, "as today". D22 and census §3a describe release-driven D names as "deployment values the operator pins", which is a policy row. D15 says env-sourced configuration must not reach the multi path. Where D values live under multi is therefore not stated consistently. This schema supports pinned deployment rows (scope = 'deployment'), and the process-level floors read the environment. [R] - M6. Config-surface §A.3 cites settings.js:290-296 and a bgHigh < 50 heuristic. Dev at db3b9e4e converts each threshold on its own when it is below 30 (lib/settings.js:292-305). The silent rewriter BF-67 is still present (lib/settings.js:311-334). The citations are stale, and the hazard remains. [R] - M7. The seam's comments say the connecting role must own the tables, or "a setup step run as a superuser would leave the policy quietly unenforced" (81a1f6ce:lib/storage/postgres-storage.js:290-293, lib/storage/ack-store.js:199-203). Measured here: with the tables owned by a separate non-superuser migration role, RLS is active for every non-owner application role (ISO-roles). FORCE matters only for the owner. [M] The danger the comment names is real only if the application itself connects as a superuser. This bears on who runs migrations (plan §4). - M8. The queue item's note says Nocturne's TenantAlertSettingsEntity is a typed side-table "where constraints matter". At 42275c812 it holds a do-not-disturb schedule; Nocturne's thresholds are JSON parameters on alert rules (§10a). [R]

    11. Open questions for the maintainer¶

    # question lab's working choice
    Q1 Does an operator override replace the deployment row whole, or field by field? whole row
