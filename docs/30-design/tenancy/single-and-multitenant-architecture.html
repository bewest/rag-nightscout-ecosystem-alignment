    Single and multitenant Nightscout: architecture and compatibility¶

    Living document, last changed 2026-11-10 at 0fb666fca.

    Contributor-facing living explanation, groomed 2026-11-08; header 2026-11-10. The restore/Compose reference this page explains is cgm-remote-monitor ed2ced00c80bd0a6a7d75f834d2c6e2af8c71364, recorded in the publication measurement.     What the proofs can inform¶

    The useful result is an executable one-host multitenant reference with separate services and tenant-local restore. It gives current architecture decisions a measured basis. Production qualification and additional deployment models still need their own evidence; an accepted component is not a completed platform track.

    Capability Recorded basis Useful for decisions now Remaining admission

    Tenant-local restore and shared-role restart c23 native acceptance, plus ed2 packaged ordinary restore above A can stay suspended while B progresses; forward correction/deletion history allows tested clients to converge without a global pause.     Nonresident single-site execution or another backend Independently attributed R43 and later profile records in the platform plan Inform seam and acquisition research within their measured caller policies.     A prototype answers a bounded feasibility or semantics question. An integrated functional reference proves cooperating components on a named topology. A production server additionally needs its actual trust and identity setup, credential/lifecycle recovery, selected workload limits and operator procedures accepted together. Merge, release and default enablement are separate decisions. The deployment/fault-domain guide compares the independent tenancy, backend, computation, process and host axes.

    Component paths describe the reference source, with executed acceptance bounded by its named record above. Realtime's raw record frames and evaluator-derived values are distinct products; see the characterization. Existing client protocols do not change when these roles move into containers. The default single-tenant process retains its existing composition.

    During tenant A restoration, each participating process must stop admitting A's new work, finish admitted work, and acknowledge clearing A's retained state before reactivation. Tenant B has its own operation window. The implemented fixed cohort registers actual separate processes through configured private participant endpoints. A PostgreSQL advisory lock protects participating code. A database-enforced fence would reject bypassing operations in PostgreSQL itself. Process separation and that stronger fence are separate questions; neither a process list nor a configuration assertion proves exclusive credential custody. The native matrix exercises the actual separate processes and uncertainty/restart cases under its declared fixed trusted-cohort boundary. Arbitrary direct SQL actors remain outside that proof and are unsupported under the exclusive application ownership contract. The database ownership map distinguishes cross-component commands from admitted reads and owned persistence. The tenant-local startup requirement prevents a suspended tenant from blocking another tenant's shared-role restart. The c23 native acceptance reproduces fresh API/realtime/evaluator startup and B operation while A remains suspended in the tested failure scenarios. It does not clear claims or provide automatic uncertain-outcome recovery.

    See deployment/rig scenarios, evaluator/realtime communication and SQL/migration architecture for runnable preparation, sequence diagrams and storage/recovery boundaries. Documentation checks do not establish an executed deployment or capacity/recovery guarantee.

    What the write seam made possible¶

    Shared single-tenant code did change. The storage/write seams let the multitenant preview reuse shipping domain rules and version-specific handlers while injecting a different store and tenant context. They did not make every service tenant-safe automatically, or freeze the code used by single.

    The compatibility objective is to preserve the existing default MongoDB behavior when no trusted replacement is injected. That objective is supported by tests; it is different from claiming no shared source changed or every possible request behaves identically.

    There are two related seams: reads/counts use a storage interface, and mutations use shared write-intent rules and a write boundary. Tenant resolution, credentials, current grants, settings, caches, derived views and service lifecycle also require explicit boundaries. The clinical-record write seam is not a universal wrapper around operator policy, secrets or every side effect.

    Tenant identity must also bind reads, settings, history/lastModified clocks, secrets, cache frames and returned derived values. PostgreSQL/RLS is defense in depth alongside request-bound application context; it does not replace request authorization. Static host maps and loopback lab trust do not establish durable provisioning or production transport/service identity.

    Current grants are checked again on the next protected operation, rather than frozen into an exchanged token. This does not promise cancellation of work already authorized. The shipping read-then-write precondition behavior is retained; the preview does not claim a new atomic compare-and-swap guarantee.

    Properties/ddata retain shipping entries-and-treatments permission semantics, including secondary profile/device/activity/food snapshot arrays. Summary retains its wildcard read requirement. Those are inherited compatibility boundaries, not new declarations that every exposed field has an independent collection grant.

    Hypothetical third-backend smell test¶

    Read-derived at ded254b9, 2026-11-05, and the resolver anchor re-read at 83582e87 on 2026-11-06 (collection at line 34, resolve at 41, intent at 54); no SQLite adapter, isolation or performance experiment was run. A third backend has a clearer insertion point than the Mongo-only base: trusted ctx.storagePorts.resolve supplies storage and an intent factory (lib/server/storage-reads.js:34–56), and the PG adapters call the shared write-intent.forCollectionResolved rules. Existing shipping routers, validation and client quirks therefore need not be copied into another API. This improves reuse; it does not establish a backend-neutral runtime.

    There are concrete consolidation candidates:

    Source at the pinned CRM head Smell / bounded improvement
    lib/storage/postgres-entries-intent.js:16,30,84 and postgres-collection-intent.js:24,47,142 Related filter/projection helpers and transaction/event wrappers are repeated. Generalize only their measured common contract; entries-specific and legacy query/natural-order differences are intentional until disproved by tests.
    lib/server/tenant-app/entries.js:20, treatments.js:18, profile-food-errors.js:13 Repeated PG error classification and representation-refusal translation can drift. A shared adapter helper is plausible, guarded by existing HTTP error tests.
    lib/server/tenant-app/domain-catalogue.js:7–13 Domain factories are coupled to PG candidate migrations. A hypothetical additional backend needs trusted backend-specific factory/schema/readiness selection behind the same domain capabilities.
    PG intent adapters' fromMongo/toMongo dialect bridge and api3/storage/mongoCollection/utils import The boundary still carries Mongo-shaped legacy semantics and Mongo-named normalization helpers. Separate API/document semantics from backend query lowering before treating this as a neutral database plugin interface. Renaming alone proves nothing.
    lib/storage/postgres-connection.js:26–50 and tenant authority/secrets persistence PostgreSQL RLS, roles, tenant-bound transactions and control-plane persistence are a separate protection contract. A cell/file/container isolation primitive would need equivalent tested ownership, lifecycle, failure and authority boundaries; substituting the data adapter alone is insufficient.

    For a hypothetical celld/SQLite design, keep the domain/write semantics above the backend; implement query/identity/document representation, atomic writes and commit hooks below it. Reuse the Mongo/PG differential corpus for a third adapter, including refusal cases. Isolation placement, concurrent writers, crash recovery, migration/backup and durable event delivery each need a new measured contract. This is easier at the handler/write-rule layer, still substantial at the storage and runtime layers. No claim of SQLite equivalence, operational advantage or celld adoption follows. The current REST/compatibility wave comes first; measured duplication can be consolidated without introducing a third backend.
