    Multitenant decisions in force¶

    Living document, last changed 2026-11-24 at 7b8bfd465.

    The original November 18 review indexed the anchored rows at a0a8c3956d. Subsequent programme decisions and amendments extend that index. This is a read-derived guide. Each linked decision row owns its policy and evidence. The execution log identifies the candidate and what has been measured.

    In force¶

    Rows marked deferred or proposed record a direction that is not yet adopted behavior.

    Data model, storage and isolation¶

    • d1 — Multitenant service is the design target; self-hosted single-tenant stays first-class permanently.
    • d2 — Shared logical storage with a tenant discriminator, not a database per tenant.
    • d3 — PostgreSQL with RLS; serving connections never own tables or bypass RLS; binding is transaction-local.
    • d4 — MongoDB stays permanent for single-tenant sites; adapter changes preserve single-tenant behavior.
    • d8 — API v3's closed operator set is the query contract; mingo is a differential oracle.
    • d11 — Devicestatus: generated columns for indexed fields only; body kept as JSONB.
    • d18 — Well-known and controller-owned typed declarations; the hub records and observes, never derives dosing state.
    • d19 — Content-addressed definitions separate from leased instances; one device source of record per channel role.
    • d20 — identifier is client sync identity; _id is the hub key; quirks are version-scoped.
    • exclusive-application-postgres-ownership — Nightscout owns its PostgreSQL namespaces; other direct database writers are unsupported.
    • view-reads-total-order — Sort-key ties break on the per-tenant insertion ordinal, in SQL and in process.
    • write-clock-history-arms — The write clock serves only v3 history no-missed-write (arms settled by multitenant-requires-write-clock).
    • multitenant-requires-write-clock — Arm (a) per-tenant clock row is kept; multitenant requires writeClock; floor checks move to admin (narrowed by platform-verification-removal: floors are operation postconditions).

    Roles, listeners and horizontal shape¶

    • statefulset-ordinal-scaling — Evaluator and realtime are StatefulSets, ordinal from the hostname, K = replicas (one env value), one headless Service; api is a Deployment; cohort and participant manifest deleted. Evaluator K is bound at seed only under pgstream; writer-driven fixtures are K-free, one seed serves any K (amended 2026-11-20).
    • d5 — One core; stateless api, change-driven evaluator, fan-out realtime, connector vcpool; single keeps its server.
    • d16 — Separate data, owner and operator sockets, multiplexed by tenant, not duplicated per tenant.
    • d21 — One executable: single, multitenant <role>[,<role>…] and operator tools.
    • d23 — Realtime is a reader; every socket write and alarm ack is forwarded to api.
    • d7 — Operator plane is credential-free and secured by unreachability (narrowed by admin-plane-same-address-different-port).
    • admin-plane-same-address-different-port — Admin listener may share the API address on another port; never all interfaces.
    • internal-service-contracts — Internal APIs: separate service contracts per listener; no new bearer authentication (narrowed by internal-listener-ory-pattern).
    • internal-listener-ory-pattern — One private serve.internal listener per role, Ory-style (narrowed by k1-per-role-deployments).
    • internal-listener-graceful-shutdown — On SIGTERM the internal listener drains in-flight calls up to a deadline.
    • static-hash-ownership — Evaluator and realtime processes own slice(hash(tenant), K); proxy routes match; changing K is a restart.
    • legacy-topology-retirement — Legacy pools and leases retire. Writer-driven transport replaces the native stream input.
    • pool-primitive-shared — One pool-membership primitive, kinds kept separate (narrowed by legacy-topology-retirement: kept for connectors).
    • census-operational-list — Operational catalogues are listed explicitly and excluded from per-tenant restore, export and deletion.
    • pool-member-hygiene — Pool members reclaim stale sockets and wait-and-alert instead of exiting.
    • cohort-pod-not-scaled — Never scale the all-roles monolith horizontally (narrowed by k1-per-role-deployments).
    • vcpool-egress-capacity — Connector pools are sized against upstream quotas; core reports upstream refusals per member.
    • evaluator-scale-direction — Profile first, then K evaluator processes; no coalescing window (narrowed by static-hash-ownership: not urgent).

    Platform/application boundary, startup and simplification¶

    • platform-verification-removal — No configuration-digest certificate and no per-tenant verified floor; migration Job plus schema check; a range of single-concern health endpoints.
    • config-few-dozen-env — A few dozen environment settings (about 74 is fine) plus minimal PostgreSQL bookkeeping; per-role JSON documents retire.
    • predictable-fixes-then-test — Predictable simplifications run affected tests only, no per-item break-it control; qualify the joined candidate once.
    • provisioning-secrets-in — Secrets flow into Jobs and roles, never out of a Pod; one apply converges.
    • prometheus-metrics-narrow — official Prometheus Node client (@prometheus-io/client), /metrics on an internal port, opt-in, multitenant roles only (not the classic server); no tenant-id labels; one Prometheus Pod plus postgres_exporter per lab run, TSDB snapshot retained; per-input events still decide verdicts; no OTel tracing now. Supersedes metrics-endpoint-deferred.
    • storage-events-single-tenant-parity — /storage socket events fire for exactly the write paths a single site uses.
    • writer-driven-transport-direction — Adopted 2026-11-21: the api is the only writer; post-commit hints to the owning evaluator and realtime; level-triggered recompute plus sweep; pgstream, its slot and the storage-event journal retire.
    • stateful-evaluator-resident-window — Adopted 2026-11-21: each evaluator slice keeps its tenants' windows resident and updates them from the pending mark; memory is planned per resident; output byte-identical to the full rebuild.
    • evaluator-k-planned-restart — K changes by planned restart with headroom; no logical-shard map, live K change or hash change.
    • prerelease-schema-in-place — No operator databases yet: multitenant schema and migrations change in place; two-step migrations start at the first operator release.
    • platform-application-boundary — Application assumes a verified platform and fails closed; it never re-verifies the platform while serving.
    • brittle-check-removal — Checks that refuse for anything other than a product property are removed; run identity is image digest plus run configuration.
    • unclear-rows-resolved — The six Unclear questions resolved toward removal (desired count, writer census, revision wake, cost step A, idle witness, move readiness).
    • architecture-justified-removal — Machinery from an obsolete design is removed on architecture grounds with correctness controls, no measurement.
    • serial-machinery-retirement — Remove serial machinery the streaming design no longer needs, rather than tune it.
    • operable-architecture-first — Simplified, runnable, operable architecture first; performance work is lower priority meanwhile.
    • boot-independent-of-tenants — Serving boot is independent of tenant count; expensive platform verification runs on admin (narrowed by platform-verification-removal: no verification record or proof).
    • catalogue-verification-admin-owned — Admin verifies the catalogue once per deployment; serving keeps one cheap fail-closed check (narrowed by platform-verification-removal: migration Job plus schema-version check).
    • stable-evaluator-runtime — Evaluator runs on a stable schema; relevant DDL after startup stops it with a typed code.
    • migration-rehearsal-separate — Migrations are rehearsed as scheduled maintenance, separate from performance and acceptance runs.
    • multitenant-upgrade-shape — Platform rolls processes; core supplies two-step migrations and checks (narrowed by stable-evaluator-runtime).
    • tenant-local-startup-admission — A suspended tenant never prevents other tenants becoming ready after a restart.
    • tenant-defect-tenant-scoped — A defect in one tenant's state refuses that tenant only; deployment defects refuse startup.
    • readiness-serve-then-warm — A role is ready when its own dependencies are up; tenants warm in the background (narrowed for the api by api-tenant-cache-bounded-lru).
    • api-tenant-cache-bounded-lru — The api's per-tenant state is a bounded LRU optimization; a miss builds inline; restart cost is independent of tenant count.
    • datastore-loss-recover-in-place — On PostgreSQL loss a role reports unhealthy, reconnects and rebuilds; exits only past a bound.
    • datastore-loss-before-window-retirement — Move datastore-loss recovery to a connection probe before retiring the operation window.
    • lane-failure-recover-in-place — A failed session lane is replaced in place, never hiding an uncertain completion.
    • compose-restart-on-failure — Compose production default is restart: on-failure; tests may disable restart.
    • pg-connection-budget — Deploy sizes max_connections from the declared per-role connection budget.
    • pg-connection-pooler-allowed — PgBouncer and/or a larger max_connections meet the budget as K grows; check session state before transaction pooling.

    Deployment repository and Kubernetes¶

    • d12 — Alignment holds tooling and evidence; shipping code and tests live in cgm-remote-monitor.
    • platform-home-nightscout-deploy — Platform concerns without a core home move to nightscout-deploy.
    • deploy-tree-home-now — nightscout-deploy holds the Compose tree now (narrowed by deployment-plan-contract).
    • deployment-plan-contract — One deployment plan in deploy, checked against a contract core publishes.
    • core-static-plan-retired — Core's static Compose plan retires; core tests use a small registry-mode fixture plan.
    • deploy-repo-readme — The deploy README addresses operators: what runs, how to run it, the pinned core commit.
    • k1-per-role-deployments — Kubernetes: one Deployment per role, Recreate, per-role Services; migrations as Jobs before serving (narrowed by statefulset-ordinal-scaling: evaluator and realtime are StatefulSets).
    • kubernetes-idiomatic-operations — Use Kubernetes ordering, digests, quotas, probes and in-cluster Jobs instead of re-proving guarantees.
    • k8s-platform-proofs-to-deploy — Kubernetes runs stop selecting opt-in platform proofs; one fit check and image publication move to deploy.
    • tanka-binding-parallel — The Kubernetes binding is a Tanka-style Jsonnet environment in nightscout-deploy.

    Tenant registry, resolution, ingress and provisioning¶

    • d10 — Slug is a unique host label; trusted resolution maps host to label to stable tenant id.
    • d15 — single reads the environment; multitenant per-tenant values come from storage under policy.
    • tenant-registry — Tenants and aliases live in a PostgreSQL registry (narrowed by event-driven-reset: refresh signal).
    • provisioning-split — Provisioning is an admin operation every caller uses; no caller writes provisioning rows directly.
    • operator-rest-api — Operator operations are a versioned REST API on admin; reachability, not core, controls callers.
    • static-mode-lab-flag — A role refuses a tenants list unless MULTITENANT_STATIC_TENANTS=lab; static mode then retires.
    • tenant-live-add — Running evaluator and realtime pick up newly provisioned tenants without restart (separate lane).
    • registry-connector-definitions — Connector definitions are durable tenant configuration; endpoint and credential values stay in tenant secrets.
    • operator-repair-scope — Use provision for creation, inspect for diagnosis and known-good backups for exceptional recovery. Factory reset preserves clinical data and credentials.
    • deployment-signing-secret — Vault keeps only the per-tenant data key; tenant signing keys derive in process from one deployment secret (file via Vault Agent or Secret); no signing key in PostgreSQL; issuance never calls Vault; one Kubernetes Secret delivers the signing secret; the api ns-access+jwt data verifier, verifyLegacyCredential and the api access namespace retire (2026-11-20).
    • one-call-usable-provisioning — One bulk admin call returns usable tenants (owner, subject, credential in the provisioning transaction); the harness prefers an exact key and verifies a bootstrap migration receipt when restoring a compatible writer-driven Kubernetes fixture from an ancestor (amended 2026-11-21).
    • deployment-ingress-peer-list-trust — One explicit peer list serves tenant selection and TRUST_PROXY; empty refuses startup.
    • edge-forwarded-headers-left — The edge keeps forwarding its headers; core's selector refusal is the control.
    • failed-login-delay-core — Failed authentication delays the next request as on a single site, keyed on the real client address.
    • deployment-admission-probes-and-trust-record — Production admission needs a written trust record plus spoof, conflict and outage probes.

    Identity, credentials and secrets¶

    • d13 — No deployment-wide secret on any multitenant interface; each tenant keeps its own root credential.
    • d14 — Per-tenant signing authority; resolve the tenant before examining a credential.
    • d17 — Devices keep native tenant credentials; humans use shared optional OIDC (narrowed by deployment-identity-generic-adapter-authentik-reference).
    • d22 — Effective settings layer code, operator, owner and pins under project floors; secrets are a separate component.
    • shared-oidc-provider-renewal — One optional OIDC integration for both modes, provider-backed renewal first, ENABLE=oidc.
    • oidc-provider-outage-existing-access — During provider outage, existing access lasts until expiry; no new login or renewal.
    • human-session-outage-and-logout — Pointer anchor; the policy lives in the provider-outage row above.
    • human-session-idle-scope-management-only — Idle and absolute lifetimes apply to management sessions only; data viewing is unchanged.
    • human-session-logout-local-first — Logout invalidates the Nightscout session first, then the browser credential, then the provider.
    • human-session-renewal-fenced — Concurrent renewal is fenced and idempotent per session; never resurrects revoked state.
    • human-session-transport-cookie-default — HttpOnly cookie is the default browser transport under OIDC; direct-token mode remains.
    • deployment-identity-generic-adapter-authentik-reference — Generic OIDC adapter; Authentik intended reference if it passes the proof; Kratos fallback.
    • oidc-browser-discovery-opt-in — The browser looks for a human session only on pages marked OIDC-enabled.
    • single-site-oidc-identity-list — Single-site OIDC: an operator list maps identities to existing roles, with a fallback role.
    • single-site-oidc-list-authoritative — The single-site identity list is re-applied at each start and removes delisted people.
    • registry-oidc-origins — In registry mode OIDC derives each tenant's origin from its resolved alias.
    • deployment-secrets-ladder-vault-all-stages — Vault Transit at every stage (narrowed by vault-agent-sidecar: no login adapter in core).
    • vault-agent-sidecar — Vault Agent sidecar handles auth and renewal; the app reads the token file at call time.
    • vault-one-approle-per-deployment — One AppRole per deployment; tenant separation comes from application authority and RLS.
    • vault-approle-lockout-off — Vault user lockout is disabled for the deployment's single AppRole login.
    • vault-readiness-honest — Vault is Ready only when it can serve; a sealed restart stops the run; unseal automation is staged toward production.
    • integration-credential-parts — Integration credentials split into operator-owned and owner-owned parts; neither reads the other's.
    • tenant-root-secret-owner-control — Owners can reveal (after re-authentication), audit, rotate and set the tenant root secret.
    • authorize-cost-first — Cut per-authorization cost before API scale-out (narrowed by authority-recheck-deferred).
    • legacy-decision-reuse-60s — Optional legacy-credential decision reuse, 60 s default, off by default (narrowed by authority-recheck-deferred).
    • authority-recheck-deferred — Deferred: no authority cache or epoch machinery this round; revocation stays immediate.

    Owner, root and subject authority¶

    • authority-split-diagram — Figure: root, owner and operator authorities as decided 2026-11-10.
    • tenant-root-single-site-parity — Tenant API_SECRET has single-site authority; never owner or operator authority.
    • root-may-edit-owner-subjects — Root may edit or delete any subject; removing the last usable owner is refused.
    • root-role-edit-delete — Root may edit role permissions; renaming, or deleting a held role, is refused.
    • root-grant-ceiling-default-all — Root may grant any tenant data permission unless the operator narrows the list.
    • admin-role-subjects-use-admin-tools — Subjects granted admin:api:subjects:* use the admin tools with their own token.
    • owner-credentials-single-tenant-equivalent — Owners manage subjects and roles with any single-tenant Shiro string, wildcards included.
    • permission-tightening-applies-to-both — Any permission tightening is a separate proposal applying to single and multitenant alike.
    • owner-may-revoke-subjects — An owner may revoke subjects on their own site.
    • preview-operator-assisted-ownership — First-preview ownership changes are operator-assisted; self-service comes later.
    • owner-settings-projected-catalogue — Owner-writable settings are the projected display catalogue plus plugin enable; others refuse.
    • owner-alarm-thresholds — Glucose thresholds and alarm enables are owner-writable, bounded 30–600 mg/dL.
    • owner-integrations-none-first-preview — No owner-configurable integrations in the first preview.

    Tenant activity and deletion lifecycle¶

    • tenant-activity-states-diagram — Figure: active, paused and suspended states as decided 2026-11-10.
    • activity-is-pause-suspend — Activity is pause or suspend only; paused sites store uploads but compute no alarms.
    • activity-adopted-semantics-wiring — Suspend refuses ingest and reads; pause blocks reads and UI while uploads continue.
    • owner-may-pause — Owners may pause their own site; only the operator suspends and deletes.
    • activity-row-always-provisioned — Every tenant has an activity row; an unreadable row stops that tenant's evaluator only.
    • suspended-refusal-423 — Suspended and paused refusals return 423 (narrowed by restore-fence-generation: retryable during restore).
    • d6-activity-control-path — Paused or suspended tenants do no evaluator or realtime data work; detection needs no data write.
    • connector-pause-gap-accepted — A connector started while paused waits for unpause; no data is lost.
    • deletion-request-auto-pauses — An owner's deletion request pauses the site; cancelling restores the earlier state.
    • preview-deletion-confirmation — Deletion needs an explicit request and operator confirmation; no mandatory waiting period.
    • platform-backup-and-test-fixtures — The deployment manages PostgreSQL and Vault backup, rollback and seeded fixture copies.
    • tenant-copy-export — Core exports per-tenant COPY data with a digest manifest and restores it under the tenant fence.
    • tenant-deletion-key-retention — Deletion keeps Transit keys and export artifact 30 days, then the operator destroys keys.
    • key-destruction-removes-export — Key destruction also removes the export artifact file, in the same audit entry.
    • export-removal-no-retry — A repeat destruction reports the recorded removal outcome; it does not retry.

    Restore and recovery¶

    • restore-identity-and-cloning — Restore keeps the original tenant id; cloning is a separate operation with new secrets.
    • deleted-tenant-exact-artifact-first — Deleted-tenant recovery first uses the exact confirmed deletion artifact within retention.
    • m5-bounded-snapshot-reconciliation — Current-state recovery reconciles a bounded consistent snapshot (narrowed by stream-fed-clinical-materializer).
    • tenant-local-insertion-semantics — Insertion order is required only within a tenant and collection; pursue tenant-local insertion state.
    • tenant-local-restore-existing-allocator — Original-tenant restore preserves other tenants (narrowed by restore-suspend-drain-replace).
    • restore-history-forward-correction — Restore publishes normal history updates and deletions so clients converge.
    • restore-service-processes — Restore works across separately deployed roles (narrowed by restore-suspend-drain-replace: no cohort invalidate).
    • restore-fence-generation — Tenant generation fencing replaces the operation window (narrowed by restore-fence-read-path and catalogue-verification-admin-owned).
    • restore-fence-read-path — Read-only port skips the final generation compare; writes keep lock then generation read.
    • restore-suspend-drain-replace — Restore is suspend, drain in-flight transactions, replace, activate.
    • restore-census-and-ownership-phase — Ownership operations respect tenant activity. The later unclear-rows resolution retired the pre-restore writer census.
    • restore-resume-and-precheck — Interrupted restore reopens by audited resume (narrowed by restore-suspend-drain-replace: operation-record precheck).

    Event feed, evaluator and realtime¶

    • d6 — Clinical writes remain independent of notification delivery. Writer-driven transport supersedes the replication slot.
    • single-host-streaming-first — The November 16 UDS baseline and pgstream qualification retain their source scope. See the current campaign.
    • single-evaluator-efficiency-priority — One evaluator's efficiency first (narrowed by operable-architecture-first: lower priority).
    • trusted-worker-performance-boundary — Trusted evaluator and feed workers skip per-tenant impersonation and repeated integrity screens.
    • tenant-version-batch-read — One batched version read per pass (narrowed by trusted-worker-performance-boundary).
    • version-batch-shared-login-bound — Shared pool login bound accepted (narrowed by event-driven-reset: idle feed checkpoint part).
    • evaluator-settings-safety-net — The evaluator re-reads every tenant's full settings on a slow timer, 10 minutes default.
    • evaluator-settings-error-shape — Settings-read failures reach the evaluator as SETTINGS_POLICY_UNAVAILABLE with a cause code.
    • alarm-output-idempotent-by-content — Alarm output freshness and origins derive from content, so overlapping evaluators produce one request.
    • alarm-repeat-clock — Active alarms repeat on the single-site heartbeat clock, independent of evaluator revisions.
    • versioned-output-not-owner-lock — Proposed, deferred by versioned-output-deferred: versioned conditional output commits.
    • versioned-output-deferred — W not joined; xdripjs keeps its in-memory notification interval in both modes, documented.
    • realtime-connection-driven — Realtime loads a tenant only while it has sockets (narrowed by static-hash-ownership: placement).
    • realtime-move-alarm-parity — Reconnects do not replay alarms; they return on the heartbeat (narrowed by static-hash-ownership: no dynamic moves).
    • realtime-no-socket-cap — No per-process socket cap; disconnects carry cause codes; flood control belongs to the edge.
    • tenant-devicestatus-status-parity — Tenant status reports devicestatus: {advanced: true, days: 1} as a single site does.

    Alarms and external delivery¶

    • tenant-wide-alarm-suppression — Ack and snooze suppress tenant-wide, keeping the original absolute expiry across restart.
    • durable-notification-requests-and-retries — Persist a stable notification request before dispatch; retry the same identity after ambiguity.
    • first-preview-no-push-provider — No live push provider; in-app alarms; Nightscout-to-Nightscout sync is the first external channel.
    • notification-bounds-single-tenant-constants — Initial notification and connector bounds are the single-tenant constants.
    • external-delivery-admission-by-probe — External delivery is admitted by channel-appropriate probes, not a human-observed device.

    Testing, capacity and process¶

    • performance-signals-not-gates — Performance results are signals; correctness and safety gates stay strict.
    • capacity-characterize-not-gate — Capacity runs characterize; they stop only on incorrect behavior or an unmeasurable harness.
    • capacity-test-tiers — Smoke, discovery and acceptance tiers with a target ladder (narrowed by cluster-fan-out-testing: environments).
    • outcome-evaluator-gate — The evaluator gate judges outcomes against the 120 s clinical deadline; typed transient retries are counted.
    • deadline-from-acceptance — The clinical deadline runs from acceptance; catch-up is per accepted input; no warm evidence in any gate.
    • latency-objectives — p95 within 30 s at expected load is the planning objective; about 1 s the stretch; 120 s the clinical gate under overload.
