    Multitenant REST v1–v3: design and parallel implementation plan¶

    Record

    Record as of 2026-11-04. A point-in-time document; it is not kept up to date.

    Current-use guide, 2026-11-06: Use the dashboard for acceptance and the batching plan §5 for current sequencing. This page retains the route/domain design and original implementation packets; its original heads and next steps describe that dispatch.

    2026-11-04 · Contributor-facing proposal · implementation delivery, not REST readiness.

    Deliver one runnable API listener with tenant-safe versions of the actual v1, v2 and v3 surfaces below. Implement by collection/domain across versions, reusing shipping handlers, query construction and write rules. Do not build three new APIs or wait for a universal framework, production registry, owner lifecycle or a chain of administrative packets.

    Current delivery status lives in the dashboard and release acceptance record. The November 5 priority packets and compatibility matrix sequence current administration, wider REST and parallel historical/current compatibility execution. Their expected-change rules preserve intended RC fixes and measured client quirks; the historical source inventory is not current admission. The source inventory and initial package assignments below retain their captured baseline; already accepted domain implementations must not be rebuilt from those historical missing/pending labels. The continuation lanes carry derived reads, pinned-pattern replay and independent authority review.

    2. Source route inventory¶

    Reading the matrix¶

    Paths are relative to /api/v1 or /api/v2 in the legacy table and /api/v3 in the v3 table. Every v1 row is also mounted in v2, because lib/api2/index.js:14 mounts the entire v1 application before its extras. A regex app.all dispatch is not an implemented business method: only the child registrations below count.     3. Architecture to implement¶

    3.1 One tenant service graph, thin version adapters¶

    Recommendation: retain version-specific HTTP handlers over shared, tenant-bound collection ports and shared write-intent rules. Bind a request to stable tenant identity, then obtain a trusted collection/service bundle. Never switch a global ctx, environment, Mongo collection name or "current tenant" between requests.

    The source already supplies the hard seams:

    • lib/api3/generic/collection.js:26–44 accepts trusted storage/intentFactory options, while the default still constructs Mongo plus cache. lib/api3/shared/collectionWriteIntent.js:5–8 selects that intent factory. Extend those existing seams where the CRUD lane proves the need.
    • Legacy domain wrappers already share lib/storage/write-intent.js; for example lib/server/entries.js:34–35, treatments 28–29, devicestatus 57–58, profile 34–35, food 20–21, activity 22–23. Their parsers, domain transformations, callbacks and event shaping stay in the wrappers. lib/server/storage-reads.js:34–36 still hardcodes Mongo construction; that, not a new REST framework, is the remaining legacy injection seam.
    • lib/storage/postgres-entries-intent.js:48–89 combines reader/writer with forCollectionResolved, commits through an owned transaction, and emits the intent event after commit. It currently refuses source other than v3; it is not already a legacy adapter. postgres-entries-read.js:85–99 refuses v1 dialect/readOptions and unsorted bounded reads. Do not erase those refusals to make v1 tests green.

    Proposed narrow additions, owned by S (§5), defaulting to current behavior:

    1. A trusted logical-collection resolver used by legacy storage-reads.collection, and an injected intent factory in legacy wrapper construction, so each wrapper can use source: 'v1/internal' rules without constructing a raw Mongo handle. Keep callable driver accessors on the single/Mongo path; tenant routers must not receive those accessors.
    2. A small explicit domain registration object per collection: legacy wrapper/router factory, v3 Collection options, schema/readiness requirements, admitted method set. These are trusted code, not user registration or request-supplied SQL identifiers.
    3. An integrator-owned composition point that mounts completed domain routers under all their real prefixes with version-aware admission. An unsupported route is refused before backend lookup, never forwarded to the single application or a catch-all Mongo adapter.

    Concretely, the proposed resolver accepts trusted { logical, source } constants and returns the existing storage interface plus an intent factory; tenant identity comes from the bound request scope, not those arguments. Legacy store()/step() closures consume this bundle; API3 consumes the same domain's storage/intentFactory constructor options with source v3. Missing domain capabilities fail closed in tenant mode; absence of the optional injection in single mode preserves today's Mongo construction. S owns the shared resolver contract; each domain owner makes its own wrapper-constructor change against that contract. Test both injected and uninjected construction before expanding mounts.

    Share pools and immutable code, not credentials or mutable domain state. Construct tenant settings/authorization views from persisted services; capture tenant-bound bundle references for each handler execution. A bounded cache of router/service bundles may be keyed by stable tenant ID plus configuration generation, with eviction/shutdown; it must not cache permission decisions across protected operations. Request-bound transaction context remains authoritative even if a router bundle is reused.

    Why not just mount lib/api with a renamed database? Its handlers capture ctx at construction. Entries uses ctx.ddata for conditional responses and ctx.cache for fast reads (lib/api/entries/index.js:73–98,447–477); writes use ctx.ddata.processRawDataForRuntime and ctx.bus (lib/server/entries.js:167–179). Properties, summary, assistants and notifications capture sandbox/runtime/plugin/egress state. lib/server/bootevent.js:313–335,514–551 constructs this process graph and event subscriptions. A global context clone or Object.assign is not isolation.

    For initial legacy data routes, inject tenant-local read snapshots, cache and bus, with the existing normalization functions. Where cache-backed behavior has not been implemented, admit only paths proven storage-only; do not silently return empty ddata or suppress conditional headers. H owns the reusable snapshot/data-loader binding; collection teams can implement and test their storage and version handlers in parallel using an actual tenant snapshot fixture, then join the runtime seam. Expensive sandbox evaluation can later be externalized without changing the REST contract; that is not a prerequisite for collection writes.

    3.2 Storage: reuse JSON document machinery, not entries policy¶

    Keep PostgreSQL/RLS as the multitenant target and Mongo as the single compatibility baseline. lib/server/storage-backends.js:21–27 registers only Mongo; tests/support/backends.js:39–63 also marks global PG fixtures unavailable. Do not flip either registry globally to claim every collection works. Add capability-scoped tenant composition and focused real-PG fixtures; promote the global backend only when its advertised fixture/storage contract is genuinely built.

    Reuse tenant connection/transaction/scope, typed _id codec, JSON representability checks, filter compiler and common row operations. Proposed storage layout: one RLS-protected table per logical collection, using the existing tenant_id + id_kind + JSON document pattern, with collection-specific generated time/index columns. No per-version tables and no one-off copy of every generic operation. A new collection may use the common row adapter only after its query columns, ordering, identity and write rules are tested.

    The entries candidate migrations/candidates/postgres-entries-v1.json is entries-only: typed primary identity, tenant-prefixed indexes, identifier uniqueness and FORCE RLS. Do not rename its table and call the other schemas done. Domain-owned migration candidates must preserve:

    collection required semantics to specify and test before admission
    entries date/sysTime/type, model-specific coercion, fallback identifier and current/history order; existing schema and accepted intent seam are the starting point
    treatments created_at/eventType/timezone handling, identifier and fallback-key matching, treatment duration/target units, same-time distinct records, array resend and validation outcomes
    devicestatus created_at/device matching, prediction JSON shape/size rules, stable retry identity and latest read order
    profile legacy startDate/current profile/list order and pruning; v3 created_at fallback; nested profile JSON, exact identifier/_id rules
    food quickpick ordering/regular filtering, server-created timestamps versus submitted dates, edit semantics and unknown nested fields
    activity its own date coercion and v1/internal rules, including absence of automatic server dates where shipping rules omit them; no invented v3 route
    settings documents generic v3 document/history/strict-read semantics; physically and semantically distinct from versioned tenant-owner settings and secrets

    Source detail: lib/storage/write-intent.js:160–171 names collection-specific identity time keys; lib/api3/generic/setup.js:56–115 names v3 fallback dates/dedup fields; lib/server/profile.js:131–177 uses startDate queries/current ordering; lib/server/food.js:136–170 implements quickpick/regular selection. Domain packages inspect their full rules, not just this summary. Missing migration/index/normalization decisions block that collection or path, not every REST team.

    Retain unknown representable extension fields without registration. The existing PG codec keeps ObjectId and same-spelling string identity distinct (lib/storage/postgres-identity.js:13–38). JSONB validation and unsupported operations (lib/storage/postgres-entries-write.js:22–79) are deliberate boundaries, not reasons to coerce or discard client fields. A generic JSON schema need not enumerate future controller fields. Use explicit operator migrations/read-only startup checks; never create schema in a gate, route constructor or readiness probe.

    3.3 Version-aware parsing, current authority and error contracts¶

    Use the existing permission vocabulary for each collection/action and consult persisted current authority on every protected operation. Host selects a stable tenant ID, not a principal. Keep root explicit; subject mutations require exact current name alongside stable identity. No anonymous writes; invalid presented credentials never degrade to anonymous/default grants. Keep data, service, tenant-owner and private operator authority separate.

    Do not reuse v3's credential reader for v1/v2 unchanged: lib/authorization/index.js:30–91 reads bearer, query token, object/first-array-item body token, query secret/header secret and body secret, with its own precedence and removal from the body. API3 security uses its own header flow (lib/api3/security.js:11–39), and the accepted tenant data bridge explicitly refuses legacy carriers. H implements a version-aware extraction bridge that reuses shipping extraction behavior without invoking the process enclave or process subject store. Differentially test valid carrier precedence, empty/duplicate/malformed credentials and body-field consumption. If shipping fallback behavior contradicts the approved tenant invalid-credential rule, preserve single behavior and expose a specific tenant refusal; do not quietly change legacy single semantics or silently accept the fallback.

    Preserve middleware order and body limits, not just happy-path documents:

    • lib/api/index.js:40–48,120–145 places experiments before format rewriting and validates counts before data routes. Entries has send-status, raw parser, JSON up to 50 MB, URL encoding, extension rewriting and read permission before action permission (lib/api/entries/index.js:44–59). Other routers have their own ordering/limits.
    • lib/middleware/index.js:23–32 supplies 1 MB JSON/raw/URL-encoded defaults. Treatments and activity override JSON limits. lib/api/notifications-api.js:10–11 also registers parent parsers during router construction; v2 inherits v1 middleware before its extras. Avoid replacing this with one process-wide parser that changes credential consumption.
    • API3 uses its 50 MB JSON parser, parser-error response and extension negotiation (lib/api3/shared/jsonParser.js:6–12, lib/api3/index.js:39–41). Malformed JSON is not automatically the same status in every stack. The accepted tenant v3 mount parses before protection (lib/server/tenant-app/index.js:168); changing order or format admission needs explicit HTTP characterization.

    Version responses stay version responses. For example, legacy missing entries ID yields HTTP200 with an empty list; verifyauth returns a boolean/message probe, and API3 addressed mutation/history has distinct statuses, envelopes and headers. Preserve v1 count tolerances, default count/type/sort, deprecation headers, deletion response, batch partial results and optional Nightscout-Write-Results / results=items (lib/api/index.js:76–145, lib/api/shared/batch-reply.js:38–66). Legacy queries carry nested find[...]/sort structures and path models, whereas API3 search parses field/operator parameters, repeated filter_parameters, sort/sort$desc, limit, skip and fields (lib/api3/generic/search/input.js:109–213). Keep those parsers in their version layer and compile their resulting predicates only where representable. Defaults are not uniform: treatments chooses count100 or count1000 when a find is present (lib/api/treatments/index.js:89–103), devicestatus defaults to count10 and may read cache (lib/api/devicestatus/index.js:82–105), while API3 uses its configured maximum/limit and identifier/created_at/date/_id order chain. The PG compiler currently refuses regex, v1 AST, dotted paths and several operand types (lib/storage/postgres-filter.js:11–20,82–96); time/slice pattern support and legacy coercion therefore need real translation work, not an admission-only switch.

    The approved tenant mutation policy is narrow: missing current subject name401, actual authority outage503; demonstrably nonrepresentable submitted document400, recognized storage outage503, internal/unclassified error500. It is not a global conversion of legacy exceptions, stored-data faults or TypeError. Preserve shipping API3 read-then-write preconditions, seconds flooring and invalid-date behavior (lib/api3/generic/update/operation.js:67–75, patch 50–58), without claiming atomic CAS. Unsupported PG query/update semantics refuse explicitly, not approximate Mongo behavior. Where a new legacy refusal has no established public mapping, the domain owner brings the exact mechanism and proposed version-specific status to the maintainer; unrelated routes proceed.

    3.4 Cross-version writes, histories and notifications¶

    Keep one canonical tenant/collection document store visible to every version. Continue using write-intent's v1/internal versus v3 source rules; they intentionally differ. Reuse its single/array, identifier matching, resend, duplicate-recovery and per-item outcome machinery, plus the legacy batch reply helpers. Do not implement a PG-specific duplicate policy or translate every successful write into an API3 reply.

    Preserve srvCreated/srvModified, modifiedBy, validity/tombstones, fallback visibility and lastModified/history after legacy writes, including restart behavior. A v1 create followed by v3 search/history/read is a required test, not an assumption. History is the shipping modified-document synchronization contract, not a newly invented append-only audit log. Physical deletes and configured pruning retain their actual visibility semantics.

    lib/storage/write-intent.js:4598,4681–4706 separates resolved write execution from intent event emission. The PG entries wrapper emits after its transaction; legacy wrappers also produce data-update/data-received, and v3 handlers emit storage-socket updates. Keep these layers distinct, tenant-tagged, and non-duplicated. Refused/rolled-back writes must not publish committed changes. A tenant-local in-process invalidation bus suffices for the runnable preview; it must not enable realtime/evaluator roles or imply durable multi-process notification delivery. Durable change-feed/outbox delivery, if needed for later scale, is separately measured.

    3.5 Status, discovery and management boundaries¶

    Build an explicit safe env/settings view for each tenant. Never pass process.env, Vault configuration, database configuration, all-tenant maps or process-wide admin notices into a legacy status handler. Preserve legitimate client settings and token exchange behavior, not secret values. v1 status may issue authorization material; mark responses no-store as shipping does (lib/api/status.js:14–18,24–44). v3 status/lastModified must describe only that tenant's admitted, authorized collections, not a configured-but-unimplemented six-collection list.

    Keep API3 settings documents separate from owner configuration CAS/rollback APIs. For v2 subject/role administration, the proposed target is a tenant-scoped legacy compatibility facade with its existing admin permissions backed by persisted authority/identity services; data tokens never become owner or platform-operator credentials. Token/name/role changes must invalidate current authorization across workers. That capability needs a concrete authority mutation/import contract; read-only subject fixtures cannot substitute for it.

    Runtime target: one consumer API listener for the v1/v2/v3 REST compatibility facade, plus separately authorized owner and private operator listeners. The current headless single api role (lib/server/serve/api.js:3–13,36–40) supplies only v3 and authorization, and is not multitenant merely because of its name; serve/roles.js:14–25 says so. The active CLI lane enables only its explicit API preview; keep that scope and use environment credential references, direct-alias defaults, and per-request immediate-peer checks in opt-in canonical mode. Static operator maps remain configuration, not a durable registry.

    4. Policy recommendations, without blocking collection delivery¶

    These are proposed defaults, not new maintainer approvals.

    topic recommendation and operator-visible effect trade-off and bounded blocker
    shared storage vs version forks common collection ports, version-specific frontends; existing client bodies/replies retained a small injection seam is maintained once; rejects unsupported semantics rather than claiming universal Mongo emulation
    cache/runtime-dependent reads tenant-local snapshots using existing normalizers/loaders; admit storage-only paths earlier preserves conditional/derived behavior; cache-backed legacy paths wait for H's real snapshot seam, not CLI or CRUD
    unknown helper collection selectors code-owned allowlist; never lookup arbitrary tenant/process services; preserve shipping fallback only when it selects a safe admitted entries port some previously meaningful dynamic contexts may need an explicit new refusal; E must characterize and present any observable change rather than guess
    v2 subject/role management eventually implement tenant-scoped compatibility facade; keep initial preview excluded avoids breaking existing admin clients long-term; H can deliver status/exchange/discovery now while persisted mutation semantics are resolved
    notification/assistant endpoints retain explicit exclusion until tenant runtime, receipt ownership and fake-provider egress tests exist preview breadth comes from data clients first; X rows stay incomplete, not "all REST complete"
    unsupported inputs exact translation where representable, explicit refusal otherwise protects reliability/data fidelity; migration/client footprint and performance are unmeasured, so no parity claim outside tested shapes

    Long-term direction and architecture favor one shared domain graph rather than three adapters that duplicate business rules. Backward compatibility is enforced against single/Mongo; forward compatibility retains representable extension fields. Maintenance favors small injected ports over a universal framework. Reliability requires current authority, RLS and honest refusal; performance needs later representative query/index/snapshot measurements, not inferred wins. Only a newly observed policy mismatch blocks the affected path. No new global maintainer decision is required merely to begin domain storage, HTTP and synthetic tests.

    Per-package acceptance: behavior, not document production¶

    Each package must drive its listed actual HTTP methods, both successful and refused, through the composed tenant application with real PG/RLS and persisted current authority. Use single/Mongo shipping handlers as a differential oracle with normalized synthetic time/IDs; normalize only transport nondeterminism, not bodies, ordering, outcome count or status differences. Use two tenants sharing external identifier spellings; inspect stored rows, headers, history, attribution and committed events. Test legacy v2 inheritance, suffixes, HEAD/OPTIONS and unknown routes as well as v1/v3. For every write domain cover:

    • valid create/read/edit/delete routes actually present; single and arrays only where shipping accepts them; default and opted-in item replies; a successful extension-field round trip;
    • same request resent, identifier/_id collision, duplicate race and rollback; mixed failures where legacy batches permit them, without upgrading all batches to atomic transactions;
    • current grant/role/revocation/rename changes after JWT issuance; anonymous reads only when tenant policy permits; denied anonymous writes, invalid credential and exact subject attribution;
    • cross-version read/history/lastModified after legacy writes, tombstones/permanent delete, tenant-local pruning, cache invalidation and restart; data in tenant B remains unchanged;
    • known service outage versus invalid submitted data versus internal fault, using that route's approved status contract; no credential/error payloads in logs or response bodies.

    Red controls are part of coding: remove/bypass the newly added admission or intent seam and require an actual HTTP success test to fail; cross-wire the tenant binding in a synthetic owned fixture and require row/cache/event isolation to fail; freeze current authority or drop attribution and require revoke/rename tests to fail. For query support, change the translation of one exercised operator/order and require differential results to fail. For N, wrong-tenant receipt routing must fail a fake-provider assertion; for H, inserting a synthetic sentinel into process-only configuration must fail a non-disclosure assertion. Record exact failure symptoms, restore the source and rerun. A suite that passes because its routes remain refused, fixtures fall back to Mongo, or opt-in suites are skipped proves nothing.

    Execution and integration order¶

    1. Start clean domain worktrees from the accepted cumulative base; pin source and characterize the owned legacy/G3 family against Mongo. Implement domain schemas/adapters and tests while S makes the narrow legacy injection exports. Domain tests may inject completed exported ports, but must later pass through the real integration mount before admission is claimed.
    2. Join existing CRUD and CLI deliveries when accepted. S reconciles their shared surfaces once, preserving their tests; teams rebase/merge only clean accepted commits. Land E/T/D/F independently with scoped capability admission and real-provider HTTP tests. No blanket enabledCollections switch, NS_TEST_BACKEND=postgres availability switch or broad permission wildcard as a shortcut.
    3. Join H's snapshot/credential/status work; expand cache-backed/derived reads only after their cross-tenant tests pass. Implement authority administration and N side effects as their own bounded capabilities. Excluded endpoints remain visibly excluded until delivered.
    4. At coherent delivery joins, run the full established suite and browser/client workflows, then the existing PR check last. Parent records acceptance once; do not manufacture a packet dependency before each collection can code or test.

    6. Completion gate for the full REST goal¶

    S adds a focused executable route-matrix regression test in CRM as the implementation evolves: enumerate the actual mounted router graph with its configuration predicates and compare against the families in §2. Exercise each expanded family/method over HTTP for one authorized success and its relevant refusal; distinguish native methods, implicit HEAD/OPTIONS, prefix redirects, inherited v2 and disabled conditional integrations. An unknown collection/method must not acquire permission or storage merely because the generic code exists.

    Do not write a constants-only inventory test. Its negative control adds a synthetic mounted route with no matrix case and must fail; remove a mapped mount and require an exercised HTTP case to fail. Turning off provider opt-ins or skipping backend fixtures must make the completeness report incomplete. Existing source fixtures with dormant PATCH routes are not evidence that the real credential bridge admits PATCH.

    The full v1–v3 target is complete only when:

    • every unconditional matrix row is tenant-implemented and verified, and every shipping conditional family either has its tenant capability implemented/tested or an explicit approved product disposition; "preview excluded" alone does not close it;
    • Mongo-compatible semantics and explicit tenant differences have actual HTTP evidence for parsing, credentials, response/status/headers, queries, retries, batches, writes and history;
    • persisted authority, PG/RLS, shared identity collisions, tenant snapshots/events and restart controls pass without tenant/process secret leakage or fallback to single/Mongo;
    • the runnable API process advertises and serves that measured breadth, with read-only readiness and owned shutdown; owner/private-operator roles remain separately authorized;
    • the integrated full suite, relevant client/browser workflows and last-step PR check pass, with pending/unmeasured exclusions disclosed rather than counted green.

    Production identity/transport provenance, HA, durable registry, activation/owner lifecycle, realtime and connector/evaluator operation retain their own completion criteria. Completing REST does not silently complete those programmes, and a useful partial preview does not require waiting for them.
