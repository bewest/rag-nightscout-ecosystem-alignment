Report that point alongside the first constrained point and the evidence for its cause. Ten thousand tenants is a point of interest. A lower, repeatable breakpoint answers the question too. ## Interpreting a breakpoint

| Observation at matched achieved load | Architectural hypothesis | Measurement or single-change comparison |
|---|---|---|
| A broader roster hurts at constant RPS, especially on first input | Registry work, resident-model churn or first-seen recovery grows with the working set | Compare eligible and actually active tenants, registry queries, evictions/reloads and recoveries/s. Contrast first-input latency with already active tenants. Account for provisioning separately. |
| HTTP tails rise as the API main thread approaches one core | Synchronous API work or authorization cost limits starts | Measure main-thread CPU and event-loop delay separately from worker/GC and container CPU. Check SQL time and waits per request before attributing the bend to Node. |
| HTTP stays fast while durable output falls behind | Acknowledgement decouples intake from clinical completion. The queue may be in stream delivery, recovery, or evaluation. | Align accepted, received and durably completed positions with WAL lag, snapshot starts/completions, evaluator CPU, accepted/completed inputs per second and outstanding age. Vary only write rate. |
| Reads and writes slow together while database waits or statement cost grows | A shared PostgreSQL resource or pool constrains multiple roles | Attribute SQL work and waits to roles, including the observer. Compare execution and connection waits, CPU, I/O and throttling at the two adjacent points. |
| Durable output stays timely but matched viewer frames slow | Realtime fanout, socket queues or the viewer instrument constrain delivery | Vary viewers at the same write rate. Trace the same input through durable output, server frame and receiving client. |
| Target rises while issued starts flatten and driver misses grow | Generator concurrency or resources limit the traffic actually presented | Inspect per-operation in-flight counts, driver CPU/memory and placement. Compare the two driver allocations below on the same application. |

A later breakpoint with lower CPU-seconds per completed request or fewer SQL calls per accepted write at matched load supports a gain from simplification. An earlier breakpoint with a larger active set, more writes or more viewers may reflect that workload. Where practical, repeat one controlled change and restore the reference before attributing causality. Reserve horizontal scaling for a subsequent experiment on the role shown to bind.

**Fold in a thin profile resolver.** One operator input should select provisioned and eligible tenants, either total ordinary RPS or per-tenant cadence, viewer count and optional per-operation driver allocation. Use the existing seven-shape calculator. Preview requested and rounded effective rates by operation, then emit the normal Compose settings and Kubernetes workload profile under a new run ID. Preserve prior artifacts and keep the current runtime and assessors. [Workload profiles](../../../tools/mt-bench/kubernetes/workloads/README.md)

The baseline inherited two preallocated and four maximum k6 virtual users per operation. Compare it at 1,000 tenants and 13.89 req/s against eight preallocated and eight maximum per operation (56 total). Keep image, offer, resources and fixture matched. Record delivered starts, drops, in-flight requests, driver memory, HTTP tails and clinical backlog. More concurrency can expose server latency by sending turns previously skipped. A change on both settings measures their combined effect. Use a 4/4 or 2/8 intermediate point only if distinguishing allocation from ceiling would change the choice. Select the driver for the subsequent sweep from those measurements. Distributed generators are a follow-up if a single generator is the demonstrated limit.

For each point publish scheduled, issued, completed and successful rates, errors and drops by operation, HTTP p50/p95/p99, accepted-to-durable and matched-frame tails with denominators, late/missing counts and backlog after drain. Report per-role CPU and working set, setup duration, and the timing and cost of sampling. Display achieved rate on the latency curve and annotate the offer, drops and product verdict. Mark single exploratory points as discovery. For a repeatable operating point, report passes out of three and min/median/max across the matched repeats. Show the highest healthy achieved rate, its multiple of realistic cadence at that population, and the next constrained point. A driver drop, HTTP refusal or setup delay remains evidence with its own attribution. An unavailable counter leaves its dependent hypothesis open. The existing four product checks and run-ownership rules govern the experiment.
