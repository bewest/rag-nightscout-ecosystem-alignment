    Supported database ownership contract¶

    The exclusive application ownership decision defines supported writers. Nightscout collectively owns its selected namespaces: multiple internal processes and controlled maintenance tools may use PostgreSQL, but every supported participant follows the relevant application contract. External direct writers are unsupported and their effects are undefined behavior, consistent with single-tenant Nightscout's external MongoDB writer boundary. Other applications may own unrelated namespaces; this does not require exclusive ownership of an entire PostgreSQL server.

    Exclusive application ownership does not confer unrestricted SQL rights on each component. Retain effective privilege/readiness checks, tenant-bound transactions, forced RLS, current authorization and narrowly scoped credentials. Internal clinical writes must use the canonical write path; lifecycle participants must honor admission, drain and invalidation. The advisory-lock protocol coordinates these supported participants. A direct writer ignoring it is outside the contract, not a reason to require a stronger database fence for the supported topology. PostgreSQL documents advisory locks as application-coordinated locks.

    Logical API, workers and admission¶

    One logical REST/API component¶

    REST v1, v2 and v3 belong to one logical stateless request-serving API component, together with credential authorization and owner-management modules. Version-specific adapters retain their request, authorization and response semantics; protocol versions are not separate application services. Stateless means durable authority/data are external and request state is reconstructible, not that the process has no in-flight work or retained readiness state. This logical grouping does not prescribe a single listener, process or privilege set. Owner management retains its own audience and listener contract and may be colocated with API serving under the existing owner-authority boundary. The accepted separate-role reference remains one concrete composition, not a requirement that every REST responsibility become a separate service. Grouping the versions does not admit additional routes: the recorded compatibility scope and admitted handler/storage contracts still bound actual coverage.

    Headless workload owners¶

    Realtime owns live connections; the evaluator is a headless worker and remains one current workload owner. Connector actors (vcpool) belong to background polling/egress work and submit clinical writes through the canonical API boundary; the ed2 role declaration has no runnable start. Evaluator partitioning and realtime replication are separate future capabilities, not prerequisites for the queued request-serving API scale-out.

    Private maintenance execution¶

    The lifecycle/restore controller executes as a private operator CLI, job or worker; the ed2 operator tool composes it outside API serving. Each serving instance supplies generic operation-admission, lifetime and invalidation hooks; those hooks do not place a restore engine or maintenance credentials in every API replica. A future command/status REST surface could request or observe maintenance while the privileged worker executes it separately; no new endpoint or process layout is selected here. The logical placement map owns the broader component explanation.

    Maintenance safety is distinct from desired activity¶

    The existing claim/generation-bound maintenance window determines whether an operation can run safely during recovery. Operator-controlled resource/activity policy asks which serving, ingestion, evaluation or connector work should run at all. That policy is decided as two durable flags, pause and suspend (activity-is-pause-suspend), and stored in tenant_activity beside, not inside, the maintenance window; see tenant activity. A maintenance phase named active is not evidence of activity eligibility, and clearing the restore hold never changes the activity flags (policy module). Observed health is a further separate fact.

An internal API can be a module interface within a process or a private application protocol between processes. The reference's process transport is private HTTP/JSON over Unix sockets; network endpoint selection requires the separately described transport binding. The following ownership map does not introduce a generic SQL-over-HTTP service.

    Kubernetes scalability smell test¶

    Yes, as an architecture smell test: a replaceable request-serving instance with durable authority outside the process is a natural candidate for a Kubernetes Deployment. Exclusive application database ownership permits multiple cooperating replicas; it does not mean a single API process. An internal API boundary helps separate those replicas from consumers, but does not itself make either end stateless.

    Binding, forced RLS and privileges¶

    The lower connection transaction acquires the selected window lease before starting SQL, binds the tenant with transaction-local app.current_tenant_id, then verifies current window admission. Tenant policies compare tenant_id with that setting for both reads and writes. Reviewed tables use ENABLE ROW LEVEL SECURITY and FORCE ROW LEVEL SECURITY. An application identity must be a nonowner without superuser/bypass authority. A tenant binding is trusted service context; RLS does not authenticate the end user or constrain a compromised worker that holds all tenants' credentials.

    Readiness examines effective grants and ownership, including inherited rights; a reassuring role name is insufficient. The insertion readiness oracle distinguishes:

    • serving roles: clinical read/update/delete, input-column INSERT excluding insertion_ordinal, allocator execution and bounded counter read/insert/update;
    • readers: clinical/counter SELECT, without mutation or allocator execution;
    • restore roles: separately checked explicit-ordinal and counter maintenance rights for the admitted restore protocol.

    The actual trigger is SECURITY INVOKER, with fixed pg_catalog search path. It neither grants a writer extra authority nor requires a service with elevated function privileges. The structural oracle checks the current function body, trigger enablement/binding, exact counter shape, ownership, RLS, constraints and absence of a native identity default. A ledger check alone cannot prove these physical invariants.

    The reserved metadata tenant binding is a separate lower-connection path that requires a database-confirmed read-only transaction. It permits shared schema/ACL checks while normal tenants are suspended; it is not permission to read a paused tenant's documents. The source uses it for the consumer advisory-lock same-database challenge and unconditional metadata checks. The c23 native matrix measures its stated actual startup cases; other guard controls retain their own source/protocol scope. Consumer startup source

    History clock and insertion counter serve different contracts¶

    State Meaning Client-visible implication
    last_stamp The clock decorator locks the tenant row through the outer data transaction, allocates strictly increasing numeric server stamps and updates the durable floor. Preserves the existing srvModified / history cursor protocol. Clinical timestamps and public IDs retain their own meanings. Serialization is tenant-local; a sequence value alone would not prevent a reader advancing past an earlier uncommitted write.
    last_ordinal The insertion trigger allocates within one tenant/collection in the same transaction as the row. Missing/invalid state refuses; updates cannot change tenant/ordinal identity. Reproduces supported natural/first-match ordering. The read path selects id_kind,doc and orders by the private ordinal; the ordinal is not a public ID or history cursor.

    There is no required cross-tenant total order. Separate insertion state also works without opting into the history-clock decorator. Counter-row contention serializes same-tenant inserts for that collection; history-clock composition serializes admitted stamped writes across that tenant's domains. Pools, storage, CPU and DDL locks remain shared resources. The adopted insertion semantics and history-forward restore policy own compatibility decisions; the counter analysis retains alternatives and comparisons with database revision/change-stream designs.

    Upgrade and readiness sequence¶

    The catalogue validator accepts an explicit ordered JSON catalogue, checks SQL checksums and validates the exact reviewed typed conversion/correction plans. It does not discover arbitrary executable migrations. The runner's ledger inspection requires applied migrations to be an exact checksum-matching prefix, refusing unknown entries, gaps and drift.

    The operator runner uses one direct client for the namespace advisory lock, DDL and ledger writes. Each migration and its ledger entry commit atomically; the catalogue as a whole can span several transactions. status and check use a read-only inspection transaction; stale check refuses. There is no migration-down operation. Serving boot checks; it does not run migrations or provision grants.

    Deployment backup restore has a stricter order: prepare fresh target namespaces with the artifact's exact catalogue, verify exact ledgers and restore raw state, then upgrade. A longer current ledger is not interchangeable with the artifact's schema. The physical restore module validates before effects, recreates selected ACLs and verifies restored counts/digests before COMMIT; it does not fabricate migration ledger entries.

    The insertion conversion takes an ordinary access-exclusive DDL lock, validates existing identity rows, seeds counter maxima by tenant, removes the table-wide identity and installs the tenant trigger/index. That one-time upgrade exclusion is distinct from a recurring tenant restore pause. Its original catalogue bytes remain immutable; the binding SQLSTATE correction is an appended checksummed operation. An upgraded binary must still verify the current physical trigger/function, grants and tenant floors before admission.

    The startup helper defers only actual-window suspension errors, not arbitrary errors with a matching string. Lazy initialization runs under the actual later tenant admission; invalidation rejects stale initializer completion. A suspended A therefore need not prevent B startup in the new source. The startup decision requires fresh-process native proof.     Write transaction and restore transaction boundaries¶

    For ordinary admitted writes, the upper HTTP/IPC/socket lifetime and the lower SQL transaction have different lengths. The operation window records unfinished work until the outer callback/response/acknowledgement ends; ending a SQL transaction alone does not prove that work drained. Within SQL, the tenant clock, document changes and insertion counter changes commit or roll back together. Post-commit publication runs only after the outer transaction acknowledges COMMIT.

    Logical tenant restore uses the private maintenance controller, not an arbitrary quiesced: true assertion. It pins actual fixed participants, checks current operator authority, commits durable suspension/generation/claim, drains unfinished operations, then obtains the tenant's exclusive advisory lock. The bound claim is revalidated on the same operator transaction. Unknown actors and changed participant incarnations refuse; a restarted process cannot inherit an earlier pin's authority.

    The logical planner preserves public/typed identities and sorts captured ordered rows using BigInt ordinals. It replays them through ordinary allocation, preserving relative order without preserving private numeric ordinal values. Unchanged documents keep current server metadata. Changed/restored history documents receive stamps above the live issued floor; current records absent from the artifact become isValid:false deletion records. Activity has no v3 history protocol and uses snapshot replacement plus invalidation. Exact physical/raw backup import has a separate fidelity contract in tenant operations; it must not be substituted for client history reconciliation.

    The restore implementation retains current nonclinical catalogues, including selected authority, sessions, secrets, policies, checkpoints, outbox and suppression. It retains the live history floor and advances it through the clock decorator. It does not replay old control claims/audit as clinical data. The identity guarantee covers records retained in the current tenant or artifact; identities hard-purged from both retain the existing history-retention limit.

    A DATA COMMIT whose acknowledgement is lost has an uncertain outcome. Retrying or reopening automatically could publish contradictory history or reuse stale cache state. A committed suspension, unresolved unfinished operation, missing invalidation acknowledgement or uncertain activation requires verification and operator recovery. If the activation COMMIT acknowledgement is lost, the stored window may already be active and its audit activated; the uncertain response does not prove continued suspension. Inspect the committed state rather than automatically replaying activation. The controller commit handling preserves those distinctions. This preview provides no automatic orphan clearance or supported suspended-restore resume command. Operator-verified recovery remains separate work; no deterministic recovery-time bound follows from the refusal/restart evidence.

    Tenant activity: pause and suspend¶

    Migration 0007_tenant_activity in the lifecycle control catalogue creates tenant_activity (primary key tenant_id, referencing tenant_lifecycle_windows; a positive version; paused and suspended booleans; a deletion_request_id/paused_before_deletion pair that is set or null together) and an append-only tenant_activity_audit whose verb is one of provision, pause, unpause, suspend, unsuspend, deletion-request, deletion-cancel or deletion-execute, with authority owner or operator. Both tables use enabled and forced RLS on app.current_tenant_id, and PUBLIC has no rights.

    A row for every tenant. The same migration backfills one active row (version 1, both flags false) for every existing window row, with a provision audit row attributed to principal migration, consumer backfill-0007. It lifts FORCE ROW LEVEL SECURITY on tenant_lifecycle_windows for the two backfill statements and restores it before the migration commits; migration and ledger entry are one transaction (see upgrade and readiness). New tenants get their row from provisionInTransaction, which the Compose bootstrap calls in the same transaction that inserts the window row (activity-row-always-provisioned).

    Two flags, three states. The policy module defines active, paused and suspended, with suspended taking precedence. Paused admits uploads and connector polling and stops the evaluator, so alarms are not computed or delivered; suspended admits nothing. The column grants enforce who sets which flag (grant set): the owner identity may update version and paused only, the operator identity version, paused and suspended, and the deletion-ceremony identity also the deletion pair. The ceremony effects pause on a deletion request, restore the earlier pause state on cancel, and suspend on execution, each inside the ceremony's transaction (deletion-request-auto-pauses).

    Where it is read. Each consumer reads the row afresh through a reader store, after a check of the control catalogue ledger:

    Consumer Effect Anchor
    API (HTTP) Write methods, OPTIONS and the v2 credential exchange count as uploads; everything else is a read. Refusals are 423 TENANT_PAUSED / TENANT_SUSPENDED; an unreadable row is 503 TENANT_ACTIVITY_UNAVAILABLE. serving gate, API wiring, status map
    Realtime Every current-state read checks eligibility; an ineligible tenant reads as disabled and its sockets are invalidated. realtime gate
    Evaluator Work lists are built from tenants eligible now; an unreadable or missing row makes that tenant ineligible with its own code (ACTIVITY_UNAVAILABLE, ACTIVITY_NOT_PROVISIONED). eligibility, evaluator wiring

    The activity block is optional in each role's configuration; without it the role does not consult the table. The in-tree Compose plan at 16a1fc2d provisions rows but grants no role the activity tables (deployment grants contain no tenant_activity grant), so its roles run without activity admission.

    Key retention and export-file removal¶

    Migration 0005_tenant_lifecycle_key_retention keeps one record per deletion request: the export artifact's 64-hex digest, the retained key names and a phase of retained, restored, destroying or destroyed. Migration 0006_tenant_lifecycle_artifact_removal adds artifact_removal (removed, absent or failed) and artifact_removal_code, with a CHECK that a removal outcome is present exactly when the phase is destroyed and a code is present exactly when the outcome is failed.

    destroyRetainedKeys refuses LIFECYCLE_ARTIFACT_REMOVER_REQUIRED before any state change when no remover is composed. It commits destroying, has the key custodian delete and confirm the absence of every key, then removes the export file by digest and records the outcome in the same row update that commits destroyed. A missing or unremovable file never blocks key destruction; a repeat call on a destroyed record reports the recorded outcome without retrying. The filesystem remover builds the path only from the configured private directory and the recorded digest (tenant-artifact-<digest>), and refuses a symlink or non-directory at that name. Copies outside that directory are the operator's responsibility (key-destruction-removes-export, export-removal-no-retry).

    Restore census and non-clinical identities¶

    The actor census in assertComplete reads every other client backend in the database whose identity holds any privilege, direct, inherited or by ownership, in the protected namespaces. A backend matching a pinned participant's PID, birth and role passes. Any other backend is exempt only when its identity holds no privilege on any clinical table (entries, treatments, devicestatus, profile, food, settings, activity) and no write privilege on tenant_insertion_ordinal or tenant_write_clock; otherwise the census refuses RESTORE_COHORT_UNKNOWN_BACKEND. Grants read from the catalogue in the census statement decide; role names and application_name do not. Read-only identities and the admin role's ownership_operator are therefore accepted while connected (restore-census-and-ownership-phase, restore-census-counter-writers). The exemption is a configuration check of connected identities, not a check of live writes. The disposable-PostgreSQL integration test admin-lifecycle-fit exercises the admin role beside a restore, including granting it a clinical table to make the census refuse.

    The ownership_operator identity¶

    The deployment plan declares a separate <prefix>_ownership_operator database identity for the admin role's ownership operations. In the authorization namespace it may read and row-lock tenant_authorization_config and tenant_owner_policy through UPDATE(owner_fence), insert and update active, can_update and delegable on tenant_owner_actors, read tenant_authorization_subjects and insert into tenant_subject_admin_audit. In the control namespace it gets only SELECT on the window, request and ceremony tables (phase grants). It holds no clinical grant and no counter grant, so the census above accepts it. Each ownership change reads the tenant phase under the shared window lock before any ownership row lock and refuses OWNERSHIP_TENANT_INACTIVE unless the tenant is active (ownership check). The admin role is not a lifecycle cohort participant.

    Shared resources and remaining fences¶

    The fixed cohort uses private same-UID sockets and trusted credential custody. It compares actual backend PID, birth, role and datastore identity; application names are not membership. The actor census refreshes PostgreSQL's statistics snapshot on the same operator client before reading actors; at 16a1fc2d it also accepts non-clinical identities. It remains a diagnostic/refusal check, not a physical database fence against a newly opened raw client with already-authorized DATA credentials. Such external writers are unsupported under the application ownership contract; arbitrary-writer exclusion is not a supported-topology admission gate. A trusted all-tenant worker or DBA remains within the deployment trust boundary. See the deployment/trust decision.

    Tenant-local state removes cross-tenant counter maintenance during restore; it does not partition database capacity or remove shared service failure. Restarts, full membership availability and operator recovery remain distinct from running B continuity. Realtime aggregate readiness remains strict while additive live and per-tenant fields describe partial tenant availability. The exact startup, health and fixed-cohort boundaries live in the application cohort guide. The ed2 cold measurement adds the packaged ordinary-restore/UI/B-continuity scope. HA, multihost membership, capacity and whole M6 retain separate admission criteria. The current acceptance family owns the distinct browser, cold Compose, client, regression and corpus verdicts.
