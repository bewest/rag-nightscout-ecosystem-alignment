    Proposed K=1 capacity study¶

    Record

    Record as of 2026-11-19. A point-in-time document; it is not kept up to date.

    The November 19–20 campaign used this plan. Its measured endpoints, population comparisons and fixture timings are recorded separately.

    Find the highest achieved ordinary request rate at each tested population for which all accepted writes reach storage, clinical output arrives within 120 seconds of acceptance, every input has durable output by end of drain, isolation and authorization hold, and the datastore stays healthy. Report that point alongside the first constrained point and the evidence for its cause. Ten thousand tenants is a point of interest. A lower, repeatable breakpoint answers the question too.     Run order¶

    1. Use the completed paired baseline. Its three product passes on each platform release the local 3,000 then 10,000 realistic-cadence discovery points. Collect the cold first inputs from acceptance on both. On Kubernetes, seed 1,000 tenants once under the fixture candidate and restore an independent copy per point. Start at the original offer of 13.89 req/s with derived driver sizing. Measure fresh and restored setup to the same roster-ready boundary, including primer, PVC attach and roster transfer. Record snapshot capture and teardown separately, so the cost of repeated fresh setup can be compared with one seed plus the restores. Use a fresh observation with the same harness and binding when attributing a difference to restore. The older 291–307 s fresh times give historical context.     Interpreting a breakpoint¶

    Observation at matched achieved load Architectural hypothesis Measurement or single-change comparison
    A broader roster hurts at constant RPS, especially on first input Registry work, resident-model churn or first-seen recovery grows with the working set Compare eligible and actually active tenants, registry queries, evictions/reloads and recoveries/s. Contrast first-input latency with already active tenants. Account for provisioning separately.
    HTTP tails rise as the API main thread approaches one core Synchronous API work or authorization cost limits starts Measure main-thread CPU and event-loop delay separately from worker/GC and container CPU. Check SQL time and waits per request before attributing the bend to Node.
    HTTP stays fast while durable output falls behind Acknowledgement decouples intake from clinical completion. The queue may be in stream delivery, recovery, or evaluation. Align accepted, received and durably completed positions with WAL lag, snapshot starts/completions, evaluator CPU, accepted/completed inputs per second and outstanding age. Vary only write rate.
    Reads and writes slow together while database waits or statement cost grows A shared PostgreSQL resource or pool constrains multiple roles Attribute SQL work and waits to roles, including the observer. Compare execution and connection waits, CPU, I/O and throttling at the two adjacent points.
    Durable output stays timely but matched viewer frames slow Realtime fanout, socket queues or the viewer instrument constrain delivery Vary viewers at the same write rate. Trace the same input through durable output, server frame and receiving client.
    Target rises while issued starts flatten and driver misses grow The generator could be CPU- or memory-bound, or slow responses could keep its workers busy Compare measured in-flight requests and driver use to the rendered per-operation limits. Align missed starts with response latency, throttling, memory pressure and placement. Record the cause as open when the samples cannot distinguish them.

    A later breakpoint with lower CPU-seconds per completed request or fewer SQL calls per accepted write at matched load supports a gain from simplification. An earlier breakpoint with a larger active set, more writes or more viewers may reflect that workload. Where practical, repeat one controlled change and restore the reference before attributing causality. Reserve horizontal scaling for a subsequent experiment on the role shown to bind.

    Profile ergonomics and reporting¶

    Driver sizing is implemented. The shared k6 code derives VUs for each operation from its offered req/s and platform headroom. The default headroom is 1.5 for Compose, 2 for Kubernetes and 3 for a remote generator. Scheduled, issued, completed and dropped requests are reported by operation. Only the four product properties determine the product verdict. At 1,000 tenants and the realistic offer, the Kubernetes driver renders 14 preallocated / 144 maximum VUs. At 240 req/s it renders 122 / 2,405. These are configuration figures. Actual concurrency, generator memory use and the cause of dropped starts require live observations. This decision supersedes the proposed fixed 2/4 versus 8/8 experiment. Driver sizing decision

    Operator convenience remains proposed. A single total-ordinary-RPS or per-tenant-cadence input could preview the seven resolved rates, platform headroom and VU totals before writing a fresh run configuration. The existing planners already accept the converted population and rate settings. For this sweep use the prepared profiles from retained evidence k1-capacity-study-20261119/resolved-33889a80a0. The portable cold-archive/PVC path remains a later Codex option for environments without DigitalOcean snapshots. Workload profiles

    For each point publish scheduled, issued, completed and successful rates, errors and drops by operation, HTTP p50/p95/p99, accepted-to-durable and matched-frame tails with denominators, late/missing counts and backlog after drain. Report per-role CPU and working set, setup duration, and the timing and cost of sampling. Display achieved rate on the latency curve and annotate the offer, drops and product verdict. Mark single exploratory points as discovery. For a repeatable operating point, report passes out of three and min/median/max across the matched repeats. Show the highest healthy achieved rate, its multiple of realistic cadence at that population, and the next constrained point. A driver drop, HTTP refusal or setup delay remains evidence with its own attribution. An unavailable counter leaves its dependent hypothesis open. The existing four product checks and run-ownership rules govern the experiment.
