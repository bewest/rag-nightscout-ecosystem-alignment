    Multitenant clinical storage by age: brief and proposal¶

    Record

    Record as of 2026-11-24. A point-in-time document; it is not kept up to date.

    Contributor- and maintainer-facing proposal, 2026-11-24. Proposed; nothing here is adopted. It builds on the measured storage layout proposal and restates none of its figures beyond what the argument needs. Figures are labelled measured (ours, linked), read-derived (arithmetic or reading of code and records), or vendor-documented (a provider's page as read on 2026-11-24, linked). Prices change; re-read them before quoting.

    1. Summary¶

    • Accept the larger volume for the first production boundary. On the current layout, multitenant PostgreSQL stores about 1.6 MB per tenant-day where single-site MongoDB stores 0.24–0.38 MB on the same documents (measured). At 30–90 retained days this costs cents per tenant-month and the 1,000-tenant run passes with a 0.9996 buffer hit rate. Bytes are not yet the problem.
    • Keeping years of detail in the hot layout is the problem. Ten years at today's layout on replicated block storage costs about $2.30 per tenant-month, roughly ten times an illustrative compute share of $0.10–0.25 (section 3). That would erode the savings from consolidating compute.
    • Store data by age, matching how Nightscout is used. Recent days serve live coordination at today's latency. Up to about 90 days serve reports and comparisons. Older data serves statistics and audits, which can be slower. A tiered layout keeps ten-year detail for about $0.06–0.27 per tenant-month (read-derived). A detail-retention limit with summaries kept beyond it is a later, deferred option.
    • Every lever, its trade-off and its priority is in section 10.
    • Stay on plain PostgreSQL. Native time partitioning and our own cold tier get most of the benefit. TimescaleDB's compressed chunks do not support row-level security (vendor-documented), which conflicts with D3. Citus solves a scale-out problem we have not measured and adds a cluster of database nodes.

    2. What has been tried¶

    All measured on synthetic tenants written through the product unless marked; detail and evidence in the layout proposal.

    Attempt Result State
    Remove the size trigger and four redundant indexes −17.1 % clinical bytes Adopted, storage-machinery-removal
    lz4 or toast_tuple_target No effect: rows under ~2 KB are never compressed Rejected
    Typed device status (predictions as arrays) Larger (1,026 vs 825 MB): smaller rows fall under the compression threshold Rejected
    Device status as one compressed row per tenant-hour (stage 2) −82 % per added day; evaluator window p95 82 → 113–276 ms; 288-document write hold 45 → 638 ms Parked, devicestatus-hour-chunks
    Typed entries and treatments (stage 1) −24.7 %; indexes unchanged and 72 % of the result; window read ~2× slower, settings-off resends 1.13 → 5.23 s, a selective lookup scans the tenant Built locally, not adopted
    Prediction curve cap Saves nothing: uploaders send at most 48 points Parity only, predictions-max-size-single-tenant-parity
    Filesystem compression (ZFS, proxy) ~4.5× on disk; buffer cache and vacuum see uncompressed pages Not proposed for hot data
    Per-tenant-day cold chunks (scratch) ~0.13 MB per tenant-day for cold data Priced, not built

    The lesson. Every attempt that compressed hot rows traded clinical read or write latency for bytes. The ones that helped removed work (a trigger, indexes). The remaining large wins are in data nobody reads at low latency.

    4. Use cases set the tiers¶

    Nightscout data is read in three distinct ways. Today all three share one layout and one latency expectation.

    Use Age read Who Latency need
    Live coordination: dashboards, alarms, followers, the evaluator Last ~48–60 hours, sometimes a week Clients, evaluator, realtime Today's: tens of milliseconds
    Reports and comparisons: a 4–12 week period against another Up to 90 days routinely; comparison periods 1–3 years back Owners, clinicians, report tools Seconds are acceptable
    Statistics and audit Months to years Owners, auditors, researchers Minutes, or an asynchronous job, are acceptable

    Beyond about 90 days, detail is rarely looked at directly; it feeds statistics and occasional audit. At five to ten years it is debatable whether full detail is still needed, or only summaries.

    5. Proposal¶

    Tiers¶

    Tier Age (defaults; the tenant chooses within operator limits, section 6) Storage Served by Latency
    Hot 0–14 days Today's row layout, in the current time partition Every API, evaluator, realtime Unchanged
    Warm 14–90 days Same rows, older partitions, fewer indexes Every API Same order, may be slower on unindexed filters
    Cold Over 90 days One compressed bundle per tenant, collection and month v1/v3 reads with a relaxed latency; export; report jobs Seconds; audit-scale reads as jobs
    Summary Any age, kept beyond a detail-retention limit if one is chosen One small statistics row per tenant-day Reports Fast

    Hot and warm differ only in partition and index set, so a report over 90 days reads ordinary rows. The 14- and 90-day boundaries are defaults (section 6).

    5.1 Hot and warm: native time partitioning (no new dependency)¶

    PostgreSQL's declarative partitioning splits each clinical table by time, for example monthly, under the same table name. Row-level security, grants and the API are unchanged; serving roles keep grants only on the parent. Partitions are created ahead of time by the admin role on a schedule (pg_partman would also do it but is one more component).

    Predicted gains (read-derived from the 10k evidence; none measured yet): - The working set stays in memory. Reads of the last few days touch only the newest partition and its indexes. The failed 10k run coincided with a buffer hit rate of 0.952 and autovacuum running across a 13 GiB relation. - Vacuum stays small. Only the current partition takes writes. Older partitions are frozen once and then left alone. - Fewer indexes on older partitions. PostgreSQL allows an index on some partitions only. Warm partitions can drop indexes that only live traffic uses. Indexes are about half of every table today (measured). - Moving data to cold, or deleting it, becomes detaching a partition, not deleting billions of rows.

    Costs and open design points: - No global unique index. A unique index on a partitioned table must include the partition key, so tenant-wide uniqueness of _id and identifier (d20) needs a small identity table mapping each key to its time. Stage 2 measured that structure at about 172 bytes per document. - Queries without a time range read every partition. Identity lookups go through the identity table. Resend matching keys already carry a time (created_at, date), read-derived; confirm per collection. - The partition key is chosen in section 5.2. - Late or backfilled data writes into its older partition; this must stay under the bounded write-lock hold (per-tenant-lock-bounded-hold).

    5.2 The partition key¶

    Three candidates, judged on architecture, performance and compatibility. Read-derived from candidate 5's catalogues (core 0952306f7, migrations/candidates/postgres-{entries,treatments-socket-order,devicestatus}-v1.json) and the read paths; nothing here is measured yet.

    What the key must serve. Today's indexes show the access paths: entries by date (and dateString, sysTime); treatments and device status by created_at; v3 history by srvModified in every collection; identity through the unique (tenant_id, identifier) indexes and _id; tie order through the unique (tenant_id, insertion_ordinal) index. The evaluator window, v1 lists, reports and the tier and retention policy are all defined on clinical time.

    Clinical time as uploaded (date, created_at) Server receipt time (srvCreated) Normalized clinical time (leading option)
    What it is The collection's own time field, as stored When the hub received the record A clinical_ms column computed at write from the collection's time field, parsed to UTC; srvCreated when missing or unparseable
    Architecture: tiers and retention Matches the policy, but created_at is text with mixed spellings and offsets, so ranges do not partition cleanly Ages data by arrival. An imported five-year history, the expected path for migrating existing sites, would all sit in the newest partition, and a policy written in clinical age could not drop partitions Matches the policy; one numeric range per partition; imports land in the right months
    Performance: evaluator, lists, reports Prunes on date; created_at text filters prune unreliably No pruning for the main read paths: they filter by clinical time, which the database cannot relate to arrival Prunes. ORDER BY date DESC LIMIT n reads the newest partition first. A text created_at range maps to a safe numeric bound widened by the largest UTC offset (±14 h)
    Performance: writes Late uploads write into older partitions Every write goes to the newest partition Late uploads write into older partitions; uploads are overwhelmingly recent
    Performance: v3 history Scans srvModified on every attached partition Prunes Scans every attached partition. Tiering keeps that to a few (hot and warm); cold edits are promoted (5.4)
    Compatibility Visible behaviour unchanged; a stored-value edit moving a row between partitions is a delete and insert inside PostgreSQL Unchanged Unchanged; the column is internal and never returned. Odd values (string date, missing created_at) fall back to receipt time and stay readable

    Leading option: normalized clinical time, monthly ranges. It compares best on the three criteria above but needs a measured comparison before adoption (phase 2). It would come with: - a default partition that takes rows whose month is already cold (late uploads, imports into old months); the tiering job folds them into that month's bundle; - an identity table (tenant_id, collection, key) → clinical_ms keeping _id and identifier unique across partitions (about 172 bytes per document, measured in stage 2); - the insertion ordinal kept unique by its allocator; per-partition indexes need not be unique.

    Server receipt time is simpler and best for history, but it breaks the tiering policy for imported history and loses pruning on the paths that matter most.

    5.3 Index cut, first and independently¶

    Before partitioning, read pg_stat_user_indexes.idx_scan from a 1k run with the realistic mix and drop indexes never used, behind the existing end-schema comparison and API differential. Entries carries 15 indexes and 11 generated columns copied from MongoDB's list; generated columns alone cost 120–136 bytes per row (measured). Lowest risk, no layout change, and it benefits every tier.

    5.4 Cold: compressed monthly bundles¶

    When a month passes the cold boundary, a job writes each tenant's documents for that collection and month as one compressed bundle (zstd-compressed NDJSON or similar), with a small manifest of time range, counts and identities, and then detaches the warm partition once every tenant's bundle verifies. Scratch measurement of a similar layout: about 0.13 MB per tenant-day (measured, lane R).

    • Where bundles live. First in a PostgreSQL table, so backup, restore and row-level security stay as they are. Moving them to object storage (Spaces, or Cold Storage) is a later step that changes backup and access control, and is what takes the 600 TB case from impossible to about $4,000/month.
    • Reading. A v1/v3 query reaching cold months decompresses the months it covers and filters with mingo, already the query oracle under d8. Results and order match the warm path; latency is seconds. Very large ranges may run as jobs.
    • Edits promote. Editing or deleting a cold document copies it back to the hot table with a new srvModified and marks it superseded in the bundle's manifest. v3 history keeps working from the hot table (write-clock-history-arms).
    • Export and restore get cheaper: a tenant export of old data is a copy of its bundles.

    5.5 Summaries and detail retention¶

    What the ecosystem computes. The reports survey read the report and statistics code of cgm-remote-monitor (official/dev 79144cbd0), nightscout-reporter, Nocturne, nighttroop, AndroidAPS, Trio, LoopFollow, xDrip, xdripswift, nightguard and GlycemicGPT, against the 2019 time-in-range consensus, GMI and the AGP layout (read-derived and cited): - Spans. Users pick 1, 7, 14, 30 and 90 days nearly everywhere. cgm-remote-monitor's reports default to 7 days and cap at 186; xdripswift offers 365; nightscout-reporter compares a window with the same window up to 12 months earlier. The clinical standards work on 14–90 whole days with at least 70 % coverage. - cgm-remote-monitor computes every report in the browser from day-by-day API v1 reads; there is no statistics endpoint. Its low/in/high split uses a target the user types per request. - Persisted daily aggregates are rare: AndroidAPS and Trio keep insulin totals; nighttroop keeps a full per-day row (including a 288-slot glucose trace) rebuilt by a background job when writes mark a day stale. It is the closest prior art. cgm-remote-monitor's CGP pentagon already reduces each day to sums and merges days by addition. - Thresholds and weighting differ between tools (inclusive or exclusive band edges, count- or time-weighted, population or sample SD), so a summary must store raw ingredients, not finished percentages.

    Proposed summary row (one per tenant and local day, in the profile time zone; survey section 5): coverage counts and observed minutes; count- and time-weighted Σ and Σ²; a 1 mg/dL glucose histogram over 39–400; standard band minutes; the pentagon's AUC terms; per-day variability path sums; hypo episode counts; a 288-slot 5-minute glucose trace and per-hour sums; insulin and food totals per day and per hour; optionally 5-minute IOB and COB series. About 1.0–1.3 KB per tenant-day, about 2 KB with the loop series (estimated, not measured), about 1–2 % of a cold bundle; about 4–7 MB per tenant over ten years.

    From the summary row Statistics
    Exact Coverage and the 14-day/70 % sufficiency check; mean, SD (either form), CV, GMI, eA1c over any day range; every standard band and any user target band; pooled median and quartiles; GRI, LBGI/HBGI, ADRR; the CGP pentagon; daily and average insulin, basal/bolus split and carbohydrates; hourly means; calendar-aligned week, month and comparison periods
    Exact for 5-minute sensors AGP and time-of-day percentiles across days, from the 5-minute trace. With one reading per 5 minutes the trace holds every reading, so the result equals one computed from detail. Sensors that report more often keep one value per 5-minute slot, which can shift a percentile slightly; storing every reading per time-of-day bin would remove that at about 1–2 KB more per day, which this proposal does not take
    Needs detail Day-by-day charts (daytoday, weektoweek, reporter's daily graphics); loopalyzer's meal alignment; treatment lists and edits; calibrations; prediction overlays; audit and single-document reads

    The reports that need detail are viewed over 1–14 days and occasionally up to the 90–186-day caps, which is the hot and warm tiers, with cold reads at seconds beyond. Treatments are small and back several of them, so they are a candidate for longer detail retention than entries and device status (section 6), pending per-collection bytes.

    Rules for summaries: - Built from detail, before any deletion. Once detail is gone a new statistic or a fix cannot be recomputed; schema_version records what a row carries. - Stale and rebuilt when a backfill, an edit, a promoted cold document or a time-zone change touches the day. - Same deduplication as the reports (one reading per minute, values 39–600), so a summary and a detail read agree. - Both modes. The row is computed above the storage seam, so single-site MongoDB can build the same rows.

    Detail retention stays keep everything by default, matching the decision taken today for device status; section 6 sets out who may limit it. Summaries are derived statistics for reports, not dosing state; section 5.7 treats them as a cache of the statistics API, which this proposal reads as within d18.

    5.7 One statistics API for both modes¶

    Today every reader computes its own statistics from raw reads (survey sections 2–4). cgm-remote-monitor's reports run in the browser and fetch each day with up to three v1 calls, so a 90-day report is up to 270 requests returning every reading; nightscout-reporter, LoopFollow, xDrip and others each repeat the same work with their own band edges, weighting and SD form.

    Proposal: a standard, versioned set of report endpoints, served by both single-site MongoDB and multitenant PostgreSQL, with one statistics library in core behind them. Proposed shape (read-derived from the survey; names illustrative): - daily summaries over a date range: the section 5.5 statistics per local day; - period statistics for one or more ranges, for comparisons (bands, mean, SD, CV, GMI, GRI, percentiles, insulin and carbohydrate totals); - time-of-day profile (AGP percentiles) over a range.

    Parameters cover the variations the survey found: target range and band edges, count- or time-weighting, population or sample SD, time zone and day boundary. Defaults follow the 2019 time-in-range consensus. Read permission is the same as for the underlying collections. Raw v1 and v3 reads stay as they are; clients adopt the endpoints when their maintainers choose. Nocturne's analytics endpoints (period windows and comparisons) are prior art.

    Why it stacks with the other optimizations. The endpoint is the contract; what sits behind it can change without clients noticing, provided every step returns the same answer as computing from detail: 1. Compute from detail on request, in both modes. Fewer requests and less data transferred than today's per-day raw reads, and one implementation of every statistic. 2. Read per-day summary rows (section 5.5) for the days they cover, in both modes, falling back to detail for stale or missing days. 3. Tiers (multitenant): long ranges read summaries instead of decompressing cold bundles; detail is read only for the hot and warm days a chart shows. 4. Cache finished responses for repeated report views.

    Each step is gated by a differential against step 1 on a synthetic corpus. Because the endpoint computes from records with a shared library, storing summaries is a cache of that computation while detail exists, which this proposal reads as within d18; only after a detail-retention limit deletes detail do summaries become the only copy.

    6. Retention policy framework¶

    Retention today is one rule, "keep everything", and age-related settings are scattered: PREDICTIONS_MAX_SIZE, single site's devicestatus cleanup tool, DBSIZE_MAX, the deleted-tenant retention window. Tiering needs one model that covers every use case, so an operator and a tenant can reason about it in one place.

    Policy dimensions¶

    Dimension Values Example default
    Data class entries, treatments, device status, profile, food, activity; summaries —
    Hot boundary days at today's latency 14 days
    Warm boundary days served as ordinary rows 90 days
    Detail retention days, years or unlimited; after it, detail is deleted and summaries stay Unlimited
    Summary retention years or unlimited Unlimited

    Each dimension is set per data class. Device status (loop decisions and predictions) is the largest class and the one most often trimmed elsewhere; entries and treatments carry the long-range statistics.

    Who decides¶

    Three layers, each narrowing the one above: 1. Product floors and ceilings, fixed in code because something depends on them. The hot boundary covers at least the evaluator's window (about 60 hours) and a week of coordination. The warm boundary covers at least 14 days, the minimum period for a glucose profile report. Summaries are never deleted before the detail they summarise. 2. Operator limits per deployment: the range the tenant may choose for each dimension, and the default. This is where cost is controlled: an operator bounds hot and warm days and may cap detail retention. 3. Tenant choice within the operator's range, made by the owner through the owner settings surface. Changes are recorded in the existing owner settings history.

    Rules¶

    • Deletion by age is a setting. Detail is deleted by age only where a detail-retention limit is set, by the tenant within the operator's range. Changes are recorded in the owner settings history. Lengthening applies to data that still exists; deleted detail does not come back. Notices and export prompts need a user interface, which is out of scope.
    • Same model in both modes. Single-site MongoDB maps the same settings onto its own mechanisms (a scheduled delete with summaries kept) so the behaviour matches; tiers are internal to multitenant storage, latency aside.
    • Inactive sites. A site that stops uploading keeps its history under the same policy. Removing whole inactive tenants stays a lifecycle decision (deletion, export, key retention), not a retention setting.
    • Clinical age, not arrival. Every boundary is measured in the record's clinical time (section 5.2), so an imported history is tiered as it would have been had it arrived live.

    7. Plugins and alternatives evaluated¶

    Option What it is For Against Verdict
    Native partitioning Built into PostgreSQL No new component; works with row-level security; available everywhere No global unique index; partition creation to schedule Proposed (5.1)
    pg_partman Extension that creates and drops partitions Mature, saves writing the scheduler Another component; not available on DigitalOcean Advanced Edition (vendor-documented) Optional
    TimescaleDB Extension: time-chunked "hypertables", compressed columnar old chunks, retention policies Exactly the hot/cold pattern; typically large compression Row-level security is not supported on compressed (columnstore) chunks (vendor-documented), against d3. Compression is under the Timescale License: free when not offering TimescaleDB itself as a hosted database (licence); some operators would need a licence reading. Listed only for DigitalOcean Standard Edition, not Advanced (extensions). Unique indexes must include the time column, as with native partitioning Not proposed. Revisit only if cold data is served through a narrow, audited function rather than row-level security
    Citus Extension that spreads tables across worker nodes by tenant_id; also a columnar format Built for tenant-keyed SaaS; row-level security on distributed tables since 11.0 (vendor-documented) A multi-node database cluster to operate; not on DigitalOcean managed PostgreSQL; our triggers and write clock need requalifying; columnar is historically append-only. Solves a single-node limit we have not measured: hot and warm at 10k × 90 days is about 1.5 TB at today's layout, much less after cuts Not now. Several independent deployments, each with its own database and placed by the tenant registry, scale out with no new software
    Columnar extensions (pg_duckdb, pg_mooncake, pgEdge ColdFront) DuckDB or Iceberg/Parquet beside PostgreSQL Analytics and cold data in object storage Young; ColdFront announced June 2026 inside a vendor distribution; pg_mooncake mirrors rather than moves data Watch
    Filesystem compression for cold partitions A tablespace on a compressed filesystem No schema change; ~4.5× (measured proxy) Node-level setup on Kubernetes; disk only Possible stopgap for warm partitions
    MongoDB for multitenant Single-site's store Compresses well No database-enforced tenant isolation Excluded by d3

    8. Plan¶

    Each phase is one lane with its own gates; performance results are signals (performance-signals-not-gates) and correctness gates stay strict.

    Phase Work Gate
    0 — first production boundary Accept today's volume. PostgreSQL on its own node with memory for the hot set. Size volumes for the admitted retention (90 days to 1 year). Keep everything. The paid 5k/10k run on the qualified candidate
    1 — index cut idx_scan from a realistic 1k run; drop unused indexes End-schema comparison and API differential red then green; bytes and latency signals before and after
    2 — time partitioning Compare the partition keys of section 5.2 on device status, then partition entries and treatments; identity table; warm index set; partition creation in admin Key comparison on the same reads and writes; contract differential against official/dev; evaluator window, v1/v3, resend and lock hold at 1k and 10k; export and restore round trip
    3 — cold bundles Tiering job, manifest, cold read path, edit promotion; bundles in PostgreSQL As phase 2, plus cold reads equal warm reads; an interrupted tiering job leaves every document readable once
    4 — statistics API, summaries and retention options The statistics API computing from detail (section 5.7; can start any time, both modes), then summary rows (section 5.5), retention settings (section 6) and bundles in object storage Report statistics from summaries equal the same statistics from detail on a synthetic corpus, for the exact set in section 5.5; maintainer decisions in section 9

    Phases 1 and 2 also improve latency at 10k independently of cost.

    9. Maintainer direction and open questions¶

    Direction, 2026-11-24 (maintainer; shapes this proposal, adopts nothing): - Relaxed latency for data older than about 90 days: probably acceptable, given a holistic retention framework across the use cases (section 6). The 90-day boundary is configurable: the tenant sets it within operator limits. - Hot and warm boundaries: the tenant sets them within operator limits (section 6, "Who decides"). - Summaries: the statistics to keep need an analysis of the report definitions used across the open-source ecosystem and Nightscout's built-in reports. Done in the reports survey; the resulting row is in section 5.5. - Partition key: normalized clinical time is a potential option when compared against the alternatives (section 5.2); it is measured against them in phase 2 before a choice. - Automatic deletion by age: unclear whether to build it; if built, the tenant chooses within operator limits (section 6). - Notice before deletion: not in scope; there is no user interface to deliver one (section 6, rules). - Summaries and d18: produce the same statistics optimizations for both modes behind a standard set of report endpoints, so reports reuse one implementation instead of per-reader logic (section 5.7). - AGP fidelity: settled in section 5.5 (the 5-minute trace is exact for 5-minute sensors).

    • Deletion by age: may be deferred, for example past the initial production release; first see every lever with its trade-offs and priority (section 10).
    • Statistics API placement and first clients: unclear, needs more research; deferred and out of scope for now.
