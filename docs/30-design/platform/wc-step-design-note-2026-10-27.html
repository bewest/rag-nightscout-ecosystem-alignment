    WC-STEP-PATCH: mapping the write step onto dev db3b9e4e¶

    Record

    Record as of 2026-10-27. A point-in-time document; it is not kept up to date.

    Contributor-facing design note, milestone 1 of WC-STEP-PATCH (decision Q6 (a), first release: the step with today's write matrix pinned, no behaviour change). Written 2026-10-27 against cgm-remote-monitor official/dev db3b9e4e (the merge of #8872). Every claim carries a mark: [M] measured in this milestone (commands in §7), [R] read from source at db3b9e4e, not run. file:line is at db3b9e4e unless it names the branch feat/write-intent.

    The specification is docs/30-design/tenancy/write-contract-spec-2026-10-07.md (§2 the step, §5 gates, §6.1 decisions). It was written against 43289dde, before the storage seam landed. This note says where its pieces are now, and what the step has to do on the code as it is.

    0. The rule, and the gate that holds it¶

    Decided 2026-10-27 (maintainer): a new write rule goes into lib/storage/write-intent.js, not into a route. This applies from now on, before every collection is enrolled. §3 below lists the copies that already exist outside any step; the slices move them in.

    Two gates hold it:

    • G2 (scripts/check-write-intent.js on the branch): an enrolled module writes only through write(intent). Its coverage grows as each slice enrols a module.
    • Write-rule copies (tools/queue/gates/write-rule-copies.js, control write-rule-copies-control.sh): for seven rule modules (merge-patch, the BF-194 units helper, write-validation, validated-update, srv-dates, object-id-forms, the treatment fallback key), it counts the lines in each other file under lib/ and bin/ that use the rule. It fails on a new (rule, file) pair or a grown count against write-rule-copies.baseline.json. The baseline was measured on dev db3b9e4e: 47 pairs. On feat/write-intent (slice 1) it reads 45: food's srv-dates and object-id-forms copies are gone. The count can only go down; the baseline is re-written after a slice moves a copy into the step, never to make a failure pass.

    Progress, 2026-10-27 late. Slices 1-3 are built on local feat/write-intent (2b9d3687, 84e21a66, f0d51ee7, a0e7fcac), each with G1 at 0 of 360 cells. The slice list below is revised: slice 3 covers the socket's generic dbAdd (entries, food, activity) and dbRemove (all six); a new slice 6 takes the socket's dbAdd for treatments, devicestatus and profile (the near match, WRITE_VALIDATION, BF-194, the refused/failed slots) plus dbUpdate/dbUpdateUnset, retiring idMatch (new question Q-I: until then the step's id-match duplicates it).     Release-1 answers (maintainer, 2026-10-27).     Maintainer, 2026-10-29. Slices 4 and 6 are released. Slice 6 has an extra gate, because its rules decide whether a treatment is a duplicate (websocket.js:743-860): a wrong move would drop a real second bolus or carb entry, or store a re-send twice. Each rule needs a fixture that keeps today's result and an ablation that goes red: exact NSCLIENT_ID and fallback-key (BF-121) match, the 2-second similar match at its edges, each BF-09 zero case, a different eventType being a second record, soft-deleted records never matching, the similar match setting only created_at and srvModified, and WRITE_VALIDATION reply slots. Any difference is stop-and-report. On slice 4: as built, it keeps v3 writing by identifier through the cached wrapper (mongoCachedCollection), which updates or removes only the record written, so it adds no cache flush and no MongoDB load. Q-A for release 2 is open, with research continuing, on the maintainer's proposal: instead of the full flush a query-based write causes today (a remove with no ids empties all three caches, lib/server/cache.js), the step would read the collection back from a srvModified watermark. This rests on three things on dev. Every server write path stamps srvModified (since 718efddc, in 15.0.9). srv-dates.js issues those values in increasing order. Every v3 collection indexes the field (mongoCollection/index.js:147-150). The record's own time (date, created_at) cannot serve as the watermark: it is the event time a client set, so late uploads, edits and future-dated clocks would be missed. Hard deletes leave nothing for the watermark to find, so they keep reading ids before the delete. Single-tenant Nightscout supports writes to MongoDB only through its own APIs (maintainer, 2026-10-29), so every write the catch-up must see carries srvModified. A since-watermark arm is to be added to the D-EVENT bench (tools/lab/commit-event-bench).

    Cache lab, 2026-10-29 (tools/lab/cache-value, dev e1f7ac41; 3 real hours, 5 parallel arms). The cache cuts bytes returned by MongoDB about 32 times: 2.0 MB an hour against 63.9 MB bypassed. Operations barely change. Without the cache, the modelled site exceeds MongoDB Atlas M0's published transfer limit of 10 GB per 7 days; with it, the site uses 3.3 to 3.7 % of that limit. Pool size 5 against 100 made no latency difference. This supports keeping the cache for single (D4), and it makes Q-A's watermark catch-up, which avoids full reloads, worth building. The lab also reproduced the over-broad flush, BF-211.

A soft-deleted profile is matched, and so revived, by a socket dbAdd with the same NSCLIENT_ID or startDate (same on 15.0.9): Q-R, release 2. Measured on dev e1f7ac41 with an AndroidAPS-shaped profile (AndroidAPS 3.4.2.6's v1 NSClient sends startDate, never NSCLIENT_ID). It is reachable only by a sequence no app was found to start. The profile must be soft-deleted through API v3 (the profile editor and every v1 path delete hard, and no client in the corpus calls the v3 profile delete). Meal grouping belongs in the display layer.

    A side finding: the chart-drag split (treatmenttime.js splitRecord) keeps the original's client identity on the new half. This is reproduced on dev e1f7ac41 (probe probe/split-ident-2026-10-29 95570d41, local, with a control). Two stored records then share one syncIdentifier or identifier. API v3 lookups and dedupe resolve to the new half. A v1 upsert by identifier replaces the original but replies with the new half's _id. Separately, and also with the identity removed: a full re-upload of the original by the client that still holds it writes the moved insulin back, so the insulin appears twice. Not run on 15.0.9. The maintainer's direction: editing is mainly for fixing broken records, so a lossy edit of a record that an automated controller claims (one with a client identity) should need an extra manual confirmation. Filed as BF-212 in the backfix register.

    1. Placement: two layers, not one¶

    The spec (§2.1) puts write(intent) in lib/storage/write-step.js, "applied in collectionFor above both adapters". On db3b9e4e that file name is taken by a different layer, and collectionFor does not exist.

    What exists [R]:

     lib/server/{entries,treatments,devicestatus,profile,food,activity}.js   (API v1 + in-process)
 lib/server/websocket.js  dbAdd / dbUpdate / dbUpdateUnset / dbRemove      (socket)
 lib/api3/generic/{create,update,patch,delete}                             (API v3)
          |                                   |
          |  lib/server/storage-writes.js     |  lib/api3/storage/mongoCachedCollection
          |  (v1 query doc -> filter AST)     |  (cache events, then delegates)
          v                                   v
 lib/api3/storage/mongoCollection  = THE STORAGE INTERFACE (one per collection and source label)
   writes: insertOne, insertMany, replaceOne(identifier), updateOne(identifier), deleteOne,
           updateEveryForm, deleteEveryForm, deleteManyOr, deleteMany(ast), updateMany(ast),
           replaceFiltered(ast), bulkUpsert(ops)
          |
          v
 lib/storage/write-step.js  = THE PERSISTENCE BOUNDARY: a Proxy over the driver collection;
   one driver call -> one `storage-write-committed` event; socket treatment validation;
   the conditional validated update (compare-and-set) for treatments in reject mode
          |
          v
 MongoDB driver collection
    • The storage interface is MongoCollection (lib/api3/storage/mongoCollection/index.js:20-101). Its writes are listed at index.js:68-100; each is handed col, the write-step proxy (index.js:43). API v1 and the socket acquire it through lib/server/storage-reads.js:34-37 with a source label (MongoCollection.SOURCES, index.js:140-145: v1/internal, v3, socket, internal). API v3 reaches it through mongoCachedCollection (lib/api3/storage/mongoCachedCollection/index.js:10-159), which adds cache data-update emissions around the same methods. [R]
    • lib/storage/write-step.js is below the interface: collection() (write-step.js:96-107) wraps the driver collection; write() (write-step.js:70-94) makes one driver call and publish() (write-step.js:57-68) emits storage-write-committed once per call. [R]
    • The next-gen plan already records the naming decision: "the intent layer gets its own name" (next-gen-platform-plan.md:45) [R].

    So the step is a second layer, above the interface. In feat/write-intent it is lib/storage/write-intent.js. It calls only storage-interface methods, never the driver, and it emits nothing; the commit event stays exactly where #8854 put it. Nothing in this milestone changes write-step.js or the event (D-EVENT is deferred, and session -2e's crm-devent-* trees prototype that change).

    Adapter methods the step calls, against the spec's seam list (§2.1: findFiltered, insertMany, bulkUpsert, replaceFiltered, updateMany, deleteMany) [R]:

    path today interface methods it writes with in the seam list?

    socket (websocket.js) insertOne (websocket.js:784-787), updateMany and replaceFiltered and deleteMany via storage-writes insertOne is not
    API v3 (api3/generic/*) insertOne, replaceOne(identifier), updateOne(identifier), updateEveryForm, deleteEveryForm (create/insert.js:40, update/replace.js:46, patch/operation.js:116, delete/operation.js:60,87), all through the cached wrapper none of these

    Slice 1 (food, v1/in-process) calls findFiltered (through srv-dates carryForReplace), bulkUpsert and deleteMany: all in the seam list. Bringing the socket and v3 paths in either keeps two method families under the step, or re-expresses v3's identifier-addressed writes as filter writes, which changes the driver calls and, for v3, the cache events of mongoCachedCollection (its five filter methods reload the whole cache, index.js:147-159). That is question Q-A (§5).

    2. Where each rule of §2.3 lives today¶

    Paths: v1 (API v1 routes), in (in-process callers: the same lib/server/<col>.js module as v1, under the same v1/internal label), ws (socket), v3. All [R].

    Rule 6, one change event. There is no step-level change event. What exists: per-path data-update emissions (15 write-side processRawDataForRuntime calls in treatments.js, entries.js, devicestatus.js, websocket.js; the cached wrapper's forCache, mongoCachedCollection/index.js:184-200); v3's storage-socket-* emissions (insert.js:55, replace.js:67, patch/operation.js:125, delete/operation.js:70,96); per-path data-received; and, below the interface, storage-write-committed once per driver call. v1 food and activity emit no data-update at all [M: the baseline matrix, food and activity v1/in columns, ev –].

    4. Proposed slicing¶

    Every slice holds G1 (the matrix equals the pinned file, apart from the known racy cache field) and npm test equal to baseline plus its own tests, and runs node scripts/test-tiers.js check: a new test file is in no tier until tests/tiers.json names it, and test:all then silently skips it (slice 1 hit this; fixed in 84e21a66). Every slice that moves a rule re-targets the matching ablation of write-contract-ablate.sh at the step and shows it red.

    1. Slice 1 (built, feat/write-intent): food, API v1 + in-process. write(intent) and WriteResult.items[] in lib/storage/write-intent.js; lib/server/food.js writes only through it. Rules moved: _id form (both of today's spellings, create and save), target by _id, carryForReplace server dates, string-twin removal, the bulkUpsert/deleteMany call. COLLECTION_RULES is keyed by collection and source label, holding today's per-path rules (not the spec's §2.2 target table, which is release 2). G2 check scripts/check-write-intent.js with ENROLLED = ['lib/server/food.js'].     5. Contradictions and open questions for the maintainer¶

    The step has to pick a side on each of these. Picking would change a matrix cell or an emission in every case marked (cell), so none is picked here; slice 1 keeps each path as it is.

    • Q-A, two method families. The spec's step calls only filter methods (§2.1); v3 writes by identifier through the cached wrapper (table in §1). Re-expressing v3 as filter writes changes the driver calls and the cache behaviour (the wrapper reloads the whole cache after any filter write, mongoCachedCollection/index.js:147-159) (emission: data-update changes from update with docs to remove with no changes). Keep both families under the step for release 1, or accept the cache change?
    • Q-B, twin removal timing. Spec rule 5: "directly after the write it belongs to (BF-130)". Code: food, activity create and treatments batches append one deleteMany after all replaces in the same ordered bulk write; treatments/profile/activity save make a separate driver call. Unifying changes the number of storage-write-committed events per request (not a matrix cell, but an emission the brief forbids changing). Which form is the rule?
    • Q-C, v1 and in-process share one label. The spec's origin.path distinguishes v1 and internal; on dev both write as v1/internal (index.js:140-145) through the same module, and the module cannot tell them apart. Is that distinction needed before release 2? Adding it changes the commit event's source value (D-EVENT territory).
    • Q-D, _id rule on a PUT/save with a non-hex id (cell, in-process only). v1/in-process food and activity save turn a non-hex _id into a fresh ObjectId (food.js:28-34), i.e. a "save" of a custom-id record inserts a new record; create keeps the custom id (toStoredId). The spec's rule 1 says a non-hex string keeps today's per-collection rule; the per-op difference inside one collection is not mentioned. The v1 route refuses non-hex ids with 400 before this (api/food/index.js:92-96), so only in-process callers reach it. Slice 1 keeps both spellings as named rules (objectid-or-new, stored-or-new).
    • Q-E, identical re-send outcome (cell). Q2 decided (b1) "status quo per path". In the step's vocabulary, today's v1 food re-send is replaced (srvModified advances, [M] baseline food v1 resend-hex C=M+), the socket's is a refused insert (empty, C=M=), v3's is 400 (BF-170). Slice 1 labels the v1 one replaced. Confirm that unchanged is reserved for release 2 and that labelling today's no-ops does not count as a behaviour change.
    • Q-F, WRITE_VALIDATION has two homes. The plan row says validation moves into the step; part of it already sits below the interface (write-step.js:27-42, the conditional update at write-step.js:79-86), and moving it up would move code out of the file whose publish() the D-EVENT prototypes rewrite. Should validation's lower half stay in the persistence boundary (it is the compare-and-set), with only the above-interface checks (treatments.js:43-58, websocket.js:685, operationTools.js:100-112) moving into the step?
    • Q-G, the spec's §1.3 table is stale. Against the spec's own result file (tools/qc/results/write-contract-matrix/dev-43289dde.json) the db3b9e4e baseline differs in 65 cells [M] (BF-170's v3 400s, #8859's profile merge, devicestatus identifier rule, BF-194, and MongoDB 7 vs 8 under the harness). G1 for this work pins db3b9e4e, not the spec's file; the spec's tables should be re-generated before release 2 decisions cite them.
    • Q-H, the step's name for "create" on v1. v1 POST for food and activity is an upserting replace by _id, not a create; treatments' is a replace by natural key. The intent says create; the rule table says onMatch: replaced. The spec's create + near vocabulary fits; noting only that create on v1 has always been allowed to replace.

    • The order of driver calls and their exact arguments: covered for slice 1 by a unit test that runs the pre-move food.js logic and the step over the same recording driver and compares the calls and the commit events (tests/write-intent.test.js).
