    Next-gen platform: one write path, four tracks¶

    Living document, last changed 2026-11-07 at c3cf4d1d7.

    Contributor-facing living plan. Tenancy reconciled 2026-11-06 to R62 and R64: draft #8898 is 83582e87, based on dev 4a482627, with CI and CodeQL green on that head. R67/R68 add bounded local component evidence. Earlier storage, identity and registration measurements retain their named pins. Current milestone claims live in the delivery dashboard; release placement lives in release allocation.

    The interactive version, with the dependency map, is the site page nightscout-next-gen-platform.html.

    This plan covers the work that follows the 16.0.0 modernization:

    • storage behind one write path;
    • the client and server identifiers Loop asked to separate;
    • controller registration, from a read-only catalogue to typed writes;
    • multitenant Nightscout.

    It names each piece of work, what it needs first, where it goes in the code, and the check that pins it.

    1. 16.0.0 scope (maintainer, 2026-10-30)¶

    16.0.0 targets every single-tenant item of this plan, through the entry bar and in priority order. A miss rolls to 16.1.0, or to 17.0.0 if it changes a default. - The identity work is the core. It is the substance of the agreement with the Loop maintainers: identifier-first on every path, re-sends recognised, the format rules, and one record per identifier. - The unique index on identifier is in 16.0.0, behind WRITE_IDENTIFIER_INDEX=try|require|off|drop (default try). - Under try, boot attempts a partial unique index per collection: records with an identifier, soft-deleted ones included, built online. If existing duplicates block it, the counts per collection (never the values) are logged and shown on the status page, and the server runs without the index. - The write rule (ID-Q5) still refuses to create a second record with a stored identifier. - require refuses to start until the index exists. off skips building it but leaves any existing index enforced; drop removes the index at boot, then runs as off. - An operator-run tool reports duplicate groups and resolves them by the P4 pick. - Multitenant items may ship dormant, labelled alpha behind explicit multitenant configuration, or not ship.

    Feasibility, from the 7 days to 2026-10-30: 53 PRs merged into dev, and 14 of this plan's 36 items went to done. Build speed is not the limit. Time on dev, cohort checks and review are, so items land in priority order and early, and the tag is gated by the bar, not by a date.

    2. Why the tracks meet at the write step¶

    Every track changes what happens when a record is written:

    track what it needs from the write step
    Identity a single place that matches a re-sent record on identifier first, then on the time key, for v1, v3 and the socket alike
    Registration a single place that applies a controller's declared schema to its typed writes, and leaves unregistered writers byte-identical
    Validation a single place for #8841's rules, so the socket and the v1 modules are not checked separately
    Tenancy a single place that carries the tenant binding, so no path can write without one

    8854 built that place as a boundary at the driver call, and the storage interface sits above it. Each later slice adds one rule there. Every slice must keep the following:¶

    must hold pinned by
    the _id forms: ObjectId, upper- and lower-case hex, UUID, and UUID_HANDLING moving a non-hex _id to identifier #8854's matrix rows; tests/identity-matrix.test.js
    the API v3 create and deduplication reply (status, identifier, isDeduplication, lastModified), and AndroidAPS's string-matched refusal texts tests/write-validation.test.js; the v3 suites
    Loop's syncIdentifier and Trio's id stored and returned untouched write-contract matrix
    v1 treatment upsert on created_at + eventType write-contract matrix

    The forward constraints are two mature backends behind one interface (D2–D4), the closed query operator set as a filter tree (D8), a source label and later a tenant binding on every write, and one commit fact the change feed can carry (D6; D-EVENT decided 2026-10-31: one in-process event per write, named from WriteResult.items[], and the per-database-call event kept as backend instrumentation; delivery between processes is decided with the serve roles; its card in §5). Under #8854's merge conditions, the commit event stays internal and unstable, and the intent layer gets its own name. The later B7 recovery direction uses a durable feed and the adopted bounded full current-state snapshot backstop; the time-only alarm tick remains separate from that reconciliation schedule.

    Rules in force (maintainer, 2026-10-26 and 2026-10-27; updated 2026-10-31):

    • Null removes. An explicit null removes a field on a merged re-send (WRITE_RESEND=merge), API v3 PATCH and the socket's dbUpdate (RFC 7386; write contract §6.1). It never does so on PUT or create, and devicestatus never merges.
    • Fallback. A v1 entries re-send whose identifier matches nothing still matches on sysTime+type; treatments never fall back. A devicestatus re-send whose identifier is stored replaces the stored record by default (compatibility B, 2026-10-31; it merged from ID-Q2, 2026-10-29); WRITE_RESEND=merge keeps that, and WRITE_RESEND=acknowledge the rule before it (write nothing, answer with the stored _id).
    • Absent identifier. identifier is SHOULD for legacy writers, and the time-key fallback stays. It is MUST for registered controller instances. Revisited as adoption grows.
    • Scope. Uniqueness is per collection, with the tenant in the key under multi. Values stay globally unique by convention.
    • Re-send after delete. It is acknowledged with a 2xx naming the stored, deleted record, and the record stays deleted. WRITE_DELETED_RESEND=revive (default stay, 2026-10-31) restores 15.0.9's re-send that revives a deleted record.
    • Format (2026-10-29, D-LOOP-ID rule 1 and ID-Q6). Any string of 1 to 256 characters, with no character restriction, percent-encoded in a URL path; a UUID is recommended. A placeholder or over-length value is treated as absent with a warning; refusing it is WRITE_IDENTIFIER=strict, off by default. 2026-10-31 (compatibility A): API v3 refuses a malformed identifier with 400 by default, as 15.0.9 did; API v1, the socket and in-process stay lenient. Which placeholders are named is open (ID-PLACEHOLDER-LIST, identity specification §5).
    • _id (2026-10-29). A client may still send an ObjectId _id over API v1 (legacy). Going forward the server sets _id and the client sets identifier.
    • Replace on match (2026-10-31, compatibility B; supersedes merge on match of 2026-10-29). A re-send matching a stored record replaces it on every collection, as slice 4 does for treatments. Extended the same evening: every re-send matched by identifier replaces on every path, including the identifier-first matches for profile, food, activity and device status over v1, in-process and the socket; entries over v1 and in-process keep merging, as on 15.0.9. Merge stays for edits: API v3 PATCH and the socket's dbUpdate. WRITE_RESEND=replace|merge|acknowledge|refuse (default replace) and WRITE_DELETED_RESEND=stay|revive (default stay) are built before the tag as opt-in ways back, parsed with the other WRITE_* settings; per-client D20 quirks may select a WRITE_RESEND mode. Each path that changes is listed cell by cell.
    • Re-send after delete, every path (2026-10-29). "Acknowledged, stays deleted" applies on every path, and the spec text is corrected. Every changed cell is documented, so the change can be reverted or adjusted as cohort feedback arrives.
    • Records without an identifier. Natural keys for device status and profile are a separate item, ID-NATURAL-KEY, with its own corpus check of what would merge. Food and activity have no natural key.
    • Socket edits and removes, and activity. Identifier addressing is added where it changes nothing for writes that carry no identifier: socket dbUpdate, dbUpdateUnset and dbRemove accept an identifier when there is no _id, and activity creates match on identifier. This is conditional on the extended matrix showing every existing form unchanged.
    • Re-send with changed fields (2026-10-29). Merge on match stays the default, because Loop and Trio re-send changed doses, overrides and temp targets by POST (client survey). API v3 keeps refusing a changed date, device or event type, and PUT replaces. A site setting plus per-client quirks (D20) may opt a client into keep-first or refuse. A default changes only in a major: 16.0.0 if it clears the entry bar (§1a), otherwise 17.0.0.

    The rules are in the identity specification and the identifier conventions; the conversation with the Loop maintainers is in upstream-asks-loop-identifier.

    6. How the work moves¶

    • Pull requests. Sized by milestone, not by slice: the single-tenant registration PR (S0, S1, S2, S5); storage slices grouped into few PRs. A track with many pieces in flight uses an integration branch with child PRs, the way #8605 carried 109 children. Dev is merged into a branch, not rebased, and a PR's merge records that the merged tree matches the reviewed tree.
    • What pins behaviour. #8854's CRUD matrix and this repository's write-contract matrix (tools/qc/write-contract-matrix.js; v1, v3, socket and in-process). A slice that changes no behaviour changes no cell; a slice that changes behaviour lists the cells it changes and why.
    • Red controls. Every new test is shown failing against the code it guards before the change, with the original symptom.
    • Conformance. The registration and identity cases in specs/sync/conformance/ run against a booted server by a harness in this repository (D12), reported case by case as passed, mapped or not applicable.
    • Agents. Agents build slices in their own worktrees, run the checks and hand back a branch, a PR body and the push commands. They never push. Maintainers push, open, review and merge.
    • Releases. #8865 (one executable, the image's start and stop, the boot split; multitenant is the current namespace after #8899; only the explicitly configured API preview is implemented in #8898) merged into 16.0.0 on 2026-10-30. Since 2026-10-30 every single-tenant item of this plan targets 16.0.0 through the entry bar (§1); a miss merges after the tag, one theme per minor; the 16.0.0 quiet period starts when its merge list is closed, not on a date. Components shipped before they are mature are labelled alpha; the label belongs to the multitenant bindings, not to code every single-tenant site runs.
    • Records. Each landed slice updates its queue item (queue/work-queue.yaml) and this plan's data file, and the page is re-rendered.
