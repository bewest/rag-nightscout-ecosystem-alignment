    Platform contracts: where each piece is specified¶

    Living document, last changed 2026-10-18 at 8d2b93ede.

    Contributor-facing. Living index, current at main 5a9a49cc (2026-10-18). Terms are defined in the platform glossary.

    This page maps the work on how controllers (Loop, Trio, AndroidAPS and others) and hubs (cgm-remote-monitor, Nocturne) agree on what records are, who wrote them, and how they move. The aim has three parts:

    • Full audit fidelity. Every stored record says what it is, which copy of which controller wrote it, under which definition, and whether it was requested, applied, mapped or projected.
    • Controller-owned definitions, secured. A controller declares its own typed definitions. The hub accepts them per element, binds them to the credential that wrote them, and never lets one controller redefine another's data.
    • Cost-effective sync. Fewer requests per cycle with typed records, REST for writes and catch-up, a socket for live delivery, and versioned definitions so a new release does not need a full re-sync.

    The material is organised in six layers. A lower layer never depends on a higher one.

    layer question it answers depends on
    L0 Identity Which record, definition, instance or subject is this? —
    L1 Records What typed observations exist, and how are today's documents decomposed into them? L0
    L2 Definitions and instances Who declared what a record means, and which running copy wrote it? L0, L1
    L3 State and intent What was requested, what was applied, what is active now, and why did it end? L1, L2
    L4 Change and sync How are writes matched, re-sent, ordered and delivered over REST and the socket? L0–L3
    L5 Authority Who may register, write, route a command or act for someone else? L0, L2

    Audit fidelity is not a separate layer. Each layer's section below lists what it records for audit.

    Status words used here. Evidenced: measured or read from source in the corpus or controller code. Specified: a contract with synthetic conformance cases and a reference decision function in tools/nsschema/, which checks the cases but is not a hub. Implemented: a hub serves it. On 2026-10-18, no hub implements any L2, L3 or L5 contract on this page.

    Evidence identifier format (UUID not required; constraints C1–C7); identifier duplicates; Loop identifier ask

    Audit the composite document is kept beside its decomposed records, so "what did the device send" stays answerable

    Schemas, cases specs/sync/controller-state-model.schema.json, hub-capabilities.schema.json, registration-submit.schema.json, controller-instance.schema.json; generated registrations in specs/sync/registrations/; 54 cases in specs/sync/conformance/, 103 in conformance/instances/
    Decisions D18 and its addendum; D19
    Open SPEC-REG-MODES, SPEC-REG-MIGRATE; implementation HUB-REG-CRM, HUB-REG-CRM-SEAM, HUB-REG-CRM-ADMIN; adoption HUB-REG-NOCTURNE, PROPOSAL-REG-CONTROLLERS; §3.7's choices 2, 3, 4, 6, 7, 9, 10, 11 and 12 await the maintainer
    Audit every typed record carries its instance, its definition id and its role's provenance; projected documents carry projectedFrom; records are attributed to the registration and its bound credential, never to a namespace string
    Status specified

    L3 State and intent¶
    Spec today stateSpans in hub-sync §3.1 (slot, states, end reasons, wire carrier, requested and applied, initiators, composition, acceptsFromHub); slot sharing and sameAs in §3.6 and §3.7 rule 2
    Evidence intent and workflow landscape (per-controller matrix, end encodings, how each hub decides what is active, command lifecycles); effects and versioning (effect separated from motivation); authority model
    Schemas specs/sync/controller-state-model.schema.json (stateSpans, composition, commands); specs/sync/shared-slots.yaml; specs/sync/therapy-effect.schema.json; specs/sync/effect-remapping.yaml
    Open iAPS has no registration; end-reason vocabularies for Trio override and temporary target and for AndroidAPS profile switch, AndroidAPS initiator values and every command vocabulary are undeclared (landscape §10); LAB-TRIO-INTENT
    Audit requested and applied are recorded separately; each span records its end reason and initiator in the controller's own vocabulary; composition is recorded as the controller reports it, never computed by the hub
    Status evidenced and declared in the generated registrations; LAB-HUB-ACTIVE-STATE measured cgm-remote-monitor and Nocturne disagreeing on what is active for the same records (landscape §5)

    L4 Change and sync¶
    Spec today write contract §2–§3 (one write step, the re-send rule, every path's writes reaching the storage socket); hub-sync §3.2 (cursor envelope and batch write); replay-fidelity proposal §1 (one history read across collections on API v3); §3.5's fallback and load-versus-definite refusal rule; D6 (the change feed under multi)
    Evidence hub-sync §2 (make schema-sync-cost: up to 5,760, 2,016 and 1,440 requests a day for AndroidAPS, Loop and Trio against 576 for two requests a cycle; source-derived upper bounds, not traffic); the write contract's measured matrix
    Open WRITE-CONTRACT, WC-STEP-PATCH, ID-BATCH-RESULTS (blocked). Not specified anywhere: socket delivery of typed records, cursor semantics under concurrent writers, and migrating stored typed records when a definition changes version (rule 4 of the D18 addendum converts nothing without a declared mapping)
    Audit one change event per write call; a matched re-send stores no second copy and is answered with the stored ids; each mapping the hub applies is recorded as quirksApplied
    Status the write matrix is evidenced; the write step is specified; the typed sync transport is not

    L5 Authority¶
    Spec today binding, credential kind, owner actions and the block state in hub-sync §3.5; roles, provenance, command-sink binding and command routing in §3.6
    Evidence agent trust boundaries (develop, interpret and act; a proposal lifecycle, proposed and not specified); configuration and delegation §5 (what a delegation design must provide); control-plane reconciliation; authority model
    Decisions D13–D17 (credential root, listeners, auth plane; D17 row 2 open)
    Open SPEC-REG-COMMANDS (the command API itself is not specified); delegation of a principal's authority to a caregiver, app or agent, and proposals awaiting approval, are not specified
    Audit the owner's listing shows every product's binding, credential kind and binding event, every instance's roles and liveness, and every overlap
    Status specified for registration and routing; not specified for commands and delegation

    Reading order¶

    For someone new to the series: this page, then the glossary, then intent and workflow landscape §2 and §9 for why the contract exists, then hub-sync §3.5–§3.7 for the contract itself.

    Planned layout¶

    Each layer's living specification has, or will have, its own undated file under spec/: identity is written; registration, state-intent, sync-transport and authority are queued as SPEC-REGISTRATION, SPEC-STATE-INTENT, SPEC-SYNC-TRANSPORT and SPEC-AUTHORITY. The dated documents above stay where they are as snapshots, and each moved section leaves a pointer to its new home.
