    Reply to the Loop developers' identifier proposal¶

    Living document, last changed 2026-10-29 at f3a1d540d.

    What this is: an outreach draft (contributor-facing). Read after the identity specification; leads to the device-simulator requests. Status: posted 2026-10-27 as an update on this page (the maintainer's choice of channel); the reply is reply.body.md. Queue item LOOP-ID-REPLY. Facts first checked 2026-10-17 at cgm-remote-monitor 15.0.8 (92d08342) and dev fade2299; the reply re-measured 2026-10-27 at 15.0.9 (c6a0d8ed) and dev 7abe1cf6; Loop at LoopWorkspace 548b332 (NightscoutService 2cef489, LoopKit d9f1437) and NightscoutKit 4ec9fd1, from this repository's 5a6cef4d. Each project's maintainers decide what, if anything, to do.

    Update, 2026-10-27¶

    Our reply is posted here as an update, re-measured on 15.0.9 and 16.0.0's dev: the gap the first draft described (v1 entries and device status ignoring identifier) is closed for 16.0.0, and our defaults for a re-send after a delete (case 4) and for apps that send no identifier (case 5) are now decided. Read the reply; its six cases ask for your answers.

    What this is¶

    The Loop developers shared a proposal on 2026-10-17: Client-supplied identifiers for Nightscout, based on 15.0.8. It is a private page shared with the maintainer and is not linked from here. Our draft reply is reply.body.md, ready to paste as GitHub or Zulip markdown. It links the published pages on the project site.

    The simple contract¶

    What the reply proposes, and what Nightscout supports today except where the reply's table says otherwise:

    1. _id is a MongoDB ObjectId (24 hex) or absent. A client may create its own ObjectId and send it over API v1; API v3 refuses a client _id with 400 from 16.0.0 (BF-170, identity I2). Other values are not valid; UUID_HANDLING (default on) moves any non-24-hex string _id to identifier on treatments and entries, as a compatibility rule.
    2. If _id is absent, the client sends identifier, an opaque string compared exactly, not necessarily a UUID: the record's semantic identity (this reading, this pump event, this carb entry), so two uploads of one real thing carry one value. URL syntax, from the identifier conventions table: a source scheme for readings and pump events (manufacturer as scheme, model first: dexcom://g7/<serial>/<offset>), an app scheme for records made in the app (loop://carbs/<uuid>) (maintainer, 2026-10-18). 1-256 characters from A-Za-z0-9._~:/-, percent-encoded as one segment in API v3 paths (a raw / is 404; measured 2026-10-18, identifier format §3.4), not exactly 24 hex, no placeholders (invalid, undefined, null, NaN); a UUID is needed only for today's v1 by-_id routes (queue ID-FORMAT-DECISION, ID-CONVENTIONS). The server assigns _id. One identifier names one record.
    3. If neither is sent, the collection's time key applies (entries sysTime + type, treatments created_at + eventType). identifier becomes mandatory at a future version boundary and for registered controller instances; until then legacy paths keep this fallback (maintainer, 2026-10-18; queue ID-ABSENT-DECISION).

    Tie-break (maintainer, 2026-10-18; queue ID-CLIENT-OID-DECISION): when a write carries both and they point at different records, identifier decides, as in D20 rule 5 and v1 treatments today (identifier present drops _id, server/treatments.js:356-362 @15.0.8). An earlier draft proposed _id-first; it was reversed to keep today's behaviour. Every write reply returns both ids (rule 5).

    The one server change it needs, v1 entries and device status matching on identifier, is queue item ID-SIMPLE-MATCH; it ships with BF-169 after 15.0.9 (maintainer, 2026-10-17; see 15.0.9 decisions).

    The proposal, summarised¶

    The ask. An uploader gives each record a stable identifier taken from the data's source. The server puts a unique index on it and upserts on it, in every collection and both API versions. Records without one keep today's rules.

    • identifier is an opaque client string with a published length limit; a sparse unique index in entries, treatments and device status.
    • If present, upsert on it and keep the stored _id. If absent, today's rules. Additive.
    • v1 GET, PUT and DELETE by identifier. API v3 treats a client's value as authoritative and computes one only when none is sent.
    • Clients derive it from the source: sensor serial + sensor time (for example g7:<serial>:<seconds since activation>, so a phone and a watch agree), the pump's event id, or a UUID made once for a manual entry.
    • Loop would send its syncIdentifier as identifier on all three collections.
    • Questions: (Q1) a new identifier at an existing sysTime + type: keep both or merge, perhaps merge only when the stored row has none; (Q2) per-record batch results; (Q3) is insert-only device status intentional, and should an identifier make re-sends idempotent.

    How the reply argues¶

    Rewritten 2026-10-17 around the simple contract, at the maintainer's direction that the simple model is generally workable; the previous, longer version is in git history at dd6febcc.

    1. Agrees with the ask; most of it works; the confusion is largely the swagger sentence (BF-169).
    2. The three rules and the tie-break, with D20 rule 5's "every write reply returns both" quoted.
    3. A table of what works today and the one gap (v1 entries and device status store identifier but do not match on it).
    4. The watch-and-phone case: four options; recommends a source-derived identifier, with an agreed timestamp as an interim that needs no server change. FHIR and HealthKit precedents.
    5. Cautions for Loop starting today; what we will do (the one server change and BF-169, after 15.0.9); the deferred questions as a short list.

    Open for the maintainer before sending¶

    • Where to post. Unknown: the proposal names no channel. Candidates are Loop Zulip, a cgm-remote-monitor issue or discussion, or a pull request against our decision records.
    • ADR-002. ADR-002 (Proposed, 2026-01-17) names a new syncId field in UUID v4 format. D20 rule 5 and this reply use identifier, and Loop proposes opaque non-UUID values. The reply does not cite ADR-002; it may need a superseding note.
    • Q1–Q3 and the date question. The rewritten reply takes no position on them; they are in its "Later, only if needed" list. The date behaviour on API v3 is reproduced (lab results).
    • Tie-break. Settled 2026-10-18: identifier decides, keeping D20 rule 5 and today's v1 treatments behaviour (ID-CLIENT-OID-DECISION).
    • Push first. The reply links pages on the project site; the gh-pages build of 2026-10-17 (de66763c) has every linked page and anchor, including the folder's index.html the rewritten reply links. BF-169 is cited by number only.
