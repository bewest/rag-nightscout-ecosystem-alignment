    Intent, workflow and entity management across the AID controller landscape¶

    Record

    Record as of 2026-10-09. A point-in-time document; it is not kept up to date.

    Contributor-facing. Snapshot — describes 2026-10-09. Status: current; the evidence for D18. Every claim is read-derived (from source, a hypothesis about behaviour) unless marked measured. Sources and commits are in §1. Current decisions: execution plan §1. Corrected in place 2026-10-12: §5 is measured on both hubs (TL;DR and §12 follow it); the §10 rows for the hub-sync design and specs/sync/registrations/ record what the registrations now declare and what remains; the registrations row also records the D18 addendum grammar (SCHEMA-REG-EXT, 2026-10-12). Also 2026-10-18: §2 records the maintainer's decision on agent initiators (P5). The rules this evidence supports are maintained in the state and intent specification.

    The question. Nightscout's API v1 and v3 manage entities: create, read, update and delete documents in treatments, devicestatus, profile. AID controllers increasingly manage intent: a named preset is activated, several intents run at once and combine, the controller applies something that may differ from what was asked, and the intent ends for a reason. This document finds, per controller and per hub, where the two differ, so that a controller registration can describe the difference.

    The direction this serves (maintainer, 2026-10-09). Registration has two tiers: well-known declarations shipped with the hub, for backwards compatibility, and controller-owned typed registrations, for extensibility. Adoption follows the WHATWG pattern — specify what happens now, leave room to extend. The hub (Nightscout, Nocturne) is responsible for observability; the controller is responsible for sending data accurately and for syncing and reconciling. Recorded as D18 in the execution plan (§2.6.1).

    TL;DR¶

    Finding
    Single records Entity CRUD works. Every controller keeps one document per instance and amends or deletes it. Each encodes identity and "ended" differently (§4)
    Six things CRUD cannot carry definition identity, concurrent intent slots with a composition rule, requested vs applied, end reason, initiator, and the command → acknowledgement → outcome link (§2)
    Every controller already built them each in its own place: AAPS on the NS settings collection (dev), Loop and Trio over APNs replies and failure Notes, iAPS over NS Announcement treatments. None of it is typed, and most of it is invisible to the hub (§3, §6)
    The hubs disagree on "what is active now" Measured on both hubs: cgm-remote-monitor and Nocturne differ on temp-target cancel, devicestatus override duration units, profile fallback after a timed switch, AAPS timeshift units, and out-of-order override backfill; they agree on Temporary Override Cancel (§5)
    Composition is controller-specific Loop: pre-meal target wins, override factor applies. Trio/iAPS: temp target wins the target, override factors apply. AAPS: temp target replaces targets, profile-switch percentage has already scaled basal/ISF/CR. No hub composes, and under the stated roles none should (§7)
    Cowpaths already exist Loop and Trio publish preset definitions in the profile document; Nightscout's careportal builds its remote-override picker from Loop's. AAPS dev publishes scene and automation definitions plus active-scene state. These are registrations in all but name (§8)

    2. Where intent differs from entity management¶

    Six properties. A controller's intent model has each of them; an entity collection has none.

    # Property What it means Why CRUD loses it
    P1 Definition identity an activation refers to a preset by a stable id presets are copied into the instance, or referenced by name only
    P2 Concurrent slots and composition several intents active at once, combined by a controller rule one collection, one "latest wins" reading per eventType
    P3 Requested vs applied what was asked, what the device or algorithm accepted, what it computed one document is both request and effect, or the effect is elsewhere and unlinked
    P4 End reason expired, cancelled, superseded, deleted before start, ended by a trigger (carbs, glucose, loop off) "ended" is encoded as a shortened duration, a delete, or a zero-duration record
    P5 Initiator phone, watch, shortcut, automation, caregiver, remote recorded locally or in debug logs; on the wire only free-text enteredBy
    P6 Command lifecycle request → validate → apply → acknowledge, with a correlation id no request record; success visible only as the resulting entity; failure as free text

    P5, decided 2026-10-18 (maintainer): no agent value is added to any initiator vocabulary; an agent initiator is written in the open-vocabulary form {value: other, controllerTerm}, as the registration specification (§9) does for an agent's roles. No controller records an agent as initiator today. The registrations are built for needs that are latent but measured and demonstrated — in the corpus, in controller source and in the labs — not only for what apps send now; the open form lets a controller, simulator or lab record an agent initiator today, and a shared value can be named once the corpus or a lab shows one in use. (execution plan, row 17; agents in the ecosystem §4.2).

    3.1 Loop¶

    • Override wire shape. eventType: "Temporary Override", reason = preset symbol and name, duration (minutes) or durationType: "indefinite", correctionRange (mg/dL), insulinNeedsScaleFactor, remoteAddress, _id = the instance UUID. No syncIdentifier field is sent. Whether the UUID _id survives depends on the server's UUID_HANDLING setting; without it the upsert falls back to created_at + eventType.
    • Pre-meal is not on the wire. Not a treatment, not in the profile; devicestatus override.active is false when only pre-meal is on. Its target replaces the override's while it lasts; the override's scale factor still applies.
    • Scale factor. basal × f, ISF × 1/f, CR × 1/f. Target replaces the scheduled target.
    • Pump suspend uploads as Temp Basal rate 0, reason: "suspend"; resume is not uploaded.
    • Measured (distinct documents, make schema-effects). 2,428 Temporary Override treatments, all with effect and motivation. Of 55,938 active devicestatus overrides: 42,799 effect + motivation, 2,176 effect only (custom overrides have no name), 10,892 motivation only.

    3.2 Trio and iAPS¶

    • Override wire shape. eventType: "Exercise" for every override regardless of purpose; notes = the preset name (or "Custom Override"); duration with indefinite sentinel 43200 (Trio) or 2880 (iAPS). Percentage, target, ISF/CR scope and SMB settings are not sent. The struct's id is excluded from its coding keys. The wire identity is created_at + eventType.
    • Measured. One site carries all Trio Exercise documents: 399 distinct _id, 389 distinct created_at, 81 with duration: 43200. Applied ISF, CR, target and sensitivityRatio are present on all 73,898 of that site's openaps devicestatus documents.
    • Recovering the effect needs a time join to devicestatus (post-composition, unattributed) or, for presets only, a name join to profile.overridePresets. The second is untestable in this corpus.
    • Temp targets. Trio sends notes = name; iAPS drops it. Trio ends a TT by re-posting the same created_at with the actual duration; iAPS writes a zero-duration TT one second before the next start. Trio's halfBasalTarget is not uploaded.
    • Composition (Swift and JS agree). The override target applies only when no temp target is set; the override percentage and ISF/CR scaling still apply alongside a temp target.
    • Trio also downloads Temporary Target treatments entered by other clients and enables the newest one directly, with no acknowledgement record — an entity used as a command.
    • dosingMode {closed, open, lowGlucoseSuspend, basalTesting} is in devicestatus.openaps.dosingMode (Trio); the change itself is not a treatment. Pump suspend/resume are Note treatments with notes: PumpSuspend | PumpResume.

    3.3 AndroidAPS¶

    • ProfileSwitch → EffectiveProfileSwitch is the ecosystem's clearest request/effect pair. A PS is written by a user, SMS, automation, scene or NS sync; the profile is pushed to the pump; only if the pump accepts is an EPS written. A failed or pending change is visible on the wire only as a PS with no following EPS. The EPS is uploaded as eventType: "Note", recognised by originalProfileName; its profileJson is scaled, the PS's is the base profile. dev-only: EPS.originalPsId links the two locally and is not sent.
    • percentage scales overall insulin needs. ProfileSealed.convertToNonCustomizedProfile: basal × p/100, ISF × 100/p, IC × 100/p; targets only time-shifted (pinned by ProfileSealedTest.kt:136-141; same maths at the 3.4.2.6 tag). With Dynamic ISF the percentage enters the TDD-based ISF formula instead.
    • RunningMode has a requested layer and a constraint-forced layer (autoForced: true, reasons), both uploaded as OpenAPS Offline; open-ended DISABLED_LOOP is sent with a 10-year duration and originalDuration: 0. dev-only: RunningModeReconciler drives the pump from the mode record and re-checks drift at startup.
    • Temp targets have a closed reason vocabulary (Custom, Hypo, Activity, Eating Soon, Automation, Wear); a new TT ends the running one; inbound merges are shorten-only.
    • Accepting remote intent is opt-in per type. The pump-owning phone applies NS-originated PS, TT and RunningMode records only if NsClientAcceptProfileSwitch, …TempTarget, …RunningMode are on; all default off.
    • dev-only client control and scenes. Commands and acknowledgements travel as documents in the NS v3 settings collection under fixed identifiers; scene and automation definitions are published under aaps, active-scene state (with the NS identifiers of the records the scene created) under aaps-state. Scene revert shortens only records the scene still owns.

    5. How the hubs decide what is active¶

    cgm-remote-monitor recomputes active state on every load; Nocturne materialises StateSpans on write and supersedes open spans within exclusive categories.

    Status 2026-10-12: every row below is measured on both hubs by the lab tools/lab/hub-active-state (cgm-remote-monitor fade2299, Nocturne 42275c812 on SQLite, one synthetic record set, a control per case where the hubs agree). Against the 2026-10-09 text, whose Nocturne cells were read-derived: the "Agree?" cells of the cancel rows change, the same-millisecond Nocturne cell is corrected, the backfill row is new, and the other cells are confirmed. The careportal storage claim in the override-cancel row is still read-derived. "Agree?" means the two hubs report the same active state at the lab's query times; for Nocturne, "latest span" is GetActiveAtAsync(category, state: null, t) and "list" is GetStateSpansAsync over t, which hides records deduplication marked non-primary.

    Temporary Override Cancel not stored by careportal (APNs request only, read-derived); a stored one has no duration and is ignored (measured) not classified; produces no record (measured) yes: in both, the override runs its full duration
    Loop devicestatus override latest devicestatus override; timestamp + duration read as seconds (measured) one span per devicestatus, starting at devicestatus time, duration read as minutes; spans are not superseded, and active: false closes nothing (measured) no (30-min override: active at +40 and +120 in Nocturne only)

    Two hub writes do not reach any controller: Nocturne POST /api/v4/state-spans writes Override, TemporaryTarget or Profile spans directly, and careportal or nightguard temp targets are honoured only by controllers that download them (Trio; AAPS behind an opt-in).

    6. The remote-command lifecycle¶

    Path Request recorded at hub Acceptance visible Success visible Failure visible
    Careportal or Nocturne → Loop (hub → APNs) no no as the resulting entity Note with free text
    LoopFollow → Loop (direct APNs) no no reply to sender only Note
    LoopFollow → Trio (direct APNs) no no reply to sender only Note
    LoopCaregiver "Remote Commands 2" (status Pending → InProgress → Success/Error) expects a hub collection; neither hub has one — — —
    Any client → iAPS (Announcement treatment) the request is the treatment no no no
    Careportal / nightguard TT → Trio, AAPS the request is the treatment no indistinguishable from enacted no
    AAPSClient → AAPS (dev-only, NS settings) yes, signed Executing ack Done/Ok ack Done/Failed, Expired, Delivery/Failed

    Neither hub forwards a reply channel in the APNs payload it builds, so hub-routed commands cannot receive a reply; that channel exists only on direct APNs. The RFC's DeliveryRequest.requestType covers tempBasal, bolus, suspend and resume; the commands caregivers actually send — override, temp target, carbs, loop mode — have no request object, and OverrideInstance.status has no requested or rejected state.

    7. Composition: who combines overlapping intents¶

    Controller Rule
    Loop target = pre-meal if active, else override, else schedule; basal ×f, ISF ×1/f, CR ×1/f from the override only, applied over the history window
    Trio, iAPS target = temp target if set, else override target (unless 0 or 6), else profile; override percentage and ISF/CR scope apply regardless; a high or low TT separately sets sensitivityRatio via halfBasalTarget (the multiplication order with the override factor is not traced)
    AAPS TT replaces min/max/target; PS percentage has already scaled basal, ISF, IC in the EPS; one PS, one TT, one RunningMode, one Scene at a time
    cgm-remote-monitor no composition; draws bands per kind
    Nocturne no composition; exclusive within Override, TemporaryTarget, Profile; Exercise/Illness/Travel may overlap

    No two controllers share a rule, and the rules depend on algorithm settings (Dynamic ISF, AutoISF, halfBasalTarget). Under the stated roles the hub records the controller's result rather than computing it. The RFC's companion conflict-resolution.md composes overlapping overrides inside the hub; that section is inconsistent with the roles and would need revising.

    8. Cowpaths: what controllers already publish as definitions¶

    Controller Where What Missing
    Loop profile.loopSettings overridePresets (symbol, name, duration, target, scale factor), preMealTargetRange, dosingEnabled, dosingStrategy, APNs coordinates preset id; workout target; GBAF, IRC
    Trio profile overridePresets (name, duration, percentage, target), APNs coordinates ISF/CR scope, SMB settings, id
    iAPS a non-Nightscout service presets everything, as far as the hub is concerned

    Nightscout's careportal already builds its remote-override picker from profile.loopSettings.overridePresets. Each row is a registration in practice: a controller publishing its definitions to the hub, in a controller-private shape, overwritten as a snapshot.

    9. What a registration has to be able to declare¶

    Derived from §3–§8. Each element is something at least one controller does today.

    1. Definitions with stable ids and typed fields, per intent kind (override preset, TT preset, scene, mode), including controller-unique fields (Trio SMB schedule, iAPS end conditions, AAPS scene actions).
    2. Intent slots: which kinds exist, which are exclusive within themselves, which coexist.
    3. States and end reasons: scheduled, active, ended {expired, cancelled, superseded, deleted before start, ended by trigger}, with the trigger vocabulary (carbs, glucose above/below, loop off, chain).
    4. The wire carrier: how today's documents map onto the declared kinds — eventType, the discriminating fields, indefinite sentinels, units, and how "ended" is encoded (§4).
    5. Requested vs applied: where the controller reports the applied effect (AAPS EPS, Loop and Trio devicestatus) and how it links back to the request.
    6. Composition result, as reported by the controller (§7), not a hub-side rule.
    7. Initiator vocabulary: the controller's own (Loop EnactTrigger, Trio AdjustmentSource, AAPS Sources).
    8. Command contract: vocabulary, authorisation, expiry, acknowledgement states and correlation id; whether the hub is in the path.
    9. Acceptance policy: which intent the controller accepts from the hub (AAPS opt-in per type, Trio TT download, iAPS announcements).
