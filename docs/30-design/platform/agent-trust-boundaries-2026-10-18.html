    Agents in the ecosystem: develop, interpret, act¶

    Record

    Record as of 2026-10-18. A point-in-time document; it is not kept up to date.

    What this is: a map (contributor-facing). Read after the authority specification; leads to auditioning a dosing algorithm. Snapshot — describes 2026-10-18. Status: current; a map of what exists and what is missing for each of develop, interpret and act. The proposal lifecycle in §4.3 is proposed, not specified. Also 2026-10-18: §1 adds the drawing 1·agents (the three domains as paths from an agent to the ecosystem); §4.3 adds a figure of the command lifecycle replayed from the commands specification's conformance cases (tools/diagrams). Repository facts are read at this repository's 5a9a49cc; facts about other repositories and publications were checked 2026-10-18 through the GitHub API or the publisher's page, and each names its commit or date. Every claim is read-derived (from source or documents) unless marked measured. Current decisions: execution plan §1.

    The question. Software agents built on language models now touch this ecosystem in three different ways: they write and change the code of apps and servers, they read a person's data and explain it, and they could propose or start a therapy change. Each needs a different assurance, and most of what each needs is already written down here or in cgm-remote-monitor's docs/proposals, in separate places. This page puts them side by side and names what is missing.

    TL;DR¶

    Domain What the agent does What exists What does not exist
    Develop writes or changes code each controller project's own contribution rules; review and test work measured in the evidence; simulator asks drafted (§2) signed builds, an SBOM or a build-provenance record in any project surveyed
    Interpret reads data and explains it one read role; seven requirements for delegated reads; at least seven MCP servers and two agent tools that read a Nightscout site (§3) scoped, purpose-bound or audited reads; a hub whose "what is active now" both hubs agree on

    3. Interpret¶

    3.1 Read access today¶

    Item Where Status
    The read role is one bit: readable is *:*:read, every collection, every field, all time cgm-remote-monitor lib/authorization/storage.js:235 at dev fade2299; configuration and delegation §5.3 shipping
    Seven requirements for a delegated reader: scoped reads enforced in storage, bounded queries, purpose and expiry, answers rather than data, read audit, revocation that is real, minimization at the boundary configuration and delegation §5.4 requirements, stated 2026-09-10; the read role above is still one bit
    A worked delegation grant with constraints, purpose and expiry authority model proposed, not implemented
    Tools that read a site for an agent: MCP servers, an agent skill, an AI platform evidence §7.1 third-party; the list lives there

    Requirement 6 bears hardest on agents: once a model has read raw data, revoking the grant does not un-read it, and the data has also gone to whoever runs the model. Where the model runs is a property of the agent's host, not of the tool that fetched the data: a tool that keeps its database local still returns its output into the conversation, which goes to the model provider when the model is a hosted service. Lumose (repository GlycemicGPT) states this choice in its README; the evidence table records which tools do. A plain-language page for people connecting such a tool to their own site is giving an AI tool access to your Nightscout data.

    3.2 MCP is an adapter¶

    The Model Context Protocol, at its current revision 2026-07-28, lets a server offer resources (context and data), prompts (templated messages) and tools (functions the model may call), over stdio or Streamable HTTP. The revision describes stateless, self-contained requests, and says the protocol cannot enforce its security principles itself: hosts must obtain the user's consent before invoking a tool. An MCP server for Nightscout is therefore an adapter over the API it calls, not a new source of state or authority: a local copy it keeps is a copy, and it holds whatever credential it is given and reads or writes what that credential allows. The servers surveyed differ on exactly that point — which credential they accept and whether they expose write tools (evidence §7.1). The statistics API proposal specifies an MCP resource provider over a documented statistics API (REQ-STATS-005, proposal).

    3.3 Compute first, then explain¶

    An explanation is only as right as the numbers under it. Two layers come before the model:

    1. The hub's state. The two hubs do not always report the same thing as active. Measured by tools/lab/hub-active-state on synthetic records, running each hub's storage and active-state code directly rather than over HTTP (cgm-remote-monitor fade2299, Nocturne 42275c812; intent landscape §5):
    2. Temporary Override Cancel: the hubs agree — in both, the override runs its full duration.
    3. A temporary target followed by a cancel: the latest span agrees (it is Nocturne's Cancelled span); Active-state and list reads disagree until the target's own end, and the open Cancelled span stays in Nocturne's list reads afterwards.
    4. A Loop devicestatus override: cgm-remote-monitor reads duration as seconds, Nocturne as minutes, so a 30-minute override is active at +40 and +120 minutes in Nocturne only.
    5. Also disagreeing: the profile after a timed switch ends, AAPS timeshift units, and out-of-order backfill of two open overrides.

    An agent that asks either hub "which override is active?" gets the hub's answer, not the controller's. 2. Deterministic computation. Time in range, GMI, variability and patterns are arithmetic; a tool that computes them in code and hands the model the result can be tested, and one that asks the model to compute them cannot. Several MCP servers in the evidence table compute aggregates server-side; one documents checking them against Nightscout's own report.

    4.2 The earlier draft and the rules proposed to supersede it¶

    The authority and commands specifications are proposed to supersede the agent parts of the earlier draft in cgm-remote-monitor's docs/proposals; the control-plane supersession map covers the rest of it.

    earlier draft proposed to be superseded by
    agent as an issuer type state and intent S8: an agent initiator is {value: other, controllerTerm}; registration §9: an agent's role is an other role a hub lists
    suggest scope ("can propose, human must approve") commands CM11–CM14: a proposal needs api:proposals:create and a granted propose role; an approval names the payload hash and needs api:commands:create; a readable credential can do neither
    DelegationGrant: who granted, to whom, scopes, constraints, expiry, revocation authority §7, DR1–DR7: requirements; the grant's shape is open (authority §9 item 6)
    append-only audit with issuer and authority authority §8; commands CM1: a command is recorded before it is sent
    conflict rules: override composition inside the hub, "Human > Agent > Controller" state and intent S1: the controller composes; the hub records the result (D18)

    The same draft's integration questionnaire has a default answer per controller, read from source, in integration questionnaire defaults.

    An agent as initiator (maintainer, 2026-10-18). No agent value is added to any initiator vocabulary; an agent initiator is written {value: other, controllerTerm} (state and intent S8), as an agent's role is (registration §9). No controller records an agent as initiator today. The registrations are built for needs that are latent but measured and demonstrated — in the corpus, in controller source and in the labs — not only for what apps send now; the open form lets a controller, simulator or lab record an agent initiator today, and a shared value can be named once the corpus or a lab shows one in use. Recorded in the execution plan (row 17).

    4.3 What a proposal lifecycle would add — proposed, not specified¶

    Nothing in this subsection is specified or decided. It states what exists nowhere above, so that the item that specifies commands can take it or leave it.

    propose → validate → (evaluate) → approve | reject → command → outcome
    Step Who What it would carry
    propose an agent instance holding a propose role ({value: other, controllerTerm}) the exact change; the controller instance it is for (D19 instanceId and definitionId); the state it was based on; an expiry; the SHA-256 of the payload's RFC 8785 canonical JSON, the rule D19 already uses for definition ids and etags
    validate the controller (D18) its own checks, as today on every remote path (technical loops §3.3); a proposal the controller would refuse goes no further
    evaluate optional; any checker a risk check may request human review; it never grants authority. A probabilistic check — a classifier or a second model — is evidence for the approver, not a decision
    approve or reject a subject that may send the command itself; when an agent proposed, not the subject that proposed it (commands CM14) an approval names the payload hash, so it binds to that exact change and no other; an expired proposal cannot be approved
    command the hub routes to the live device command-sink, as specified in registration §9 the approved payload and its hash; the controller checks the hash before enacting
    outcome the controller accepted or refused, applied effect (P3), correlated to the proposal

    Three constraints carry over unchanged. Validation and enactment stay the controller's (D18). Read access never confers a propose or act role: a readable credential, or an MCP server holding one, cannot be promoted to either. And the hub routes and records; it does not decide whether a change is safe. For comparison, OWASP's LLM06:2025 Excessive Agency recommends minimum extensions, minimum permissions, and human approval of high-impact actions.

    "The state it was based on" has no home yet. What D19 versions is the registration: the product's etag and the instance's etag cover the declaration, the binding and the granted roles (registration specification §5.4 and §8). Neither covers the controller's therapy state — which override is active, which profile, what is on board — so neither tells an approver that the state the agent read is still the state the controller holds.

    What one prototype shows. A commercial controller prototype implemented the client side of the agent control-plane RFC of that earlier draft: sources including agent, delegation grants with auto-approve types, and an audit log held in memory. Its approval records only the reviewer, the time and a note against the proposal id — no payload hash and no state — and its remote-command "success" means the HTTP request succeeded, with no acknowledgement or outcome (read-derived from its source, 2026-10-18; not reproduced here). That is evidence for the binding requirement above and for its open question: an approval that names neither the payload nor the state does not bind to either, and an HTTP status says nothing about what the controller did.

    Where it is specified. The command record, outcomes, proposals and approvals are proposed in the commands specification §4–§7 (SPEC-REG-COMMANDS; the proposal record was folded in by the maintainer on 2026-10-18), with cases for an approval bound to one payload hash, an expired proposal, and a proposal from a credential with no propose role. Its CM15 takes the open question above: an approval is refused when the hub's state version differs from the proposal's, which still says nothing about the controller's own state. What controllers do with outstanding commands, enacting each once (CM21), and plans confirmed in advance are in the command queue and planning design note.

    The lifecycle as the commands specification proposes it, from five synthetic conformance cases, call by call. An approval names the payload hash and creates one command with the proposal's payload (CM13, CM14, CM1); the controller fetches it and recomputes the hash before enacting (CM10). An approval after the proposal's expiry is refused 409 proposal-expired (CM13). A received payload whose hash differs is refused hash-mismatch, and the hub records the report as a mismatch (CM10, CM7, CM8). A command fetched before its expiry reads unconfirmed after it, and the controller's late report replaces that state (CM3, CM9). A cancel after hand-over is a request: 202 cancelRequested, carried by the next fetch, refused by the controller with reason cancelled (CM25, CM21). Proposed (commands specification §4–§7); replies from each case's expected block (specs/sync/conformance/commands/), replayed by the reference tools/nsschema/commands.py.     5. Evaluating an algorithm before it acts¶

    An agent that proposes a change, and a developer who changes an algorithm, both need to know what the algorithm does with the inputs it gets.

    • Cross-implementation equivalence. ADR-005 fixes the adapter protocol for comparing oref0 in JavaScript, Swift and Kotlin, and Loop, on identical inputs; the vectors and assertions are under conformance/.
    • Shadow comparison. The cross-validation log (A10, 2025-03-30) records Trio's shadow mode, which logs JavaScript and Swift outputs for the same inputs; at Trio e41c9db37 the Swift port is the running algorithm (intent landscape §1).
    • Replay is bounded by what was recorded. Of the dosing inputs each algorithm declares, 20% are recorded for Loop and 50% for the oref0 family (55% and 72% counting inputs derivable from history), as of 2026-09-11 (hub-sync §4.2). Loop's input set is read from its source; oref0's is the union of inputs across 385 replay vector files (specs/nsschema/dosing-input-sources.yaml), which hold 308 distinct inputs, 22 of them synthetic (measured 2026-10-18, algorithm audition §2.1). A derived input is a value, not necessarily the one the controller used, so a replay on derived inputs tests the replayer as much as the algorithm. The change list that would raise the figures is replay-fidelity changes.

    Comparing algorithms on the same recorded inputs in shadow, what an independent implementation's shadow runner and replay work show, and what an audition harness would need without ever granting control, are in auditioning a dosing algorithm.

    6. Regulatory boundary¶

    Facts, and questions for counsel; no conclusion is drawn here.

    • FDA's guidance Clinical Decision Support Software was issued January 29, 2026, superseding the issue of January 6, 2026 (nonbinding recommendations). It states: "Software functions that support or provide recommendations to patients or caregivers – not HCPs – meet the definition of a device", and that FDA intends to be consistent with its existing digital-health policies for them.
    • The programme's question for counsel is §9 item 11: whether a report that proposes settings changes is clinical decision support under device regulation, and what clinical review it needs. The same question arises for an agent that explains data to a person with diabetes or a caregiver and ends with a suggestion.
    • Regulatory roles, intended use and complaint handling in any agreement with a manufacturer are in partner readiness §5 and §6.

    Questions for counsel: whether an MCP server or agent skill that only reads and summarises is in scope of the guidance when its user is a patient or caregiver; whether a server that exposes a treatment-write tool changes that; and who, among the server's author, the host's provider and the person running it, would be the manufacturer of such a function.

    7. Not measured, not decided¶

    • No agent, MCP server or skill was run against a site for this page; the tool facts are from READMEs and source read.
    • Whether any controller project would accept an agent as a command sender at all, under any grant.
    • How an agent instance is scoped, limited and revoked: no decision covers it (authority §9 item 6; process models).
    • A shared initiator list (§4.2).
    • A therapy-state version a proposal could bind to (§4.3): the hub's state version is proposed in commands CM15; it versions the hub's record, not the controller's state.
    • Read audit, purpose limitation and real revocation for a delegated reader (§3.1).
    • The delegation grant's shape, storage and checks (authority §9 item 6).
    • Whether outstanding commands on a channel are shown to an approver or included in what the state version check compares (commands §9 item 7).
