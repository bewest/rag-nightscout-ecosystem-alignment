    Identifier conventions: one identifier per real thing¶

    Living document, last changed 2026-10-18 at 9442b2243.

    Contributor-facing. Living draft, as of 2026-10-18. Decisions recorded here are the maintainer's of 2026-10-18; the templates in §4 are proposals unless a cell says otherwise. Read after the identity specification (L0), whose format section this page fills in. Evidence: identifier format research (§1 per-app identity, §3.4 URL-form identifiers measured, §7 the G7 counter) and identifier duplicates. Queue: ID-CONVENTIONS, ID-FORMAT-DECISION, ID-ABSENT-DECISION, ID-SCOPE-DECISION.

    identifier names the real thing a record describes (this CGM reading, this pump event, this carb entry), written in URL syntax whose scheme says where the thing comes from: the manufacturer for things that exist outside any app (dexcom://g7/<serial>/<offset>), the app for things made inside it (loop://carbs/<uuid>). The server treats the value as opaque, enforces one record per identifier in each collection and publishes the limits; clients compute the values, and this table is how two apps that see the same sensor or pump arrive at the same value. Measured 2026-10-18 at 15.0.8 and dev: URL-form identifiers work on API v3 when percent-encoded as one path segment, and on API v1 find[identifier]=; a raw / in a v3 path is 404.

    Marks: [R] read from code at the commit given; [M] measured (the cited page says how); [proposed] a template or rule for the maintainer and client developers to confirm; [decided] the maintainer's decision of 2026-10-18.

    1. Decisions¶

    # decision status
    1 identifier becomes mandatory at a future version boundary, and for registered instances of controllers (registration §8). Until then the legacy paths keep the time-key fallback for a write that carries none (entries sysTime + type, treatments created_at + eventType). The version boundary and how a hub tells a registered instance's writes apart are open (ID-ABSENT-DECISION). [decided]
    2 Meaning. _id identifies the stored record (uniqueness in the database). identifier is the record's semantic identity in the data model: two uploads of the same real thing carry the same identifier, whichever device or app sends it. The server enforces uniqueness and states the format; clients compute the values. This refines the wording of D20 rule 5 ("the sync identity the client assigns") without changing its mechanics. [decided]
    3 Format. Opaque to the server, one rule for every collection, plus this published table per record kind so different apps converge on one value. URL syntax: <scheme>://<segment>/<segment>/…. [decided]
    4 Scheme. Things that exist outside the app (sensor readings, pump events) use a source scheme: the manufacturer is the scheme and the model is the first segment (dexcom://g7/…, dexcom://g6/…, abbott://libre3/…). Things created inside an app (manual carbs, boluses, overrides, temporary targets, device status) use an app scheme (loop://carbs/…). [decided]
    5 A controller's own format. A controller may use one format of its own across collections for the records it creates, for example loop://carbs/<uuid>, loop://tempbasal/<syncId>, loop://override/<uuid>, loop://devicestatus/<uuid>. Constraints: unique per collection, within the limits of §2, stable across re-sends. A registered instance declares the format it uses (§5). [decided]

    Why a source scheme. The maintainer's first example, loop://g7/<serial>/<sensor offset>, names the uploading app. Loop and xDrip+ reading one G7 would then produce two identifiers for one reading, which is the opposite of what decision 2 asks. With the manufacturer as the scheme, every app that reads the sensor's own serial and counter produces the same bytes. One scheme per vendor covers all its models, serial numbers are a manufacturer's namespace, and the shape matches loop://g7/….

    Recommended, not decided (ID-SCOPE-DECISION). Uniqueness is enforced per collection (each collection has its own index), while values are globally unique by convention: the kind segment (carbs, tempbasal, devicestatus, or the model for a source scheme) keeps two collections from ever holding the same value.

    The kind segment fixes a measured hazard. 13 Loop syncIdentifier values are each on 2 to 4 treatments in the corpus; 9 of them are a Suspend Pump and a Temp Basal at the same created_at (identifier duplicates §2.2) [M]. Sent as identifier today, the second would replace the first. loop://suspend/<id> and loop://tempbasal/<id> differ. The other 4 values are Temp Basals only (groups spread over more than a day, and one pair 1 s apart); a kind segment does not separate those, and the cause on Loop's side is not known.

    2. The rule the server states¶

    # constraint status
    C1 a JSON string with at least one non-whitespace character enforced on API v3 create today [R]
    C2 at most 256 characters [proposed]; an indexed value near 1 KB fails the insert on MongoDB before 4.2 [M]
    C3 characters from A-Z a-z 0-9 - . _ ~ : /; no %, ?, #, space or control characters [proposed]; / and : are allowed because the URL form needs them and the measurement below holds
    C4 not exactly 24 hex characters, unless it equals the record's own _id [proposed]; both APIs read a 24-hex value as an _id too [R]
    C5 not history, . or .., and no client placeholder (invalid, undefined, null, NaN, unknown) [proposed]
    C6 one identifier, one record, per collection, for as long as the record is stored identity rule I6
    C7 compared exactly: case-sensitive, never trimmed or normalised identity rule I6
    C8 URL syntax <scheme>://<segments>: scheme lower case, [a-z][a-z0-9+.-]*; segments separated by /; no empty segment [proposed]; the server does not parse it, so this is a convention for clients, not a check

    Writing one in an API v3 path. Percent-encode the whole identifier as one path segment (encodeURIComponent in JavaScript: : becomes %3A, / becomes %2F). At 15.0.8 92d08342 and dev fade2299, an encoded URL-form identifier works on v3 GET, PATCH, PUT (update and create) and DELETE, ?identifier$eq= search finds it, and v1 find[identifier]= finds it encoded or raw; a raw / in the path is 404 [M, §3.4]. A path helper that leaves / unescaped (Foundation's urlPathAllowed set allows /) builds the wrong route. v1 by-id routes (DELETE /api/v1/treatments/:id, find[_id]=) understand UUID- and ObjectId-shaped values only, so a client deletes over v1 with the _id the write reply returns. Reverse proxies that decode or refuse %2F were not measured; behind one, reads work through search and find[identifier]=.

    Build the string, do not normalise it. In RFC 3986 terms the first segment after // is the authority; some URL libraries lower-case or re-encode it. Clients should build the value by concatenation from the convention's parts and send those exact bytes, since the server compares them exactly (C7).

    3. How two apps converge¶

    They converge only when every input of the template comes from the device itself (the sensor's serial and counter, the pump's own event record), not from the receiving phone's clock or a random generator (format research §1). A record created inside one app (a carb entry typed on the phone) has one origin, so there is nothing to converge: an app that reads it back from Nightscout keeps the identifier it received and never mints a new one. If an input is missing (no serial yet, no counter), send no identifier and let the time key apply; never a partial value or a placeholder.

    5. How a registered controller declares its convention¶

    Decision 5 says a registered instance declares the format it uses. Where it goes is a proposal: the registration grammar v1 has no member for it.

    • An instance carries no meaning of its own; it names a stored definition by definitionId (registration §8), and a definition is where a product says what its data means (registration §7). So the declaration belongs in the definition, as a meaning member, for example identifiers: [{collection: treatments, kind: carbs, template: "loop://carbs/{uuid}"}, …]. Being meaning, a changed template would need a new definition version (§7's "one element at one version has one meaning").
    • A hub can then check a registered instance's writes against its own declaration (scheme and kind segment) and, under decision 1, refuse one with no identifier. It cannot check that a value names the right real thing; that stays the client's contract.
    • Source schemes (§4.1) are not a product's to declare: they belong to this table, and a definition that uses one names it rather than restating it, as a well-known kind is named by wellKnownRef today.

    7. Open¶

    • The version boundary at which identifier becomes mandatory on legacy paths, and how a hub recognises a registered instance's write on a legacy path (ID-ABSENT-DECISION).
    • The client developers' answers: whether the source-scheme templates work for them, and each app's scheme spelling (Loop is asked first, reply).
    • Unknown cells in §4: Dexcom ONE+ and Stelo model segments, the Libre 2 serial source, AndroidAPS per-driver pumpId origin, Trio override ids, a per-cycle device status id for Trio, AndroidAPS and oref0.
    • The G7 two-display capture (format research §7.6) before any client relies on dexcom://g7/… converging.
    • Proxies: whether common reverse-proxy setups pass %2F through to v3 paths.
    • The UUIDv5 bridge: format research §4 proposed hashing a source-derived name into a UUIDv5 for today's v1 by-id routes. With URL-form identifiers the readable form is the identifier; whether a v5 form is still offered for v1-only clients is open.
