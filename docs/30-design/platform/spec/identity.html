    L0 Identity: how records, definitions, instances and subjects are named¶

    Living document, last changed 2026-10-26 at 38fb13008.

    Contributor-facing. Living specification, current at 2026-10-26 (cgm-remote-monitor dev 47723cda). Layer L0 of the platform index; terms are in the glossary. Status: specified, not implemented; §6, today's behaviour, is evidenced. Decisions: D20, the write contract's §6.1 and the 16.0.0 decisions (I2 on API v3, BF-170; the null rule of §3, Q1b). Queue: SPEC-ID.

    Specification 1 of 8 in the reading order; every other specification uses these ids. Expect rules I1–I9, the contract ids, the match order per collection, the identifier format, today's behaviour in cgm-remote-monitor, and the conformance cases.

    This page defines how records, definitions, instances and subjects are identified, and how a hub decides that a write is a re-send of something it already stores. Every other layer uses these ids; none of them redefines one.

    1. Rules¶

    # rule
    I1 Two ids, two jobs. identifier is the sync identity the client assigns: stable across retries and across the devices that write the same record. _id is the storage key the hub assigns. In the typed API, identifier is the controller's record id.
    I2 _id is 24 hex on every legacy surface. The hub assigns a 24-hex _id, on MongoDB and PostgreSQL alike; API v1 serves it, and API v3 reads do not return it (§6). On API v1, a client _id that is 24 hex, in either case, or {"$oid": …}, is kept as that ObjectId in lower case, and a client _id that is any other string is never stored as _id; it is handled by the quirks registry (I9). On API v3, a client-supplied _id in the body of a create, PUT or PATCH is refused with HTTP 400, whatever its form, and no quirk applies: a v3 client names its records by identifier (maintainer, 2026-10-25; BF-170). A hub's own newer APIs may use other ids.
    I3 An assigned _id's time is the receipt time. The first four bytes of an ObjectId the hub assigns are when the hub received the write, not the record's own time. Readers take a record's time from created_at or date.
    I4 Every write reply returns both ids. Per item: identifier (null when the client sent none and the path assigns none), _id, and matchedBy: identifier, _id, or null for a new record. On v1 and v3 this is the write step's WriteResult.items[]; on a typed write it is write.ids. A duplicate is never answered with a 5xx, an error to the callback or an empty acknowledgement.
    I5 A re-send matches on identifier first, then on _id, then on the collection's natural key (§3). A matched re-send stores no second copy and is answered with the stored ids, so a client needs no cache of server ids.
    I6 One identifier names one record per collection, for as long as the record is stored, and is compared exactly: case-sensitive, with no trimming or normalisation. For devicestatus, a re-send whose identifier is already stored writes nothing (no merge, no new record, no srvModified change) and is answered with the stored _id, on API v1 and v3 alike (maintainer, 2026-10-26; §3).
    I7 A typed re-send matches across instances of one product. A typed write matches a stored typed record of the same (vendor, product) with the same identifier, whichever instance sent it. The dual-write link (§2) is the exception: it is scoped by instance.
    I8 Projected documents have both ids. When a hub serves a typed record to older readers as a projected document, it assigns an ObjectId at the typed write and stores it with the record, so every read of that projection carries the same _id. The projection's identifier is the typed record's id. A write aimed at either id of a projected document is refused projected-read-only.
    I9 Today's _id handling is a recorded quirk. A non-ObjectId string _id on a treatment or entry is moved to identifier when UUID_HANDLING is on (the default) and the client sent no identifier, and dropped otherwise (QUIRK-TREATMENTS-006, QUIRK-ENTRIES-004). The hub records the move on the reply and the stored record as quirksApplied (moved-to-identifier or dropped).

    identifier is the record's semantic identity in the data model (this CGM reading, this pump event, this carb entry), so two uploads of the same real thing carry the same value whichever app sends it; _id identifies the stored record (maintainer, 2026-10-18).

    Rules I1–I9 are D20 rules 5–8 with the walk-through rows 1–3, specified in the hub-sync design §3.7, and the write contract's U1 and U6.

    2. Contract ids¶

    id form assigned by identifies
    definition id sha256: + the lowercase hex SHA-256 of the RFC 8785 canonical JSON of the definition as submitted the hub computes it; the controller may compute it to check one immutable definition; equal content gives an equal id
    registration etag sha256: over the canonical JSON of {registration, state, boundTo} the hub one state of a product resource
    instance id a random lowercase UUID v4, generated once per running copy; any other form is refused invalid-instance-id the controller one running copy of a controller
    instance etag sha256: over the canonical JSON of {instance, boundTo, granted}; the lease is outside it the hub one state of an instance
    subject an opaque id of the principal a credential belongs to the credential issuer a principal; tokens rotate, the subject does not
    dual-write link (instance id, the controller's record id) the controller one typed record and its carrier copy

    An instance id is never derived from a device name, model, serial number or the free-text devicestatus.device. A hub cannot check that an id is random; the contract states it. Bindings are to a subject, never to a token. These are specified in the registration specification §7–§8.

    3. Match order per collection¶

    The write step (write contract §2.2) resolves a re-send's target by trying keys in order; the first that resolves wins.

    collection keys, in order on a match
    treatments identifier, _id, client identity, created_at + eventType merge
    entries identifier, _id, date + type merge
    devicestatus identifier, _id, NSCLIENT_ID, created_at + device for an identical body only an identifier match is unchanged whatever the body: nothing is written, no srvModified changes, and the reply carries the stored _id; on the other keys an identical body is unchanged and a differing body is a new record
    profile identifier, _id, NSCLIENT_ID, created_at merge
    food identifier, _id merge
    activity _id merge
    • Merge follows JSON Merge Patch (RFC 7386): a field sent as null is removed from the stored record. The rule is recursive (a null inside a nested object removes that nested field) and an array is replaced whole, never merged element by element. It applies to a merge on match (a re-send that matches a stored record, in the collections above whose outcome is merge), to an API v3 PATCH, and to the socket's dbUpdate, which follows PATCH. It never applies to a replace (v1 PUT, v3 PUT), which stores the document as sent, or to any create, which stores a null as sent. On API v1 it runs after prepareData, so a field that prepareData removes or rewrites never reaches it. The socket's dbUpdateUnset stays as the explicit removal of named fields (maintainer, 2026-10-26; write contract Q1b; ships in 16.0.0).
    • Because the merge is recursive, a profile re-send whose store leaves out a named profile keeps that stored profile; removing it takes store: {"<name>": null} or a replace (PUT, which the profile editor uses). The same nested merge applies to an API v3 PATCH and a socket dbUpdate (maintainer, 2026-10-26, accepted with this consequence).
    • Client identity is treatment-fallback-key's client ids, with its rule that a write without identity matches only a stored record without identity.
    • The devicestatus natural key matches identical retries only, because Loop writes distinct statuses that share created_at and device (3,078 groups, 14,757 documents, at 11 of 12 corpus sites, measured 2026-10-12).
    • An _id matches every stored form of that id. A soft-deleted record is not a target for a create, so a re-send of a deleted record is stored again.

    4. The identifier format¶

    identifier is an opaque string, with one rule for every collection. Values follow the identifier conventions table, one row per record kind, in URL syntax: a source scheme for things that exist outside the app, the manufacturer as the scheme and the model as the first segment (dexcom://g7/<serial>/<offset>), and an app scheme for records made in an app (loop://carbs/<uuid>) (maintainer, 2026-10-18). What makes two devices agree is that they derive the id from the same inputs, not its format. A UUID is not required.

    The constraints proposed for ID-FORMAT-DECISION, each grounded in the identifier format research §0:

    # constraint
    C1 a JSON string with at least one non-whitespace character
    C2 at most 256 characters
    C3 characters from A-Z a-z 0-9 - . _ ~ : /; in an API v3 path the identifier is percent-encoded as one segment (an encoded / works on every v3 by-identifier route at 15.0.8 and fade2299, a raw / is 404: format research §3.4)
    C4 not exactly 24 hex characters, unless it equals the record's own _id
    C5 not history, . or .., and not a client placeholder such as invalid, undefined, null or NaN
    C6 one identifier, one record (I6)
    C7 compared exactly (I6)

    A client that sends no usable identifier sends none, and the natural key applies. A client that uses today's v1 by-_id routes needs a UUID (§6).

    5. Open decisions¶

    item question where the rules above stand
    ID-FORMAT-DECISION adopt C1–C7? opaque values, URL syntax and the source and app schemes are decided (maintainer, 2026-10-18); C1–C7 are proposed; I6 holds either way
    ID-CLIENT-OID-DECISION may a client create its own ObjectId as _id over API v1? the API v3 half is decided: I2 refuses a client _id on v3 (maintainer, 2026-10-25, BF-170). When identifier and _id match different records, identifier decides (maintainer, 2026-10-18), as I5 orders it. Open: whether the v1 half of the Loop reply's simple contract (a client-created ObjectId as _id) is recommended, which waits on Loop's answer and is carried by ID-SIMPLE-MATCH
    ID-V3-IMMUTABLE-DECISION on an identifier match, may date, device or eventType change? API v3 refuses it (400, reproduced by LOOP-ID-V3-IMMUTABLE); v1 does not
    ID-ABSENT-DECISION a write with no identifier: keep the time-key fallback, deprecate it, or require identifier? decided (maintainer, 2026-10-18): identifier becomes mandatory at a future version boundary and for registered controller instances; until then legacy paths keep the time-key fallback. Open: which version, and how a hub recognises a registered instance's write. Today v1 entries and treatments fall back to a time key, API v3 to its fallback fields; v1 device status has no key; two distinct doses with one created_at and eventType and no identifier are merged by §3 (UCA-SYNC-STORE-007)
    ID-DELETE-REUSE-DECISION after a delete, does a re-send of the same identifier resurrect, get refused, or create new? §3 stores it again today; a resurrected dose is UCA-SYNC-STORE-003 in the control-loop analysis API v3 resurrects a soft-deleted record on POST (measured 2026-10-18, record identity reference)
    ID-SCOPE-DECISION is identifier unique per collection, across collections, and per tenant? per collection today (each collection is its own MongoDB collection and index); the rules above do not say
    D20 choice 6 (text) is identifier null in the reply when the client sent none and the path assigns none? I4 states null, pending confirmation
    D20 choice 7 does a typed re-send match across instances of one product? I7 states yes, pending confirmation

    6. Today, in cgm-remote-monitor¶

    Read-derived unless marked, at official/dev fade2299 except where another revision is named. Measured per collection and path at 15.0.8 and fade2299 in the record identity reference (2026-10-18).

    • API v1 treatments match a re-send on identifier, and drop a client _id when identifier is present (lib/server/treatments.js:356-362 at 15.0.8).
    • API v1 entries and devicestatus do not match on identifier. Queue item ID-SIMPLE-MATCH adds that, after 15.0.9.
    • API v1 by-id routes treat only UUID-shaped values as identifiers (UUID_RE, lib/server/query.js:12). Stored identifiers are compared exactly, so an upper-case UUID matches only itself.
    • API v3 keeps a client identifier. When none is sent it computes a UUID v5 over the device, date and, for treatments, eventType (lib/api3/shared/operationTools.js:6, :106). It refuses a re-send whose date, device or eventType differs (400, reproduced).
    • API v3 and a body _id (dev 47723cda, since #8845): create, PUT and PATCH refuse a client-supplied _id with 400 (lib/api3/shared/operationTools.js:197-203, read), as I2 states. On v15.0.9 a 24-hex body _id is stored as a string (BF-170, reproduced). v3 reads do not return _id (lib/api3/storage/mongoCollection/utils.js:10-16, read).
    • A devicestatus re-send with a stored identifier (dev 47723cda): API v1 stores a second record (no identifier match) and API v3 replaces the stored record and moves its srvModified (reproduced, the devicestatus study of 2026-10-26). I6's rule is built for 16.0.0 with ID-SIMPLE-MATCH on branch bf/16.0.0-null-removes.
    • A null in an update (dev 47723cda): a merge on match stores a field sent as null as null ($set), on every path, and tests/api.profiles.resend.test.js:218 pins that. §3's removal is built for 16.0.0 on branch bf/16.0.0-null-removes (in progress), with BF-195's fix.
    • UUID_HANDLING (default on) moves a non-24-hex string _id to identifier on treatments and entries, as I9 describes (lib/server/treatments.js:394-411, lib/server/entries.js:267-284 at official a8888f0d).
    • The write paths disagree. A record created through one path and re-sent without _id through another is stored twice in 38 of 66 ordered path pairs (measured on dev 43289dde; write contract §0). The write step (WRITE-CONTRACT) is what makes §3 hold on every path.

    What controllers send is in the client id analyses, the identifier format research §1, and the quirks registry: QUIRK-TREATMENTS-006 (Loop override _id), QUIRK-ENTRIES-004 and QUIRK-TREATMENTS-007 (Trio's id member).
