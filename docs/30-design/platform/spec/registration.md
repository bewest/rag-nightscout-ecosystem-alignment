and the maintainer's decisions of 2026-10-14, 2026-10-16 and 2026-10-17 recorded there. Queue:
`SPEC-REGISTRATION`.*

A controller declares what its data means; the hub accepts the declaration element by element,
stores typed records for what it accepts, and tells the controller to write everything else in
today's document shapes. Several running copies of a controller can share a site without
overwriting one another. The hub records what each copy reports; it never decides dosing.

Paths and permission names on this page are proposals. Every request below is on the data listener
(`ns-api`, or `single`) unless it says the owner's listener (`ns-tenant-admin`, or `API_SECRET` on
`single`).

## 2. Two tiers

| tier | who writes it | purpose | what changes for the controller |
|---|---|---|---|
| **well-known** | the hub, generated from measurement | today's writers are described as they are | nothing |
| **controller-owned** | the controller, per release | typed definitions for features unique to that controller, and the hub API derived from them | it submits a registration when it wants typed support |

The hub ships the well-known registrations and serves them at `/.well-known/nightscout/controllers`.
Precedence is controller-published, then operator-declared, then structurally inferred. A
registration is an affordance: what a controller may sync, how often and with which filters
(`cadence`, `queryProfile`) is declared by the controller, and the hub honours a declaration it can
bound.

## 3. The grammar

A registration (`apiVersion: nightscout.dev/sync/v1`) declares:

- **documents**: the composite documents it writes, each with a structural discriminator (a
  devicestatus carrying a `loop` object rather than an `openaps` one) and the observation
  primitives it decomposes to. The free-text `device` string is never the discriminator.
- **stateSpans**: one entry per intent kind; its meaning is specified in L3.
- **composition**: how overlapping intents combine, as reported by the controller
  (`reportedBy: controller`, `hubComputes: false`).
- **commands**: transport, whether the hub is in the path, authorisation, expiry, acknowledgement.
- **replayInputs**: every dosing input the controller could supply, with a status and a path; an
  input it has but does not publish has a null path.
- **settings**: the effective-dated configuration snapshot it publishes.
- **extensions**: controller-specific typed data under reverse-DNS namespaces.
- **cadence**, **queryProfile** and **sensitivity**.

Rules:

| # | rule |
|---|---|
| G1 | **Must-ignore.** Within a grammar major, a reader keeps members it does not know as written and does not interpret or serve them. No object in the grammar is closed. |
| G2 | **Typed declarations.** A typed field carries `type`, a restricted JSON Schema fragment (`type`, `enum`, `minimum`, `maximum`, `format`, `items`, `properties`, `required`; closed; an object lists its properties), or `typeRef` to a Nightscout-published definition such as a ControllerSettings field; plus `unit`, `range`, `horizon`, `sensitivity` and `evidence`. `settings.fields[]` and `replayInputs[]` take a name or a typed declaration. An extension or extension field without a type is rejected. A field with no sensitivity label falls under `sensitivity.unlabelledPolicy`, `withhold` when absent. |
| G3 | **Open vocabularies.** `endedEncoding`, command `transport`, `replayInputs[].status`, the discriminator `test` and `endReasons` take a shared value or `{value: other, controllerTerm}`. A hub renders an unknown term as "other: *term*" instead of rejecting the registration. |
| G4 | **Per-element versions.** Each stateSpans kind and each extension may declare `version`, or `versions` (`served`, one `stored`, optional lossless `mappings`). Without a declared mapping nothing is converted. |
| G5 | **Horizons.** Documents, kinds, fields, settings and extensions may declare a `horizon`: `cycle`, `span`, `effective-dated`, `definition` or `aggregate`, each with its own cadence and retention. `availability` includes `experimental`, stored as declared with no well-known mapping and no long-term promise. |

The well-known registrations carry `typeRef` only where the ControllerSettings definition was read
from the controller's own algorithm family, and horizons only on the `devicestatus` document
(`cycle`) and `settings` (`effective-dated`). They declare no kind versions.

## 4. The capability document

`GET /.well-known/nightscout/sync`, beside the catalogue at `/.well-known/nightscout/controllers`
(RFC 8615). It is unauthenticated, cacheable and about the hub software, not a person. Under
`TENANCY_MODE=multi` each tenant's host serves the same deployment-level content. It never lists a
tenant's registrations.

| member | states |
|---|---|
| `grammar.versions[]` | each grammar major the hub reads and the minor it implements; a registration carries no minor |
| `grammar.interprets[]` | the grammar members the hub interprets, as dotted paths with `*` for an array item or map key; an entry covers its subtree. It covers at least `apiVersion`, `kind`, `metadata.vendor`, `metadata.product`, `metadata.tier`, `spec.cadence`, `spec.documents.*.collection` and `spec.documents.*.decomposesTo` |
| `horizons.classes[]`, `horizons.availability[]` | the horizon classes and availability values the hub stores |
| `typeFragment.keywords[]`, `typeFragment.formats[]` | the type keywords and formats the hub can store, validate and index; includes `type` |
| `limits` | `maxRegistrationBytes` (RFC 8785 canonical JSON), `maxExtensions`, `maxFieldsPerExtension`, `maxTypeDepth` |
| `wellKnown.catalogue`, `wellKnown.kinds[]` | each shipped registration's vendor, product, version range and `href` |
| `wellKnown.slots`, `wellKnown.mappings[]` | the shared slot list (§9) and the catalogue mappings for older versions (§16) |
| `submit.href`, `submit.tiers`, `submit.permissions` | where a controller-owned registration is submitted, and the permissions it needs; absent when the hub takes no submissions |
| `instances` | present when the hub serves definitions and instances (§7–§8): `leaseSeconds` (at least 60), the instance id form (`uuid-v4`), the roles and channels it grants, and label bounds |

The document is must-ignore like the grammar. Its vocabularies (horizon classes, availability,
keywords, formats) are closed lists that match the grammar's.

A controller reads the capability document and its registration at launch and after a controller
release, never on a timer, on a lease renewal or because a request was refused.

## 5. The product resource

### 5.1 Identity and methods

A registration's identity within a tenant is `(metadata.vendor, metadata.product)`.
`versionRange` is an attribute: a new release updates the same registration. The product resource
is `<submit.href>/<vendor>/<product>`, each segment percent-encoded.

| method | who | meaning | precondition |
|---|---|---|---|
| `PUT` | controller | create or update | `If-None-Match: *` to create; `If-Match: <etag>` to update |
| `GET` | controller | the stored registration with its current element results, binding and credential kind | none |
| `DELETE` | controller | retire | `If-Match` |
| `DELETE` | owner | retire | `If-Match` |
| `POST …/block` | owner | block | `If-Match`; `If-None-Match: *` when nothing is stored |
| `POST …/unblock`, `…/release`, `…/transfer`, `…/free-namespaces` | owner | §15 | `If-Match` |

### 5.2 Order of checks

1. **Authorisation (403).** The permission, then the binding: any credential other than the one
   the registration is bound to is refused `not-registration-owner` for an update or retire. An
   owner action is authorised by its listener and refused `not-authorised` elsewhere.
2. **Preconditions.** None sent: 428. A failed one: 412 with the current etag and state. Retiring
   an identity with nothing stored: 404. Then the owner's block: a write to a blocked identity is
   403 `blocked-by-owner`. The block is checked after the preconditions, so a controller holding
   the etag from before the block gets 412 with `current.state: blocked`. A pre-emptive block
   stores no registration, so a create's `If-None-Match: *` passes and the block answers 403.
3. **The registration as a whole**, each rejecting it entirely and storing nothing (422 unless
   stated): `apiVersion` not among `grammar.versions` (`unsupported-grammar-major`); wrong `kind`,
   or grammar-invalid outside `spec.extensions` (`invalid-registration`); identity differing from
   the resource (`identity-mismatch`); a tier other than `controller-owned` (`wrong-tier`); over
   `maxRegistrationBytes` (413) or `maxExtensions` (`limit-exceeded`).
4. **Each element** (§5.3).

### 5.3 Elements and their results

| element id | from | carrier when not accepted |
|---|---|---|
| `stateSpans/<kind, else category>` | `spec.stateSpans[]` | its `wire` (`write: carrier`); `none` when `wire` is null |
| `extensions/<namespace>` | `spec.extensions` | its `carrier`; `none` when it declares none |
| `settings.fields/<name>` | a typed `settings.fields[]` entry | written as today, name-only (`write: untyped`) |
| `replayInputs/<input>` | a typed `replayInputs[]` entry | written as today, name-only (`write: untyped`) |

Everything else (documents, cadence, composition, commands, query profile, sensitivity, untyped
settings and inputs) belongs to the registration as a whole.

Each element is `accepted`, `accepted-with-ignored-members` (with the ignored members as dotted
paths), or `rejected` with reasons. Ignored members are those the grammar does not define plus
those `interprets` does not cover; they are kept as written. Ignored members outside any element are
listed at registration level. An element is `not-interpreted` when a
member that defines it is ignored: a kind's `category`; an extension's `fields`,
`version`/`versions` and each field's `name`, `type` and `typeRef`; a typed setting's or input's
name and type. Otherwise an element is rejected for:

| reason | when |
|---|---|
| `namespace-not-owned` | the credential has stated namespace roots and none covers the namespace (§15.4) |
| `namespace-claimed` | another registration on the tenant holds the namespace, whatever its state |
| `untyped-extension` | an extension without a type declaration |
| `unsupported-type-keyword` | a keyword or format outside `typeFragment`, including in a `typeRef` target |
| `limit-exceeded` | over `maxFieldsPerExtension` or `maxTypeDepth` |
| `invalid-element` | an extension that fails the grammar; for a stateSpans kind, a restated member of a `wellKnownRef` entry or a `sameAs` that breaks §9's checks (any other grammar failure outside `spec.extensions` rejects the whole registration as `invalid-registration`, §5.2) |
| `version-plan-invalid`, `unsupported-availability`, `unsupported-horizon` | checked only where the hub interprets them |
| `version-conflict`, `unknown-well-known-kind` | §7 |
| `unknown-shared-slot` | §9 |

Reason codes are an open vocabulary (`other` with the hub's term); `detail` is for people.

The outcome is `accepted` when every element is accepted and `partial` when at least one is
rejected; both store the registration as written (201 on create, 200 on update). An accepted
element may carry `carrierView` (§13). A controller that does not know an element result, reason
or `carrierView` value treats the element as not accepted.

### 5.4 Etag and idempotency

The etag is `sha256:` over the RFC 8785 canonical JSON of `{registration, state, boundTo}`
(`registration` and `boundTo` null for a pre-emptive block), so it changes on every change of
content, state or binding. The credential kind, the binding event and freed namespaces are stored
beside it and are not in it. A request whose content and state are already stored is a no-op
(200, `noop: true`, the stored etag), so a create retried after a lost response succeeds. A stale
`If-Match` with different content is 412 `stale-etag`; `If-None-Match: *` over different content is
412 `registration-exists`. The hub evaluates a stored registration against its current
capabilities on every read, so an element's result can change after a hub upgrade while the stored
registration and its etag do not.

### 5.5 Retire

The bound controller retires with `api:registrations:delete`; the owner may also retire. Retiring
sets the state to `retired`, changes the etag, and keeps the declaration and the binding frozen:
data already stored under it stays stored and readable as declared, and no typed write is accepted
for its elements. Its namespaces stay claimed until the owner frees them. A later `PUT` with the
retired etag reactivates it; a freed namespace is claimed again only if no other registration holds
it by then, and otherwise that extension is rejected `namespace-claimed`. The controller writes its
carriers from the moment it retires.

## 6. The controller's side: fallback and refused writes

An element is written through the typed API only when the response to this registration has
outcome `accepted` or `partial` and the element's result is `accepted` or
`accepted-with-ignored-members`. Everything else falls back to the element's carrier (§5.3): a
rejected element; an unknown result, reason or `carrierView`; a rejected registration; a failed
precondition; a retired or blocked registration; no response (a submit answered 429 or any 5xx is
no response); no capability document, no `submit`, or a grammar major the hub does not list.

A controller that depends on an ignored member may treat that element as not accepted.

An accepted element whose `carrierView` is `served` is written typed only. One whose view is not
served is written typed only, or typed and as its carrier when the element declares
`dualWriteLink` (`typedIdPath`, `carrierIdPath`): the record is linked by (instance id, the
controller's record id), so counting and de-duplication follow the link. Writing both is for an
element with no declared carrier mapping, and while an app moves over.

A typed write refused for load (429 or any 5xx, with or without `Retry-After`) is retried with
backoff, no sooner than `Retry-After` when sent, until it succeeds. It is never written as its
carrier, the record is not dropped and the write plan does not change, so a write the hub stored
before failing cannot appear twice. Any other refusal is definite (`blocked-by-owner`, a retired or
missing registration, `instance-required`, a typed route answering 404 after a hub rollback, or a
4xx the controller does not know): the controller sends that record as its carrier at once and
treats the element as not accepted until its next re-check (§4).

The capability document carries everything the response depends on except the tenant's stored
registrations with their bindings and blocks, the credential's grants, and whether the hub serves a
carrier view of an element. A controller can predict most of the result before it submits; the
response is authoritative.

## 7. Definitions

The product resource registers what a controller's data means. Definitions let several releases
and builds of one product coexist; instances (§8) say which copy is connected.

| resource | method | who | meaning | precondition |
|---|---|---|---|---|
| `<…>/<product>` | as §5 | as §5 | the product: binding, state, owner actions, namespaces, etag, element results. Its body is a definition | as §5 |
| `<…>/<product>/definitions/<definitionId>` | `PUT` | the credential the product is bound to | add a definition, immutably | `If-None-Match: *` only |
| `<…>/<product>/instances/<instanceId>` | `PUT` | any credential with `api:registrations:create` | create, renew or change an instance | as §5 |
| `<…>/<product>/instances/<instanceId>` | `DELETE` | the credential the instance is bound to, with `api:registrations:delete` | release the instance and all its roles | `If-Match` |

A hub that advertises `instances` serves the two added resources; one that does not serves
neither, and §5 applies unchanged.

**Identity.** The definition id is defined in [identity §2](identity.md#2-contract-ids). A product
`PUT`'s accepted or partial response names the `definitionId` the hub computed. Every definition
the hub accepts is stored content-addressed: the product's current registration, every
registration a product update replaced, and every definition added by `PUT`. Any number coexist
under one product.

**Adding one.** Order of checks: (1) authorisation: the owner never adds one (403
`not-authorised`); the permission; a registered product (404); the product's binding (403
`not-registration-owner`). A definition `PUT` never binds a released product, because a binding
changes the product's etag and a definition never does; the controller re-binds with a product
`PUT`. (2) `If-None-Match: *` (428 otherwise); a blocked product is 403 `blocked-by-owner`, a
retired one 409 `product-retired`. (3) The body's hash equals the path id (422
`definition-id-mismatch`), then §5.2 step 3. (4) Element results as §5.3, plus the rules below. An
identical retry is a 200 no-op. Adding a definition never changes the product resource or its
etag, so instances of one product never contend on it.

**Namespaces belong to the product** across all its stored definitions: another product's
definition declaring any of them is rejected `namespace-claimed` until the owner frees it.

**One element at one version has one meaning.** Within one product, an element of a new
definition (a stateSpans kind or an extension namespace) whose stored version equals that of the
same element in a stored definition, and whose meaning differs, is rejected `version-conflict`.
This applies to definition `PUT`s and to product `PUT`s, where an update is compared with the
registration it replaces, which stays stored. A different meaning needs a new version; definitions
that agree, or declare different versions, coexist. The version compared is `version` or
`versions.stored`; an element that declares none is one unversioned version. Typed settings fields
and replay inputs carry no version in grammar v1 and are not compared.

| | members that are meaning | not meaning |
|---|---|---|
| stateSpans kind | `category`, `kind`, `slot`, `exclusiveWithinSlot`, `coexistsWith`, `overlay`, `supersedes`, `states`, `endReasons`, `wire`, `dualWriteLink`, `requested`, `applied`, `initiators`, `definitions`, `acceptsFromHub`, `horizon`, `sameAs` | `description`, `evidence`, `availability`, `version`/`versions`, members the grammar does not define |
| extension | `carrier`, `dualWriteLink`, `horizon`, `fields` (compared by `name`) | `description`, `evidence`, `availability`, `version`/`versions` |
| extension field | `name`, `type`, `typeRef`, `unit`, `range`, `horizon`, `sensitivity` | `description`, `evidence` |

Inside a meaning member, `description`, `evidence` and a carrier's `writtenWhen` are prose and not
compared, and order is not meaning: an array of strings compares as a sorted set, an array of
objects as the sorted list of their canonical forms. `availability` is a promise level, so an
experimental kind can be released at the same version. `sensitivity` is meaning, so a later
definition cannot relabel data stored under an earlier one.

**Well-known references.** A stateSpans entry whose kind is exactly a kind of the hub's catalogue
names it instead of copying it: `wellKnownRef: {catalogue, kind, version}`, where `catalogue` is the
`id` of an entry in the capability document's `wellKnown.kinds[]`, `kind` is the catalogue kind's
`kind` (else its `category`) and `version` its stored version. `wellKnownRef` is additive under
must-ignore. The entry carries only
`category` and `kind` (the catalogue kind's), the reference, `availability`, `description` and
`evidence`; a restated member is rejected `invalid-element`. Its meaning, version, slot, carrier and
`sameAs` are the catalogue kind's, so an identical copy agrees with a reference and a differing copy
at that version is `version-conflict`. A reference to a kind the catalogue does not have at that
version is rejected `unknown-well-known-kind`, and the controller writes that kind's carrier. Only a
catalogue kind that declares a version can be referenced; the three well-known registrations
declare none, so none of their kinds can be referenced until the generator versions them.

## 8. Instances

**Identity.** The instance id is defined in [identity §2](identity.md#2-contract-ids): a random
lowercase UUID v4 supplied by the controller.

**Body** (`controller-instance.schema.json`): `apiVersion`, `kind: ControllerInstance`,
`definitionId` (a stored definition of this product, else 422 `unknown-definition`), `roles[]` and
`labels{}`. An instance carries no hardware identifiers; anything identifying a controller reports
is a typed, sensitivity-labelled field of its definition.

**Observed alias.** The hub may record the free-text `devicestatus.device` it sees in an
instance's writes as an observed alias, labelled `{level: identifying, category: device}`. It is
withheld by default: absent from the owner's default listing (shown only when the owner asks for
withheld members), never in the capability document, never in a default export, and never the
instance's identity.

**Order of checks for `PUT`.** (1) Authorisation: the owner never writes an instance (403
`not-authorised`); the permission; a registered product (404); an existing instance's binding (403
`not-registration-owner`). An instance is bound to the subject that created it (or the shared
secret on `single`), not to the product's binding, so a development build with its own subject may
run a copy of a registered product. (2) Preconditions: none is 428; `If-None-Match: *` over a
different stored body is 412; an `If-Match` that is not the current etag is 412 `stale-etag` with
the current etag and lease; then a blocked product is 403 `blocked-by-owner` and a retired one 409
`product-retired`. (3) The instance as a whole, each 422 with nothing stored: the id form
(`invalid-instance-id`), labels (`invalid-label`), the schema (`invalid-instance`, including a role
without provenance and a (channel, role) claimed twice), `unknown-definition`. (4) Each role (§9).

**Lease.** Each create or renewal sets `leaseExpiresAt` to now plus `instances.leaseSeconds`; the
response carries it and per-role results (outcome `accepted`, or `partial` when a role is refused;
201 on create, 200 on renewal). An instance that stops renewing lapses and holds no roles, with no
housekeeping. A renewal is not a capability re-check.

**Etag.** `sha256:` over the canonical JSON of `{instance, boundTo, granted}`. The lease is outside
it, so a renewal that changes nothing keeps it (`noop: true`) and a retried renewal still matches.
A role granted on renewal, moved by the owner, or dropped by a rebind (§9) changes it, so the
instance learns of the change through a 412 on its next renewal, and two owner actions racing on
one instance meet 412. A create retried with the same body by the same subject is a renewal.

**`DELETE`** releases the instance and all its roles. Records it wrote keep its id.

## 9. Channels, roles and provenance

**A role** is `{channel, role, provenance}`:

- `source`: the instance writes the channel's typed records as their source of record.
- `command-sink`: the instance accepts hub-originated commands for the channel. Only on a channel
  whose kind declares `acceptsFromHub.channels` with `command`, else `not-a-command-channel`.
- `{value: other, controllerTerm}`: any other role, such as an agent's. A hub grants only the roles
  its capability document lists (`unsupported-role` otherwise); a bare unknown string is invalid.

`provenance` is required and closed: `device` or `simulated`. One instance may mix them (a
development build with a real CGM and a simulated pump). An unknown provenance refuses that role
(`unknown-provenance`), never the instance. Only `device`-provenance data is therapy data in default
views and exports.

**Channels.** For a stateSpans kind that declares a `slot`:

- if the slot is on the hub's shared slot list (`wellKnown.slots`, shipped from
  `specs/sync/shared-slots.yaml`: `override`, `loopMode`, `temporaryTarget`), the channel is that
  shared slot, contended across products;
- if the kind declares `sameAs: <shared slot>` on a hub that interprets `sameAs` and lists that
  slot, the channel is the shared slot;
- otherwise the slot is the product's own channel, `<vendor>/<product>/<slot>`: on the wire the
  channel keeps the slot's name and its roles are scoped to the product; instances of one product
  contend on it, and equal names from different products do not.

Every other element's channel is `<vendor>/<product>/<element id>`. A slot name containing `/`
derives no shared channel. A role on a channel the instance's definition does not derive is
refused `unknown-channel`. Two slots are joined only by a listed name or a declared `sameAs`, never
because their names look alike: AndroidAPS's `runningMode` and Loop's and Trio's `loopMode` stay
separate until a definition or a catalogue mapping says otherwise, as do names that differ only in
case. The owner's listing records each unlisted slot name used by two or more products as
`slotNameObservations`, for the catalogue to act on.

**`sameAs` checks**, at a product or definition `PUT`: a shared slot the hub does not list, or a hub
with no list, is `unknown-shared-slot`; a `sameAs` without a `slot` (or with `/` in it), on a slot
whose own name is a different shared slot, or disagreeing with another entry of the definition that
names the same slot, is `invalid-element`. A refused element goes as its carrier and its slot
derives no channel, so it never joins another product's slot by name instead.

**Exclusivity.** Among live `device`-provenance instances of active products on the tenant, each
(channel, role) has one holder. A second claimant is refused that role `role-held`; its other roles
are granted, and it writes the elements on that channel as their carriers. The hub shows the overlap
on the owner's listing (channel, role, claimant, holder) until the claimant drops the claim or
lapses; `holder: null` when the holder has lapsed or dropped the role. `simulated` roles never
contend with `device` roles or with each other.

**Command-sink binding.** A `device` command-sink role goes only to an instance whose binding
equals the product's `boundTo`, or to one the owner moved it to with `transfer-role` (stored with
`grantedBy: transfer-role`); any other `device` claim is refused `not-registration-owner` for that
role, after the channel checks and before exclusivity. A `simulated` command-sink claim is open to
any permitted subject and never receives a routed command. Source roles are open to any permitted
subject. When a product's `boundTo` changes (the owner's `transfer` or `release`, or a released
registration bound by its next writer), every `device` command-sink role held by an instance whose
binding no longer matches is dropped at once and stored refused `not-registration-owner`, and that
instance's etag changes; roles with `grantedBy: transfer-role` are kept. A held `device`
command-sink survives renewal only when the instance matches the binding or the role carries
`grantedBy`.

**Handoff.** A role passes when its holder drops it (a renewal without it, or `DELETE`), when the
holder's lease lapses, or when the owner transfers it. A lapsed or dropped role is not
auto-assigned: a claimant is granted it on its own next renewal, which re-evaluates every claim.

**Command routing.** A command for a channel goes to the live `device` instance holding
`command-sink` on it. A command that names no product for a channel that is not shared goes to the
one product that declares that channel; when more than one product declares it, it is refused 409
`ambiguous-command-destination`, and naming the product (`request.identity`) resolves it.
"Declares" reads every product's current registration and stored definitions, in any state. With
no holder, or a channel no product declares, the command is refused `no-command-destination`; the
hub never routes to a lapsed former holder, a `simulated` command sink or the product's latest
instance. The command API itself is `SPEC-REG-COMMANDS`.

**The hub never decides dosing.** Exclusivity decides only which instance is the typed source of
record for a channel and where a command for that channel is routed. A claimant refused a role keeps
running and keeps writing its carriers; the hub records what each instance reports.
`devicestatus` and other documents are not channels: writes to them are attributed by instance,
and loop-status exclusivity is not specified until `devicestatus` decomposition is typed.

## 10. Labels

String keys to string values, which distinguish, select and filter instances. A key is
`<reverse-DNS namespace>/<name>` (`com.example.testcontroller/rig`); labels are not subject to
namespace claims. The prefix `dev.nightscout/` is reserved for `dev.nightscout/purpose`
(`therapy`, `development`, `lab`, `research`), `dev.nightscout/build` (`release`, `dev`) and
`dev.nightscout/migration-group` (an opaque string shared by the old and new phone of one
migration). A reader reads an unlisted value of the first two as `other`. Another key under the
prefix, a key not in the form, a non-string value, or labels over `instances.labels` bounds are
refused `invalid-label`. Labels carry no names, device names or serials. Provenance, never a label,
decides what is therapy data.

## 11. Typed writes and attribution

A hub that advertises `instances` requires an instance id on every typed write (proposed as a
request header). An instance-less typed write is refused 422 `instance-required`, a definite
refusal (§6). The writing instance must be live (409 `not-live`) and hold `source` on the element's
channel (409 `role-held` when another instance does, `role-not-granted` otherwise), so a refused
claimant's record goes as its carrier. An accepted typed record carries its instance, its
definition and the role's provenance.

Writes with no instance (older controllers, and anything the well-known tier describes) are
attributed to an implicit unregistered instance of the product, which holds no roles and is never
refused for exclusivity. Exclusivity never blocks a carrier write, from any instance. Readers
attribute typed records to the registration and its bound credential; a namespace string proves
nothing about authorship.

The ids each write returns, and how a re-send is matched, are in [identity §1](identity.md#1-rules).

## 12. Read selection

Writes need no selection: each instance names its definition. A view chooses, per versioned
element of a product, the version it shows:

1. the operator's capability document limits what is accepted at all: only versions of stored
   definitions whose element the hub accepts today are candidates;
2. the owner's pin, for the site's default views;
3. the newest version run by a live instance holding a `device` `source` role on the element's
   channel;
4. the newest stored version.

A view with a label selector (every selector key must have that value) uses only the live instances
that match, whatever their provenance, and no pin. "Newest" compares dot-separated parts, numeric
parts as numbers and before text. Pins are the owner's `pin-version` and `unpin-version`, a resource
of their own per product with its own etag (`If-None-Match: *` for the first pin, `If-Match`
after), so a pin never changes the product's etag or stored data. A pin names a version some stored
definition stores (422 `unknown-version`).

## 13. Projected views for older readers

An accepted element's `carrierView: served` requires a declared mapping: the catalogue's carrier
for a referenced well-known kind, the kind's `wire`, or an extension's `carrier`. A hub that would
serve a view of an element without one reports `not-served`, and the controller writes as §6
says. For a served element, each typed record is served to API v1 and v3 readers as a projected
document in the carrier's shape: the collection, `eventType`, start time and duration in the wire's
unit (or its indefinite sentinel) from the mapping, and nothing the mapping does not declare. The
projected document is labelled `projectedFrom: {definitionId, element, entities}`, is never stored
as a source, and is read-only (409 `projected-read-only`); its ids are in
[identity I8](identity.md#1-rules). Where one carrier document is projected from several entities,
the id is the primary entity's and `entities` lists them all. A projection without a declared
mapping is refused 409 `no-carrier-mapping`.

A projected view is not a conversion between typed versions (G4).

Prior art, read-derived at Nocturne `42275c812`: `V4ToLegacyProjectionService` and
`LegacyTreatmentTables` serve v1–v3 reads from V4 records, project a meal bolus from a bolus and a
carb intake under the bolus's id, and tell legacy mirrors from V4-native records with a
`NativeOnly` filter; the projected treatment carries no projection marker.

## 14. Retention

A definition may be removed only when no stored record references it, no live instance runs it,
and it is not the product's current registration (otherwise `definition-referenced`,
`definition-in-use` or `definition-current`). Each record's declared horizon retention decides when
the record goes.

## 15. Binding, credentials and the owner

`SPEC-AUTHORITY` will carry this section into the authority specification.

### 15.1 Binding and credential kind

A create or update binds the registration to the credential that wrote it: `boundTo: {kind:
subject, subject}`, never the token, so a token rotated on the same subject changes nothing; or
`{kind: api-secret}` for the shared secret on `single`, which any holder of the secret presents. The
stored registration records `credentialKind` (`subject`, `api-secret`, or `other` with the hub's
term), the kind that last created or updated it; both are returned with it. `API_SECRET` against a
subject-bound registration is `not-registration-owner` on the data path. A released registration
(`boundTo: null`) is bound by the next credential with the permission that updates it, even with
identical content (200, not a no-op); it records `bindingEvent: next-writer`, kept by later updates
under the same binding and cleared by a release or transfer, and not in the etag. When a
single-tenant site moves into a tenant, a registration bound to `api-secret` is bound to the
tenant's root credential, a further credential kind; the etag changes with `boundTo` (decided;
the mechanics are `SPEC-REG-MODES` and `SPEC-REG-MIGRATE`).

### 15.2 The owner's actions

On the owner's listener. The owner never edits a registration's content (an owner `PUT` is 403
`not-authorised`) and never submits one. An action other than retire answers outcome `applied`
with the resource after it; a request for what is already the case is a no-op.

| action | effect |
|---|---|
| retire | §5.5 |
| block | state `blocked`, recording the interrupted state as `blockedFrom`; etag changes; declaration, binding and stored data kept frozen; the controller's writes and typed writes are refused 403 `blocked-by-owner`. With `If-None-Match: *` it blocks an identity with nothing stored (stored with no registration), and a create for it is 403 |
| unblock | restores the interrupted state (`active`, or `retired`); removes a pre-emptive block; never reactivates a retired registration. A blocked registration is unblocked before it is retired (409 `blocked-by-owner` otherwise) |
| release | `boundTo: null`; §15.1; drops non-matching `device` command-sinks (§9) |
| transfer | binds to a named subject; drops non-matching `device` command-sinks (§9) |
| free-namespaces | a retired registration's namespaces are no longer held by it (409 `not-retired` otherwise); its declaration and stored data stay readable |
| transfer-role | moves one role from its holder to a live instance that claims it with `device` provenance (409 `role-not-granted`, `role-not-claimed` or `not-live` otherwise); `If-Match` the etag of the instance it is moved from; both instances' etags change; the moved role records `grantedBy: transfer-role` |
| pin-version, unpin-version | §12 |
| listing | every instance with its roles, labels and liveness; the overlaps; `registrations` (every stored product with its `boundTo`, `credentialKind` and `bindingEvent`); `slotNameObservations`; observed aliases only when asked |

An owner action on the data listener is 403 `not-authorised`.

### 15.3 Authorisation

- **The submitter is the controller, a device.** It holds the native per-tenant credential (D17
  row 1). Submit, update, read and retire are on the data listener with that credential. Under
  `TENANCY_MODE=multi` there is no deployment secret (D13) and the credential's token is signed
  with the tenant's key (D14), so a registration is per tenant and a controller on two tenants
  registers twice. On `single`, `API_SECRET` may also register and is recorded as `api-secret`.
- **Permissions.** Submitting needs `api:registrations:create` and retiring
  `api:registrations:delete`, granted by the tenant owner on `ns-tenant-admin` (D16). Updating and
  retiring also need the binding.
- **Storage.** Registrations, definitions and instances are tenant data: per tenant, under RLS
  under `multi` (D3), never in the public capability document.

### 15.4 Namespaces

First to claim, per tenant. A credential with no stated namespace roots may claim any namespace no
other registration on the tenant holds. A hub may restrict a credential to owner-granted roots; a
registration may then declare a namespace equal to or below one of them (`com.example` covers
`com.example.negotiation.targets`; `com.examplefoo` does not), else `namespace-not-owned`. Either
way a namespace another registration holds is `namespace-claimed`. A retired registration holds its
namespaces until the owner frees them. Readers spanning tenants interpret a field by the
declaration carried with it, never by its namespace. A published list of namespace conventions may
record use; it is never a check.

## 16. Version-scoped quirks

The [quirks registry](../../../../specs/quirks/README.md) records how stored documents deviate,
per collection and project, with measured prevalence.

| # | rule |
|---|---|
| Q1 | **`affects`.** It applies to stored documents and to declarations (slot names, units, vocabulary). An entry may carry `affects: [{vendor, product, versions}]`, `versions` a range over the vendor's own version strings (`*`, or whitespace-separated comparators `=`, `>=`, `>`, `<=`, `<` that must all hold; dot-separated parts compare numerically, numbers before text), stated only where the corpus or source shows it, else `unmeasured` with the reason. `seen` lists versions the evidence shows. Each claim says `measured` or `read-derived`. `versionSource` says where `make schema-quirks` reads a version: in the same document, or by co-occurrence (the nearest version-bearing document of the same site within a window), labelled as co-occurrence and never copied into a range. Entries without `affects` keep their project-level attribution. |
| Q2 | **Catalogue for older versions, `sameAs` for newer.** A newer definition declares its own mapping (`sameAs`, §9). Versions released before registration get it from a registry entry with `applies_to: declarations` (`declaration: {member: slot, value, sameAs}`, with `affects`), published as `wellKnown.mappings[]` (`{quirk, vendor, product, versions, slot, sameAs}`). When an older controller's write is described by its well-known registration and the hub knows the writer's version and it is in `versions`, the hub attributes the records to the shared slot. A mapping changes which channel records are shown on and which overlaps the owner sees, never whether they are stored. |
| Q3 | **Recorded, never silent.** Each mapping the hub applies is recorded on the reply and on the stored record or document as `quirksApplied: [{quirk, member, action, sameAs?}]`, `action` one of `moved-to-identifier`, `dropped`, `same-as`. A write whose channel a `sameAs` decided carries `slotMapping: {slot, channel, by}`, `by` being `declared`, `catalogue` (with the entry's id) or `name`. |
| Q4a | **Entry members.** Beside `affects`, an entry may carry `retired`, and `mapping: {action, flag, erasesEvidence}` for what a hub does with the quirk: QUIRK-TREATMENTS-006 and QUIRK-ENTRIES-004 carry `{action: move-to-identifier, flag: UUID_HANDLING, erasesEvidence: true}`, because a mapped write no longer shows the quirk in storage. QUIRK-TREATMENTS-007 (Trio's treatment model sending its UUID as `id`) is a measured, version-scoped entry with no mapping: cgm-remote-monitor matches such treatments by `created_at` + `eventType`, and whether Trio should send `identifier` goes to `PROPOSAL-REG-CONTROLLERS`. |
| Q4 | **Lifecycle.** `proposed` → `active` → `historical` → `retired`. `make schema-quirks` writes which statuses the measurement supports and why not the others; `make schema-quirks-check` fails a `historical` or `retired` claim it does not support and never fails a `proposed` one. `historical` needs no recent document, zero live instances of an affected version in a hub's de-identified instance listing (unmeasured without one), and a detector whose evidence the hub's mapping does not erase (an entry whose `mapping` has `erasesEvidence: true` becomes `historical` only through Q3 records). `retired` also needs no stored document that depends on the mapping. Recent is within `RECENT_DAYS` = 365 days of the newest snapshot's collection date. Declaration entries are measured by a hub's recorded mappings. |

## 18. Open choices

Rules the specification chose that await the maintainer's confirmation:

- **Product (§5, §15):** unblock restores the interrupted state; a blocked registration is
  unblocked before it is retired; `credentialKind` is the kind that last created or updated it;
  reactivation reclaims a freed namespace only if no other registration holds it; the cases assume
  a controller does not treat an element as not accepted merely because it depends on an ignored
  member.
- **Definitions and instances (§7–§12):** a definition `PUT` never binds a released product;
  definitions and instances are refused for a retired product; the instance etag covers granted
  roles; every listed role, including an `other` role, is exclusive among `device` instances; a
  typed write needs a granted `source` role; the owner transfers only to a live instance already
  claiming the role with `device` provenance; pins are their own resource; "newest" is numeric by
  part; a label selector ignores provenance and pins; the current registration keeps its
  definition from removal; typed settings fields and replay inputs are outside `version-conflict`;
  `wellKnownRef` needs a versioned catalogue kind; the permission names reuse
  `api:registrations:create` and `delete`.
- **Quirks (§16):** the shipped slot list holds the three names already used identically;
  `unknown-shared-slot` refuses the element rather than falling back to the slot's own name;
  catalogue mappings need a known writer version; `historical` needs a hub's instance listing; a
  mapping that erases its evidence makes `historical` depend on Q3 records; a `proposed` entry never
  fails the check; declaration entries are measured only by hub records.
- **Identity:** two choices are listed in [identity §5](identity.md#5-open-decisions).

Not yet specified: the contract per tenancy mode (`SPEC-REG-MODES`), the mechanics of registration
state across a site's move into a tenant, whose binding rule §15.1 states (`SPEC-REG-MIGRATE`), and the command API (`SPEC-REG-COMMANDS`).
