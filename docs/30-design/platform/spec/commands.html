    L3 and L5 Commands: how a request or a proposal reaches a controller, and how its outcome comes back¶

    Living document, last changed 2026-10-26 at 36487a5dd.

    Contributor-facing. Living specification, current at main 9736bd65 (2026-10-18). Layers L3 and L5 of the platform index; terms are in the glossary. Decisions: D18 and D19 and the maintainer's decisions of 2026-10-14 to 2026-10-18 recorded with them; the proposal record was folded into this item on 2026-10-18. Queue: SPEC-REG-COMMANDS.

    Specification 5 of 8 in the reading order; after state and intent, whose acceptance policy (S10, S11) it builds on, and before plans, which builds on its proposals. Expect where a command goes, the command path today, rules CM1–CM32 for the command record, outcomes, proposals, delivery in each mode and the request paths, compatibility with each controller, and the conformance cases.

    How a request to change therapy reaches a controller through a hub, what the hub records about it, how the controller's outcome comes back, and the proposal and approval that can stand in front of a command. The hub routes and records; it never decides whether a change is safe, never alters what was asked, and never doses (D18). Validation and enactment stay the controller's.

    Status: §2 is specified; §3 and §8 are evidenced; §4–§7 are proposed and specified with cases; none is implemented.

    2. Where a command goes¶

    A command names a channel (registration §9). It goes to the live device instance holding command-sink on that channel, on the command's tenant. A command that names no product for a channel that is not shared goes to the one product that declares that channel; when more than one product declares it, it is refused 409 ambiguous-command-destination, and naming the product resolves it. "Declares" reads every product's current registration and stored definitions, in any state. With no holder, or a channel no product declares, the command is refused 409 no-command-destination. The hub never routes to a lapsed former holder, a simulated command sink, or the product's latest instance. Which instance may hold the sink is authority §6.

    3. Commands today¶

    Read from cgm-remote-monitor at the 15.0.8 release (92d08342), dev (fade2299) and the multitenancy seam branch (81a1f6ce), 2026-10-18; "run" marks what was executed.

    One path carries a command. POST /api/v2/notifications/loop (lib/api2/notifications-v2.js, line 17 at 15.0.8, 21 on dev) hands a request to lib/server/loop.js, which sends an APNs push to Loop.

    what the hub does
    permission notifications:loop:push; of the default roles only admin holds it, so a caller needs API_SECRET, an admin token or a custom role (lib/authorization/storage.js:232-238 on dev)
    commands four eventType values: Temporary Override, Temporary Override Cancel, Remote Carbs Entry, Remote Bolus Entry; anything else is refused "Unhandled event type" (loop.js:67-110 on dev; run)
    payload the command's fields, remote-address, notes, entered-by, sent-at, expiration five minutes ahead, and otp only when the sender gave one (loop.js:61-126); no command id, nonce or signature, and no limit on an amount beyond "greater than zero"
    the one-time password forwarded, never checked; checking it is the controller's
    destination the device token and bundle id in the latest profile's loopSettings (loop.js:31-47); Trio publishes its token at the profile's top level, so this path does not reach Trio
    credentials the deployment's LOOP_APNS_KEY, LOOP_APNS_KEY_ID and LOOP_DEVELOPER_TEAM_ID, read only when ENABLE includes loop; without it, or with it but no LOOP_* variable set, extendedSettings.loop is never created and the route fails with a TypeError at loop.js:16 (run without ENABLE, all three commits; read for the second case, lib/server/env.js:281 on dev)
    what is stored nothing: neither file writes to a store, and the careportal's submit hook replaces its treatment write, so no treatment is stored either
    response 200 when APNs accepted the push (loop.js:139-141 on dev); it says nothing about delivery, the password or enactment
    outcome none: no route, collection, socket event or field records that a controller received, accepted, refused or enacted a command

    Senders are the careportal's Loop plugin (lib/plugins/loop.js:110-180 on dev) and the NightscoutKit fork LoopCaregiver uses, for overrides, bolus and carbs when its newer remote-command option is off; LoopCaregiver sends closed-loop and automatic-bolus changes to /api/v2/remotecommands whatever the option, a route neither cgm-remote-monitor nor Nocturne implements. Trio, LoopFollow and AndroidAPS do not call this route.

    Everything else is data. Temporary Target, Profile Switch and Announcement treatments are stored and broadcast like any other record; a controller that downloads treatments may act on them by its own rules, and the hub does not know whether it did. AndroidAPS dev writes signed command envelopes and acknowledgements to the API v3 settings collection; the hub stores them as documents and reads none of them. What each controller does with these paths is in state and intent §7.

    Under TENANCY_MODE=multi, on the seam branch:

    • the request is bound to its tenant (lib/server/tenant-middleware.js:263-272), but nothing on the APNs path reads the binding: ctx.loop is built once per process (lib/server/bootevent.js:229), so the key, team id and device lookup are the deployment's, against one process-wide copy of the loaded data;
    • multi requires PostgreSQL, and the PostgreSQL store at that commit implements only entries (lib/storage/postgres-storage.js:127-133), so no tenant's profile or treatments can be stored;
    • socket emissions go to the bound tenant's room and are withheld when no tenant is bound (lib/server/socket-tenancy.js:157-170,255-267). The dataUpdate and alarm events come from the process-wide load cycle and are withheld; storage events from an API v3 request reach their tenant.

    CM19 and CM20 are written against these two facts: a signal from the load cycle reaches no one under multi, and the only push credential today is the deployment's.

    4. The command record (proposed)¶

    # rule
    CM1 The hub records a command before it sends it. A command the hub accepts is stored as a record: commandId (assigned by the hub), its tenant, channel, the product named or inferred, the destination's instanceId and definitionId as routed, the payload exactly as received, payloadHash (sha256: over the payload's RFC 8785 canonical JSON, the rule D19 uses for definition ids), the initiator in the form state and intent S8 gives it, the subject that sent it, proposalId and the proposal's basedOn when it came from an approval (§6), createdAt, expiresAt and state. A command refused at routing (§2) is recorded as not-routed, with its reason, and never sent.
    CM2 Routed once. The destination is fixed when the command is accepted; it is never re-routed to a later holder, which would enact a request its sender addressed to another device. If the destination lapses or loses its role while the command is pending, nothing was handed over, whatever signals were sent (CM27), and the command becomes undeliverable. If that happens after it was fetched, the controller has it: the command keeps its state, and the destination's report is accepted (CM7).
    CM3 An expiry is required. A command without expiresAt, or with one not after the request's time, is refused 422 expiry-required; one more than the hub's commands.maxExpirySeconds after the request is refused 422 expiry-too-long. Times are the hub's. A command at or past its expiry is never signalled or fetched. At its expiry a pending command becomes expired, because nothing was handed over; a fetched command becomes unconfirmed, because the controller may have enacted it; an acknowledged command keeps the controller's state. A hub never reports a command that may have been enacted as expired or undeliverable, which a sender would read as safe to send again.
    CM4 Re-sending a request. A sender may give a requestId. Within a tenant and subject, a second command with the same requestId, channel, product as the request names it (naming none differs from naming the one that would be inferred) and payloadHash returns the first command and its current state; with any of them different it is refused 409 request-id-reused. Without a requestId, every request is a new command.
    CM5 The hub does not judge. The hub checks only that the channel accepts commands, the routing, the expiry, the size (a payload over the hub's commands.maxPayloadBytes of canonical JSON is refused 413 payload-too-large) and the sender's permission (403 not-authorised without api:commands:create). It never checks a dose, a limit or the therapy state, and it never changes the payload.
    CM6 Tenant isolation. A command's tenant is the tenant its request resolved to. Routing, sending, fetching, proposals, reports and reads see only that tenant: a command, proposal or instance from another tenant is 404, as one that does not exist is, so a request never reveals that it exists.
    CM24 The outstanding list. For a channel, the hub lists every proposal that is open and every command that is not final, with its sender or proposer, initiator, createdAt, expiresAt and state, and the times of the dose and carb records for the channel's products that reached the hub since the earliest of them, and, under destinations, each live holder of the channel's sink with its fetch bound (CM30). A reply that accepts a command or an approval carries the list of the other items when there are any. Anyone holding api:commands:read, api:commands:create or api:proposals:read on the tenant may read it, so a follower can see the queue without acting on it; anyone else is 403 not-authorised.
    CM25 Cancel. The sender of a command, or the subject acting for the person (CM14), may cancel it; anyone else is 403 not-authorised. A pending command becomes cancelled, which is final, and is never sent or fetched. A command already fetched or acknowledged stays in its state with cancelRequested (202): the destination's fetches carry the cancel until it reports (CM26), and the controller, deciding the command once (CM21), refuses it with reason cancelled if it has not decided it yet. A command with a final state is 409 already-final.

    Order of checks. Where more than one refusal applies, the first wins: another tenant (404), then the sender's permission and ownership (403), then the request's own content (413, 422), then state (409). Among an approval's 409s the order is: the proposal's state (proposal-expired, proposal-closed), hash-mismatch, routing, destination-changed, state-changed, doses-since. A signal checks the binding (withheld), then the command (expired, then nothing-waiting when no fetch would return it or its cancel, CM26), then the transport (no-live-transport, then no-tenant-credential). Without the capability's commands member every path in CM32 is 404 (CM31).

    States. The hub sets pending, not-routed, fetched, unconfirmed, undeliverable, expired and cancelled; only the destination sets acknowledged, succeeded, failed and refused (§5).

    state set by means
    pending hub accepted and routed; not yet fetched, whatever signals were sent (CM27)
    not-routed hub refused at routing (§2); its reason is recorded
    fetched hub the destination instance read it with its own credential (CM18); a receipt, not an outcome; returned again by each fetch until the controller reports (CM26)
    unconfirmed hub fetched, with no outcome, and its expiry passed. It may have been enacted (CM3)
    undeliverable hub the destination lapsed or lost its role before it fetched the command (CM2)
    expired hub its expiry passed before the destination fetched it (CM3)
    cancelled hub its sender or the person cancelled it before anything was handed over (CM25)
    acknowledged controller received; validating or enacting
    succeeded controller enacted
    failed controller accepted but not enacted, such as a pump that did not respond
    refused controller declined by the controller's own checks

    succeeded, failed, refused, not-routed, undeliverable, expired and cancelled are final; the hub sets the last four only for a command that was never fetched. A signal, fetched and unconfirmed are never reported as success or as failure.

    5. Outcomes (proposed)¶

    # rule
    CM7 Only the destination reports. An outcome report names the commandId and is accepted only from the bound subject of the destination the command was routed to, whether or not that instance still holds the role; any other subject is refused 403 not-registration-owner. The report carries state (acknowledged, succeeded, failed or refused; any other is 422 invalid-state), the payloadHash the controller computed over the payload it received, a reason when refused or failed, and, when enacted, the identity of the record that shows the effect (how the link works is open, §9 item 9; effect-link prototype) (identity). A reported hash that differs from the command's is recorded as reported, with the record marked as a mismatch; the hub does not refuse it, because the report is evidence of what the controller did.
    CM8 Reasons. A refusal or failure reason is one of hash-mismatch, expired, not-accepted (the controller's acceptance preference is off, S10), limit (a limit the controller enforces), doses-since (CM23), cancelled (CM25) or {value: other, controllerTerm}; a bare unknown string is refused 422 invalid-reason. The hub records the reason and does not interpret it.
    CM9 One outcome. After a final state, a further report is refused 409 already-final. A report on an unconfirmed command is accepted and replaces it: that state is the hub's inference, and the controller's report of what it did is better evidence. acknowledged may precede a final state and may be skipped.
    CM10 The controller checks the hash. Before enacting, the controller recomputes payloadHash over the payload it received and refuses hash-mismatch when it differs from the hash the command carries. It also refuses a command past expiresAt by its own clock. These checks are the controller's, as all validation is (D18). The controller receives the payload and the hash from the same hub, so the check detects a payload changed in transit or storage; it does not show that a hub, or anything acting as one, delivered what an approver approved, and it does not authenticate the sender. Binding an approval to a payload end to end needs a signature by the sender or approver. Authentication between sender and controller, such as Loop's one-time password, Trio's shared secret or AndroidAPS's per-client signature (§8), stays the controller's, and the hub carries it unread.
    CM23 The controller checks doses since. Before it enacts a dose or carbs, the controller compares the doses and carbs it holds since the command was made, and refuses doses-since when its own rule says the command is no longer wanted. The rule and its threshold are the controller's, as all validation is (D18); Trio's refusal when boluses since reach 20 % of the request is one such rule (§8).

    6. Proposals and approvals (proposed)¶

    propose → (evaluate) → approve | reject | withdraw | expire → command (§4) → outcome (§5)
    # rule
    CM11 A proposal. A proposal names the proposing instance, the target channel and, when known, the target product and instanceId; the payload and its payloadHash, under CM5's size limit; basedOn, the state version of the target product that the proposer read, required (422 based-on-required); and expiresAt, under the same limits as CM3. The hub routes the proposal when it is made (§2) and records the destination with its definitionId: a proposal with no destination is refused as a command would be, with nothing recorded; a named instanceId on another tenant, or none at all, is 404 (CM6); and one that is not the destination is refused 409 destination-changed. Its states are open, approved, rejected, withdrawn and expired; only open changes. A proposal is read by its tenant's subjects holding api:proposals:read or api:commands:create.
    CM12 Who may propose. The sender holds api:proposals:create, and the proposing instance is its own and holds a granted propose role on the channel: an other role that the hub's capability document lists as proposing (registration §9); a hub grants only roles it lists. Without the permission it is 403 not-authorised; an instance that is not the sender's is 403 not-registration-owner; without the role it is 403 role-not-granted. Reading confers neither: a readable credential, or a tool holding one, cannot propose.
    CM13 An approval binds to one payload. An approval names the proposalId and the payloadHash it approves. A hash that differs from the proposal's is refused 409 hash-mismatch; a proposal past its expiry is refused 409 proposal-expired; one that is not open is refused 409 proposal-closed. The approval routes again: with no destination it is refused as a command would be (§2), and when the destination differs from the one recorded at the proposal it is refused 409 destination-changed, because the proposer read one device's state and the change would reach another. A refused approval leaves the proposal open and creates no command. An accepted approval creates one command (CM1) whose payload is the proposal's, byte for byte, with the same hash, proposalId and basedOn set, and the proposal's expiresAt.
    CM14 Who may approve. The approver holds the permission to send the command itself (api:commands:create), else 403 not-authorised; approving is sending. When the proposing instance's propose role is an agent's, the subject that proposed cannot approve it (403 self-approval); a person may approve a proposal they made from their own app. Rejecting needs the same permission. Withdrawing is the proposer's, and also the person's: the subject the tenant marks as acting for the person whose therapy it holds may withdraw any proposal. The tenant owner sets that mark on a subject, on the owner's listener, as part of subject and role configuration; the hub reads it from the subject when it checks a withdrawal, a cancel (CM25) or an approval, and a client cannot assert it in a request (maintainer, 2026-10-26). Either by anyone else is 403 not-authorised. How a capability document marks a propose role as an agent's is open (§9).
    CM15 Based on. An approval is refused 409 state-changed when the target product's state version at the hub, at the time of approval, differs from the proposal's basedOn. This checks the hub's record of what the controller reported, the way an etag does; it does not tell the approver that the controller's own state is unchanged, which only the controller's own validation can (D18); the controller is given basedOn but cannot recompute it, because it versions the hub's record.
    CM16 Evaluations are evidence. Anyone who may read the proposal (CM11) may attach an evaluation: a risk check, a second model's opinion, a request for review. An evaluation never changes the proposal's state and never approves.
    CM22 Doses since the proposal. An approval is refused 409 doses-since when a dose or carb record for the target product reached the hub after the proposal was made and by the time of approval. The proposer could not have seen it, as basedOn (A12) does not cover doses or carbs. It is the hub's record, limited by the controller's upload lag; the controller's own check is CM23. A refused approval leaves the proposal open.

    7. Delivery in each mode (proposed)¶

    # rule
    CM17 The record is the command. The hub's record (CM1) is what states, outcomes and audit refer to, and only a fetch (CM18) hands a command over. A fetch-now signal (CM27) carries none of the record.
    CM18 Fetch. The destination reads the commands waiting for it (CM26) with its own credential. This works the same in both modes, because the request is bound to the tenant; it is the path a hub must offer, and the only one by which a payload and its hash reach a controller. A fetch returns only commands whose destination is that instance; a fetch naming an instance that is not the credential's own is 403 not-registration-owner, and an instance that no longer holds the role gets an empty list.
    CM19 Signals only inside a bound request. A fetch-now signal (CM27), on the socket or by a platform push, is sent only inside a request already bound to the command's tenant, such as the request that accepted the command, the approval or the cancel, or a later request from the destination. Under TENANCY_MODE=multi, nothing is sent from a context with no tenant bound, such as the load cycle; a signal there, or one bound to another tenant, is withheld (withheld), and the command waits for the destination's fetch (CM29). Under single the one tenant is always bound.
    CM20 A platform push is a signal sent with the tenant's credential. A platform push carries only a fetch-now signal (CM27) and is sent with a credential the command's tenant holds, never the deployment's. Without one, no platform push is sent (no-tenant-credential), and the destination fetches on its cadence (CM29).
    CM21 Enacted once. Delivery is at least once: a fetch returns a command again until the controller reports (CM26), a reply can be lost after the hub recorded the fetch, and a signal can arrive twice or after the fetch it asked for. Every fetch carries each command's commandId. The controller decides each commandId once: it records the id when it first enacts or refuses the command, keeps that record across restarts until expiresAt by its own clock, and answers any later delivery of the id without enacting it and without a second outcome report. A sender who sends again without the same requestId makes a new command (CM4), which this rule does not catch.
    CM26 Fetched until reported. A fetch returns every command routed to the fetching instance that is pending or fetched, while the instance holds the role and before the command's expiry. The first fetch moves it to fetched; later fetches return it again until the controller reports (acknowledged or a final state) or it expires, when it becomes unconfirmed (CM3). A cancel requested after hand-over (CM25) is carried under cancels, in place of the command, by every fetch until the controller reports after it. A fetch reply that never reaches the controller delays a command and never loses it; CM21 makes the repeats harmless.
    CM27 A signal says only "fetch now". While a command or a carried cancel waits for a destination (CM26), the hub may send that instance a fetch-now signal. The signal goes to the destination instance only, over a live transport it listens on (CM28), and carries nothing beyond its event: no payload, no payloadHash, no commandId, no channel. It names no command because the fetch that follows returns every waiting command anyway, so an id would give the controller nothing, while each signal passes through the transport's operator (a platform push service or a broker), which an id would let count and time one person's commands. A forged signal causes at most one extra fetch with the controller's own credential. A signal changes no state: a signalled command stays pending until fetched, and becomes expired or undeliverable if it never is. A signal is a hint: lost, late or repeated, it delays a command and never loses or duplicates one, because the fetch bound (CM29) still holds. None is sent for a command at or past its expiry (expired) or when nothing waits (nothing-waiting).
    CM28 Live transports. The capability's commands.liveTransports lists the transports the hub sends signals on, an open vocabulary: socket (Socket.IO on the hub's existing listener, sync-transport T16), apns, fcm, or {value: other, controllerTerm}, such as a message broker. A controller declares the transports it listens on in its registration: the liveTransports of its commands[] entry whose transport is nightscout-commands. The hub signals by the first transport the destination lists that the hub also lists; with none in common no signal is sent (no-live-transport), and the controller fetches on its cadence. A controller moves from polling to a live transport by adding the transport to its registration; it keeps fetching.
    CM29 The fetch bound. A destination fetches at least once per controller cycle: within cadence.nominalSeconds of its last fetch, deferred by at most cadence.maxDeferralSeconds, so its fetch bound is the sum of the two. It may declare a tighter bound, fetchIntervalSeconds on its nightscout-commands entry; the bound is then the shorter of that and the cycle. A bound under the hub's commands.minFetchIntervalSeconds is raised to it. A signal (CM27) can bring a fetch sooner and never lengthens the bound.
    CM30 The fetch bound is shown. The reply that accepts a command or an approval carries fetchWithinSeconds, the destination's fetch bound (CM29), so a sender sees how soon the command can be fetched without a signal. The outstanding list (CM24) carries, under destinations, each live holder of the channel's sink with its fetchWithinSeconds. A command whose expiresAt is no more than the fetch bound after the request is accepted unchanged and flagged mayExpireUnfetched, in the reply and on the record: the hub does not judge an expiry within CM3's limits (CM5), and a command never fetched expires harmlessly (CM3). A live transport does not clear the flag, because a signal is a hint.

    What in this table bears on the rules:

    • A late failure after success. AndroidAPS reports Done Ok when the pump queue accepts a bolus and Delivery Failed if the pump later fails it; Trio replies "initiating bolus" before it enacts and may reply failed after. CM9 as written refuses a report after succeeded (§9).
    • One command, part enacted. Trio's meal command stores the carbs before it validates the bolus, so a refused bolus leaves carbs entered and the reply says failed. A single final state cannot say which part happened (§9).
    • No controller computes a payload hash (CM10); each checks its own authentication instead.
    • No released controller de-duplicates by a hub's command id (CM21). Loop's bolus and carbs are single use through the one-time password, stored across restarts; its overrides are de-duplicated in memory only, so a replay after a restart starts the override again. Trio refuses a bolus when boluses since the command's own time reach 20 % of it, refuses a meal when newer carbs exist, and has no check for overrides or temporary targets; its dev branch carries a command_id it does not yet check. AndroidAPS client control's per-client counter must strictly increase and is stored, which already meets CM21. The unreleased Remote Commands 2 controller stores the ids it handled, as CM21 asks, without pruning them (read at Loop v3.14.9, Trio v1.0.2, AndroidAPS 4.0.0-rc1, 2026-10-18).
    • Expiry is not uniform. Loop checks an expiration only when one is sent; Trio checks a fixed window around the sender's time; AndroidAPS's validUntil is unbounded unless the sender sets it; Remote Commands 2 records carry none. CM3 requires one of every command.
    • Today's push paths stay as they are. Loop's and Trio's APNs paths, through /api/v2/notifications/loop or straight from a follower, and AndroidAPS's settings documents carry their payloads outside the hub command record. CM17–CM20 and CM26–CM31 do not change them; a controller keeps them beside the hub path, or alone when a hub has no commands member (CM31).
    • Sender authentication is end to end. Every controller that accepts a remote dose authenticates the sender itself; a hub forwards that material and is not trusted with it.

    9. Open¶

    1. Choices for the maintainer:
    2. How a capability document marks a listed other role as proposing (CM12), and as an agent's (CM14). Today it lists role names only; nothing says which listed role may propose, or which belongs to an agent.
    3. The command's expiry after an approval (CM13 proposes the proposal's expiresAt), or a new one set at approval within the proposal's.
    4. Refusing a stale approval (CM15), or only showing the approver that the state version changed.
    5. Recording refusals at routing (CM1) as not-routed commands, or answering them only.
    6. Who may approve (CM14): today anyone who may send the command; a grant could narrow it (authority §7).
    7. A command that expires within its destination's fetch bound (CM30) is accepted and flagged mayExpireUnfetched. Refusing it instead would stop a sender relying on a signal that may not arrive; flagging keeps the hub out of judging an expiry (CM5), and such a command, if never fetched, expires with nothing enacted (CM3).
    8. A controller check before approval. The proposal lifecycle drew propose → validate → (evaluate) → approve; CM11–CM16 send nothing to the controller before approval, because no controller offers a dry run of a remote command except AndroidAPS dev's two-step prepare and commit, which computes and caps a dose on the controller before it is committed.
    9. The payload grammar. No definition declares the shape of a command's payload; the hub stores it unread, and an approver's display has nothing to render its units or product from (UCA-PROP-004). A plan made of elements, and an approval that accepts some of them, is specified in plans; the maintainer chose (2026-10-18) that the approval names each accepted element by id and hash and the command carries one hash of the accepted subset, with approver signatures as the next step, since only a signature lets a controller detect a hub that built the wrong subset (partial acceptance prototype).
    10. Outcomes that change after a final state: a late delivery failure after success (§8), and a command enacted in part (§8). Either a further state (failed after succeeded, with the record keeping both) or an outcome per part (UCA-CMD-011, UCA-CMD-013).
    11. The grant that lets a person approve for someone else, and auto-approval: authority §7.
    12. The registration contract per tenancy mode (SPEC-REG-MODES).
    13. Found by the control-loop analysis:
    14. A second command or approval while one is outstanding (UCA-CMD-001, UCA-PROP-007). CM24 shows the sender and approver what is outstanding, and nothing refuses a second one. The state version changes only when the controller's records arrive (A12), so two approvals in that window both pass CM15. The remaining choice: refuse a second approval on a channel while a command from an approval is not final, or include outstanding commands in what CM15 compares.
    15. The definition at approval (UCA-PROP-008). CM11 records the destination's definitionId; CM13 refuses destination-changed only when the instance differs, so an instance that renewed under a new definition receives a payload approved under the old one.
    16. Proposal volume (UCA-PROP-002). Nothing limits the open proposals one instance holds on a channel.
    17. Required reviews on a moment proposal. Plans name reviews an approval waits for (plans PN6); a proposal for one command has no such member.
    18. Who acts for the person (CM14). The owner sets the mark (decided 2026-10-26); whether more than one subject may hold it is open.
    19. A process holding the destination's credential (UCA-CMD-014). CM7 and CM18 check the subject, not the process: under single every holder of API_SECRET is one subject, so another app can fetch a command, which moves it to fetched and out of the controller's next fetch, or report its outcome.
    20. Approving at once (UCA-PROP-013). CM13 lets only an open proposal change, and approve-approved-proposal shows a second approval refused; that the change from open to approved is atomic under concurrent approvals is not stated.

    21. The operator's limits (UCA-AUTH-006). commands.maxExpirySeconds bounds every expiry (CM3) and has no bound of its own.

    22. The address for a platform push. A platform push signal (CM20) needs the destination's device address for that platform; where an instance gives it is not specified. Instance labels cannot carry it (registration §10), and the tenant's credential for the platform has no place in the capability document, which describes the deployment.

    23. The effect link (CM7). Where the identity of the record that shows an enacted command's effect lives: an effect[] list on the report, the commandId on the record, both with disagreements flagged, or a separate reconciliation record (item 4 overlaps it). The effect-link prototype measures each against the same scenarios, with its cost and failure modes.
