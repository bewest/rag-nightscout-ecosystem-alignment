    Completion-focused coordination¶

    Maintainer direction, 2026-11-06: organize sessions and subagents around complete capabilities and adopted milestone criteria. The acceptance ladder and A–C schedule below remain the plan; this section governs task size, test timing and reporting.

    • A lane has an observable deliverable, one owner, an exit criterion, focused positive/negative checks, unresolved decisions and a next integration boundary. Helpers, fixture repairs and controls belong inside it. A new chat is useful for an independently deliverable capability or context/ownership transfer.
    • Complete the coherent implementation package before comprehensive acceptance. During development, choose changed-code lint and affected/focused suites for the behavior at risk. Preserve semantic controls for isolation, authorization, clinical behavior and compatibility. Do not run full/browser/whole-corpus per helper, leaf commit or resumption, or replay valid captures merely to repeat them.
    • Keep small early proofs when an architectural unknown could invalidate dependent work, a critical boundary needs native evidence, or an observed mismatch needs diagnosis. Name the question and its stop condition; once resolved, incorporate the result into the capability instead of extending a chain of proof-only tasks.
    • The coordinator freezes the assembled candidate and runs one comprehensive campaign plus final prcheck. If it fails, retain the failure and diagnose with focused assertions/controls. Join the planned repairs, freeze the replacement, and repeat acceptance when material inputs changed. Exact-head attribution and justified source-identity reuse remain required; this changes no milestone bar.
    • Resolve setup-only failures with preflight/startup checks before retrying the intended campaign. Preserve their captures as invalid attempts, not product results or separate milestone events. Valid in-flight work may finish.
    • Report the capability delivered, criterion verdict, remaining blocker and next integration boundary/owner, with an evidence link. Preserve supporting logs and source identities without turning every checkpoint into a new programme update. Use one evolving lane handoff and one acceptance bundle/update per coherent batch; substantive failures, decisions and ownership changes still need prompt records.

    R72 closes the adopted M1/M2 criteria, then M3/M4 on the same coherent campaign. The next completion path is M5 durable runtime and M6 operations. B/M5 runtime and C operations continue as parallel capabilities. Use the current roadmap for scope; resource budgets, human identity or other explicitly deferred C/M6 work must not become invented prerequisites to earlier milestones. Current ownership and executed evidence remain in the dashboard, release records and local handoffs.

    Three facts shape the rules below.

    • The regression surface on shipping code is narrow. The preview is mostly new, opt-in, dormant modules; the modified existing files are small hooks in the v1 and API3 handlers. A leaf commit that adds opt-in code does not need the full Mongo suite.
    • The campaign is cheap; the serialized slot is not. One full plus browser plus prcheck costs about ten minutes of machine time. R51, R52 and R53 each ran a native full campaign and R54 ran a fourth on the composition, serialized through one runtime slot, with more than eighty lane handoffs written in four days.
    • The queue's multitenant gates are instruments that skip without a database. tools/queue/gates/multitenant-next-slices.js --suite <name> --ref <sha> and its siblings replay archived suites against a pinned head. make queue-status reports them UNMEASURED when run without NS_TEST_POSTGRES_ADMIN_URI; that is the measuring environment, not a missing instrument.

    2. Acceptance ladder and what runs at each stage¶

    The dashboard's ladder is locally accepted → incorporated → integrated acceptance recorded → milestone promoted. Verification depth follows the stage, not the lane's nerves.

    Stage Claim What runs Who records
    Locally accepted this lane's change does what it says on its own head changed-code lint and affected/focused capability suites; meaningful authored controls, then restoration; no separate full campaign per leaf the lane, in its handoff
    Incorporated the change is an ancestor of the frozen batch head ancestry check; affected suites on the combined tree; tier registry check the coordinator
    Integrated acceptance recorded the frozen batch head regresses nothing one full nonbrowser, one default browser, the enabled multitenant corpus and batch labs, final prcheck.sh; applicable queue positives and paired breaks run against the frozen head the coordinator, as one R entry
    Milestone promoted an adopted roadmap milestone criterion list is fully met the milestone's own list; controls rerun on the cumulative tree; client-binary replay where the milestone claims client compatibility; benchmark where it claims capacity maintainer decision, recorded in the roadmap and dashboard

    A batch does not repeat lower-stage work for its members. A fresh agent resuming a lane does not rerun an accepted campaign.

    3. Batch rules¶

    1. Batch toward completion, with one frozen candidate per completion stage. The A–C schedule below governs current work. Parallel lanes join through an owned integration branch; do not rewrite shared published history. The coordinator records one comprehensive acceptance campaign per candidate. Publication remains the maintainer's action; agents never push.

    Commit integration direction adopted 2026-11-07: integrate original committed lane branches by fast-forward or ordinary merge, preserving commit identity. Before joining a lane, check ancestry and patch equivalence against the integration branch; resolve existing overlap explicitly. Do not copy lane patches by cherry-pick or rebase and then merge their original history to make evidence commits reachable. Evidence records retain the actual measured source head and separately identify its integration commit; incorporation requires ancestry, and acceptance applies to the measured candidate. Preserve the shared published history of draft #8898 and continue work there. A second or cleaned PR is deferred until more work is complete; no cleanup rewrite is authorized by this direction. 2. Triggers that require a full campaign on the final candidate. Any change to: an existing shipping file under lib/api, lib/api3, lib/server, lib/storage or lib/data; tests/tiers.json; package.json or the lock; a migration; a fixture another lane shares; or any red result that is not a declared control. These changes do not require one full campaign per member slice. After a failure, run focused regression/controls during repair; a material source, migration, dependency or shared-fixture change invalidates final acceptance and requires the full campaign on the replacement head. New opt-in files alone never trigger a separate native full campaign. 3. The local runtime slot serializes full, browser and whole-corpus campaigns. Focused suites own their random ports, schemas and containers and may overlap, after checking free disk and the inotify watch budget, both of which caused the November 5 ENOSPC holds. Capacity for overlap is unmeasured; the coordinator decides and records the check. 4. One command for the preview's own corpus. Measured by B5: 31 opt-in suites, all in the integration tier, gated by 23 flag variables plus the bare PostgreSQL admin URI; 18 start at least one container of their own, and 15 also open a real MongoDB client. npm run test:multitenant provisions one disposable PostgreSQL 16, one MongoDB 8.0 where a selected suite needs it and one Vault dev server where needed, then runs every opt-in suite with --fail-zero, so the corpus is one tier for the local slot and for CI. These counts describe the original B5 capture; every later batch reconciles the source inventory before freezing, including joined clock suites. An explicitly disabled benchmark stays named pending, never a functional pass. 5. CI runs the corpus. A PostgreSQL plus Vault job on #8898 moves the stage-three campaign off the single local slot. The current roadmap's milestone criteria call for explicit PG jobs as applicable suites execute. 6. Queue gates measure the batch head. After a batch's campaign passes, move each member item's --ref to the frozen batch head and run make queue-status with the admin URI set, inside the slot. Native refs stay in the R record as history. 7. Fuller V&V is a batch property. Escalate to stage four work only when a batch claims a milestone gate, touches shared code beyond rule 2, or fails its own controls. Never because a session resumed. 8. Every brief carries the standing instructions. Confirm the head commit and that the task is still open before starting; stop and report a mismatch rather than reaching for the nearest thing that works. Agents never push.

    Parallel execution and evidence accounting¶

    Parallel implementation and test preparation are the default. Isolated focused jobs may overlap only with recorded capacity and positive resource ownership; unknown containers/volumes remain untouched. CI or independent workers may run separate labs concurrently when their namespaces, ports, fixtures and teardown are isolated and capacity is measured. The local slot is a machine constraint, not an ordering dependency between independent implementation lanes. Quiet performance measurements receive a separate controlled window.

    Before freezing a batch, reconcile the enabled-suite inventory with source and publish named pending/unsupported cases.     7. What this plan does not do¶
