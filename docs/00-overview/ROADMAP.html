    Roadmap for cgm-remote-monitor: what comes next, and in what order¶

    Living document, last changed 2026-11-12 at 9ab7c284a.

    What this is: a map of the work ahead (contributor-facing). Read after programme status; leads to work waiting on a person. Prepared for the Nightscout project; proposed for Nightscout Foundation stewardship. Living document: §1 and §2 dated 2026-10-25 against cgm-remote-monitor official/master c6a0d8ed (tags v15.0.9, 15.0.9) and official/dev eb72a1d3 (16.0.0, cut 1 merged as #8828); §3 prose 2026-11-10; other prose dated 2026-10-08 against dev fade2299 and master 92d08342 (tag 15.0.8).     How to read the order tables. An item's wave comes from the blockers it is still waiting on. An item waiting on nothing that is still open is wave 1. Any other item is one wave later than its latest-wave open blocker. Items that are merged, done, closed or answered are left out. A wave shows dependency, not a date. The states shown are claims about what the gates will say, not measurements.

    3. Multitenant¶

    Self-hosted single-tenant Nightscout stays first-class permanently (D1, D4). Multitenant is an additional deployment target.

    The multitenant delivery roadmap owns milestone acceptance criteria; the batching plan §5 owns the current completion sequence. Start with the tenancy reading guide. Use the delivery dashboard for bounded accepted evidence and remaining gates, and the next-generation platform map for architecture dependencies and parallel lanes. The generated table below gives queue dependencies; make queue-status measures its claimed states. Release readiness is recorded separately in the release contents.

    The published one-host reference now includes cold Compose/UI/restore/client acceptance; native shared-role restart and the functional M5 runtime retain their exact source scope. This evidence can inform component and recovery decisions. M6 is split into M6a–M6d and M7 (decision): the M6a and M6b joined candidates have acceptance records on draft #8898 (M6a, M6b), with no milestone promoted. Deployment trust (M6c) and the M7 bench, scale, evaluator partition, realtime sharding and Android items follow, in the order the generated table gives; multi-host failover has no acceptance. Use the deployment models and fault domains to distinguish these boundaries. Tenant-local suppression and controlled notification handoff are measured; live provider/device delivery remains separately gated by runtime and clinical acceptance.

    4. Remedial: fix what ships¶

    The remedial work is not a sequence. It is prioritized by what reaches operators today: the operator-exposure table on PROGRAMME-STATUS lists the queue items for defects that are present on 15.0.8. A fix reaches operators only in a release, so each merged fix joins the next step on the release train.

    5. Proposals¶

    These are proposals for discussion with other projects and maintainers. None is scheduled in the queue.

    Cross-project adoption (hub and spoke). This is a proposal to the controller projects (AAPS, Loop, Trio) and to Nightscout as the hub. Each phase is useful even if the next never happens:

    1. A schema for controller settings documents in the existing v3 settings collection.
    2. Two one-symbol fixes, one in Nocturne and one in NightscoutKit, that stop dosing records being discarded.
    3. A catalogue of controller registrations shipped with the hub.
    4. A read-only sync contract.
    5. Therapy effects, then batched writes, then decomposition.

    Nothing in it requires a Loop protocol change. Detail and evidence: adoption roadmap.

    Product direction after the modernization baseline. This is a discussion between the maintainers. It proposes these work packages once the modernization branch is accepted:

    • bringing the connector's source in-tree;
    • extracting the report statistics into a tested module and exposing them through a documented API;
    • a first Svelte report (Daily Stats), also usable as a standard Web Component;
    • PDF export for sharing with a clinician;
    • vendor test fixtures shared across projects.

    Library and implementation choices are open. Detail: modernization review and proposed next steps.

    A shared quality kit for the whole stack. A proposal to every project: vector corpora for device protocols, simulators, fixture suites and a change canary for vendor clouds, a conformance suite any server can run, and one record shape for every test run, built in four stages. It also proposes how requirements that touch several projects are agreed. Detail: quality-system proposal, measured by the stack census.

    6. What bounds all of it¶
