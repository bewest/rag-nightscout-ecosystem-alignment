    Omnipod DASH Pod Simulator (LoopKit/pod) Deep Dive¶

    Living document, last changed 2026-10-17 at 5e265927f.

    Contributor-facing. Measured 2026-10-17 at LoopKit/pod a491a5ea (2026-10-12; 183 commits; GPL-3.0; GitHub lists it as a fork of randallknutson/pod). Other repositories cited: loopandlearn/pod ec13f460 (2025-12-05), randallknutson/pod main 12c54c2 (2022-12-06), jwoglom/faketandem 34c9401 (2026-10-17), loopandlearn/OmnipodKit main 4e923d7 (2026-09-19), dev 928bb79 (2026-10-13) and next-dev c21a077 (2026-10-14), LoopKit/OmniBLE 29358d5 (2026-05-29), nightscout/AndroidAPS dev 7e1d537d49 (2026-09-23) and master 598e2eb39c (2026-08-02), LoopKit/LoopWorkspace f841285 (2026-09-19) with NightscoutService fe075ef (2026-09-17), nightscout/Trio e41c9db37 (dev, 2026-09-22), LoopKit/g7sim 7c039de (2026-10-12), jwoglom/trio-test-harness c3c1bfe (2026-10-17); this repository at d9167f59 (2026-10-16).

    Repository: LoopKit/pod Language: Go (module path github.com/avereha/pod, go 1.15 in go.mod, dependencies vendored) Purpose: the pod side of Omnipod DASH: a program that a Loop or Trio phone (or an app in the iOS Simulator) pairs with, primes and runs as if it were a pod Source: externals/pod/

    1. Summary¶

    • pod plays the pod in the Omnipod DASH protocol. It pairs, runs the session cryptography, decodes the controller's commands, keeps pod state (reservoir, delivered insulin, pod progress, delivery flags, alerts, fault, age) and builds status responses from that state.
    • Two transports: a BLE peripheral on a Linux Bluetooth adapter (a Raspberry Pi in the README), and, since 2026-10-12, an iOS Simulator transport over ImpossiBLE's Unix socket, so an app in the iOS Simulator on a Mac talks to it with no radio.
    • A control panel and JSON API on port 8080 (GET /status, POST /command) set the reservoir and pod age, raise alert slots, set or clear a pod fault code, and crash the process on the next state-changing command, before or after it is applied.
    • The pod advertises a fault or a firing alert the way a real pod does (2nd service UUID C00A / C005, plus manufacturer data), hangs up after 3 minutes without a command, and since 2026-10-12 hangs up, rather than exiting, on a message it cannot use.
    • Tests: 7 test functions in 5 files at a491a5e, all passing (§7). A GitHub Actions workflow runs go test ./... on pushes and PRs since 2026-05-23.
    • Lineage: randallknutson/pod → LoopKit/pod → loopandlearn/pod. LoopKit/pod is where PRs merge. loopandlearn/pod's main is an older LoopKit/pod commit with no commits of its own (§2).
    • Not modelled: basal and temp-basal insulin draw from the reservoir, the delivery rates themselves, alert timers, pod-side rejection of commands, battery, transport-level faults, a controllable clock (§4).
    • jwoglom/faketandem shares this repository's root commit. The mechanisms compare in §8.
    • pod's own hex literals and test hex appear almost nowhere in the DASH driver test suites (§9).
    • The iOS Simulator path needs OmnipodKit's ImpossiBLE detection, which is on OmnipodKit next-dev and not in the OmnipodKit that LoopWorkspace and Trio pin: 928bb79 on their dev, 043b91d in Loop v3.14.9 and Trio v1.0.2 (§10).

    4. What pod state it models¶

    State lives in PODState (pkg/pod/state.go) and is saved to a TOML file (-state, default state.toml) after every command, so a restarted process resumes the same pod. -fresh starts an unpaired pod with 150 U (3,000 pulses of 0.05 U).

    Aspect Modelled as
    Pod progress Advanced by the commands seen during setup (version request, set unique id, the prime, basal-programming and cannula-insertion insulin programs), then by elapsed time for the prime and cannula boluses, then to "below 50 U" when the reservoir reaches 1,000 pulses (handleCommand)
    Reservoir Decremented by each bolus program, all at once when the bolus is programmed. Reported as the "above 50 U" value until it is 50 U or below, as a real pod reports it (generalstatusresponse.go)
    Delivered Incremented by each bolus program only
    Bolus in progress BolusEnd = now + 2 s per pulse (1 s per pulse during setup). BolusRemaining is derived from it. A bolus cancel reports the remaining pulses, then clears BolusEnd
    Temp basal Active until now + duration (half-hour units). The rate is decoded but not stored
    Scheduled basal An on/off flag set by programming basal table 0 and cleared by a stop-basal command
    Extended bolus A flag that commands only clear. No command sets it
    Alerts An 8-slot mask with a trigger time per slot. Set only from the control panel. Silence-alerts and program-alerts clear the named slots
    Fault A fault code and the pod minute it was set. Set from the control panel (any 0–255), or 0x1C automatically at 80 hours. With a fault set, status requests of type 0 and 7, and the response to every other command, are the detailed status instead of the general one, with progress "fault" and delivery suspended (detailedstatusresponse.go)
    Pod age ActivationTime, from which minutes active is computed on the wall clock. The control panel's setActiveTime moves it
    Status types General status; detailed status (type 2); types 1, 3 and 5 from state; types 0x46, 0x50, 0x51 hard-coded
    Message handling A retry with the same message sequence number is ignored. The response carries the command's sequence and request id. A missing ACK ends the session. Deactivation exits the process on the next loop

    What it does not model (from the code at a491a5e):

    • Basal and temp-basal insulin are not drawn from the reservoir or added to delivered insulin. Rates and basal schedules are not stored.
    • The pod never refuses a command. There is no nonce or program-sequence check, no "bolus already in progress", and commands sent while faulted are still applied (a bolus still decrements the reservoir). Reservoir -= Pulses is an unsigned 16-bit subtraction with no lower bound check.
    • No alert timers. Program-alerts only clears slots, so expiry and low-reservoir alerts fire only when raised from the control panel.
    • No battery, no occlusion detection or other physical behaviour except through setFault. A fault does not stop the bolus timer or the temp-basal end time in state.
    • No controllable clock (§8). Timers run on time.Now().
    • The 80-hour fault is evaluated when a response is built, so /status keeps showing no fault after 80 hours until the next command arrives (run: setActiveTime 4800 → /status fault: 0, minutesActive: 4800). The control panel says the same: "At 80 hours the pod faults with 0x1C at the next command."
    • Eros and Omnipod 5 are not covered. The commands recognised are the DASH set in pkg/command/command.go. Any other opcode gets a fixed NACK-type response.

    5. Control panel and JSON API¶

    -api (default :8080) serves:

    Endpoint Behaviour
    GET / An HTML control panel (pkg/api/web.go): pod id, paired/connected, progress, reservoir, delivered, age, alerts, fault, delivery flags, sequence counters; controls for each command below; a list of 120 named fault codes
    GET /status JSON Status (pkg/pod/status.go) as of the last completed command or control change. Fields include progress, progressName, reservoir and delivered in units, minutesActive, alerts, fault, faultMinutes, the basal/temp/bolus flags, bolusRemaining, crashNext, and the message, command, nonce, session and program sequence numbers
    POST /command {"command": ..., "value": ...}, answered with the new Status, or HTTP 400 with a reason
    /ws The WebSocket API used by the separate ps2/pod_simulator_frontend. It pushes the raw state after each acknowledged command and accepts the same command JSON
    Command Value Effect
    changeReservoir units, 0–200 Sets the reservoir
    setActiveTime minutes, 0–6000 Sets pod age by moving the activation time
    setAlerts slot mask, 0–255 Replaces the active alert slots and stamps their trigger times
    setFault fault code, 0–255 (0 clears) Sets the fault code and fault time
    crashNextCommand "beforeProcessing": true\|false Exits the process (log.Fatalf) on the next state-changing command, either before it is applied or after it is applied and saved, so the phone never gets the response. run.sh restarts the process in a loop

    Run on 2026-10-17 (-transport impossible -api 127.0.0.1:18080, scratch state file): each command returned the updated Status, changeReservoir 250 returned 400 reservoir 250: want 0 to 200, an unknown command returned 400 unknown command "bogus", and GET /command returned 405.

    State-changing commands, for crashNextCommand, are those whose DoesMutatePodState() is true: set unique id, silence alerts, program alerts, program insulin, program beeps, stop delivery and deactivate. The crash flags are process globals, so a crash clears them.

    6. Transports and connection behaviour¶

    -transport ble (default) -transport impossible
    Peer A phone, over a Linux HCI adapter (paypal/gatt, vendored). Needs cap_net_raw,cap_net_admin An app in the iOS Simulator with ImpossiBLE's library injected, over a Unix socket (-socket, default /tmp/impossible.sock) carrying newline-delimited JSON (hello, scan, connect, discoverServices, discoverCharacteristics, writes, notifications, didDiscover with the advertisement)
    Builds on Linux only (gatt_linux.go). On other platforms NewGattRadio returns an error naming the other transport Any platform. The protocol tests run on Linux
    Peripheral id – A stable UUID saved in state (peripheral_id)

    Both build from the same tree: go build succeeds for linux/amd64, linux/arm and darwin/arm64 at a491a5e.

    Behaviour common to both (pkg/bluetooth/bluetooth.go, pkg/pod/pod.go):

    • 3-minute hang-up. The command loop waits 3 minutes (ReadMessageWithTimeout(3 * time.Minute)) for the next command, and for an ACK after each response. On timeout the pod disconnects and waits for a new connection. The README describes this as mimicking DASH pods that disconnect every 3 minutes, which can drive Loop as a heartbeat when no BLE CGM is available (PR #10, 2023-03-15, set the 3-minute value).
    • Reconnect. A new connection during setup or the command loop abandons the current exchange and renegotiates the session (#18). Each connection gets its own input channels (#22).
    • Messages the pod cannot use. A setup or session message that fails to parse, a command that fails to decrypt or unmarshal, or a bad ACK, makes the pod hang up and wait for a new session (#23). Failures while building or encrypting its own response still exit the process.
    • Start delay. On the ImpossiBLE transport, a connect that carries a start delay (kCBConnectOptionStartDelay) is held for that delay, as iOS does.
    • Advertised state. For a paired pod, the 2nd advertised service UUID is C001, C005 when an alert slot is active, and C00A when a fault is set. The manufacturer data carries the fault code and alert slots. An unpaired pod advertises 2470 there. Run on 2026-10-17 over the socket with a hand-made paired state: C001 → setAlerts 4 → C005 → setFault 20 → C00A. The README notes that Loop treats a pod fault as final, so after clearing a fault in the simulator Loop must be relaunched before testing another one.

    Cryptography is named here by family only: pairing uses X25519 key agreement and AES-CMAC, sessions use EAP-AKA with Milenage (vendored wmnsk/milenage), and messages use AES-CCM.

    Operational facts for contributors. The control API listens on all interfaces by default, has no authentication, and the WebSocket upgrader accepts any origin. The state file holds the simulated pod's pairing and session keys and is written with mode 0777. The info-level log prints those keys. These are keys of a simulated pod, but logs and state files from a run should be handled as such.

    11. Nightscout relevance¶

    pod does not talk to Nightscout. A controller paired with it uploads what it would upload for a real pod. From NightscoutService fe075ef and OmnipodKit 4e923d7, for Loop:

    pod event or state What Loop records (code path) Nightscout upload
    Bolus program Bolus DoseEntry treatments bolus (BolusNightscoutTreatment, Extensions/DoseEntry.swift)
    Temp basal program / cancel Temp-basal DoseEntry treatments temp basal (TempBasalNightscoutTreatment)
    Suspend (stop delivery) / resume Suspend / resume DoseEntry treatments: a suspend is uploaded as a zero-rate temp basal with reason: "suspend" and the suspend's duration; a resume DoseEntry maps to no treatment (case .resume: return nil)
    New pod paired NewPumpEvent "Pod Change", .replaceComponent(.pump) (OmniPumpManager.swift) treatments Site Change (Extensions/PersistedPumpEvent.swift)
    Fault or pod life exceeded A pump-manager alert and a status highlight ("Pod Error", "Pod Expired", "No Insulin" in OmniPumpManager.swift) devicestatus.pump.reservoir_display_override and reservoir_level_override (NightscoutKit PumpStatus). OmnipodKit emits no .alarm pump event, so no Note treatment is created from a pod fault in this path
    Reservoir ≤ 50 U didReadReservoirValue (only for a real level, not the "above 50 U" value) devicestatus.pump.reservoir, when read within the last 15 minutes
    Delivery state basalDeliveryState, bolusState devicestatus.pump.suspended, bolusing

    Trio uses the same OmnipodKit, so the pump-side events are the same. Trio's own upload mapping was not read for this document. A pod-driven run can therefore produce real-shaped treatments and devicestatus in a test Nightscout, including the fault and expiry status paths that are hard to reach with a real pod. Because the pod does not draw basal from the reservoir (§4), reservoir figures in such a run reflect boluses only.
