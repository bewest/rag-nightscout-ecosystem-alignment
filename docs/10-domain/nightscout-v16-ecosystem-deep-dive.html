    Nightscout v16 ecosystem and release acceptance¶

    Living document, last changed 2026-11-03 at 22d0bdd41.

    Evidence refresh: 2026-11-03. This is the current contributor-facing follow-up to the November 1 readiness snapshot. It records upstream metadata, maintainer reports and proposed next work separately. It is not a release approval, clinical validation or a claim of a certified QMS.

    Release position¶

    official/dev at 4a482627bfdafb1fef8dcbe0ac6c484811cae563 is the current 16.0.0 release candidate. Release preparation is in progress, not blocked; the remaining acceptance and staging steps are pending. The latest published release is still v15.0.9, and no 16.0.0 tag or release is published. The maintainer reports multiple testers have been using the code for over 24-48 hours and that AID authors are considering changes. This establishes that cohort/rig testing has started, not which versions, scenarios or outcomes have been accepted.

    The merged backend storage/write/identity work, frontend bundles, dependency refresh and optional modern dashboard are implementation outputs, not a remaining modernization merge queue. The previous candidate 61eb3733 has recorded green public CI: 6,323 passing / 3 pending in the top-level suite, or 7,660 passing / 3 pending counting each reported suite once. #8899 adds the D21 CLI naming amendment; its merged tree equals the locally tested PR head (6652 passing / 3 pending / 0 failing across non-browser tiers). Merged-head CI was in progress at capture. See the integration record R21/R22. These results are not proof of live acceptance.

    BF-72 and BF-161 remain pre-tag private-security work. No new private inspection, merge or disclosure is claimed here. The previously recorded 402 focused tests do not establish full combined-tree acceptance. Integrate privately, validate the resulting tree, and coordinate disclosure with availability of the fixed release. Public dev testing can continue in parallel; testers need the exact new commit/image and affected checks repeated after integration.

    Compatibility without synchronized client releases¶

    The aim is an explicit contract with independently deployable clients, not a claim that v16 has zero behavior changes. The existing compatibility report classifies 2,803 changed cells with none unexplained in its measured scope. It compares dev 497d08c9, not the eventual security-integrated release, and uses index off to seed duplicates. Index startup/races and live clients are separate evidence.

    Boundary What is implemented / what needs agreement
    Legacy v1 versus item results Without Nightscout-Write-Results: items (or ?results=items), retain the legacy reply slots/array contract. The richer {items, documents} reply is request opt-in. Do not silently switch existing uploaders to the new envelope.
    HTTP success versus stored item A 2xx batch response is not proof every item was stored. New clients must understand item outcomes before opting into refusal/retry behavior; test old clients that clear their entire upload queue on 2xx separately.
    Re-send versus edit Default WRITE_RESEND=replace may remove omitted fields on identity-matched live re-sends. merge-except-treatments, acknowledge, refuse are explicit site-wide choices, not per-client negotiation or a universal 15.0.9 compatibility switch. API v1/in-process entries and explicit edits retain path-specific rules.
    Deleted records Default WRITE_DELETED_RESEND=stay acknowledges an identity-matched re-send without reviving the record. Test retained client queues and deliberate edits separately; document any request to change this, not just the word "upsert".
    Identifier validation Unset WRITE_IDENTIFIER is not identical to explicit lenient: API v3 retains specific historical refusals. strict is opt-in. Keep default/lenient/strict distinct in author guidance.
    Unique index and rollback Default WRITE_IDENTIFIER_INDEX=try attempts the index and reports duplicate counts without cleaning up data or stopping startup for duplicates. off does not remove an index already built; drop does. Verify rollback on a disposable deployment before reverting server versions.
    Additional AID fields Optional fields should be documented and tested as optional across supported old/new endpoints. Do not make a new controller build mandatory merely because an uploader adds metadata. Unknown-field preservation/display behavior still needs endpoint-specific evidence.
    Capability discovery Registration/catalogue proposals are not merged capabilities clients can rely on. Do not require #8857 or invent capability flags on the released server.

    Canonical source read through GitHub at 61eb3733: externals/cgm-remote-monitor/lib/api/shared/batch-reply.js:8-43 and externals/cgm-remote-monitor/lib/server/write-settings.js:7-68,129-144. The local corpus was not refreshed; these paths describe upstream files at that commit, not an assertion that the local lockfile pin contains them.

    AAPS 4.0.0 was released October 31, including changed client pairing/roles, multiplatform clients, units/concentration support and steps/heart-rate graphs (release notes). Include both existing supported AAPS installations and 4.0.0 master/client roles in the cohort; do not equate AAPS release notes with proof of Nightscout interop. Keep the non-default API3_SETTINGS_STRICT_READ_ENABLED follower caveat visible in the v16 notes.

    LoopWorkspace's published release is v3.14.11. NightscoutKit main at 6efa02d4 includes optional failureCode and bolusCalculation fields: externals/NightscoutKit/Sources/NightscoutKit/Models/LoopStatus.swift:19-36,79-96, read at that upstream commit. This is additive client model evidence, not proof that a given Loop release includes that exact dependency or that every server read/write path round-trips those fields.

    For each ambiguous behavior raised by an author, capture: route and collection; client version; old/new request and response shape using synthetic data; stored result; retry/deletion/permission expectations; whether the change is a bug fix, opt-in extension or changed default; and the smallest discriminating test. Decide its release placement before changing implementation or a public specification. Keep missing/empty/null, merge/replace, batch partial success, identity, deletion, units and event-time/receipt-time semantics explicit.

    Compatibility confidence: what the record supports¶

    Assessment: strong automated and source-derived evidence supports the intended interoperability of known client contracts without coordinated client upgrades. This review identified no confirmed requirement for all known AID clients to upgrade together. It does not establish unconditional backwards and forwards compatibility for every client version, consumer, configuration or future feature.

    The client catalogue has 15 implementations, 120 group-specific shape matches: 11 measured-tier, 109 read-tier. As the comparison's limits explicitly state, no client application ran against those matrix trees. Even a measured shape match is not a live-app test. Client applications and actual live testers may have separate evidence; do not erase or double-count it.

    Claim Supported interpretation / boundary
    Old clients with v16 Legacy routes/reply shapes are retained without forcing adoption of new item envelopes. Known request shapes and extensive regression evidence support high confidence; intended identity/deletion/unit fixes still change some stored outcomes.
    New clients with old Nightscout A new client that stays within the old contract can remain interoperable. A new-only feature needs an actual supported capability or tested fallback; sending an opt-in header is not by itself proof an old server supports its envelope. This reverse-version claim is not demonstrated for every client by the server write matrix.
    Forward-compatible data Optional additional fields avoid an inherent lockstep requirement, but preservation and interpretation must be verified per endpoint. New metadata does not make old software understand a new behavior.
    No defect-classified matrix cells All differences are classified within the synthetic experiment; this is not a proof of no defects in deployment, readers, third-party plugins or future data.

    The catalogue itself maps intentional changes to known shapes: deleted-record behavior, profile identity, reply handling and Temporary Target unit corrections. These are not automatically broken clients. Some cells cross paths: for example, the "API v3 client _id refused" group is matched to a Loop v1 override shape because the synthetic seed was written using v3. It is not evidence that Loop now sends a forbidden body _id to v3. Read the seed, write path and outcome together before turning a catalogue match into an incompatibility allegation.

    Recommended release wording:

    Nightscout 16 is designed to preserve interoperability with existing clients without coordinated client upgrades. New item-result replies are opt-in. Identity, re-send, deletion and unit-handling fixes have documented behavior changes; non-default strict/rejection settings need separate client checks.

    This qualifies the compatibility claim without downgrading confidence in already tested contributions or inventing a new release gate.
