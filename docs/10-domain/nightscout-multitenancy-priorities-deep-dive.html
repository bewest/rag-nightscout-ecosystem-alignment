    1. Bottom line¶

    The next useful delivery is an entries-first PostgreSQL RLS slice on current dev, alongside a tenant configuration/authentication integration workstream. Neither needs to wait for the v16 tag to conduct synthetic, isolated experiments. Do not reopen the v16 merge list just to land multitenancy.

    Celld is worth a bounded tenant actor/scheduling/realtime experiment, not an immediate replacement for PostgreSQL or the Nightscout Node server. PostgreSQL addresses shared-record authorization; Celld addresses durable actor execution and placement. They can complement each other, but a hybrid adds a cross-system commit/delivery boundary that must be proved, not assumed.

    Retain D1-D4: first-class single-tenant MongoDB, and shared PostgreSQL with RLS for the hosted target. A Celld/SQLite record-store alternative would be an explicit architecture experiment, not an already authorized change to D2/D3.

    Prior work to preserve, not repeat blindly¶

    • The PG backend measurement exercised the actual old adapter and emitted schema, including 3,000 filter comparisons. It also exposed limit/order/projection/materialization issues. Those results do not certify a port to the current write/identity contract.
    • The pooler experiment demonstrated transaction-local tenant binding through real transaction pooling, including a shared backend and a red session-binding control. Statement pooling could not run the adapter. Its unregistered defect labels collide with later BF IDs; do not treat them as current register identifiers.
    • The configuration lab measures policy/floor/RLS behavior on PostgreSQL 16.15. Its October 27 schema predates October 29 decisions, including tenant_access_grants replacing tenant_members; the next integration must reconcile them.

    A coordination blocker: two generations of planning¶

    At the initial assessment, the platform map had ST-PG, TEN-RESOLVE and TEN-LAB without corresponding executable-work items in queue/work-queue.yaml. The adopted roadmap has since added those queue items and bounded M0/Vault checks. Their complete acceptance is still open. The queue also carries older seam-era dependencies; SEAM-REFRESH is blocked on the old release train. The current platform plan explicitly keeps that chain as reference, not a bulk merge.

    Keep each assigned slice in the queue with its current-dev base, owner and discriminating gate. Do not make a blanket September-chain refresh a new prerequisite for ST-PG. Preserve completed measurements, but do not infer that a platform-map card has a runnable queue gate.

    3. Recommended independent workstreams¶

    Priority / stream Bounded deliverable Acceptance / stop boundary
    P0: PG storage slice Current-dev topic branch, entries adapter, emitted DDL and backend harness integration; explicit list of unsupported collections/operations. Both stores execute the applicable cases, not pending PG storage tests; request/reply/stored outcomes cover filtering, paging, identity, resend, delete, null and batch semantics. Stop short of claiming a complete hosted site.
    P0: tenant control plane Reconcile T30 decisions, then config/credential/schema integration, resolver and per-tenant key wiring. A's token succeeds on A and fails on B by signature; unknown tenant refuses; no process-env secret leaks into hosted config; owner/operator/data boundaries hold. Synthetic device tokens do not need a production human IdP.
    P1: evaluator/realtime Wire the computed view behind an experimental execution profile; define durable wake/reconnect and state ownership. Equality with resident outcomes on relevant replay fixtures; tenant-specific units/thresholds/language; durable ack/snooze; no cross-tenant rooms or notifications. No live alert promise until the alarm gate passes.
    P1: Celld feasibility Two synthetic tenants, tenant-addressed actors, fake delivery sink, restart/failover and event-retry probes. Compare with a simple Node worker baseline. Measure useful runtime benefit and integration cost; no real records, provider secrets, push delivery or release dependency. Reject a design that needs unsafe routing or a hidden second source of truth.
    P2: hosted operations Extend covered collections, import/export fidelity and repeatable migration/restore/rollback. Full supported-client surface and failure acceptance before onboarding. Entries-only synthetic data needs no Mongo-to-PG migration first.

    BF-72/BF-161 remain in the separate private release/security workstream. They are not prerequisites to a synthetic PG or Celld experiment; any later deployed hosted build must incorporate the applicable fixes and validate its final tree. nightscout/cgm-remote-monitor#8829 remains explicitly nonblocking for v16; it is not promoted into a blanket tenancy research blocker.

    PG experiment: the smallest useful proof¶

    Use two tenants with overlapping _id and identifier values, plus an unbound bystander, against the real adapter. Exercise reads and inserts/updates/deletes. Bind the tenant inside each transaction with set_config(..., true), use non-owner NOSUPERUSER NOBYPASSRLS application roles and forced RLS, and keep migration privileges separate. Test missing scope, rollback and error cleanup through a transaction-pooling PgBouncer with demonstrably reused connections. Pair isolation checks with deliberate breaks so that zero rows cannot mean the fixture never stored anything.

    PostgreSQL's RLS documentation also limits the promise: superusers/BYPASSRLS bypass it, owners normally bypass unless forced, and operations such as TRUNCATE are outside row policies. RLS protects against omitted row filters under the trusted application's binding; it does not authenticate the chosen tenant or make arbitrary tenant-controlled SQL safe. Grants, parameterization and trusted tenant resolution remain required.

    4. Where Celld fits, and where it does not¶

    The primary docs retrieved November 2 describe v0.6.2 beta. These are vendor claims and documented limits, not measurements made by this workspace.

    Question Assessment
    What does it provide? Single-threaded Durable Object actors, each with SQLite; bucket-backed replication/ownership, timers, hibernatable WebSockets, queues and workflows. A scheduling alarm is a runtime callback, not verified Nightscout clinical notification delivery.
    Can today's server simply run unchanged? Not established. It targets the Workers programming model with partial Node compatibility. Containers are experimental. Express/socket.io/plugins and their dependencies need actual compatibility work; raw WebSocket support does not prove socket.io protocol compatibility.
    Does it supply tenancy? No account service, multi-tenant scheduler or managed ingress. The application still owns identity, authorization, tenant routing, quotas, secrets and egress policy. A cell per tenant is not RLS and is not authorization.
    Can it retain PostgreSQL? A Node/PG service can remain authoritative while an actor handles scheduling/fan-out over a narrow interface. Celld has TCP support but no Hyperdrive; direct PG-driver compatibility is not demonstrated here. Keep direct SQL out of the first spike.
    What changes operationally? TLS terminates outside Celld; peer HTTP is plaintext, so use a private/encrypted network. Bucket semantics, fleet credentials and an appropriate restarting supervisor are part of correctness. No placement/jurisdiction guarantee is supplied.
    What survives failure? Docs claim acknowledged writes survive according to the durability mode and required bucket/follower conditions. Recovery can block for missing or uncertifiable tails. Socket transports do not move with cell ownership; clients must reconnect. This is not a no-outage or exactly-once-notification guarantee.
    Why not replace PG with per-tenant SQLite now? That is a different storage architecture, requiring query/write fidelity, migration, export, fleet isolation and cost evidence. September's per-tenant WiredTiger cost does not measure Celld SQLite, so it neither proves nor disproves this alternative.

    Celld spike gates¶

    1. Derive actor addressing from an authenticated, authorized immutable tenant ID, not a caller-selected cell name. Reject forged cross-tenant routing; verify each tenant's own positive case.
    2. Use synthetic committed-event envelopes with stable operation IDs. Exercise duplicate and out-of-order delivery, suspension, restart and owner loss. Queues are documented as at-least-once and unordered; one queue has one writer.
    3. Keep PG as the record authority for the hybrid arm. Demonstrate the commit-before-publish crash gap explicitly. An in-process commit event followed by a queue send is not atomic; durable replay/outbox/CDC semantics need a separate choice consistent with D6 and D-EVENT before promotion.
    4. Persist scheduling/ack state and distinguish an unacknowledged client retry from a proven failed write. A timeout does not imply the original effect did not happen. Fake external effects must expose duplicate attempts.
    5. Test a qualified bucket and the documented supervisor/fencing setup, socket reconnect and full stopped-fleet restore. Measure latency, recovery delay, resident/idle cost, object-store operations and noisy-neighbor impact. Published headline density/pricing is not a Nightscout capacity estimate.
    6. Avoid renaming the Worker/script as an innocent deployment change: idFromName() incorporates script/class identity; docs say a script rename reaches new empty objects. Record identity and upgrade constraints.

    Recommendation: PG integration is the primary progress track; Celld gets a small parallel feasibility budget only if someone owns the runtime experiment. Do not wait for production human-login/edge compliance to run synthetic storage tests, or mistake those tests for permission to accept real identities/data.
