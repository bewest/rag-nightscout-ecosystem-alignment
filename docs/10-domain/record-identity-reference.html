    Record identity in cgm-remote-monitor: _id, identifier and time keys¶

    Living document, last changed 2026-10-29 at c47dbe6a9.

    Contributor-facing. Living reference, as of 2026-10-18. Pinned to cgm-remote-monitor 15.0.8 (92d08342, the shipping release) and dev (fade2299, the 15.0.9 candidate). Queue item DOCS-RECORD-IDENTITY. It describes what the code does today; it proposes nothing.

    Every claim is marked [M] measured or [R] read. Measured claims come from tools/lab/record-identity (results 2026-10-18: both refs, MongoDB 7.0.43, UUID_HANDLING at its default) and, where cited, from tools/lab/v3-identifier-immutable. Read claims cite lib/ paths at the ref named. When this page and the code disagree, the code wins; re-run the lab before quoting a cell for a newer ref.

    Summary¶

    A Nightscout record has two ids. _id is MongoDB's storage key; the server serves it as 24 hex characters and, on v1, a client may send its own 24-hex value. identifier is the client's sync identity: API v3 matches on it everywhere, v1 matches on it only for treatments, and the socket does not match on it at all. When neither is sent, each path falls back to a time key (entries sysTime + type, treatments created_at + eventType), and devicestatus has none, so every POST adds a record. The paths disagree in the details that matter to an uploader: whether a 24-hex _id is stored as an ObjectId or as a string (15.0.8: ObjectId on v1 entries and treatments, string on v1 devicestatus, profile and food, on the socket and on API v3; dev: ObjectId everywhere except API v3), whether _id or identifier wins when both are sent (v1 treatments: identifier, and the sent _id is dropped), and whether the reply names the stored _id (not after a v1 treatments time-key match, on either ref). dev removes most of 15.0.8's _id failures (#8758): a re-sent devicestatus no longer fails its batch, an entry re-sent under another _id no longer fails, and string-stored ids are found by every v1 and socket lookup.

    1. The two ids¶

    _id, the storage key. MongoDB accepts any non-array value as _id; the lab stores UUID strings and 24-hex strings as _id through the socket and API v3 [M]. Nightscout's convention is an ObjectId: 12 bytes, served as 24 lower-case hex characters. ObjectIds are designed to be made by any client without coordination (a timestamp, a random value and a counter), so a client that creates one and sends it as _id is using the type as intended. On v1 entries and treatments, a 24-hex _id has been converted to an ObjectId since 15.0.7 [R] (normalizeEntryId, lib/server/entries.js:267-284; normalizeTreatmentId, lib/server/treatments.js:394-412 @15.0.8). Until #8758 (merged to dev 2026-09-25, not released), v1 devicestatus, profile and food, and the socket, stored a sent 24-hex _id as the string itself, while their lookups convert to an ObjectId, so the record could not be found, edited or deleted by its id [M]; that is BF-99 to BF-102. On dev those paths store an ObjectId, and every v1 and socket lookup also matches the string form (lib/server/object-id-forms.js @fade2299) [M]. API v3 stores a body _id as sent, a 24-hex value as a string, on both refs [M]; see §2.6. On dev since #8845 (merged 2026-10-26, 47723cda) API v3 refuses a body _id with 400 [R] (BF-170).

    identifier, the client's sync identity. A string the client chooses, compared exactly as stored (case kept) [M]. API v3 requires one on every record: when a POST has none, the server computes uuid.v5(device + "_" + date [+ "_" + eventType], "NightscoutRocks!") (lib/api3/shared/operationTools.js:97-126 @15.0.8) [M: the stored value equals that computation]. When a client sends one, the server keeps it and logs APIv3: Identifier mismatch if it differs from the computed value [M, server log]. API v3's swagger says "The client should not create the identifier"; the code does the opposite, which is BF-169. No index on identifier is unique, on either ref [R] (lib/server/entries.js:224,226, treatments.js:430,432, devicestatus.js:168, api3/storage/mongoCollection/index.js:21 @15.0.8).

    2. Match keys per collection, and their pitfalls¶

    2.1 Entries (v1)¶

    The upsert filter is sysTime + type, always (upsertQueryFor, lib/server/entries.js:238-256 @15.0.8, :301 @fade2299) [R]. Neither _id nor identifier selects the record.

    sent 15.0.8 dev
    a new 24-hex _id stored as that ObjectId; reply names it [M] same [M]
    the same _id and time again 200, one record, fields updated [M] same [M]
    the same _id at another time 500, E11000 duplicate key: the filter finds no record at the new time, so the upsert inserts the _id already in use [M] same [M]
    another _id at a stored time 500, "Performing an update on the path '_id' would modify the immutable field '_id'": $set carries the sent _id (:136) [M] 200; _id goes into $setOnInsert only (:147), so the stored record keeps its _id and the reply names it [M]
    no _id, same time twice 200 twice, one record; the second reply has no _id [M] the second reply names the stored _id [M]
    the same identifier at another time two records [M] same [M]
    a new identifier at the time of a stored entry one record; the stored identifier is overwritten [M] same [M]
    a batch whose 2nd item collides 500; item 1 stored, items 2 and 3 not (ordered bulkWrite) [M] same [M]
    a UUID or any other non-24-hex string _id moved to identifier (when none is sent), server assigns _id [M] same [M]

    The socket's dbAdd on entries does no matching: an identical body sent twice is stored twice [M] (generic insertOne, lib/server/websocket.js:707 @15.0.8).

    2.2 Treatments (v1)¶

    upsertQueryFor (lib/server/treatments.js:356-381 @15.0.8, :411 @fade2299) tries, in order [R, each step M]:

    1. identifier when present. Under UUID_HANDLING the filter is identifier = X or _id = X, so a legacy record stored with the value in _id matches. The sent _id is deleted (:362 @15.0.8, :417 @fade2299): a write carrying identifier X and a new _id A is stored under a server-assigned ObjectId, not A, and the reply names the stored one [M]. Re-sending X with yet another _id updates the same record [M]. Sending a stored record's _id with a new identifier creates a second record [M].
    2. _id when present: a re-send with the same _id replaces the record, even at a new created_at [M].
    3. created_at + eventType. On 15.0.8 that is the whole key, so a second carb entry at the same time with another amount replaces the first [M]. On dev (BF-121, #8780) the key adds the client's own id when it sends one (syncIdentifier, id, uuid or NSCLIENT_ID), and otherwise carbs and insulin and the absence of any id, so the two entries are kept [M] (lib/server/treatment-fallback-key.js @fade2299).

    After a step-3 match the reply item has no _id, on both refs [M]: the server looks the stored _id up only after an identifier match (:104-129 @15.0.8). A v1 batch is one ordered bulkWrite; a failure stops it and earlier items stay stored [R] (:91).

    The socket's dbAdd on treatments matches NSCLIENT_ID, else created_at + eventType exactly, then a ±2 s window on equal insulin, carbs, percent, absolute or duration (lib/server/websocket.js:515-580 @15.0.8; dev uses the BF-121 key without amounts) [R]; it never reads identifier, so one identifier at two times is two records [M].

    2.3 Devicestatus¶

    v1 POST is insertMany with no key on 15.0.8 (lib/server/devicestatus.js:70) [R]: identical bodies, or one identifier, sent twice are two records on both refs [M]. A re-sent 24-hex _id fails the whole POST with 500 on 15.0.8; the items before it are stored and the items after it are lost [M]. On dev, withoutStoredIds (:57-90 @fade2299) answers a re-sent _id with the stored record and stores the rest of the batch (unordered insertMany, :135) [M]. Any _id that is not 24 hex is refused with 400 before storage (lib/api/shared/objectid-validation.js, since 15.0.7) [M]. The socket's dbAdd matches NSCLIENT_ID, else created_at, and answers a match with the stored record [M].

    2.4 Profile and food¶

    v1 POST and PUT accept only a 24-hex _id or none; anything else is 400 [M]. On 15.0.8 the POST stores a sent 24-hex _id as a string while PUT and DELETE look up the ObjectId, so a PUT after a POST leaves two records (BF-99, BF-100) [M]. On dev both store the ObjectId and PUT leaves one [M]. Re-POSTing a stored profile _id is 500 (duplicate key) on both [M]. The socket's dbAdd on profile matches NSCLIENT_ID, else startDate, and replaces the match (:653-690 @15.0.8) [R].

    2.5 API v3 (every collection)¶

    POST looks for identifier, or a 24-hex identifier equal to the _id of a record that has none, or the collection's fallback fields against a record that has no identifier (identifyingFilter, lib/api3/storage/mongoCollection/utils.js:128-168 @15.0.8; fields in lib/api3/generic/setup.js: entries date + type, treatments created_at + eventType, devicestatus created_at + device, profile and food created_at) [R]. A match is answered 200 with isDeduplication; but date, utcOffset, eventType, device and app may not change, so a re-send with another time or device is 400 and the record is unchanged [M, 2026-10-17 lab]. A record first written through v1 has no date or device: on 15.0.8 its v3 re-send is 400, on dev it is accepted when date equals created_at [M]. GET by a v1 record's hex _id works on both [M].

    2.6 A body _id on API v3¶

    API v3 does not read or convert _id; a POST that carries one is stored with it as sent, and a 24-hex value becomes a string _id, on both refs [M]. v3 replies and reads never show _id [M], so the client cannot see this. On 15.0.8 a v1 find[_id] for that hex then misses the record (query.js converts to an ObjectId); dev's v1 lookups match both forms [R]. Filed as BF-170 (2026-10-18). On dev since #8845 (merged 2026-10-26, 47723cda), API v3 create, PUT and PATCH refuse a client-supplied body _id with 400 [R], and identity I2 states that rule.

    2.7 What a re-send does, by collection and path (added 2026-10-29)¶

    This section has its own pin: the write-contract matrix on dev db3b9e4e (dev-db3b9e4e-v2.json, measured 2026-10-27, form resend-identity). The record re-sent is identical to the first and carries no identifier, so it is matched by each collection's own key. [M]

    collection API v1 API v3 socket in-process
    entries updated updated duplicate updated
    treatments updated updated kept updated
    device status duplicate kept kept duplicate
    profile duplicate updated updated duplicate
    food duplicate updated duplicate duplicate
    activity duplicate n/a duplicate duplicate
    • updated: one record, and srvModified advances (upsert). Whether fields left out of the re-send are kept (merge) or dropped (replace) differs by path. The census reads replace on v1 and in-process treatments, the v3 dedup and the socket profile match. This is not yet re-measured.
    • kept: one record and nothing written. The reply names the stored record (first upload wins).
    • duplicate: a second record is stored.

    The same matrix's resend-near form re-sends the record one second later. Every path stores a second record, except the socket's treatments, where the ±2 s similar match keeps one. [M]

    Three related facts: - With an identifier. v1 treatments match on it first and update (since 15.0.7, #8421). On dev since #8859, v1 entries match on it and update, and v1 device status matches on it and keeps the stored record. [M] - With changed fields. A v1 treatment re-sent with a changed amount or time is updated. API v3 answers 400 when date, device or eventType changes (v3-identifier-immutable). That 400 is the only refusal of a re-send on any path. [M] - The socket's treatment exact match keeps the first record and drops an edited re-send. Session -4f's dedupe gate, 2026-10-29, pins this. [M]

    What clients rely on. Loop's doses and early-ended overrides, and Trio's finalized doses and temp targets, are re-sent by POST over v1 and rely on the update. Carb edits use PUT, PATCH, or a delete followed by a new record (client survey). D-LOOP-ID rule 3 (maintainer, 2026-10-29) keeps today's per-path behaviour as the default. A switch, a site setting plus per-client quirks, may opt a client into keep-first or refuse. The duplicate cells are re-sends without an identifier, which identifier-first cannot reach. Closing them needs a natural key per collection (food and activity have none), and that changes outcomes (corrected 2026-10-29 by the ID-FIRST-MATCH census).

    3. UUID_HANDLING¶

    UUID_HANDLING is on unless set false (env.uuidHandling = readENVTruthy("UUID_HANDLING", true), lib/server/env.js:93 @15.0.8, :102 @fade2299) [R]. It was added in 15.0.7 (commit bf6cfb77, reached dev in #8456) [R].

    • Writes, v1 entries and treatments only. Any string _id that is not 24 hex is moved to identifier when the write has no identifier, and dropped either way; the server assigns an ObjectId [M]. The test is "not 24 hex", not "is a UUID": ridlab-1a2b3c4d is moved too [M]. With the flag off the value is dropped, not kept [R]. v1 devicestatus, profile and food refuse such an _id with 400 instead [M]; the socket and API v3 store it as _id [M].
    • Reads and deletes, v1 entries and treatments only. A find[_id] (or DELETE /treatments/<id>) value that matches UUID_RE (lib/server/query.js:7 @15.0.8, :12 @fade2299, case-insensitive) becomes identifier = value or _id = value; the comparison is exact, so a record sent with a lower-case UUID is not found by the upper-case form, nor the reverse [M]. A value that is neither 24 hex nor UUID-shaped is passed as a literal _id, so DELETE /api/v1/treatments/<non-UUID identifier> deletes nothing [M]; find[identifier]= finds it [M]. $in lists are not rewritten [R]. Devicestatus lookups do not pass the flag [R].
    • Version-scoped quirks it serves (D20 rule 7: today's handling becomes a registry entry scoped to the versions that send it, its behaviour unchanged). QUIRK-TREATMENTS-006: Loop sends a Temporary Override's syncIdentifier UUID as _id (read at LoopWorkspace f8412858, Loop 3.14.8; measured in the corpus: every stored document it fires on is an override with an upper-case UUID). QUIRK-ENTRIES-004: upper-case UUIDs and 24-character non-hex strings stored as entries _id on two corpus sites, attributed to older Trio versions by a backlog, unmeasured. Trio 1.0.1 (e41c9db3) sends _id on carbs and temporary targets (CarbsEntry.swift:29, TempTarget.swift:50) and its other treatments' UUID as id, which Nightscout does not read (QUIRK-TREATMENTS-007). [R]

    What 15.0.0 broke. Not _id values, as far as the record shows. #8026 ("Mongo driver update & less frequent database polls", merged 2023-10-12) moved to mongodb-legacy 5, which no longer has the collection methods insert, save and update. 15.0.0 still called them on several paths (git show 15.0.0:lib/server/…): profile.js:11,22, food.js:8,26, activity.js:11,24, treatments.js:163 (v1 PUT) and websocket.js:406,454,472 (dbAdd). The issues filed in the two days after the release report exactly those calls: #8114 (profile editor and v1 profile saves fail), #8119 (iAPS profile upload), #8120 (api(...).save is not a function at treatments.js:163, xDrip+ treatments), #8121 (ctx.store.collection(...).insert is not a function at websocket.js:406, AndroidAPS dbAdd), #8146 (api(...).insert is not a function at profile.js:11), and #8117 (deleting treatments from Reports answers 500, closed as the same root cause without a stack trace). #8115 reverted #8026 "to allow further testing", which is 15.0.1; #8111 ("WIP: fix WS v1") was closed unmerged. The entries, treatments-create and devicestatus write code of 15.0.0 differs from 15.0.1 only in the method names (replaceOne / insertOne against update / insert), both replacing with the document as sent, so a non-ObjectId _id was handled the same way on both. No issue in that window names _id. [R: issues and PRs read with gh on 2026-10-18; diff of lib/ between the tags]

    Why a non-ObjectId _id still broke apps before 15.0.7. MongoDB never rejected the value: a UUID or other string _id was stored as sent. What failed was every later operation that coerced the id with ObjectID(), which throws on a value that is not 24 hex characters. At 15.0.6 that coercion sits in the v1 by-id query helper (updateIdQuery, lib/server/query.js:92-96, used by GET and DELETE by _id), in v1 PUT (treatments.js:142, profile.js:18, food.js:20, activity.js:22), in the profile, food and activity deletes (profile.js:81, food.js:44, activity.js:64) and in the socket's dbUpdate and dbRemove (websocket.js:272, 510). So a record stored under a UUID could not be edited or deleted by its id. A throw inside a socket event handler is not caught by an HTTP framework and can stop the server process. The maintainers' fix was UUID_HANDLING in 15.0.7, which moves such a value to identifier and lets the server assign the ObjectId. [R at 15.0.6; the maintainer's account, 2026-10-18; the crash path is read, not run]

    5. For app developers: what holds today¶

    Each rule says the version it holds from; "dev" means not yet released.

    1. To keep your own handle on a record, send either a 24-hex ObjectId you create as _id, or an identifier. A 24-hex _id is stored as that ObjectId on v1 entries and treatments since 15.0.7, and on v1 devicestatus, profile, food and the socket on dev; on 15.0.8 those paths store it as a string that their own id lookups miss [M]. API v3 stores a body _id as a string on both, and never returns it [M]; on dev since #8845 it refuses one with 400 [R]. On v3, use identifier.
    2. Do not put any other value in _id. On v1 entries and treatments it is moved to identifier or dropped (UUID_HANDLING, 15.0.7+); on v1 devicestatus, profile and food it is refused with 400 (15.0.7+); on the socket and v3 it is stored as the _id (all versions) [M].
    3. identifier is matched by v1 treatments (15.0.7+) and API v3 (all 15.x), not by v1 entries, v1 devicestatus, or the socket [M]. On v1 treatments, sending identifier makes the server ignore the _id you send [M].
    4. Entries are matched on time, not on either id. One reading per sysTime + type; a new identifier at a stored time overwrites the stored one's, and one identifier at two times is two readings (15.0.x) [M]. Do not re-send an entry's _id with a different time: 500 and the rest of the batch is lost (15.0.x) [M].
    5. Devicestatus has no match key. Every POST adds a record (15.0.x); re-sending a 24-hex _id is 500 on 15.0.8 and answered with the stored record on dev [M].
    6. Read the reply for the _id that is stored. It can differ from the one you sent (v1 treatments with identifier; entries matched by time, on dev) or be absent (v1 treatments matched by time, 15.0.x; entries matched by time, 15.0.8) [M]. API v3 replies name only identifier [M].
    7. A delete is not final on API v3. v1 DELETE removes the record and a re-send stores it again; v3 DELETE marks isValid: false, and a v3 POST with the same identifier restores it, even with another time and device (15.0.x) [M].

    6. Open decisions¶

    Each is a row in the queue. All six are decided (maintainer, 2026-10-27 and 2026-10-29, D-LOOP-ID); none of the 2026-10-29 rules is built yet. The rules are stated in the identity specification §3–§5.

    item decision
    ID-FORMAT-DECISION 1 to 256 URL-safe characters, a UUID recommended, placeholders (invalid, undefined, null, NaN) refused (2026-10-29). Not enforced; ID-VALIDATE ships with or before ID-FIRST-MATCH
    ID-CLIENT-OID-DECISION a client may still send an ObjectId _id over API v1 (legacy); going forward the server sets _id and the client sets identifier (2026-10-29). API v3 refuses a client _id (BF-170); identifier wins when the two name different records (2026-10-18)
    ID-V3-IMMUTABLE-DECISION merge on match stays the default for a re-send with changed fields; API v3 keeps refusing a changed date, device or eventType; PUT replaces; a site setting plus per-client quirks may opt a client into keep-first or refuse (ID-RESEND-SWITCH); a default changes only in a major (2026-10-29)
    ID-ABSENT-DECISION identifier is SHOULD for legacy writers, with the time-key fallback kept, and MUST for registered controller instances (2026-10-27). New natural keys for re-sends without identifier are ID-NATURAL-KEY
    ID-DELETE-REUSE-DECISION a re-send of a deleted record is acknowledged and the record stays deleted, on every path (2026-10-27; every path 2026-10-29). Today's code differs per path (§2.7 and the 2026-10-18 lab)
    ID-SCOPE-DECISION unique per collection, with the tenant in the key under multi; values globally unique by convention (2026-10-27)
    ID-SIMPLE-MATCH v1 entries and devicestatus match on identifier: on dev since #8859
