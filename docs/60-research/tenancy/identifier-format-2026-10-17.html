    ID-FORMAT: should Nightscout require a client identifier to be a UUID?¶

    Record

    Record as of 2026-10-17. A point-in-time document; it is not kept up to date.

    Contributor-facing. Snapshot, 2026-10-17. Input to queue item ID-FORMAT-DECISION and to the reply in upstream-asks-loop-identifier. Companion to identifier duplicates, whose corpus, site labels and client classes this note reuses. The proposed constraints are carried in the identity specification §4.

    Marks: [R] read from code at the commit given; [M] measured, by identifier-format-2026-10-17/idshape.py (corpus shapes, output results-2026-10-17.txt, control control-results-2026-10-17.txt) or by the two small harnesses in §3.3. Corpus output is aggregate counts and value shapes (regex classes, lengths, token signatures); no identifier value, serial or record content is printed or committed.

    0. Answer¶

    No. Do not require a UUID. Define identifier as an opaque, case-sensitive string with a small set of constraints, and recommend (not require) a UUID: v4 for a record made once on one device, v5 of a source-derived key when several devices must agree.

    Why not require it:

    • Non-UUID values are already in the wild and the server already accepts them on every write path [R][M]: 489 stored treatment identifiers at one site are 32-hex strings (§2); 15,117 entries at another site carry a 24-character non-hex alphanumeric _id, which 15.0.7 and later move into identifier (§3.1); and API v3 checks only "non-empty string" (§3.2). A UUID rule would reject writes that work today.
    • The ecosystem's own sync keys are not UUIDs. Loop's CGM syncIdentifiers are derived strings, and Loop's dose syncIdentifiers are pump-event hex of 14 to 72 characters (§1, §2). HealthKit and FHIR both define their sync or business identifier as a plain string (§5).
    • A UUID rule does not solve the watch-and-phone problem. What makes two devices agree is the derivation (the inputs must be the same on both), not the format. A UUIDv5 of a device-dependent key is still device-dependent (§4, §6.4).

    The constraints a format rule does need (each grounded below):

    # constraint why
    C1 a JSON string, at least one non-whitespace character already enforced on API v3 create (create/validate.js:19) [R]; v1 treatments reject a non-string (treatments.js:18-25) [R]
    C2 at most 256 characters (proposal) an indexed identifier near 1 KB fails the insert on MongoDB before 4.2 (measured on 3.6.8: 1,000 characters fails, the compound {date, identifier, created_at} key is 1,026 bytes) [M]; the URL path of an API v3 read is capped by Node's 16 KB header limit (20,000 characters gave 431) [M]
    C3 printable ASCII, no /, %, ?, #, space or control characters (proposal; or "URL-unreserved characters A-Z a-z 0-9 - . _ ~ plus :") API v3 addresses a record as /api/v3/{collection}/{identifier}. A raw / gives 404, a malformed % gives 400, and ?/#/space must be percent-encoded by every client [M]; %2F works in Express but is commonly rewritten or refused by reverse proxies [R, not run]. End to end on both servers, an encoded / works on every v3 by-identifier route: §3.4 (2026-10-18) [M]
    C4 not exactly 24 hex characters unless it equals the record's own _id both API v3 (filterForOne, identifyingFilter) and v1 (normalizeIdValue) treat a 24-hex value as an ObjectId _id as well, so it can address a different record [R]
    C5 not a reserved word: history (shadowed by GET /api/v3/{col}/history), . and .. (normalized away by URL libraries), and client sentinels such as invalid, undefined, null, NaN GET /api/v3/entries/history reaches the history route, not the record [M]; G7SensorKit returns the literal invalid when its inputs are missing (§1) [R]
    C6 one identifier, one record, per collection, forever (no reuse after a long interval) already in the reply; the companion note found 13 Loop syncIdentifier values on 2 to 4 treatments [M]
    C7 compared exactly (case-sensitive, no trimming or normalization) v1 and v3 match with $eq [R]; Loop sends upper-case UUIDs and the server's own v5 is lower-case (§2, §4), so a client must send one spelling consistently

    Use the UUID recommendation where it buys something concrete: v1 by-id routes understand only UUID- and ObjectId-shaped values (query.js UUID_RE, §3.1). A client that wants find[_id]=<identifier> or DELETE /api/v1/treatments/<identifier> to work must use a UUID; a client that uses find[identifier]=, API v3, or the reply's two-id rule does not need one.

    Readings:

    • Non-UUID identity values are the majority, not the exception. 248,949 treatments at 11 sites carry a non-UUID, non-ObjectId value in a client identity field (results, last section), almost all Loop dose syncIdentifiers. As identifier itself, 489 are non-UUID.
    • A / appears in real client keys. 503 Loop syncIdentifiers at site i end in a 3-character token containing /. Sent as identifier, each would need %2F in an API v3 path (C3).
    • Every UUID in the corpus is upper case and v4. No v5 UUID was found, so no stored record shows a client using UUIDv5 today, and none shows the server's own v5 (this corpus has no API v3 writer).
    • No CGM entry carries a client identity field. This agrees with the code read in §1: Loop and xDrip+ send none for entries; Trio's id (from 2026-03-24) postdates most of this corpus.
    • The 24-alphanumeric _ids at site j were stored as string _ids by whatever server version received them; on 15.0.7 and later the same write moves the value into identifier (§3.1).

    Not visible here: AndroidAPS, xDrip+ uploader and other API v3 writers are absent from the corpus, as the companion note says. Shapes, not values, were read.

    3. Server compatibility of non-UUID identifiers¶

    3.1 API v1 [R] (15.0.8 92d0834, dev fade2299)¶

    path behaviour with a non-UUID identifier
    treatments write, identifier in body matched first, by exact string ({identifier: {$eq: v}}), any characters; _id dropped from the replacement (treatments.js:356-381 @92d0834). Non-string values throw (treatments.js:18-25). Same on fade2299
    treatments / entries write, string _id that is not 24-hex moved to identifier when UUID_HANDLING is on (the default), deleted otherwise (treatments.js:394-405, entries.js:267-277 @92d0834; treatments.js:452-459, entries.js:334-341 @fade2299). The test is "not 24-hex", not "is a UUID", although the comments say UUID: an xDrip4iOS 24-alphanumeric _id or a Loop-style derived string becomes an identifier
    entries write, identifier in body stored, not matched; entries match on sysTime + type (the reply's "gap")
    read/delete by _id (find[_id]=, DELETE /api/v1/treatments/:id) normalizeIdValue: 24-hex becomes an ObjectId; only a value matching UUID_RE (query.js:7 @92d0834, query.js:12 @fade2299) is looked up by identifier; any other string is compared to _id and finds nothing (query.js:131-143 @92d0834, 195-206 @fade2299)
    query by find[identifier]= generic exact match on the field, any string
    index identifier is indexed alone and in {date, identifier, created_at} on entries and {eventType, created_at, identifier, date} on treatments (entries.js:224-226, treatments.js:430-432 @92d0834)

    3.2 API v3 [R]¶

    • Create: resolveIdentifier computes the server key; a client value that differs only logs a warning and is kept (operationTools.js:114-126); validate requires a non-empty, non-whitespace string, nothing more (create/validate.js:19). No pattern, no length. Same at both commits.
    • Address: /{collection}/:identifier for GET, PUT, PATCH, DELETE (generic/collection.js:42), registered after GET /{collection}/history (lines 54-57).
    • Lookup: exact identifier match, plus _id when the value is 24-hex (mongoCollection/utils.js:107-116 @92d0834). On fade2299 a non-hex string is also compared to a string _id (utils.js:105-123), so a v1 record stored with a non-hex string _id is reachable.
    • Swagger: paramIdentifier and identifierField are type: string with a UUID-shaped example only, no pattern or maxLength (swagger.yaml:1052-1060 @92d0834, 1011-1020 @fade2299).

    3.3 What breaks: two small harnesses [M]¶

    URL path. Express 4.22.2 (the version in the checkout's node_modules; dev pins 4.22.2, 15.0.8 4.22.1) with the four v3 routes and the history route registered in the server's order, driven over HTTP (v3-path-routing.js; Express routing only, no proxy, no auth, no storage):

    identifier in path GET result
    UUID, g7:SERIAL:12345 (colon), a+b reaches the record route; colon and plus pass through unchanged
    a%20b%20c, a%2Fb, a%25b, a%23b, a%3Fb reaches the record route, decoded to space, /, %, #, ?
    a/b (raw slash) 404
    a%zzb (malformed escape) 400 "Failed to decode param"
    history reaches the history route, not the record (PUT and DELETE do reach the record)
    . and .. reach the record route in this harness; client URL libraries normalize them away
    8,000 characters reaches the route; 20,000 characters: 431 (Node's 16 KB header limit)

    Index key size. (index-key-size.js.) Local MongoDB 3.6.8 (FCV 3.6), a scratch database with the v1 entries indexes {identifier: 1} and {date: -1, identifier: -1, created_at: -1}, dropped afterwards: a 256-character identifier inserts; 1,000, 1,010, 1,020, 1,100 and 2,000 characters fail with code 17280 "key too large to index" (the compound key is 1,026 bytes at 1,000 characters). MongoDB 4.2 removed this limit at FCV 4.2 (not fetched from MongoDB's documentation; MongoDB's tracker DOCS-11942 was listed by a search, not opened).

    3.4 URL-form identifiers, end to end (2026-10-18) [M]¶

    The maintainer prefers URL syntax for identifiers (dexcom://g7/<serial>/<offset>, see the identifier conventions), which puts : and / in every value. §3.3 ran Express routing alone; this run asks the two servers. url-identifier-probes.js wrote synthetic scheme://g7/<digits>/<seconds> identifiers to 15.0.8 (92d08342) and dev (fade2299), started by the record-identity lab on a dedicated mongo:7 container (7.0.43), with no proxy in front. Output: url-identifier-results-2026-10-18.md. Both refs gave the same cell in every row, and two runs gave the same table.

    path encoded (%3A, %2F) %2F only, : raw raw
    v3 POST (identifier in the body), entries and treatments 201, stored exactly — —
    v3 GET /{collection}/{identifier} 200, the record 200, the record 404
    v3 PATCH, PUT, DELETE by identifier 200 each; PATCH and PUT change the stored value, DELETE sets isValid: false not run PATCH 404
    v3 PUT for a new identifier (create) 201, stored exactly — —
    v3 search ?identifier$eq= and ?identifier= 1 found each — —
    v1 find[identifier]= 1 found — 1 found (raw : and / are legal in a query string)
    v1 treatments POST, then a re-send with another amount one record, updated — —
    v1 entries POST, then v3 GET stored with the identifier; v3 GET 200 — —
    v1 DELETE /api/v1/treatments/{identifier} 200 with deletedCount: 0, the record stays — —

    Controls: the same identifier plus /1 finds nothing on v3 GET (404), v3 search (0) and v1 find[identifier]= (0), on both refs; the raw rows are the routing control.

    Consequences for the character set:

    • / and : can be allowed. A URL-form identifier works on every API v3 by-identifier route and on v1 find[identifier]= at the shipping release and at dev, provided the client percent-encodes the identifier as one path segment in a v3 path (every reserved character, / included: encodeURIComponent in JavaScript). A path-escaping helper that leaves / alone builds a different route and gets 404; Foundation's urlPathAllowed character set is such a helper (it allows /) [R, Apple documentation, not run].
    • v1 by-id routes do not take them, as for every non-UUID value (§3.1): v1 DELETE by such an identifier answers 200 and deletes nothing. A client that deletes over v1 uses the _id from the write reply.
    • Reverse proxies are not measured. Some decode %2F before forwarding or refuse it (§3.3). A client behind one can read with v3 search (?identifier$eq=, measured above) and with v1 find[identifier]=; update and delete by identifier over v3 still need the path. A site operator check of a proxied deployment is the open item.
    • %, ?, #, space and control characters stay excluded: they need escaping everywhere and appear in no convention.

    4. UUIDv5 as the bridge¶

    If a client hashes its derived key into a UUIDv5 and sends that as identifier:

    gained lost
    works with today's v1 by-id routes (UUID_RE), every version since UUID_HANDLING readability: the sensor, session and time are no longer visible in the record

    Namespace. The server's v3 namespace is the 16 ASCII bytes of NightscoutRocks! (operationTools.js:6,106), i.e. 4e696768-7473-636f-7574-526f636b7321; read as a UUID its variant bits are the reserved NCS variant, so it is not an RFC-conformant UUID of any version (computed, not a defect: v5 accepts any 16 bytes). The server's names are <device>_<date>[_<eventType>] (operationTools.js:95-107). A client v5 in the same namespace collides with a server-computed identifier only if its name string is byte-identical to such a name (SHA-1 makes accidental collisions between different names negligible). A scheme-prefixed name such as g7:<serial>:<seconds> cannot equal <device>_<digits> unless a client's device string were itself crafted to match. The risk is semantic, not cryptographic, but it is avoidable: RFC 9562 recommends a v4 or v7 value for a custom namespace (§6.6). Proposal: Nightscout publishes one client namespace (a fresh v4, documented next to the format rule) and asks clients to put a scheme prefix in the name (g7:, g6:, libre: …). Two independent apps that adopt the same scheme then agree with each other, and none can coincide with a server key.

    5. Precedents (fetched)¶

    FHIR R4's Identifier.value is a string "unique within the context of the system", with system a URI that "establishes the namespace for the value"; FHIR strings are limited to 1 MB and should contain non-whitespace content, while FHIR's resource id (the server id) is a separate type limited to [A-Za-z0-9\-\.]{1,64}, case-sensitive (FHIR R4 data types). HealthKit's HKMetadataKeySyncIdentifier is "a unique string that identifies a piece of data so it can be updated and synced", must be accompanied by HKMetadataKeySyncVersion, and a save with a greater sync version replaces the stored object (Apple, documentation JSON for HKMetadataKeySyncIdentifier). Neither imposes a UUID. The FHIR split, a free-form business identifier beside a tightly-charactered, length-capped server id, is the same split as Nightscout's identifier beside _id; FHIR's id rule is a reasonable model for C2/C3 if the maintainers want a stricter character set. Open mHealth and IEEE 11073 were not checked.

    6. Implications¶

    6.1 The reply (reply.body.md)¶

    • Nothing in it overstates a UUID requirement. It says "a string. We recommend a UUID", which this note supports.
    • Rule 1 is narrower than the code. "UUID_HANDLING … moves a UUID _id to identifier": the code moves any non-24-hex string _id (§3.1). Not wrong for Loop, but "a non-ObjectId string _id (a UUID, for example)" would be exact.
    • Option 3 needs two qualifiers if it stays as written: the <serial> must be the sensor's serial number, not G7SensorKit's sensorID (a DXCMxx BLE name that repeats across sensors), and the string form works on v1 treatments, API v3 and find[identifier]= but not on v1 by-id routes; its UUIDv5 works on all of them.
    • Option 2's premise matches the code: today each device computes its own activation estimate from its own receive time, so phone and watch timestamps differ unless one adopts the other's.
    • "Later, only if needed: the identifier's length limit, character set and case comparison" can now carry a concrete proposal (§0, C1-C7) instead of an open question.

    6.2 ID-FORMAT-DECISION (proposed answer)¶

    identifier is an opaque, case-sensitive string, 1 to 256 characters, from [A-Za-z0-9._~:-], not exactly 24 hex characters, not history, ., .., invalid, undefined, null or NaN; one identifier names one record per collection. Recommended: UUID v4 for a one-device record; UUID v5 in the published Nightscout client namespace over a scheme-prefixed, source-derived name when several devices must agree; required only by clients that use v1 by-id routes. The 256 limit and the character set are proposals for the maintainers: the corpus's longest client key is 72 hex characters plus a 4-character suffix, and the only character outside the set seen in client keys is the / in §2 (and the space in Loop's CGM keys, §1).

    6.3 ID-VALIDATE (server checks worth adding)¶

    In order of value, each a 400 on API v3 and a per-record rejection on v1 once per-record results exist:

    1. Length over the limit (protects pre-4.2 MongoDB from a failed insert that today surfaces as a storage error, §3.3).
    2. Exactly 24 hex in identifier that is not the record's own _id (C4: ambiguous addressing).
    3. Reserved words (history, ., ..) and known client sentinels (invalid from G7SensorKit; undefined, null, NaN from string-formatting bugs). A sentinel shared by many readings is the worst case for C6: with identifier matching on entries, every "invalid" reading would overwrite the last.
    4. Characters outside the set (C3), at least /, %, ?, #, whitespace and control characters. This one would reject Loop's current G7/G6 syncIdentifiers (they contain spaces) if Loop sent them unchanged, so roll it out as a warning first, or define the set to allow a space and accept that such ids must be percent-encoded in v3 paths.

    Do not add a UUID pattern check: it would reject the 489 stored values and every non-UUID key in §1.

    6.4 Loop's G7 identifier¶

    Verified: today's G7 syncIdentifier would not dedupe a watch and a phone reading the same sensor. Its first token is activatedAt.timeIntervalSince1970.hours, a Double printed in full, where activatedAt = (local time when the first glucose message was received) − (the message's sensor seconds counter), computed independently on each device (G7Sensor.swift:134, G7CGMManager.swift:313-322,511-517 @dd91f46; unchanged in next-dev e17129d). Receive latency and clock offset differ between devices, so the token differs; it would differ even between two discoveries on one device. The reading's date is derived from the same per-device estimate (G7CGMManager.swift:469,476,547), which is why the reply's option 2 needs one device to adopt the other's estimate.

    A device-independent G7 form needs only inputs both devices read from the sensor:

    • sensor identity: the real serial number (transmitterVersion.serialNumberString, read in next-dev), not the DXCMxx peripheral name, which has a 2-character suffix and repeats across sensors. Without the serial, the session must be identified some other sensor-sourced way; rounding the activation estimate is not safe (two devices can fall either side of a rounding boundary).
    • reading position: the sensor's own seconds counter (glucoseTimestamp), already used.
    • no fallback sentinel: if either input is missing, send no identifier (let the time key apply) rather than "invalid".
    • one spelling: fixed scheme, separators and case (e.g. g7:<serial>:<seconds>), or its UUIDv5 in the published namespace; both devices must produce the same bytes.

    Whether messageTimestamp counts from the sensor session or from each display's pairing slot: see §7. Very probably the sensor session (shared by every display, and equal between live and backfill), not yet measured with two displays.

    7. Is the G7 seconds counter shared across devices?¶

    Answer: very probably yes, but nobody has measured it with two displays. The value Loop keys on (glucoseTimestamp = the glucose message's counter minus its age, equal to a backfill record's timestamp) is the sensor's own session clock. It counts seconds from sensor activation. It does not start at each display's pairing. Every independent implementation read here, the official app's own field name, a captured session, and the sensor's expiry behaviour all point that way [R][M]. Two caveats: no capture with two displays on one sensor exists in any repository or source opened here, and one implementation (xDrip4iOS) reads the field's relation to age the other way round (§7.3). So g7:<serial>:<seconds since activation> should be device-independent. Confirm it with the two-display capture in §7.6 before a client relies on it.

    Do they agree? On the clock, yes. Every implementation treats the counter as seconds since sensor activation (the "pairing" in G7SensorKit's comments is the sensor's start-up pairing; next-dev says "seconds-since-activation" outright). Every one converts it to a date as now − counter, and every one that reads backfill puts it on the same clock. The one disagreement is where a reading sits on that clock (§7.3).

    The alignment repo's own deep dives already say "seconds since sensor activation" (g7-protocol-specification.md lines 269, 312, 358), but they were read from the same code [R]. Its dexcom-ble-protocol-deep-dive.md line 18 gives the G7 "1 (exclusive connection)" slot. That is contradicted by the slot model in G7SensorKit next-dev, g7sim, xDrip4iOS and DiaBLE (§7.2).

    7.2 A property of the sensor, or of the connection?¶

    The G7 holds one slot per display type: phone 2, watch 3, receiver 4, pump 5, and others (G7DisplayType.swift:18-28 next-dev). A client says which type it is during authentication (Juggluco sends 0d 00 02, phone, DexGattCallback.java:391). Held slots set bits in the advertisement's types-in-use byte (G7DisplayType.swift:31-33; g7sim sensor.go:295-302). G7SensorKit next-dev: "a watch app takes its own [slot], alongside the phone's" (G7CGMManager.swift:283-284, G7Sensor.swift:190-192). xDrip4iOS: each Bluetooth channel is "an independent authentication slot inside the sensor" (CGMG7Transmitter.swift:8-13). So a phone and a watch reading one sensor directly hold separate connections with separate keys [R].

    Nothing read here shows the counter is per slot, and five things show it is the sensor's:

    1. The official app names it txTime (transmitter time). It does so in DiaBLE's record of the app's EGVResponse class (DexcomG7.swift:256-259) and in an app log line kept in G7SensorKit's tests: readEGV(txTime=40104,seq=136,session=1,age=4,...) (G7GlucoseMessageTests.swift:87 @dd91f46). That is a sensor clock, not a link clock [R].
    2. A captured session starts the counter at activation [M]. In G7SensorKit's lifecycle vectors (G7GlucoseMessageTests.swift:33-43), the first message is state stopped at counter 182, sequence 1, session byte 0. The next messages are warmup at reading positions 200, 500, … and ok from 1700. A session that began when this display paired would also look like this. But see 3.
    3. The sensor's own expiry is on this clock [M]. The same vector set's expired message has reading position 907,385 s. A 10-day sensor's own 0x52 reply gives a session length of 907,200 s (10 days + 12 h grace; g7sim state.go:49-56, from captured replies). The sensor marks itself expired just past its session length on this counter. A per-display counter that started late would put expiry late for that display. Loop's expiry display (G7CGMManager.swift:134-144), Juggluco's maximum-life check (java.cpp:151,173) and xDrip4iOS's lifetime checks all rest on the counter being session-relative. If the counter started at each display's pairing, all of them would misplace expiry for a display paired after activation. None of them guards against that case, and none of their issue trackers was searched for such a report.
    4. Commands that write to shared sensor state use it. A calibration (0x34) is sent as a time on this clock (G7CalibrationMessage.swift:13-14 next-dev; xDrip4iOS "converts its date into transmitter time", CGMG7Transmitter.swift:98-104). The sensor then reports it back in the calibration-bounds reply as lastCalibrationTime, beside a sessionNumber and sessionSignature (DexcomG7.swift:319-330). One calibration applies to the sensor for every display, so the clock it is expressed on must be one every display shares.
    5. Backfill is requested by range on this clock (0x59 + start + end, DexcomG7.swift:292-294; g7sim handler_test.go:121-123). The sensor serves records from one 24-hour store (g7sim models one store; the backfill reply carries a first sequence number and first and last timestamps, DexcomG7.swift:362-369).

    g7sim models exactly this: one Activation and one reading list per sensor, with every slot served the same Reading in a window (state.go:11-18,64-71; sensor.go:421-431). It is a model built on the same assumption, so it does not prove the assumption.

    An analogue on Dexcom's side: an EGV record in Dexcom's v3 API carries transmitterId, transmitterTicks (int64) and displayDevice (iOS, android or receiver) side by side ([S] third-party schema mirror, apis.io "Dexcom API EGV record", opened 2026-10-17). Dexcom's own endpoint overview says systemTime is "the UTC time according to the device" and "not 'true' UTC time because of drift and/or user manipulation of the device's clock" ([S] developer.dexcom.com/docs/dexcomv3/endpoint-overview, opened 2026-10-17). The schema keeps a transmitter tick count apart from the display's clock. It does not say whether two displays report the same ticks, and the official schema page did not load, so this is context only.

    7.3 Live and backfill: same value for the same reading?¶

    Yes, on G7SensorKit's reading, which the captured data supports. G7SensorKit, DiaBLE, Juggluco and g7sim put a live reading at counter − age and a backfill reading at the record's counter, and treat the two as equal. xDrip4iOS puts a live reading at counter and adds age to get the sensor's age. If xDrip4iOS were right, G7SensorKit's live key would sit age seconds before the same reading's backfill key.

    The lifecycle vectors settle it for one session [M]. Their age varies (5 or 7 s), and so does the raw counter mod 300 (205, 207). counter − age is constant mod 300 (200) for all seven readings after start-up. That holds only if counter − age is the reading's position on the sensor's 5-minute grid and counter is the time the message was sent.

    lifecycle 6 1707 7 1700 200 207

    Reproduce: decode the hex strings at G7GlucoseMessageTests.swift:33-43 (bytes 2-5 and 10-11, little-endian).

    xDrip4iOS's offset matters only to xDrip4iOS. If it ever built a key from transmitterTime, its live and backfill keys for one reading would differ by age. It does not build one today.

    Two smaller points:

    • The backfill counter is 24-bit (data[0..<3]), good to 194 days, well past a 15.5-day session. The live counter is 32-bit. A key should print the decimal value, not the bytes.
    • sequence is also sensor-side and appears in the backfill reply, but it is not a clean reading index. In the lifecycle vectors it runs 1, 3, 4, … against positions 80, 200, 500, …, and a backfill record does not carry it. The seconds counter is the better key.

    7.5 Verdict¶

    g7:<serial>:<seconds>, where <seconds> = messageTimestamp − age for a live reading and the record's timestamp for backfill, printed in decimal, is device-independent on everything read here:

    • Counter: sensor-side, from activation, shared by live and backfill, measured on one captured session.
    • Serial: sensor-side.
    • Clock drift: irrelevant. Neither input touches a receiving device's clock.
    • 5-minute slots: no rounding is needed or wanted. The counter lands on the sensor's own grid (activation + k·300 + phase, with phase 185-200 s in the post-warm-up vectors), so the exact integer is the key. Rounding to a 300-s slot would only add a boundary risk.

    Caveats:

    • Not measured with two displays. Points 1-5 in §7.2 make a per-slot counter very unlikely, but nothing rules it out.
    • The serial needs 0x4A. G7SensorKit main does not send it. Until it does, Loop cannot form this key, and a DXCMxx name is not a substitute (§6.4).
    • Readings before the serial arrives. The serial comes after the first glucose message (recordPendingSensorStart waits for it, G7CGMManager.swift:585-596 next-dev). Readings in that gap should carry no identifier rather than a partial one.

    7.6 The lab that would settle it¶

    Use one real G7 sensor (g7sim cannot settle this, because it encodes the assumption) and two displays holding different slots:

    • A. A phone on Loop next-dev in direct mode (display type 2). G7SensorKit already logs every G7GlucoseMessage with messageTimestamp and age and every G7BackfillMessage.
    • B. A watch-type or receiver-type client. Juggluco or xDrip4iOS primary mode on a second phone, set to another display type, or a Dexcom receiver if its log can be exported.

    Steps:

    1. Run both for at least 2 hours, with B paired at least a day after sensor start. A per-pairing counter would then differ by about 86,400 s, which is impossible to miss.
    2. For every 5-minute window, compare A's and B's messageTimestamp − age.
    3. Force a gap on B (out of range for 30 min), then compare B's backfill timestamps with A's live values for the same windows.
    4. Read 0x4A on both and compare serials.

    Pass criterion: every shared window matches exactly. Record only the differences and counts, never the serial or raw frames, in anything committed. Once one real capture exists, g7sim can then regression-test that each client forms the same g7: string from the same bytes.

    7.8 Implications¶

    For the reply's option 3. The source-derived identifier is sound for G7 if it uses only the serial and the sensor counter. Suggested wording:

    For a G7, an identifier both devices can compute is g7:<serial>:<seconds>, where <serial> is the sensor serial number from the transmitter-version (0x4A) reply and <seconds> is the sensor's seconds-since-activation counter for the reading (messageTimestamp − age for a live reading, the record's timestamp for backfill). Every G7 implementation we read (G7SensorKit, xDrip+, xDrip4iOS, Juggluco, DiaBLE) treats that counter as the sensor's session clock, and a captured session lands on its 5-minute grid only that way. We have not yet seen a capture with two displays on one sensor, so we would confirm with one before relying on it. The activation date estimated from the receiving device's clock must not be part of it.

    For Loop.

    • Change the key:
    • drop the activatedAt.hours token;
    • key on serialNumberString, which next-dev already reads;
    • keep the counter it already uses (glucoseTimestamp / backfill timestamp, which agree);
    • send no identifier until the serial is known.
    • Leave date alone: it can stay derived from the per-device activation estimate, since dates are not compared for identity under the two-id rule.
    • Before shipping: the two-display capture in §7.6.
