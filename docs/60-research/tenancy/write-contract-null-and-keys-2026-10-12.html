    WRITE-CONTRACT: explicit nulls, natural keys and identical re-sends, measured¶

    Record

    Record as of 2026-10-12. A point-in-time document; it is not kept up to date.

    Contributor-facing. Snapshot, 2026-10-12. Status: superseded for Q1b by the maintainer's decision of 2026-10-26, which sets the null rule's scope (merge on match, API v3 PATCH and the socket's dbUpdate; never a replace or a create) and ships it in 16.0.0; the current rule is in the write contract §6.1 and identity §3. §1.3's devicestatus case does not arise: under Q3 (i) a devicestatus re-send is never merged. Input to the maintainer decisions in write-contract spec §6 after the 2026-10-12 choices: Q1 = (a) merge on match; Q1b = (ii) under merge a JSON null deletes the field (RFC 7386); Q2 = (b) an identical re-send keeps today's rewrite. Three questions:

    1. Does any client send "field": null on a create or re-send, so that Q1b(ii) would remove a stored field on retry? (§1)
    2. For Q3: do distinct devicestatus records share (created_at, device), and do entries' date and sysTime name different instants? (§2)
    3. Under Q2(b), who re-sends unchanged records, and what does a consumer do with a record whose content is unchanged but whose srvModified is new? (§3)

    Marks: [M] measured, by the script and output named, in write-contract-null-and-keys-2026-10-12/. [R] read, from source at path:line@commit, not run. Paths for client sources are relative to externals/<repo>/. Most client reads were made by two read-only sub-agents; the citations marked (checked) were re-read for this document, the rest were not.

    0. Verdicts¶

    question verdict
    1. explicit nulls Yes, four uploaders send them on create, all through API v1 POST: tconnectsync, oref0, nightscout-connect and cgmsim-lib. Loop, Trio, xDrip4iOS, xDrip+, AndroidAPS (dev and master) and nightscout-librelink-up do not [R]. The stored corpus cannot confirm or refute this: it has no uploader from that list, and its only nulls are carbs/insulin, which the v1 treatments read adds [M]. Which fields matter: the treatment nulls (tconnectsync and cgmsim-lib carbs/insulin/duration) are normalised away by v1 prepareData before storage [M]. The devicestatus nulls are stored verbatim [M]: tconnectsync pump.battery.percent, oref0 openaps.iob, nightscout-connect librelinkup.sensor.* and librelinkup.patientDevice.*. All of these clients re-send the identical body after a failure [R]. Under Q1b(ii) such a retry deletes keys that the first write stored as null: the stored shape changes, but no non-null value is lost. A stored value is lost only if a second writer filled the field in between.
    2a. devicestatus (created_at, device) 3,078 groups (14,757 documents) are distinct records sharing the key. All are Loop, at all 11 sites with Loop devicestatus. A further 4,001 groups (22,635 documents) are byte-identical retry copies, also all Loop. Trio and the phone-model uploader have 0 of either [M]. In every distinct group the members share loop.timestamp and differ in loop.enacted.* (1,457 groups differ only there), uploader.battery, loop.predicted and the dose recommendations [M]. Keying devicestatus on (created_at, device) with merge would fold these into one record. Many are retries of one report whose upload-time fields changed, and some are distinct decisions (§2.1.1)
    2b. entries date vs sysTime 0 entries name instants 1 s or more apart. 427,003 of 719,559 differ by less than 1 s, because date carries sub-second milliseconds and sysTime is second-resolution. 292,556 are exactly equal [M]. Per client: §2.2.
    3. identical re-sends (Q2(b)) Every uploader re-sends records it already uploaded, mostly as whole-batch retries after a lost reply [R]. The only deliberate re-send of unchanged records is xDrip+'s user-triggered backfill; no client has a periodic "touch" [R]. AndroidAPS NSClientV3 is the only client that syncs by srvModified. For a record whose content is unchanged it writes nothing to its database and uploads nothing, with one exception: an Announcement less than 60 min old raises its alarm notification again [R]. A re-delivered copy can also revert a pending local edit of a few fields, but only when the server copy differs from the local one, which an identical re-send by definition does not cause. The corpus cannot measure how often this happens: 1 of 1,589,356 stored documents carries srvModified and none carries srvCreated [M].

    1.3 What a null does today, and what it would do under Q1b(ii)¶

    Today [M], on dev fade2299 and 15.0.8 92d08342, MongoDB 7.0.43 in a dedicated container (repro.py, v3.py; outputs repro-results.txt and v3-results.txt):

    • v1 POST stores null verbatim for any field prepareData does not handle. This was shown for:
    • treatments: a top-level field, a nested field, and reason;
    • entries: direction, noise, and a nested field;
    • devicestatus: top-level, pump.battery and uploader.battery;
    • profile: a top-level field, and mills.
    • v3 POST stores null verbatim, carbs and insulin included, because v3 does not run prepareData.
    • A v1 re-send of a treatment matched by syncIdentifier, with reason changed from "x" to null, stores reason: null (today's replace).

    Under Q1b(ii), applied to the per-client facts above:

    • The treatment nulls from tconnectsync and cgmsim-lib never reach the merge on v1, provided the null rule runs after prepareData, as the write step in spec §2.3 would. duration arrives as 0.
    • On v3 they would reach it, but neither client uses v3 [R].
    • The devicestatus nulls (tconnectsync, oref0, nightscout-connect) are stored by the first write. An identical retry would then delete those keys, assuming RFC 7386's recursive merge reaches nested objects. The record changes shape (the key goes from null to absent). No value is lost unless something else wrote that field in between.
    • nightscout-connect's Nightscout-to-Nightscout source re-POSTs stored documents. Any null stored on the source site deletes the matching field on the target on every re-send.

    2.1 devicestatus sharing (created_at, device)¶

    [M] analyze.py (corpus-results.txt, ## devicestatus … groups) and dsdiff.py/dsdiff2.py (dsdiff-results.txt, dsdiff2-results.txt). Bodies were compared with _id, srvModified, srvCreated, identifier, mills and utcOffset removed. The groups are the same whether created_at is compared as a string or as an instant.

    client groups with distinct bodies (documents) groups with identical bodies (documents)
    Loop 3,078 (14,757) 4,001 (22,635)
    Trio 0 0
    phone-model uploader 0 0
    • Distinct groups appear at 11 of the 12 sites, which is every site with Loop devicestatus.
    • Most distinct groups have 2 members (2,509). 178 have 10 or more members with 2 distinct bodies.
    • Loop created_at is stored with a .000 millisecond part; Loop sends whole seconds (§2.1.1). Every distinct group shares loop.timestamp.

    What differs, counted in groups:

    fields that differ groups
    only loop.enacted.{bolusVolume, duration, rate, received, timestamp} 1,457

    Reading (corrected by §2.1.1): these are either one stored decision re-sent by a whole-batch retry with fields read at upload time (B1), or two decisions in the same whole second (B2); the code does not say which is commoner. Under Q3(a) with merge they would become one record, and the last report's enacted or recommendation would overwrite the earlier one.

    Non-vacuity [M] (control-results.txt). A planted identical copy moved the identical-bodies count up by one group (2 documents). Two planted copies, each with one leaf changed (one with a nested null, one with an extra loop field), moved the distinct-bodies count up by two groups (4 documents).

    2.1.1 Loop's same-key devicestatus pairs¶

    Sources: LoopWorkspace f8412858 with submodules Loop c2fddb76, LoopKit 325bd820 and NightscoutService fe075ef0; NightscoutKit 4ec9fd12. NightscoutService tracks NightscoutKit branch = main, not a fixed revision (NightscoutService.xcodeproj/project.pbxproj:1324-1327@fe075ef0), so 4ec9fd12 is an assumption [R]. All citations below were read for this section. Paths are relative to externals/ (LoopWorkspace/<submodule>/… for submodules).

    Verdict: mixed, and neither half is (A). No code path re-uploads a status once an enactment is confirmed. Same-key bodies differ for two reasons. (B1) A whole-batch retry re-uploads the same stored decision, and some fields are filled in at upload time, so they can change between attempts. (B2) Two distinct decisions fall in the same whole second. The code does not say which reason dominates.

    Where the devicestatus is built [R]. Loop does not upload its loop decisions as devicestatus. The batch is walked in order. A loop decision is only remembered in lastDosingDecisionForAutomaticDose. A decision with reason updateRemoteRecommendation, normalBolus, simpleBolus or watchBolus becomes one devicestatus, paired with the remembered loop decision (LoopWorkspace/NightscoutService/NightscoutServiceKit/NightscoutService.swift:101,284-297@fe075ef0). deviceStatus(automaticDoseDecision:) takes iob, cob, predicted, automaticDoseRecommendation and recommendedBolus from the uploaded decision. It takes enacted and failureReason from the paired loop decision (…/Extensions/StoredDosingDecision.swift:148-164@fe075ef0). The function sets no identifier (same lines). NightscoutKit writes identifier only when one is set (NightscoutKit/Sources/NightscoutKit/Models/DeviceStatus.swift:60-62@4ec9fd12), so the server cannot tell a re-send from a new record.

    created_at and loop.timestamp [R]. Both are the uploaded decision's date (StoredDosingDecision.swift:149-150,153-155@fe075ef0). The date defaults to Date() when the decision is built (LoopWorkspace/LoopKit/LoopKit/DosingDecisionStore.swift:265@325bd820; LoopWorkspace/Loop/Loop/Managers/LoopDataManager.swift:966@c2fddb76). NightscoutKit formats both with .withInternetDateTime, which has whole-second resolution (Extensions/TimeFormat.swift:12,15-16; Extensions/ISO8601DateFormatter.swift:14-16@4ec9fd12). So two decisions made in the same second get the same created_at and loop.timestamp.

    The corpus agrees [M, one-off aggregate script, not committed]. All 485,141 Loop devicestatus documents store created_at with a .000 fraction, and loop.timestamp has no fraction. All of them report Loop version 3.x. §2.1's "millisecond resolution" is therefore the stored format; the values themselves are whole seconds.

    enacted and received [R]. enacted exists only when the paired loop decision has an automaticDoseRecommendation and no errors. received is hard-coded true, and enacted.timestamp is that loop decision's date (StoredDosingDecision.swift:63-70@fe075ef0). Nothing sets received to false or updates a status that was already sent. The only devicestatus write is postToNS (POST) (NightscoutKit/.../NightscoutClient.swift:646-648@4ec9fd12).

    Corpus [M, same script]: in the distinct groups received is never false. In 1,743 groups enacted is present in some members and absent in others. In 170 groups every member has enacted but with different values, and in all 170 the enacted.timestamp differs.

    What triggers an upload [R]. Every storeDosingDecision purges expired decisions, and the purge calls the delegate (DosingDecisionStore.swift:35-49,85@325bd820). The delegate is triggerUpload(for: .dosingDecision) (Loop/Managers/DeviceDataManager.swift:1319-1321@c2fddb76). So each stored decision starts an upload pass. triggerUpload for any data type also re-runs every type in failedUploads (Loop/Managers/RemoteDataServicesManager.swift:182-196@c2fddb76).

    Each loop stores a loop decision (LoopDataManager.swift:497-511@c2fddb76) and then calls updateRemoteRecommendation() (:954). That call stores an updateRemoteRecommendation decision only if carbs, glucose or dose data changed since the last one, and only if a manual bolus recommendation exists (:187,201,216,520-542). updateRemoteRecommendation() is also called after every enactBolus (DeviceDataManager.swift:863), from the watch (Loop/Managers/WatchDataManager.swift:395) and from bolus entry (Loop/View Models/BolusEntryViewModel.swift:382). A manual bolus stores its own decision (LoopDataManager.swift:817-837). Several decisions can therefore be stored within one second. Whether a given same-second pair came from these calls, and from which ones, is not settled by the code.

    Retry: whole batch [R]. Uploads for one type run one at a time (RemoteDataServicesManager.swift:347-385@c2fddb76). Each pass queries up to 50 decisions after the saved anchor, ordered by modificationCounter (NightscoutService.swift:274@fe075ef0; DosingDecisionStore.swift:197-198@325bd820). The anchor advances only on success. On failure the type is added to failedUploads, and the same batch is queried again on the next trigger (RemoteDataServicesManager.swift:363-371,106-111). There is no timer and no backoff. The batch goes out as one POST. A reply whose array length differs from the number sent counts as a failure, even if the server stored the documents (NightscoutClient.swift:479-491@4ec9fd12).

    Why a retried decision can get a different body (B1) [R]. Three inputs are read at upload time, not stored with the decision:

    • Pairing. lastDosingDecisionForAutomaticDose is reset to nil only after a successful POST (NightscoutService.swift:304-308). After a failure it still holds the last loop decision of the failed batch. On the retry, a status that comes before any loop decision in the batch is paired with that later decision. On the first attempt it was paired with nil or an earlier decision. So enacted appears, disappears, or moves to a later timestamp, while created_at and loop.timestamp stay the same.
    • Uploader battery. uploader.battery (and isCharging) are read from UIDevice.current each time the status is built (StoredDosingDecision.swift:139-146).
    • Reservoir. pump.reservoir is dropped once the reservoir reading is more than 15 minutes older than the time the status is built (StoredDosingDecision.swift:90-95).

    The corpus fits B1 [M, same script]. The batch is in chronological order, so on a first attempt the paired loop decision cannot be later than the uploaded one. Yet 1,714 Loop documents have enacted.timestamp later than loop.timestamp, and 200 distinct groups contain such a member. Server insert times (the _id ObjectId time) are spread out within a group: in distinct groups, first to last, 1,300 are within 0 s, 1,237 within 5 s, 27 within 60 s, 245 within 10 min, 223 within 1 h and 46 within 1 day. Along insert order, 2,873 distinct groups change body exactly once. That matches a first attempt followed by retries that all pair with the same stale decision.

    Same-second distinct decisions (B2) [R]. cob, predicted.values, automaticDoseRecommendation and recommendedBolus come only from the uploaded decision (StoredDosingDecision.swift:153-160). A retry cannot change them. So the groups where they differ (for example, recommendedBolus differs in 271 of the 3,078 [M]) are distinct decisions whose dates round to the same second.

    Not settled by the code:

    • how a same-second pair is split across the triggers listed above;
    • why 1,300 distinct groups and 613 identical groups were inserted within the same second. A retry needs a new trigger after a failed POST, so a gap of 0 s points to two passes in quick succession or to a re-send below Loop (URLSession or a proxy). Neither is visible here;
    • whether Loop builds older than these commits behaved the same. The pairing logic dates from NightscoutService 08abe27 (2022-07-18); the release history was not checked against it.

    This qualifies §2.1's Reading. Some distinct groups are separate reports (B2). Many others are retries of one report whose upload-time fields changed (B1). Under Q3(a) with merge, a B1 group would keep only the last attempt's pairing and battery.

    3.2 What a consumer does with "unchanged content, new srvModified"¶

    AndroidAPS NSClientV3 is the only client found that syncs by srvModified. Loop, Trio and xDrip4iOS re-read a time window on created_at/date/dateString. xDrip+ does a full v1 GET gated by an ETag. nightscout-connect, librelink-up, tconnectsync and oref0 read by created_at/date [R].

    How AndroidAPS dev 7e1d537d49 reads (master 598e2eb39c is the same where noted) [R]:

    • It reads GET v3/treatments/history/{from}?limit=500, with from = max(cursor, now − 100 d).
    • The cursor is the response ETag, persisted before the batch is processed (LoadTreatmentsRunner.kt:39-42,56-67; NSAndroidClientImpl.kt:327-334).
    • Each record goes through a SyncNs*Transaction (StoreDataForDbImpl.kt:201-261).

    What happens when the record's content is unchanged:

    • No database write, no upload back.
    • Bolus: SyncNsBolusTransaction.kt:19-31 (checked). Writes only on invalidation or when amount differs.
    • Carbs, temporary target, temp basal, extended bolus, profile switch, running mode: write only on invalidation or a shorter duration.
    • Effective profile switch, bolus calculator result: invalidation only.
    • Therapy event: invalidation, a shorter duration, or a different location/arrow/note.
    • Food, calibration: write only if contentEqualsTo fails.
    • Exception: Announcement. An Announcement whose timestamp is less than 60 min old raises its alarm notification each time it is processed, whether or not the database changed (NsIncomingDataProcessor.kt:208-221@7e1d537d49; :204-211@598e2eb39c). Under Q2(b), an identical re-send of a recent Announcement by any client alarms AndroidAPS users again. No client in §3.1 was found to retry Announcements in particular; careportal posts once.
    • Cost. Every rewrite re-enters the 500-record history pages.

    Can it override a local edit? Only if the server copy differs from the local one. The transactions accept the server's bolus amount, a therapy event's note/location/arrow, a whole food or calibration record, and a shortened duration. A local edit that has not been uploaded yet can therefore be reverted by a re-delivered stale server copy, and the reverted value is then PATCHed back [R; not run].

    An identical re-send by a third client re-delivers the server's current copy. That copy can differ from an AndroidAPS local edit only while the edit is still pending. So Q2(b) does not create this hazard, but each rewrite is one more re-delivery that can trigger it. This was not reproduced.

    Not traced: AndroidAPS's devicestatus, profile and entries runners, and its WebSocket onDataCreateUpdate path.

    3.3 The corpus¶

    [M] Across the 12 sites' 1,589,356 stored documents:

    • srvModified appears on 1 (a profile);
    • srvCreated appears on 0;
    • identifier appears on 505 treatments.

    The corpus was written by v1 clients, and 15.0.8 does not stamp v1 writes. dev fade2299 does stamp them: in repro-results.txt, the dev rows carry srvCreated/srvModified and the 15.0.8 rows do not. How often a record's srvModified advances without a content change cannot be recovered from this corpus. Measuring it would need a dev or 15.0.9 site's v3 history, or MongoDB change history.
