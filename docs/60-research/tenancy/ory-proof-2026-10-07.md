## 0. Results

1. **The gate condition held, and it held in our code.** With U a member of tenant A only, U's
   Kratos session is exchanged for an A token on A's host and refused on B's host; an A token
   presented to B fails as a signature failure. The control on the identical setup — U added to
   B — makes B mint, and the A token still fails on B. Removing one defence at a time turns the
   probe red with the predicted symptom. 23 of 23 predictions held on both Ory release lines
   (§2).
2. **Ory holds none of it.** The pool authenticates U identically at every tenant, by design:
   Hydra's login session carries across tenants' OAuth clients (`skip=true` on the second
   tenant), both tenants' Hydra tokens share one issuer and one signing key, and Hydra's
   introspection reports another tenant's token as `active`. What separates tenants is the
   tenant-first Host resolution, the `tenant_members` row, the per-tenant signing key, and — for a
   Hydra token — a client-id comparison, all in the `nsjwt` exchange (§2, §4.2).
3. **The cookie domain decides what the tenant hosts can see, and neither working setting is
   free** (§4.1). Host-only on the auth host (the default): no tenant host ever receives the
   session, so a browser on a tenant host has no Kratos credential to present at all. Apex
   (`apex.test`): every tenant host receives every user's session; B refused it, but the cookie
   B's host received, replayed to A, minted an A token, and a script on B's origin made A mint by
   cross-origin POST (tenants are same-site, so `SameSite=Lax` does not separate them). A cookie
   domain of the tenant content domain alone breaks login, because the auth host is outside it.
4. **Two read claims were wrong.** "`V0alpha2Api` no longer exists in Kratos 1.x" is an SDK
   rename, not a server break: NRG's own 2022 SDK resolves sessions and identities against
   v1.3.1 and v26.2.0. And Kratos's recorded `request_url` follows the request's
   `X-Forwarded-Host`/`Host`, not `base_url` (§4.4).
5. **NRG's decision pipeline runs** against Kratos 1.x with real browser sessions, including its
   own cross-tenant denial. What breaks is around it: Node 24, npm 11's peer check, the Hydra
   1.x admin path on v2.3.0, and NRG's pairwise OAuth client, which Hydra refuses while access
   tokens are JWTs (§5).
6. **The "1.x / 2.x" lines are not current.** Ory moved to calendar versions; the current
   release is v26.2.0 (2026-03-20). Every isolation result is the same on v26.2.0; only NRG's
   Hydra-path result differs (§2, §5).

Tenant resolution is D10's configured rule with one capture group:
`^([a-z0-9](?:[a-z0-9-]*[a-z0-9])?)\.user-content\.apex\.test(?::\d+)?$`. Tenants `tenant-a` and
`tenant-b` are rows in `tenants`; membership is `tenant_members (tenant_id, subject_id)` with
`subject_id` the Kratos identity id.

**The `nsjwt` stand-in** (`lib/nsjwt.js`, 146 lines including the DDL) is the part D17 says is ours
under any vendor. In order: resolve the tenant from `Host` — unknown slug or a host outside the
rule is a 404 before any credential is read; authenticate with a Kratos session cookie, a Kratos
session token (`X-Session-Token`) or a Hydra access token (`Authorization: Bearer`, introspected,
and required to have been issued to the tenant's own OAuth client); require a `tenant_members` row
for this tenant; mint an HS256 JWT `{sub, tenant, tid, via, iat, exp}` with this tenant's key.
Keys are 32 random bytes per tenant, generated at process start and held in memory (key storage is
`T30-SCHEMA-CRED`'s). `GET /api/nsjwt/verify` checks the signature with the resolved tenant's key,
then the `tenant` claim. `NSJWT_BREAK` removes one defence for the break-it controls:
`skip-membership`, `shared-key`, `no-claim-check`, `skip-client-check`.

**Secrets.** `./lab.sh secrets` writes `.secrets.env` (gitignored): the Postgres password, Kratos
cookie/cipher/default secrets, Hydra system secret and pairwise salt, all from `/dev/urandom`.
Committed files are templates only.

## 2. The gate: `probes/proof.js` — measured

U is a member of tenant A only; V of tenant B only. Both hold a Kratos session from the one pool
(native login, `X-Session-Token`). 23 checks; 23 as predicted on v1.3.1/v2.3.0 and on v26.2.0.

| phase | check | predicted | got |
|---|---|---|---|
| intact | liveness: both tenant hosts answer, U exchanges and verifies on A | 200 ×4 | 200 ×4 |
| intact | the A token's claims | `tenant-a`, U | `tenant-a`, U |
| intact | **U's session on B's host** | 403 `not-a-member` | 403 `not-a-member` |
| intact | **the A token presented to B** | 401 `signature` | 401 `signature` |
| intact | V exchanges on B in the same run (B is alive, not just refusing) | 200 | 200 |
| intact | a B token presented to A | 401 `signature` | 401 `signature` |
| intact | unknown slug `tenant-zz`, and `tenant-a.apex.test` (outside the rule) | 404, 404, 0 credential examinations | 404, 404, 0 |
| intact | on A: no credential; junk session token | 401, 401 | 401, 401 |
| **control** | U added to B: the same session on B mints a B token that verifies on B | 200, 200, claim `tenant-b` | 200, 200, `tenant-b` |
| **control** | U a member of B: the A token on B | 401 `signature` | 401 `signature` |
| **control** | U removed from B again | 403 | 403 |
| revocation | Kratos revokes all U's sessions (admin `DELETE /admin/identities/{id}/sessions`); U exchanges on A | 401 | 401 |
| revocation | an A token minted **before** the revocation, verified on A | 200 (no link to Kratos) | 200 |
| break `skip-membership` | liveness; **U's session on B** | 200, a B token for U | 200, `tenant-b`, U |
| break `skip-membership` | that token verified on B | 200 | 200 |
| break `no-claim-check` | per-tenant keys intact: A token on B | 401 `signature` | 401 `signature` |
| break `shared-key` | one deployment key, claim check on: A token on B | 401 `tenant-claim` | 401 `tenant-claim` |
| break `shared-key,no-claim-check` | **A token on B** | 200, claim `tenant-a` | 200, `tenant-a` |

Read together: the refusal on B tracks the membership row (control and restore), the
signature failure tracks the key and not membership (control), the per-tenant key alone is
sufficient (`no-claim-check` stays green), and the claim check is a second layer that catches a
shared key. Without the membership check the pool's session becomes a working B credential.

The revocation rows are a property of the exchange, not of Ory: a minted Nightscout token lives
until its own `exp` (3600 s in the lab) whatever happens to the Kratos session.

## 4. The attack surfaces that come from the pool

### 4.1 Session cookie scope — `probes/cookies.js`, measured in Chrome

The browser logs U in through a Kratos browser flow on `auth.apex.test` with `return_to` on
tenant A, then loads `/api/echo` on each tenant host, which reports the cookie names it received
and a 16-hex-digit SHA-256 prefix of any session cookie (never the value). Kratos was recreated
between variants with a compose overlay (`variants/cookie-*.yaml`).

| variant | session cookie stored as | reaches A | reaches B | result |
|---|---|---|---|---|
| host-only (default) | domain `auth.apex.test`, HttpOnly, SameSite=Lax | no | no | the cookie path cannot work: A answers `no-credential`. Control in the same run: the same session handed to A explicitly mints an A token |
| `apex.test` | domain `.apex.test`, HttpOnly, SameSite=Lax | yes | yes | A mints; **B refuses (403 `not-a-member`)**; control — U added to B, the identical browser state mints a B token |
| `user-content.apex.test` | — none stored | no | no | the browser rejects the CSRF cookie Kratos sets for a domain the auth host is not inside; the flow fails `security_csrf_violation`. Control: native login and the A exchange still succeed |

Under the apex variant, two more measured results:

- **Replay.** The session cookie that arrived at B's host (same digest as the browser's), sent by a
  non-browser client to A's exchange, mints an A token. Any process that sees B's request headers
  — B's server, its logs, a proxy in front of it — holds a credential that works on every tenant
  U belongs to.
- **Cross-origin.** A script on B's origin `fetch`es A's exchange with `credentials: 'include'`:
  the session cookie is sent, A's server mints a token (the event log shows `origin` =
  B's origin), and the browser withholds the response from the script (no CORS). The two hosts are
  the same site (`apex.test`; `.test` is not on the Public Suffix List), so `SameSite=Lax` does not
  separate them. Whether listing the content domain on the Public Suffix List would change this is
  **read**, not measured.

**Per-tenant proxy.** Kratos proxied under `tenant-a…/.ory/` answers, but the flow's `ui.action`
names `auth.apex.test` (the single `serve.public.base_url`) while the CSRF cookie it set is
host-only on tenant A — so the form posts to a host that does not hold the CSRF cookie. Measured
on both release lines. Kratos is reachable at one browser origin per deployment.

The three cookie variants are the only shapes available: a cookie domain must contain the auth
host, so it is either host-only on the auth host or a parent of both the auth host and every
tenant.

### 4.2 Hydra, one client per tenant — `probes/hydra.js`, measured

Clients `tenant-a` and `tenant-b`, each with its own `redirect_uris` and `audience` (its tenant
origin), `client_secret_post`. **U is a member of both tenants**, so membership cannot be what
stops A's token on B; the client binding is the only variable. 18 checks, 18 as predicted on both
release lines.

| check | result |
|---|---|
| A's client, A's redirect and audience | handed to the login app |
| A's client asking to redirect to B's callback | `invalid_request`; the redirect goes to Hydra's own host, not B's |
| A's client asking for B's audience | `invalid_request` |
| authorization-code flows for A then B in one browser | both complete through the Kratos login |
| B's login request after logging in for A | **`skip=true`** — Hydra's login session is cohort-wide |
| B's consent request | `skip=false`; control: a second A flow sees its remembered consent (`skip=true`) |
| A's and B's access tokens | same `iss`, same `kid`; A's verifies against the one JWKS |
| A's token `aud` | A's origin only |
| A's token at A's exchange | 200 |
| **A's token at B's exchange** | 401 `hydra-token-other-client`; B's own token on B: 200 |
| break `skip-client-check` | **A's token mints a B Nightscout token** (200, `tenant-b`); with U removed from B, the membership check still refuses (403) |
| NRG's client shape (`subject_type: pairwise`) | refused: `invalid_client_metadata` |

The pairwise refusal has a stated cause in Hydra's own startup warning (**read**): "The pairwise
subject identifier algorithm is not supported by the JWT OAuth 2.0 Access Token Strategy and is
thus being disabled." With opaque access tokens (`variants/hydra-opaque.yaml`,
`probes/hydra-pairwise.js`, **measured**, 3 of 3): pairwise clients are accepted; each tenant's ID
token carries a different `sub` and neither is the Kratos identity id; introspection returns the
Kratos identity id for both; a public client's ID token `sub` is the Kratos id.

This measures §3.2 of the research document: with Hydra issuing the token, a tenant can tell its
own token from another tenant's only by comparing `client_id` or `aud` — a claim check, which is
what D14 set out to replace with a signature failure.

### 4.3 `return_to` allow-list — `probes/return-to.js`, measured

`allowed_return_urls` is `http://auth.apex.test:44480/` and `http://*.user-content.apex.test:44480/`.
Each candidate offered to the login, registration and recovery browser flows; the three flows
agreed on every candidate. 14 of 14 as predicted on both release lines.

| `return_to` | outcome |
|---|---|
| own tenant (first and last, the liveness pair) | allowed |
| sibling tenant `tenant-b` | allowed |
| unregistered slug `tenant-zz` | allowed |
| two labels deep, `x.tenant-a.user-content…` | allowed |
| bare suffix `user-content.apex.test` | refused |
| other port, `https` scheme | refused |
| `evil.test`; `tenant-a….evil.test`; `tenant-a…@evil.test`; `evil.test/http://tenant-a…`; `//evil.test`; `javascript:` | refused |

The list is one list for the deployment. Kratos does not know which tenant a flow started from, so
it cannot restrict a flow's `return_to` to that tenant; within the cohort, `return_to` is an open
redirect by construction, and the wildcard reaches slugs that are not tenants and hosts the D10
rule would not resolve. Off-cohort redirection is refused by configuration.

### 4.4 Recovery and verification email — `probes/recovery.js`, measured

U (member of A only) has recovery started three ways: on the auth host; through tenant B's
`/.ory/` proxy path; and, in the template variant, with `transient_payload: {tenant: "tenant-b"}`.
Emails are read from the mail catcher.

| variant | result |
|---|---|
| built-in `recovery_code` template | each email arrives with a code; **names no tenant and no host**, whichever host started the flow |
| template rendering `.TransientPayload.tenant` (`variants/recovery-template.yaml`) | the email names the tenant **the caller sent** — `tenant-b`, where U is not a member |
| template rendering `.RequestURL` | the email for the flow started through B's proxy names B's host |
| flow `request_url` | follows the request: B's host via the proxy; `evil.test` when `X-Forwarded-Host: evil.test` is sent directly to Kratos public |

The prediction for `request_url` was that it would name `base_url`; the first run measured
otherwise, and the probe now records what Kratos does. The verification email uses the same
courier and template mechanism (**read**; only recovery was run).

So "an email naming the wrong tenant" cannot happen with the built-in templates because they name
none, and can be made to happen by anyone the moment a template names one, because every input a
template could take a tenant from is chosen by whoever starts the flow.

single-tenant operator. D1 keeps that deployment first-class and D17 row 1 keeps devices and
uploaders on native per-tenant credentials permanently, so the Kratos/Hydra stack, its two
databases and its migration chains exist only on the hosted path, beside a native credential path
that does not go away (§3.3 of the research document).

## 7. What the identity half of `T30-SCHEMA-CONFIG` would need, from these measurements

- **`tenant_members.subject_id` holds the Kratos identity id** (a UUID), with no foreign key — the
  identity lives in another database. Measured: it is what Kratos `whoami`, Hydra introspection
  and a public client's ID token all return. A pairwise client's ID token does not carry it; if
  pairwise subjects are ever used, the exchange must take the subject from introspection, not the
  ID token.
- **No credential, recovery or MFA columns** under row 2 — Kratos holds them. Recovery email text is
  deployment-wide (§4.4); a per-tenant display name or role is ours (`tenant_members`), not a
  Kratos trait, because one identity schema serves the pool.
- **A per-tenant OAuth client id** (`tenants.oauth_client_id` in the lab) if Hydra is in the path:
  the client-id comparison is the only thing that stops A's Hydra token at B (§4.2). Row 3 defers
  Hydra; §4.1 shows what that leaves for a browser on a tenant host — no credential under the
  host-only cookie, every user's session under the apex cookie. Which of those the hosted design
  takes decides whether this column exists.
- **The minted token outlives the Kratos session** (§2). If revocation is to reach Nightscout
  tokens, the exchange needs the Kratos session id in the token and a check against it, or a short
  `exp`; neither is in the lab.
- **The per-tenant signing key** is `T30-SCHEMA-CRED`'s, unchanged by this: the lab confirms it is
  sufficient on its own for the token-reuse vector (§2, `no-claim-check`).

## 8. What this does not establish

- **The compliance question** of a third-party processor adjacent to health data is untouched;
  self-hosting Ory does not dispose of it.
- **TLS and `Secure` cookies.** The lab runs `--dev` over http; cookie domain scoping does not
  depend on `Secure`, but nothing here was measured over https.
- **Public Suffix List** treatment of a content domain, and how it would change §4.1's same-site
  result, is read, not measured.
- **Verification email**, MFA, passkeys, account linking and Kratos's `oauth2_provider` integration
  were not run.
- **Load.** Idle figures only.
- **Nocturne** was not run.
