    Technical control loops: controller, hub and spoke, delegation¶

    Living document, last changed 2026-10-18 at 7e6fab2b5.

    Contributor-facing. Snapshot — describes the source revisions in §0, read 2026-10-17. Every behavioural claim cites source or an existing repository document. Claims are read-derived (from reading code, not from running it) unless marked otherwise; anything inferred beyond what the code says is marked inferred. Nothing here was run on a device or simulator.

    This page supplies content for three STPA-style control-structure drawings. Each family has a drawing input (YAML, same schema as tools/structure-diagrams/inputs/), a short narrative of what the loop controls and how the controller learns the result, and unsafe-control-action (UCA) prompts. The prompts are questions for analysis, not findings.

    Family Drawing input Zoom levels proposed (not drawn)
    1. Controller loop on the phone 3-controller.yaml L1a inside the controller app
    2. Hub-and-spoke sync loop 3-hub-sync.yaml L2a per-collection view of the hub
    3. Delegation loop 3-delegation.yaml L3a per-controller validation pipeline

    The three drawings nest: L1's hub node opens into L2, L2's app node opens into L1, and L3 reuses the hub and controller boxes with the command path added.

    Relabelled 2026-10-17: L1, L2 and L3 are now the drawings 3·controller, 3·hub-sync and 3·delegation, published in Control structures, drawn; their inputs moved to tools/structure-diagrams/inputs/. The zoom levels L1a–L3a below remain proposals; the drawings no longer carry markers for them.

    1. The controller loop on the phone¶

    1.1 Drawing¶

    3-controller.yaml: six nodes. Person (supervisor) at the top; the controller app; pump (actuator) and CGM (sensor); the body (controlled process). A pointer node for the Nightscout hub carries the app's outbound record of applied state and opens into L2.

    Zoom L1a (proposed, not drawn). The controller box opens into: algorithm; CGM manager; pump manager with its command queue; dose, glucose and carb stores; uploader. That is where the differences in the table below live, and drawing them on L1 would take it past ten nodes.

    1.2 What the loop controls and how the controller learns the result¶

    The controlled variable is glucose; the manipulated variable is insulin delivery above or below the scheduled basal. All three controllers run a cycle of roughly five minutes, triggered by new CGM data or a pump heartbeat; read glucose, pump state and recent insulin and carbohydrate records; predict glucose; and command a temporary basal rate with a bounded duration, plus (when enabled) a small automatic bolus. The pump's acceptance or failure of each command is the immediate feedback; the CGM reading some minutes later is the feedback on the process.

    The bounded temp-basal duration is the design property that matters for lost communication: the loop-set temp basal is 30 minutes by default in all three (Loop LoopKit/LoopKit/LoopAlgorithm/DoseMath.swift:404,477; Trio Trio/Sources/APS/OpenAPSSwift/DetermineBasal/DosingEngine.swift:402,431,463; AAPS plugins/aps/.../openAPSSMB/DetermineBasalSMB.kt:200-265). Inferred from temp-basal semantics, not traced per pump driver: if the controller stops commanding, the pump returns to its scheduled basal when the running temp basal ends. That fallback can be higher or lower than what the controller would have chosen.

    1.4 Unsafe control action prompts (L1)¶

    Control action: temp basal / automatic bolus from controller to pump.

    • Not provided. What does each controller do when glucose is stale and a high temp basal is running — enact a neutral rate, or leave the high temp to run out? (Trio's two stale-glucose paths in §1.3 are the case to check first.) What does the person see, and when?
    • Not provided. When the phone app is suspended by the OS and no cycle runs, which alarm tells the person, after how long, and is that alarm on the phone that has also stopped?
    • Provided when unsafe. Can an automatic bolus be enacted when the pump's own history has not been read since the last manual bolus on the pump body? Which controllers refresh pump data before every cycle?
    • Provided when unsafe. Can a CGM reading that is fresh but wrong (compression low, calibration artefact, a follower CGM fed from the hub) drive dosing? Which noise or "unchanged data" checks apply in each controller?
    • Wrong timing or order. If the temp basal succeeds and the bolus fails, or the reverse, what state does the controller believe the pump is in? (All three order temp basal before bolus; is the reverse failure handled the same way?)
    • Wrong timing. Can a recommendation computed before a slow pump exchange be enacted after newer glucose arrives? (Loop: 5-minute expiry; AAPS: 1-minute SMB deliverAt; Trio: 30-minute determination lookup window in enactDetermination.)
    • Stopped too soon / applied too long. When the controller stops (crash, phone off), the last temp basal runs up to 30 minutes and then scheduled basal resumes. For which situations is the scheduled basal itself the unsafe action?
    • Supervisor. When the person switches to open loop or a constrained mode, does every display (phone, watch, followers via L2) show that automation is reduced, or only the phone?

    2. The hub-and-spoke sync loop¶

    2.1 Drawing¶

    3-hub-sync.yaml: seven nodes. The hub in the middle; uploaders and the controller below it (writers); followers and the web UI above it (readers and, for the web UI, writers of requested state); reports to the side. Requested state and applied state are separate edges: requests flow down to the controller as downloaded entities; applied state flows up as devicestatus and delivered records.

    Zoom L2a (proposed, not drawn). The hub box opens into its collections (entries, treatments, devicestatus, profile, settings, food, activity) with the API generation each spoke uses. Drawing every spoke separately would need about fifteen nodes, so followers are one group box here.

    2.2 What the loop controls and how each side learns the result¶

    The hub does not control insulin. It is the shared record that lets people and software away from the phone observe the L1 loop, and, through a few opt-in paths, lets requests reach the controller. Under decision D18 the hub is responsible for observability and the controller for sending data accurately and reconciling (landscape, preamble). No hub composes intents (landscape §7).

    2.3 Unsafe control action prompts (L2)¶

    Control actions: a requested entity downloaded by the controller; a follower's display or alarm acted on by a caregiver.

    • Not provided. If the controller cannot upload for an hour, what does each follower show, and does any follower alarm on missing devicestatus as opposed to missing glucose?
    • Not provided. A caregiver enters a temp target in careportal for a controller that has downloads off. Who tells the caregiver it was not applied?
    • Provided when unsafe. Carbs entered on the hub by one client and downloaded by Trio or AAPS change carbs-on-board and therefore dosing. What prevents a duplicate entry (entered on the phone and on the hub) from being counted twice?
    • Provided when unsafe. When a controller uses hub entries as its CGM source, the uploader, the hub and the controller form a loop through the network. What bounds the age of that reading at the moment of dosing?
    • Wrong timing. A temp target written with a past created_at, or arriving out of order: which one does each controller enable? (Trio enables the newest of a batch, FetchTreatmentsManager.swift:47-64.)
    • Stopped too soon / applied too long. A cancel encoded as a zero-duration record or a shortened duration (landscape §4): which spokes read the cancel and which keep showing the target until its original end? (Measured for the two hubs, landscape §5.)
    • Display. Two followers reading the same site show different "active override" states (units and supersession differences, landscape §5). Which one does a caregiver act on?

    3. The delegation loop¶

    3.1 Drawing¶

    3-delegation.yaml: seven nodes. The person or primary caregiver who grants the credential; the caregiver or automated agent who sends; the remote app; the hub; the push or SMS relay; the controller; the pump. Two edges are status: proposed: a command record with an id at the hub, and a correlated acknowledgement from the controller. Those are the parts that are missing on most paths today (§3.4).

    Zoom L3a (proposed, not drawn). The controller box opens into each controller's validation pipeline (enabled check → authentication → freshness → replay check → amount limits → enact → reply). The rows of the table in §3.3 are that drawing's content.

    3.2 What the loop controls and how the sender learns the result¶

    The sender asks the controller to change its inputs: deliver a bolus, record carbs, set a temp target or override, change mode. The controller, not the sender, owns the pump, so every path ends in the controller's own validation and enactment. The sender learns the result through one of four channels: a direct reply (APNs or SMS) on paths where the sender supplied a return address; the resulting record appearing on the hub; a free-text failure Note on the hub; or, dev-only in AAPS, a signed acknowledgement document with a correlation id. No path gives the hub a request record it could show (landscape §6).

    A "smart agent" acting on someone's behalf has no path of its own. It would hold one of the credentials below and be indistinguishable from the caregiver who gave it that credential. The delegation grants with scopes, constraints, expiry and revocation in the authority model are recorded there as not implemented ("Current State (Gaps)").

    3.4 What is missing¶

    1. A request record and correlated acknowledgement on the hub. Only F has one, and F is dev-only and AAPS-only. On A–E the hub sees success only as the resulting entity and failure only as free text (landscape §6). The two status: proposed edges in L3 are this gap.
    2. Replies on hub-relayed paths. Path A cannot reply to the sender, because the hub does not add a return address. A careportal user learns of failure only by reading Note treatments.
    3. Accepted versus delivered. Loop's and Trio's success messages are sent after the pump accepts the command (read-derived). Only AAPS dev has a separate late delivery-failure ack.
    4. Authorisation granularity. The hub's relay permission sits in admin by default, so the person who can send a remote bolus can also do everything else on the site. No per-caregiver identity reaches the controller: enteredBy is free text and remote bolus and carbs lose the initiator (landscape §3, P5; authority model).
    5. Unequal protection across command types. In Loop, overrides need no TOTP (path A), yet an override scales basal, ISF and carb ratio (landscape §3.1). Entity downloads (path D) carry no expiry and no authentication beyond hub write access.
    6. No agent model. No scopes, rate limits, time windows, expiry or revocation per agent. The authority model's grants are a proposal. Revoking one caregiver today means rotating the shared credential for everyone (inferred from the credentials being shared secrets).

    3.5 Unsafe control action prompts (L3)¶

    Control actions: remote bolus, remote carbs, remote override or temp target.

    • Not provided. A remote bolus fails validation on a hub-relayed path. How long until the caregiver knows, and through what? Could they assume success and give carbs?
    • Not provided. A caregiver cancels an override remotely while the phone is offline. When does the controller learn of it, and what does the caregiver see in the meantime?
    • Provided when unsafe. The same bolus arrives twice: APNs redelivery after a force-quit (Loop dedupes by id), a resend inside Trio's ±600 s window, or a caregiver retrying after no reply. Which guard stops the second one in each path?
    • Provided when unsafe. A caregiver and the person both bolus for the same meal within minutes. Which paths see the other's bolus before validating (Trio's 20 % rule, AAPS SMS distance)? Which do not?
    • Provided when unsafe. An agent holding the same credential as a caregiver sends a command the person would not have authorised. What, other than the shared secret, distinguishes them at the controller?
    • Wrong timing. A command delayed in APNs or SMS arrives near the end of its validity window, after glucose has changed. Is the dose re-evaluated at arrival (AAPS dev prepare/commit), or only checked against static limits?
    • Wrong timing. Remote carbs with a past start time: does each controller back-date absorption, and does that produce an immediate correction?
    • Stopped too soon / applied too long. A remote override with duration 0 means indefinite in Loop (ServicesManager.swift:289-291). Who ends it, and does every follower show that it is still running?
