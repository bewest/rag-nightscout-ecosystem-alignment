# T0.2 and T0.3 — what the runtime cache's defensive clone actually costs, and how much of it is safe to take

**Date**: 2026-09-15 · **Branch**: `bf/cache` (cgm-remote-monitor), based on `origin/dev` `a8888f0d`
**Register**: [BF-06, BF-07](../30-design/nightscout-backfix-register.md) ·
**Plan**: [T0.2, T0.3](../30-design/nightscout-multitenancy-execution-plan-2026-09-14.md) Phase 0
**Commits**: `ddcdb1a8` (T0.2), `4f86bab1` (T0.3)

---

## 1. Summary

| | before | after | gate |
|---|---|---|---|
| **T0.2** untyped `/api/v1/entries?count=10` | 0.837 ms p50 | 0.025 ms p50 | **within 2× of typed: PASS (0.7×)** |
| **T0.3** the three cache calls one load cycle makes | 3.747 ms p50 | 2.657 ms p50 | **clone cost < 1 ms: NOT MET — 2.6 ms remains, see §5** |

T0.2 landed whole. **T0.3 landed at about a third of its measured prize, on purpose**: two of
the three load-cycle call sites provably never write to what they read, and one of them does,
repeatedly, to documents that then live in `ddata` for the rest of the process. That one keeps
its copies. §5 says exactly what would have to be proved to take the rest, and why this change
declines to claim it.

## 2. Baseline, re-measured

Node **v24.15.0** (the repo's `.nvmrc` says 22; nothing in these paths is version-sensitive,
but the absolute numbers are that runtime's), npm 11.12.1, Linux 6.18.7, `mongod` on 27033.
Harness: `tools/mt-bench/apitier.js`, arms `read` and `cycle`, run as
`NS_ROOT=<worktree> node --expose-gc tools/mt-bench/apitier.js <arm>`.

**The harness changed before anything was measured.** Both arms used to transcribe the modules
they price, which means a fix in the repository would not have moved them — the "done" command
would have kept reporting the defect after it was gone. They now build the real
`lib/server/cache.js` and read `lib/api/entries/index.js` and `lib/data/dataloader.js` to decide
which shape of each call site is actually in the tree, and throw if they cannot recognise one.

Against that harness, the figures quoted in the brief reproduce almost exactly:

| | brief | re-measured |
|---|---|---|
| untyped `?count=10` | 0.83 ms | **0.837 ms** |
| typed `?count=10` | 0.02 ms | **0.020 ms** |
| ratio | 42× | **42.0×** |
| clone of all three retained arrays, per cycle | 4.08 ms | **4.008 ms** |

Fixture: 576 entries (183 KB JSON), 600 treatments of which **361** survive the 60-hour
retention filter, 576 device statuses with a 72-point prediction array each. The treatments
figure differs from the earlier pass because the arm now runs the real `mergeCacheArrays`, which
applies retention; the old transcription retained all 600.

**One correction to the brief's framing.** 4.008 ms is the cost of cloning all three retained
arrays. What the cycle *calls* is `insertData`, which is merge **plus** clone, and that measured
**3.747 ms** — merging is cheap and the two numbers are close, but they are not the same number,
and after the fix they diverge sharply. Everything below quotes the call, not the clone.

## 3. T0.2 — slice first, then clone the slice

`lib/api/entries/index.js` `query_models` has two branches. The typed one filters
`ctx.cache.entries` by reference and clones only the documents it returns. The untyped one called
`ctx.cache.getData('entries')`, which deep-clones the whole retained 48-hour array, then sliced
ten documents out of the clone and cloned those again.

The fix is one identifier: the untyped branch now reads `ctx.cache.getDataRef('entries')`, a new
accessor that hands back **a fresh array of the cache's own documents**. The response is still
built by `JSON.parse(JSON.stringify(slice))`, so the documents handed to the caller are still
copies; the array is a shallow copy, so a reader cannot reorder the cache either.

| count | untyped before | untyped after | typed | ratio after |
|---|---|---|---|---|
| 1 | 0.836 | **0.002** | 0.007 | 0.3× |
| 10 | 0.837 | **0.025** | 0.035 | **0.7×** |
| 144 | 1.016 | 0.195 | 0.199 | 1.0× |
| 576 | 1.650 | 0.833 | 0.851 | 1.0× |

(ms p50. At `count=576` both branches converge on the cost of cloning the response, which is the
work the endpoint exists to do.)

**Byte-identity is asserted, not assumed.** Cloning first cannot change what comes back, because
the second round-trip is idempotent over the first — but that is an argument, and the argument is
checked in three places: the bench refuses to report unless both shapes produce identical JSON at
every count it prints; a unit test compares the two reads including a document that entered the
cache from the `data-update` bus with an `ObjectId` `_id`; and an integration test
(`tests/api.entries.test.js`) makes the same HTTP request twice, once with the cheap read and
once with the old cloning read patched back in, and compares the response bodies.

## 4. T0.3 — the load cycle, one call site at a time

`insertData` ends with `return data.getData(datatype)`. Whether that clone is load-bearing is a
different question at each of the three call sites, and the answer is different at each.

### 4.1 `dataloader.js:203` — the trap, resolved

`if (!element.mills) element.mills = element.date` **writes to the element**, which is why a
shallow copy would change behaviour. Resolution: **the write is dead.** All three branches below
it take `mills` from `element.date`, never from `element.mills`; `currentData` is a local that is
discarded when the loop ends; nothing else reads it. Under the clone regime it wrote to a
throwaway copy and was never read back, so removing it is a no-op **today** — and leaving it in
place while making the read by-reference would have written `mills` into every cached entry
document that lacks one. It is removed.

Its history supports the reading: it was added in #5947 (`80190059`) when the loop still iterated
the raw query `results`, and `f878ce11` later re-pointed the loop at `currentData` without
revisiting it.

**The semantics are pinned either way.** `tests/data.cache-clone.test.js` seeds a cached entry
with no `mills`, runs a real load cycle through the real dataloader, and asserts the cached
documents come back byte-for-byte as they went in. That test fails if the write returns.

### 4.2 entries and treatments — by reference

- **entries** reads each document and builds a new one from it. With the dead write gone it
  performs no writes at all. It reverses the array it is given, which is why the accessor returns
  a fresh array rather than the cache's own.
- **treatments** hands the array straight to `ddata.idMergePreferNew`, which **deep-clones what
  it is given** and never writes to it. The clone inside `insertData` was the first of two
  identical clones of the same documents in the same cycle.

Both now use `insertDataRef` / `getDataRef`.

### 4.3 devicestatus — keeps its copies

`eachStatus` rewrites `uploaderBattery` into `uploader` and `delete`s the original field on every
document it is handed; `mergeProcessSort` then writes `_id` and `mills` on top of that; and the
documents that come out are kept in `ddata.devicestatus` for the life of the process, where the
plugin tier and the socket payload both reach them. Reading that window by reference would strip
a field out of the cache — and out of the next API response served from it. **This site keeps
`insertData`.**

### 4.4 Why the by-reference accessors are sound

Not because the callers are careful — because **the cache already clones on the way in**.
`mergeCacheArrays` passes incoming documents to `ddata.idMergePreferNew`, whose first act is
`JSON.parse(JSON.stringify(newData))`. So the cache never retains a document still shared with
the writer that emitted it, and never an `ObjectId` or a `Date`: what it holds is already the
normalised form `getData` would hand out. The clone belongs there, where it is bounded by the
batch, rather than on the way out, where it is bounded by the retention period.

**This was found by breaking something.** The first version of this change added its own
normalising clone to the insert path, on the theory that the `data-update` bus delivers raw
writer objects — `lib/api3/storage/mongoCachedCollection`, `lib/server/entries.js`,
`lib/server/websocket.js` and five others all emit into it. Removing that clone was then supposed
to turn the normalisation tests red. It did not. `idMergePreferNew` was already doing the work,
the added clone was pure cost, and it came out again. The tests that failed to fail are the
reason the final diff is smaller than the first one.

### 4.5 Result

| datatype | n | full clone | before | after |
|---|---|---|---|---|
| entries | 579 | 0.958 | `insertData` 0.845 | `insertDataRef` **0.035** |
| treatments | 361 | 0.753 | `insertData` 0.397 | `insertDataRef` **0.017** |
| devicestatus | 579 | 2.580 | `insertData` 2.506 | `insertData` **2.605** |
| **per cycle** | | 4.0–4.3 | **3.747** | **2.657** |

Against the 2.19 ms post-#8733 cycle the plan projects, the cache's share falls from 63 % to
55 %. It is still the largest single item in the cycle.

## 5. The gate that is not met, and what it would take

`T0.3 done` asks for **clone cost < 1 ms**. It is 2.66 ms. **98 % of what remains is
devicestatus**, and taking it means establishing that nothing between `mergeProcessSort` and the
end of the process writes to a device status document or to anything nested inside one. That is a
claim about `lib/data/ddata.js`, eighteen alarm plugins, `openaps`, `loop`, `pump`, `xdripjs`, the
`dataWithRecentStatuses` projection and the socket payload. A grep over `lib/plugins/*.js` found
no in-place write to a `devicestatus` element — every consumer reads and builds new objects — but
**a grep is not the proof this needs**, and the failure mode if the grep is wrong is a field
silently disappearing from a cached document and from every API response served out of the cache
afterwards.

So: the measurement sized the prize at 4 ms and this change took 1.1 ms of it. Two cheaper
observations for whoever picks up the rest:

1. **Retention halves it for the default operator.** The 2.6 ms figure is at
   `DEVICESTATUS_DAYS=2` (579 documents). The default is one day; at ~288 documents the same
   clone is ~1.25 ms. The bench pins `days: 2` deliberately — it is the worse of the two — but
   the fleet is mostly on the cheaper one.
2. **The prize is shaped by the prediction arrays.** A device status document in the fixture
   carries a 72-point `predicted.values` array, and that is what makes devicestatus three times
   the cost of entries at the same document count. A projection that dropped prediction arrays
   from the *cached* copy would take most of the 2.6 ms — but the cache is also what
   `mongoCachedCollection` serves API v3 reads from, so a lossy cache is a different and larger
   decision than this task.

## 6. Non-vacuity

Every check below was confirmed to fail when the behaviour it describes is broken. Breaks were
applied to a clean tree and reverted from a file snapshot, not with `git checkout` — which is how
two earlier break runs in this session silently reverted the fix and produced a green result that
meant nothing (see §8).

| break | check that went red |
|---|---|
| put `if (!element.mills) element.mills = element.date` back in the entries loop | `leaves the cached entries exactly as it found them` |
| `getDataRef` returns the cache's own array instead of a copy | `hands back an array that is not the cache's` **and** `leaves the cached entries…` (the loader's `reverse()` reaches the cache) |
| `getDataRef` deep-clones like `getData` | `hands back the cache's own documents` |
| devicestatus switched to `insertDataRef` | `does not let the devicestatus rewrite reach the cache` |
| `idMergePreferNew` stops cloning `newData` | `stores an ObjectId _id and a Date the same way getData would return them` **and** `stops the writer and the cache from sharing a document` |
| the API stops cloning the slice it returns | `does not write to the cached documents while serving a read` (integration) |

One break **did not** fail anything and is recorded as such: removing the normalising clone added
in the first draft of T0.3 changed no test, because it was redundant — §4.4.

## 8. `cob.setProperties` — structural read only, not measured

The brief asked whether `cob.setProperties` is quadratic in treatments, if profiling happened to
touch it. **It did not** — nothing here runs the plugin tier, and no number below is measured.

Reading it: `cob.setProperties` calls `cob.cobTotal` once per sandbox, which calls
`cob.fromTreatments`, which iterates every treatment and, **for each treatment carrying carbs**,
calls `iob.calcTotal(treatments, …)` **twice** (`lib/plugins/cob.js:143-144`). `iob.calcTotal`
delegates to `iob.fromTreatments`, which iterates the whole treatments array
(`lib/plugins/iob.js:150`). So the shape is **O(carb-treatments × treatments)** per cycle, and
since carb entries are a roughly fixed fraction of treatments, that is quadratic in treatments.
That is consistent with the correction in the brief — 27.5 ms for the alarm set, ~74 % of it
`cob.setProperties` — but it is an argument from the source, not a measurement, and it should be
measured before anyone acts on it.

## 9. Honest limits

- **The absolute numbers are event-loop CPU on one machine, one runtime, one synthetic tenant.**
  They rank options; they are not capacity. The ordering (devicestatus ≫ entries > treatments)
  is the durable part.
- **The fixture is synthetic.** 576/600/576 documents with plausible shapes, not a replayed
  site. Device status size in particular is dominated by one design choice — the 72-point
  prediction array — and a site running xDrip with no loop would see a much smaller number.
- **The `read` and `cycle` arms still transcribe the call-site expressions**, even though they
  now drive the real cache module and read the real sources to pick which expression is live.
  A change to those call sites that the drift guards do not recognise makes the arm throw rather
  than lie, which is the best property available short of invoking the middleware itself.
- **`?count=10` is measured at 576 cached documents.** The 42× was never a constant; it is
  `retained ÷ count`, so it is worse for a follower app polling for one document and it vanishes
  for a client asking for the whole window.
- **T0.3's remaining 2.6 ms is not a mystery, it is a decision.** §5.
- **The by-reference accessors make a future mistake cheaper to make.** A new caller of
  `getDataRef` that writes to what it reads corrupts the cache silently. The contract is in a
  comment on the accessor and in two tests that assert the sharing is real; that is mitigation,
  not prevention.
- **T0.1 (#8733) is not in this branch.** The cycle totals here are this branch's, and the
  "share of the cycle" figures are computed against the plan's 2.19 ms projection for a
  post-#8733 cycle, which this work did not verify.
- **Nothing here was run against a real Nightscout instance under load.** Both suites pass and
  the response bodies are asserted identical over HTTP, but no operator traffic was replayed.
