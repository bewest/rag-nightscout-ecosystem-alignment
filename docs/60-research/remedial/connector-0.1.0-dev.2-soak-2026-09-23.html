    nightscout-connect 0.1.0-dev.2 — Nightscout-to-Nightscout lab soak¶

    Record

    Record as of 2026-09-23. A point-in-time document; it is not kept up to date.

    Snapshot: measured 2026-09-23, 03:21–07:45 UTC. Nightscout was origin/dev 74fc6619 (reports 15.0.9) and tag 15.0.8 (92d08342). The connector was 0.1.0-dev.2 (= fbd4e55, connector dev), with controls on 0.1.0-dev.1 (= 1946beb), 234d47c (the pin in 74fc6619) and 0.0.13 (the pin in 15.0.8). MongoDB 7.0.43, Node 22.22.0 in the images. Contributor-facing.

    Historical: the evidence for tagging nightscout-connect v0.1.0 and pinning it into 15.0.9. Both have happened: 0.1.0 was released 2026-09-24 and dev pins it exactly (#8762). The two defects found in §5.1 and §5.2 are registered as BF-97 and BF-98, and their fixes (connector #79) are in 0.1.0 (profile duplicate stall). Current defect facts live in the backfix register, and item state in queue/work-queue.yaml.

    The exit criterion was a seeded Nightscout source in the lab, with a second lab Nightscout syncing from it. That ran for 4 h 23 min, with sinks for 4 h 05 min–4 h 23 min and eight controls alongside for 3 h 48 min–4 h 22 min. Every figure below is reproduced (run in the lab) unless marked read-derived. All data was synthetic, generated by the lab writer. No real person's data was used.

    1. What was run¶
    Source S Nightscout 74fc6619, own MongoDB, AUTH_DEFAULT_ROLES=denied. Seeded through its API with 60 h of synthetic history: 730 entries (sgv every 5 min, plus mbg), 280 treatments (Carb Correction, Correction Bolus, Temp Basal), 240 devicestatus and 1 profile. After seeding, a writer added sgv every 5 min, devicestatus every 15 min and treatments on a fixed schedule (91 live records). The connector's Nightscout source does not read food, so none was seeded.
    Proxy A pass-through proxy between every sink and S. It logs method, path (the token segment is redacted) and status per request, so the lab can count requests even while S is down. When S is unreachable it resets the client socket.
    K1 Nightscout 74fc6619 with nightscout-connect pinned exactly to 0.1.0-dev.2 (the package.json change plus a regenerated lockfile, as P0-PIN would do). Own MongoDB. Configured with CONNECT_SOURCE_ENDPOINT=<S>/?token=<access token> for a subject whose only role is readable, and no S secret. CONNECT_DEBUG=false.
    K2 As K1, but with CONNECT_SOURCE_API_SECRET=<S's API_SECRET> (the path BF-89 fixes). The connector creates its own nightscout-connect-reader subject. CONNECT_DEBUG=true, the maximum log surface for the credential canary.
    K3 As K1, plus CONNECT_SOURCE_COLLECTIONS=entries,treatments,devicestatus. Added at 03:40 after §5.1 was found, so the disturbances would also run against a sink polling at the intended cadence.
    Measurement Every 60 s, from each server's MongoDB: counts, the ids present, when each lab record was first seen, and serverStatus().connections. Liveness came from an authenticated status.json read, which must return 200; samples where a server was not live are excluded. A host loop recorded VmRSS and open fds of each Nightscout process. A final analysis from mongo compared sets, duplicates and every field of every common record. A canary scanned the full docker logs of every container.

    The minimum credential (read-derived from lib/sources/nightscout.js at fbd4e55) is an access token on the endpoint URL, for a subject with the readable role (K1). The connector exchanges it at /api/v2/authorization/request/<token> for a JWT and reads with that. The API-secret path (K2) gives the sink the source's full admin secret. The connector uses it to list and create subjects, so it is not a minimum. BF-89 is only on the API-secret path. The token path never creates a subject.

    5. Findings¶

    5.1 Syncing profiles stalls the 0.1.0 line for 20–35 minutes at a time (new; unregistered)¶

    Reproduced on dev.2 (K1, K2, (e)) and dev.1 ((b), (d)). Not present on 0.0.13 or 234d47c ((g), (h)). The single-variable control is (f).

    Mechanism (read-derived, consistent with every measurement above):

    1. The Nightscout source reads every profile on every poll (/api/v1/profile.json?count=1000, no since).
    2. The sink's profile.create (lib/server/profile.js at 74fc6619, identical in 15.0.8) does insertMany, and the source document still carries its _id. From the second poll on, that _id already exists on the sink, so the insert fails with E11000.
    3. Up to 0.0.13, the internal output swallowed storage errors (.catch(() => known)). From 808ab1c (connector dev, in the 0.1.0 line) it rethrows as Nightscout internal write failed, so the frame fails. The sink log shows Internal persistence failed / Polling frame failed.
    4. A failed frame retries 3 times at 10 s. The loop then waits the normal 5 min plus delay_per_frame_error(frames_missing), which is 2.5 min × (2ⁿ − 1) with equal jitter, capped at 30 min. frames_missing resets only on a successful frame, which cannot happen while a profile exists. So after the second poll the sink polls every ~20–35 min, indefinitely.

    Entries, treatments and devicestatus in a failing frame are written, because the writes run in parallel. So nothing is lost, but everything is late. A Nightscout follower reading the sink sees glucose up to 35 min (K1) and 55 min (K2, across the outage) old, with no error in its UI. This is safety-relevant. The 15.0.8 connector does not do this, so pinning 0.1.0 into 15.0.9 would introduce it for every Nightscout-to-Nightscout site whose source has a profile. The workaround measured in (f) and K3 is CONNECT_SOURCE_COLLECTIONS=entries,treatments,devicestatus, which means not syncing profiles.

    A side effect in the Nightscout process, not the connector: on each failure profile.js logs the whole profile document (Error saving profile data [ … ]: basal schedule, ISF, carb ratio, targets). That happened 38 times in K1's log. The same line fires on 0.0.13 and 234d47c.

    5.2 The BF-89 fix does not repair a subject an earlier connector created (new; unregistered)¶

    Reproduced in (c) with dev.1 as the creator. That 0.0.12 and 0.0.13 create the same role-less subject is read-derived: lib/sources/nightscout.js sends role at v0.0.12, v0.0.13, 234d47c and 1946beb, and roles only at fbd4e55. The connector looks up nightscout-connect-reader by name and reuses it without checking its roles. So any site that has ever run a released connector on the API-secret path against a source that denies anonymous reads already has a subject that reads nothing, and after upgrading to 0.1.0 it still gets 401. An operator can recover by deleting or editing that subject in the source's admin tools. No such step is documented, and it was not run here.

    5.3 Other observations¶

    • Devicestatus and profile _id are stored as strings on the sink (the source's hex value). Entries and treatments keep an ObjectId of the same value. Whether any consumer of the sink trips over a string _id (for example a delete by id) was not measured.
    • Devicestatus arrives one cycle late by construction. The poll is aligned to the glucose timestamp, and an uploader posts devicestatus after the reading. Even on a healthy sink (K3, (f)), devicestatus lag p50 is about 300 s.
    • Source-side logging (Nightscout, not the connector): S logs each created treatment in full (REST API treatment created [ … ]). This is existing behaviour, outside this soak's scope.

    8. What was not covered¶

    • No real vendor service. Dexcom Share, LibreLinkUp, CareLink and Glooko were not exercised against live accounts. LibreLinkUp ran only against its fixture (§1.2).
    • Session expiry. The connector refreshes its session after 8 h (EXPIRE_SESSION_DELAY) and the run was 4 h 23 min, so a JWT expiring mid-run was never exercised.
    • A source on 15.0.8. S was always 74fc6619, except in control (g). The source's dateString normalisation matters to the $gt string comparison. Sources whose stored dateString carries a UTC offset were not tested.
    • More than one profile, profile edits, and food (the source does not read food).
    • The outage as an operator sees it. Here S's name stopped resolving (EAI_AGAIN) and the proxy reset the socket. A host that is up but returns 5xx, a slow source, TLS, or a hosting-provider proxy were not tested.
    • MongoDB 4.4 / 5.0 / 6.0 on the sink, and Node versions in the images other than 22.22.0.
    • Upgrade in place from 0.0.13. The pin was installed into a fresh image. §5.2 with 0.0.13 as the creator is read-derived.
    • The UI. The chart, alarms and pills on a lagging sink were not looked at.

    9. What this soak shows, and what it does not¶

    Shows. Over 4 h 23 min, across a sink restart and a 15-minute source outage:

    • 0.1.0-dev.2, installed exactly from npm, copied every record the source held into its window. Nothing was lost, nothing duplicated, and no field differed.
    • There was no crash, no retry storm, and no growth in memory, connections or fds.
    • It did so on the minimum-privilege token path and on the API-secret path.
    • On the API-secret path, 0.1.0-dev.2 syncs from a denied source where 0.1.0-dev.1 cannot. The dev.1 failure is the role on the created subject, not the lab.
    • Across 72 literal checks, 0.1.0-dev.2 logged no credential, where 0.0.13 in the same lab logged the source token.

    Does not show. That it is timely:

    • With the default collections, every 0.1.0-line sink ran 20–35 min behind for most of the run (§5.1), which 15.0.8's connector does not.
    • A site already holding a subject from a released connector is not fixed by upgrading (§5.2).
    • Updates, deletes and after-the-fact records at the source do not reach the sink (§3.3).
    • Nothing here speaks for the vendor sources.

    10. What would block a tag (listed; the decision is the maintainer's)¶

    1. §5.1 — with the default configuration, the 0.1.0 line lets Nightscout-to-Nightscout sync fall 20–35 min behind (55 min across an outage) whenever the source has a profile. 15.0.8 does not do this. It would ship to every such site through P0-PIN.
    2. §5.2 — BF-89's fix does not reach sites that already hold a role-less subject, which is every site that tried the API-secret path against a denied source with a released connector (read-derived).

    The following affect release notes rather than the tag: §3.3 (no updates, deletes or backdated records; not new in 0.1.0) and §5.3 (string _ids; devicestatus one cycle late).

    11. Rerunning (on 0.1.0 or any later version)¶

    Scripts: tools/lab/connector-soak/. State goes in $CKSOAK_STATE, outside the repository. Secrets are generated there at runtime and never printed. Containers are named cksoak-*, and lab.sh down removes only those.

    export CKSOAK_STATE=/path/outside/repo
tools/lab/connector-soak/lab.sh build 0.1.0          # pins exactly, checks lockfile integrity against npm
tools/lab/connector-soak/lab.sh up-main 0.1.0        # S, proxy, K1 token, K2 secret, K3 no-profiles, writer, sampler
setsid nohup env CKSOAK_STATE=$CKSOAK_STATE tools/lab/connector-soak/lab.sh stats-loop </dev/null >/dev/null 2>&1 &
CPORT_S=3482 CPORT_K=3483 tools/lab/connector-soak/lab.sh control a 0.1.0-dev.1 denied secret   # and b–h as in §4
# disturbances: docker restart cksoak-k1 …; docker stop/start cksoak-s;
tools/lab/connector-soak/lab.sh disturb main cksoak-s cksoak-mongo-s update-treatment   # update-entry | delete | backdate
tools/lab/connector-soak/lab.sh analyze main ledger.jsonl cksoak-s:cksoak-mongo-s k1:cksoak-k1:cksoak-mongo-k1=<first fetch> …
python3 tools/lab/connector-soak/staleness.py  $CKSOAK_STATE/out/main/samples.jsonl
python3 tools/lab/connector-soak/pollstats.py  cksoak-proxy --series
python3 tools/lab/connector-soak/connstats.py  $CKSOAK_STATE
tools/lab/connector-soak/lab.sh canary $(docker ps --format '{{.Names}}' | grep '^cksoak-' | grep -v mongo)
tools/lab/connector-soak/lab.sh down

    Before trusting a green result, run the break-it check. The analyser was run against a copy of a sink database with one record deleted, one duplicated, one field changed and one foreign record added, and it reported all four. A version that fixes §5.1 should show K1 and K2 polling at about 5 min, like K3. A fix for §5.2 should make control (c) sync.
