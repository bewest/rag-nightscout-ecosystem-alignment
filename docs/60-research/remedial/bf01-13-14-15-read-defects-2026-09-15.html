    BF-01, BF-05, BF-13, BF-14, BF-15 — five read defects that answer 200 with the wrong thing¶

    Record

    Record as of 2026-09-15. A point-in-time document; it is not kept up to date.

    Snapshot, 2026-09-15, against origin/dev a8888f0d (branch bf/reads). Historical: the fixes are merged into dev as PR #8738 (BF-01, BF-05, BF-13, BF-14, BF-15, BF-33), not released; 15.0.8 still has these defects. Contributor-facing. Current facts: backfix register.

    Date: 2026-09-15 Branch: bf/reads in externals/work/crm-bf-reads, based on origin/dev (a8888f0d) Environment: node v24.15.0, mongodb driver ^5.9.2 (the version dev pins), MongoDB 7.0.43 in Docker on port 27032 Full suite: 2063 passing, 3 pending, 0 failing Landing: each commit cherry-picks onto origin/dev alone and cleanly, except c8fb536b (BF-05), which shares two files with 4a398d47 (BF-01) and must land with or after it; the pair together applies cleanly. Commits (oldest first, one per defect):

    commit defect files
    4a398d47 BF-01 lib/server/aggregate.js, tests/api.count-where.test.js
    c8fb536b BF-05 lib/server/aggregate.js, tests/api.count-where.test.js
    399dc283 BF-13 lib/api3/generic/search/input.js, tests/api3.paging.test.js
    ba70f1fc BF-15 lib/api3/shared/fieldsProjector.js, tests/api3.fields.test.js

    824380a0 release note CHANGELOG.md

    All five register defects reproduce as described. One new defect was found in the code the register names as the reference fix — see §6 — and it is the same failure mode as BF-14, reachable through API v3.

    Every defect here shares a shape: a read that returns a wrong answer with HTTP 200. In this software that means a person or a caregiver is looking at data that is not what they asked for, with nothing on screen to say so.

    1. BF-01 — count/:storage/where counted nothing¶

    1.1 Reproduction¶

    The mechanism is exactly as recorded. lib/server/aggregate.js:19 called find_options(opts) with one argument, so lib/server/query.js applied its own defaults instead of the collection's options. Run directly against the shipping query.js:

    list  path (entries queryOpts, useEpoch:true): {"date":{"$gte":1789161975992}}
count path (defaults)                        : {"date":{"$gte":"2026-09-11T21:26:15.992Z"}}

    entries.date holds a number and MongoDB compares only within a BSON type, so the injected two-day window excluded every document.

    End to end, against a running server with 20 entries and 5 treatments stored in the last hour (tests/api.count-where.test.js, before the fix):

    GET /api/v1/count/entries/where     -> 200  []   (expected [{_id:null,count:20}])
GET /api/v1/count/treatments/where  -> 200  []   (expected [{_id:null,count:5}])

    1.2 One refinement the register does not state¶

    default_options sets walker = { date: parseInt, sgv: parseInt } when no walker is supplied. So on entries, a request that names its own bound — ?find[date][$gte]=... — was already answered correctly, because the default walker happens to coerce date. The defect fires on entries only when the client supplies no date constraint, which is the default and by far the commonest shape.

    On treatments it is broader and does not depend on that accident: the defaults put the window on date rather than on created_at, so the filter lands on the wrong field entirely.

    1.3 Fix¶

    aggregate() now builds its filter with api.query_for(opts) — the same function the matching list endpoint uses. The collection's date field and type coercions arrive because it is the same code, not because a second copy of the options was kept in step. All three collections that register an aggregate (entries, treatments, devicestatus) already expose query_for.

    There is deliberately no fallback to find_options(opts). A collection that registers aggregate without a query_for should fail loudly; a silent fallback is the defect.

    1.4 Non-vacuity¶

    Four tests. Two are red before the fix and green after:

    before: counts the recent entries the list endpoint returns   expected 0 to be 20
        counts treatments against the date field ...          expected 0 to be 5
after:  4 passing

    The other two — agreement with the list endpoint over an explicit find[date][$gte], and counting outside the default window — pass both before and after. They are stated in the report as guards, not as evidence, for the reason in §1.2.

    2. BF-05 — the count path printed every filter to stdout¶

    Two unguarded console.log calls on the request path printed the constructed $match and the whole pipeline, so a filter's values reached the deployment's logs on every /api/v1/count/* call. They are visible in the raw output of any count test on dev.

    Removed rather than gated. lib/server/aggregate.js has no env handle, so routing them through the quiet-logging flag added in c2ac743c (if (env.debug && env.debug.logging)) would mean threading env through a shared module for a debug print. /api/v1/echo/* already exists for inspecting how a query string becomes a filter, so the diagnostic is not lost.

    Non-vacuity: the test stubs console.log around a count request and asserts nothing matching $match query|AGGREGATE was emitted. Re-adding one of the two lines turns it red.

    3. BF-13 — v3 paging lost and repeated documents¶

    3.1 Reproduction¶

    First against mongod directly, with the sort chain parseSort produces for a request with no ?sort= — {identifier:1, created_at:1, date:1} — over twelve documents with no identifier, one created_at and one date:

    skip 0  doc0,doc1,doc2
skip 3  doc0,doc2,doc5
skip 6  doc0,doc2,doc6
skip 9  doc0,doc2,doc6
LOST 7        doc3,doc4,doc7,doc8,doc9,doc10,doc11
DUPLICATED 3  doc0 x4, doc2 x4, doc6 x2

    Then through the real v3 HTTP API (tests/api3.paging.test.js, before the fix), paging /api/v3/devicestatus?limit=3&skip=N: three documents duplicated (4, 4 and 2 times) and five of twelve never returned. Deterministic across runs.

    3.2 Fix¶

    sort._id = sortDirection after the three existing tiebreaks. _id is always present and always unique, so the order becomes total and skip becomes meaningful. Verified 0 lost, 0 duplicated, with and without a client-chosen ?sort=.

    3.3 Non-vacuity — the fixture is the thing that has to be checked¶

    This is the case the brief singles out, and it behaves exactly as warned. Three runs:

    fix fixture result
    reverted ties on the whole chain paging tests red (3 duplicated)
    applied ties on the whole chain 3 passing
    reverted date varied per document paging tests pass — vacuous

    The third row is why the suite carries a test whose only job is to assert the precondition:

    docs.filter(d => d.identifier === undefined).length.should.equal(DOC_COUNT);
new Set(docs.map(d => d.created_at)).size.should.equal(1);
new Set(docs.map(d => d.date)).size.should.equal(1);

    With the fix reverted and one + i added to the fixture's date, that guard is the only test that fails. Without it, a future edit to the fixture would quietly disarm the whole file.

    4. BF-15 — a dotted ?fields= returned an empty document¶

    4.1 Reproduction¶

    Running the shipping fieldsProjector.js directly:

    new FieldsProjector('uploader.battery')
  storageProjection  {"uploader.battery":1,"identifier":1,"srvCreated":1,"created_at":1,"date":1}
  doc from driver    {"_id":1,"uploader":{"battery":80,"type":"phone"},"device":"...","created_at":"..."}
  applyProjection    {}

    And end to end: GET /api/v3/devicestatus?fields=uploader.battery answered 200 with {}.

    4.2 Fix¶

    applyProjection now compares on paths. A key is kept when a requested field names it outright (the whole subtree is kept) or names a path below it (only that path is kept), and the prune recurses into array members the way the driver's own dotted projection does. Comma-separated top-level fields take exactly the path they took before.

    4.3 Non-vacuity¶

    Three of six tests red before the fix, green after: the dotted path ({} instead of {uploader:{battery:80}}), the array case (foods.name), and the end-to-end HTTP case. The three that pass either way — a whole subtree, a plain comma-separated list, and a dotted path the document does not have — exist to pin the behaviour that must not change.

    5. BF-14 — ?count=0 was answered with the whole collection¶

    5.1 Reproduction¶

    Measured through the shipping lib/api/ router against 24 stored entries, with a find that forces the read past the runtime cache to the database:

    request HTTP rows
    ?count=0 200 24 — the whole collection
    ?count=abc 200 24 — the whole collection
    ?count=-3 200 3
    ?count=1e2 200 1
    ?count=0x10 200 16
    ?count=2.5 200 2
    ?count=5 200 5
    ?count= (empty) 200 10 (the default)

    count=abc is unbounded for the same reason count=0 is: parseInt('abc') is NaN, and the driver treats the resulting limit as absent.

    Note ?count=0x10 returns 16 on v1, because v1 calls parseInt without a radix. This differs from v3, and it matters in §6.

    5.2 Fix¶

    Two layers, because the problem has two audiences.

    At the API. One validateCount middleware in lib/api/index.js, in front of every v1 route. count must be a whole number of documents, 1 or greater; anything else is 400 with the v1 error shape. This follows the register's instruction to give v1 the validation v3 already has, with one deliberate difference: no upper bound is introduced. The corpus census in the register records count=100000 and count=9999999 being sent deliberately, and capping v1 would break those clients for no benefit related to this defect.

    At the storage layer. lib/server/count.js is the single reading of the rule, used by the six list() helpers (entries, treatments, devicestatus, activity, profile, lib/authorization/storage.js) and by profile.list(), which reaches .limit() by a different route. These modules are a published interface; a caller that does not come through the HTTP route must not be able to produce .limit(0) either.

    profile.list(fn, count) is the one site whose non-HTTP behaviour changes: a supplied count that is not a positive whole number now falls back to PROFILES_DEFAULT_COUNT instead of producing an unbounded read. list(fn) with no count is unchanged.

    5.3 The compound with BF-18¶

    BF-18 records that driver 7 abandons READ_OPTIONS' batchSize when .limit(0) is set, and that .limit(0) is BF-14's path and only BF-14's path. After this change .limit(0) is unreachable through the v1 API and through the six storage helpers, so the compound closes — but see §7.2, because the register's suggested landing site for the defensive guard does not exist on dev, and one such path does remain.

    5.4 Non-vacuity¶

    Eight of thirteen tests are red before the fix. The storage-layer guard is separately load-bearing: with the middleware left in place and only the storage change reverted, the test that records what reaches the driver fails with

    AssertionError: expected Array [ 0, -3, 1, 7 ] to equal Array [ 7 ]

    — limit(0) for count=0, limit(-3), and limit(1) for count=1e2. With the fix in place only the one usable count reaches the driver as a limit at all.

    6. BF-33 (new) — v3's ?limit= has the same hole, and it is the code the register points at¶

    The register's fix for BF-14 is "API v3 already has it … give v1 the same validation rather than inventing one". That validation is itself defective, in the same way and worse.

    lib/api3/generic/collection.js parseLimit bounds-checked the raw string with isNaN and <=, then converted it with parseInt(_, 10). The two readings disagree:

    ?limit= isNaN / <= maxLimit sees parseInt(_, 10) produces
    0x10 16 — passes 0 — no limit
    1e2 100 — passes 1
    2.5 2.5 — passes 2

    Measured live against 30 documents with API3_MAX_LIMIT set to 20:

    GET /api/v3/devicestatus?limit=0x10  -> 200, 30 rows   (the whole collection, over the ceiling)
GET /api/v3/devicestatus?limit=1e2   -> 200,  1 row    (a hundred were asked for)
GET /api/v3/devicestatus?limit=2.5   -> 200,  2 rows

    So an unbounded read is reachable through v3 by any client with read access, and it defeats API3_MAX_LIMIT, which exists to be the ceiling. This is BF-14's severity on a second API.

    Fixed in ea50cf52 by testing the digits the client actually wrote and bounds-checking the number that will be used, rather than a different reading of the same string. ?limit=0, -3, abc and 1e400 behave as before (400). ?limit=0x10, 1e2 and 2.5 are now 400 as well.

    Non-vacuity: four of eight tests red before, including the ceiling test, which fails with expected 30 to be below or equal 20 — the bound being exceeded, not merely a status code differing.

    Id: the register's highest id was BF-32 at the moment this was written (2026-09-15, after a git pull --ff-only on main), so this takes BF-33.

    7. Honest limits¶

    7.1 BF-18 was not measured, only made unreachable. origin/dev pins mongodb ^5.9.2 and has no lib/storage/mongo-read-options.js; the batch-size doubling is a driver-7 behaviour on the modernization branch. The claim made here is narrower than "BF-18 is closed": .limit(0) is no longer reachable through the v1 API or through the six v1 storage helpers, and ?limit=0x10 no longer reaches it through v3. Whether driver 7 then holds its bound was not re-measured.

    7.2 findFiltered does not exist on dev, and one .limit(0) path remains. The register suggests a defensive if (limit > 0) in findFiltered; that function is on the seam branch. The equivalent on dev is lib/api3/storage/mongoCollection/find.js findMany, whose toSafeInt(args.limit, 1000) returns 0 for a literal 0 and then calls .limit(0). This was left alone. parseLimit can no longer produce 0, so it is not reachable from the v3 API; but findMany is a published interface and a direct caller passing limit: 0 still gets an unbounded read. Changing the storage default is wider than this brief and belongs with whoever owns the seam's ordering and limit translation.

    7.3 PostgreSQL was not exercised. The register grades BF-14 partly on second-backend behaviour — count=0 returning 0 rows and count=-3 being an HTTP 500 on PostgreSQL. dev has no PostgreSQL backend; everything above is MongoDB only.

    7.4 Two of the new v1 rejections are new restrictions, not repairs. ?count=0x10 returned 16 documents before and is now a 400; ?count=2.5 returned 2 and is now a 400. Neither returned a wrong answer in the BF-14 sense. They are rejected because "a whole number of documents or nothing" is a rule worth having whole, and because the corpus census records no client sending either. If that trade is not wanted, the regex in lib/server/count.js is the one place to loosen.

    7.5 The rule is written twice. lib/server/count.js and the v3 parseLimit express the same thing in two places, on purpose, so that each commit lands or reverts alone. Once both are in, they should be unified — the duplication is the root cause of this entire family.

    7.6 BF-13 is still synthetic. It now reproduces through the real v3 HTTP path rather than against a bare driver, but the tied documents are a fixture, not a capture from a live Nightscout. The register's corpus sizing (devicestatus median 23.5 tie-group straddles per paginated sweep) is what makes it a real-world claim, and that sizing was not re-derived here.

    7.7 Observed in passing, not fixed. lib/authorization/storage.js:84 has an unguarded console.log('Loading', opts) on the auth-storage read path. It is the same shape as BF-05 but in a different file and logs query options rather than user-supplied filter values, so it was left alone while editing that file for BF-14. Worth an operator's attention, not an id from here.

    7.8 One commit does not land alone. c8fb536b (BF-05) touches the same two files as 4a398d47 (BF-01) — lib/server/aggregate.js and the test file BF-01 creates — so it conflicts if cherry-picked onto dev by itself. The alternative was a second copy of the ~40 lines of bootevent scaffolding for one assertion, which is worse to review. BF-05 is the adjunct in this batch rather than one of the four, so it is the one that waits. The other five land alone.

    7.9 Environment note. The containerised mongod fatally asserted mid-suite in __wt_open / wiredtiger_util.cpp:772 at Docker's default nofile=1024 — which is BF-10, observed incidentally. The container was recreated with --ulimit nofile=64000 and the suite re-run. Nothing in the fixes is implicated; it is recorded because it will happen to the next person who runs this suite in Docker.

    8. Release note¶

    Added to CHANGELOG.md under [Unreleased] / Fixed in 824380a0, one bullet per fix, in plain language for someone managing their own or a family member's diabetes. Two are marked as behaviour changes because they can turn a request that used to return 200 into a 400.

    The text names the endpoints affected and gives a before and after for each. The two that most need reading are:

    • ?count= on v1: ?count=0 used to be answered with the whole collection, ?count=1e2 with one document. count must now be a whole number, 1 or greater; anything else is 400. No upper limit was introduced, so count=9999999 is unaffected.
    • v3 paging: a tool that paged devicestatus and appeared to be missing records should be re-run.
