## 2. What the page adds to a treatment (fix step 1)

The page's treatment object is not the stored document. Each field below was established as page-added in two ways: by reading where it is set, and by the probe reading the stored document straight from MongoDB before any drag (none of these fields is present on a treatment created through `POST /api/v1/treatments` or `POST /api/v3/treatments`). The research agent's read of the uploader sources (below, §6) found no uploader that sends `mgdl`, `scaled`, `endmills`, `cuttedby` or `cutting` on a treatment.

| field | where it is added | holds | removed from the split copy | cleared on a time change |
|---|---|---|---|---|
| `mills` | `lib/data/ddata.js:39-40` `processRawDataForRuntime` (server, and the page's own `ddata`), `lib/data/dataloader.js:20-21` | the old time | yes | yes (`$unset`) |
| `date` | `lib/client/renderer.js:29-33` `getOrAddDate`, `lib/client/index.js:167-171` `entryToDate`, only when the record has no `date` | a `Date` at the old time | yes, **when it is a `Date` object** | n/a |
| `endmills` | `lib/data/ddata.js:53-65` (records with a duration), `lib/profilefunctions.js:300-302` (temp basals) | the old end time | yes | yes |
| `mgdl` | `lib/data/treatmenttocurve.js:69,76,78` | glucose at the old time (glyph height) | yes | yes |
| `scaled` | `lib/sandbox.js:258-264` `scaleEntry`, set only when absent | the same, in display units | yes | yes |
| `cuttedby`, `cutting` | `lib/data/ddata.js:247-248` `processDurations`, which the page runs on its own objects (`lib/client/receiveddata.js:148`, `processTreatments(false)`) | profile names at the old overlap | yes | no |

Found but left alone, because they are not time-derived or cannot be told apart from a stored value:

| field | where | why left |
|---|---|---|
| `eventType: ''` | `lib/data/treatmenttocurve.js` | default when absent; not a time |
| `mmol` | `lib/data/treatmenttocurve.js:67,76` | derived from the stored `glucose`, not from the time |
| `absolute` | `lib/data/dataloader.js` `normalizeTreatments` (from `amount`) | not a time |
| `duration` | `ddata.js` from `durationInMilliseconds`; `processDurations` may shorten it on the page's objects | cannot be told apart from a stored `duration`. Only Profile Switch and Temp Basal records are shortened, and a split needs `carbs` and `insulin` on one record |
| `action` | `lib/data/calcdelta.js:56` | deleted by `receiveddata.js` before the object is kept |

**`date` is the one field that is both page-added and stored by uploaders.** The page adds it as a `Date` object; everything that reaches the page arrives as JSON, so a `date` that is not a `Date` came from storage. The helper uses that test (`hasStoredDate`).

## 3. What the branch changes (fix step 2: set, not remove, `date`)

One commit, `8d797ba4`: new `lib/client/treatmenttime.js` (three small functions), wired into `lib/client/renderer.js` (the three move cases) and `lib/report_plugins/treatments.js` (the editor's Save); new `tests/treatmenttime.test.js`; `tests/dependency-d3.test.js` updated for the new emit shape.

| path | dev writes | branch writes |
|---|---|---|
| Move carbs / Move insulin, new record (`dbAdd`) | a JSON copy of the page object (with `mills`, `date` as an ISO string, `mgdl`, `scaled`) | `splitRecord`: the copy without the fields in §2; a stored `date` becomes the new time in epoch ms |
| Move carbs / Move insulin, record left behind | `dbUpdateUnset {carbs\|insulin}` | `dbUpdateUnset {carbs\|insulin, mills, endmills, mgdl, scaled}`, and `dbUpdate {date}` only if a stored `date` disagrees with its `created_at` |
| plain Move | `dbUpdate {created_at}` | `dbUpdateUnset {mills, endmills, mgdl, scaled}` then `dbUpdate {created_at[, date]}` (`date` only if one is stored) |
| Reports editor Save (`PUT /api/v1/treatments`) | the record minus `mills` and `created_at` | `alignEditedRecord`: also minus `endmills`, `mgdl`, `scaled`, and a stored `date` set to the edited time |

**Why set `date` rather than remove it.** API v3 stores a treatment's canonical time in `date` as epoch ms (`lib/api3/generic/collection.js:176-199` `parseDate`; `date` is immutable to v3 clients, `lib/api3/generic/update/validate.js:21`). v3 does not synthesise `date` on read, so a v3 reader of a record without `date` gets no time from that field. Per the source read in §6, AAPS NSClientV3 writes `date` only, AAPS classic NSClient sends `date` (epoch ms) over websocket `dbAdd`, and nightguard sends `date` and `mills` as epoch ms. Removing `date` would take the time away from the v3-created records those clients read. Setting it to the new time keeps it agreeing with `created_at`. A number is used because that is v3's shape, and because the chart can draw a number: `getOrAddDate` returns a stored `date`, and `xScale` of an ISO string is `undefined`, which is the top-left glyph and the `translate(undefined, …)` console error. On a record with no stored `date`, none is added.

The v1 treatments path does not read `date`: `lib/server/treatments.js` `prepareData` builds `created_at` from `created_at` / `eventTime` only, and `ddata` builds `mills` from `created_at`.

**Two writes for a plain Move.** The websocket API has no combined `$set` + `$unset`. The unset is emitted first. Each handler reads the document back after its own write, so the later of the two broadcasts carries both changes. The probe's `live` read (before any restart) matched the stored and oracle reads in every Move phase.

## 5. Other edit paths (the coordinator's question: is "edit the treatment's time" a safe workaround?)

The main page has no treatment edit dialog. Its only dialogs are the Bolus Wizard's food picker and the authentication prompt (`lib/client/boluscalc.js:742`, `lib/client/hashauth.js:281`), and the Care Portal on the main page only creates records (`lib/client/careportal.js:396-398`, `POST`). The time-changing paths are the drag, the Reports editor and the API.

| path | dev | branch |
|---|---|---|
| drag Move of a damaged record | does not repair | repairs |
| Reports > Treatments > edit > Save | IOB/COB follow once the server has reloaded; `date` stays old, so the main chart still draws the record at top-left | repairs everything |
| raw `PUT /api/v1/treatments` with the stored document | does not repair (`lib/server/treatments.js` `save` is a `replaceOne` of what is sent) | unchanged; fixing it is a server-side change, out of this branch's scope |

Two observations on the Reports editor, identical on both builds:

- **Live lag.** Right after Save, `/api/v2/properties` still used the old value (COB 25 while the stored value was 50). It matched 70 s later, and after a restart. This is the server's reload, not BF-103.
- **Types.** The editor PUTs `application/x-www-form-urlencoded`, so every field arrives as a string. `prepareData` converts the numeric treatment fields back, but not `date`, `mgdl` or `scaled`. On the branch the moved `date` is stored as the digit string `"1790210820000"` (the chart draws it correctly; a v3 reader receives a string). On dev a report edit of a v3 record likewise turns its numeric `date` into a string. Not changed here.

**Workaround on the shipped release (read-derived, not measured on 15.0.8):** 15.0.8's editor has the same `delete data.mills` (`lib/report_plugins/treatments.js:212` at `92d08342`), so editing and saving the treatment in Reports is expected to make IOB/COB follow there too, after the server reloads. The glyph stays at top-left. A by-hand check on 15.0.8 in the maintainer's lab is listed in §8.

## 6. Tradeoffs of the two alternatives (fix step 3, measured by prototype, not committed)

Both were applied to a copy of dev (`crm-bf-split-drag-proto`), measured with the full suite (Node 22.23.2) and the same browser probe, then reverted.

### (a) `ddata` prefers `created_at` when a stored `mills` disagrees by more than 60 s

| measure | result |
|---|---|
| suite | 2440 passing, 0 failing, 3 pending: no test pins the "keep a stored mills" rule |
| IOB/COB | FOLLOW on every phase, including the raw v1 PUT and records already damaged, without any write |
| what it leaves | every stale `date` (ISO string) and `mgdl` / `scaled`. The glyphs stay at top-left on every damaged phase (5 or 10 invalid glyphs), and v3 readers still get the old `date`. `endmills` is also derived only when absent (`ddata.js:53`), so a stale stored `endmills` would survive (not exercised) |
| reach | the rule is in `processRawDataForRuntime`, which serves every collection. Measured on the function directly: a profile document's `mills` (−2880 min, its start date) became its `created_at`, and a device status whose `mills` is 5 min off was retimed. Profiles are harmless here, because `lib/profilefunctions.js:48` recomputes `mills` from `startDate` at load. Device status would change. A treatments-only rule needs a collection argument the function does not have today |
| who stores `mills` on treatments | nightguard, as epoch ms equal to its `created_at` (source read, §7), so it agrees and is unaffected; otherwise only records written by the page |

### (b) the server drops client-supplied `mills` / `mgdl` / `scaled` on websocket treatment `dbAdd`

| measure | result |
|---|---|
| suite | 2440 passing, 0 failing, 3 pending |
| IOB/COB | new splits FOLLOW. Already-damaged records do not: moveDamagedRc COB 26.17 vs 50, moveDamaged1508 IOB 3.48 vs 4.986, and splitDamaged's half left behind (IOB 5.965 vs 7.439). The raw v1 PUT stays STALE (136.0 vs 155) |
| what it leaves | the split still stores `date` as an ISO string at the old time: the glyph goes to top-left (5 invalid glyphs on each split), and a v3 reader gets the old time. Dropping `date` too would remove AAPS classic NSClient's `date` (below) |
| who it affects | read from source by a research sub-agent (labelled there by path and line; not run). **AAPS classic NSClient** emits `dbAdd` / `dbUpdate` for treatments (`NSClientService.kt:595-626`), with `date` as epoch ms on boluses and carbs and no `mills`, `mgdl` or `scaled` (`BolusExtension.kt:9-26`, `CarbsExtension.kt:12-25`; therapy events send only `created_at`, `TherapyEventExtension.kt:58-73`). **xDrip+ Android** hands `dbAdd` to a paired NSClient app through an Android intent, with `created_at` only (`NSClientChat.java:24-79`). No `dbAdd` / `dbUpdate` for treatments was found in xDrip4iOS, LoopFollow (listens only), Trio, nightguard, nightscout-connect or LoopWorkspace's NightscoutServiceKit. The rileylink_ios NightscoutService submodule was not checked out and was not read. Clone SHAs of that read: AndroidAPS `598e2eb39c`, xDrip `1e86d9a2a`, Trio `40f097fdd`, LoopWorkspace `4319ce5`, NightscoutKit `4ec9fd1`, nightguard `9ea3dea`, xdripswift `96b6afe2`, LoopFollow `9d2cea6b`, nightscout-connect `649a7de`. The same read found `docs/10-domain/websocket-event-coverage.md:237` ("the legacy WebSocket dbAdd/dbUpdate events are primarily used by the web interface") is incomplete, because the AAPS classic NSClient uses them.

## 7. Found along the way, not changed

- **A split duplicates identity fields.** The split copy keeps `identifier` (and, where present, `srvCreated` / `srvModified` and uploader ids). Measured on both builds: the two halves of a split v3 record carry the same `identifier`. The copy already drops `_id` and `NSCLIENT_ID` for the same reason.
- **Websocket `dbAdd` "similar" dedup** (`lib/server/websocket.js`, `processSingleDbAdd`): a treatment within 2 s of one with the same `carbs` / `insulin` / … updates only the existing record's `created_at`. That is another time change that leaves a stored `mills` behind. Not exercised.
- **Websocket `dbUpdate` does not set `srvModified`**, so API v3 history readers may not see a move. Not measured.
- A stored ISO-string `date` breaks the chart glyph whatever its value, because `getOrAddDate` returns it as-is.

## 8. Review query for operators (read-only)

This lists treatments whose stored `mills` or `date` disagrees with `created_at` by more than a minute. It also lists treatments whose `date` is a non-numeric string (drawn at the chart's top-left) and those whose `created_at` cannot be read. It changes nothing. Requires MongoDB 4.2+ (`$regexMatch`, `$round`). `date` is matched as a number, a digit string, an ISO string, or a BSON date, and `scaled` is not used.

```js
db.treatments.aggregate([
  { $match: { $or: [ { mills: { $exists: true } }, { date: { $exists: true } } ] } },
  { $addFields: {
      _caMs: { $toLong: { $convert: { input: '$created_at', to: 'date', onError: null, onNull: null } } },
      _millsMs: { $convert: { input: '$mills', to: 'long', onError: null, onNull: null } },
      _dateType: { $type: '$date' },
      _dateMs: { $switch: {
        branches: [
          { case: { $in: [ { $type: '$date' }, [ 'double', 'int', 'long', 'decimal', 'date' ] ] },
            then: { $toLong: '$date' } },
          { case: { $and: [ { $eq: [ { $type: '$date' }, 'string' ] },
                            { $regexMatch: { input: '$date', regex: /^[0-9]+$/ } } ] },
            then: { $toLong: '$date' } },
          { case: { $eq: [ { $type: '$date' }, 'string' ] },
            then: { $toLong: { $convert: { input: '$date', to: 'date', onError: null, onNull: null } } } }
        ],
        default: null } }
  } },
  { $addFields: {
      millsOffMin: { $cond: [ { $and: [ { $ne: [ '$_millsMs', null ] }, { $ne: [ '$_caMs', null ] } ] },
        { $round: [ { $divide: [ { $subtract: [ '$_millsMs', '$_caMs' ] }, 60000 ] }, 1 ] }, null ] },
      dateOffMin: { $cond: [ { $and: [ { $ne: [ '$_dateMs', null ] }, { $ne: [ '$_caMs', null ] } ] },
        { $round: [ { $divide: [ { $subtract: [ '$_dateMs', '$_caMs' ] }, 60000 ] }, 1 ] }, null ] },
      dateIsTextTime: { $and: [ { $eq: [ '$_dateType', 'string' ] },
        { $not: [ { $regexMatch: { input: { $ifNull: [ { $toString: '$date' }, '' ] }, regex: /^[0-9]+$/ } } ] } ] },
      createdAtUnreadable: { $eq: [ '$_caMs', null ] }
  } },
  { $match: { $or: [
      { millsOffMin: { $gt: 1 } }, { millsOffMin: { $lt: -1 } },
      { dateOffMin: { $gt: 1 } }, { dateOffMin: { $lt: -1 } },
      { dateIsTextTime: true }, { createdAtUnreadable: true } ] } },
  { $project: { created_at: 1, eventType: 1, carbs: 1, insulin: 1, mills: 1, date: 1,
      millsOffMin: 1, dateOffMin: 1, dateIsTextTime: 1, createdAtUnreadable: 1 } },
  { $sort: { created_at: -1 } }
]);
```

Checked on 12 synthetic records in the lab database:

| flagged (7) | not flagged (5) |
|---|---|
| 15.0.9 rc shape (−110 / −110 min, text date); 15.0.8 shape (same); v3 record moved on dev (`date` −40); digit-string `date` −30; BSON-date `date` −30; ISO `date` equal to `created_at` (text date only); unreadable `created_at` | v3 record with `date` = `created_at`; nightguard-style `mills` = `date` = `created_at`; plain v1 record; `created_at` with a `+02:00` offset and matching `mills`; `mills` 30 s off |

Repair is not scripted and no boot migration is added. On the branch, dragging an affected treatment to its intended time (a plain Move), or saving it in the Reports editor, rewrites it. Operators who repair by hand should review each record with its owner first.
