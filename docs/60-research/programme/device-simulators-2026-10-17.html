    Device simulators and app-level test rigs, measured — 2026-10-17¶

    Record

    Record as of 2026-10-17. A point-in-time document; it is not kept up to date.

    Contributor-facing. Record (a snapshot; not rewritten as the world moves). Measured 2026-10-17 at LoopKit/g7sim 7c039de5 (2026-10-12), LoopKit/pod a491a5ea (2026-10-12), jwoglom/trio-test-harness c3c1bfe7 (2026-10-17) and jwoglom/faketandem 34c94019 (2026-10-17), written against this repository at d9167f59. It brings the device-simulator part of the stack census of 2026-09-30 up to date; the census figures for these repositories and their neighbours were re-run the same day (tools/programme/stack-census/results/census-2026-10-17-simulators.md).     Per-repository detail: g7sim · LoopKit/pod · trio-test-harness.

    1. What this measures¶

    The question: which parts of an end-to-end virtual test of an AID app now exist, with no person's data and no hardware, from a simulated sensor and pump through a real app build to the records it uploads to Nightscout? Which parts already work together, and where are the gaps between them?

    2. The pieces¶

    piece role transports control surface tests (run 2026-10-17) CI licence
    LoopKit/g7sim Dexcom G7 / ONE+ / Stelo sensor side: advertising schedule and lockout, display slots, readings with warm-up, expiry, a 24-hour backfill store and a calibration offset, an identity certificate chain from a dummy CA, EC-JPAKE pairing on P-256 and an AES challenge; models the iOS wake, suspend and relaunch behaviour that decides whether a backgrounded app gets a reading BLE peripheral on Linux (vendored paypal/gatt); impossible: an app in the iOS Simulator through ImpossiBLE's socket HTTP API and web page: new sensor, glucose mode (sine, fixed, walk), sensor state 33 func Test, 33 pass, clean under -race and go vet none MIT

    What runs where. The three Go simulators build and test on Linux with no radio, Mac or network. On a Mac, g7sim and pod each serve an app in the iOS Simulator with no radio. trio-test-harness needs a Mac with Xcode.

    3. How they join today¶

                      iOS Simulator (Mac)                            Linux, CI or Mac
 ┌──────────────────────────────────────────────┐
 │ Loop (LoopWorkspace next-dev)                 │
 │   G7SensorKit next-dev ─┐                     │
 │   OmnipodKit next-dev ──┤ CoreBluetooth       │
 │                         ▼                     │
 │                 ImpossiBLE ── unix socket ────┼──▶ impossible-mux ──▶ g7sim   (G7 sensor side)
 └──────────────────────────────────────────────┘                    └─▶ pod     (DASH pod side)

 TandemKit / pumpX2 client ── virtual TCP/JSON GATT ──▶ faketandem (Tandem pump side)

 trio-test-harness ── drives Trio or Loop ── built-in Glucose/Pump Simulator only; Nightscout skipped
    • One join works now: Loop with a simulated G7 and a simulated DASH pod together. impossible-mux (in g7sim, cmd/impossible-mux) takes the single socket ImpossiBLE gives the app and fans it out to g7sim and pod, each of which sees the app as its only client. With -suspend the mux stops and wakes the app as iOS would. g7sim's README states that Loop pairs, reads and reconnects in the Simulator. This record did not reproduce that (no Mac); it did run g7sim's and pod's impossible transports on Linux against scratch clients.
    • The app side of that join exists only on next-dev branches. G7SensorKit's direct connection is on next-dev (e17129d), merged there as 7da3b69 (#67, 2026-09-20). OmnipodKit's ImpossiBLE detection (e60e0ab) is on next-dev and simulator-bluetooth. LoopWorkspace next-dev (1561bff0) pins both. LoopWorkspace dev (c1f55970) and Trio dev (bbb1c0e0) pin G7SensorKit dd91f46 (passive; Trio takes it from the loopandlearn/G7SensorKit fork) and OmnipodKit 928bb79. The latest releases, Loop v3.14.9 (2026-10-05) and Trio v1.0.2 (2026-10-07), pin G7SensorKit dd91f46 and OmnipodKit 043b91d. None of these contains e60e0ab or G7SensorKit's Simulator bridge (8fa9c73, #89), so their Simulator builds mock the pod and cannot pair with g7sim. In flight: Trio #1548 brings G7 direct connection to Trio dev from loopandlearn/G7SensorKit feat/trio-g7-direct, which has the direct connection (7da3b69) but not #89; LoopWorkspace #454 (next-dev into dev) has been open since 2026-06-04.
    • trio-test-harness does not attach any of the external simulators. It uses only the apps' built-in simulators, simctl launch passes no environment, and there is no reference to g7sim, pod or ImpossiBLE. A faketandem stress lane was added in dd69a8d and moved out of the repository seven minutes later in 83729b5 (both 2026-10-01). Its build hooks remain in build.py but have no CLI flags.
    • faketandem no longer needs pumpX2 to run. d60279c (2026-10-14) ports pumpX2's message library and its EC-JPAKE to Go and makes them the default. The port is held to pumpX2's jar by recorded answers: 4,819 parse and 3,142 encode cases in 282 files. Every go test checks them against the recorded answers, and CI checks them live against the jar. Pairing is checked both ways: pumpX2's client against the Go pump side, and a Go client against pumpX2's server. In this record, editing one recorded answer failed exactly that class's test and named the edited case; restoring it passed. The port is derived from pumpX2, so it is a second implementation held to the first, not an independent design.

    4. What reaches Nightscout¶

    No harness run uploads anything today. trio-test-harness's pre-seeding skips Nightscout setup, and its onboarding walk taps "Skip Nightscout Setup". Trio keeps the URL and secret in the Keychain, and no th command writes them. Nothing is checked on the server side.

    What an app driven by these simulators would upload, read from the code and not run:

    source records (inferred from code)
    Loop + g7sim entries (sgv), one per reading including backfilled ones, with a device string that marks the sensor as simulated ("g7sim (Simulator)"), so test uploads can be told apart from real-sensor data; a Sensor Start treatment; "CGM: " Note treatments driven by the sensor's algorithm state. How the backfill flag and received time serialise was not checked
    Loop + pod treatments: bolus, temp basal, a suspend as a zero-rate temp basal with reason: "suspend" (a resume uploads no treatment), a Site Change for a new pod. devicestatus.pump: reservoir (at or below 50 U), suspended, bolusing, and a display override for a pod fault or expiry; a pod fault creates no Note treatment. pod's basal and temp basal do not draw down its reservoir (only boluses do), so the reservoir in such a run follows boluses only
    Trio (any source) entries, treatments, devicestatus and profile (NightscoutManager.swift, Trio e41c9db37)

    This repository already has the receiving end, running on synthetic data: tools/lab/rc-soak (two Nightscout arms under the same synthetic traffic, including Loop and Trio shapes written by its own traffic.js), tools/mock_nightscout.py, the per-client mappings in mapping/, and the schemas and quirks in specs/. An app run against a lab Nightscout would produce real client upload shapes from no person's data, which is the evidence that traffic.js and the mappings do not yet have.

    Each item names the project whose maintainers decide it.
