# Release assets

**Status: DRAFTS. Nothing here has been tagged, pushed, merged or published.**

This directory holds the **tag messages and release notes** for releases of
`cgm-remote-monitor` and `nightscout-connect`, one directory per release.

## Why they live here and not in the shipping repositories

The maintainer's rule, stated 2026-09-15:

> **`CHANGELOG.md` is a release OUTPUT, generated by GitHub tooling between releases.
> Branches must never hand-edit it.**

So a branch carries code and a commit message, and nothing else. The changelog is
generated at release time from what actually merged. That leaves three artefacts with
nowhere to live while the release sequence is still being worked out — the **annotated tag
body**, the **operator-facing release notes**, and the **record of what is in the
release** — and this directory is where they live until the release is cut.

**These drafts complement the generated changelog; they do not replace it.** The generated
changelog is the authoritative list of *what merged*. These notes carry what a generated
list cannot: what an operator will **notice**, what they must **do**, what to **check**
afterwards, and what is still **broken**. At release time the two are reconciled — see
[Reconciliation at release time](#reconciliation-at-release-time).

## Convention

```
releases/
  <product>-<version>/
    tag-message.txt     the annotated tag body, git convention: short subject,
                        blank line, body. Plain text. No markdown headers.
                        Contributor-facing; may be terse and fully technical.
    release-notes.md    the operator-facing draft. Plain language, every term
                        defined, every safety caveat preserved. See "Audience".
    contents.md         which branches, PRs and register entries make up the
                        release; the semver argument; what is unsettled.
  _template/            copy this to start a new release directory
```

Directory names use the product's own version spelling: `cgm-remote-monitor-15.0.9`
(no `v`, matching `package.json`), `nightscout-connect-v0.0.14` (with `v`, matching the
tag). The **tag** in each repository keeps whatever prefix that repository already uses —
`cgm-remote-monitor` tags are `v15.0.8`, connector tags are `v0.0.13`.

## Audience — the two halves are written differently, deliberately

| File | Audience | Rules |
|---|---|---|
| `tag-message.txt` | contributors, maintainers, anyone reading `git show <tag>` | full technical depth; terse is fine; name commits by SHA |
| `contents.md` | maintainers and reviewers | full technical depth; every figure says how it was measured |
| `release-notes.md` | **people managing their own or a family member's diabetes** | plain language; define every term; preserve every safety caveat verbatim; never simplify algorithm or alarm behaviour in a way that could mislead someone relying on it; no individualised insulin dosing advice; say that Nightscout is not a medical device and this is not medical advice; point at the care team where a change could touch therapy decisions |

The rules in the right-hand cell of the last row are not style preferences. They are
[`docs/30-design/semver-and-release-versioning-policy-2026-09-15.md`](../docs/30-design/semver-and-release-versioning-policy-2026-09-15.md)
§5.6, and §3.3 of the same document gives the worked example of what failing them looks
like: *"Your reservoir alarm now works"* is not an adequate release note, because it does
not tell anyone that a new alert is coming at 72 hours.

## Version numbers here are proposals, not decisions

Every number in this directory is a **proposal**. The analysis behind them is
[`docs/60-research/gt4-semver-classification-2026-09-15.md`](../docs/60-research/gt4-semver-classification-2026-09-15.md)
(classification) and
[`docs/30-design/semver-and-release-versioning-policy-2026-09-15.md`](../docs/30-design/semver-and-release-versioning-policy-2026-09-15.md)
(policy, and where it overrules the classification). **Both are themselves drafts awaiting
maintainer adoption**, and both disagree with the numbers the directories here are named
after. Each `contents.md` states that disagreement at the top rather than hiding it. The
directory name is the *planned* number; the policy's number is in the file.

### Reserved slots for releases whose numbers are not settled

The five modernization parcels have **no agreed numbers**. The policy proposes a train in
§8.3 and immediately says (house rule 9) that *the ordering is more durable than the
numbers*. Nothing here invents one. When each release is cut, create its directory with
the number the maintainer chooses. Until then these are the **named placeholders**, and
they are names, not versions:

| Placeholder | Contents | Policy's proposed number (§8.3) — **not adopted** |
|---|---|---|
| `DEPRECATION_RELEASE` | MiniMed shim shipped non-fatally, Dexcom escape hatch preserved, `?count=0` warned rather than rejected, subject allow-list warned | 15.2.0 |
| `RUNTIME_RELEASE` | parcel 1 `chore/retire-jsdom` — Node floor, MongoDB 4.4 out of CI, jsdom to Playwright | 16.0.0 |
| `BUILD_RELEASE` | parcel 2 `chore/build-runtime-separation` | 16.1.0 |
| `DEPENDENCY_RELEASE` | parcels 3 + 5 | 17.0.0 |
| `INGESTION_RETIREMENT_RELEASE` | parcel 4 `chore/mime-exposure-review` — legacy Dexcom and MiniMed retirement | 18.0.0 |

Two constraints on that table are **not** placeholders and should survive whatever
numbering is chosen:

1. **Parcel 4 is contained in parcel 5.** Measured with `git merge-base --is-ancestor`
   across all four consecutive pairs: the five parcels are linear, each contained in the
   next. So *"ship 5 but hold 4 back"* is not achievable as a merge, and any plan that
   assumes it is, is wrong.
2. **The runtime break and the ingestion break must not be in the same release.** An
   operator debugging a site that will not start should not simultaneously be debugging
   why their glucose data stopped.

## Reconciliation at release time

Before a release is published, someone does this and records that they did:

1. Generate the changelog with the GitHub tooling, from what actually merged.
2. **Diff the generated list against `contents.md`.** Anything in the generated list that
   `contents.md` does not name either merged after these notes were written, or was never
   reviewed. Both are worth knowing before publishing.
3. Re-read `release-notes.md` against the generated list. Every *behaviour* change in the
   generated list needs a line in the notes or a written reason it does not.
4. Check every version number against the number actually being cut.
5. Check the register
   ([`docs/30-design/nightscout-backfix-register.md`](../docs/30-design/nightscout-backfix-register.md))
   for entries that moved to *fixed* since the draft was written, and for entries the
   release leaves open that the notes should name under "Known issues".
6. Re-cut the annotated tag from `tag-message.txt` if the text changed. **A tag other
   people have already fetched is superseded, never moved.**

## Nothing in this directory ships anything

Writing a file here is not a release. A release is three separate human decisions, and
this directory participates in none of them:

| # | Decision | Reversible? |
|---|---|---|
| 1 | Merge the code — a PR merge into `dev` | yes, `git revert` |
| 2 | Push the tag — the tarball becomes downloadable | **effectively no** |
| 3 | Publish the package — `npm publish` | **no** |

They are set out in
[`docs/30-design/maintainer-release-brief-2026-09-15.md`](../docs/30-design/maintainer-release-brief-2026-09-15.md)
§2, with the commands a human runs. Note in particular that for `nightscout-connect`
**decision 2, not decision 3, is what delivers the fix**, because every
`cgm-remote-monitor` pin is a GitHub tarball URL and none of them resolves from npm.
