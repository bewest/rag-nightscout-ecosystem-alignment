    Directory Describes Status

    nightscout-connect-v0.0.14/ the retired local tag v0.0.14 (649a7de) superseded: no 0.0.14 will be published; the line is 0.1.0 (queue P0-TAG)

    Why these files live here¶

    The maintainer's rule (2026-09-15):

    CHANGELOG.md is a release OUTPUT, generated by GitHub tooling between releases. Branches must never hand-edit it.

    So a branch carries code and a commit message. Three artefacts then need a home until the release is cut: the annotated tag body, the user-facing release notes, and the record of what is in the release. This directory is that home.

    These drafts complement the generated changelog; they do not replace it. The generated changelog is authoritative for what merged. The notes carry what a generated list cannot: what a user will notice, what they must do, what to check afterwards, and what is still broken. At release time the two are reconciled — see Reconciliation at release time.

    Open item: CHANGELOG on dev¶

    cgm-remote-monitor dev carries a hand-written ## [Unreleased] section in CHANGELOG.md (71 lines added since 15.0.8, from 12 commits by upstream contributors, measured with git log official/master..official/dev -- CHANGELOG.md). That is in tension with the rule above. The maintainer needs to decide whether the rule stands (and the section is replaced by the generated changelog at release time) or whether contributor-written entries are accepted, in which case the reconciliation below must also diff against that section.

    Convention¶

    releases/
  <product>-<version>/
    tag-message.txt     the annotated tag body, git convention: short subject,
                        blank line, body. Plain text. No markdown headers.
                        Contributor-facing; may be terse and fully technical.
    release-notes.md    the user-facing draft. Plain language, every term
                        defined, every safety caveat preserved. See "Audience".
    contents.md         which PRs and register entries make up the release;
                        the semver facts; what is unsettled.
    decisions.md        optional; the maintainer's decisions that shape the
                        release, each stated as it stands.
    testing-notes.md    optional; the call for testers of a release candidate.
                        Part 1 user-facing (plain language), part 2 for
                        operators and tool authors. Living until the tag.
    verification-record.{json,md}   optional; see VERIFICATION-RECORDS.md
  _template/            copy this to start a new release directory

    Directory names use the product's own version spelling: cgm-remote-monitor-15.0.9 (no v, matching package.json), nightscout-connect-v0.0.14 (with v, matching the tag). The tag keeps the repository's existing convention: cgm-remote-monitor has both spellings (15.0.8 and v15.0.8, lightweight tags on the same commit 92d08342); connector tags are v0.0.13.

    Audience¶

    File Audience Rules
    tag-message.txt contributors, maintainers, anyone reading git show <tag> full technical depth; terse is fine; name commits by SHA
    contents.md maintainers and reviewers full technical depth; every figure says how it was measured
    release-notes.md people managing their own or a family member's diabetes plain language; define every term; preserve every safety caveat; never simplify algorithm or alarm behaviour in a way that could mislead someone relying on it; no individualised insulin dosing advice; say that Nightscout is not a medical device and this is not medical advice; point to the care team where a change could touch therapy decisions; describe any defect still live on a shipped release by effect only

    These rules are docs/30-design/modernization/semver-and-release-versioning-policy-2026-09-15.md §5.6; §3.3 of the same document gives the worked example ("Your reservoir alarm now works" is not an adequate note, because it does not say that a new alert arrives, when, at what level, and how to turn it off). All drafts here must also meet docs/00-overview/DEFINITION-OF-DONE.md criterion 10.

    Version numbers here are proposals¶

    15.0.9 is decided (RT-D3 answered; nightscout-connect 0.1.0 released 2026-09-24, P0-TAG). Every other number in this directory is a proposal. The analysis behind them is docs/60-research/modernization/gt4-semver-classification-2026-09-15.md (classification) and the versioning policy above. Both are drafts awaiting maintainer adoption. The directory name is the planned number; each contents.md states the facts that bear on the number.

    Reserved slots for releases whose numbers are not settled¶

    The modernization parcels have no agreed numbers. When each is cut, create its directory with the number the maintainer chooses. Until then these are named placeholders, not versions:

    Placeholder Contents Policy's proposed number (§8.3) — not adopted
    DEPRECATION_RELEASE MiniMed shim shipped non-fatally, Dexcom escape hatch preserved, ?count=0 warned rather than rejected, subject allow-list warned 15.2.0
    RUNTIME_RELEASE parcel 1 chore/retire-jsdom — Node floor, MongoDB 4.4 out of CI, jsdom to Playwright 16.0.0
    BUILD_RELEASE parcel 2 chore/build-runtime-separation 16.1.0
    DEPENDENCY_RELEASE parcels 3 + 5 17.0.0
    INGESTION_RETIREMENT_RELEASE parcel 4 chore/mime-exposure-review — legacy Dexcom and MiniMed retirement 18.0.0

    Note that ?count=0 rejection (#8738) is already merged to dev and therefore ships in 15.0.9 unless reverted; the DEPRECATION_RELEASE row was written before that merge. The maintainer reports that the legacy MiniMed path (mmconnect) has been broken for some time and that legacy Dexcom Share is intended to map to nightscout-connect; the ingestion-retirement risk grading has not been redone on that basis.

    Two constraints hold whatever numbering is chosen:

    1. Parcel 4 is contained in parcel 5. Measured with git merge-base --is-ancestor across all consecutive pairs: the parcels are linear, each contained in the next, so "ship 5 but hold 4 back" is not achievable as a merge.
    2. The runtime break and the ingestion break must not be in the same release. An operator debugging a site that will not start should not simultaneously be debugging why their glucose data stopped.

    Reconciliation at release time¶

    Before a release is published, someone does this and records that they did:

    1. Generate the changelog with the GitHub tooling, from what actually merged.
    2. Diff the generated list against contents.md. Anything in the generated list that contents.md does not name either merged after the notes were written or was never reviewed. Both are worth knowing before publishing.
    3. Re-read release-notes.md against the generated list. Every behaviour change in the generated list needs a line in the notes or a written reason it does not.
    4. Check every version number against the number actually being cut.
    5. Check the register (docs/30-design/remedial/nightscout-backfix-register.md) for entries whose status moved since the draft was written, and for entries the release leaves open that the notes should name under "Known issues". Anything still live on the previous release is described by effect only.
    6. Check the commit messages that feed the generated changelog for claims the register has corrected.
    7. Re-cut the annotated tag from tag-message.txt if the text changed. A tag other people have already fetched is superseded, never moved.

    Nothing in this directory ships anything¶

    Writing a file here is not a release. A release is three separate human decisions:

    # Decision Reversible?
    1 Merge the code — a PR merge into dev (and the release PR into master) yes, git revert
    2 Push the tag — the tarball becomes downloadable effectively no
    3 Publish the package — npm publish no

    They are set out in docs/30-design/remedial/maintainer-release-brief-2026-09-15.md §2, with the commands a human runs. For nightscout-connect, decision 2, not decision 3, delivers the fix, because every cgm-remote-monitor pin is a GitHub tarball URL and none resolves from npm. For cgm-remote-monitor, a push to dev or master triggers a Docker image publish and is itself a publication event.

    Drafts. Require maintainer review before anything is tagged, published or relied upon. Nightscout is not a medical device and nothing in this directory is medical advice.
