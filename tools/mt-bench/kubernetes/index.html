    Kubernetes boundary for the M7 synthetic instrument¶

    Living document, last changed 2026-11-23 at 74793e4d3.

    This adapter prepares and observes one independently owned Kubernetes fixture. It reuses the existing M7 workload, stock client and oracles. Preparation and offline controls start no services. An operator or explicitly authorized experiment owner executes on the private environment's finite capacity, image delivery and trust allocation. Rendered resources do not grant correctness or capacity acceptance.

    The shipping application remains a secondary display for CGM and pump data. Run only synthetic tenants on independent state. A failed clinical, authority or tenant isolation check stops qualification. Preserve uncertain writes and raw evidence; do not retry a mutation to make a result green.

    Frozen-image experiments¶

    Use experiment.py to select an immutable source-owner receipt, materialize its binding, and prepare a new packet for each allocation. A manifest remains stable across namespaces, UIDs and deadlines. Its profile uses the existing workload profile format with the source selection supplied by the manifest. For example, the following selects an explicit candidate and a 1,000-tenant realistic profile. The input paths are absolute. Obtain the receipt digests from the releasing owners.

    K=tools/mt-bench/kubernetes
jq -n --slurpfile p "$K/workloads/realistic-1000.json" \
  --arg source "$SOURCE_RECEIPT" --arg ss "$SOURCE_RECEIPT_SHA256" \
  --arg build "$BUILD_RECEIPT" --arg bs "$BUILD_RECEIPT_SHA256" \
  --arg binding "$BINDING_COMMIT" --arg pg "$POSTGRES_CONFIG_ID" \
  '{version:1,kind:"k8s-frozen-experiment",sourceReceipt:{path:$source,sha256:$ss},
    buildReceipt:{path:$build,sha256:$bs},bindingCommit:$binding,postgresImageId:$pg,
    profile:($p[0] | del(.referencePins) | .workload.setupSeconds=360 |
             .workload.drainSeconds=180)}' > "$NEW_MANIFEST"
python3 -B "$K/experiment.py" describe "$NEW_MANIFEST"

    The execution owner renders the package with its private commissioning overlay. The accompanying private patch is supplied in the local release packet. Apply it to a clean copy of the indicated private base and install this release's frozen.py beside preflight.py. Set experimentManifest and experimentBindingReceipt in the environment to the respective {"path":"…","sha256":"…"} references. The existing context, trust, node placement, quota, headroom, cost and UID-conditioned cleanup checks apply. Private admin verification precedes serving roles.

    A binding with Job/verification publishes the admin proof in its completion log. Put that Job in stages/verification.json when preparing the case. The lifecycle waits for it before installing serving workloads and then launches the lab provisioning client. The attach phase reuses the captured proof and checks the native database source independently. The primer's private results live on its /run/ns-client volume.

    The primer verifies DATA credentials for the full population.provisionedTenants roster. Set population.ordinaryRosterTenants to the number of consecutive entries from the start of that roster that should receive ordinary k6 traffic. Select workload.offeredRps for an aggregate rate or workloadMix: realistic-v1 and workloadScale for per-tenant cadence. Both host k6 and the optional k6 Job use this selection. The stock probe assigns workload.logicalPollingClients across the full roster. Its probes, access checks and tenant-wide observers can reach tenants outside the ordinary subset. Storage checks require both k6 write counters for every selected tenant and query marker-tagged rows across the full database. An ordinary row on an unselected tenant fails the check. Probe writes on any provisioned tenant reconcile against the separate probe ledger.

    For a discovery fixture with an external producer, the optional manifest field pgstreamNotifierAckTimeoutMs selects a positive acknowledgment budget in milliseconds. The publisher projects the one field from the private bootstrap wire file before creating ns-config-pgstream. The selected package, source wire hash, effective wire hash and live producer incarnation are bound into the run. The controller verifies the wire hash in the owned Pod before native attachment. The producer binary, retry cadence, and clinical observation windows keep their selected source behavior.

    With --await-primer, prepare the packet before DATA credentials exist. The primer runs the image's checked source module inside the original verified waiting Pod and uses its private admin and DATA Services. It bounds execution by the earlier of the packet and active Job deadlines. The lifecycle sets the primer Job deadline to the remaining owner work budget when it releases the Job. An increased durable provisioned or DATA tenant count renews the matching stall window. An unchanged checkpoint, a retry and Pod readiness alone leave it running toward expiry. --concurrency N selects the source implementation's bounded concurrency. For fresh discovery, set profile.phases.primerOptions with concurrency and optionally maxTenants. For example, {"concurrency":64,"maxTenants":20000} selects up to 64 workers for a chunk of up to 20,000 pending tenants. The source starts no more workers than the pending chunk contains. With the extended source, both fields accept positive JavaScript safe integers. The defaults are one worker and 10,000 pending tenants per invocation. The image constructor checks the pinned parser and exact bytes before binding the selection. Legacy images refuse options beyond their supported range before resource creation. The waiting actor takes the bound selection automatically. Explicit arguments must match it. A partial DATA result stays incomplete and keeps its custody. Fresh discovery can also select profile.population.maxTenants, projected to the binding's populationCeiling and bootstrap's NS_DEMO_POPULATION_CEILING. Omission retains 10,000. An explicit selection requires the exact source protocol, image constructor and binding compatibility map, including a lower ceiling. Rendered inventory, the bootstrap environment and owned-container private-config readback must agree. Registry pages, LRU caches, file/Secret/IPC bytes, resources and clocks retain their independent contracts.

    Population and primer chunk sizing are separate. A 10,001 fresh seed with the default 10,000 pending-tenant chunk reports PARTIAL_CHUNK_BUDGET in populationCommissioning. Set profile.phases.primerOptions.maxTenants to 10,001 for one-invocation coverage budget. The effective chunk is exposed; the helper does not rewrite it. Constructor success grants no DATA completion or operating capacity, and incomplete DATA continues to refuse traffic. The successful receipt binds the privately exported DATA roster to the run, namespace, Job, Pod and container. Access and load verify this receipt. Preserve the source lock and uncertain-write journal after an interrupted request. A stalled attempt records its last observed count. While the same fixture and its private checkpoints remain available, repeat the primer command in the same packet to resume. The lifecycle releases the namespace at cleanup. After privately saving the complete roster and its receipt, the primer command acknowledges export and the waiting container can exit. A previously source-projected roster still uses the original prepare command.

    The lifecycle starts the split binding's platform bootstrap while Vault can still be sealed. Once the private admin proof succeeds it starts all serving roles, including pgstream, before releasing the tenant provision and DATA primer. The verified client's disk-backed state has no default size limit. Older bindings keep their own state representation.

    Scheduling requests and optional service limits¶

    For a fresh discovery fixture, select "resourceAccounting":"requests-v1" in the commissioning environment, binding overrides and runtime template. Use the same value in a matrix specification and its allocation grant. Inventory, preflight and lifecycle validation check this selection before expensive setup. Existing inputs that omit it retain limits-v1 accounting and capped behavior.

    In request mode, the binding removes reference per-container limits. A deliberate resources.<role>.limits override supplies exactly those optional limits; it does not inherit additional reference caps. Positive CPU, memory and ephemeral-storage requests remain necessary for this instrument's scheduling calculation. Each supplied limit must cover its corresponding request. Actual Pod readback records the returned resources and overhead, including LimitRange defaults. Kubernetes quota, LimitRange and the scheduler enforce those resources; the adapter compares the rest of the Pod spec independently.

    Namespace ResourceQuota readback compares exact numeric CPU, memory and ephemeral-storage quantities, including their requests.* and limits.* forms. For example, 4194304000 bytes and the API's canonical 4194304k are equal. Scheduling round-up is not used for this comparison: even a fractional budget change refuses. Hard-map keys, pod counts, scopes and other fields remain exact; unknown dimensions and masked values have no inferred equality. Resource readback refusals retain only the safe resource kind/name beside the code.

    Use a new copy of the released commissioner source with commissioning-accounting.patch. The patch header identifies the base source hash; retained instruments are unchanged. From the new staging directory containing bin/preflight.py, apply the patch with git apply /absolute/helper/tools/mt-bench/kubernetes/commissioning-accounting.patch. Select request accounting in its environment. Its namespace quota covers requests and existing no-provider-resource boundaries; limits.* quotas or LimitRange defaults that force hidden limits are refused. The preflight retains both requests and limits, with null for an unbounded limit dimension, and a separate accounted vector. Attachment uses the selected vector for its grant.

    To reuse a fixture across fresh standard namespaces, add --fixture reuse to experiment.py standard. The harness computes the fixture key (m7-joined/fixture_catalog.py: tenant count, --fixture-seed NAME, the core migrations tree at the image's core commit, the application and PostgreSQL image ids, the input transport, the populated-history spec and, for a K-bound transport, evaluator K) and looks it up in the local catalog ($NS_FIXTURE_CATALOG, default /mnt/data/nightscout-workspace/artifacts/fixtures/catalog.json, outside Git). On a hit the case restores that fixture: the controller creates the seed's Secrets, binds the retained handles in the new namespace (fixture.imported), clones the claims and starts through the ordinary provision Job and primer. On a miss it first runs a seed case at OUTPUT-seed (live, no traffic): it provisions and primes on four labelled claims (--storage-class, --snapshot-class), stops every role, snapshots the claims through CSI, sets their contents to Retain under the nightscout.org/fixture label, writes the handles, the original Secrets and the key to a private catalog directory, and registers it, then prepares the restore. --fixture build can build the seed ahead of time. A writer-driven case prefers an exact key. It can also reuse a seed from an ancestor core commit with the same tenant count, seed, history specification, transport and PostgreSQL image. A forward restore runs the provision Job's ordinary migrations and records the bootstrap result in fixture-forward.json before starting serving roles. Writer-driven fixtures can be used at different evaluator replica counts. Cleanup deletes the namespace and the run's labelled contents; fixture_copy.py delete DIR CONTEXT ends the fixture (the CSI driver deletes the provider snapshots) and retires its catalog entry. python3 m7-joined/fixture_catalog.py list shows the catalog. Snapshots and restored volumes are billed storage.
