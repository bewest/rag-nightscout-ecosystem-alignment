    Joined M7 capacity adapter¶

    Living document, last changed 2026-11-20 at c6082a7ed.

    This prepares the next measurement; it does not establish a capacity result. The prior capacity record and authorization/allocation profiles retain their own source scope. No prior working-tree lib mount or bootstrap patch is reused here. Only committed paired core/deployment sources can serve a run.

    A separate fresh-image diagnostic permits bounded useful tests before full acceptance without claiming acceptance or capacity.

    The coordinator must finish the coherent candidate and its full acceptance, then hand over a quiet host. This lane does not stop foreign containers, including a peer's nsauthz-base-n1000, or start a capacity campaign during other work.

    First pgstream sample¶

    Use the same prepare/deploy/run/down CLI below with --profile pgstream-sample, --tenants 2 (existing global bound 1–10000), --replicas 1, and --postgres-image sha256:EXACT_EXISTING_WAL2JSON_IMAGE_ID on prepare. Pass --backend-subnet and --edge-subnet together for owner-selected private CIDRs when Docker default address pools are exhausted. The binding validates syntax/overlap; the owner checks host availability. For the first diagnostic, use --run-purpose discovery and an existing joined-diagnostic / AUTHORIZED_DIAGNOSTIC receipt with exact pair/image/ instrument, functionalAcceptanceAtAuthorization: PENDING, and limits matching tenants, one API and selected load seconds. This route records UNACCEPTED metrics and cannot pass capacity/pilot/campaign acceptance. Accepted mode still requires the existing acceptance receipt. The owner supplies the exact pair and image. Discovery preparation checks both existing image IDs and the app's core/deploy labels before creating the cell or installing dependencies. A mismatch leaves the target absent; retain the command refusal separately. Successful preparation records imageInputPreflight in owner.json. Runtime/config/collector preflight still follows deployment. Baseline and candidate use separate directories, receipts and exact source/image arguments; neither substitutes for the other's attribution. Use --fixture-project ns-rest-joined-baseline (and a distinct candidate name) when preparing a new fixture for the REST helper. The selected name is passed to the existing source binding and retained in owner.json; defaults still use a unique generated name. Existing containers or orphaned volumes/networks under that project refuse before source staging. This option creates a new fixture; attach --project continues to bind an existing owner's fixture without changes. After source-driven deploy and preflight, pass the prepared cell directly as the REST attachment and its state directory as --state, with the same project and exact expected source/image. REST retains its own source allowlist and traffic authorization; selecting a fixture does not authorize a workload window. This selects writer-driven input (NS_INPUT_TRANSPORT=writer-driven), a 60-second sampler-disabled baseline, 120-second idle and 600-second ordinary load (ACCEL=1, HOT_FACTOR=1). A separate synthetic correctness uploader writes every 300 seconds. Its stored ID/glucose, durable completed versions/rows/frame and already-connected stock clients must agree. All workload writes also pass the independent count oracle and row-mutation control. No worker restart campaign runs in this sample. The selected startup and runtime roster omit the retired legacy feed-reader.

    Source helpers resolve only the cell-owned lockfile dependency tree; evaluator and realtime image processes independently check /opt/app pg resolution before load. Per-process CPU-counter bookends and RSS cover evaluator Node; process replacement/missing data is UNMEASURED. sql-attribution.json uses full private statement bookends for disjoint SQL-role buckets. A native recovery connection may use the configured pgstream role on the evaluator database. That role has a separate shared bucket, counted once; the exclusive pgstream bucket and the split between processes are UNMEASURED. The observer checks the selected recovery environment and database endpoint, rejects other overlapping identities, and retains actual per-role SQL totals. Historical disjoint-role captures retain their original two-bucket shape. The frozen PostgreSQL command preloads pg_stat_statements, enables top-level statement capture and I/O timing. Deploy creates the extension only in maintenance database postgres after infrastructure startup; an already-running server without the preload requires owner-controlled restart/recreation. Statement execution time is not PostgreSQL CPU or WAL-decoding CPU. A measured diagnostic cell establishes that sample; it grants no capacity acceptance or ceiling. Live sample behavior remains UNMEASURED until run.

    --warmup-seconds, --idle-seconds, --load-seconds, --accel, --hot-factor and --sampler-interval retain the selected values in the manifest. Short windows record incomplete nominal-cycle/timer coverage. No automatic sweep runs. attach accepts the prepare provenance arguments plus existing --project, --source-root, --state, --env-file and repeated --compose inputs. It binds metadata to exact existing container IDs/images/birth times without deployment or installation. --dependencies-root selects an explicit runtime-owned lockfile installation when the source links node_modules to a separate install; the historical default is the source root. Both package files must match the exact source commit, and stock-client and source module resolution remain confined to that installation. --runtime-owner /absolute/fixture/owner.json also binds a canonical prepared fixture's project/owner labels, source and dependency paths, image, lockfile and recorded generator provenance. Invocation working directories are retained separately from installed module identity; module bytes and tools must still match. Neither option installs dependencies or guesses a sibling root. For an attached fixture, down stops instrument jobs only; runtime cleanup remains with its owner. preflight CELL --k6-image ID checks the existing production modules/private config, SQL/roles, process/cgroup/sampler readability and k6 export interface before timed phases. Setup failures have separate retained attempts and preserve the deployment. Repair/rebind source or resource changes; never reuse old counters or resume into existing timed phase folders.

    run, direct readiness collection and each sampler window claim their output once with an exclusive attempt marker. Reusing a metadata directory refuses before overwriting its summary, bookend or collector files and writes a unique attempt-refusals/<id>/refusal.json. Use a new metadata-only attachment for a retry on the same owned runtime; preserve the original attempt and its provenance. Host commands default to this instrument's absolute root, and sampler commands use the absolute fixture directory. Explicit source-command working directories remain explicit. The sampler resolves its input paths before entering the first Compose file's accessible directory; an unavailable context refuses.

    Source and ownership¶

    adapter.py prepare creates a unique detached core worktree from a full commit, archives the deployment's committed Compose tree over its deployment directory, and writes the product build overlay marker. Every remaining core input must pass the shipping build's two-source admission. There is no borrowed node_modules: probe and source-helper dependencies use a separate owned install during preparation of the exact committed core package.json and lockfile with npm ci --include=dev --omit=optional --ignore-scripts --force. The serving image still prunes development dependencies. generator-provenance.json pins host Node/npm paths, hashes and versions, manifests, client entry/version/hash; actual stock-client resolution is checked before deployment traffic and each workload. The controller must preserve that host toolchain across cells/profiles. Preparation failures retain private prepare-commands/ raw stdout/stderr even before owner.json exists; prepare-failure.json contains only a sanitized error code. Generator installation output is private under generator-commands/. The image's core/deployment labels and immutable image ID are checked. Serving mounts cannot replace /opt/app or any subtree; all existing binding mounts must resolve within this cell's own private state. External/shared resources refuse. Ambient NS_/BENCH_/NODE_OPTIONS settings cannot silently alter the experiment.

    Every cell has a random project nonce, private worktree/state, randomly selected loopback port and ownership labels on its containers/networks/volumes. Cleanup verifies ownership before removing only that project and its recorded worktree. An ownership/source mismatch refuses rather than forcing cleanup. No attach mode or foreign teardown command exists. Raw state/config contains synthetic credentials; keep the entire work directory private and outside any checkout. Do not commit it.

    Build, deploy and traffic require a source-matched frozen acceptance receipt:

    {"kind":"joined-acceptance","status":"UNMEASURED","pair":{"core":"FULL_COMMITTED_CORE_SHA","deploy":"FULL_COMMITTED_DEPLOY_SHA"},"evidenceSha256":"SHA256_OF_COORDINATOR_ACCEPTANCE_RECORD"}

    The example deliberately refuses. The coordinator supplies PASS only after acceptance; provisional source heads are never silently substituted. The receipt is an attribution gate, not a new permission dialog. A build/initial deployment also requires load below the chosen quiet threshold and zero foreign running containers. During owned workload, foreign-container checks continue; the owned workload's own load average is measured instead of rejecting its expected CPU. Host inventories include container IDs/labels, image IDs, load, RAM, Docker/context, kernel and process names/CPU/RSS, never command arguments/environments. Only local Unix-socket Docker contexts are supported: host metrics must describe that daemon.

    Compose project and cleanup¶

    Every Compose call is docker compose -p <project> --env-file <run>/env -f <run>/frozen.compose.json, built by adapter.compose_prefix. The project name is unique to the run; cleanup is down -v on that project and one absence check on its label (decision simple-run-cleanup). The run records the alignment commit and image digest; no file, binding or epoch hashing precedes a Compose call (decision four-product-failures).

    JWT setup concurrency¶

    Local preparation, attachment and campaign commands accept --jwt-setup-concurrency 1..64, with serial default 1. The cell owner manifest and campaign record retain jwtSetupConcurrency; campaign resume refuses a changed selection. Both local k6 launch paths forward that value explicitly. The generated M7 workload preserves offered arrival rates, current nominal arrival timestamps, scenario attempt/response/transport counters, status fingerprinting and bounded setup-refusal evidence.

    Setup uses one response hook for serial requests and bounded batches. Refusal tenantIndex and requestOrdinal follow tenant roster order; they do not assert network dispatch order within a batch. Start and finish timestamps bound the chunk dispatch and subsequent response processing. Serial default retains a single-request bound. Batched refusal discovery can follow other exchanges in the same chunk. These observations do not measure per-response wire latency. Select a changed concurrency only when preparing a new coordinator-adopted run.

    Commands after the handoff¶

    Run from the alignment checkout containing the committed instrument:

    python3 tools/mt-bench/m7-joined/adapter.py prepare \
  --directory /absolute/private/m7-cell \
  --core-repo /absolute/core-repository --core-commit FULL_CORE_SHA \
  --deploy-repo /absolute/deploy-repository --deploy-commit FULL_DEPLOY_SHA \
  --image ns-m7:paired-image --freeze /absolute/private/frozen-acceptance.json \
  --tenants 1000 --replicas 1
python3 tools/mt-bench/m7-joined/adapter.py build /absolute/private/m7-cell
python3 tools/mt-bench/m7-joined/adapter.py deploy /absolute/private/m7-cell
python3 tools/mt-bench/m7-joined/adapter.py run /absolute/private/m7-cell --k6-image PINNED_OR_LOCALLY_RESOLVED_K6_IMAGE
python3 tools/mt-bench/m7-joined/adapter.py down /absolute/private/m7-cell

    The joined deployment starts admin and serving roles through Compose's completed bootstrap dependency. The lab client provisions through the private admin API and primes through DATA APIs. The harness reads its private primer/tenants.json and exchanges DATA tokens before starting k6.

    Set prepare.fixture to reuse (and optionally prepare.fixture-seed to a seed name) to start from a cold fixture found by key (fixture_catalog.py: tenant count, seed name, core migrations tree, application and PostgreSQL image ids, input transport, populated history and, for a K-bound transport, static-workers). On a catalog hit the runner restores that copy of PostgreSQL, Vault, private settings and primer state into the fresh Compose project. On a miss it first builds the fixture in a sibling point DIRECTORY-seed: an ordinary deploy (bootstrap, roles, provision, prime) without traffic, adapter.py fixture-capture (stop the project, deployment fixture.js snapshot into the catalog directory), cleanup, register. runner.py fixture-build CONFIG DIRECTORY builds and registers ahead of time. The point records the lookup in fixture-key.json and the restore in fixture-restore.json. A hand-named prepare.fixture-snapshot is refused. Vary the workload or viewers in each run; a different population or image is a different key.

    Instrument¶

    The run records the alignment commit and candidate image identities. Compose and Kubernetes execute the same joined probe with their respective SQL transports. The existing capacity/k6/workload.js supplies seven client shapes: CGM entry and Loop devicestatus uploaders, AAPS-style v3 treatments, and follower entry/devicestatus/treatment/status reads. The generated workload records two explicit adaptations: current deterministic nominal-arrival timestamps replace prior day-old timestamps (which could suppress current frame changes), and read4xx responses increment a functional refusal counter. Payloads and client route shapes are reused. Default cadence is real (one CGM cycle per 300 seconds), hot tenant factor10. Default idle600s/load900s. Two stock-browser polling sockets per tenant use JWT exchange and preserve stock reconnect behavior; retry-flood results are labelled separately. All sockets must prime before load.

    The capacity socket probe is generated from its tracked source with explicit, anchor-checked adaptations (and both hashes retained): actual replica-service restart roster, hot/cold write-to-frame distributions, strict initial priming, and sparse private runtime acquisition inspection replacing the prior lifecycle-lease proxy. New runtime ready && cycles>0 confirms acquisition in the restarted process; it is not clinical equivalence. Write stamp→durable evaluator checkpoint latency remains an independent per-write SQL observation with about1s resolution. Missing/oversized inspection fails as NO-INSTRUMENT, never falls back to leases.

    Inspection cadence is15s; payload byte totals, call counts and wall time are saved. Per-role Docker CPU/memory, process RSS snapshots, cgroup CPU/anon/memory.current, PG statement counts/time and waits/locks are retained. A60s sampler-disabled idle window precedes the600s sampled idle window; per-minute rates and collection costs let the reviewer assess observer overhead. Two-second sampler/controller and host probe CPU/RSS are recorded. Load samples are bounded by load timestamps; reconnect samples remain separate raw observations. Cgroup usage/anon and process RSS are named separately; no figure is described as JavaScript heap or hard process bound. pg_stat_statements lives only in the maintenance database to preserve application operation-window admission. No diagnostic extension enters the application DB.

    The same sampler also records host-io-metadata.json and host-io.jsonl without additional SQL. The small host observer samples at the selected interval (2s by default), independently of blocking Docker stats, with wall and monotonic read brackets. It retains aggregate CPU/iowait ticks, IO PSI some/full averages and totals, and raw disk counters for sysfs-identified physical leaves. Metadata gives device names/major-minor/sysfs paths, units and source documentation. Missing or changed sources are NO-INSTRUMENT, never zero. Match these timestamped samples to the actual cost-window bookends; do not claim simultaneous reads.

    These are shared host/device counters. Kernel disk request-time sums are not application or PostgreSQL latency, and device activity does not identify its cause. Guest-visible leaves do not establish backing physical media. No counter deltas, IO cause or capacity threshold is inferred by the collector. Counter reset, iowait decrease and hotplug limitations remain explicit in its metadata.

    Oracle and controls¶

    Client acknowledgements are compared with independent superuser SQL stored counts per tenant and domain/run marker. The oracle does not call the API. Empty workloads, unknown tenants or missing accepted totals cannot be green. Uncertain writes are reported and refuse a capacity pass. The adapter alters one owned synthetic stored row, requires RED, restores it in finally, and requires GREEN. A summary cannot claim a passing cell without complete metrics, primed/delivered/recovered sockets, observed runtime acquisition and the oracle control. No latency or CPU capacity threshold is invented; report those distributions and marginal costs as measured.

    Focused preparation only:

    python3 tools/mt-bench/m7-joined/test_contract.py -v

    The smoke owns one tiny PostgreSQL fixture and six synthetic HTTP accepted writes using the tracked payload functions under deterministic mocks. It proves the independent SQL oracle/control wiring, not k6 scheduling, product authorization, clinical behavior, full deployment, stock sockets or capacity. These remain UNMEASURED until the coordinator runs the frozen adapter on a quiet host.

    The restart observer rejects command failure or an unchanged container StartedAt; its own PG smoke control skips a restart, requires refusal, then actually restarts and observes a new process. Sharded placement additionally requires its committed controlled-replacement binding helper; raw restart is refused until that seam exists.

    Successful evaluator completion observer¶

    The current evaluator is a stream-fed bounded clinical materializer. Accepted input, completed clinical coverage and delivered client output are separate positions. A transport ACK requires durable acceptance; acquisition alone does not prove clinical completion. Current tenant/owner/restore authority, coherent transaction cohorts and subscribed raw mutation delivery remain required. Realtime consumes completed clinical output, while the raw mutation tail remains independent of bounded clinical membership. Bootstrap, cache loss, stream gaps and missing history may read SQL.

    Private inspection samples owner and foreign rows throughout ordinary traffic and at the end of drain. Runtime IDs, owner placement, counter rewinds, evaluator health and foreign work remain checked. The acceptance observer reconciles per-input acknowledgements against durable output and stored-write counts. Idle tenants owe no work. Run and gate configuration

    Restart recovery remains a separate bounded observation of changed process IDs and successful fresh acquisition. It does not establish clinical recovery by itself. The existing local under-demand recovery capability and operator drill own their stronger input/completion/authority/output checks.

    SQL snapshot request bounds¶

    The existing role totals and statement-list queries are unchanged. Each existing psql invocation now records adjacent host wall/monotonic start and finish values in before-sql-snapshot-timing.json / after-sql-snapshot-timing.json, including fixed status on failure. No extra query or polling is added. These are request brackets, not exact SQL execution instants. sql_counter_rate_bounds requires successful, nonoverlapping same-domain monotonic bounds and a nonnegative counter delta; it returns a range from the shortest/longest possible elapsed interval. Missing old timings remain unmeasured. Nominal120seconds or nearby cgroup times cannot substitute for SQL timestamps. SQL execution time remains distinct from database-role CPU; wall stamps support correlation, not a cross-host clock claim.

    Discovery runs¶

    prepare --run-purpose discovery freezes an explicit observational route; acceptance remains the default. Discovery preserves evaluator source and scope verdicts, including UNMEASURED and failed work-completion counters, and executes the existing bounded HTTP load despite incomplete socket priming. Missing .window stops/drains the owned probe before HTTP load; it does not manufacture a restart or probe-count proof. The original workload, deadlines and cadence are retained. Failed HTTP requests, dropped iterations, dark sockets and recovery timeouts are outcomes rather than performance SLOs.

    check-discovery <summary.json> accepts only the explicit discovery cell or aggregate shape, matching source/image/profile/ownership identity and no known hard safety violation. Status MEASURED means complete observations; PARTIAL retains absent measurements. Both carry capacityAcceptance: NOT_GRANTED and cannot pass check-pilot or check-campaign. Known wrong stored counts, foreign/source/reset/custody violations, invalid settings fingerprints and explicit unsafe output remain refusals. A failed evaluator completion counter alone is preserved as a FAIL finding, not classified as unsafe clinical output.

    The independent count oracle retains ACK <= stored <= ACK + uncertain. Missing ack metadata is UNMEASURED, never zero; known per-tenant/domain bounds and foreign scope still refuse even with other fields missing. Probe counts are separately UNMEASURED when fanout metadata is absent. Raw process exits, probe partials, strict progress artifacts and existing AFTER bookends are retained on failure. A timed-out k6 CLI requires an exact owned-container stop before recovery. No observation route grants functional or capacity acceptance.

    Recording controls: python3 -m unittest discover -s tools/mt-bench/m7-joined -p test_discovery.py (join the command on one line). The optional discovery-transport-control.py --repo <transport> --commit <full commit> tests the actual Record producer against an immutable transport validator without executing commands, applications or networks.

    Discovery classifies partial load observations separately. A missing midpoint may continue only with a current-source, correctly attributed, fixed-phase 1/2-round artifact; its available owner/foreign/reset/selector/budget invariants still apply (and idle clock brackets, when present in that source schema). Zero/extra rounds, wrong phase/source and unknown or malformed observations refuse. This validates available observations only: it creates no missing round or completed-work credit. The two previously declared work-error findings remain soft even with FAIL; timing-code FAIL and all structural/source/owner/clock failures stay hard.

    Discovery probe counts use the separately versioned probe-accounting.json ledger (v2). Each attempt is persisted before HTTP; each tenant retains accepted (200), uncertain (status 0 or 5xx), definitely refused, and pending counts. Admission closes before awaiting all writers. A complete proof requires that closure and zero pending attempts; interruption/open admission remains UNMEASURED. No pending write is silently converted to zero. The frozen helper is copied and hash-checked with the generated probe, and bounds the roster to 10,000 and attempts to 100,000. Partial ledger snapshots add host file I/O per probe attempt/completion; they add no HTTP or SQL requests.

    Discovery checks accepted <= stored <= accepted + uncertain independently for each tenant's probe actor, alongside the existing workload/domain and tenant scope checks. Another tenant's uncertainty grants no allowance. A definite refusal grants none. Legacy ACK-only metadata cannot establish an upper bound: missing acknowledged rows still refuse, while missing uncertainty remains probe-specific UNMEASURED. Original historical failures are unchanged.

    stored-counts.json, oracle-findings.json and bounded failure diagnostics are retained before a known violation throws. The existing resource reducer reads already captured files even on that refusal; it adds no queries. Wrong roster, run identity, negative/mismatched attempt totals or ACK disagreement refuse before the count SQL. Strict acceptance retains its original exact probe oracle. Focused controls: PYTHONPATH=tools/mt-bench/m7-joined python3 -m unittest test_probe_counts test_discovery test_discovery_classification (one line). The loopback control starts one finite local HTTP server with in-memory synthetic persistence, exercises actual generated request/callback code for committed 503 and delayed-response timeout, and closes all its sockets. It proves accounting behavior, not PostgreSQL or application correctness.

    Discovery reads counter count fields explicitly (flat or nested values). Absent fields remain UNMEASURED, including a present empty object; they never become zero. Present malformed, boolean, negative, fractional or nonfinite counts refuse before the existing count query. Finite integral numeric counts within JavaScript's safe integer range are preserved. The acceptance metric helper is unchanged.

    Source-bound completion readers¶

    New pgstream-sample preparations and attachments select --completion-contract evaluator-work-v1 for the legacy JSON work state or --completion-contract evaluator-work-v2 for typed work state. The selection is stored in the owner manifest. Sample preflight binds it to the exact core, deploy, image and instrument identities. It does not infer a version from a missing column or fall back after a query failure. Existing captures remain unchanged and require their original instrument to resume.

    The v2 witness reads work arrays and output metadata columns with the clinical JSON body in one SELECT snapshot. Versions are decimal strings, including array elements. NULL means a source version is missing. The fixed array order is clock, settings, policy, activity, lifecycle, bootstrap. Its assessor checks row kind, work version, contract digest, array bounds/order, exact bigint range, output revision precision and metadata ownership before the existing stored write, BG-now and stock-client frame checks. It performs no duplicate writes.

    Current native configurations select the compact-input reader from the actual pgstream.generation and recovery configuration. One SELECT binds input source identity and restore generation, recoverable WAL positions, the local input floor, completed clinical coverage, pending/due work, output metadata and raw-tail head/base. The public history stamp is observed separately. Clinical completion can advance while an unchanged output keeps its original captured input floor and revision. Explicit lifecycle invalidation may reset the snapshot position to 0/0; accepted commit positions retain their own source, generation and coverage fences. The reader checks the actual stored marker, BG-now result and stock callback; metadata alone does not qualify clinical equivalence or raw delivery.

    The unqualified selected-intake/profile reader and its mechanism-only control are removed. Original v1/v2 readers remain for historical source fixtures and retained baseline reproduction. A native configuration cannot fall back to them when its source/restore/coverage proof is missing.

    Client delivery is per logical viewer. Reconnection alone does not refute a valid callback. New captures retain the exact expected viewer slots, observed transport incarnation, connection count, SGV identity/time/value and a single-probe monotonic request-to-callback deadline. Missing, duplicate, foreign, wrong-value or late callbacks refuse. The historical hold4000 failure stays unchanged: retained callbacks show timely stored-ID delivery, but omit connection counts and full callback values needed to identify its strict-predicate rejection.

    Bounded commissioning on a fresh capacity point¶

    prepare --primer-concurrency N records a worker bound from 1 to 32. Default 1 keeps the serial primer command. A larger bound adds --concurrency N only to the commissioning phase; stage timeouts, API sequence and worker startup order stay the same. The selected deployment and qualified image must contain the bounded primer. Never copy a newer primer into an accepted image or change the instrument of an existing attachment.

    Use a fresh point with its full selected seed. Extending provisioned.json and tenants.json alone does not revise the seed, settings fingerprint or published operator roster. A resumed fixture and a cold commissioning run have different setup costs.

    For concurrent commissioning, deployment records primer-start.json and reads primer-counts.private.json before starting the remaining roles. The latter checks the exact seed, provisioned and accepted custody rosters, completion and uncertainty state, then independently counts synthetic commissioning entries in PostgreSQL. Each selected tenant must have exactly one entry. Accepted custody means a successful HTTP response saved by the primer, not an HTTP attempt count. The count query and raw per-tenant output stay in the private run workspace. Call adapter.primer_counts(fixture, owner) after the prime phase when using the existing canonical command packet instead of adapter deploy.

    Focused file/SQL-shape controls run without a database:

    cd tools/mt-bench/m7-joined
python3 -B -m unittest test_primer_adoption test_contract

    These controls cover count assessment and command wiring. Live database execution and speedup at bounds 2 or 4 remain measurements for the next qualified point.

    For a rate curve on one qualified cohort, prepare or a new attach may select --offered-rps 120 in pgstream-sample discovery mode. This changes the shared arrival cycle for the same seven request shapes and tenant weighting; it does not change stock-client count, payloads, credentials, authority or write oracles. Write timestamps follow the selected arrival cycle. Ordinary cadence remains the default. The owner and discovery result retain the requested rate and the effective rate after millisecond rounding.

    scenario_request_attempts counts entry into the load HTTP call; scenario_http_responses counts returned HTTP responses; scenario_transport_failures counts calls returning without an HTTP status. An attempt does not establish a server receipt or a successful write. Credential exchanges in setup and stock-client probes remain separate from this scenario target. Keep accepted/persisted writes and evaluator/client witnesses separate. Raw k6 iterations and dropped_iterations remain distinct; a metric absent from the capture stays unmeasured.

    Clinical sender and early-request diagnostic (source qualified)¶

    The clinical completion criterion remains open. This instrument separates the actual maintained Go notifier's message admission/handoff, each HTTP attempt, Node's first request-handler entry and later selected-row parsing. It is source instrumentation, not a product optimization or a capacity result. No native run, image or resource slot is selected by this implementation.

    Raw bounds are 32,768 rows, 8 MiB and 128 pending writes, separate from the existing 4,096-row/2 MiB selected trace. Saturation, short writes, pending drain, missing status or an entry without an abort/response terminal record is UNMEASURED. Retention verifies the record count, byte count, sequence, instance/PID, permitted fields and lifecycle coverage. Status fields are mandatory with exact types and ranges; missing counters and falsey substitutes never mean zero. Each raw phase has an exact field schema, typed lifecycle flags, bounded numeric connection/port fields and consistent request identity. Response finish requires finished:true; response close with finished:false and explicit abort remain valid capture observations. A request-close alone is not a response terminal. Selected capture counts and its optional seal also match the retained bytes. COMPLETE here describes metadata capture; it does not prove target delivery or clinical completion. Node entry is a JavaScript handler boundary, not socket or kernel arrival. Malformed selected-row inspection forwards to the actual receiver's validation and preserves its rejection.

    Authored resource and nginx allocations¶

    Retired 2026-11-19: the diagnostic-resource-profile and diagnostic-resource-allocation options were deleted; Compose services always run uncapped and the host's MemAvailable is recorded once at run entry (run-before-host.json). The text below is historical.

    --diagnostic-resource-allocation accepts one exact version-1 JSON allocation with services, driver, ceiling and edge fields. It replaces reference CPU/memory sizing when preparing a fresh fixture. Named profiles retain their exact sizes. The service roster must match the rendered fixture, including its existing supported role names and ordinal range. There is no separate 32-service, 64-CPU or 128-GiB reference ceiling for an authored allocation. Every selected role, declared bootstrap/primer overlap and standalone driver still counts against the authored aggregate ceiling. Remote receiving helpers additionally check the actual declared SUT and driver host inventories independently.

    Fresh authored service allocations use integer cpu_quota and cpu_period fields. Compose's float32 cpus field can round a selected value, and its native conversion can lose precision even when config JSON looks unchanged. The integer path preserves integer quota/period through Compose; native runtime precision requires a separate check. Native readback requires zero NanoCpus, exact quota/period and no alternate CPU limiter. Named profiles and entered legacy explicit fixtures keep their existing cpus/NanoCpus path; standalone Docker --cpus keeps its exact decimal CLI path. The frozen config selects the mechanism, so legacy records are not migrated during an entered run.

    Each new service record includes cpuEnforcement with quota and period in microseconds. Fresh ordinary allocations keep a 100,000-microsecond period. Values from 1 through 9 millicpu use 1,000,000 microseconds to meet Linux's minimum 1,000-microsecond quota, where the runtime can represent that average. Very large fresh values use a 1,000-microsecond period before quota exceeds 9,223,372,036,854 microseconds: runc 1.3.3's systemd conversion multiplies signed quota by 1,000,000 before division. These recorded period changes preserve the selected CPU average but change scheduling granularity. Entered quota records keep their frozen period; validation and census never select a new one. The Linux 6.18 source defines max_bw_runtime_us=MAX_BW, with BW_SHIFT=20 and MAX_BW=(1<<(64-BW_SHIFT))-1; at a 1,000-microsecond period, that necessary service maximum is 17,592,186,044,415 millicpu. This read-derived kernel representation bound is separate from host fit and actual kernel admission. The kernel validation and bandwidth representation own those limits. Docker also validates the period and minimum quota and carries explicit quota/period directly into its OCI CPU resources.

    Actual fresh preparation reads the selected daemon's cgroup driver/version, default runtime and reported runc version before resource leases or fixture effects. This early observation does not qualify every template role. After source rendering, the existing deployment stages and their transitive Compose dependencies select the actual execution roles for precision qualification, before any container command. An ops profile alone does not make a role active: bootstrap and primer run in these stages; unused demo/operator templates may remain dormant. All authored roles still count against the aggregate ledger. The confirmed systemd/cgroup-v2 path with runc 1.3.3 or 1.3.3-0ubuntu1~24.04.3 rounds CPU bandwidth up to whole percent units. Its runc conversion therefore represents service CPU only in multiples of 10 millicpu. It also requires quota times 1,000,000 to fit signed int64. Preparation refuses an affected field with its requested value, runtime and representation reason; the stable CLI code retains the field suffix, and a bounded JSON diagnostic reaches the runner's retained private preparation output. It never rounds the selection. For example, 65.001 CPU is unsupported on this path while 65.01 CPU is representable. A different period cannot change that ratio precision. Retained native controls observed 65.01 CPU for the requested 65.001 CPU at both 100-ms and 1-second periods, despite exact HostConfig values; both strict failures and owned cleanup remain recorded under the lane's overflow-disk evidence. This is a runtime capability, not a reference CPU cap.

    Pure configuration/receipt plans never query the daemon. Missing inventory, other drivers and unqualified runtime versions retain runtime precision as UNMEASURED; they do not acquire this runtime-specific restriction or a native pass. A fresh explicit owner's cpuPrecisionPreflight records qualifiedRoles and deferredRoles, the execution-scoped PASS or UNMEASURED, and the classified runtime when available. A deferred role keeps its exact authored allocation and remains unqualified. The existing Compose actor admission guard checks requested targets, dependencies and already active quota roles before each actor command, including later activation of a dormant template. Existing --no-deps selections retain their dependency semantics; read-only commands and exact-owned cleanup remain available after refusal. Named profiles, entered legacy fixtures and standalone --cpus keep their existing paths. Exact native admission/readback remains required.

    Standalone driver CPU must fit Docker's signed-64-bit NanoCpus field; service and driver memory must fit its signed-64-bit byte fields. The current memory-unit contract starts at one MiB. Native engine and kernel admission and exact quota readback remain required. An accepted numeric JSON allocation does not reserve CPUs, enlarge host inventory or establish memory headroom. Docker's container resource API defines the native field representations.

    An authored edge selects independent positive integer workerProcesses and workerConnections. The helper first runs the pinned deployment renderer with its existing reference worker settings. It then projects only those two unique numeric directives into the owned mounted nginx config, before capturing its digest. All routing, public Host handling, header trust and handshake admission bytes remain source-rendered. An unexpected baseline, duplicate directive or changed descriptor budget refuses. Named-profile output remains unchanged. The existing runtime nginx -T readback must match the selected numeric values and the retained worker_rlimit_nofile 65536 directive.

    The Linux nginx implementation has a total process-table bound of 1,024 child slots, shared by workers, optional cache helpers and overlapping generations during reload. This is a necessary implementation maximum, not a promise of 1,024 available worker slots or evidence that those workers started. The process table and worker/helper/reload paths own that read-derived boundary. Actual process births, cgroup PID limits and effective OS descriptor limits need observation in the selected environment. Configured workerConnections cannot exceed the retained actor's 65,536-file descriptor directive and Compose nginx.ulimits.nofile hard limit. A larger request reports ALLOCATION_EDGE_DESCRIPTOR_LIMIT; extending it requires an explicit descriptor budget, mounted-config and Compose-ulimit projection, and effective descriptor readback. Connections include upstream connections and consume descriptors for other work too, so the configured value does not prove a client capacity. See nginx's connection and descriptor directives.

    The Python remote receiver uses the same explicit numeric contract and retains physical-host fit. Older remote controllers can still lack explicit allocation support or retain their own reference validation. Their precise source guard must be extended by the controller owner before using those values through that controller; local rendering and receiver controls do not establish a remote run. The existing restriction policy separates these instrument boundaries from application and acceptance claims.
