# Reuse the canonical local runner

`runner.py` replaces copied per-attempt preparation and execution scripts with
one configuration and the existing `adapter.py` entrypoints. It does not build
an image, allocate a remote host or grant capacity acceptance.

For new runs on this workstation, use the overflow-disk storage layout in
`AGENTS.md`. Keep helpers under the appropriate
`/mnt/data/nightscout-workspace/worktrees/` directory and select outputs under
`/mnt/data/nightscout-workspace/artifacts/<lane>/<run>`. The directory arguments
below are explicit storage choices, not automatic runner defaults. A missing or
unwritable `/mnt/data` is a storage error; do not fall back to the home drive.
Existing runs and their original guards keep their current paths.

Copy [the small rehearsal profile](examples/local-rehearsal.json) to private
storage. Set its verified helper head, repository paths, existing diagnostic
receipt, new project and unused explicit CIDRs. The receipt still binds the
source pair, image, instrument and traffic duration through the adapter's
existing contract. Reusing a qualified app/image does not require rebuilding
that image or running application acceptance for a tenant/RPS change.

For new configurations, run `python3 -B tools/mt-bench/m7-joined/runner.py identity`
from the committed helper, then replace `helperHead` in the configuration with
the returned `helperInstrument` field. Choose exactly one pin. Content pinning
permits the same executed bytes at another commit; the adapter still records the
actual commit. Markdown documentation is excluded from the instrument digest.
Changed executable/configuration inputs remain pinned and dirty inputs refuse.
Existing `helperHead` configurations keep their exact-commit behavior. This new
manifest definition applies only to new captures; old runs keep their original
helper, receipts and attribution. Do not change helpers under a live guard.

The adapter preflight still checks required source/runtime and instrument paths.
Optional realtime cost-counter gaps are saved in `preflight-observations.json`
as `NO-INSTRUMENT`; they do not ban discovery traffic or become measured zeros.
These counter observations grant no acceptance. Shared-host discovery already
records contention without requiring other agents to stop their containers.

```bash
python3 -B tools/mt-bench/m7-joined/runner.py prepare \
  /absolute/private/run.json /mnt/data/nightscout-workspace/artifacts/example-lane/run01
python3 -B tools/mt-bench/m7-joined/runner.py rehearse \
  /mnt/data/nightscout-workspace/artifacts/example-lane/run01
python3 -B tools/mt-bench/m7-joined/runner.py result \
  /mnt/data/nightscout-workspace/artifacts/example-lane/run01
```

Use the qualified Node/npm paths in `PATH`. `prepare` stages canonical source,
configuration, probe, workload and owned dependencies. It starts no services.
`rehearse` performs canonical deploy, real instrument preflight, a generated
program failure control, ordinary tiny traffic, collection, reduction and
cleanup. The control omits the required probe URL, checks Node's actual
`ERR_INVALID_URL` refusal before network I/O, then the normal caller runs the
same unmodified generated bytes. `execute` runs the same path without that
intentional refusal. Neither action retries a phase.

The example uses two synthetic tenants, four stock clients, serial JWT setup
and 1 offered scenario request/s. Its work window is finite; its independent
guard stops an active stage and invokes the adapter's owned-project cleanup at
the deadline. The runner checks process birth and group before escalating a
stage that ignores TERM. Normal completion also cleans up. Explicit cleanup is:

```bash
python3 -B tools/mt-bench/m7-joined/runner.py down /mnt/data/nightscout-workspace/artifacts/example-lane/run01
```

Keep the helper source fixed while a run or its guard is live. Cleanup retains
the adapter's ownership and source checks. It never stops peer services.
`result.json` records the phase, native adapter status, traffic phase, process
failures and cleanup outcome. Native summaries, readiness, recent role logs and
collector outputs remain private artifacts. A missing scenario counter stays
unknown; zero scenario attempts with HTTP setup exchanges is setup-only data.
`COMPLETED_PARTIAL` means the pipeline returned with a partial adapter result;
it is not a successful application or capacity claim.

clock is subtracted. A missing/invalid row gives no negative bound. Query count,

not all ordinary writes or isolated executor latency. Client-frame timings match

The old `writeToEvaluationMs` is a combined durable-plus-client polling witness

Local configuration uses the existing `prepare` object. For example, change a
private copy of the rehearsal profile to these values and run the same
`runner.py prepare`, `execute` and `result` commands:

```json
{"tenants":37,"offered-rps":73,"warmup-seconds":3,"idle-seconds":4,
 "load-seconds":45,"probe-every-ms":1000,"sockets-per-tenant":3}
```

Those fields alter synthetic work and observations, not the application image.
The same supported source/image, current source-matched receipt and finite
execution/cleanup window still apply. The new client count is explicit; offered
scenario rate remains independent from client population. Ordinary five-minute
probe cadence remains the default; comparisons that select a shorter cadence
must record it. No application rebuild or full acceptance follows a reporting,
tenant, rate or client-count change.

Remote calibration keeps its existing strict default and exact source/image
presets. A future remote discovery binding explicitly selects
`"reportMode":"discovery"`; its authorization receipt must select
`"remoteReportMode":"discovery"` and contain that exact `remoteWorkload`.
The existing controller config supplies the binding and receipt. For the same
work above, its existing `workload.cadence` selects `warmupSeconds:3`,
`idleSeconds:4`, `loadSeconds:45`, `offeredRps:73`, `probeEveryMs:1000`,
`socketsPerTenant:3`, with ordinary `accel:1`, `hotFactor:1`,
`samplerIntervalSeconds:2` and `restart:false`. Set the binding's `tenants:37`
and its existing resource plan's `tenants:37` and `logicalPollingClients:111`.
Retain the actual host identities and selected primer concurrency in that plan.
These are configuration examples, not new authorization or measured headroom.

To vary the total independently, add `"logical-polling-clients":2` to local
`prepare` for a 37-tenant roster. This discovery-only integer accepts zero or a
positive JavaScript array length, through 4,294,967,295. This representation
bound does not establish memory or connection capacity.
When omitted, `sockets-per-tenant` keeps its existing default and behavior.
Remote discovery uses the existing `resourcePlan.logicalPollingClients` as the
total; the controller's `logicalPollingClients` mirror and receipt must match.
Do not add a second total to remote cadence. The worker forwards the total to
the same local parser only when it differs from the legacy per-tenant product.

The first `total % tenants` roster entries receive one additional viewer over
`floor(total / tenants)`. Viewer IDs follow tenant-major opening order. Zero
opens no sockets and exchanges no probe-viewer JWTs; ordinary traffic and its
independent stored-write/output checks still run. Frame evidence reports
`NOT_EXERCISED` when selected writes have no viewers, including a zero total.
Reducers derive frame expectations from this plan and per-tenant accepted probe
writes, validate every emitted viewer binding and keep stored/output/authority
checks separate. Changing load does not extend source/image/deadline or budget
authority, and does not alter an already entered run.

Compose and native Kubernetes discovery resolve positive roster sizes and hot
weights within the generated JavaScript arrays' combined length limit. Finite
phase durations must fit k6's Go duration representation; the work window must
cover the selected phases. Offered rates must produce a positive representable
k6 time unit. These are planning contracts. The selected source provisioner,
role configuration, available resources and actual authority still govern
execution. Source/image identity and fixed acceptance profiles stay exact.
Each experiment keeps its selected source/image tuple and its own receipts.

The actual public probe accounting helper is exported with a hash and checked
before driver installation. It records admitted, accepted, uncertain, refused
and pending writes without SQL or provider authority. The existing collector
retains its ledger and generator process results alongside probe/fanout/k6
artifacts. Discovery summaries remain `PARTIAL`, with no capacity acceptance;
HTTP failures, incomplete clients, failed processes and missing optional metrics
remain observations. Source/ownership mismatches, observed wrong data, clinical
failures and invalid metadata still fail. Strict reporting retains its original
full-client, zero-failure and required-metric checks. REST metrics, sampled client
frame times and SUT completion observations remain separate; remote output timing
is `UNMEASURED` and no cross-host clock subtraction is used.

## Finite experiment batches

`runner.py batch-plan <batch.json> --payload-root <absolute-private-directory>`
prints a deterministic review plan without starting services. `batch-run
<batch.json> <new-private-output> --payload-root <absolute-private-directory>`
executes that same admitted specification. `batch-result <private-output>` reads
completed and partial per-cell results, including after an interrupted batch.
The ordinary single-point commands and their defaults stay available.

Before copying a cell's resource fields, run:

```bash
python3 -B tools/mt-bench/m7-joined/runner.py batch-resources /absolute/private/run.json
```

This validates the ordinary runner configuration and prints `resources` plus the
allocation breakdown without starting actors. Copy `resources` to the cell and
set the batch envelope for the desired concurrency. Then `batch-plan` checks the
complete payload, workload, isolation and aggregate bounds. These commands grant
no infrastructure or spending authority.

Start from [the local batch template](examples/local-batch.json). Replace its
source/helper/receipt paths and hashes, project/CIDRs and zero cleanup cutoff
with the reviewed inputs and original absolute cutoff; the template is inert.
Both cells reuse the same immutable source/image/helper. The template declares
room for two whole cells. Set its aggregate envelope to the resources allocated
to your lane; a smaller envelope queues cells without reducing their quotas.

Batch digests use the [shared canonical vectors](examples/batch-digest-vectors.json).
Numbers must be finite; integral numbers must fit the exact shared range
−9007199254740991 through 9007199254740991. Negative zero becomes zero,
and `1.0` and `1` have one identity. Payload bytes are never transformed.

The common version 1 batch structure is shared with the deployment controller's
`pgstream-caller.mjs` batch API. A batch contains explicit cells; expand an R&D
matrix into cells before review rather than submitting executable generators.
Each `cell.config` is an ordinary runner configuration locally, or an existing
remote caller specification remotely. Local and remote batches have the same
review fields; each backend still checks its own typed runtime contract.

| Field | Meaning |
|---|---|
| `version`, `id` | Version 1 and a unique lowercase batch name |
| `payload.source` | Exact `core` and `deploy` Git commits |
| `payload.image`, `payload.helper` | Immutable image ID and executed helper content hash; remote helper is its extension hash |
| `payload.files` | Explicit relative `{path, sha256}` allowlist under the private payload root; local receipts must be included; symlinks refuse |
| `envelope` | `maxConcurrent`, aggregate `millicpus`, `memoryBytes`, `heapMiB`, `hourlyMicrousd`, `totalMicrousd`, `maxLiveResources`, `maxOfferedRps`, and absolute Unix-seconds `cleanupAt` |
| `envelope.workload` | Inclusive `[minimum, maximum]` bounds for `tenants`, `offeredRps`, `durationSeconds`, `probeEveryMs`, `hotFactor`; explicit `faultCases` allowlist |
| `cells[]` | Unique `id`, `namespace`, `ports`, `subnets`, `target`, `resources`, `offeredRps`, `workSeconds`, `cleanupSeconds`, and `config` |
| `cell.resources` | Whole-cell `millicpus`, `memoryBytes`, `heapMiB`, `hourlyMicrousd`, `totalMicrousd`, `liveResources`; costs use integral millionths of USD |

For local cells, `target` is `{"kind":"local"}`, ports are empty (no host-port
configuration is supported by this runner), and subnets exactly match the
configuration's backend and edge CIDRs. Names and CIDRs cannot overlap another
cell, even when cells run sequentially. The existing adapter performs its fresh
host census before effects. Local cells use any existing named diagnostic profile or an explicit
`diagnostic-resource-allocation`, with the same adapter selection and topology
checks as a direct run. A cell must reserve at least the selected CPU/memory
ceiling, host V8 heaps and managed-resource allowance. Larger authored
reservations are valid; the batch envelope remains the aggregate bound. An
explicit allocation supplies its own driver limits and is not capped by the
old local reference reservation.

Named profiles retain their server limits, while discovery replaces their old
500-millicpu/1-GiB k6 default with the existing 2000-millicpu/4-GiB driver. The
planner includes that delta. For example, the named 4-CPU/8-GiB profile requires
5500 millicpus and 11811160064 memory bytes for the complete discovery cell,
plus 1024 MiB host V8 heaps, zero money and a conservative 64 managed resources.
Use `batch-resources` for the selected configuration instead of repeating this
arithmetic. Profile names describe their original reference allocation.

The allocation breakdown uses the selected ceiling as a conservative upper
bound for SUT roles and declared oneoffs; it does not claim they consume that
amount simultaneously. Host heaps include helper, generator and probe overlaps.
Host RSS/native memory remains separately observed; a V8 heap limit does not
bound RSS. The caller keeps the aggregate envelope within its lane allocation.
Concurrent cells share the host: record contention in comparisons. The scheduler
accounts declared maxima; it does not reserve a quiet machine, establish physical
CPU demand or bound host RSS. Phase-specific lower reservations require matching
producer enforcement and focused controls.

Each batch holds the original UID-global driver lock and atomically reserves
whole cells in a private ledger. Only a live exact-birth coordinator and matching
nonce can authorize a child driver to use its own cell heap lock. This retains
legacy-driver exclusion, per-cell native quota/census checks and stale-marker
refusal. It does not rename the global lock to pretend aggregate admission.
The unchanged independent guard owns each cell's finite cleanup window, starting
with preparation; the batch cutoff never extends it. Source-loader preflight now
runs automatically during batch preparation before services. A failed cell keeps
its private phase and partial outputs. Admission continues for independent cells
when their reservations fit. Unconfirmed cleanup retains its entire reservation.
A child rechecks the ticket's absolute cleanup cutoff before preparation, so
process-launch delay cannot silently authorize a fresh full window.
Coordinator death leaves custody markers intact for explicit exact-resource
reconciliation; PID expiry alone never frees resources.

SIGINT/SIGTERM stops new admissions while entered cells finish their original
finite cleanup. Reservations release only after the child returns, the original
guard is absent, adapter cleanup records exact absence and the cell heap marker
is empty under exclusive lock. No other cell's reservation or resource is
released. Changing payload bytes or source/image/helper pins refuses before a
new cell starts. Raw logs, tickets, namespaces, process births and ledgers stay
in ignored private output, not the public repository.

Local batch configurations use existing tenant/rate/duration/cadence/hot-factor
options and preserve the adapter's required correctness oracles. Ordinary local
batches currently require an empty fault allowlist; unsupported fault cases
refuse. Remote component cases retain their existing typed implementation.
Optional counters and generator headroom remain UNMEASURED when unavailable.
A constrained generator can limit offered load; that is not a product capacity
measurement. Every batch result keeps `capacityAcceptance: NOT_GRANTED`.
Parameter changes inside the declared envelope use the same tool and focused
input checks; they do not trigger an application rebuild or full acceptance.

A reviewable batch plan does not grant remote spending, export or tool permission.
Remote plans must disclose their payload allowlist and exact provider destinations
and use the existing authoritative budget/custody hooks. Paid allocation and
transport remain with the remote owner. Independent remote pairs retain exact
unconditional deletion; retaining a pair across cells is a separate reset and
rig-ownership capability. Active experiments stay pinned to their original tools.

Scheduling checks use the real local caller/process/ticket/flock path with
synthetic prepare/execute actors, and the remote caller with synthetic root hooks.
They qualify admission, overlap, failure isolation and custody, not application
capacity or a native live provider gateway. Remote batches reuse verified sealed
input directories; `batch-run` does not call `bundle` or export images again.
Changed inputs require their own matching source/image/helper pins and hashes.
Remote cleanup uncertainty retains accounting while other eligible pairs proceed;
reservation/authority uncertainty stops admission. Per-cell deadlines skip only
the expired cell; the common cutoff leaves no cell eligible. Native approval
message lookup/provider installation remains UNMEASURED here and belongs to the
remote custodian; source adapters do not grant tool permissions.

serving. Remote targets refuse; no provider or paid gateway is added.

(256, 512 or 1024). Unknown fields refuse. Each cell declares one unused explicit
loopback port and an empty subnet list; it uses the existing Docker bridge,
without creating or deleting a network. Names and ports still pass common batch
isolation checks. `offeredRps` is zero because this producer has no application
load driver; Vault work is bounded by target sets and four-worker concurrency,
not an asserted zero provider-request rate. The shared workload axes bound
`tenants` as component set count and `durationSeconds` as the work window;
`probeEveryMs` is the inapplicable fixed zero and `hotFactor` is fixed one.
Fault cases remain unsupported.

The capsule has exact fields `version`, `producer`, `source`, `image`, `imageId`,

matching image ID. Tools are exact resolved `node` and `docker` paths, hashes and
version receipts; Node is 24.22.1. The executor verifies them before SUT effects,

are created in memory and sent to the fixed worker over stdin only.

measurements with exact cleanup let independent cells continue; uncertain

### Resolve once for local and remote discovery

The existing version-1 runner JSON remains the authoring source. `prepare` holds
workload and source options; `workSeconds` and `cleanupSeconds` bound the finite
window in seconds. `runner.py project` resolves adapter defaults and produces the
configuration digest, receipt limits and a **draft** version-2 diagnostic receipt.
The command creates no run and grants no execution or provider authority.

```bash
python3 -B tools/mt-bench/m7-joined/runner.py project /absolute/private/run.json
python3 -B tools/mt-bench/m7-joined/runner.py project /absolute/private/run.json \
  --source-acceptance /absolute/private/source-acceptance.json \
  --remote-overlay /absolute/private/remote-overlay.json
```

The optional source-acceptance document is exactly `{"status":"PENDING"}` or
`{"status":"PASS","reference":"/absolute/private/acceptance.json","sha256":"…"}`.
PASS requires the referenced file's actual SHA-256 and a `joined-acceptance` PASS
record matching the exact core/deploy pair and image. The evidence record must
also identify its own instrument and evidence digest. The acceptance instrument
can differ from the experiment helper. A missing, changed or mismatched record
refuses. This validates the retained record, not a new application campaign.
The resource owner issues genuine authorization from the draft only within
existing authority; changing `DRAFT` to `AUTHORIZED_DIAGNOSTIC` is an attestation,
not a permission bypass. Keep historical receipts and captures unchanged.

Version 2 requires `purpose: BOUNDED_DISCOVERY`, the generated
`configurationSha256`, `execution`, `limits`, `sourceAcceptance`, and matching
`functionalAcceptanceAtAuthorization`. It binds source/image/helper,
PostgreSQL image, tenants, cadence, viewers, concurrency, topology, selected
resource profile, completion reader, k6 image and work/cleanup limits. The runner
refuses altered mirrors before output creation or guard arming. Adapter admission
checks source/image/receipt before dependency preparation, checks actual project
and CIDR availability before staging, and rechecks prepared semantic input before
deploy/run. Actual image labels, generated plans, dependency bytes, quotas,
process births, ownership, free ports and runtime census remain independent
readbacks. Namespace readback is an observation, not a reservation.

Legacy version-1 discovery receipts retain their PENDING-only semantics and
UNACCEPTED result attribution. Version-2 results record PENDING or PASS truthfully,
with the source-acceptance reference and configuration digest. Every discovery
result still carries `capacityAcceptance: NOT_GRANTED`; accepted-source diagnosis
cannot promote capacity or release claims. The proof owner's recovery classifier
retains failed correctness episodes and dependent UNMEASURED claims. Strict
acceptance remains separate and failed correctness remains failed.

## Outcome evaluator gate

Decision [outcome-evaluator-gate](../../../docs/30-design/tenancy/multitenancy-decisions.md#outcome-evaluator-gate)
replaces the lifetime `failedCompletions == 0` rule and the instant midpoint
readiness rule. [outcome_gate.py](outcome_gate.py) is the one frozen gate; its
identity is the SHA-256 of that file. Tenants, rate, windows, budgets and
`deadlineMs` (default 120000) are configuration under the same identity.

| component | FAIL | UNMEASURED |
|---|---|---|
| failed completions (lifetime counters at the end point) | untyped, `unknown`, hard or unrecognised reason; a transient reason resolved or still open past the deadline | typed rows without reasons or resolution fields; a transient still open at the end inside the deadline; no end point |
| isolation | runtime reset, foreign row ready, foreign counters changed, duplicate owner | one point only |
| readiness | preload refused; an owner not ready, with a code or with an alert at the end point | preload not selected or not retained; no end point |
| storage | count oracle RED | oracle missing or not GREEN |
| sampled oracle | probe `completedOutput` FAIL | missing |
| all-tenant catch-up | a tenant pending once the window after writer join exceeds the deadline; a completion whose lower bound exceeds it; input changed | not captured; pending inside the deadline |

A declared transient reason (`verification-pending`, `startup-warming`) that
completed inside the deadline is counted by reason and passes. Until the
source declares `view.failureReasonContract = evaluator-failure-reasons-v1`
with `progress.failureReasons`, `unresolvedFailure` and
`maxFailureResolutionMs`, every failed completion is untyped and fails.

The midpoint is a signal. The runner records ``load/evaluator-midpoint-signal.json`` and stops
the driver only for a hard reason (a FAIL above, or an evaluation alert). A
not-ready owner at the midpoint continues. Raw responses are written before
any decoder reads them (`load/evaluator-progress-raw/`). The verdict is ``load/outcome-gate.json` and the discovery check `outcomeGate``; HTTP
latency over every k6 shard summary is reported beside it (exact pooled
count and mean; per-shard quantile ranges; pooled quantiles UNMEASURED).
`outcome_rereduce.py` re-reduces a retained run into a new file beside it and
refuses if any original file changes.

### Bounded rate brackets for the realistic mix

`workload-scale` is an optional positive finite factor, accepted only
with `workload-mix: realistic-v1`. Default factor one preserves every existing
per-tenant cadence. Other factors are **uniform rate brackets**: factor two
halves all seven per-tenant intervals while retaining the roster, viewer count,
shape proportions, duration and resource allocation. A factor above one is not
realistic sensor cadence. An aggregate `offered-rps` override remains incompatible
with the mix. Zero, nonfinite factors and factors whose rounded time units cannot
be represented by k6 refuse before preparation. Compose and Kubernetes share
this rule. The legacy remote calibration binding retains its earlier 0.25–8
bracket until that binding and its validator are extended.

The canonical cadence and receipt bind `workloadScale`. Local and remote k6
commands mirror it as `M7_WORKLOAD_SCALE`, including every shard in the existing
shared container. Each scenario time unit is rounded to integer milliseconds;
`rate_offer` reports the actual rounded time units and resulting rates. It marks
factor-one sensor cadence separately from a uniform rate bracket. This selector
authorizes no run, expense or capacity. Select a justified bracket in a fresh
configuration/receipt; never change an entered run.

To vary ordinary writes independently, set `writeRateScale` in the configured
`driverPlan` for `realistic-v1`. Its positive finite multiplier applies to SGV,
device-status and treatment writes on top of the selected `workloadScale`.
The default is one. A plan with `workloadScale` one and `writeRateScale` two
doubles the three write rates with the four read intervals held at baseline.
Viewer count and the probe-write interval remain separate workload inputs.
Compose and Kubernetes report the rounded rates per shape.

### Phase clocks and local discovery to completion

`viewer-setup` selects the Socket.IO connection scenario. The ordinary driver
opens at most 50 viewers per second by default. It tries WebSocket first and
permits polling fallback. For example, `{"opensPerSecond":20,"stallSeconds":90}`
selects a slower ramp. Setup advances on successful tenant JWT exchanges,
first connections and first data frames for distinct viewers. A lack of
progress for the selected interval (default 300 seconds) stops viewer setup.
The operator's overall work deadline still applies. Select
`{"transport":"polling"}` for stock display transport compatibility.
`{"scenario":"simultaneous-reconnect"}` ramps and primes the full cohort,
disconnects it, then reconnects all its viewers together before ordinary
traffic. The probe records actual initial and reconnect frame coverage and
transport counts under `viewerSetup`.

`setup-seconds` covers the ordinary k6 driver's JWT exchanges. `drain-seconds` governs the post-writer probe and fixed-target
observer. Local and Kubernetes probes measure 120 seconds from the later of HTTP
acknowledgement and evaluator warmth for that tenant. Independent owner inspection
brackets the transition between the last zero-acquisition read and the first ready
owner with a credited acquisition. A deadline inside that uncertainty interval can
leave the verdict UNMEASURED. The outcome includes per-tenant warm intervals and
coverage, acceptance-to-durable and acceptance-to-frame delays, nominal deadline
misses before warmth, and witnesses censored by the remaining drain clock. Terminal
zero lifetime acquisitions on the observed owner fail the never-warm criterion.
Earlier packets retain the clinical verdict of their own instrument.
Use `plan` to inspect their values and the work they cover. Set these limits
from observed phase timings and keep their evidence with the experiment.
Deployment priming is a separate provisioning stage. A traffic window names
the generator's offered-work plan and does not set the overall cleanup clock.

## Offline resolution, signals and removed instruments

`workSeconds`, `cleanupSeconds` and `drainSeconds` with their maximum and origin,

required (`M7_RUNNER_FINITE_LIMIT`); 600 seconds is accepted.

through the outcome gate only. Retained runs re-reduce with
`outcome_rereduce.py`.
