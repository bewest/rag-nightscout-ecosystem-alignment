    Reuse the canonical local runner¶

    Living document, last changed 2026-11-16 at cd850286a.

    runner.py replaces copied per-attempt preparation and execution scripts with one configuration and the existing adapter.py entrypoints. It does not build an image, allocate a remote host or grant capacity acceptance.

    For new runs on this workstation, use the overflow-disk storage layout in AGENTS.md. Keep helpers under the appropriate /mnt/data/nightscout-workspace/worktrees/ directory and select outputs under /mnt/data/nightscout-workspace/artifacts/<lane>/<run>. The directory arguments below are explicit storage choices, not automatic runner defaults. A missing or unwritable /mnt/data is a storage error; do not fall back to the home drive. Existing runs and their original guards keep their current paths.

    Copy the small rehearsal profile to private storage. Set its verified helper head, repository paths, existing diagnostic receipt, new project and unused explicit CIDRs. The receipt still binds the source pair, image, instrument and traffic duration through the adapter's existing contract. Reusing a qualified app/image does not require rebuilding that image or running application acceptance for a tenant/RPS change.

    For new configurations, run python3 -B tools/mt-bench/m7-joined/runner.py identity from the committed helper, then replace helperHead in the configuration with the returned helperInstrument field. Choose exactly one pin. Content pinning permits the same executed bytes at another commit; the adapter still records the actual commit. Markdown documentation is excluded from the instrument digest. Changed executable/configuration inputs remain pinned and dirty inputs refuse. Existing helperHead configurations keep their exact-commit behavior. This new manifest definition applies only to new captures; old runs keep their original helper, receipts and attribution. Do not change helpers under a live guard.

    The adapter preflight still checks required source/runtime and instrument paths. Optional realtime cost-counter gaps are saved in preflight-observations.json as NO-INSTRUMENT; they do not ban discovery traffic or become measured zeros. These counter observations grant no acceptance. Shared-host discovery already records contention without requiring other agents to stop their containers.

    python3 -B tools/mt-bench/m7-joined/runner.py prepare \
  /absolute/private/run.json /mnt/data/nightscout-workspace/artifacts/example-lane/run01
python3 -B tools/mt-bench/m7-joined/runner.py rehearse \
  /mnt/data/nightscout-workspace/artifacts/example-lane/run01
python3 -B tools/mt-bench/m7-joined/runner.py result \
  /mnt/data/nightscout-workspace/artifacts/example-lane/run01

    Use the qualified Node/npm paths in PATH. prepare stages canonical source, configuration, probe, workload and owned dependencies. It starts no services. rehearse performs canonical deploy, real instrument preflight, a generated program failure control, ordinary tiny traffic, collection, reduction and cleanup. The control omits the required probe URL, checks Node's actual ERR_INVALID_URL refusal before network I/O, then the normal caller runs the same unmodified generated bytes. execute runs the same path without that intentional refusal. Neither action retries a phase.

    The example uses two synthetic tenants, four stock clients, serial JWT setup and 1 offered scenario request/s. Its work window is finite; its independent guard stops an active stage and invokes the adapter's owned-project cleanup at the deadline. The runner checks process birth and group before escalating a stage that ignores TERM. Normal completion also cleans up. Explicit cleanup is:

    python3 -B tools/mt-bench/m7-joined/runner.py down /mnt/data/nightscout-workspace/artifacts/example-lane/run01

    Keep the helper source fixed while a run or its guard is live. Cleanup retains the adapter's ownership and source checks. It never stops peer services. result.json records the phase, native adapter status, traffic phase, process failures and cleanup outcome. Native summaries, readiness, recent role logs and collector outputs remain private artifacts. A missing scenario counter stays unknown; zero scenario attempts with HTTP setup exchanges is setup-only data. COMPLETED_PARTIAL means the pipeline returned with a partial adapter result; it is not a successful application or capacity claim.

    Measured boundary and reuse limits¶

    The retained local rehearsal on helper e156c798310e626c05a96711e832d229f2c34c9b ran the actual generated path against cached core 8aeefaefc88c79c3d548f7683d5651bec9cf5c01, deploy df5362745a1b2d1b02b9186daedef3faccc14e58 and immutable image sha256:382e44696c4415e710698ee6135c499ae2d480d9f39a2fb85c59675fdd8d2150. It reached ordinary scenarios, collected and reduced native outputs, exercised the existing stored-count break/restore control, and removed its owned resources. The later process-cleanup change has a separate real-process failure control; no additional application campaign follows that helper change.

    This profile uses the original qualified serial workload. A newer optional JWT batching series did not compose with the capture helper's whole-callback setup rewrite: actual preparation refused M7_WORKLOAD_SETUP_ANCHOR_CHANGED before runtime. Keep that source failure distinct from an application admission failure. This joined helper adopts the supported single-commit compatibility repair; its default remains serial 1. Explicit batching changes setup and must be recorded in comparisons.

    Existing adapter.py attach binds fresh collector metadata to a compatible prepared and seeded fixture. Source, config, dependency installation, resource IDs and runtime owner stay explicit. Attachment does not acquire cleanup custody. The default prepare / execute path still cleans at the end of each point. Opt-in bounded sessions below retain the fixture for subsequent observations.

    The remote trusted supervisor and nsload environment are not qualified by this local exercise. Existing remote adapters keep their separate source binding and UID/configuration requirements. The next remote executor must run that exact prepare/caller path on an already available qualified private driver; this tool has no paid-resource authority. Do not infer remote environment qualification from local source tests or from execution of the generated public probe alone.

    Joined candidate and metric meanings¶

    The paired 1k and 3k profiles hold ordinary cadence, hot factor 1, two clients per tenant, offered scenario rate 180/s and load duration 310 seconds constant. Primer concurrency is explicitly four and JWT setup is serial one. Client population and nominal request rate are independent. Replace every source/image/receipt/path placeholder from the accepted candidate before preparation; templates are HELD inputs. Use new private output paths and unused explicit CIDRs for each point. Run 1k to cleanup, then 3k with that same accepted app image, helper and workload.

    The global k6 HTTP window includes JWT setup; per-shape REST durations and failure metrics describe ordinary scenarios. Native scenario attempts, HTTP responses, transport failures and dropped iterations remain separate. The stored-count oracle compares accepted, persisted and uncertain writes. All-roster evaluator health is required independently of opportunity-aware progress; quiet tenants need no forced work. The optional opportunity caller supports unselected v2 discovery only and refuses selected-profile collection before SQL.

    load/probe.json and the runner result retain durableOutputObservation. This uses the existing private oracle, including typed completion, stored tuple and clinical output checks, with the client gate removed only for durable observation. Request start, SQL invocation/return and frame callbacks share the probe's performance.now() clock. The last proven-negative SQL invocation and first positive SQL return bound request-to-durable-output visibility. No server wall clock is subtracted. A missing/invalid row gives no negative bound. Query count, bytes, elapsed time, misses, distinct tenants and sample count are retained.

    This is sparse synthetic probe observation at the unchanged five-minute cadence, not all ordinary writes or isolated executor latency. Client-frame timings match the actual stored ID and remain separate; frames do not carry output revision identity. Existing evaluator duration reducers retain executor/durable-completion bin intervals and n; those intervals are separate from this visibility bound. The old writeToEvaluationMs is a combined durable-plus-client polling witness and must not be called pure evaluator lag. Missing optional data is UNMEASURED.

    Configurable discovery and strict remote reporting¶

    Local configuration uses the existing prepare object. For example, change a private copy of the rehearsal profile to these values and run the same runner.py prepare, execute and result commands:

    {"tenants":37,"offered-rps":73,"warmup-seconds":3,"idle-seconds":4,
 "load-seconds":45,"probe-every-ms":1000,"sockets-per-tenant":3}

    Those fields alter synthetic work and observations, not the application image. The same supported source/image, current source-matched receipt and finite execution/cleanup window still apply. The new client count is explicit; offered scenario rate remains independent from client population. Ordinary five-minute probe cadence remains the default; comparisons that select a shorter cadence must record it. No application rebuild or full acceptance follows a reporting, tenant, rate or client-count change.

    Remote calibration keeps its existing strict default and exact source/image presets. A future remote discovery binding explicitly selects "reportMode":"discovery"; its authorization receipt must select "remoteReportMode":"discovery" and contain that exact remoteWorkload. The existing controller config supplies the binding and receipt. For the same work above, its existing workload.cadence selects warmupSeconds:3, idleSeconds:4, loadSeconds:45, offeredRps:73, probeEveryMs:1000, socketsPerTenant:3, with ordinary accel:1, hotFactor:1, samplerIntervalSeconds:2 and restart:false. Set the binding's tenants:37 and its existing resource plan's tenants:37 and logicalPollingClients:111. Retain the actual host identities and selected primer concurrency in that plan. These are configuration examples, not new authorization or measured headroom.

    To vary the total independently, add "logical-polling-clients":2 to local prepare for a 37-tenant roster. This discovery-only integer accepts 0..80000. When omitted, sockets-per-tenant keeps its existing default and behavior. Remote discovery uses the existing resourcePlan.logicalPollingClients as the total; the controller's logicalPollingClients mirror and receipt must match. Do not add a second total to remote cadence. The worker forwards the total to the same local parser only when it differs from the legacy per-tenant product.

    The first total % tenants roster entries receive one additional viewer over floor(total / tenants). Viewer IDs follow tenant-major opening order. Zero opens no sockets and exchanges no probe-viewer JWTs; ordinary traffic and its independent stored-write/output checks still run. Frame evidence reports NOT_EXERCISED when selected writes have no viewers, including a zero total. Reducers derive frame expectations from this plan and per-tenant accepted probe writes, validate every emitted viewer binding and keep stored/output/authority checks separate. Changing load does not extend source/image/deadline or budget authority, and does not alter an already entered run.

    Discovery supports 1..10000 tenants, a legacy default of 1..8 polling clients per tenant, bounded cadence values and offered scenario rates 1..10000/s. Total configured phase time remains at most three hours and the existing earlier deadline governs. Strict preset ranges and source/image tuple checks remain unchanged. An exact qualified tuple is still required; a different candidate cannot borrow a previous candidate's source qualification or receipt.

    The actual public probe accounting helper is exported with a hash and checked before driver installation. It records admitted, accepted, uncertain, refused and pending writes without SQL or provider authority. The existing collector retains its ledger and generator process results alongside probe/fanout/k6 artifacts. Discovery summaries remain PARTIAL, with no capacity acceptance; HTTP failures, incomplete clients, failed processes and missing optional metrics remain observations. Source/ownership mismatches, observed wrong data, clinical failures and invalid metadata still fail. Strict reporting retains its original full-client, zero-failure and required-metric checks. REST metrics, sampled client frame times and SUT completion observations remain separate; remote output timing is UNMEASURED and no cross-host clock subtraction is used.

    Finite experiment batches¶

    runner.py batch-plan <batch.json> --payload-root <absolute-private-directory> prints a deterministic review plan without starting services. batch-run <batch.json> <new-private-output> --payload-root <absolute-private-directory> executes that same admitted specification. batch-result <private-output> reads completed and partial per-cell results, including after an interrupted batch. The ordinary single-point commands and their defaults stay available.

    Start from the local batch template. Replace its source/helper/receipt paths and hashes, project/CIDRs and zero cleanup cutoff with the reviewed inputs and original absolute cutoff; the template is inert. Both cells reuse the same immutable source/image/helper. The template declares room for two whole cells. Set its aggregate envelope to the resources allocated to your lane; a smaller envelope queues cells without reducing their quotas.

    Batch digests use the shared canonical vectors. Numbers must be finite; integral numbers must fit the exact shared range −9007199254740991 through 9007199254740991. Negative zero becomes zero, and 1.0 and 1 have one identity. Payload bytes are never transformed.

    The common version 1 batch structure is shared with the deployment controller's pgstream-caller.mjs batch API. A batch contains explicit cells; expand an R&D matrix into cells before review rather than submitting executable generators. Each cell.config is an ordinary runner configuration locally, or an existing remote caller specification remotely. Local and remote batches have the same review fields; each backend still checks its own typed runtime contract.

    For local cells, target is {"kind":"local"}, ports are empty (no host-port configuration is supported by this runner), and subnets exactly match the configuration's backend and edge CIDRs. Names and CIDRs cannot overlap another cell, even when cells run sequentially. The existing adapter performs its fresh host census before effects. Local cells require the existing local-diagnostic-4cpu-8g-v1 producer or explicit local-diagnostic-external-pgstream-4cpu-8g-v1 with pgstream-topology: external-service-v1, reserving 4000 millicpus, 8589934592 memory bytes, 1024 MiB host V8 heaps, zero money and a conservative 64 live resources. This profile reserves 500 millicpus/1 GiB for k6 and the remaining 3500 millicpus/7 GiB for SUT roles and declared oneoffs. Host heaps include helper, generator and probe overlaps. Host RSS/native memory remains separately observed; a V8 heap limit does not bound RSS. Plans expose this allocation breakdown. The aggregate envelope is configurable independently of those per-cell limits. Two simultaneous full cells require at least 8000 millicpus, 17179869184 memory bytes, 2048 MiB host heaps and 128 live resources, plus their summed offered rate and two execution slots. The caller must keep that envelope within its allocated host resources. A smaller per-cell quota still needs a typed producer and controls. Concurrent cells share the host: record contention in comparison evidence; the scheduler does not reserve a quiet machine or bound host RSS.

    Each batch holds the original UID-global driver lock and atomically reserves whole cells in a private ledger. Only a live exact-birth coordinator and matching nonce can authorize a child driver to use its own cell heap lock. This retains legacy-driver exclusion, per-cell native quota/census checks and stale-marker refusal. It does not rename the global lock to pretend aggregate admission. The unchanged independent guard owns each cell's finite cleanup window, starting with preparation; the batch cutoff never extends it. Source-loader preflight now runs automatically during batch preparation before services. A failed cell keeps its private phase and partial outputs. Admission continues for independent cells when their reservations fit. Unconfirmed cleanup retains its entire reservation. A child rechecks the ticket's absolute cleanup cutoff before preparation, so process-launch delay cannot silently authorize a fresh full window. Coordinator death leaves custody markers intact for explicit exact-resource reconciliation; PID expiry alone never frees resources.

    SIGINT/SIGTERM stops new admissions while entered cells finish their original finite cleanup. Reservations release only after the child returns, the original guard is absent, adapter cleanup records exact absence and the cell heap marker is empty under exclusive lock. No other cell's reservation or resource is released. Changing payload bytes or source/image/helper pins refuses before a new cell starts. Raw logs, tickets, namespaces, process births and ledgers stay in ignored private output, not the public repository.

    Local batch configurations use existing tenant/rate/duration/cadence/hot-factor options and preserve the adapter's required correctness oracles. Ordinary local batches currently require an empty fault allowlist; unsupported fault cases refuse. Remote component cases retain their existing typed implementation. Optional counters and generator headroom remain UNMEASURED when unavailable. A constrained generator can limit offered load; that is not a product capacity measurement. Every batch result keeps capacityAcceptance: NOT_GRANTED. Parameter changes inside the declared envelope use the same tool and focused input checks; they do not trigger an application rebuild or full acceptance.

    A reviewable batch plan does not grant remote spending, export or tool permission. Remote plans must disclose their payload allowlist and exact provider destinations and use the existing authoritative budget/custody hooks. Paid allocation and transport remain with the remote owner. Independent remote pairs retain exact unconditional deletion; retaining a pair across cells is a separate reset and rig-ownership capability. Active experiments stay pinned to their original tools.

    Scheduling checks use the real local caller/process/ticket/flock path with synthetic prepare/execute actors, and the remote caller with synthetic root hooks. They qualify admission, overlap, failure isolation and custody, not application capacity or a native live provider gateway. Remote batches reuse verified sealed input directories; batch-run does not call bundle or export images again. Changed inputs require their own matching source/image/helper pins and hashes. Remote cleanup uncertainty retains accounting while other eligible pairs proceed; reservation/authority uncertainty stops admission. Per-cell deadlines skip only the expired cell; the common cutoff leaves no cell eligible. Native approval message lookup/provider installation remains UNMEASURED here and belongs to the remote custodian; source adapters do not grant tool permissions.

    Typed local Vault component cells¶

    cell.config.producer: "vault-component-v1" selects the fixed Vault component executor in vault_component.py, through the same batch-plan, batch-run, private _batch-cell and result gateway. It runs the six actual key purposes and synthetic 48-byte root-secret encryption from the pinned source capsule. It does not provision SQL tenants or qualify application serving. Remote targets refuse; no provider or paid gateway is added.

    The exact config fields are version: 1, producer, capsule (absolute private allowlisted JSON path), helperInstrument, workSeconds (30–3600), cleanupSeconds (30–180), targetSets (1–10000) and vaultMemoryMiB (256, 512 or 1024). Unknown fields refuse. Each cell declares one unused explicit loopback port and an empty subnet list; it uses the existing Docker bridge, without creating or deleting a network. Names and ports still pass common batch isolation checks. offeredRps is zero because this producer has no application load driver; Vault work is bounded by target sets and four-worker concurrency, not an asserted zero provider-request rate. The shared workload axes bound tenants as component set count and durationSeconds as the work window; probeEveryMs is the inapplicable fixed zero and hotFactor is fixed one. Fault cases remain unsupported.

    The capsule has exact fields version, producer, source, image, imageId, helper, files, workerSha256 and tools. Its source binds the shared batch pins; core is 3b2cec6405451d0aff103f5d21f4312606d4295b and the four required module hashes are fixed by this producer. The common deploy pin is retained provenance, not an executed deployment tree for this component. The payload allowlist contains source/lib/tenant-registry/{vault-keys,rules}.js, source/lib/secrets/{vault-transit,component}.js and the capsule itself, with exact bytes and no symlinks. No credentials, token, key path or root secret is part of that capsule. The image is the retained pinned Vault manifest and matching image ID. Tools are exact resolved node and docker paths, hashes and version receipts; Node is 24.22.1. The executor verifies them before SUT effects, uses only fixed argv, refuses preloads and never installs, pulls or builds. Docker commands explicitly select the local Unix socket. Provider credentials are created in memory and sent to the fixed worker over stdin only.

They do not by themselves qualify native Vault overlap; that requires retained source-bound native actors, progress and independent exact cleanup evidence.

    Resolve once for local and remote discovery¶

    The existing version-1 runner JSON remains the authoring source. prepare holds workload and source options; workSeconds and cleanupSeconds bound the finite window in seconds. runner.py project resolves adapter defaults and produces the configuration digest, receipt limits and a draft version-2 diagnostic receipt. The command creates no run and grants no execution or provider authority.

    python3 -B tools/mt-bench/m7-joined/runner.py project /absolute/private/run.json
python3 -B tools/mt-bench/m7-joined/runner.py project /absolute/private/run.json \
  --source-acceptance /absolute/private/source-acceptance.json \
  --remote-overlay /absolute/private/remote-overlay.json

    The optional source-acceptance document is exactly {"status":"PENDING"} or {"status":"PASS","reference":"/absolute/private/acceptance.json","sha256":"…"}. PASS requires the referenced file's actual SHA-256 and a joined-acceptance PASS record matching the exact core/deploy pair and image. The evidence record must also identify its own instrument and evidence digest. The acceptance instrument can differ from the experiment helper. A missing, changed or mismatched record refuses. This validates the retained record, not a new application campaign. The resource owner issues genuine authorization from the draft only within existing authority; changing DRAFT to AUTHORIZED_DIAGNOSTIC is an attestation, not a permission bypass. Keep historical receipts and captures unchanged.

    Version 2 requires purpose: BOUNDED_DISCOVERY, the generated configurationSha256, execution, limits, sourceAcceptance, and matching functionalAcceptanceAtAuthorization. It binds source/image/helper, PostgreSQL image, tenants, cadence, viewers, concurrency, topology, selected resource profile, completion reader, k6 image and work/cleanup limits. The runner refuses altered mirrors before output creation or guard arming. Adapter admission checks source/image/receipt before dependency preparation, checks actual project and CIDR availability before staging, and rechecks prepared semantic input before deploy/run. Actual image labels, generated plans, dependency bytes, quotas, process births, ownership, free ports and runtime census remain independent readbacks. Namespace readback is an observation, not a reservation.

    Legacy version-1 discovery receipts retain their PENDING-only semantics and UNACCEPTED result attribution. Version-2 results record PENDING or PASS truthfully, with the source-acceptance reference and configuration digest. Every discovery result still carries capacityAcceptance: NOT_GRANTED; accepted-source diagnosis cannot promote capacity or release claims. The proof owner's recovery classifier retains failed correctness episodes and dependent UNMEASURED claims. Strict acceptance remains separate and failed correctness remains failed.

    Planned evaluator restart during local discovery demand¶

    For a new local capture, restart-during-load-after-seconds selects a planned restart of the complete rendered evaluator roster while ordinary k6 traffic and the stock-client probe continue. This mode requires discovery, completion contract evaluator-work-v2, a version-2 configuration-bound receipt, probe cadence at most 1000ms, and at least 60 seconds between selected delay and the end of offered load. Example preparation fields are restart-during-load-after-seconds: 60, load-seconds: 310, and probe-every-ms: 1000. The default remains unchanged.
