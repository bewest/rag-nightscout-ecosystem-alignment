    Reuse the canonical local runner¶

    Living document, last changed 2026-11-23 at ef8b39a5f.

    runner.py replaces copied per-attempt preparation and execution scripts with one configuration and the existing adapter.py entrypoints. It does not build an image, allocate a remote host or grant capacity acceptance.

    For new runs on this workstation, use the overflow-disk storage layout in AGENTS.md. Keep helpers under the appropriate /mnt/data/nightscout-workspace/worktrees/ directory and select outputs under /mnt/data/nightscout-workspace/artifacts/<lane>/<run>. The directory arguments below are explicit storage choices, not automatic runner defaults. A missing or unwritable /mnt/data is a storage error; do not fall back to the home drive. Existing runs and their original guards keep their current paths.

    Copy the small rehearsal profile to private storage. Set its verified helper head, repository paths, existing diagnostic receipt, new project and unused explicit CIDRs. The receipt still binds the source pair, image, instrument and traffic duration through the adapter's existing contract. Reusing a qualified app/image does not require rebuilding that image or running application acceptance for a tenant/RPS change.

    For new configurations, run python3 -B tools/mt-bench/m7-joined/runner.py identity from the committed helper, then replace helperHead in the configuration with the returned helperInstrument field. Choose exactly one pin. Content pinning permits the same executed bytes at another commit; the adapter still records the actual commit. Markdown documentation is excluded from the instrument digest. Changed executable/configuration inputs remain pinned and dirty inputs refuse. Existing helperHead configurations keep their exact-commit behavior. This new manifest definition applies only to new captures; old runs keep their original helper, receipts and attribution. Do not change helpers under a live guard.

    The adapter preflight still checks required source/runtime and instrument paths. Optional realtime cost-counter gaps are saved in preflight-observations.json as NO-INSTRUMENT; they do not ban discovery traffic or become measured zeros. These counter observations grant no acceptance. Shared-host discovery already records contention without requiring other agents to stop their containers.

    python3 -B tools/mt-bench/m7-joined/runner.py prepare \
  /absolute/private/run.json /mnt/data/nightscout-workspace/artifacts/example-lane/run01
python3 -B tools/mt-bench/m7-joined/runner.py rehearse \
  /mnt/data/nightscout-workspace/artifacts/example-lane/run01
python3 -B tools/mt-bench/m7-joined/runner.py result \
  /mnt/data/nightscout-workspace/artifacts/example-lane/run01

    Use the qualified Node/npm paths in PATH. prepare stages canonical source, configuration, probe, workload and owned dependencies. It starts no services. rehearse performs canonical deploy, real instrument preflight, a generated program failure control, ordinary tiny traffic, collection, reduction and cleanup. The control omits the required probe URL, checks Node's actual ERR_INVALID_URL refusal before network I/O, then the normal caller runs the same unmodified generated bytes. execute runs the same path without that intentional refusal. Neither action retries a phase.

    The example uses two synthetic tenants, four stock clients, serial JWT setup and 1 offered scenario request/s. Its work window is finite; its independent guard stops an active stage and invokes the adapter's owned-project cleanup at the deadline. The runner checks process birth and group before escalating a stage that ignores TERM. Normal completion also cleans up. Explicit cleanup is:

    python3 -B tools/mt-bench/m7-joined/runner.py down /mnt/data/nightscout-workspace/artifacts/example-lane/run01

    Keep the helper source fixed while a run or its guard is live. Cleanup retains the adapter's ownership and source checks. It never stops peer services. result.json records the phase, native adapter status, traffic phase, process failures and cleanup outcome. Native summaries, readiness, recent role logs and collector outputs remain private artifacts. A missing scenario counter stays unknown; zero scenario attempts with HTTP setup exchanges is setup-only data. COMPLETED_PARTIAL means the pipeline returned with a partial adapter result; it is not a successful application or capacity claim.

    Configurable discovery and strict remote reporting¶

    Local configuration uses the existing prepare object. For example, change a private copy of the rehearsal profile to these values and run the same runner.py prepare, execute and result commands:

    {"tenants":37,"offered-rps":73,"warmup-seconds":3,"idle-seconds":4,
 "load-seconds":45,"probe-every-ms":1000,"sockets-per-tenant":3}

    Those fields alter synthetic work and observations, not the application image. The same supported source/image, current source-matched receipt and finite execution/cleanup window still apply. The new client count is explicit; offered scenario rate remains independent from client population. Ordinary five-minute probe cadence remains the default; comparisons that select a shorter cadence must record it. No application rebuild or full acceptance follows a reporting, tenant, rate or client-count change.

    Remote calibration keeps its existing strict default and exact source/image presets. A future remote discovery binding explicitly selects "reportMode":"discovery"; its authorization receipt must select "remoteReportMode":"discovery" and contain that exact remoteWorkload. The existing controller config supplies the binding and receipt. For the same work above, its existing workload.cadence selects warmupSeconds:3, idleSeconds:4, loadSeconds:45, offeredRps:73, probeEveryMs:1000, socketsPerTenant:3, with ordinary accel:1, hotFactor:1, samplerIntervalSeconds:2 and restart:false. Set the binding's tenants:37 and its existing resource plan's tenants:37 and logicalPollingClients:111. Retain the actual host identities and selected primer concurrency in that plan. These are configuration examples, not new authorization or measured headroom.

    To vary the total independently, add "logical-polling-clients":2 to local prepare for a 37-tenant roster. This discovery-only integer accepts zero or a positive JavaScript array length, through 4,294,967,295. This representation bound does not establish memory or connection capacity. When omitted, sockets-per-tenant keeps its existing default and behavior. Remote discovery uses the existing resourcePlan.logicalPollingClients as the total; the controller's logicalPollingClients mirror and receipt must match. Do not add a second total to remote cadence. The worker forwards the total to the same local parser only when it differs from the legacy per-tenant product.

    The first total % tenants roster entries receive one additional viewer over floor(total / tenants). Viewer IDs follow tenant-major opening order. Zero opens no sockets and exchanges no probe-viewer JWTs; ordinary traffic and its independent stored-write/output checks still run. Frame evidence reports NOT_EXERCISED when selected writes have no viewers, including a zero total. Reducers derive frame expectations from this plan and per-tenant accepted probe writes, validate every emitted viewer binding and keep stored/output/authority checks separate. Changing load does not extend source/image/deadline or budget authority, and does not alter an already entered run.

    Compose and native Kubernetes discovery resolve positive roster sizes and hot weights within the generated JavaScript arrays' combined length limit. Finite phase durations must fit k6's Go duration representation; the work window must cover the selected phases. Offered rates must produce a positive representable k6 time unit. These are planning contracts. The selected source provisioner, role configuration, available resources and actual authority still govern execution. Source/image identity and fixed acceptance profiles stay exact. Each experiment keeps its selected source/image tuple and its own receipts.

    The actual public probe accounting helper is exported with a hash and checked before driver installation. It records admitted, accepted, uncertain, refused and pending writes without SQL or provider authority. The existing collector retains its ledger and generator process results alongside probe/fanout/k6 artifacts. Discovery summaries remain PARTIAL, with no capacity acceptance; HTTP failures, incomplete clients, failed processes and missing optional metrics remain observations. Source/ownership mismatches, observed wrong data, clinical failures and invalid metadata still fail. Strict reporting retains its original full-client, zero-failure and required-metric checks. REST metrics, sampled client frame times and SUT completion observations remain separate; remote output timing is UNMEASURED and no cross-host clock subtraction is used.

    Resolve once for local and remote discovery¶

    The existing version-1 runner JSON remains the authoring source. prepare holds workload and source options; workSeconds and cleanupSeconds bound the finite window in seconds. runner.py project resolves adapter defaults and produces the configuration digest, receipt limits and a draft version-2 diagnostic receipt. The command creates no run and grants no execution or provider authority.

    python3 -B tools/mt-bench/m7-joined/runner.py project /absolute/private/run.json
python3 -B tools/mt-bench/m7-joined/runner.py project /absolute/private/run.json \
  --source-acceptance /absolute/private/source-acceptance.json \
  --remote-overlay /absolute/private/remote-overlay.json

    The optional source-acceptance document is exactly {"status":"PENDING"} or {"status":"PASS","reference":"/absolute/private/acceptance.json","sha256":"…"}. PASS requires the referenced file's actual SHA-256 and a joined-acceptance PASS record matching the exact core/deploy pair and image. The evidence record must also identify its own instrument and evidence digest. The acceptance instrument can differ from the experiment helper. A missing, changed or mismatched record refuses. This validates the retained record, not a new application campaign. The resource owner issues genuine authorization from the draft only within existing authority; changing DRAFT to AUTHORIZED_DIAGNOSTIC is an attestation, not a permission bypass. Keep historical receipts and captures unchanged.

    Version 2 requires purpose: BOUNDED_DISCOVERY, the generated configurationSha256, execution, limits, sourceAcceptance, and matching functionalAcceptanceAtAuthorization. It binds source/image/helper, PostgreSQL image, tenants, cadence, viewers, concurrency, topology, selected resource profile, completion reader, k6 image and work/cleanup limits. The runner refuses altered mirrors before output creation or guard arming. Adapter admission checks source/image/receipt before dependency preparation, checks actual project and CIDR availability before staging, and rechecks prepared semantic input before deploy/run. Actual image labels, generated plans, dependency bytes, quotas, process births, ownership, free ports and runtime census remain independent readbacks. Namespace readback is an observation, not a reservation.

    Legacy version-1 discovery receipts retain their PENDING-only semantics and UNACCEPTED result attribution. Version-2 results record PENDING or PASS truthfully, with the source-acceptance reference and configuration digest. Every discovery result still carries capacityAcceptance: NOT_GRANTED; accepted-source diagnosis cannot promote capacity or release claims. The proof owner's recovery classifier retains failed correctness episodes and dependent UNMEASURED claims. Strict acceptance remains separate and failed correctness remains failed.

    Tenant roster and topology The source limits tenant count. The generated roster and hot wheel must fit JavaScript arrays.     offered-rps Positive finite scenario HTTP attempts per second with a representable k6 time unit. Setup and stock-probe requests have separate rates.
    warmup-seconds, idle-seconds, load-seconds, setup and drain Positive integer seconds within the shared duration representation. A finite work window must contain the applicable phases. Compose accepts the legacy warmup and idle options without running those phases. Native Kubernetes binds finite setup, load, drain and its outer work window.
    probe-every-ms Positive whole milliseconds up to 2,147,483,647. The planned write count must stay below the probe ledger's entry ceiling.
    sampler-interval Compose sampler interval of 1–60 seconds. Native Kubernetes has its own observer settings.

    primer-concurrency, primer-max-tenants The bound DATA primer accepts positive JavaScript safe integers when the selected source supports them. Defaults are one worker and at most 10,000 pending tenants per invocation. Both settings are bounded by the actual pending roster.
    population-ceiling Optional whole-registry population budget for a fresh discovery fixture. Omission retains 10,000. The seed must fit the selected budget and the source's UUID/array representation. Page, cache, byte, resource and primer chunk bounds stay independent.

Legacy source refuses an unsupported value before fixture preparation. A smaller maximum can produce a partial DATA result and leave its saved custody for the owner. The owned deployment requires complete priming before publishing the roster.

    The common intent selects this optional population budget with profile.population.maxTenants. Any explicit value, including a lower value, requires the pinned source's population-ceiling-v1 support. Preflight checks the actual cached image constructor before fixture preparation. Bootstrap's private primer configuration and every serving population budget must agree; the helper records effective values and private configuration hashes.

    The preflight's populationCommissioning describes a fresh seed's chunk budget. For 10,001 seed tenants, the unchanged primer default of 10,000 pending tenants per invocation reports PARTIAL_CHUNK_BUDGET and one tenant beyond that budget. Author primer-max-tenants: 10001 (common intent profile.phases.primerOptions.maxTenants: 10001) for one-invocation coverage budget. The helper keeps the author's value. Constructor or budget success does not establish DATA completion; the existing partial/custody oracle remains strict.

    The remote overlay has exactly binding, hostInventory, and resourceReference. binding contains existing controller protocol identity, endpoint/transport authority, expiry and extension identity; it must omit source, image, workload, tenants, report mode, resource selection and k6 mirrors. hostInventory is the existing sut/driver planning inventory with provider ID, CPU cores and RAM bytes; it is not measured headroom. For the existing supported external topology, the binding also retains its exact helperDependencies receipt. The projection derives the other fields and runs existing remote protocol admission. Unsupported remote resource profiles/PostgreSQL images still refuse; this does not extend application topology.

    Use the returned binding and remoteReceiptProjection with the version-2 receipt template in the authorized controller packet. cell.py prepare accepts --run-config /absolute/private/run.json instead of mirrored adapter flags. Only repository/dependency/receipt paths and output locations need environment-specific copies. Do not change workload to make a transport fit; incompatible projections refuse. Existing remote CLI flags and strict profiles remain available.

    The runner runs the paired source/plan preflight before deployment seeding. rehearse now executes its generated-program missing-URL control before deploy, then checks the actual tiny fixture through ordinary runtime preflight and traffic. A changed remote environment still needs its own small actual transport and probe qualification under separately authorized remote access. Offline CLI and protocol tests are not that qualification. An entered run stays on its original helper/configuration/receipt/clock and cleanup owner.

    Phase role snapshots retain an optional separate memoryObservation from cgroup-v2 memory.peak and memory.events. Peak bytes cover the container cgroup lifetime since birth or an external reset, not the measured phase. The reducer requires matching container identities and nondecreasing peaks/events; missing files or malformed reads remain UNMEASURED. It never subtracts peaks or sums independent role peaks as a concurrent total. Existing raw cgroup counters, current memory and configured-limit checks keep their separate meanings.

    Outcome evaluator gate¶

    Decision outcome-evaluator-gate replaces the lifetime failedCompletions == 0 rule and the instant midpoint readiness rule. outcome_gate.py is the one frozen gate; its identity is the SHA-256 of that file. Tenants, rate, windows, budgets and deadlineMs (default 120000) are configuration under the same identity.

    component FAIL UNMEASURED
    failed completions (lifetime counters at the end point) untyped, unknown, hard or unrecognised reason, or a transient failure still open past the deadline typed rows without reasons or resolution fields; a transient still open at the end inside the deadline; no end point
    isolation runtime reset, foreign row ready, foreign counters changed, duplicate owner one point only
    readiness evaluator health or scope failure missing terminal inspection
    storage count oracle RED oracle missing or not GREEN
    sampled oracle probe completedOutput FAIL missing
    accepted-input catch-up an accepted input missing durable output by end of drain or known late from acceptance incomplete input identity, source, timing or output evidence

    Resolved verification-pending and startup-warming failures are counted by reason. Their maximum resolution time describes the process lifetime. The clinical deadline uses the current run's HTTP acknowledgement and tenant-bound durable output. On replay, the gate checks distinct input identities against each writer's accepted count and compares individual keys wherever the writer records are available. Until the source declares view.failureReasonContract = evaluator-failure-reasons-v1 with progress.failureReasons, unresolvedFailure and maxFailureResolutionMs, every failed completion is untyped and fails.

    The midpoint is a signal. The runner records load/evaluator-midpoint-signal.json and stops the driver only for a hard reason (a FAIL above, or an evaluation alert). A not-ready owner at the midpoint continues. Raw responses are written before any decoder reads them (load/evaluator-progress-raw/). The verdict is load/outcome-gate.json` and the discovery check `outcomeGate; HTTP latency over every k6 shard summary is reported beside it (exact pooled count and mean; per-shard quantile ranges; pooled quantiles UNMEASURED). assessor.py <load> re-reduces a retained run into a new file beside it and refuses if any original file changes.

    Planned evaluator restart during local discovery demand¶

    For a new local capture, restart-during-load-after-seconds selects a planned restart of the complete rendered evaluator roster while ordinary k6 traffic and the stock-client probe continue. This mode requires discovery, completion contract evaluator-work-v2, a version-2 configuration-bound receipt, probe cadence at most 1000ms, and at least 60 seconds between selected delay and the end of offered load. Example preparation fields are restart-during-load-after-seconds: 60, load-seconds: 310, and probe-every-ms: 1000. The default remains unchanged. A one-second probe adds one global clinical witness write per second, separately from ordinary offered scenario RPS. It does not write once per tenant per second.

    The local recovery example selects 37 tenants, 16 logical viewers, 20 offered scenario RPS and a restart after 30 seconds of a 90-second load. Replace every source, image, dependency and receipt placeholder, then use project to generate the configuration-bound receipt template for authorization. Use the exact Node executable recorded by the dependency receipt. The external pgstream resource profile derives one nginx worker from its 125-millicpu quota; native preflight verifies the rendered running configuration.

    The delay begins after the actual first ordinary scenario marker, following JWT setup. Existing exact-owned mutation checks and restart.cjs verify evaluator container replacement. The existing recovery oracle requires a changed runtime and successful fresh owned acquisition. Separate typed durable bookends require unchanged sampled registry/lifecycle authority and restore generation, monotone accepted/completed positions, and clinical completion of the pre-restart targets. This planned bracket retains the unplanned-runtime-reset hard stop in the default load observer. It does not claim observation of every instant between bookends.

    The probe keeps uploading and keeps stock sockets open during the evaluator restart. Final qualification requires actual later viewer-bound requests, their completed output and matching stock frames. Missing witnesses refuse the result. Stored ordinary writes, clinical probe writes, completion floors and client frames remain separate denominators. The receipt records partial captures and the fixed finite runner guard continues to own exact cleanup. Source/image acceptance is separate; this helper capability does not require another application campaign.

    The remote supervisor has a different load route. Remote projection explicitly refuses this selection as REMOTE_DEMAND_RECOVERY_LOCAL_ONLY; a coordinated controller/deployment implementation is required before a remote capture can use it. Offline mocked scheduling and controls qualify helper behavior; native restart-under-demand remains UNMEASURED until an actual selected capture runs.

    Memory observations bind each read to Docker inspect State.StartedAt from the owned container census and matching post-read inspect. A changed start timestamp with the same container ID separates the two cgroup lifetimes. Their peaks remain separate observations and the phase gap/events delta are UNMEASURED. Same-lifetime counter rewinds still refuse. Captures without verified birth metadata retain unknown continuity; this does not repair old captures.

    Reuse a bounded local fixture¶

    session-start uses the existing runner configuration and its prepare and deploy paths. It retains any explicitly selected resources. It seeds once and prints the session owner token and original cutoffs. Preparation consumes the same workSeconds. The original independent guard remains responsible for cleanup; retain its helper worktree unchanged until exact absence. An existing point, foreign fixture or sealed run cannot be adopted into a session.

    python3 -B tools/mt-bench/m7-joined/runner.py session-start CONFIG.json /mnt/data/nightscout-workspace/artifacts/example-lane/session01
python3 -B tools/mt-bench/m7-joined/runner.py session-observe /mnt/data/nightscout-workspace/artifacts/example-lane/session01 \
  --owner OWNER_FROM_SESSION_START --name first --config CONFIG.json
# A second named observation uses the same seeded physical fixture.
python3 -B tools/mt-bench/m7-joined/runner.py session-observe /mnt/data/nightscout-workspace/artifacts/example-lane/session01 \
  --owner OWNER_FROM_SESSION_START --name repaired-collector --config COLLECTOR-CONFIG.json
python3 -B tools/mt-bench/m7-joined/runner.py session-close /mnt/data/nightscout-workspace/artifacts/example-lane/session01 --owner OWNER_FROM_SESSION_START

    Each observation records fixture reuse. The optional --history argument accepts legacy operator metadata.

    A later observation can select a newer collector and receipt, workload timing, a configured driver plan, viewer count or existing TIME/recovery observation options. Discovery and smoke tiers generate each observation's receipt from its own configuration. To measure a write-rate change on the same roster, change driver-plan.writeRateScale in a realistic-v1 observation. To compare tenant counts, start a session with the new roster and match the per-shape aggregate read and write rates across sessions. Each observation has a distinct run ID for storage and probe accounting. All other preparation options, the application image, source/deployment pair, dependency roots, topology, configuration and resource ceiling must stay compatible. The existing attach and preflight paths check the physical resources and current runtime/authority contracts. The original guard can stop later collector jobs and exact-owned oneoffs without adopting their helper version. Cleanup of the runtime always uses the original helper and owner. Observations are serialized on this fixture, using the existing diagnostic driver lock without a bypass.

    Collector or phase failure retains partial observations and the runtime until its owner closes it or the original guard expires. A new name is a new observation, not an automatic retry of uncertain writes. Inspect the original result and account for previous effects before choosing another scenario. Compatibility or authority refusal stops that observation; it does not license source or state replacement. Missing optional metrics remain scoped gaps. Interrupting a collecting command invokes original cleanup. Losing the coordinator leaves the independent finite guard responsible at the original cutoff. Close is idempotent; resources remain reserved until cleanup and independent absence are confirmed. No command extends a deadline, paid budget or resource allocation.

    Focused local tests exercise the actual attach function with synthetic filesystem and resource readbacks, two named runner observations, retained collector failure, compatibility refusals, default cleanup and real finite child termination. Docker, application clinical execution and remote transport reuse are UNMEASURED here; this helper change grants no application acceptance or paid-resource authority. Diagnostic resource profiles derive nginx worker processes from the role's CPU quota (ceiling of millicpus / 1000). Preparation passes the explicit count to the deployment producer and records the generated config digest. The existing connection budget remains 16384 per worker. Preflight reads exact-owned nginx -T output and refuses an omitted, automatic or changed worker count before traffic. This qualifies the fixture configuration; it does not measure edge or application capacity. Default deployments retain their existing automatic count.

    Discovery pgstream-sample observations now declare a prospective standalone k6 driver allocation of 2 CPU cores and 4 GiB in loadgen-resource-allocation.json. The original session resource record and server limits remain unchanged; the sidecar records the replaced 0.5-CPU/1-GiB standalone reservation and the effective combined ceiling. Native launch, container census and oneoff custody validate the new allocation together. Strict observations retain the original driver limits.
