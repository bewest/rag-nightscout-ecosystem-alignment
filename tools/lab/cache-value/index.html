    cache-value lab¶

    Living document, last changed 2026-10-29 at 329da703e.

    What cgm-remote-monitor's in-memory cache still saves on a single-tenant site, and a reproduction of an over-broad cache flush. Synthetic data only; never a real site or real health data. Approved by the maintainer 2026-10-29.

    Marks: [M] measured in this lab, [R] read from code, [A] an assumption of the lab's traffic model.

    Containers run with --ulimit nofile=64000:64000, no --rm (mongo.sh). The API secret is generated per run into a state directory outside git and is never written into results.

    Code read first [R]¶

    • lib/server/cache.js: retention 60 h treatments, 48 h entries, 24 h devicestatus (48 h with devicestatus.days == 2). isEmpty is "fewer than 20 records". dataChanged: a remove with no changes empties all three caches and bumps all three removal generations (Part 1). invalidate(type) exists for a per-type flush.
    • lib/data/dataloader.js: with a warm cache the entries, treatments and devicestatus loaders query a 15-minute window; with isEmpty they query 48 h / 60 h / 24 h. Each reload also runs the other loaders (profile, food, activity, profile switches, latest sensor/insulin change treatments), which do not depend on the cache: a warm reload is 13 queries (8 of them on treatments) and 1 command [M].
    • lib/api3/storage/mongoCachedCollection/index.js: per-record cache updates for insertOne/replaceOne/updateOne/deleteOne; deleteInCache(undefined) (a no-changes remove, so all three caches) after the filter-AST writes and after deleteManyOr of more than one document. The comment there says it drops "this collection".
    • lib/server/storage-writes.js: v1 writes go through the plain MongoCollection (lib/server/storage-reads.js collection()), not the cached wrapper; the v1 modules emit their own data-update.
    • lib/storage/mongo-storage.js: DEFAULT_POOL_SIZE = 5, LEGACY_POOL_SIZE = 100; maxPoolSize from env.mongo_pool_size, else 5; minPoolSize from env.mongo_min_pool_size, else 0; maxIdleTimeMS 30000. lib/server/env.js reads MONGO_POOL_SIZE / MONGO_MIN_POOL_SIZE via readENV, which also accepts the lowercase name and the CUSTOMCONNSTR_ prefix [R]; MONGO_POOL_SIZE=100 and mongo_pool_size=9 both reach env.mongo_pool_size [M].
    • v1 GETs from memory: entries (lib/api/entries/index.js query_models) when the only find key is type and count ≤ cached length; treatments (lib/api/treatments/index.js) only when count is the only query key and the cache holds at least count records (default count 100, so a site with fewer than 100 treatments in 60 h never serves /treatments.json from memory); devicestatus (lib/api/devicestatus/index.js) when the only key is count and the cache holds at least count.
    • lib/server/bootevent.js: tick (every HEARTBEAT s, default 60) and data-received call a debounced reload (1 s wait, 5 s max wait, leading and trailing).

    Part 2: what the cache saves¶

    Method¶

    • Five arms run in parallel, in real time, each with its own MongoDB container, its own server process and its own replay process started at the same moment with the same schedule (run.sh). Real time, not compressed: compressing would shrink the heartbeat and follower intervals but not the dataloader's 15-minute window or the debounce, so a warm reload would return many more records than on a real site (the compressed smoke run in results/smoke shows this; its figures are not used).
    • Arms: base-a and base-b (dev, cache, pool default 5: the noise floor), cache-pool100 (dev, MONGO_POOL_SIZE=100), bypass-pool5 and bypass-pool100 (dev + patches/cache-bypass.patch). The bypass makes cache.isEmpty always true (every reload is a long load) and makes the three v1 GETs never serve from memory. The cache still exists and is still filled.
    • Seed: the Part 1 history. Traffic [A], per arm (replay.js):
    • uploader: a v1 entry and a devicestatus every 5 min, devicestatus alternating v1 and v3 (JWT from an admin subject); a treatment every 40 min alternating v1 and v3;
    • follower 1: GET /api/v1/entries/sgv.json?count=1 every minute;
    • follower 2, every 5 min: entries/sgv.json?count=288, devicestatus.json?count=1, treatments.json?count=10;
    • follower 3, every 5 min: entries.json?count=300&find[date][$gte]=<24 h>, treatments.json?find[created_at][$gte]=<24 h>, devicestatus.json?count=2 (the first two are never served from memory, in either arm);
    • the website: one socket.io connection, authorize with the secret. Followers authenticate with the API secret header [A].
    • Bypass control (in replay.js, before hour 0): 20 entries/sgv.json?count=1 and 20 devicestatus.json?count=1, counting serverStatus opcounters.query. A cache arm must cause fewer than 10 queries, a bypass arm at least 40. Shown red for the right reason with the declarations swapped (results/bypass-check-red.txt: "caused 0 MongoDB queries: FAIL: expected every one to read MongoDB" and "caused 40 MongoDB queries: FAIL: expected them served from memory").
    • Measures per hour: serverStatus deltas (opcounters, metrics.document.returned, network.bytesOut minus the sampler's own two serverStatus replies per sample), client-side request latency p50/p95, server RSS and data-loaded count from preload.js, connections.current.
    • Atlas M0 column: MongoDB, "Atlas Free Cluster Limits", https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/ , read 2026-10-29 (the page shows no last-updated date): "Free clusters: 100 operations per second"; "a maximum of 500 connections"; "10 GB in and 10 GB out per period" (rolling seven days); 0.5 GB storage; throttling when a limit is exceeded. The page does not say whether commands (as opposed to reads and writes) count toward the operations limit, so the ops/s column counts CRUD plus commands, which is the upper reading. Bytes out per 7 days is the hour's figure × 168. These figures are a local 8.0.34 server's counters, not Atlas's metering.

    Reading the measurements:

    • [M] Noise floor (base-a vs base-b): CRUD ops and documents returned agree within 2 per hour; bytes out within 0.1 % in hours 1 and 3. Hour 2 of base-a (and of cache-pool100 and bypass-pool5) carries a 5-minute command-breakdown probe this lab ran by hand (three extra connections, ~250 KB of serverStatus replies, ~60 commands), which explains base-a hour 2's 2.20 MB against base-b's 1.96 MB.
    • [M] Reloads: 85-86 per hour in every arm (60 heartbeat ticks plus the uploader's posts). The cache does not change how often the server reloads, nor the number of queries per reload; it changes the window, so what the cache saves is documents and bytes, not operations. The operations it saves are the follower GETs it serves from memory (≈9 finds per 5 min here).
    • [M] Commands are more than half of all operations in every arm; in the 5-minute breakdown they are mostly driver monitoring (hello 178, isMaster 21-35, dbStats 7). Whether Atlas counts these toward the M0 operations limit is not published on the page read.
    • [M] Pool 100 against pool 5 (same cache mode): about 40-57 more CRUD ops and 120-200 more commands per hour (more isMaster, i.e. connection handshakes, and more update in opcounters), 1-2 more connections, no latency difference beyond the hour-to-hour spread. With this traffic the server never had more than 12 connections open (including the replay's own).
    • [M] Against M0: at this traffic, average operation rate is under 1 % of 100/s in all arms (per-second peaks were not measured). Bytes out is the limit the cache matters for: about 0.33 GB per 7 days with the cache, about 10.7 GB without, which is above the published 10 GB out per rolling 7 days. These are a local server's counters, not Atlas metering, and the traffic is the model above [A]; a site with more followers or a larger devicestatus scales the bypass figure roughly with the long-load size.
