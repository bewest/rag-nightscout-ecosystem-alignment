    commit-event-bench lab¶

    Living document, last changed 2026-10-29 at c1c0bcdbd.

    Measures what decision D-EVENT would cost and buy. Today (dev 9668b179), lib/storage/write-step.js publish() emits the internal event storage-write-committed once per driver call (insertOne … bulkWrite). Its frozen payload is {collection, source, operation, partial, counts:{inserted, upserted, modified, deleted}} and names no record. Option 1 keeps one event per call and adds records: [{change, _id, identifier?}] for every record the call inserted, upserted, modified or deleted. Option 2 keeps the payload as it is.

    Contributor-facing. Synthetic data only: the lab writes its own records into its own databases and must never be pointed at a real site.

    Status¶

    D-EVENT was deferred on 2026-10-27. No event shape is adopted. This lab is research to inform that decision, and it continued after the deferral.

    • Round 1 compares base with the uncapped pre-read variant.
    • Round 2 (below) adds three arms:
    • the post-write variant
    • the same variant with counts-only deletes
    • a pre-read capped at 500 records (the pattern Nocturne uses)
    • Round 3 (below) adds Ben's since-watermark arm. Each table reports misses (which matter for a cache catch-up) and cross-attribution (which matters for a per-write event) separately.
    • Prior art. Comparable systems name records from the database's own log (change streams, an oplog or write-ahead log) or by a read before the write. A read after the write cannot see deleted records. It also misses records whose filter fields the update itself changed. Round 2 measures both of these.

    What it measures¶

    axis script question
    (a) bench.js Write latency and throughput of 16 write shapes and two 1,000-record backfills, base vs prototype, with arms interleaved
    (b) payload.js Event bytes at 1, 100, 1,000 and 10,000 records per call, the cost of naming them (in-process, through each tree's write-step.js), and what a listener pays to act on the event
    (c) changefeed.js Can a consumer rebuild which records were created, modified or deleted from the events alone, or does it need a follow-up read? Ground truth is MongoDB's change stream
    (d) concurrent.js With 3k uploaders at once (k = 1, 2, 4), plus an optional pruner racing the CGM bridges: latency, throughput, and whether any event names another writer's record

    The prototype (option 1)¶

    Branch proto/d-event-per-call in externals/cgm-remote-monitor-official, head 8a396715 (parent 9668b179). It changes only lib/storage/write-step.js and tests/write-step.test.js.

    • Inserted and upserted records come from the driver result (insertedId(s), upsertedId(s), keyed by operation index), with the identifier of the document that was sent. This needs no extra I/O. In a partial batch, the records the driver did not commit (its writeErrors, and everything after the first error in an ordered batch) are left out.
    • Matched records (update, replace and delete) are named by one read before the write. The read is find of the call's filters (an $or when there are several), projected to {_id, identifier}, with limit(1) for single-document calls. There is one read for updates/replacements and one for deletes. This read is the cost of option 1.
    • The read runs only when a listener is attached (bus.listenerCount(...) > 0). Nothing subscribes in production today, so as of 9668b179 production would pay nothing (arm proto0 below).
    • A failed identity read does not fail the write. The event then names only what the result names.
    • The read is not atomic with the write. A concurrent writer can insert or delete a matching record between the read and the write. counts still come from the driver, so a listener can see when a change kind has more or fewer records than its count, and treat that event as inexact.
    • The event stays internal, frozen (records and each record frozen) and off public channels. It still carries no document contents and no selectors.

    Tests changed: in tests/write-step.test.js, the first test used to assert that the stored _id is absent from the event (!includes('stored')). That pins option 2, so it now pins the named record. Three tests are new: identity for insert, delete and a mixed upsert batch (including the projected read); the committed records of a partial batch (unordered and ordered); and no identity read without a listener. The other five tests that listen for the event (storage.v1-writes, api.crud-by-id.matrix, api3.storage.filter-semantics, websocket.partial-reconciliation, api3.configured-write-boundary) check only collection, source and counts. They pass unchanged.

    Controls for the new tests: - Red on base. The proto test file on the base tree has 3 failing tests (21 passing), and each fails because records is undefined. - Break-it. Removing the listener gate (return true || ...) makes "reads nothing for record identity when no listener is attached" fail. That test passes vacuously on base, because base never reads.

    npm test (MongoDB 8.0.29 on 127.0.0.1:27602, Node v22.23.4): - proto 8a396715: 4703 passing, 0 failing, 3 pending - base 9668b179 (control, port 27603): 4700 passing, 0 failing, 3 pending

    The trees are set by CEB_BASE, CEB_NOOP and CEB_PROTO, and default to externals/work/crm-devent-{base,noop,proto}. Each tree needs its own npm ci. The API secret is generated per run and is never written to disk. Each arm is its own server.js child: the tree booted as lib/server/server.js boots it, with its own database. Every log starts and ends with the container's docker inspect state and restart count.

    (c) Change-feed reconstruction, 5 calls per shape and arm¶

    Ground truth is the MongoDB change stream of the arm's database. The window is bounded by start and end sentinel writes: startAtOperationTime is inclusive of the seed write, so the stream skips to the start sentinel first.

    shape (all 20, including query deletes of 100 and 1,000) base: names exact base: events needing a follow-up read proto: names exact proto: events needing a follow-up read
    every shape 0 / 5 (no records) 5 / 5 5 / 5 0 / 5

    Every shape is exact on proto (100 / 100 calls, 10,000 + 5,550 change-stream operations in the bulk and query-delete shapes). On base every changing event needs a follow-up read, because counts say how many records changed, never which.

    Controls (results/changefeed.log): - BROKEN-drop-last (option 1, but drops each event's last record) is reported wrong in 100 / 100 proto calls. - BROKEN-guess (counts only, guesses that the newest count documents are the created ones) is reported wrong for every update, delete and resend shape. It is right for the single-writer create shapes (5 / 5 on most of them; 1 / 5 on socket dbAdd). A serial test of creates alone cannot tell a counts-and-guess consumer from a correct one.

    Verdict (round 1: base vs uncapped pre-read)¶

    • With no subscriber, option 1 is free. proto0 is inside the base-vs-base noise floor on all 18 shapes, because the identity read is gated on a listener and nothing subscribes today.
    • With a subscriber:
    • It is free for inserts (driver result).
    • It costs one extra round trip per update, replace, delete or upserting call: about +0.4–1.8 ms median on 4–8 ms requests (+7–33%) on localhost, and 2–5% of concurrent throughput.
    • The expensive case is the v1 upload path. v1 entries and treatments POSTs are upserting bulkWrites, so a 1,000-record backfill pays a 1,000-way $or read: +24 ms (+13%) for entries, +106 ms (+27%) for treatments over HTTP; +39% in-process at 1,000 and 10,000.
    • What it buys:
    • Single-writer reconstruction goes from 0 / 100 calls to 100 / 100 exact with no follow-up read.
    • The payload is about 55–105 B per record (about 1 MB at 10,000).
    • Acting on the event costs ≤ 0.5 ms at 10,000 records.
    • Not atomic. Exactness is not guaranteed under overlapping concurrent filters, but counts exposes every inexact event the lab saw.
    • Recommendation for review. The 27–40% bulk-upsert cost is the number to decide on. A cheaper variant was not built, per the lab's stop rule: name upserts from upsertedIds and read only the operations that did not upsert, after the write and only when matchedCount > 0. That would make a fresh backfill free. Its own exactness cost (a post-read misses records whose filter fields the update changed) is unmeasured.

    Not measured (round 1; see round 2 for what it added)¶

    • Network latency. Everything ran on localhost. On a hosted MongoDB every identity read adds a network round trip, so the absolute +0.4–1.8 ms will grow with the RTT.
    • MongoDB versions other than 8.0.29. A standalone mongod (only a replica set was used).
    • Node versions other than 22.23.4.
    • deleteOne, updateOne upserts and real-driver partial batch failures. Partial batches are covered only by the mock unit test.
    • The reject-mode validated update path (WRITE_VALIDATION=reject).
    • Client-visible socket dataUpdate latency, server memory, and event retention by listeners.
    • A base-vs-base noise floor for the concurrent axis.
    • The post-read variant above.
    • An event-by-event proof that every inexact event under the race shows records ≠ counts.

    Round 2 verdict¶

    • The post-write variant is not cheap overall.
    • It is free where the pre-read was most expensive: fresh uploads, single (×0.949–0.992) and bulk (treatments 1,000 +112 ms → +4 ms).
    • A full re-send pays the same read: +9–19%, up to +1.35 s on a 10,000-treatment re-send.
    • Deletes still need their pre-read: ×1.12–1.43 on single deletes.
    • It mis-names updates that move records out of their own filter, which the pre-read names correctly.
    • Under the pruner race it was inexact two to four times as often as the pre-read.
    • Every mis-name was flagged by records ≠ counts.
    • Counts-only deletes remove the delete cost entirely. But every delete event then needs a follow-up read, so a change feed cannot rebuild deletions from the event alone.
    • The capped pre-read is the cheapest arm on bulk writes. It is free on every backfill over 500 records. Below the cap it costs the same as the pre-read, and it keeps the pre-read's exactness. Its price: events over 500 records (the 1,000- and 10,000-record backfills) name nothing and say so with collapsed: true. That is the case where a listener's follow-up read is most expensive.
    • No arm adds a measurable throughput cost to the concurrent uploaders. Base-vs-base varies by up to 17% there.
    • PR-readiness. The post-write head was not made PR-ready (not squashed onto 9668b179 and not merged with official/dev 7abe1cf6), because by these numbers it is not cheap.

    Not measured in round 2¶

    • Network latency: localhost only, so every extra read is one localhost round trip.
    • MongoDB versions other than 8.0.29.
    • Caps other than 500.
    • A post-read issued asynchronously after the reply.
    • An HTTP route that sends a filter-changing update (none was found; the shape is internal).
    • postnodel under the concurrent run without the pruner.
    • An event-by-event proof under the pruner race that every inexact event is flagged. The in-process mis-naming test does prove it for its cases.
    • Memory and client-visible socket latency.

    Round 3 (2026-10-29): since-watermark¶

    The arm and its two uses¶

    Ben proposed this arm. After a write, the arm reads the collection back for every document with srvModified after a watermark: the last srvModified the process issued before the write, less a small overlap. The records are deduplicated by _id. Two uses judge the result differently:

    • (a) Cache catch-up. A cache refreshes after a query-based write instead of flushing. Only misses count: records this write changed that the read did not return. Records from other writers do no harm there. Load counts too: queries, bytes and latency.
    • (b) Per-write event. The event names "this write's records". Records from other writers are then errors, counted as cross-attribution (extra).

    Every table below gives both, as "missed" (both uses) and "extra" (event only).

    arm tree head what it does
    since proto/d-event-since-watermark 978aa282 (on post 408c7d03) inserts and upserts are named from the result.     since0 same tree 978aa282 overlap 0 (CEB_SINCE_since0=overlap=0)
    late0, late5 same tree 978aa282 break-it control: the watermark one write late (the call's last stamp instead of its first stamp minus one), overlap 0 and 5
    • The watermark. It is the smallest srvModified the call's operations carry, minus one. That is the last value lib/server/srv-dates.js issued before the call's first stamp. write-step.js runs after the route has stamped, so it reads the watermark from the stamps. A call with no stamp falls back to srvDates.last() (a new export) at the boundary.
    • No upper bound and no filter. The read returns everything any writer stamped after the watermark. The table in (d) shows what that costs the event use.

    • Red control: the since test file on post 408c7d03 has 5 failing tests.
    • Break-it: removing the _id dedupe makes 1 test fail.

    Findings (D-EVENT deferred; research continuing)¶

    • As a cache catch-up (use a):
    • Since-watermark missed nothing a single writer changed. That includes the filter-changing update, which the post-write read misses.
    • With concurrent writers and no pruner it missed nothing either.
    • Under the pruner race it missed 3–54 records per round, between pre (2–14) and post (9–86).
    • Its read is one indexed range read, so it costs nothing measurable on backfills of 1,000 and 10,000 records, re-sends included. The two $or arms pay +6–28% there.
    • It cannot see hard deletes. Deletes keep a pre-read, and that read sets the delete latency (+16–44% on single deletes, as for pre and post).
    • As a per-write event (use b):
    • With one writer it is exact.
    • With concurrent writers it attributes other writers' records to an event: 136–1,946 cross-attributed events per 20 s round, up to 5,845 extra records at k = 4. Pre and post attribute none.
    • Every such event was flagged by records ≠ counts.
    • The watermark is the safety-critical part. One write late with overlap 0, it misses every record of 13 shapes; every one of those events is flagged. The 5 ms overlap hides a late watermark only for calls that span fewer stamps than the overlap.
    • Unmeasured:
    • a read with an upper bound (srvModified ≤ the last value issued after the write), which would cut cross-attribution from later writes;
    • multi-process writers (one srv-dates clock per process);
    • network latency;
    • MongoDB versions other than 8.0.29;
    • the socket merge-patch edge above.
