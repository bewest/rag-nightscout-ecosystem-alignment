    Tenant-configuration call-path lab¶

    Living document, last changed 2026-10-27 at 4930ea69a.

    Contributor-facing. Lab approved by the maintainer on 2026-10-27 to inform the open question in execution plan §2.13 (D22, "Not decided"): how does a hosted owner dashboard reach the tenant-owner listener? The lab informs that decision. It does not make it. Synthetic tenants, owners and credentials only.

    Marks: [M] means the lab measured it, in the run recorded in results.json. [R] means it is reasoned from the code or the design documents and was not measured.

    What it compares¶

    A tenant is one Nightscout site on a shared host. Its owner is the person whose site it is. The operator runs the host.

    design how an owner's edit travels
    A, owner token end to end The dashboard logs the owner in at the identity provider, then trades that login for an owner token: a short-lived token signed with that tenant's own key (D14). Nightscout mints it after checking the login (D17). The dashboard sends the edit straight to the tenant-owner listener (ns-tenant-admin, D16) with that token.
    B0, trusted orchestrator, no identity The dashboard forwards the owner's login to an internal orchestrator. The orchestrator checks ownership itself, then writes the tenant's configuration through an internal API. Internal calls carry no identity and name the site in the URL.
    B1, trusted orchestrator, service tokens As B0, but every internal call carries a service token (a credential that names a component, not a person): dashboard to orchestrator, operator console to orchestrator, orchestrator to listener and to the secrets service.
    C, split by audience Owner edits travel as in A. Provisioning and suspension go through an orchestrator that lives only on the operator plane (D7) and that the dashboard cannot reach.
    AK, A with keys kept in the secrets service ("A-keys-stay", added 2026-10-27) As A, but tenant signing keys never leave the secrets service. The token exchange asks the secrets service to sign; the listener asks it to verify each token. The secrets service takes the tenant from the address, sets the claims and the token lifetime itself, and refuses to hand a signing key to anyone.

    What runs¶

    Six Node processes per deployment, plain http, each bound to 127.0.0.1. Ports 47410 to 47418 were free when the lab was built (checked with ss -ltn).

    process port(s) role
    roles/idp.js 47410 identity provider stub: password in, signed assertion naming the human out
    roles/dashboard.js 47411 owner dashboard backend
    roles/tenant-admin.js 47412 public, 47413 internal ns-tenant-admin: token exchange, owner API (A, C), service API (B); policy and floors
    roles/ns-admin.js 47414 platform operator plane (D7): no credential; tenants, suspension, operator policy
    roles/orchestrator.js 47415 B: owner and operator routes. C: operator routes only. Not started in A or AK
    roles/secrets.js 47416 public, 47417 internal, 47418 operator secrets: AES-256-GCM at rest, consume, logged reveal; the operator port provisions and never reveals; in AK also sign and verify for the listener, and no key leaves

    lib/policy.js implements D22 over seven census names: AUTH_DEFAULT_ROLES (bounded list), WRITE_VALIDATION (floor log, owner may tighten), CONNECT_SOURCE_ENDPOINT (driver host allow-list), API3_AUTOPRUNE_ENTRIES (bounded 30 to 3650 days, confirmation and export offer), DISPLAY_UNITS (open), TRUST_PROXY (pinned) and DEBUG_LOGGING (pinned to its floor). Effective value: code default, then operator default, then owner value if the mode and constraint allow it, then operator pin.

    Network separation is a model, not isolation¶

    Every listener is on 127.0.0.1, so any local process could reach any port. The lab encodes the intended network as a reachability matrix (lib/net.js). It is enforced twice: the client refuses to dial a port its zone may not reach, and each server refuses a request whose declared zone may not reach it. The attack harness declares its zone truthfully. The open-matrix control shows the matrix is doing the work.

    How to run¶

    node harness.js --scratch /some/dir/outside/the/repo   # about 5 minutes; writes results.json
node harness.js --scratch DIR --only A,C,AK             # a subset (A, B0, B1, C, AK)

    Each run makes throwaway keys under DIR/runs/<n>-<design>-<label>/keys, starts every process with setsid nohup, records the PIDs, and stops them by those PIDs only. Each measured run checks that every process is alive, owns its ports and answers its health check, at the start and at the end. The harness refuses a scratch directory inside the git tree. results.json holds no key, token, password or revealed value.

    The five measures¶

    1. Blast radius. For each compromised component, which tenants can be read, written (owner value), changed by operator action (a pin), or have their connector credential revealed. The attacker acts from that component's network position and from the internet, with exactly the credentials it holds. Success is judged against the store and the stored secret, not by the response code.
    2. Audit. What the log records for an owner's edit, an attacker's edit, and an operator edit.
    3. Policy. Where the policy and floors are enforced, and whether a crafted request gets round them.
    4. Cross-tenant confusion. Whether tenant 1's owner can change tenant 2, and what stops it.
    5. Effort. Calls and credentials per edit, latency, and what the owner sees.
    6. Persistence (A, C, AK). What a compromised tenant-owner listener can do while the compromise lasts, and what it keeps after it ends: stolen keys, or tokens minted while it had a live signing service to ask. Run with a 3-second token lifetime so expiry can be observed.

    Every check has a control: the same deployment with one protection removed. A control reports when the check it targets changes. All 46 controls reported, and the liveness check failed when one process was killed by its PID [M].

    3. Policy [M]¶

    Policy and floors are enforced in ns-tenant-admin for every owner write, in all five arms (AK's results equal A's). Floors are enforced again in ns-admin for every operator policy write. The dashboard's own check (hidden keys) is a convenience; every crafted request below skipped it.

    attempt A B0 B1 C
    pinned TRUST_PROXY through the dashboard refused, dashboard refused, dashboard refused, dashboard refused, dashboard
    same, crafted request skipping the dashboard refused, pinned refused, pinned refused, pinned refused, pinned
    owner floors: WRITE_VALIDATION=off, anonymous-write role, link-local connector host refused, floor refused, floor refused, floor refused, floor
    owner outside the operator's bound (status-only; autoprune 7 days) refused, constraint same same same
    autoprune 90 days without, then with, the confirmation phrase 409, then accepted same same same
    open and tightening edits (DISPLAY_UNITS, WRITE_VALIDATION=reject) accepted accepted accepted accepted
    re-pin TRUST_PROXY from the dashboard's network position unreachable accepted refused, caller token unreachable
    operator plane pins an anonymous-write role, a link-local host, WRITE_VALIDATION=off refused, floor same same same

    Controls: no-policy let the crafted pinned write and the out-of-bound writes through. no-floors let the owner and operator floor breaches through. no-confirmation let autoprune through without the phrase. open-matrix and b1-no-service-token let the dashboard re-pin.

    Also measured: dev's code defaults break two floors. WRITE_VALIDATION defaults to off, and TRUST_PROXY to empty. Under multi, the operator policy has to set both, or the tenant is refused at provisioning [M, policy engine]. The WRITE_VALIDATION default is read from a dev-based checkout (lib/server/env.js:129); the empty TRUST_PROXY default is taken from the census, §3 item 5 [R].

    6. Persistence: during the compromise, and after it [M]¶

    The attacker controls the tenant-owner listener (its network position and its service token), writes, collects what it can carry, then loses both. Token lifetime is 3 seconds in this run.

    A, C AK
    writes during the compromise all all (through the signing service)
    signing keys carried out 3 0 (the secrets service refuses to hand a key out)
    tokens carried out, longest lifetime 3, 900 s (the attacker set it, holding the keys) 3, 3 s (the secrets service set it; the attacker asked for a day)
    writes after the compromise, before the tokens expire all all
    writes after expiry all (mints fresh tokens with the stolen keys) none (expired, and signature for forgeries)
    reveals after expiry all none

    So AK changes what is kept, not what is reachable during the compromise. In A and C, recovery means rotating every tenant's signing key; until then the stolen keys mint tokens for every tenant. In AK the attacker keeps only tokens that live as long as the secrets service allows, and recovery means ending the compromise and waiting out that lifetime [R].

    Controls (AK): - consume-allowed (the secrets service hands the key out, as in A): 3 keys carried out; writes and reveals after expiry went from none to all. - sign-accepts-exp (the sign endpoint honours the caller's expiry): writes and reveals after expiry went from none to all. - sign-any-caller (a sign endpoint on the public port with no caller check, any tenant): tenant 1's owner credential, the dashboard and the operator plane each wrote and revealed every tenant. - verify-skips-tenant: see §4.

    What the lab does not model¶

    • Real network isolation. One host, one loopback address, a matrix in code.
    • A real identity provider. Passwords and an Ed25519 assertion; no sessions, MFA, recovery, or federation.
    • Real key management. The key-encryption key is a file in scratch that only the secrets process reads, and every process runs as the same user. No rotation, no versioning (C.3, E.3), no hardware or cloud key service.
    • The database. One JSON file stands in for PostgreSQL. There is no row-level security. A compromised ns-tenant-admin can write every tenant's row directly [R].
    • Performance, scale, concurrency and availability.
    • The connector process. The secret's consumer is named, not run.

    Notes on the controls¶

    Some controls changed more than their target. These side effects are expected, and the full changed list for each control is in results.json:

    • install-wide-key also emptied the "secrets API caller" row. In that control the key sits in a file beside the listener, not in the secrets service. This is an artifact of the control, not a protection.
    • no-ownership-check also cut one call from B's edit, because it skips the membership lookup.
    • install-wide-key (A, C) also emptied the "tenant-owner listener" row, for the same reason.
    • no-sig-verify in AK also cut the verify call from each edit.
    • Controls that do not target §6 do not re-run it; their §6 values are copied from the baseline.
