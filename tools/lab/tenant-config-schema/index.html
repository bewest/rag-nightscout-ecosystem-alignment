    Tenant configuration schema lab (T30-SCHEMA-CONFIG)¶

    Living document, last changed 2026-10-27 at 1670247de.

    Contributor-facing. Built 2026-10-27 to support the tenant configuration schema spec (queue T30-SCHEMA-CONFIG) and the migration-tooling plan. It uses synthetic tenants, hosts and credential references only. No real data and no real credentials are involved.

    Marks: [M] means this lab measured it, in the run recorded in results.json. [R] means it is read or reasoned, not measured.

    What it is¶

    The lab has three parts:

    • The schema, as eight ordered migrations in migrations/, each with a .down.sql.
    • 0001 is the seam's lib/admin/platform.sql from cgm-remote-monitor 81a1f6ce, byte-identical below a three-line header. It has the same sha256, b50efaf0…, as git show 81a1f6ce:lib/admin/platform.sql.
    • 0002 changes tenant_members so that a person is identified by identity provider and subject, as text, unique together within a tenant, with no foreign key (maintainer, 2026-10-27). It refuses to run while the table holds rows, because nothing records which provider issued them.
    • 0003 to 0008 add the configuration tables without altering tenants. They were 0002 to 0007 in the first run, renumbered before anything shipped.
    • A runner, lib/migrator.js, which drives the migrations through umzug 3.8.3. It adds the three things umzug leaves to its caller: one transaction per migration and its ledger row, an advisory lock, and a checksum drift check.
    • A harness, harness.js, with 59 tests. Each test runs twice on a fresh database cloned from a migrated template:
    • the pass run must be green;
    • each control removes the protection under test, and the same test must then go red.

    A control that stays green is reported as VACUOUS?, and the harness exits non-zero. A control whose setup fails is reported as a setup error and never counted red. (Run 3 of this lab found one such control, whose SQL still named a dropped column. Raw tests, which set up inside run, are not covered by that guard; their assertions match specific messages instead.) - A tool comparison, compare.js, which measures umzug against node-pg-migrate on PostgreSQL, and umzug (with a project ledger and lease lock, lib/mongo-migrator.js) against migrate-mongo on MongoDB, for the same five properties. Results are in compare-results.json; the side-by-side table is in the migration-tooling plan §3. - MIG-VV, mig-vv.js, which repeats the MongoDB rows on four servers: - MongoDB 8.0 standalone and as a three-member replica set; - MongoDB 5.0.32 (dev's floor) standalone and as a replica set.

    It adds a primary step-down during a migration, and the adapter running a migration and its ledger record in one transaction (--txn 1). Results are in mig-vv-results.json; the table is in the plan's MIG-VV section. Each replica set is one container running three mongod processes on the host network, bound to 127.0.0.1 (mongo-rs/start-rs.sh).

    Roles, and why the isolation tests are not vacuous¶

    bootstrap/roles.sql creates four roles. The harness gives each one a random password per run and keeps it in memory only.

    role is owns
    cfg_owner the migration role: NOSUPERUSER NOBYPASSRLS every table (it runs the migrations)
    ns_operator the operator plane (D7) nothing
    ns_tenant_admin the tenant-owner listener (D16) nothing
    ns_api the consumer, evaluator and connector roles (D5, D21) nothing

    Every tenant-scoped check runs as a non-superuser, non-owner application role. A superuser bypasses RLS and would make an isolation test pass whatever the policy says. The harness checks this three ways:

    • ISO-roles asserts that each role is NOSUPERUSER NOBYPASSRLS, owns no table, and has row_security_active() true on every tenant table. Its control adds the container superuser to the list, and the test goes red. [M]
    • Every ISO-<table> test has a second control that repeats the same reads as the superuser. It goes red on all seven tables, because the superuser sees tenant B's rows. [M]
    • ISO-roles' second control removes FORCE from one table, and the owning migration role then escapes RLS. [M]

    How to run¶

    You need Docker, Node 22 and a free port. The lab used 5447, checked free with ss -ltn.

    S=/path/outside/the/repo            # holds the superuser password; never inside the repository
mkdir -p "$S" && chmod 700 "$S" && (umask 077; openssl rand -hex 24 > "$S/pg-superuser-password")
docker run -d --name cfgschema-pg -p 127.0.0.1:5447:5432 \
  -e POSTGRES_PASSWORD="$(cat "$S/pg-superuser-password")" postgres:16
cd tools/lab/tenant-config-schema && npm ci
node harness.js --secrets "$S"                    # about 60 s; writes results.json
node harness.js --secrets "$S" --only isolation   # one group, or test ids; results.json untouched

# the tool comparison also needs MongoDB (port checked free with ss -ltn)
(umask 077; openssl rand -hex 24 > "$S/mongo-root-password")
docker run -d --name cfgschema-mongo --ulimit nofile=64000:64000 -p 127.0.0.1:27747:27017 \
  -e MONGO_INITDB_ROOT_USERNAME=labroot -e MONGO_INITDB_ROOT_PASSWORD="$(cat "$S/mongo-root-password")" mongo:8.0
node compare.js --secrets "$S"                    # about 2.5 min; writes compare-results.json

# MIG-VV: a replica-set keyfile, then 8.0 and 5.0 replica sets and a 5.0 standalone
(umask 077; openssl rand -base64 756 > "$S/rs-keyfile"); chmod 644 "$S/rs-keyfile"   # inside a 700 directory
for spec in "cfgschema-mongo8-rs mongo:8.0 27750 27751 27752" "cfgschema-mongo5-rs mongo:5.0.32 27753 27754 27755"; do
  set -- $spec
  docker run -d --name $1 --network host --ulimit nofile=64000:64000 \
    -e MONGO_ROOT_PW="$(cat "$S/mongo-root-password")" -v "$S/rs-keyfile:/run/lab/keyfile:ro" \
    -v "$PWD/mongo-rs/start-rs.sh:/run/lab/start-rs.sh:ro" --entrypoint sh $2 /run/lab/start-rs.sh $3 $4 $5
done
docker run -d --name cfgschema-mongo5 --ulimit nofile=64000:64000 -p 127.0.0.1:27748:27017 \
  -e MONGO_INITDB_ROOT_USERNAME=labroot -e MONGO_INITDB_ROOT_PASSWORD="$(cat "$S/mongo-root-password")" mongo:5.0.32
node mig-vv.js --secrets "$S"                     # about 15 min; writes mig-vv-results.json

    Before every run, the harness asserts that cfgschema-pg is running and is published on 127.0.0.1:<port>. compare.js also asserts that cfgschema-mongo is running on 127.0.0.1:27747 with the 64000 nofile limit. mig-vv.js asserts the same for each of its four servers before every row, and checks that each replica set has three members. It refuses a --secrets directory inside the repository.

    Observations worth reading in results.json¶

    • The §A.2 draft, measured (MMOL-old-shape-profile). On the old shape:
    • the partial override {"bgHigh": 14} is accepted;
    • the complete mmol set, the integer mmol-looking set, the misordered set and a string threshold are refused with 23514.

    So the old CHECK is live, and only the NULL path lets the partial override through. The document's second hole, a cast error instead of a clean refusal, was read-derived. It did not reproduce on this input: the string threshold gave 23514, not 22P02. That does not rule the hole out, because the evaluation order is still not guaranteed. [M] - The new shape (MMOL-stored-safely) refuses all five bad inputs, each with a message naming the reason, and stores 56/81/180/252 exactly. [M] - umzug's default split loses a migration, even when the kill comes mid-migration (MIGRATE-crash-mid, control). - With one implicit transaction per file and the ledger row written afterwards, a runner killed during migration 0005 (then numbered 0004) left it committed, because the server finished the statement after the client was gone. The ledger row was never written. - The orphaned server session ran for about 5.4 s after the kill. - In the lab's runner, which sends COMMIT and the ledger row in the same transaction, the same kill leaves nothing applied, and a re-run completes. [M] - Concurrent starters: four migrate up processes started together on an empty database. - With the advisory lock, one applied every migration and three found nothing pending. - Without the lock, 3 of 4 failed with duplicate key value violates unique constraint "pg_type_typname_nsp_index". [M] - The commit-time version guard is only as good as cfg_current_state (VERSION-numbered, control). If the state function is broken, every write still commits, because the guard compares the state with itself. The test catches this. The guard does not. [M]

    Compatibility with the seam¶

    • tenants is untouched, and 0001 is byte-identical to 81a1f6ce. [M] tenant_members is changed by 0002 only (provider column, text subject, the pair unique within a tenant). MEMBER-identity's control runs the same inserts on the seam's shape, which cannot hold them. [M]
    • New tables add tenant_id foreign keys to tenants with ON DELETE CASCADE.
    • The seam's ensureSchema (81a1f6ce:lib/admin/platform-store.js:120-158) creates the platform tables only when none of them exist. It cannot add these tables to an existing database, which is the migration-tooling plan's subject. [R]
    • tenantScopedTables() (platform-store.js:186-197) would discover every new table that has a tenant_id column. Those tables would enter the export and the deletion gate unless they are added to NOT_TENANT_DATA. This is an open question in the spec. [R]
