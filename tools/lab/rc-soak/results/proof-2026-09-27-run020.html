    The cob.lastCarbs question (R24 and R29)¶

    B no longer names an older carb entry. In run 018's R24 and run 019's R29, both arms named the same wrong carb entry before the server restart and different wrong ones after it (BF-133's mechanism on both trees). On ce30a94d the treatments are in time order:

    • R34 (R29's traffic and disturbances): in the 73 captured lastCarbs differences B names the newest carb entry (carb-189, then carb-585, 621, 657, 729, 765, 801, 837 as each is written), apart from the two write-tick timings above. A stays on older, edited entries: carb-153 before any disturbance (ticks 198 to 210), then carb-549 and carb-585, the entries R24 and R29 showed.
    • The differences now start before the restart, because only A is wrong there; before, both arms were wrong in step and the key comparison saw nothing.
    • The check trace-order.js from run 019, run on R34's kept databases after the run, found every treatment with a finite mills and the newest carb entry last on both arms after a fresh boot (A 794 treatments, B 779), as in run 019.

    So the R24/R29 findings did not disappear as differences: they are now 15.0.8 alone naming an older entry, which is the BF-133 defect #8784 fixes. They are classified under the new entry.

    R34's page-load finding¶

    21 differences, all BF-135's intended change, as in R29: run 018's scratch check finds 23 page loads on arm A (15.0.8) that send an AndroidAPS record whose v3 soft DELETE was acknowledged more than 10 s earlier, from tick 611 (the first page load after the server restart) to the end, and none on arm B. The analyser's 10 s rule leaves 21; the two other raw differences are readings acknowledged under 10 s before the load. Page loads have no expected-difference rule, so this stays a finding by design.
