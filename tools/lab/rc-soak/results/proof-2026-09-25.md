replaced by the growth difference over the evaluated span; R4 and R5 were re-analysed with it.

## Candidates

**CANDIDATE-1: a deleted record keeps being served from memory (B only).** On ab7b22d6,
`DELETE /api/v1/entries/<id>`, `/api/v1/treatments/<id>` and `/api/v1/devicestatus/<id>` answer
200 and remove the document from MongoDB, but the server's in-memory copy keeps it:

- `GET /api/v1/entries.json?count=10` (and `count=100`, `count=288`) keeps returning the deleted
  reading after 35 s and after a new reading arrives; the same read with a filter
  (`find[sgv][$gte]=0`), which goes to MongoDB, does not.
- `treatments.json?count=5` and `devicestatus.json?count=5` keep returning the deleted record.
- A newly opened web page is sent the deleted treatment in its first `dataUpdate` (R8: 36
  deleted records, some 24 minutes after the delete).
- Websocket `dbRemove` of a treatment does not show it (control, same probe).
- A (15.0.8) and dev 4f705217 do not show it, with the same probes on fresh databases.

Mechanism: `lib/server/entries.js` `remove()` emits `data-update` with `changes: opts.find._id`
after `query_for(opts)`; on B, `idForms.matchEitherForm` rewrites `opts.find._id` in place to
`{ $in: [<hex>, ObjectId] }` (confirmed with node against B's `lib/server/query.js` and
`object-id-forms.js`), so the cache's `removeFromArray` (`o._id == id`) never matches. On A the
same field is left as a single id. Ablation: a copy of ab7b22d6 whose `remove()` passes the id as
asked (branch `lab/6a-soak-ablate`, f76e6fd5, one file, +3/-1) passes `probe-deleted-entry.js`;
unmodified ab7b22d6 fails it in the same session. Only entries was ablated; treatments and
devicestatus were reproduced, not ablated.

Reproduce: `lab.sh up`, then `node tools/lab/rc-soak/probe-deleted-entry.js
http://127.0.0.1:17532 <run>/secrets/api_secret` (exit 1 on B, 0 on A).

Why it matters: a treatment deleted because it was entered by mistake (a bolus or carbs) is
still sent to newly opened pages and to readers of the unfiltered API, so insulin and carbs on
board shown there can include it until the server restarts or the record leaves the in-memory
window.

**CANDIDATE-2: `/api/v2/properties` `cob.lastCarbs` differs at one tick.** Once per run, at the
same tick in two different runs (tick 57 of a 24 h and a 48 h run; tick 195 of the 72 h run), B's
`cob.lastCarbs` has a `notes` field that A's does not, and asking again 3 s later gives the same
answer (R8). `notes` is set by the careportal edit of the latest Carb Correction (tick n%24==20).
The harness compares this endpoint by key set only, so the values were not captured; open.

## Observations that are not findings

- R6 (node 24.20.0, mongo 4.4): both arms' RSS rose to about 250 MB under load; after traffic
  stopped, A's last sample was 136 MB and B's 280 MB (one sample each). The heap check passed
  (10.8 MB, threshold 25). Watch RSS in the long soak.
- A socket.io `authorize` with a readable access token in the `token` field (instead of the JWT the
  web client sends) fails with "All validation failed" on both builds, and the failure adds the
  client address to the authentication delay list, after which every HTTP request from that
  address waits about 5 s. Seen while building the harness; by design on both arms.
- 45 s MongoDB outage (R6): 3 of 3079 requests per arm without a 2xx, every write retried and
  stored afterwards on both arms.
- `treatments.json?count=50` (harness 2, R8: 576 reads) did not differ between the arms, although
  the direct probe with `count=5` shows CANDIDATE-1 on treatments; not explained.
