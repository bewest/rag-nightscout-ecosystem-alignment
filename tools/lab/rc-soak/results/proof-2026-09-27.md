## Why `cob.lastCarbs` names an older carb entry (BF-133)

`lib/plugins/cob.js` sets `lastCarbs` to the last carb treatment in array order. The dataloader
sorts the treatments with `(a, b) => a.mills - b.mills`. The question left open by BF-133 and run
018 was why the array is not in time order.

**The cause: records written through API v3 reach the server's in-memory copy without `mills`.**
`lib/api3/storage/mongoCachedCollection/index.js` (`updateInCache`) emits the stored document to
the cache as it is (`changes: doc`). The v1 paths in `lib/server/treatments.js` pass their
documents through `ddata.processRawDataForRuntime`, which adds `mills`; the v3 path does not. The
cache keeps such a record (its age falls back to `date`). The dataloader builds
`ddata.treatments` from the cache and sorts it by `mills`. With a record whose `mills` is
`undefined`, the comparator returns `NaN` for every pair that includes it, so the sort result is not
defined by time and depends on the order the records came in. The code is the same on 15.0.8
(`mongoCachedCollection/index.js` line 117) and on 699eb5fa.

**How it was measured (T1).** T1 repeated R29's traffic and disturbances. After `lab.sh up`, each
arm's server was stopped by PID and started again from the run's own environment file with one
more `--require`: a scratch instrument that, on every `data-loaded`, logged the order of
`ctx.ddata.treatments`, the records whose `mills` is not a number, the last carb entry in array
order, the newest carb entry by `mills`, and the `cob.lastCarbs` the properties then carried. The
server restart was done the same way. The harness code was not changed; T1 was not analysed as a
soak.

| arm | reloads with a carb entry | last carb in array order is not the newest | of those, with records lacking `mills` | without | `cob.lastCarbs` = last carb in array order |
|---|---:|---:|---:|---:|---:|
| A 15.0.8, before the restart | 914 | 828 | 828 | 0 | 914 of 914 |
| A 15.0.8, after the restart | 525 | 497 | 497 | 0 | 524 of 524 |
| B 699eb5fa, before the restart | 912 | 827 | 827 | 0 | 912 of 912 |

- Every record without `mills` was an AndroidAPS Temp Basal or SMB written through v3 (up to 140
  at once). The last column leaves out reloads where the properties had not yet been rebuilt.
- The wrong entry was named on both arms before the restart too, in step with each other, so the
  key-set comparison saw nothing there. After the restart the arms' arrays differ and so do their
  answers.
- A scratch check before T1 found the ordering correct in a simpler case with only v1 writes, and
  a fresh boot on R29's kept databases (after the run) sorted both arms correctly, with the newest
  carb entry last.

**Why the two arms are out of phase.** The arms hold different sets of v3 records: 15.0.8 keeps the
AndroidAPS records that were soft-deleted, and 699eb5fa removes them (BF-135). With a different
array, the undefined sort puts a different carb entry last. The traffic is identical in every
run, so the result is the same tick for tick in run 018's R24 and R29.

**Why the harness sees it only after the restart.** Before the restart both arms name the same
wrong entry (T1, above), so there is no difference to report. The first load after the restart
fetches every record from MongoDB with `mills`; later v3 writes add records without it, and from
then on the two arms' arrays differ (15.0.8 also holds the soft-deleted AndroidAPS records). In a
compressed run each record is dated hours or days in the past, so after the first load the
dataloader's incremental query never fetches new records from MongoDB; they reach memory only
through the cache.

**What this is and is not.** It is BF-133's mechanism, live on 15.0.8 and on the candidate alike,
and not a 15.0.9 regression.

**A consequence beyond the detail line, found while tracing it (candidate new finding, not
filed).** `lib/plugins/iob.js` counts a treatment only when `treatment.mills <= time`, and
`cob.js` only when `treatment.mills < time`, so a treatment held without `mills` counts in neither.
In real time the next incremental load normally fetches a new v3 record from MongoDB with `mills`
and replaces the cached copy. It does not when the record is dated further in the past than that
load's window, as a late AndroidAPS upload is. A scratch reproduction (fresh test database,
synthetic records, Node 22.23.2, MongoDB 7.0.43) showed this on both trees, with the same numbers:

- Once the server held enough treatments to take its incremental load path, a v3 bolus and a v3
  carb entry dated in the past left the server's treatment-based IOB and COB unchanged.
- A v1 bolus of the same age was counted, and so was a v3 bolus dated now.
- After a server restart all of them were counted.
- With only a few treatments held, every load is a full load, and the late v3 records were
  counted at once. That is why a small test does not show it.

The server prefers a current IOB or COB reported in device status, so an AndroidAPS site that is
uploading its own device status would not show this in the pill. It affects the values the server
derives from treatments (`/api/v2/properties` when no device status is current, and whatever reads
them). What the browser computes from the same records was not checked.

## Why `bgnow` was missing once (run 018's R24, not reproduced in R29)

In run 018's R24, arm A's `/api/v2/properties` `bgnow` was empty at tick 282 and again 3 s later,
while arm B had a reading. `lib/plugins/bgnow.js`, the dataloader's two-day entries window and the
reload debounce (`UPDATE_DEBOUNCE_WAIT` 1000 ms, `UPDATE_MAX_WAIT` 5000 ms in
`lib/server/bootevent.js`) are the same on both trees.

- **Tick 282 is the first reading inside the two-day window.** In a 72 h compressed run each
  reading is dated in the past and ages into the window during the run. Tick 282's reading was
  47 h 57 min old when it was written; tick 281's was just over 48 h. Before tick 282 both arms'
  `bgnow` is empty (no difference).
- **The property is rebuilt only after a reload finishes.** A write requests a reload through a
  debounce whose data is promised within 5 s, and a reload already running queues the next one.
  The harness asks 60 ms after the write and again 3 s later, both inside that 5 s.
- R29 ran the same traffic and showed no `bgnow` difference, and nothing in the two trees differs
  on this path. It is a timing race on the first reading to enter the window, which the harness's
  3 s re-ask does not always cover. Not a defect on either tree; not traced further.
