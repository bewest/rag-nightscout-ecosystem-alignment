    Candidates¶

    CANDIDATE-1 (BF-131, fixed (branch) e9dbb1fb): a deleted record keeps being served from memory (B only). On ab7b22d6, DELETE /api/v1/entries/<id>, /api/v1/treatments/<id> and /api/v1/devicestatus/<id> answer 200 and remove the document from MongoDB, but the server's in-memory copy keeps it:

    • GET /api/v1/entries.json?count=10 (and count=100, count=288) keeps returning the deleted reading after 35 s and after a new reading arrives; the same read with a filter (find[sgv][$gte]=0), which goes to MongoDB, does not.
    • treatments.json?count=5 and devicestatus.json?count=5 keep returning the deleted record.
    • A newly opened web page is sent the deleted treatment in its first dataUpdate (R8: 36 deleted records, some 24 minutes after the delete).
    • Websocket dbRemove of a treatment does not show it (control, same probe).
    • A (15.0.8) and dev 4f705217 do not show it, with the same probes on fresh databases.

    Mechanism: lib/server/entries.js remove() emits data-update with changes: opts.find._id after query_for(opts); on B, idForms.matchEitherForm rewrites opts.find._id in place to { $in: [<hex>, ObjectId] } (confirmed with node against B's lib/server/query.js and object-id-forms.js), so the cache's removeFromArray (o._id == id) never matches. On A the same field is left as a single id. Ablation: a copy of ab7b22d6 whose remove() passes the id as asked (branch lab/6a-soak-ablate, f76e6fd5, one file, +3/-1) passes probe-deleted-entry.js; unmodified ab7b22d6 fails it in the same session. Only entries was ablated; treatments and devicestatus were reproduced, not ablated.

    Reproduce: lab.sh up, then node tools/lab/rc-soak/probe-deleted-entry.js http://127.0.0.1:17532 <run>/secrets/api_secret (exit 1 on B, 0 on A).

    Why it matters: a treatment deleted because it was entered by mistake (a bolus or carbs) is still sent to newly opened pages and to readers of the unfiltered API, so insulin and carbs on board shown there can include it until the server restarts or the record leaves the in-memory window.

    CANDIDATE-2: /api/v2/properties cob.lastCarbs differs at one tick. Resolved below (section Candidate e9dbb1fb): the "last carbs" entry can be an older carb record on every build, 15.0.8 included; ab7b22d6 differs from 15.0.8 only in the tick at which it switches.

    R10's two findings. - parity devicestatus: ds-604 stored once on A and twice on B. The original POST was sent during the server restart at 21:17:26: A answered ECONNREFUSED (never reached), B's connection dropped mid-request (UND_ERR_SOCKET), so B's server had it.     carb-9 is a 25 g Carb Correction from 4 hours earlier, edited at tick 44 (notes: "edited 44"); carb-45 is the newest carb entry (15 g). Not from #8758 and not from dev: 15.0.8 behaves the same. lastCarbs is shown on the COB pill's detail line ("last carbs" amount and time); the COB total adds up every carb entry and is not affected by which one is picked. A candidate for the register as a defect live on 15.0.8, not a 15.0.9 regression.

The follower read carries token as a second key, so it always went to MongoDB. The direct probe used a header and count alone. lib/api/entries/index.js decides on find keys only, which is why entries.json?count=288&token=… did hit the stale copy. Harness 4 adds the header forms; on ab7b22d6 (R11) they differ from 15.0.8 in 259 reads, on e9dbb1fb (R13) in none.
