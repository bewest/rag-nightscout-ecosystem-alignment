    ID-BATCH reply lab: results, 2026-10-30¶

    Living document, last changed 2026-10-30 at 7aab61504.

    Contributor-facing. Synthetic data only. Evidence for the open questions (ii)-(vii) of the ID-BATCH design note; the maintainer decides them. Run file: results/run-2026-10-30.json; how to run it: README.md.

    • Server: cgm-remote-monitor proto/id-batch-replies at 7d81e1c1 (base feat/id-first-s5 545f941e), MongoDB 8.3.9, Node 22.23.4, booted three times: WRITE_VALIDATION off, =reject, and WRITE_IDENTIFIER=strict.
    • Clients: Loop = NightscoutKit 4ec9fd12a1 (the pin LoopWorkspace 548b332451 resolves, Package.resolved:104-109), NightscoutService 2cef4896f0, Loop c30b5c89; Trio 0b29cd5341; xDrip+ 1ed760048a; xDrip4iOS c268542e64; AndroidAPS 7e1d537d49; nightscout-connect 04102f9d26.
    • Method. Every reply below came from the real server. Loop, Trio, xDrip+ and xDrip4iOS are harnesses that reproduce each client's reply handling rule by rule, each rule cited file:line in clients.js; the client binaries were not run. nightscout-connect was run: its own Nightscout output module, cycle by cycle (connect-run.js). Each client re-sends what its code re-sends, for up to 3 cycles; then MongoDB is read for how many records each item left. Two full runs gave identical tables.
    • "Forever" means: the reply to the re-send is the same every time, and the client's code has no attempt counter or age limit on that path.

    Findings, by open question¶

    (ii) How a client asks: header, query parameter or Accept¶

    • Header and query parameter gave the same reply on every path measured, with and without the .json suffix. cgm-remote-monitor writes no access log, so neither shows in the server's own output; a query parameter would show in a proxy's or host's request log, which the lab does not have.
    • An Accept opt-in never reaches the route on a .json path. lib/middleware/express-extension-to-accept.js:30-36 replaces Accept with the extension's type before routing. On /api/v1/treatments.json the vendor type is dropped silently and the client gets today's array; on /api/v1/treatments/ it works and the reply carries the vendor content type. Trio (NightscoutAPI.swift:15-16) and nightscout-connect (lib/outputs/nightscout.js:63, :109, :161, :222) post to .json paths; Loop (NightscoutClient.swift:13-17), xDrip4iOS (NightscoutSyncManager.swift:54, :58) and xDrip+ (NightscoutUploader.java:130, :145) do not. An Accept form would need the route to read the original header (req.extToAccept.accept).
    • NightscoutKit already sets Accept: application/json on every call (NightscoutClient.swift:523), so Accept is the one form that shares a field with a header a client already sends.
    • The prototype answers a malformed opt-in with 400 before writing. A client that sets the opt-in once and gets it wrong would fail every upload in either form.

    (iii) Profile's update permission per item¶

    Server side only (not run through the client harnesses):

    • Today and profile=whole: 401, nothing written; the new profile in the same batch is not stored.
    • profile=per-item: 200; the changing re-send has a refused slot (403), the new profile is stored.
    • For Loop, the one surveyed client posting profile arrays (NightscoutClient.swift:398-408), the 401 is a failure re-tried on every trigger, forever; the per-item 200 is a success, and the refused change is recorded as "NA" and not re-tried.

    (iv) The preBolus derived record in the reply¶

    • Today (the same as prebolus=keep) the reply has one element more than the request. A count-checking client (Loop, NightscoutClient.swift:488-491) fails it and re-sends the whole batch forever, with later records waiting; each re-send is matched on the server, so nothing is stored twice (rr).
    • nightscout-connect, run: the derived record's later created_at moves the treatments bookmark past records not yet sent. A record 5 minutes after the preBolus item, available at the next cycle, is never sent (SSL today and with keep; SSS with omit). nightscout-connect takes the bookmark from the newest created_at in the reply (lib/outputs/nightscout.js:247-253, :282). Its Glooko source sets preBolus (lib/sources/glooko/convert.js:58), so this is a live path.
    • prebolus=omit removes both effects. No surveyed client reads the derived record's _id.

    (v) E11000 on a sent _id: 409 or 5xx¶

    • Today and duplicate-id=5xx: 500 (description.code 11000). The ordered write keeps item 0 and stops there. Every client re-sends the whole batch: Loop forever, later records waiting; Trio while within a day; xDrip+ until the queue entry is 7 days old; xDrip4iOS from its bookmark on every sync; nightscout-connect on every cycle. Item 2, a valid record, is never stored by any of them (rRR).
    • duplicate-id=409: 200; item 1 refused with 409, items 0 and 2 stored. Every client counts item 1 uploaded (SLS): Loop as "NA", the others by status.
    • The 409 variant writes the batch's other items in a further call from the route. Landing it means R5's continuation in the step.
    • Senders: xDrip4iOS sends _id on calibration entries (Calibration+Nightscout.swift:17, :36). An entry at a stored entry's time under another _id (E-sametime) does not fail on this base: the step matches it by time and type and answers the stored _id, so xDrip4iOS's "500 with code 66 is success" path (NightscoutSyncManager.swift:1692-1708) is not reached.

    (vi) acknowledged, or unchanged with a reason¶

    • On this base the case is a devicestatus re-sent with its stored _id, which the step answers refused "already stored" (lib/storage/write-intent.js:1121-1125).
    • Kept as a refusal (ack-refused): the slot loses _id and Loop records "NA" for a record that is stored. Nothing is lost (Loop caches no devicestatus ids), but the reply misstates the outcome.
    • A re-send on its own is then an all-refused batch: 400. The red control below measured it: with the slots shape on by default, 17 devicestatus re-send cells go from 200 [1 _id] to 400 [1 no _id] (for example devicestatus v1 resend-hex). Loop would re-send that devicestatus forever. So keeping the step's refused word for a re-send makes R3's "every item refused: 400" fire on a record that is stored.
    • word and unchanged: the slot keeps the stored _id, byte-identical for every client; they differ only in items[].outcome. No surveyed client reads items[], so the choice has no client-visible effect today; it decides what a future reader of items[] can tell apart (a change not applied, against nothing to change).
    • nightscout-connect never re-sends a stored devicestatus: its own bookmark filter drops it first (lib/outputs/nightscout.js:117-160).

    (vii) Refusals that status-only clients never see¶

    Under WRITE_VALIDATION=reject (T-mixed) and under strict-on-v1 (T-strict, E-strict), a refused item in a 200:

    client refused item counted uploaded? trace on the client
    Loop yes, as "NA" (NightscoutClient.swift:493-503) none; later edits and deletes of that record are skipped too, because "NA" is never sent (:83, :112, :140)
    Trio yes: 2xx marks the chunk (NightscoutManager.swift:1096-1110; Temporary Targets :1258-1275) none. Trio sends Temporary Targets, so this is the live case for reject
    xDrip+ entries: yes, by status. Treatments are not batched none
    xDrip4iOS no: the slot has no _id, matches nothing, and the item is re-sent on every sync while among the latest 50 treatments. Re-sent alone it is an all-refused batch and gets 400 the item never completes
    nightscout-connect (run) yes: the refused slot echoes created_at, and the bookmark passes it none
    • Every item refused (T-allrefused; D-badid today): 400; every client re-sends forever or until its window closes. Nothing is lost and nothing is stored.
    • A refused slot is final for every client except xDrip4iOS: right for a refusal a retry cannot fix, and a dropped record with no trace on the client.

    Strict on v1 (ID-STRICT-V1)¶

    • Today strict on v1 treats the invalid identifier as absent: the record is stored without it (SSS).
    • With per-item replies strict refuses the record: every client except xDrip4iOS drops it (SLS). The refusal is about an identifier the client chose, and what is lost is the record's data (carbs, a glucose value).

    The shapes as a default¶

    • items (the object reply) as a default breaks Loop (not an array) and xDrip4iOS (counted failed): both re-send forever. Safe only as an opt-in.
    • 207 breaks Loop (not 200): forever. Trio, xDrip4iOS and nightscout-connect accept it.
    • slots as a default gives the same client outcomes as today's treatments-under-reject reply in every measured case, and turns devicestatus's whole-batch 400 for one bad _id (D-badid today: forever, for Loop and nightscout-connect) into one refused slot.

    Corrections to the design note's §2¶

    • xDrip+ treatments are not a v1 batch: inserts go into the upsert list ("always use singular upserts", NightscoutUploader.java:803-806) and are PUT one object at a time (:880-889); the POST of insert_array (:859-863) is never reached.
    • The NightscoutKit pin inside LoopWorkspace is the standalone checkout (Package.resolved:104-109 names 4ec9fd12a1).
    • Loop's retry has no bound: the query anchor moves only on success (RemoteDataServicesManager.swift:278-287), and a failed type is re-tried on every later trigger (:182-183).
    • nightscout-connect's preBolus uncertainty is resolved: the derived record does move the bookmark past unsent data (iv).

    Prototype checks¶

    • Default replies unchanged.
